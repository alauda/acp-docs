# Observability

Use platform status, component health checks, metrics, logs and an application
request together. A `Running` pod is not proof that a workload received an
identity.

## Check the installation

```shell
ac get moduleinfo -A
ac get apprelease -A
ac get pods -n spire-server -o wide
ac get pods -n spire-system -o wide
ac get pvc -n spire-server
ac get csidriver csi.spiffe.io
ac get clusterspiffeid -A
```

A healthy installation should show:

- ModuleInfo and AppReleases in a successful state.
- SPIRE Server and Agent pods Ready.
- Controller Manager running with the Server release.
- SPIFFE CSI Driver Ready on the required nodes.
- The Server PVC in `Bound` state.
- `csi.spiffe.io` registered with ephemeral volume support.
- Required `ClusterSPIFFEID` objects selecting the expected pods.

Check `podsSelected`, `entriesToSet` and entry errors in each
`ClusterSPIFFEID` status. A selector that selects no pods cannot issue the
expected workload identity.

## Health checks

The validated deployment exposes health endpoints for the Server, Agent,
Controller Manager and CSI Driver. Use a temporary port-forward with the
actual pod names:

```shell
ac port-forward -n spire-server pod/spire-server-0 38080:8080 38082:8082 39988:9988
ac port-forward -n spire-system pod/<agent-pod> 39982:9982 39989:9988
ac port-forward -n spire-system pod/<csi-pod> 39809:9809
```

In another terminal, query the endpoints:

```shell
curl -fsS http://127.0.0.1:38080/live
curl -fsS http://127.0.0.1:38080/ready
curl -fsS http://127.0.0.1:39982/live
curl -fsS http://127.0.0.1:39982/ready
curl -fsS http://127.0.0.1:38082/healthz
curl -fsS http://127.0.0.1:38082/readyz
curl -fsS http://127.0.0.1:39809/healthz
```

Expected responses are a healthy JSON object from the Server and Agent and
`ok` from the CSI Driver and Controller Manager endpoints.

## Metrics

The validated baseline exposes metrics for the Controller Manager, Server and
Agent. The available metric set depends on the chart configuration and platform
collector. Useful groups include:

- Controller Manager certificate watcher, controller worker and entry failure
  metrics.
- SPIRE Server service and Go runtime metrics.
- SPIRE Agent service, renewal and Go runtime metrics.

Example metrics include `certwatcher_read_certificate_total`,
`cluster_static_entry_failures` and
`controller_runtime_active_workers`. Use the metrics endpoint exposed by
the component and confirm that the target is being collected before creating
an alert.

## Logs

```shell
ac logs -n spire-server pod/spire-server-0 -c spire-server --tail=120
ac logs -n spire-system pod/<agent-pod> -c spire-agent --tail=120
ac logs -n spire-system pod/<csi-pod> --tail=120
ac logs -n <workload-namespace> pod/<workload-pod> -c <application-or-proxy> --tail=120
```

Healthy signals include `Connected to SQL database`,
`Starting Workload and SDS APIs`, `Renewing X509-SVID` and
`Volume is healthy`. Correlate these messages with the workload identity
and an actual application request.

## Alerting recommendations

Configure platform alerts for:

- AppRelease failure or loss of readiness.
- Server, Agent or CSI Driver unavailable.
- Server PVC not Bound or storage errors.
- A required `ClusterSPIFFEID` selecting no pods.
- Health endpoint failure.
- Repeated SVID acquisition, attestation, bundle or SDS errors.
- Missing renewal activity during the expected renewal window.

Use the component metrics and logs as alert evidence; do not use pod status as
the only alert condition.
