# Troubleshooting

Start with the platform installation status, then check component health, the
registration selector, the Agent socket and the application result. Always
collect the expected and actual result before changing resources.

## Installation problems

| Symptom | Checks | Action |
| --- | --- | --- |
| ModuleInfo or AppRelease is not successful | `ac get moduleinfo -A` and `ac get apprelease -A`; inspect the status message. | Fix the reported configuration or chart error, then wait for reconciliation. |
| Strict validation fails | Check the trust domain, cluster name and CA subject values. | Replace chart example placeholders with real values. The plugin defaults already pass this check. |
| Image pull fails | Check the failed pod events and the image reference recorded by the AppRelease. | Restore registry access or use the image supplied by the same ACP release package. Do not mix component images from another release. |
| Server PVC is `Pending` | Check `ac get storageclass` and `ac get pvc -n spire-server`. | Select an existing StorageClass with available capacity and recreate or update the installation. |
| SPIRE pod is not Ready | Check `ac get pods -n spire-server`, `ac get pods -n spire-system` and recent events. | Resolve image, storage, permission or scheduling errors before deploying workloads. |
| CSI Driver is not registered | Check `ac get csidriver csi.spiffe.io` and CSI Driver logs. | Restore the CSI Driver on the target nodes before creating CSI volumes. |

## Workload identity problems

| Symptom | Checks | Action |
| --- | --- | --- |
| `podsSelected=0` or `entriesToSet=0` | Compare the `ClusterSPIFFEID` namespace selector and pod selector with the actual namespace labels and pod labels. | Correct the selector, then wait for reconciliation and recreate the workload. |
| Workload has no SVID | Check the ServiceAccount, `className`, Agent status and Controller Manager logs. | Use the ServiceAccount named by the pod and the class used by the installed Controller Manager. |
| Workload cannot connect to the Agent socket | Check the CSI volume, mount path and `SPIFFE_ENDPOINT_SOCKET` value. | Ensure the driver is `csi.spiffe.io`, the volume is read-only and the socket path is identical in the mount and application configuration. |
| Workload init or helper cannot fetch an SVID | Check Agent logs and the workload's socket mount. | Restore the Agent and CSI path, then restart the workload. |
| SDS reports that the workload is unauthorized | Check the workload ServiceAccount, pod UID/labels, `ClusterSPIFFEID` status and Agent attestation logs. | Fix the selector or attestation input; do not use a shared ServiceAccount to bypass it. |
| The peer is rejected unexpectedly | Check the peer SPIFFE ID, trust domain and authorization rule. | Authorize the complete expected SPIFFE ID and create a new connection. |

## Rotation and recovery problems

| Symptom | Checks | Action |
| --- | --- | --- |
| SVID renewal is not visible | Check the configured TTL, Agent logs and the time since the last renewal. | Use a disposable test identity with a short TTL and verify a new connection after the renewal window. |
| SVID renews but the application still fails | Check whether the SDK, proxy or file-based TLS configuration reloads the new identity. | Use the SDK update mechanism, SDS or a file watcher, then create a new TLS connection. |
| Server is Ready but new workloads fail | Check Server registration entries and Agent authorization state. | Restart the Agent, restart the workload and rerun the identity test. |
| Trust bundle cannot be parsed | Inspect the bundle ConfigMap and Agent logs. | Restore the valid bundle, restart the Agent and retest the workload. |
| A component restart leaves workloads unavailable | Check the component health endpoint, pod events and workload socket. | Wait for the component rollout, restart A/B and verify a new mTLS connection. |

## Fault evidence

For every incident, record:

1. The operation and the affected namespace/resource.
2. The expected behavior and the actual behavior.
3. Resource status and recent events.
4. Server, Agent, Controller Manager, CSI and workload logs.
5. The recovery action and the post-recovery application result.

A healthy pod status is only one input. A successful identity request or mTLS
connection is required to confirm workload functionality.

## Quick runbook

For a daily or pre-release check, run the following sequence:

1. Check ModuleInfo, AppRelease, Server, Agent, CSI Driver and PVC status.
2. Check required `ClusterSPIFFEID` selector results.
3. Query health endpoints and review recent Server, Agent and CSI logs.
4. Run a new SDK identity request or the A/B mTLS check.
5. If a check fails, preserve the status and logs before applying a recovery
   action, then repeat the application-level check.
