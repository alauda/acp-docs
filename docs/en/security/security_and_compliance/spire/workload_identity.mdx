# Workload Identity

A workload receives an SVID only after the SPIRE Agent can identify both the
node and the workload. In ACP, workload identity is controlled by three inputs:

1. The workload's namespace and labels.
2. Its ServiceAccount.
3. A matching `ClusterSPIFFEID` selector and identity template.

## Choose a consumption path

| Path | How the workload obtains identity | Use this path when |
| --- | --- | --- |
| Workload API and SDK | The application connects to the Agent socket and requests an X.509-SVID and trust bundle. | The application can use a SPIFFE SDK or an equivalent Workload API client. |
| CSI-mounted socket | The CSI Driver exposes the Agent socket through an ephemeral volume; the application or a proxy uses the socket. | A sidecar, proxy or existing application expects a local socket. |

Both paths use the same registration, attestation and trust-domain rules.

## Register a workload

The Controller Manager converts a `ClusterSPIFFEID` into SPIRE registration
entries. Set `className` to the class used by the installed Controller Manager.
The current ACP plugin installation uses `cpaas-system-spire`; check an
installed `ClusterSPIFFEID` if the release uses a different class.

The following example gives every pod with the selected label in the selected
namespace an identity:

```yaml
apiVersion: spire.spiffe.io/v1alpha1
kind: ClusterSPIFFEID
metadata:
  name: example-workload
spec:
  className: cpaas-system-spire
  namespaceSelector:
    matchLabels:
      kubernetes.io/metadata.name: example-workload
  podSelector:
    matchLabels:
      app.kubernetes.io/name: example-workload
  spiffeIDTemplate: spiffe://{{ .TrustDomain }}/ns/{{ .PodMeta.Namespace }}/sa/{{ .PodSpec.ServiceAccountName }}
```

The default identity template is:

```text
spiffe://<trust-domain>/ns/<namespace>/sa/<service-account>
```

The chart's default identity rule is a fallback: a more specific
`ClusterSPIFFEID` selector takes precedence for a matching workload. Review
the installed rules before relying on the default rule in a shared cluster.

Use a custom template only when the application needs a stable identity
different from the default. Use narrow namespace and pod selectors. A broad
selector can give the same identity rule to more pods than intended.

Complete the workload configuration below first, then apply the registration
after the namespace and workload labels exist:

```shell
ac apply -f cluster-spiffeid.yaml
ac get clusterspiffeid example-workload -o yaml
```

The status should show that the expected pod was selected and an entry was
created. If `podsSelected=0` or `entriesToSet=0`, check the selectors before
checking the application.

## Configure the workload

Create the namespace before the ServiceAccount and workload. The namespace
name must match the `namespaceSelector` in the registration.

```shell
ac create namespace example-workload
```

Create a dedicated ServiceAccount:

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: example-workload
  namespace: example-workload
```

Save the manifest and apply it to the target cluster:

```shell
ac apply -f service-account.yaml
```

Set that ServiceAccount and the matching label in the workload Pod template.
For a CSI consumer, add the following fields under a Deployment's `spec`:

```yaml
spec:
  template:
    metadata:
      labels:
        app.kubernetes.io/name: example-workload
    spec:
      serviceAccountName: example-workload
      containers:
      - name: application
        image: <registry>/<image>:<tag>
        env:
        - name: SPIFFE_ENDPOINT_SOCKET
          value: unix:///spiffe-workload-api/spire-agent.sock
        volumeMounts:
        - name: spiffe-workload-api
          mountPath: /spiffe-workload-api
          readOnly: true
      volumes:
      - name: spiffe-workload-api
        csi:
          driver: csi.spiffe.io
          readOnly: true
```

Replace the image placeholder with the application image and merge this block
into the workload's existing Deployment. Do not apply this fragment as a
standalone resource.

The pod label `app.kubernetes.io/name=example-workload` must match the
`ClusterSPIFFEID` selector. The namespace must also match its namespace
selector. The `csi.spiffe.io` volume is ephemeral and exposes the Workload API
socket; it does not create a Kubernetes Secret containing the workload private
key.

## Workload API and SDK

An SDK consumer connects to the socket and requests the current X.509-SVID and
trust bundle. Configure the SDK with the socket address used by the workload,
for example:

```shell
SPIFFE_ENDPOINT_SOCKET=unix:///spiffe-workload-api/spire-agent.sock
```

The application should:

- Keep the SDK-managed identity source open while it needs credentials.
- Use the SDK's update or callback mechanism when the SVID changes.
- Create new TLS connections with the current SVID.
- Close the identity source during application shutdown.

ACP does not inject an SDK into the application. The application owner must
add `go-spiffe` or another compatible Workload API client and use the returned
SVID in its own TLS configuration.

The validated ACP SDK path uses a Workload API client based on `go-spiffe` or an
equivalent SDK. A successful pod `Running` state alone does not prove that
the application obtained an SVID.

## CSI and proxy path

A proxy such as Envoy can use the CSI-mounted socket through the Agent SDS
endpoint. The proxy configuration must use the same socket path as the volume
mount and must verify the peer SPIFFE ID.

The CSI Driver does not automatically configure application TLS or application
authorization. The application or proxy remains responsible for choosing the
peer identity it accepts.

## Verify workload identity

Use these checks after deploying the workload:

```shell
ac get clusterspiffeid example-workload -o yaml
ac get pods -n example-workload -l app.kubernetes.io/name=example-workload -o wide
ac get csidriver csi.spiffe.io
```

Then verify an application-level result, such as an SDK call that returns an
SVID or a successful mTLS connection. Do not treat a mounted socket, a
Running pod or a registration object alone as proof of successful identity
consumption.

## Certificate refresh

SVIDs are short-lived and are refreshed by SPIRE. An SDK should use its update
callback or source refresh mechanism. An application that reads certificate
files through a helper must watch for file changes and reload its TLS context.

An already-open TLS connection does not change its peer certificate in the
middle of a session. Establish a new connection after a refresh when the new
SVID must be used.

## Fixed A/B/C example

The repeatable ACP mTLS example uses separate ServiceAccounts and selectors:

| Workload | Namespace | ServiceAccount | SPIFFE ID |
| --- | --- | --- | --- |
| A | `acp-55264-mtls` | `acp-55264-a` | `spiffe://demo.org/acp/55264/a` |
| B | `acp-55264-mtls` | `acp-55264-b` | `spiffe://demo.org/acp/55264/b` |
| C | `acp-55264-mtls` | `acp-55264-c` | `spiffe://demo.org/acp/55264/c` |

Use the fixed manifest and verification script from the same ACP release
validation package when reproducing this example. Keep the trust domain,
selectors, ServiceAccounts, socket paths and peer authorization rules
unchanged.

## Do not use

- Manually copying certificates or private keys between pods.
- A Kubernetes Secret to distribute a workload private key.
- A shared ServiceAccount or broad selector to bypass an attestation failure.
- An existing TLS connection as proof that a newly rotated SVID is active.
