# Architecture

## Identity flow

The ACP SPIRE integration follows this sequence:

1. The SPIRE Agent verifies the ACP node with the Kubernetes PSAT node attestor
   using a projected service-account token.
2. The Controller Manager matches the workload namespace and pod labels against
   `ClusterSPIFFEID` selectors and synchronizes the registration entry.
3. The Agent performs workload attestation using the workload's Kubernetes
   attributes and requests the matching entry from the SPIRE Server.
4. The SPIRE Server issues an SVID and trust bundle to the attested workload.
5. The workload obtains the identity through the Workload API socket.
6. The application or proxy uses the identity to establish mTLS and verifies
   the peer SPIFFE ID.

   ```text
   Kubernetes node
     SPIRE Agent -- node/workload attestation --> SPIRE Server
          ^                                      | registration entries
          |                                      v
     Workload API socket <-- SVID + bundle -- SPIRE Server
          ^
          |
     Application SDK or proxy
     SPIFFE CSI Driver can expose the socket to the pod
   ```

## Component relationships

| Area | ACP component | Result |
| --- | --- | --- |
| Registration | Controller Manager and `ClusterSPIFFEID` | Matching workloads receive registration entries. |
| Node verification | SPIRE Agent and Kubernetes attestor | Only an attested node can serve workload identity. |
| Workload verification | Kubernetes workload attestor | The workload's attributes are checked before an SVID is issued. |
| Identity delivery | Agent Workload API | The workload obtains an SVID and trust bundle locally. |
| Socket delivery | SPIFFE CSI Driver | A pod receives an ephemeral mount for the Workload API socket. |
| Peer authorization | Application, SDK or proxy | The expected peer SPIFFE ID is accepted and other IDs can be rejected. |

## SPIFFE ID construction

The default workload identity template is:

```text
spiffe://<trust-domain>/ns/<namespace>/sa/<service-account>
```

A custom `ClusterSPIFFEID` can define a narrower selector and an explicit ID.
For example, the ACP mTLS validation uses:

```text
spiffe://demo.org/acp/55264/a
spiffe://demo.org/acp/55264/b
spiffe://demo.org/acp/55264/c
```

The SPIFFE ID alone is not an authorization policy. The registration selector
must match the intended workload, and the receiving application or proxy must
verify the expected peer ID.

## Socket paths

The node-local Agent socket is:

```text
/run/spire/agent-sockets/spire-agent.sock
```

The path exposed inside a workload pod is selected by its CSI volume and mount
configuration. The socket path in the SDK or proxy configuration must match
the mount path inside the pod.

## ACP deployment topology

The ACP ModulePlugin creates one AppRelease for the SPIRE CRDs and one for the
main SPIRE chart. The main chart deploys the Server, Controller Manager, Agent,
CSI Driver and OIDC Discovery Provider. Workloads are registered separately by
creating `ClusterSPIFFEID` resources with selectors that match their labels and
ServiceAccounts.
