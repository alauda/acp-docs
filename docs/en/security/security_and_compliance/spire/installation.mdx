# Installation

Install SPIRE through **Administrator > Marketplace > Cluster Plugins**. The
plugin is published in the global cluster and can be installed on the target
cluster selected in the installation form.

## Prerequisites

- Permission to install a Cluster Plugin.
- SPIRE is available in the ACP Marketplace.
- An existing StorageClass that can provision the SPIRE Server datastore.
- A test or maintenance window for the initial installation.
- No workload should depend on SPIRE until installation verification passes.

Check the available StorageClasses before opening the installation form:

```shell
ac get storageclass
```

The StorageClass is environment-specific. ACP does not assign a universal
StorageClass default.

## Install from the console

1. Open **Administrator > Marketplace > Cluster Plugins**.
2. Select the target cluster.
3. Find the SPIRE plugin and click **Install**.
4. Keep the default values unless the environment requires custom values.
5. Select an existing StorageClass for the SPIRE Server datastore.
6. Start the installation and wait for the ModuleInfo and AppRelease resources
   to report success.

The plugin creates one AppRelease for the SPIRE CRDs and one for the main SPIRE
chart. Both must be ready before a workload can obtain an identity.

## Configuration values

The plugin form uses these defaults:

| Parameter | Default | Purpose |
| --- | --- | --- |
| `clusterName` | `dce-cluster` | Name used by SPIRE to identify the cluster. |
| `trustDomain` | `demo.org` | Root of the SPIFFE ID namespace. |
| `caSubject.country` | `CN` | Country field of the SPIRE CA subject. |
| `caSubject.organization` | `Demo` | Organization field of the SPIRE CA subject. |
| `caSubject.commonName` | `demo.org` | Common name of the SPIRE CA. |
| `persistence.storageClass` | Environment-provided | StorageClass for the Server datastore. |

`caSubject.organization` describes the SPIRE CA subject. It does not
restrict the organization value used by a workload or application. Custom
values are allowed, but do not leave the chart's example placeholder values in
a strict-mode deployment. In particular, do not use `example-cluster`,
`example.org`, `Example` or `ARPA` for the cluster name, trust domain/CA common
name, organization or CA country. If the trust domain changes, update every workload's
SPIFFE ID and peer authorization rule to use the new trust domain.

## Install from YAML

For an automated installation, create the following `ModuleInfo` in the global
cluster. The version must be the SPIRE version currently published in the ACP
Marketplace.

```yaml
apiVersion: cluster.alauda.io/v1alpha1
kind: ModuleInfo
metadata:
  name: spire-install
  labels:
    cpaas.io/cluster-name: <target-cluster>
    cpaas.io/module-name: spire
    cpaas.io/module-type: plugin
spec:
  version: <published-spire-version>
  config:
    clusterName: dce-cluster
    trustDomain: demo.org
    caSubject:
      country: CN
      organization: Demo
      commonName: demo.org
    persistence:
      storageClass: <existing-storage-class>
```

The resource must be created in the global cluster. The
`cpaas.io/cluster-name` label selects the installation target; it does not
change where the `ModuleInfo` resource is created.

## Verify installation

Run the following checks after installation:

```shell
ac get moduleinfo -A
ac get apprelease -A
ac get pods -n spire-server -o wide
ac get pods -n spire-system -o wide
ac get pvc -n spire-server
ac get csidriver csi.spiffe.io
ac get clusterspiffeid -A
```

The installation is ready for workloads when the ModuleInfo and AppReleases
report success, the Server and Agent pods are Ready, the Controller Manager is
running with the Server, the CSI Driver is Ready, the Server PVC is Bound, and
`csi.spiffe.io` is registered.

If an AppRelease is not successful, inspect its status before inspecting
workload pods. If the PVC is Pending, fix the StorageClass or storage capacity.
If strict validation fails, replace the placeholder value named in the error.
Continue with [Workload Identity](./workload_identity.mdx) only after the
components are Ready.

## Uninstall preflight

Uninstalling SPIRE invalidates identities for workloads that depend on the
Workload API or CSI socket. Before uninstalling:

1. Stop or migrate all SPIRE-consuming workloads.
2. Back up the SPIRE Server datastore.
3. Check the Server PVC and understand whether the environment retains it.
4. Remove the plugin in an isolated test or maintenance window.
5. Verify that no dependent workload is still attempting mTLS.
