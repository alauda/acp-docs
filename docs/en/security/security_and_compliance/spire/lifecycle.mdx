# Lifecycle and Recovery

This page describes the supported operational checks for the ACP SPIRE
installation. Perform destructive operations only in a disposable environment
or an approved maintenance window.

## SVID rotation

SVIDs and X.509 certificates are short-lived. SPIRE refreshes them through the
Workload API and SDS. Applications must consume the updated identity through
their SDK, proxy or file-reload mechanism.

To validate rotation:

1. Create a test `ClusterSPIFFEID` with a short `spec.ttl`, such as `2m`.
2. Restart the matching test workloads.
3. Verify the initial A-to-B mTLS connection.
4. Wait for the renewal window.
5. Create a new A-to-B connection.
6. Verify Agent or helper renewal logs and the new connection result.
7. Restore the original TTL after the test.

The ACP validation uses the unified recovery verifier with a short test TTL. Do
not shorten the TTL of a production identity only to reproduce the test.

## Component restart recovery

Restart each component separately. Wait for its rollout to complete, restart
the A/B workloads, and run the mTLS validation after each restart:

```shell
ac rollout restart statefulset/spire-server -n spire-server
ac rollout status statefulset/spire-server -n spire-server

ac rollout restart daemonset/spire-agent -n spire-system
ac rollout status daemonset/spire-agent -n spire-system

ac rollout restart daemonset/spire-spiffe-csi-driver -n spire-system
ac rollout status daemonset/spire-spiffe-csi-driver -n spire-system
```

The expected result after each component restart is that newly started A/B
workloads establish mTLS successfully and the unauthorized C workload remains
rejected.

## Server persistence and recovery

The Server datastore is stored on its PVC. The following sequence is the ACP
validation procedure:

1. Stop the SPIRE Server before copying the datastore.
2. Back up the SQLite datastore and run `PRAGMA integrity_check`.
3. Restore the datastore to the Server PVC in an isolated maintenance window.
4. Start the Server and confirm its health checks.
5. Restart the Agent so it re-attests and refreshes its authorization state.
6. Restart A/B/C and verify A-to-B success and C rejection.

A Server `Ready` state alone does not prove that new workload requests are
usable. Always perform the Agent restart and application-level test after
restoring the datastore.

The ACP chart does not provide an automatic backup service. Integrate the
datastore with the approved platform backup process for production and test a
restore procedure before relying on it.

## Lifecycle operations

The documented lifecycle operations are ModulePlugin installation, SVID
rotation, component restart recovery, Server datastore backup and restore, and
controlled uninstall. Review any release change and test it in a disposable
environment before applying it to a cluster with SPIRE consumers.

For an uninstall:

1. Stop or migrate workloads using the Workload API, CSI socket or SPIRE-based
   mTLS.
2. Back up the Server datastore.
3. Record the Server PVC and the identities/registration resources that must be
   recreated.
4. Remove the SPIRE plugin in a maintenance window.
5. Confirm that no dependent workload is still attempting to obtain an identity.

Uninstall can delete or orphan resources according to the ACP and chart cleanup
behavior. This release does not guarantee PVC or registration-data retention
after uninstall.
