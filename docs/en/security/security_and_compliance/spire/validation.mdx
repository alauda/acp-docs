# Validation

Use this page to verify that the ACP SPIRE installation provides usable
workload identity, not only Ready pods. Run the checks in a test namespace
before allowing business workloads to depend on SPIRE.

## Before you start

Confirm the installation first:

```shell
ac get moduleinfo -A
ac get apprelease -A
ac get pods -n spire-server -o wide
ac get pods -n spire-system -o wide
ac get pvc -n spire-server
ac get csidriver csi.spiffe.io
```

Continue only when the plugin and AppReleases report success, the Server and
Agent are Ready, the CSI Driver is Ready, the Server PVC is Bound, and
`csi.spiffe.io` is registered.

## Verify a workload identity

For an SDK consumer:

1. Create its ServiceAccount and `ClusterSPIFFEID`.
2. Deploy the workload with the matching namespace, labels and ServiceAccount.
3. Configure the SDK to use the Workload API socket.
4. Start a new SDK request for an X.509-SVID.
5. Confirm that the returned SPIFFE ID and trust domain are the expected values.

For a CSI consumer:

1. Add an ephemeral volume using the `csi.spiffe.io` driver.
2. Mount the volume at the path used by the application or proxy.
3. Configure the application or proxy to use the mounted Workload API socket.
4. Start a new identity request or TLS connection.
5. Confirm that the connection uses the expected SPIFFE ID.

A mounted socket or a Running pod is not enough. The test must show an SVID
request or a successful application-level TLS connection.

## Verify A/B/C mTLS

The ACP reference test uses three workloads:

| Workload | Expected result |
| --- | --- |
| A | Establishes mTLS to B. |
| B | Accepts A's exact SPIFFE ID and records the received identity. |
| C | Uses a different identity and is rejected by B. |

Use the fixed A/B/C manifest, startup notes and verification script supplied
with the ACP release validation package:

```shell
export AC_CMD=ac
export NAMESPACE=acp-55264-mtls
ac apply -f acp-55264-manifests.yaml
bash acp-55264-verify.sh
```

The verification is successful only when:

- A sends a test payload and B receives it over mTLS.
- B records A's exact SPIFFE URI SAN.
- C's connection is rejected.
- C's payload does not reach B.
- No manually copied certificate or workload private key in a Kubernetes Secret
  is used.

## Verify rotation and recovery

Use the unified validation script from the ACP release validation package:

```shell
KUBECONFIG=<target-kubeconfig> \
  TTL_WAIT_SECONDS=75 \
  bash acp-55265-verify-recovery.sh
```

The script verifies:

- A/B mTLS before and after a short-TTL SVID renewal.
- A/B/C recovery after separate Server, Agent and CSI Driver restarts.
- Server PVC backup and SQLite integrity validation.
- Server datastore restore, Agent re-attestation and final A/B/C mTLS.
- Component status and the application-level results for each recovery phase.

Use [Observability](./observability.mdx) for health, metrics and log checks and
[Troubleshooting](./troubleshooting.mdx) for the selector, Agent and trust
bundle fault scenarios. Those checks are part of the release gate but are not
all executed by the unified recovery script.

Record the expected result, actual result, relevant logs and recovery action for
each phase. Restore any temporary TTL or test configuration after the run.

## ACP validation checklist

| Check | Pass condition |
| --- | --- |
| Installation | ModuleInfo/AppRelease successful and core components Ready. |
| Storage | Server PVC Bound and datastore accessible. |
| Registration | Each `ClusterSPIFFEID` selects the intended pod and creates an entry. |
| SDK path | Application obtains an X.509-SVID from the Workload API. |
| CSI path | Application or proxy obtains identity through the CSI-mounted socket. |
| mTLS | A reaches B and B verifies A's exact SPIFFE ID. |
| Negative path | C cannot complete the authorized connection or deliver a payload. |
| Rotation | A new connection succeeds after SVID renewal. |
| Recovery | Server, Agent and CSI restart scenarios recover A/B communication. |
| Persistence | Backup passes integrity validation and restore recovers A/B communication. |
| Fault handling | Selector, Agent and trust bundle failures have observable symptoms and recovery steps. |
| Distribution | No manual certificate copy and no workload private key Secret. |

This checklist is the ACP release validation scope for ACP 4.4 and later. It does not replace
application-specific performance, availability or authorization testing.
