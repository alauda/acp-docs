# OIDC Management

ACP can redirect users to a standards-based OIDC identity provider and create or update their platform identity after successful login.

| Situation | Recommended ACP configuration path |
| --- | --- |
| The provider returns standard `name`, `email`, and `email_verified` Claims and group synchronization is not required | Use the **Form** tab |
| The provider does not return `name`, uses non-standard Claims, requires UserInfo, or must synchronize groups | Use the **YAML** tab and the targeted examples in [Advanced OIDC Configuration](#advanced-oidc-configuration) |

OIDC is an identity layer based on OAuth 2.0. ACP uses it to authenticate users and map the returned identity Claims to platform users and groups.

## Before You Begin

Collect these values for the ACP form:

- Issuer URL, labeled in ACP as **Server Provider URL**.
- Client ID.
- Client Secret, labeled in ACP as **Client Key**.
- Optional Logout URL.

:::note Callback URL

Register this exact callback with the upstream identity provider:

```text
https://<ACP_ADDRESS>/dex/callback
```

ACP derives this address from the platform address, so the form does not contain a Redirect URI field.

:::

Before rollout, identify a test user whose email does not collide with an existing local user or a user from another IDP.

## Upstream OIDC Requirements

The upstream identity provider must support:

- Authorization code flow.
- Confidential-client authentication with a Client ID and Client Secret.
- OIDC discovery from the Issuer URL.
- The `sub`, `email`, and boolean `email_verified` Claims.
- Preferably, the `name` Claim. If `name` is unavailable, expose a stable username Claim such as `preferred_username`.
- A string or string-array group Claim only when group-based authorization is required.

Creating the ACP connector does not require enabling password grant or creating a provider service account solely for validation. Acceptance testing uses an interactive browser authorization code login.

## Add OIDC Using the Form

1. Go to **Users > IDP**.
2. Click **Add OIDC**.
3. Complete **Basic Info**: **Name**, **Display Name**, and optional **Description**.
4. Complete **Server Setting**: **Server Provider URL**, **Client ID**, **Client Key**, and optional **Logout URL**.
5. Click **Add**.

**Server Provider URL** is the Issuer root, not an authorization endpoint, token endpoint, or login page. ACP reads the required endpoints from OIDC discovery and generates `https://<ACP_ADDRESS>/dex/callback` as the callback address.

The current form does not ask for an OIDC test username or password. Connector creation verifies discovery and client configuration, but it does not replace a real browser login test. After creation, ACP moves the submitted **Client Key** to a managed Secret. Leave **Logout URL** empty for the first integration unless the upstream logout behavior is already known.

## Verify the Integration

1. Start a browser session without an ACP login state.
2. Open ACP and select the configured OIDC **Display Name**.
3. Complete authentication at the upstream identity provider.
4. Confirm that the browser returns to ACP.
5. In **Users**, find the generated user and verify its IDP source, mapped email, non-empty username, and active state.
6. Assign a minimal role with [Manage User Roles](../../user/functions/add_role.mdx), or assign a role to a synchronized group with [Manage User Group Roles](../../group/functions/add_role.mdx).
7. Log in again and verify the intended permission.

:::warning Email identity collisions

ACP uses the mapped email as the unique platform account identity. Test for collisions with existing local or other-IDP users before rollout.

:::

Connector creation, upstream authentication, ACP user creation, and authorization are separate checkpoints. Verify each checkpoint independently when diagnosing an integration.

## Advanced OIDC Configuration \{#advanced-oidc-configuration}

Use the **YAML** tab when the standard form mapping is insufficient.

| Observed requirement or problem | Supported configuration |
| --- | --- |
| The upstream ID token does not contain `name`, but it contains `preferred_username` | Set `userNameKey: preferred_username` |
| The ID token is thin and required Claims are available from UserInfo | Set `getUserInfo: true` |
| Email or group data uses a non-standard Claim | Configure the corresponding nested `claimMapping` field |
| A standard Claim is present but a custom Claim must take precedence | Set `overrideClaimMapping: true` with the custom mapping |
| Group Claims must create or update ACP groups during login | Set `insecureEnableGroups: true` and map `claimMapping.groups` |
| Only selected upstream groups may log in or be retained | With `insecureEnableGroups: true` and a usable mapped group Claim, configure `allowedGroups` with the mapped group strings |

The current OIDC runtime has these identity and group behaviors:

- `sub` is mandatory.
- When the `email` scope is requested, `email` and boolean `email_verified` must be present.
- The default ACP username source is `name`. Use `userNameKey` in YAML to select another Claim.
- OIDC users and groups are created or updated during successful login. OIDC does not have LDAP-style manual or scheduled synchronization.
- Group values must be strings or a string array. Check for duplicate values before assigning ACP roles.
- The effective custom group mapping is the nested `claimMapping.groups` field.

### Initial Connector YAML

Use this minimal example when creating a connector through YAML:

```yaml
apiVersion: dex.coreos.com/v1
kind: Connector
id: corporate-oidc
name: Corporate OIDC
type: oidc
metadata:
  name: corporate-oidc
  namespace: cpaas-system
  labels:
    cpaas.io/idp.version: v2
spec:
  config:
    issuer: https://idp.example.com
    clientID: <CLIENT_ID>
    clientSecret: <CLIENT_SECRET>
    redirectURI: https://acp.example.com/dex/callback
    scopes:
      - profile
      - email
```

The Connector automatically adds the `openid` scope, so do not include it in `scopes`. The submitted `clientSecret` is used only for initial creation. Stored YAML later contains `clientSecretRef`, which points to the managed Secret.

### Username Fallback

If the ID token does not contain `name`, select another stable Claim:

```yaml
spec:
  config:
    userNameKey: preferred_username
```

### Group Processing

Enable group processing and map the group Claim through nested `claimMapping.groups`:

```yaml
spec:
  config:
    insecureEnableGroups: true
    claimMapping:
      groups: groups
```

The core group mapping does not assume a group scope. Add a group scope only when the upstream identity provider requires and supports one, and use the exact scope documented by that service. For example, add `groups` to the existing `scopes` list only when the upstream documentation defines `groups` as its group scope.

`allowedGroups` is evaluated only when `insecureEnableGroups: true` and a usable group Claim is available through the standard Claim or nested `claimMapping.groups`. Each `allowedGroups` value must match a mapped group string returned for the user.

If generated YAML displays a top-level `groupsKey`, do not use it as the recommended custom mapping. Configure nested `claimMapping.groups` instead.

### Non-standard Claims

Use custom mappings when the upstream identity provider returns required data in non-standard Claims:

```yaml
spec:
  config:
    insecureEnableGroups: true
    overrideClaimMapping: true
    claimMapping:
      email: preferred_email
      groups: organization_groups
```

Mapping a non-standard group Claim does not enable group processing by itself; `insecureEnableGroups: true` is also required. Set `getUserInfo: true` under `spec.config` when the required Claims are available from UserInfo rather than the ID token. Use `allowedGroups` under `spec.config` only with enabled group processing and a usable mapped group Claim, and list the mapped group strings that are allowed.

### Logout Destination

Configure the optional logout destination with the lowercase `logoutUrl` key:

```yaml
spec:
  config:
    logoutUrl: https://idp.example.com/logout
```

Logout URL controls the browser destination after ACP logout. It does not guarantee that the upstream session is terminated unless the configured URL performs that action.

:::caution Current certificate-verification limitation

In the current ACP implementation, `insecureSkipVerify` cannot be used to enforce certificate verification for the upstream OIDC connection. Use a valid upstream certificate and a trusted network, and do not treat this field as a production hardening control.

:::

## Update or Delete OIDC

On the OIDC list or details page, use the available action menu to update or delete the connector.

- Updating the Connector changes subsequent OIDC authentication and mapped identity behavior.
- Deleting the Connector without cleanup marks users from that source as invalid.
- Selecting **Clean up IDP users and User Groups** deletes generated users and groups.
- After re-integration, later successful logins recreate or update the users and groups.

## Troubleshooting

| Symptom | What ACP has already proven | Likely configuration issue | Next check |
| --- | --- | --- | --- |
| ACP cannot read the Issuer or discovery document | The connector settings were submitted, but discovery did not complete | **Server Provider URL** is not the Issuer root, the discovery document is unavailable, or ACP cannot reach it | Check the Issuer URL and retrieve its discovery document from the ACP network path using an external network diagnostic |
| Connector creation reports client authentication failure | ACP read enough discovery data to attempt client validation | The Client ID or Client Key is incorrect, or the upstream client is not configured as a confidential client | Recheck the upstream client configuration and compare the submitted credentials without exposing the secret in logs |
| The upstream service rejects the callback | The browser reached the upstream authorization step | The registered callback does not exactly match `https://<ACP_ADDRESS>/dex/callback` | Compare the registered callback character for character, including scheme, host, path, and any externally visible port |
| Authentication returns to ACP but login fails because a required Claim is missing | The browser authorization and callback completed | `sub` is absent, or the `email` scope was requested and `email` or boolean `email_verified` is absent | Inspect the returned Claims with an external token diagnostic; ensure `sub` is present and, when requesting the `email` scope, ensure `email` and boolean `email_verified` are present |
| The ACP user is created with an empty username | ACP accepted the identity and mapped its email | The default `name` Claim, or the Claim selected by `userNameKey`, is absent or empty | Confirm a stable username Claim is present, then set or correct `userNameKey` for that Claim |
| Groups are absent, duplicated, or unexpected | User authentication completed, but the group values did not produce the intended ACP groups | Group scope, `insecureEnableGroups`, nested `claimMapping.groups`, `allowedGroups`, or the upstream value shape is incorrect | Inspect the group Claim externally, confirm string or string-array values, remove duplicates, and compare the YAML with the group-processing example |
| ACP logout completes but the upstream session remains active | The ACP session ended | `logoutUrl` is empty or its destination does not terminate the upstream session | Verify the configured destination's behavior directly with the upstream service before relying on it for session termination |
| An HTTPS Issuer works with an untrusted certificate and the administrator expected verification | The connection reached the Issuer despite the certificate condition | The current certificate-verification limitation makes `insecureSkipVerify` unsuitable as an enforcement control | Replace the upstream certificate with a valid trusted certificate and keep the connection on a trusted network |
