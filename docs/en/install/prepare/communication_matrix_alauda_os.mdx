# Communication Matrix for Alauda OS Clusters

This page lists the network flows to confirm **before creating clusters whose
nodes run Alauda OS** (Immutable Infrastructure) — the clusters installed
through the
<ExternalSiteLink name="immutable-infra" href="/global/install.html" children="bootstrap installation path" />.
Use it to request firewall and security approvals; do not start the `global`
or workload cluster installation until every required flow is confirmed.

The [Communication Matrix](./communication_matrix.mdx) page covers nodes that
run a non-Alauda OS and does not apply here. Flows that are
specific to one infrastructure provider — such as the DCS VRM API port or the
Ignition ISO upload to DCS physical hosts — are listed in that provider's
pages (for Huawei DCS, see
<ExternalSiteLink name="immutable-infra" href="/create-cluster/huawei-dcs.html" children="Creating Clusters on Huawei DCS" />
and the global installation guide's bootstrap network table) and are not
repeated below.

## Required Flows

| Source | Destination | Port | Purpose |
| --- | --- | --- | --- |
| Bootstrap host | `global` VIP | `6443` | Reach the `global` control plane endpoint during installation |
| `global` nodes | Bootstrap host | `11443` | Pull images from the bootstrap registry during installation (direction: nodes → bootstrap) |
| `global` nodes | Own `global` VIP | `6443` | Cluster components reach their own API server |
| `global` nodes | Workload cluster API VIP | `6443`, `11780` | Manage workload clusters; collect monitoring and logs |
| All cluster nodes | Platform access address / VIP | `443`, `11443` | Image pulls and platform access |
| Workload cluster nodes | Own API server VIP | `6443` | kubelet and components reach the API server |
| Operations terminals / user networks | `global` VIP | `443` | Web console access |
| Operations terminals | Bootstrap host | `22` | Installation entry point |
| `global` nodes | Workload cluster nodes | `22` | Operations troubleshooting and delivery verification only — nodes are provisioned from images plus Ignition, never over SSH |
| Business networks | Application ingress VIP | `80`, `443` | Application traffic |
| All cluster nodes | Customer DNS / NTP | `53`, `123` | Name resolution and time synchronization |
| Alerting components | Customer notification endpoints | site-specific | Alert delivery |

Notes:

- Nodes do **not** need `11780` opened toward their own cluster's VIP in
  external firewalls: Alauda OS preconfigures that port in the node host
  firewall.
- The `global` VIP's load-balancer listeners (`443`, `6443`, `11443`, and
  `2379` for disaster recovery) and their health checks are defined in
  <ExternalSiteLink name="immutable-infra" href="/global/install.html" children="Global Cluster Installation" />.

## Disaster Recovery

A `global` disaster-recovery pair additionally needs **bidirectional** flows
between the two sides: `443`, `80` (only when HTTP access is enabled), `6443`,
`11443`, and `2379`. Port `2379` carries etcd synchronization and supports
**TCP forwarding only** — not Layer-7. After a failover the roles swap, so the
same flows must work in the reverse direction. See
<ExternalSiteLink name="immutable-infra" href="/global/disaster_recovery.html" children="Global Cluster Disaster Recovery" />
for the full requirements.
