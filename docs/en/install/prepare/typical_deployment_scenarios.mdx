# Typical Deployment Scenarios

This page describes two typical ways to deploy <Term name="product" /> (<Term name="productShort" />) on Alauda OS: a [Single Cluster](#single-cluster) and a [Multi-Cluster](#multi-cluster) platform, with an optional [Ceph](#multi-cluster-ceph) setup for workload clusters. Each scenario lists the resources to prepare, the solution choices, and the installation steps in order.

- The scenarios apply to the Bare Metal, Huawei DCS, VMware vSphere, and Huawei Cloud Stack providers.
- The storage choices assume that no enterprise storage is available. If enterprise storage is available, use it for all data except the node-local platform disks.
- Procedures, commands, and configuration fields are in the linked pages.

To choose between the architectures, see [Plan](./planning.mdx).

## Single Cluster \{#single-cluster}

The `global` cluster also runs the application workloads. Disaster recovery is not used.

### Resource Requirements \{#single-cluster-resources}

#### Machines

| Node pool | Nodes | CPU | Memory | Purpose |
| --- | ---: | --- | --- | --- |
| bootstrap | 1 | 4 cores | 8 GB | Runs the installer. It can also host the platform image registry. |
| control-plane | 3 | 16 cores | 32 GiB | Control plane and platform components. This is the recommended size for a Single Cluster. |
| infra | 3 | 16 cores | 48 GiB | Logging and monitoring, plus the application Ingress and the registry. Logging is planned for 5,000 log entries per second with 7 days of retention. For more logs, expand the disks. |

#### Disks

Sizes are per node, in GiB.

| Node pool | System disk | `/var/lib/containerd` | `/var/lib/kubelet` | `/var/lib/etcd` | `/var/cpaas` | Data disk |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| bootstrap | 300 or more, for the extracted packages and `/var/cpaas` | — | — | — | — | — |
| control-plane | 100 | 150 | 100 | 20 | 200 | — |
| infra | 100 | 150 | 100 | — | 100 | TopoLVM, 1 TiB |

- The tables give the minimum recommended size of each node. Physical servers are usually much larger; select servers that are at least this size. For ARM nodes, scale the sizes as described in [Machines](./planning.mdx#machines).
- For the platform disks, see [Disk Configuration](../../configure/scalability/disk_configuration.mdx). Use a dedicated high-IO disk for etcd.
- 4 cores and 8 GB is the x86 minimum for the bootstrap node. For its disk and the arm64 minimum, see [Bootstrap Node](../alauda_os/prerequisites.mdx#bootstrap-host-hardware).
- The sizes assume about 20 application worker nodes. The number and size of worker nodes depend on the applications and are not covered here. After the installation, evaluate the load on the control plane nodes and scale up when needed; see [Evaluating Resources for Workload Cluster](../../configure/scalability/evaluating_workload.mdx). The `global` cluster of a Single Cluster is also a workload cluster, so it follows the workload cluster evaluation.
- If no image registry is available and machines are limited, deploy mirror-registry on the bootstrap node as the platform image registry. The bootstrap node then cannot be reclaimed after the installation and must meet the mirror-registry requirements; see [Create an Image Registry with mirror-registry](./mirror-registry.mdx).

#### Node Pools

| Node pool | In `install-config.yaml` | Notes |
| --- | --- | --- |
| control-plane | `controlPlane` | Keep `deployMode` at the default value `normal`. Do not set it to `base`. |
| infra | A node group in `computes[]` | After the cluster is created, declare the infra label and taint on the node pool; see [Create Infra Nodes on Alauda OS Nodes](../../configure/nodes/node_planning.mdx#create-infra-nodes-alauda-os). |

For the fields, see [Installation Reference](../alauda_os/reference.mdx#install-config).

#### Control Plane Endpoint

The control plane endpoint serves the Kubernetes API and the platform access address. Choose one of the following:

- **Self-built VIP**: needs no external device.
- **An enterprise load balancer**: use it if one is available.

On Huawei Cloud Stack, use the ELB that the provider creates. For the modes that each provider supports and what to prepare, see [Plan the Control Plane Endpoint](../alauda_os/prerequisites.mdx#control-plane-endpoint).

:::tip
Platform traffic is usually light, so an enterprise load balancer for the endpoint can be more capacity than needed.
:::

### Solution Selection \{#single-cluster-selection}

#### Features and Storage

| Feature | Selection | Storage |
| --- | --- | --- |
| Monitoring | VictoriaMetrics | TopoLVM |
| Logging | ClickHouse | TopoLVM |
| Application ingress | Ingress NGINX | — |
| Application ingress VIP | An enterprise load balancer if available; otherwise MetalLB | — |
| Registry for application images | <Term name="product" /> Registry, 1 replica | TopoLVM |

#### Plugins on Infra Nodes \{#single-cluster-infra-plugins}

| Plugin | Purpose |
| --- | --- |
| Alauda Container Platform Advanced Monitoring | Monitoring |
| Alauda Container Platform Log Storage Management | Log storage management |
| Alauda Data Services Analytical Database E1 | Log storage (ClickHouse) |
| Alauda Data Services Streaming E1 | Log message queue (Kafka) |
| Alauda Container Platform Ingress Controller | Application ingress |
| Alauda Container Platform Registry | Registry for application images |

ClickHouse, Kafka, and the registry are not scheduled to infra nodes automatically. Configure their placement when you install them:

- **ClickHouse**: configure the infra toleration and node affinity on the instance; see <ExternalSiteLink name="clickhouse" href="/how_to/deploy_as_logging_storage.html" children="Deploy as ACP logging storage" />.
- **Kafka**: set the node label and the tolerations in the scheduling settings when you create the instance. The node label cannot be changed after the instance is created, so decide it first. See <ExternalSiteLink name="kafka" href="/functions/10-create-instance.html" children="Create Instance" />.
- **Registry**: configure node selection and tolerations in `Config/cluster`; see [Setting Up and Configuring the Registry](../../configure/registry/setting_up_and_configuring_the_registry.mdx).

## Multi-Cluster \{#multi-cluster}

The `global` cluster runs only the platform. Applications run on workload clusters. The `global` cluster uses a primary and a standby for disaster recovery.

### Resource Requirements \{#multi-cluster-resources}

#### Machines

**`global` cluster**: the table lists one side. Prepare it for both the primary and the standby. Without disaster recovery, prepare one side only.

| Node pool | Nodes per side | CPU | Memory | Purpose |
| --- | ---: | --- | --- | --- |
| bootstrap | 1 | 4 cores | 8 GB | Runs the installer. It can also host the platform image registry. |
| control-plane | 3 | 16 cores | 32 GiB | Control plane and platform components, for up to 50 managed clusters. |
| infra | 3 | 12 cores | 32 GiB | Monitoring and logging of the `global` cluster itself. 16 cores and 32 GiB is also suitable, and uses the same machine type as the control plane. |

**Workload cluster**: choose a size by the number of application worker nodes.

About 20 application worker nodes (size A):

| Node pool | Nodes | CPU | Memory | Purpose |
| --- | ---: | --- | --- | --- |
| control-plane | 3 | 8 cores | 32 GiB | Control plane and platform components. |
| infra | 3 | 16 cores | 48 GiB | Logging and monitoring, plus the application Ingress and the registry. Logging is planned for 5,000 log entries per second with 7 days of retention. For more logs, expand the disks. |

About 150 application worker nodes, with separate pools for ingress, monitoring, and logging (size B):

| Node pool | Nodes | CPU | Memory | Purpose |
| --- | ---: | --- | --- | --- |
| control-plane | 3 | 8 cores | 32 GiB | Control plane and platform components, sized as the 120-worker reference. |
| ingress | 2 | 8 cores | 16 GiB | Application Ingress, about 4,000 requests per second per node. |
| monitor | 3 | 12 cores | 24 GiB | Monitoring. |
| log | 3 | 12 cores | 32 GiB | Logging and the registry. Logging is planned for 5,000 log entries per second with 7 days of retention. For more logs, expand the disks. |

#### Disks

Sizes are per node, in GiB.

| Cluster | Node pool | System disk | `/var/lib/containerd` | `/var/lib/kubelet` | `/var/lib/etcd` | `/var/cpaas` | Data disk |
| --- | --- | ---: | ---: | ---: | ---: | ---: | --- |
| All | bootstrap | 300 or more, for the extracted packages and `/var/cpaas` | — | — | — | — | — |
| `global`, workload | control-plane | 100 | 150 | 100 | 20 | 200 | — |
| `global` | infra | 100 | 150 | 100 | — | 100 | TopoLVM, 1 TiB |
| Workload, size A | infra | 100 | 150 | 100 | — | 100 | TopoLVM, 1 TiB |
| Workload, size B | ingress | 100 | 150 | 100 | — | 100 | — |
| Workload, size B | monitor | 100 | 150 | 100 | — | 100 | TopoLVM, 100 |
| Workload, size B | log | 100 | 150 | 100 | — | 100 | TopoLVM, 1 TiB |

- The tables give the minimum recommended size of each node. Physical servers are usually much larger; select servers that are at least this size. For ARM nodes, scale the sizes as described in [Machines](./planning.mdx#machines).
- For the platform disks, see [Disk Configuration](../../configure/scalability/disk_configuration.mdx). Use a dedicated high-IO disk for etcd.
- 4 cores and 8 GB is the x86 minimum for the bootstrap node. For its disk and the arm64 minimum, see [Bootstrap Node](../alauda_os/prerequisites.mdx#bootstrap-host-hardware).
- The `global` cluster size covers up to 50 managed clusters. For more, evaluate again with [Evaluating Resources for Global Cluster](../../configure/scalability/evaluating_global.mdx).
- The workload cluster sizes are estimated from the number of application worker nodes and are for reference only. The number and size of worker nodes depend on the applications and are not covered here. After the installation, evaluate the load on the control plane nodes and scale up when needed; see [Evaluating Resources for Workload Cluster](../../configure/scalability/evaluating_workload.mdx). For size B, also check the sizes against the actual monitoring data volume and log retention.
- If no image registry is available, deploy mirror-registry on the bootstrap node as the platform image registry, one on each side for disaster recovery. One mirror-registry shared by many clusters is a single point of failure, so with many workload clusters, use a highly available registry. See [Create an Image Registry with mirror-registry](./mirror-registry.mdx).
- To use Alauda Storage in place of enterprise storage at a large scale, contact Alauda for an evaluation first.

#### Node Pools

- Keep `deployMode` at the default value `normal` on every cluster. For the fields, see [Installation Reference](../alauda_os/reference.mdx#install-config).
- For the infra pools of the `global` cluster and of size A workload clusters, declare the label and taint on the node pool after the cluster is created; see [Create Infra Nodes on Alauda OS Nodes](../../configure/nodes/node_planning.mdx#create-infra-nodes-alauda-os).
- For size B workload clusters, create one node pool each for ingress, monitor, and log, with its own role label and taint; see [Custom Role Nodes](../../configure/nodes/node_planning.mdx#custom-role-nodes).

#### Control Plane Endpoint

The `global` cluster and every workload cluster need a control plane endpoint. The choices are the same as for a Single Cluster: a Self-built VIP or an enterprise load balancer. On Huawei Cloud Stack, use the ELB that the provider creates. See [Plan the Control Plane Endpoint](../alauda_os/prerequisites.mdx#control-plane-endpoint).

:::tip
Platform traffic is usually light, so an enterprise load balancer for the endpoint can be more capacity than needed.
:::

### Solution Selection \{#multi-cluster-selection}

#### Features and Storage

| Feature | Selection | Storage |
| --- | --- | --- |
| Monitoring | VictoriaMetrics, one per cluster | TopoLVM |
| Logging | ClickHouse, one per cluster | TopoLVM |
| Application ingress (workload clusters) | Ingress NGINX | — |
| Application ingress VIP (workload clusters) | An enterprise load balancer if available; otherwise MetalLB | — |
| Registry for application images (workload clusters) | <Term name="product" /> Registry, 1 replica | TopoLVM. With Ceph, see [Multi-Cluster with Ceph](#multi-cluster-ceph). |

Each cluster stores only its own monitoring data and logs. Do not send them to the `global` cluster. Disaster recovery synchronizes only the etcd data of the `global` cluster, so monitoring data and logs are not copied to the standby; see [Observability Placement](../alauda_os/global_dr.mdx#observability-placement).

#### Plugins on Infra Nodes

| Node pool | Plugins |
| --- | --- |
| infra | Alauda Container Platform Advanced Monitoring, Alauda Container Platform Log Storage Management, Alauda Data Services Analytical Database E1, Alauda Data Services Streaming E1 |

Workload cluster, size A:

| Node pool | Plugins |
| --- | --- |
| infra | Alauda Container Platform Advanced Monitoring, Alauda Container Platform Log Storage Management, Alauda Data Services Analytical Database E1, Alauda Data Services Streaming E1, Alauda Container Platform Ingress Controller, Alauda Container Platform Registry |

Workload cluster, size B:

| Node pool | Plugins |
| --- | --- |
| ingress | Alauda Container Platform Ingress Controller |
| monitor | Alauda Container Platform Advanced Monitoring |
| log | Alauda Container Platform Log Storage Management, Alauda Data Services Analytical Database E1, Alauda Data Services Streaming E1, Alauda Container Platform Registry |

Configure the placement of ClickHouse, Kafka, and the registry when you install them, in the same way as for a Single Cluster; see [Plugins on Infra Nodes](#single-cluster-infra-plugins). Decide the Kafka node label before you create the instance.

### Multi-Cluster with Ceph \{#multi-cluster-ceph}

When a workload cluster needs storage that follows the Pod across nodes, deploy a small Ceph cluster inside that workload cluster, on a dedicated storage node pool.

#### Machines and Disks

| Node pool | Nodes | CPU | Memory | Purpose |
| --- | ---: | --- | --- | --- |
| storage | 3 | 12 cores | 24 GiB | Ceph. Place the 3 nodes in 3 failure domains. Do not share them with infra or worker nodes. |

Sizes are per node, in GiB.

| Node pool | System disk | `/var/lib/containerd` | `/var/lib/kubelet` | `/var/cpaas` | Data disks |
| --- | ---: | ---: | ---: | ---: | --- |
| storage | 100 | 150 | 100 | 100 | Ceph OSD raw disk, 500, SSD; persistent disk for `/var/lib/rook`, 100 |

- With 3 replicas, usable capacity is about one third of the raw OSD capacity. Add OSD disks for more capacity.
- `/var/lib/rook` must be on a persistent disk, and each OSD must be a separate raw disk; see [Prerequisites for Deploying on Alauda OS](../../storage/storagesystem_ceph/installation/immutable_infrastructure_prerequisites.mdx).
- For the CPU and memory that Ceph reserves, see the small three-node baseline in [Aggregate Cluster Planning Budget](../../storage/storagesystem_ceph/planning.mdx#aggregate-cluster-planning-budget).

#### Changes to the Workload Cluster

| Item | Change |
| --- | --- |
| Node pools | Add the storage node pool, with its own role label and taint. |
| Other components that need persistent volumes | Use Ceph block storage (RBD). |
| Registry for application images | Store the images in Ceph object storage (RGW) through the S3 interface; see [Configure S3-Compatible Storage](../../configure/registry/setting_up_and_configuring_the_registry.mdx#configure-s3-compatible-storage). |
| Installation steps | Install Ceph after TopoLVM and before monitoring; see [Install](../../storage/storagesystem_ceph/installation/index.mdx). |
