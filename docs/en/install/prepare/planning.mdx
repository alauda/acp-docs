# Plan

This page is the entry point for every installation of <Term name="productShort" />, on both installation paths. It helps you choose the deployment architecture, prepare the resources, and confirm the decisions that you cannot change safely after the installation. On Alauda OS, continue with [Typical Installation Scenarios](./typical_installation_scenarios/index.mdx) for the standard sizes and steps of the architecture that you choose.

<Directive type="info" title="INFO">
The <Term name="productShort" /> installation deploys the `global` cluster on new nodes: nodes that you prepare on a non-Alauda OS, or Alauda OS nodes that the installation provisions through an infrastructure provider. It does not support direct installation of the `global` cluster into an existing Kubernetes environment.
</Directive>

## Choose a Deployment Architecture \{#deployment-architecture}

Choose the architecture that matches your use case, management model, workload placement, resource planning, and isolation requirements.

| Architecture | Use when | Planning notes |
| --- | --- | --- |
| Multi-Cluster | You need one `global` cluster to manage multiple workload clusters. | Plan resources for the expected number of managed clusters, and run no application workloads on the `global` cluster. |
| Single Cluster | You intentionally use one cluster for platform components and application workloads, including in production. | Plan resources and platform/workload isolation before the installation, because the `global` cluster also runs application workloads. |
| Single Node | You need a test or proof-of-concept environment. | Do not use it for production, because a cluster with a single control plane node cannot be upgraded. |

- For the control plane size, see [Node Sizing](../../configure/scalability/evaluating_global.mdx#node-sizing) for Multi-Cluster and [`global` Cluster as a Workload Cluster](../../configure/scalability/evaluating_global.mdx#single-cluster-control-plane) for Single Cluster.
- For the standard node pools, machines, disks, and Extensions on Alauda OS, see [Single Cluster](./typical_installation_scenarios/single_cluster.mdx) or [Multi-Cluster](./typical_installation_scenarios/multi_cluster.mdx).
- On Alauda OS, a single control plane node is set with `controlPlane.replicas`; see [Installation Reference](../alauda_os/reference.mdx#install-config).

## Prepare Resources \{#prepare-resources}

Prepare the following machines and network before you start the installation. The pages of your installation path add the details that apply only to that path.

### Machines \{#machines}

#### Nodes of the `global` Cluster \{#global-nodes}

The following sizes apply on both installation paths and cover only the `global` cluster itself. Extensions and other components that you deploy on it need additional resources.

| Architecture | Nodes | CPU and memory of each node |
| --- | --- | --- |
| Multi-Cluster | Three control plane nodes, and more as the scale grows | Depends on the number of managed clusters. |
| Single Cluster | Three control plane nodes | At least 8 cores and 16 GB, and more as the number of worker nodes grows. |
| Single Node | One node | At least 12 cores and 24 GB. |

- For the tiers, see [Evaluating Resources for `global` Cluster](../../configure/scalability/evaluating_global.mdx).
- On ARM nodes, such as Kunpeng 920, use twice the x86 configuration, and at least 1.5 times. For example, where x86 needs 8 cores and 16 GB, use 16 cores and 32 GB on ARM, and at least 12 cores and 24 GB.
- For the disks of every node, see [Disk Configuration](../../configure/scalability/disk_configuration.mdx).

How you provide the nodes depends on the installation path:

- **Alauda OS on Bare Metal**: provide one physical host for each node.
- **Alauda OS on Huawei DCS, VMware vSphere, or Huawei Cloud Stack**: the provider creates the nodes as virtual machines, and the disks of each node are declared in `install-config.yaml`. Make sure that the platform has the capacity for them, and prepare a static IPv4 address and a hostname for each node.
- **Non-Alauda OS**: prepare the nodes yourself, as described in [Node Preprocessing](../non_alauda_os/node_preprocessing.mdx).

#### Installation Machine \{#installation-machine}

- **Alauda OS**: prepare a bootstrap node, one on each side for disaster recovery. It is a temporary machine that runs ACP CLI (ac) and the bootstrap cluster, and it does not join the `global` cluster. For its size, see [Bootstrap Node](../alauda_os/prerequisites.mdx#bootstrap-host-requirements).
- **Non-Alauda OS**: you do not need a separate machine. You start the installer on one of the control plane nodes, and that node becomes the first control plane node of the `global` cluster. For the extra disk space that this node needs, see [First Control Plane Node](../non_alauda_os/prerequisites.mdx#first-control-plane-node).

### Network \{#network}

| Network path | Bandwidth | Latency |
| --- | --- | --- |
| Within a cluster | At least 1 Gbps; 10 Gbps is recommended | At most 10 ms |
| Between clusters | At least 100 Mbps; 1 Gbps is recommended | At most 100 ms; 30 ms or less is recommended |

Insufficient bandwidth can significantly slow down data queries.

## Confirm Install-Time Decisions \{#install-time-decisions}

Confirm the following decisions and prepare what they need before you start the installation. The last two columns link to the page that documents each decision on each path.

| Decision | What to decide and prepare | Non-Alauda OS | Alauda OS |
| --- | --- | --- | --- |
| Installation packages | Download the Core Package, ACP Common Aligned Extensions, and ACP Common Agnostic Extensions for the same version and CPU architecture. | [Download](./download.mdx) | [Download](./download.mdx), [Common Prerequisites](../alauda_os/prerequisites.mdx#common-prerequisites) |
| External platform image registry | Prepare a registry that every node can reach, and upload the payload of the target version to it. | [Prepare an External Platform Image Registry](./external-platform-image-registry.mdx), [Installer Parameters](../non_alauda_os/installer-parameters.mdx) | [Prepare an External Platform Image Registry](./external-platform-image-registry.mdx), [Common Prerequisites](../alauda_os/prerequisites.mdx#common-prerequisites) |
| Cluster Endpoint | Choose an external load balancer or a Self-built VIP for the Kubernetes API. | [Network](../non_alauda_os/prerequisites.mdx#network-resources), [LoadBalancer Forwarding Rules](../non_alauda_os/prerequisites.mdx#port-forward) | [Plan the Cluster Endpoint](../alauda_os/prerequisites.mdx#control-plane-endpoint) |
| Platform access address | Prepare a domain name that resolves to the VIP of the Cluster Endpoint before the installation. | [Installer Parameters](../non_alauda_os/installer-parameters.mdx) | [Common Prerequisites](../alauda_os/prerequisites.mdx#common-prerequisites) |
| External VIP | Prepare one only if some workload clusters cannot reach the platform access address. | [Installer Parameters](../non_alauda_os/installer-parameters.mdx) | `global.platform.extraAddresses` in [Installation Reference](../alauda_os/reference.mdx#install-config) |
| Certificate | Provide a trusted certificate and private key for the platform access address, or use the self-signed certificate that the platform generates. | [Installer Parameters](../non_alauda_os/installer-parameters.mdx) | `global.platform.cert` in [Installation Reference](../alauda_os/reference.mdx#install-config) |
| Cluster network | Choose IPv4, IPv6, or dual stack on a non-Alauda OS, and change the default CIDR ranges on Alauda OS only if they overlap the node network. | [Installing](../non_alauda_os/installing.mdx#start_installer) | `cluster.network` in [Installation Reference](../alauda_os/reference.mdx#install-config) |
| Nodes | Confirm node names, node roles, and whether platform node isolation is required. | [Node Preprocessing](../non_alauda_os/node_preprocessing.mdx), [Installer Parameters](../non_alauda_os/installer-parameters.mdx) | [Infra Nodes](../../configure/nodes/node_planning.mdx) |
| Global Cluster Disaster Recovery | Decide whether your environment requires primary and standby `global` clusters. | [Global Cluster Disaster Recovery](../non_alauda_os/global_dr.mdx) | [Create a Global Cluster Disaster Recovery Pair](../alauda_os/global_dr.mdx) |

- **Installation packages**: on Alauda OS, also prepare the Alauda OS image or VM template.
- **External platform image registry**: a new installation of <Term name="productShort" /> 4.5 or later does not support the platform built-in Registry. Only a `global` cluster upgraded from an earlier version can keep using it.
- **Cluster Endpoint**: a Self-built VIP must be an IP address, not a domain name.
- **Platform access address**: it is a domain name that resolves to the VIP of the Cluster Endpoint, or the VIP itself, so no second VIP is needed. Disaster recovery and IPv6 access on a non-Alauda OS require a domain name.
- **External VIP**: configure it on the load balancer like the platform access address; see [Platform Access Address and `global` VIP](./communication_matrix.mdx#global_vip). Prepare other access addresses, for example for an internal and an external network, in the same way.
- **Certificate**: disaster recovery requires a provided certificate that covers the domain name and is the same on both sides. Self-signed certificates are not supported for disaster recovery.

If you plan disaster recovery, read the page for your installation path before you install <Term name="productShort" /> Core. Disaster recovery affects domain names, VIPs, certificates, load balancer rules, the image registry, the package architecture, and the consistency of the installation parameters.
