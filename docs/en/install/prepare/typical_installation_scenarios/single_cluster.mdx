# Single Cluster

The `global` cluster also runs the business workloads. Disaster recovery is not used. For the assumptions that apply to every scenario, see [Common Assumptions](./index.mdx#common-assumptions).

These sizes match the tier of 24 worker nodes and 500 namespaces in [Global Cluster as a Workload Cluster](../../../configure/scalability/evaluating_global.mdx#single-cluster-control-plane). For a different number of worker nodes or namespaces, select the matching tier on that page.

## Resource Requirements \{#single-cluster-resources}

### Machines

| Node pool | Nodes | CPU | Memory | Purpose |
| --- | ---: | --- | --- | --- |
| bootstrap | 1 | 4 cores | 8 GB | Runs the installer and can also host the platform image registry. |
| control-plane | 3 | 8 cores | 16 GiB | Control plane and platform components. |
| infra | 3 | 16 cores | 48 GiB | Logging, monitoring, the application gateway, and the registry. |

- The tables give the minimum recommended size of each node. Physical servers are usually much larger, so select servers that are at least this size.
- The sizes follow the capacity tiers of each product component. After the installation, scale up according to the actual utilization.
- For ARM nodes, scale the sizes as described in [Machines](../planning.mdx#machines).
- Logging is planned for 5,000 log entries per second with 7 days of retention. For more logs, expand the disks.
- The number and size of worker nodes depend on the business workloads and are not covered here.
- 4 cores and 8 GB is the x86 minimum for the bootstrap node. For its disk and the arm64 minimum, see [Bootstrap Node](../../alauda_os/prerequisites.mdx#bootstrap-host-hardware).
- If no image registry is available and machines are limited, deploy mirror-registry on the bootstrap node as the platform image registry. The bootstrap node then cannot be reclaimed after the installation. See [Create an Image Registry with mirror-registry](../mirror-registry.mdx).

### Disks

Sizes are per node, in GB. For what each disk holds and why it has this size, see [Disk Configuration](../../../configure/scalability/disk_configuration.mdx).

| Disk | control-plane | infra |
| --- | ---: | ---: |
| **IaaS** |  |  |
| System disk | 100 | 100 |
| `/var/lib/etcd` | 20 | — |
| `/var/lib/containerd` | 150 | 150 |
| `/var/lib/kubelet` | 200 | 200 |
| `/var/cpaas` (persistent) | 100 | 200 |
| Raw disk for TopoLVM | — | 750 |
| **Bare Metal** |  |  |
| System disk, minimum / recommended | 512 / 1 TB | 512 / 1 TB |
| Raw disk for TopoLVM | — | 1 TB |

- On IaaS, the raw disk for TopoLVM is sized for the current need, because it can be expanded later. See [Raw Disk for TopoLVM](../../../configure/scalability/disk_configuration.mdx#topolvm_raw_disk).
- The bootstrap node needs 300 GB or more for the extracted packages and `/var/cpaas`.

### Node Pools

| Node pool | In `install-config.yaml` | Notes |
| --- | --- | --- |
| control-plane | `controlPlane` | Keep `deployMode` at the default value `normal`, not `base`. |
| infra | A node group in `computes[]` | Declare the infra label and taint on the node pool after the cluster is created. |

- For the fields, see [Installation Reference](../../alauda_os/reference.mdx#install-config).
- For the infra label and taint, see [Create Infra Nodes on Alauda OS Nodes](../../../configure/nodes/node_planning.mdx#create-infra-nodes-alauda-os).

### Control Plane Endpoint \{#single-cluster-endpoint}

The control plane endpoint serves the Kubernetes API and the platform access address. Choose one of the following:

- **Self-built VIP**: needs no external device.
- **Enterprise load balancer**: allocate one VIP on it for the control plane endpoint. The VIP of the application gateway can also come from the same load balancer.
- **Huawei Cloud Stack**: use the ELB that the provider creates.

For what to prepare, see [Confirm Install-Time Decisions](../planning.mdx#install-time-decisions) and [Plan the Control Plane Endpoint](../../alauda_os/prerequisites.mdx#control-plane-endpoint).

## Solution Selection \{#single-cluster-selection}

### Features and Storage

| Feature | Selection | Storage |
| --- | --- | --- |
| Monitoring | VictoriaMetrics | TopoLVM |
| Logging | ClickHouse | TopoLVM |
| Application gateway | Envoy Gateway (Gateway API) | — |
| Application gateway VIP | An enterprise load balancer if available; otherwise MetalLB | — |
| Registry for application images | <Term name="product" /> Registry, 1 replica | TopoLVM |

On Huawei Cloud Stack, do not use MetalLB for the gateway VIP. Run `envoy-proxy` with the host network, and put the HCS ELB in front of the gateway nodes. See [How To Use `hostNetwork` In `envoy-proxy`](../../../networking/how_to/tasks_for_envoy_gateway.mdx#envoy_proxy_hostnetwork).

### Plugins on Infra Nodes \{#single-cluster-infra-plugins}

| Plugin | Purpose |
| --- | --- |
| Alauda Container Platform Advanced Monitoring | Monitoring |
| Alauda Container Platform Log Storage Management | Log storage management |
| Alauda Data Services Analytical Database E1 | Log storage (ClickHouse) |
| Alauda Data Services Streaming E1 | Log message queue (Kafka) |
| Alauda Container Platform Gateway API Controller | Application gateway (Envoy Gateway) |
| Alauda Container Platform Registry | Registry for application images |

The [Installation Steps](#single-cluster-steps) state how to place monitoring, logging, the application gateway, and the registry on the infra nodes.

For step 13, set the following values in `install.env` in place of the example values of the dedicated node pool:

- `NODE_AFFINITY_KEY`: `node-role.kubernetes.io/infra`, the infra label. Leave `NODE_AFFINITY_VALUE` empty, because the infra label has an empty value.
- `TOLERATION_KEY`, `TOLERATION_VALUE`, and `TOLERATION_EFFECT`: `node-role.kubernetes.io/infra`, `reserved`, and `NoSchedule`, the infra taint.
