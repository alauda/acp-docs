# Typical Installation Scenarios

Choose the deployment architecture in [Plan](./planning.mdx) first. This page then gives the standard sizes and steps of a [Single Cluster](#single-cluster) and a [Multi-Cluster](#multi-cluster) platform on Alauda OS. It also covers an optional [Ceph](#multi-cluster-ceph) setup for workload clusters.

- The scenarios apply to Bare Metal and to IaaS, which means Alauda OS on Huawei DCS, Huawei Cloud Stack, or VMware vSphere.
- The storage choices use the storage that <Term name="productShort" /> provides: TopoLVM, and Ceph through Alauda Storage.
- If enterprise storage is already available, it can hold all data except the node-local platform disks.
- Procedures, commands, and configuration fields are in the linked pages.

## Single Cluster \{#single-cluster}

The `global` cluster also runs the business workloads. Disaster recovery is not used.

The sizes are for 24 worker nodes and 500 namespaces, the first tier in [Global Cluster as a Workload Cluster](../../configure/scalability/evaluating_global.mdx#single-cluster-control-plane).

### Resource Requirements \{#single-cluster-resources}

#### Machines

| Node pool | Nodes | CPU | Memory | Purpose |
| --- | ---: | --- | --- | --- |
| bootstrap | 1 | 4 cores | 8 GB | Runs the installer and can also host the platform image registry. |
| control-plane | 3 | 8 cores | 16 GiB | Control plane and platform components. |
| infra | 3 | 16 cores | 48 GiB | Logging, monitoring, the application gateway, and the registry. |

- The tables give the minimum recommended size of each node. Physical servers are usually much larger, so select servers that are at least this size.
- The sizes follow the capacity tiers of each product component. After the installation, scale up according to the actual utilization.
- For ARM nodes, scale the sizes as described in [Machines](./planning.mdx#machines).
- The scale is a product tier. For a different number of worker nodes or namespaces, select the tier in [Global Cluster as a Workload Cluster](../../configure/scalability/evaluating_global.mdx#single-cluster-control-plane).
- Logging is planned for 5,000 log entries per second with 7 days of retention. For more logs, expand the disks.
- The number and size of worker nodes depend on the business workloads and are not covered here.
- 4 cores and 8 GB is the x86 minimum for the bootstrap node. For its disk and the arm64 minimum, see [Bootstrap Node](../alauda_os/prerequisites.mdx#bootstrap-host-hardware).
- If no image registry is available and machines are limited, deploy mirror-registry on the bootstrap node as the platform image registry. The bootstrap node then cannot be reclaimed after the installation. See [Create an Image Registry with mirror-registry](./mirror-registry.mdx).

#### Disks

Sizes are per node, in GB. For what each disk holds and why it has this size, see [Disk Configuration](../../configure/scalability/disk_configuration.mdx).

| Disk | control-plane | infra |
| --- | ---: | ---: |
| **IaaS** |  |  |
| System disk | 100 | 100 |
| `/var/lib/etcd` | 20 | — |
| `/var/lib/containerd` | 150 | 150 |
| `/var/lib/kubelet` | 200 | 200 |
| `/var/cpaas` (persistent) | 100 | 200 |
| **Bare Metal** |  |  |
| System disk, minimum / recommended | 512 / 1 TB | 512 / 1 TB |
| **All environments** |  |  |
| Raw disk for TopoLVM | — | 1 TB |

The bootstrap node needs 300 GB or more for the extracted packages and `/var/cpaas`.

#### Node Pools

| Node pool | In `install-config.yaml` | Notes |
| --- | --- | --- |
| control-plane | `controlPlane` | Keep `deployMode` at the default value `normal`, not `base`. |
| infra | A node group in `computes[]` | Declare the infra label and taint on the node pool after the cluster is created. |

- For the fields, see [Installation Reference](../alauda_os/reference.mdx#install-config).
- For the infra label and taint, see [Create Infra Nodes on Alauda OS Nodes](../../configure/nodes/node_planning.mdx#create-infra-nodes-alauda-os).

#### Control Plane Endpoint \{#single-cluster-endpoint}

The control plane endpoint serves the Kubernetes API and the platform access address. Choose one of the following:

- **Self-built VIP**: needs no external device.
- **Enterprise load balancer**: allocate one VIP on it for the control plane endpoint. The VIP of the application gateway can also come from the same load balancer.
- **Huawei Cloud Stack**: use the ELB that the provider creates.

For what to prepare, see [Confirm Install-Time Decisions](./planning.mdx#install-time-decisions) and [Plan the Control Plane Endpoint](../alauda_os/prerequisites.mdx#control-plane-endpoint).

### Solution Selection \{#single-cluster-selection}

#### Features and Storage

| Feature | Selection | Storage |
| --- | --- | --- |
| Monitoring | VictoriaMetrics | TopoLVM |
| Logging | ClickHouse | TopoLVM |
| Application gateway | Envoy Gateway (Gateway API) | — |
| Application gateway VIP | An enterprise load balancer if available; otherwise MetalLB | — |
| Registry for application images | <Term name="product" /> Registry, 1 replica | TopoLVM |

On Huawei Cloud Stack, do not use MetalLB for the gateway VIP. Run `envoy-proxy` with the host network, and put the HCS ELB in front of the gateway nodes. See [How To Use `hostNetwork` In `envoy-proxy`](../../networking/how_to/tasks_for_envoy_gateway.mdx#envoy_proxy_hostnetwork).

#### Plugins on Infra Nodes \{#single-cluster-infra-plugins}

| Plugin | Purpose |
| --- | --- |
| Alauda Container Platform Advanced Monitoring | Monitoring |
| Alauda Container Platform Log Storage Management | Log storage management |
| Alauda Data Services Analytical Database E1 | Log storage (ClickHouse) |
| Alauda Data Services Streaming E1 | Log message queue (Kafka) |
| Alauda Container Platform Gateway API Controller | Application gateway (Envoy Gateway) |
| Alauda Container Platform Registry | Registry for application images |

Envoy Gateway, ClickHouse, Kafka, and the registry are not scheduled to infra nodes automatically. Configure their placement when you install them:

- **Envoy Gateway**: set the node selector and tolerations of `envoy-proxy` in the `EnvoyProxy` resource. See [How To Set NodeSelector And Tolerations For `envoy-proxy`](../../networking/how_to/tasks_for_envoy_gateway.mdx#envoy_proxy_scheduling).
- **ClickHouse**: configure the infra toleration and node affinity on the instance. See <ExternalSiteLink name="clickhouse" href="/how_to/deploy_as_logging_storage.html" children="Deploy as ACP logging storage" />.
- **Kafka**: set the node label and the tolerations when you create the instance. The node label cannot be changed later. See <ExternalSiteLink name="kafka" href="/functions/10-create-instance.html" children="Create Instance" />.
- **Registry**: configure node selection and tolerations in `Config/cluster`. See [Setting Up and Configuring the Registry](../../configure/registry/setting_up_and_configuring_the_registry.mdx).

## Multi-Cluster \{#multi-cluster}

The `global` cluster runs only the platform, and business workloads run on workload clusters. The `global` cluster uses a primary and a standby for disaster recovery.

### Resource Requirements \{#multi-cluster-resources}

#### Machines

**`global` cluster**: the table lists one side. Prepare it for both the primary and the standby, or for one side without disaster recovery.

| Node pool | Nodes per side | CPU | Memory | Purpose |
| --- | ---: | --- | --- | --- |
| bootstrap | 1 | 4 cores | 8 GB | Runs the installer and can also host the platform image registry. |
| control-plane | 3 | 16 cores | 32 GiB | Control plane and platform components, for up to 50 managed clusters. |
| infra | 3 | 12 cores | 24 GiB | Monitoring and logging of the `global` cluster itself. |
| harbor | 3 | 12 cores | 24 GiB | Harbor, only when it is the central registry without a DevOps cluster. |
| storage | 3, or 4 on Bare Metal | 8 cores | 24 GiB | Ceph for Harbor, in the same case as the harbor pool. |

- For more than 50 managed clusters, select the control plane tier in [Evaluating Resources for Global Cluster](../../configure/scalability/evaluating_global.mdx#node-sizing).
- The harbor and storage pools go on the primary only by default. If Harbor needs a standby, prepare the same pools on the standby as well; see [Central Registry](#multi-cluster-registry).

**Workload cluster**: the two sizes are the first two tiers in [Control Plane Node Sizing](../../configure/scalability/evaluating_workload.mdx#control-plane-node-sizing).

Size A, for 24 worker nodes and 500 namespaces:

| Node pool | Nodes | CPU | Memory | Purpose |
| --- | ---: | --- | --- | --- |
| control-plane | 3 | 4 cores | 16 GiB | Control plane and platform components. |
| infra | 3 | 16 cores | 48 GiB | Logging, monitoring, and the application gateway. |

Size B, for 120 worker nodes and 1000 namespaces, with separate pools for the gateway, monitoring, and logging:

| Node pool | Nodes | CPU | Memory | Purpose |
| --- | ---: | --- | --- | --- |
| control-plane | 3 | 8 cores | 32 GiB | Control plane and platform components. |
| gateway | 2 | 4 cores | 8 GiB | Application gateway (Envoy Gateway), planned for light load. |
| monitor | 3 | 8 cores | 16 GiB | Monitoring. |
| log | 3 | 8 cores | 16 GiB | Logging. |

- The tables give the minimum recommended size of each node. Physical servers are usually much larger, so select servers that are at least this size.
- The sizes follow the capacity tiers of each product component. After the installation, scale up according to the actual utilization.
- For ARM nodes, scale the sizes as described in [Machines](./planning.mdx#machines).
- The scales are product tiers. For a different number of worker nodes or namespaces, select the tier in [Control Plane Node Sizing](../../configure/scalability/evaluating_workload.mdx#control-plane-node-sizing).
- Logging is planned for 5,000 log entries per second with 7 days of retention. For more logs, expand the disks.
- For more requests than the gateway pool handles under light load, scale up its nodes.
- The number and size of worker nodes depend on the business workloads and are not covered here.
- 4 cores and 8 GB is the x86 minimum for the bootstrap node. For its disk and the arm64 minimum, see [Bootstrap Node](../alauda_os/prerequisites.mdx#bootstrap-host-hardware).
- If no image registry is available, deploy mirror-registry on the bootstrap node of each side as the platform image registry. With many workload clusters, use a highly available registry instead, because one mirror-registry is a single point of failure. See [Create an Image Registry with mirror-registry](./mirror-registry.mdx).
- Alauda Storage can also serve as the main storage of a large platform. To size such a deployment, contact Alauda.

#### Central Registry \{#multi-cluster-registry}

A Multi-Cluster platform uses one central registry for application images, shared by the workload clusters.

- **A central registry already exists**: use it, and skip the planning and installation of Harbor.
- **Only the registry is needed, without other DevOps tools**: add the harbor and storage pools to the `global` cluster, as listed in [Machines](#multi-cluster-resources). See <ExternalSiteLink name="devops" href="/install/planning-devops-cluster.html#harbor-on-global" children="Harbor on the global Cluster" />.
- **Other DevOps tools are also needed**: run Harbor in a dedicated DevOps cluster with the other tools. Add a pipeline pool only when 3 or more PipelineRuns run at the same time at peak. See <ExternalSiteLink name="devops" href="/install/planning-devops-cluster.html#devops-cluster" children="Dedicated DevOps Cluster" /> and <ExternalSiteLink name="devops" href="/install/planning-devops-cluster.html#pipeline-pool" children="Pipeline Pool" />.

A Harbor standby is optional with disaster recovery. By default, add the harbor and storage pools to the primary only. If a Harbor standby is needed, prepare the same pools on the standby as well.

#### Node Pools

- Keep `deployMode` at the default value `normal` on every cluster. For the fields, see [Installation Reference](../alauda_os/reference.mdx#install-config).
- For the infra pools of the `global` cluster and of size A workload clusters, declare the label and taint on the node pool after the cluster is created. See [Create Infra Nodes on Alauda OS Nodes](../../configure/nodes/node_planning.mdx#create-infra-nodes-alauda-os).
- For size B workload clusters, create one node pool each for gateway, monitor, and log, with its own role label and taint. See [Custom Role Nodes](../../configure/nodes/node_planning.mdx#custom-role-nodes).

#### Control Plane Endpoint

The `global` cluster and every workload cluster need a control plane endpoint. Choose one of the following:

- **Self-built VIP**: needs no external device.
- **Enterprise load balancer**: allocate one VIP on it for each control plane endpoint. The VIP of the application gateway can also come from the same load balancer.
- **Huawei Cloud Stack**: use the ELB that the provider creates.

For what to prepare, see [Confirm Install-Time Decisions](./planning.mdx#install-time-decisions) and [Plan the Control Plane Endpoint](../alauda_os/prerequisites.mdx#control-plane-endpoint).

### Multi-Cluster with Ceph \{#multi-cluster-ceph}

When a workload cluster needs storage that follows the Pod across nodes, deploy a small Ceph cluster inside that workload cluster, on a dedicated storage node pool.

#### Machines and Disks

| Node pool | Nodes | CPU | Memory | Purpose |
| --- | ---: | --- | --- | --- |
| storage | 3 on IaaS; 4 on Bare Metal | 8 cores | 24 GiB | Ceph, on nodes not shared with infra or worker nodes. |

- Spread the storage nodes across failure domains.
- On Bare Metal, use 4 storage nodes, because a replacement for a failed server can take a long time to arrive. With 3 nodes, Ceph runs degraded on 2 nodes until then, which blocks maintenance and upgrades. With 4 nodes, 3 remain after one failure, and Ceph can restore all 3 replicas.

Sizes are per node, in GB. For what each disk holds and why it has this size, see [Disk Configuration](../../configure/scalability/disk_configuration.mdx).

| Disk | storage |
| --- | ---: |
| **IaaS** |  |
| System disk | 100 |
| `/var/lib/containerd` | 150 |
| `/var/lib/kubelet` | 100 |
| `/var/cpaas` (persistent) | 50 |
| **Bare Metal** |  |
| System disk, minimum / recommended | 512 / 512 |
| **All environments** |  |
| Raw disk for the Ceph OSD (SSD) | 512 |
| Persistent disk for `/var/lib/rook` | 100 |

- With 3 replicas, usable capacity is about one third of the raw OSD capacity. Add OSD disks for more capacity.
- `/var/lib/rook` must be on a persistent disk, and each OSD must be a separate raw disk. See [Prerequisites for Deploying on Alauda OS](../../storage/storagesystem_ceph/installation/immutable_infrastructure_prerequisites.mdx).
- For the CPU and memory that Ceph reserves, see the small three-node baseline in [Aggregate Cluster Planning Budget](../../storage/storagesystem_ceph/planning.mdx#aggregate-cluster-planning-budget).

#### Changes to the Workload Cluster

| Item | Change |
| --- | --- |
| Node pools | Add the storage node pool, with its own role label and taint. |
| Other components that need persistent volumes | Use Ceph block storage (RBD). |
| Installation steps | Install Ceph after TopoLVM and before monitoring. |

For the installation, see [Install](../../storage/storagesystem_ceph/installation/index.mdx).
