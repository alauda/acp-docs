# Typical Installation Scenarios

This page describes two typical ways to install <Term name="product" /> (<Term name="productShort" />) on Alauda OS: a [Single Cluster](#single-cluster) and a [Multi-Cluster](#multi-cluster) platform, with an optional [Ceph](#multi-cluster-ceph) setup for workload clusters. Each scenario lists the resources to prepare, the solution choices, and the installation steps in order.

- The scenarios apply to the Bare Metal, Huawei DCS, VMware vSphere, and Huawei Cloud Stack providers.
- The storage choices use the storage that <Term name="productShort" /> provides: TopoLVM, and Ceph through Alauda Storage in the [Multi-Cluster with Ceph](#multi-cluster-ceph) setup. If enterprise storage is already available, it can hold all data except the node-local platform disks.
- Procedures, commands, and configuration fields are in the linked pages.

To choose between the architectures, see [Plan](./planning.mdx).

## Single Cluster \{#single-cluster}

The `global` cluster also runs the application workloads. Disaster recovery is not used.

### Resource Requirements \{#single-cluster-resources}

#### Machines

| Node pool | Nodes | CPU | Memory | Purpose |
| --- | ---: | --- | --- | --- |
| bootstrap | 1 | 4 cores | 8 GB | Runs the installer. It can also host the platform image registry. |
| control-plane | 3 | 8 cores | 16 GiB | Control plane and platform components, sized for 24 worker nodes; see [Global Cluster as a Workload Cluster](../../configure/scalability/evaluating_global.mdx#single-cluster-control-plane). |
| infra | 3 | 16 cores | 48 GiB | Logging and monitoring, plus the application gateway and the registry. Logging is planned for 5,000 log entries per second with 7 days of retention. For more logs, expand the disks. |

#### Disks

Sizes are per node, in GB. For what each disk holds and why it has this size, see [Disk Configuration](../../configure/scalability/disk_configuration.mdx).

| Disk | control-plane | infra |
| --- | ---: | ---: |
| **On Huawei DCS, Huawei Cloud Stack, or VMware vSphere** |  |  |
| System disk | 100 | 100 |
| `/var/lib/etcd` | 20 | — |
| `/var/lib/containerd` | 150 | 150 |
| `/var/lib/kubelet` | 200 | 200 |
| `/var/cpaas` (persistent) | 100 | 200 |
| **On Bare Metal** |  |  |
| System disk, minimum / recommended | 512 / 1 TB | 512 / 1 TB |
| **On all providers** |  |  |
| Raw disk for TopoLVM | — | 1 TB |

The bootstrap node needs 300 GB or more for the extracted packages and `/var/cpaas`.

- The tables give the minimum recommended size of each node. Physical servers are usually much larger; select servers that are at least this size. For ARM nodes, scale the sizes as described in [Machines](./planning.mdx#machines).
- For the platform disks, see [Disk Configuration](../../configure/scalability/disk_configuration.mdx).
- 4 cores and 8 GB is the x86 minimum for the bootstrap node. For its disk and the arm64 minimum, see [Bootstrap Node](../alauda_os/prerequisites.mdx#bootstrap-host-hardware).
- The sizes follow the capacity tiers of each product component. After the installation, scale up according to the actual utilization.
- The sizes assume about 20 application worker nodes. The number and size of worker nodes depend on the applications and are not covered here. For more worker nodes, size the control plane with [Global Cluster as a Workload Cluster](../../configure/scalability/evaluating_global.mdx#single-cluster-control-plane).
- If no image registry is available and machines are limited, deploy mirror-registry on the bootstrap node as the platform image registry. The bootstrap node then cannot be reclaimed after the installation and must meet the mirror-registry requirements; see [Create an Image Registry with mirror-registry](./mirror-registry.mdx).

#### Node Pools

| Node pool | In `install-config.yaml` | Notes |
| --- | --- | --- |
| control-plane | `controlPlane` | Keep `deployMode` at the default value `normal`. Do not set it to `base`. |
| infra | A node group in `computes[]` | After the cluster is created, declare the infra label and taint on the node pool; see [Create Infra Nodes on Alauda OS Nodes](../../configure/nodes/node_planning.mdx#create-infra-nodes-alauda-os). |

For the fields, see [Installation Reference](../alauda_os/reference.mdx#install-config).

#### Control Plane Endpoint

The control plane endpoint serves the Kubernetes API and the platform access address. Choose one of the following:

- **Self-built VIP**: needs no external device.
- **An enterprise load balancer**: use it if one is available.

When an enterprise load balancer is available, allocate one VIP on it for the control plane endpoint. The VIP of the application gateway can also come from the same load balancer. On Huawei Cloud Stack, use the ELB that the provider creates. For the modes that each provider supports and what to prepare, see [Plan the Control Plane Endpoint](../alauda_os/prerequisites.mdx#control-plane-endpoint).

- **Envoy Gateway**: set the node selector and tolerations of `envoy-proxy` in the `EnvoyProxy` resource; see [How To Set NodeSelector And Tolerations For `envoy-proxy`](../../networking/how_to/tasks_for_envoy_gateway.mdx#envoy_proxy_scheduling).

- **Kafka**: set the node label and the tolerations in the scheduling settings when you create the instance. The node label cannot be changed after the instance is created, so decide it first. See <ExternalSiteLink name="kafka" href="/functions/10-create-instance.html" children="Create Instance" />.
- **Registry**: configure node selection and tolerations in `Config/cluster`; see [Setting Up and Configuring the Registry](../../configure/registry/setting_up_and_configuring_the_registry.mdx).

## Multi-Cluster \{#multi-cluster}

The `global` cluster runs only the platform. Applications run on workload clusters. The `global` cluster uses a primary and a standby for disaster recovery.

### Resource Requirements \{#multi-cluster-resources}

#### Machines

**`global` cluster**: the table lists one side. Prepare it for both the primary and the standby. Without disaster recovery, prepare one side only.

| Node pool | Nodes per side | CPU | Memory | Purpose |
| --- | ---: | --- | --- | --- |
| bootstrap | 1 | 4 cores | 8 GB | Runs the installer. It can also host the platform image registry. |
| control-plane | 3 | 16 cores | 32 GiB | Control plane and platform components, for up to 50 managed clusters. For more managed clusters, select the tier in [Evaluating Resources for Global Cluster](../../configure/scalability/evaluating_global.mdx). |
| infra | 3 | 12 cores | 24 GiB | Monitoring and logging of the `global` cluster itself. |
| harbor | 3 | 16 cores | 32 GiB | Only when Harbor is the central registry and no DevOps cluster is used. By default on the primary only; add them to the standby as well if Harbor needs a standby. See [Central Registry](#multi-cluster-registry). |
| storage | 3, or 4 on Bare Metal | 8 cores | 24 GiB | Ceph for Harbor, in the same case as the harbor pool. |

**Workload cluster**: choose a size by the number of application worker nodes.

About 20 application worker nodes (size A):

| Node pool | Nodes | CPU | Memory | Purpose |
| --- | ---: | --- | --- | --- |
| control-plane | 3 | 4 cores | 16 GiB | Control plane and platform components, sized as the 24-worker tier; see [Control Plane Node Sizing](../../configure/scalability/evaluating_workload.mdx#control-plane-node-sizing). |
| infra | 3 | 16 cores | 48 GiB | Logging and monitoring, plus the application gateway. Logging is planned for 5,000 log entries per second with 7 days of retention. For more logs, expand the disks. |

#### Central Registry \{#multi-cluster-registry}

A Multi-Cluster platform uses one central registry for application images, shared by the workload clusters.

- **If a central registry already exists**, use it, and skip the planning and installation of Harbor.
- **If no central registry exists**, use Harbor. Plan its resources in one of the following ways:
  - **Only the registry is needed, without other DevOps tools**: add a harbor node pool of 3 nodes with 16 cores and 32 GiB each, and a storage node pool for Ceph (3 nodes, or 4 on Bare Metal, with 8 cores and 24 GiB each), to the `global` cluster. With disaster recovery, a Harbor standby is optional: by default, add the pools to the primary only; if a Harbor standby is needed, prepare the same harbor and storage pools on the standby as well. See <ExternalSiteLink name="devops" href="/install/planning-devops-cluster.html#harbor-on-global" children="Harbor on the global Cluster" />.
  - **Other DevOps tools are also needed**: run Harbor in a dedicated DevOps cluster together with the other tools, and add a pipeline pool for builds. See <ExternalSiteLink name="devops" href="/install/planning-devops-cluster.html#devops-cluster" children="Dedicated DevOps Cluster" /> and <ExternalSiteLink name="devops" href="/install/planning-devops-cluster.html#pipeline-pool" children="Pipeline Pool" />.

Each of the two linked sections lists the machines, the disks, and the totals of its case.

#### Node Pools

- Keep `deployMode` at the default value `normal` on every cluster. For the fields, see [Installation Reference](../alauda_os/reference.mdx#install-config).
- For the infra pools of the `global` cluster and of size A workload clusters, declare the label and taint on the node pool after the cluster is created; see [Create Infra Nodes on Alauda OS Nodes](../../configure/nodes/node_planning.mdx#create-infra-nodes-alauda-os).
- For size B workload clusters, create one node pool each for gateway, monitor, and log, with its own role label and taint; see [Custom Role Nodes](../../configure/nodes/node_planning.mdx#custom-role-nodes).

#### Control Plane Endpoint

The `global` cluster and every workload cluster need a control plane endpoint. The choices are the same as for a Single Cluster: a Self-built VIP or an enterprise load balancer. When an enterprise load balancer is available, allocate one VIP on it for the control plane endpoint. The VIP of the application gateway can also come from the same load balancer. On Huawei Cloud Stack, use the ELB that the provider creates. See [Plan the Control Plane Endpoint](../alauda_os/prerequisites.mdx#control-plane-endpoint).

### Multi-Cluster with Ceph \{#multi-cluster-ceph}

When a workload cluster needs storage that follows the Pod across nodes, deploy a small Ceph cluster inside that workload cluster, on a dedicated storage node pool.

#### Machines and Disks

- With 3 replicas, usable capacity is about one third of the raw OSD capacity. Add OSD disks for more capacity.
- On Bare Metal, use 4 storage nodes. A replacement for a failed physical server can take a long time to arrive. With only 3 nodes, Ceph then runs degraded on 2 nodes for that whole time, and maintenance operations and upgrades are blocked. With 4 nodes, 3 nodes remain after one failure, and Ceph can restore all 3 replicas.
- `/var/lib/rook` must be on a persistent disk, and each OSD must be a separate raw disk; see [Prerequisites for Deploying on Alauda OS](../../storage/storagesystem_ceph/installation/immutable_infrastructure_prerequisites.mdx).
