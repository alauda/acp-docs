# Troubleshooting the global Cluster on Bare Metal

For the installation stages and the failures every provider shares, see [Troubleshooting](../troubleshooting.mdx). The following are specific to Bare Metal. Run the commands below on the bootstrap node; unless a row says otherwise, they read the bootstrap cluster, which exists until the installation completes. If `/var/cpaas/data/alauda.kubeconfig` is missing, see [Common Failures](../troubleshooting.mdx#common-failures).

| Result | Action |
|---|---|
| The first run does not print the ISO URL | Run `<extract-dir>/res/<arch>/ac --kubeconfig /var/cpaas/data/alauda.kubeconfig -n cpaas-system get seedimage global-registration-iso -o yaml` and read the `SeedImageReady` condition. If the registry does not serve `tkestack/baremetal-base-image-iso:<isoImageTag>`, push the images as described in [OS Images in the Registry](./prerequisites.mdx#os-images), then run `create` again. Otherwise, contact technical support. |
| The ISO build fails with `SeedImageBuildFailure` | Read the cause with `<extract-dir>/res/<arch>/ac --kubeconfig /var/cpaas/data/alauda.kubeconfig -n cpaas-system logs global-registration-iso -c baseiso`, fix it, and run `create` again. If it fails again, contact technical support. |
| A host does not appear as a `MachineInventory` | From the host console, check that the host has a network address in the live ISO and reaches `https://<bootstrapIP>:12443`, and fix the network. If it does, contact technical support. |
| A `MachineInventory` is not `Ready=True`, or its `status.plan.secretRef.name` is empty | Wait until the host has installed Alauda OS and rebooted, then list the inventories again with `<extract-dir>/res/<arch>/ac --kubeconfig /var/cpaas/data/alauda.kubeconfig -n cpaas-system get machineinventories.elemental.cattle.io -o yaml`. If it does not change, contact technical support. |
| The registration check fails on a pool | Check that the pool named in `install-config.yaml` exists in `cpaas-system` with `spec.clusterName: global` and lists at least as many hosts as the replicas of the node groups that draw from it. Correct the pool, then run `create` again. |
| The registration check fails with `pool members invalid` | The `MembersValid` message names the host that does not exist or belongs to another pool. Correct the pool, then run `create` again. |
| Stage 4 does not advance | Run `<extract-dir>/res/<arch>/ac --kubeconfig /var/cpaas/data/alauda.kubeconfig -n cpaas-system describe baremetalmachine <name>`. If it reports `ImageCatalogMiss`, see the next row. If the pool has no available `MachineInventory`, add a registered host to the pool. Otherwise, contact technical support. |
| A `BaremetalMachine` stays `Failed` with `ImageCatalogMiss` | Contact technical support to add the image catalog entry. After the entry exists, delete the `Machine` with `<extract-dir>/res/<arch>/ac --kubeconfig /var/cpaas/data/alauda.kubeconfig -n cpaas-system delete machine <name>`; its owner creates it again. |
| Stage 7 waits for the agent handover | Write the `global` kubeconfig from the bootstrap cluster to a private file, `(umask 077; <extract-dir>/res/<arch>/ac --kubeconfig /var/cpaas/data/alauda.kubeconfig -n cpaas-system get secret global-kubeconfig -o jsonpath='{.data.value}' \| base64 -d > <global-kubeconfig>)`, then run `<extract-dir>/res/<arch>/ac --kubeconfig <global-kubeconfig> -n cpaas-system get configmap baremetal-system-agent-handoff -o jsonpath='{.data.ready}'`. While `create` runs, wait until it prints `true`. If `create` stops at stage 7, run it again; if it stops again, contact technical support. Delete `<global-kubeconfig>` afterwards. |
| Stage 8 waits for the image catalog | With the same `<global-kubeconfig>`, run `<extract-dir>/res/<arch>/ac --kubeconfig <global-kubeconfig> -n cpaas-system get configmap elemental-image-catalog -o yaml` and check for an entry for the Kubernetes version of the cluster. If `create` stops at stage 8, run it again; if it stops again, contact technical support. |
| `curl … /healthz` through the Self-built VIP does not print `ok` | Check that the network allows VRRP (IP protocol `112`, multicast `224.0.0.18`) and gratuitous ARP between the control plane nodes, and that no other VRRP instance in the Layer 2 domain uses the `vrid`. If both are met, contact technical support. |

For provider conditions that also apply after installation, see [Troubleshooting Bare Metal Workload Clusters](../../../workload_clusters/alauda_os/bare-metal/troubleshooting.mdx).
