# Prerequisites for Bare Metal

Complete the [common prerequisites](../prerequisites.mdx) first, then prepare the following for Bare Metal. `ac` creates no machines.

## Host OS and Architecture \{#host-os}

Every host of the `global` cluster runs the same host OS on the same host architecture. Choose them before you push the OS images:

- **Alauda OS M55**, on `amd64` only.
- **Alauda OS KU**, on `amd64` or `arm64`.

When the host architecture differs from the architecture of the bootstrap node, use the hybrid Core Package; see [Download](../../prepare/download.mdx).

## OS Images in the Registry \{#os-images}

Push both Bare Metal OS images of the host OS to the external registry, under its `tkestack/` project. They come from one OS archive and are not interchangeable:

{/* lint ignore no-legacy-os-names */}

| Image (Alauda OS M55) | Image (Alauda OS KU) | Used for |
|---|---|---|
| `tkestack/baremetal-base-image-iso` | `tkestack/kubeos-iso` | The live ISO that hosts boot to register. |
| `tkestack/baremetal-base-image` | `tkestack/kubeos-rootfs` | The root filesystem that hosts are installed, upgraded, and reprovisioned with. |

Download the OS archive of the host OS. For Alauda OS KU, download the archive of the host architecture, which holds single-architecture images. The archive is described in [Image Format by Provider](../../../overview/alauda_os_support_matrix.mdx#image-format-by-provider). The `tkestack` project must exist in the registry.

Run the following as root on a Linux host with containerd that reaches the external registry and has free space in `/var/lib/containerd` of at least the archive size. The same commands serve both OSes: set `ISO_REPO` and `ROOT_REPO` for your OS first.

- `<registry-address>`, `<registry-username>`, and the password are the address, user name, and password of the external registry. When the registry needs no credentials, omit the `read` line and the `-u` options.
- `<archive-tag>` is the tag that `images ls -q` prints for the two images.
- `<os-image-tag>` is the tag the images get in the registry: the ISO image tag and the root filesystem image tag. Use the archive file name without `.tar`, such as `alaudaos-44.m55.202610030151-0.x86_64`, so that each release, OS, and architecture keeps its own tag. For Alauda OS M55 this is also `<archive-tag>`; the Alauda OS KU archive tags both images `baremetal`.

{/* lint ignore no-legacy-os-names */}

```bash
# Alauda OS M55
ISO_REPO=baremetal-base-image-iso; ROOT_REPO=baremetal-base-image
# Alauda OS KU
# ISO_REPO=kubeos-iso; ROOT_REPO=kubeos-rootfs

read -rsp 'Registry password: ' REGISTRY_PASSWORD; echo
ctr -n bare-metal-os images import --all-platforms --no-unpack <bare-metal-os-archive>
ctr -n bare-metal-os images ls -q     # ${ISO_REPO}:<archive-tag> and ${ROOT_REPO}:<archive-tag>

for repo in "${ISO_REPO}" "${ROOT_REPO}"; do
  ctr -n bare-metal-os images push --local --skip-verify \
    -u "<registry-username>:${REGISTRY_PASSWORD}" \
    "<registry-address>/tkestack/${repo}:<os-image-tag>" "${repo}:<archive-tag>"
  curl -sSk -u "<registry-username>:${REGISTRY_PASSWORD}" \
    "https://<registry-address>/v2/tkestack/${repo}/tags/list"
done

ctr -n bare-metal-os images rm "${ISO_REPO}:<archive-tag>" "${ROOT_REPO}:<archive-tag>"
unset REGISTRY_PASSWORD
```

Push the images with `ctr` as shown. Do not use `docker push` or another tool that rewrites the image manifest: the Alauda OS KU installer reads the manifest as it is in the archive.

Continue when each `tags/list` response contains `<os-image-tag>`; otherwise check the registry address, the credentials, the `tkestack` project, and the push output.

### Look Up the Image Tags \{#os-image-tags}

The ISO image tag and the root filesystem image tag are the tags of the two images in the registry. To look them up later, run the following on a host that reaches the registry, such as the bootstrap node. When the registry needs no credentials, omit the `read` line and the `-u` option.

```bash
# ISO_REPO and ROOT_REPO as set for the push above
read -rsp 'Registry password: ' REGISTRY_PASSWORD; echo
for repo in "${ISO_REPO}" "${ROOT_REPO}"; do
  curl -sSk -u "<registry-username>:${REGISTRY_PASSWORD}" \
    "https://<registry-address>/v2/tkestack/${repo}/tags/list"; echo
done
unset REGISTRY_PASSWORD
```

The output lists the tags of each repository, here for Alauda OS M55:

```text
{"name":"tkestack/baremetal-base-image-iso","tags":["<os-image-tag>"]}
{"name":"tkestack/baremetal-base-image","tags":["<os-image-tag>"]}
```

{/* lint ignore no-legacy-os-names */}

The tag of `tkestack/baremetal-base-image-iso` (`tkestack/kubeos-iso`) is the ISO image tag, and the tag of `tkestack/baremetal-base-image` (`tkestack/kubeos-rootfs`) is the root filesystem image tag. When a repository lists more than one tag, for example because images of another release were pushed earlier, use the tag of the archive that you downloaded for this ACP release.

## Hosts \{#hosts}

One host for each control plane replica, plus one for each worker replica. Before a host boots the ISO:

- Wipe the system disk and any obsolete boot disk, so that the host boots the ISO and not an old OS.
- Put the ISO first in the boot order. On virtual machines where ejecting the CD does not take effect, boot from disk first and CD second.
- Set the clock from firmware. The hosts must stay within 10 seconds of each other; see [Host Time Synchronization](../../../workload_clusters/alauda_os/bare-metal/prerequisites.mdx#host-time-synchronization).

## Network \{#network}

- **An address during the live ISO boot**, from DHCP or configured on the host console as described in [Network Connectivity](../../../workload_clusters/alauda_os/bare-metal/prerequisites.mdx#network-connectivity).
- **A route from the hosts to the bootstrap node address**, the IPv4 address of the bootstrap node that the hosts reach. The hosts download the ISO and register through it on port `12443`. For the flows from the hosts to the bootstrap node, see [Installation](../../prepare/communication_matrix.mdx#installation).
- **A control plane endpoint**, as planned in [Plan the Control Plane Endpoint](../prerequisites.mdx#control-plane-endpoint): a Self-built VIP with its VRID, or an external load balancer that forwards the ports marked **Yes** in **Forward on load balancer** in [Platform Access Address and `global` VIP](../../prepare/communication_matrix.mdx#global_vip).

## Next Steps
