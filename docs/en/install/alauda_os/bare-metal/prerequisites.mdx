# Prerequisites for Bare Metal

Complete the [common prerequisites](../prerequisites.mdx) first, then prepare the following for Bare Metal. `ac` does not create any machines. You provide the hosts yourself.

## Host OS and Architecture \{#host-os}

All hosts of the `global` cluster run the same host OS on the same host architecture. Choose the OS and the architecture before you push the OS images:

- **Alauda OS M55**, on `amd64` only.
- **Alauda OS KU**, on `amd64` or `arm64`.

Use the hybrid Core Package if the host architecture differs from the architecture of the bootstrap node. See [Download](../../prepare/download.mdx).

## OS Images in the Registry \{#os-images}

Download the OS archive for the host OS and architecture that you chose above, as described in [Downloading Alauda OS](../../../overview/alauda_os_support_matrix.mdx#downloading-alauda-os). For a description of the archive, see [Image Format by Provider](../../../overview/alauda_os_support_matrix.mdx#image-format-by-provider).

The archive contains two OS images, the live ISO and the root filesystem. They come from the same archive but are not interchangeable. Push both images to the `tkestack/` project of the external registry of `global.registry`, with the account of `global.registry`. The `tkestack` project must exist in the registry.

Fill in the form below with the ACP version, the host OS and architecture, the OS image tag (see [Look Up the Image Tags](#os-image-tags)), and the registry address. The form prints two sections: **Push the OS images** and **Values for `install-config.yaml`**.

Run the printed commands as root on the bootstrap node. The bootstrap node needs at least as much free space in `/var/tmp` as the size of the archive. The commands run the `packtool` of the Core Package as `<extract-dir>/res/<arch>/packtool`, in the same way that the other commands of the installation run `ac`.

<BareMetalImageCatalog mode="install" />

Do not push with `docker push` or any other tool that rewrites the image manifest. The Alauda OS KU installer reads the manifest exactly as it is in the archive.

Continue when each `tags/list` response contains the tag. Otherwise, check the registry address, the credentials, the `tkestack` project, and the push output.

Keep the **Values for `install-config.yaml`** section. You paste these values into `install-config.yaml` in [Create the global Cluster on Bare Metal](./create_cluster.mdx#install-config).

### Look Up the Image Tags \{#os-image-tags}

The two images have the same tag: the archive file name without `.tar`, such as `alaudaos-44.m55.202610030151-0.x86_64`. This tag is the value of both `isoImageTag` and `rootImageTag`.

To look up the tags in the registry later, run the following commands on a host that can reach the registry, such as the bootstrap node. If the registry needs no credentials, omit the `read` line and the `-u` option.

{/* lint ignore no-legacy-os-names */}

```bash
# Alauda OS M55
ISO_REPO=baremetal-base-image-iso; ROOT_REPO=baremetal-base-image
# Alauda OS KU
# ISO_REPO=kubeos-iso; ROOT_REPO=kubeos-rootfs

read -rsp 'Registry password: ' REGISTRY_PASSWORD; echo
for repo in "${ISO_REPO}" "${ROOT_REPO}"; do
  curl -sSk -u "<registry-username>:${REGISTRY_PASSWORD}" \
    "https://<registry-address>/v2/tkestack/${repo}/tags/list"; echo
done
unset REGISTRY_PASSWORD
```

The output lists the tags of each repository, here for Alauda OS M55:

```text
{"name":"tkestack/baremetal-base-image-iso","tags":["<os-image-tag>"]}
{"name":"tkestack/baremetal-base-image","tags":["<os-image-tag>"]}
```

{/* lint ignore no-legacy-os-names */}

- The tag of `tkestack/baremetal-base-image-iso` (`tkestack/kubeos-iso` for Alauda OS KU) is the ISO image tag.
- The tag of `tkestack/baremetal-base-image` (`tkestack/kubeos-rootfs` for Alauda OS KU) is the root filesystem image tag.

If a repository lists more than one tag, use the tag of the archive that you downloaded for this ACP release and the host architecture. This can happen, for example, when images of another release or architecture were pushed earlier.

## Hosts \{#hosts}

Provide one host for each node of the `global` cluster. The number of hosts is `controlPlane.replicas` plus the `replicas` of every node group in `computes`. For example, 3 control plane nodes and 3 worker nodes need 6 hosts.

Each host later boots the installation ISO, which the first run of `create` builds in [Build the Installation ISO](./create_cluster.mdx#build-iso). Prepare every host before it boots that ISO, as described in [Prepare the Hosts](../../../workload_clusters/alauda_os/bare-metal/register_hosts.mdx#prepare-hosts):

- Wipe the OS install disk and any old boot disk, so that the host does not start an old OS. See [Disks and Boot Order](../../../workload_clusters/alauda_os/bare-metal/register_hosts.mdx#host-disk-and-boot-preparation).
- Put the virtual CD or ISO first in the boot order.
- Set the clock in the BIOS/UEFI setup or through the BMC. All hosts use the same time zone, and their clocks differ by at most 10 seconds. See [Clock](../../../workload_clusters/alauda_os/bare-metal/register_hosts.mdx#host-time-synchronization).
- If the network gives the hosts no DHCP address, make sure that you can open the host console to configure an address. See [Network in the Live ISO](../../../workload_clusters/alauda_os/bare-metal/register_hosts.mdx#live-iso-network).
- On `arm64` hosts, make sure that SMBIOS data is available. An `arm64` host without SMBIOS cannot register. See [arm64 Hosts](../../../workload_clusters/alauda_os/bare-metal/register_hosts.mdx#arm64-hosts).

## Network \{#network}

- **An address during the live ISO boot**, from DHCP or configured on the host console as described in [Network in the Live ISO](../../../workload_clusters/alauda_os/bare-metal/register_hosts.mdx#live-iso-network).
- **A route from the hosts to the bootstrap node address**, which is the IPv4 address that the hosts use to reach the bootstrap node. The hosts register through this address, on port `12443`. Until the handover from the bootstrap cluster to the `global` cluster, the agents on the hosts also read their plans through it. The ISO download URL is on the same address and port, so the machine that you download the ISO with also needs a route to it. For the flows from the hosts to the bootstrap node, see [Installation](../../prepare/communication_matrix.mdx#installation).
- **A control plane endpoint**, as planned in [Plan the Control Plane Endpoint](../prerequisites.mdx#control-plane-endpoint). It is either a Self-built VIP with its VRID, or an external load balancer. The load balancer must forward every port marked **Yes** under **Forward on load balancer** in [Platform Access Address and `global` VIP](../../prepare/communication_matrix.mdx#global_vip).

## Next Steps

In addition to the common values, you now have:

- The host OS and architecture.
- The values for `install-config.yaml` that the form printed: the ISO image tag and the root filesystem image tag.
- The bootstrap node address.

Continue with [Create the global Cluster on Bare Metal](./create_cluster.mdx).
