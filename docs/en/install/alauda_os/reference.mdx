# Installation Reference

This page describes what every provider shares: the installation directory, the common `install-config.yaml` fields, and the `manifests`, `create`, and `destroy` commands. Each provider's installation and parameter pages link here.

## Installation Directory \{#install-directory}

You write `install-config.yaml`; `ac` writes everything else in the directory.

```text
<install-dir>/
  install-config.yaml       written by you; ac never changes it
  manifests/                the rendered cluster objects
  output/kubeconfig         kubeconfig of the global cluster; it is not renewed automatically
  logs/ac.log               log of every ac run in this directory
  logs/cpaas-installer.log  copy of the platform installer log
```

- Keep the file private (`chmod 600 <install-dir>/install-config.yaml`); it holds the password.
- Do not edit the files in `manifests/`.
- Keep the directory after the installation: `output/kubeconfig` and `logs/` exist only there.

## Common `install-config.yaml` Fields \{#install-config}

The file has four parts: `global` (the registry and the platform identity), `cluster` (the network, keys, and encryption), `provider.<name>` (the infrastructure of one provider), and the node groups `controlPlane` and `computes`. The following structure shows the fields that every provider uses; it is not a complete file. Copy the template of your provider instead: it adds the provider's own fields, such as the control plane endpoint and the node network and disks, and describes them. An unknown or misspelled field fails before `ac` changes anything, and the error names the field path.

```yaml title="install-config.yaml (common structure)"
global:
  registry:
    address: <host>:<port> # [!code callout]
    username: <user> # [!code callout]
    password: <password> # [!code callout]
  platform:
    address: <platform-domain-or-ip> # [!code callout]
    username: admin@cpaas.io # [!code callout]
    password: <password> # [!code callout]
    extraAddresses: [] # [!code callout]
    cert: # [!code callout]
      certificateFile: <console-cert-file>
      privateKeyFile: <console-key-file>
      # pkcs12CertificateFile: <console-pkcs12-file>
      # pkcs12Password: <password>

cluster:
  sshKeys: # [!code callout]
    - <ssh-public-key>
  encryptionProviderConfig: <encryption-key> # [!code callout]
  ntpServers: [] # [!code callout]
  network:
    podCIDR: 10.199.0.0/16 # [!code callout]
    serviceCIDR: 10.96.0.0/12 # [!code callout]
    kubeOVN:
      joinCIDR: 100.64.0.0/16 # [!code callout]

provider:
  <provider-name>: {} # [!code callout]

controlPlane:
  replicas: 3 # [!code callout]
  deployMode: normal # [!code callout]
  <provider-name>: {} # [!code callout]

computes:
  - name: worker # [!code callout]
    replicas: 3 # [!code callout]
    deployMode: normal
    <provider-name>: {}
```

`computes` is optional: without it, the platform runs on the control plane nodes alone.

### Platform Node Groups \{#deploy-mode}

`deployMode: base` labels and taints a node group so that only the platform runs on it. If any node group uses `base`, the whole platform is installed in `base` mode, and the `base` groups must hold at least one replica in total.

| | Applied to a `base` node group |
|---|---|
| Label | `node-role.kubernetes.io/cpaas-system: "true"` |
| Taint on a worker group | `node-role.kubernetes.io/cpaas-system:NoSchedule` |
| Taints on the control plane group | `node-role.kubernetes.io/control-plane:NoSchedule` and `node-role.kubernetes.io/cpaas-system:NoSchedule` |

## Rendered Manifests \{#render-manifests}

To render the cluster objects without applying anything, run on the bootstrap node:

```bash
<extract-dir>/res/<arch>/ac adm alpha global manifests \
  --dir <install-dir> --provider <baremetal|dcs|vsphere|hcs>
```

`manifests` runs the checks that need no bootstrap cluster and writes the objects to `<install-dir>/manifests/`; `create` runs the remaining checks. `create` renders the same way, so this step is optional.

When `manifests/` already exists, `manifests` and `create` ask whether to reuse it. Press Enter to reuse it, or answer `n` to render again after you change `install-config.yaml`. When standard input is not a terminal, pass `--reuse-manifests=true` or `--reuse-manifests=false`.

- **Reusing** applies the files on disk as they are, without checking them. A changed infrastructure credential, encryption key, or Bare Metal ServiceAccount signing key does not take effect.
- **Rendering again** replaces the whole `manifests/` directory. A Secret that is already applied stays as it is: a changed infrastructure credential or encryption key still does not take effect, and a changed Bare Metal ServiceAccount signing key stops `create` with an error.

## The `create` Command \{#create-command}

Run `create` on the bootstrap node:

```bash
<extract-dir>/res/<arch>/ac adm alpha global create \
  --dir <install-dir> --provider <baremetal|dcs|vsphere|hcs>
```

| Flag | Description |
|---|---|
| `--dir` | The installation directory. Required. |
| `--provider` | `baremetal`, `dcs`, `vsphere`, or `hcs`. It must match the provider section in `install-config.yaml`. Required. |
| `--core-package` | The extracted Core Package. Needed only when `ac` runs from outside it. |
| `--reuse-manifests` | Reuse or render again an existing `manifests/` directory. See [Rendered Manifests](#render-manifests). |
| `--timeout` | The wait limit for each stage, timed separately. Default `2h`. |

`create` does not accept `--kubeconfig`.

If `create` stops, because of an interruption, an error, or a stage that exceeds `--timeout`, run the same command again; completed work is skipped. Every error prints the command to resume; it starts with `ac`, so replace that with `<extract-dir>/res/<arch>/ac`. When the registry check fails, the error also prints a variant with `--reuse-manifests=false`; run that one after you correct `global.registry`. Once the bootstrap cluster has started, do not change `global.registry`; see [Troubleshooting](./troubleshooting.mdx#common-failures).

When `create` returns without an error, the installation is complete and the bootstrap cluster is removed. For what to keep, see [Installation Directory](#install-directory). `create` only installs the cluster: to change the running cluster, see [Manage Nodes on Alauda OS Clusters](../../configure/nodes/alauda_os/index.mdx).

<Directive type="warning" title="Do not delete the Cluster API objects to clean up">
  Do not delete the Cluster API `Cluster` `global`, its `KubeadmControlPlane`, or the provider infrastructure objects on the `global` cluster: deleting them destroys the cluster's machines. To remove the cluster, use `destroy`.
</Directive>

## The `destroy` Command \{#destroy}

Run `destroy` on a machine whose kubeconfig reaches the `global` cluster, for example with `<install-dir>/output/kubeconfig`. On the bootstrap node, run `ac` as `<extract-dir>/res/<arch>/ac`.

```bash
ac adm alpha global destroy --kubeconfig <install-dir>/output/kubeconfig          # lists what will be deleted, then asks you to type the cluster name
ac adm alpha global destroy --kubeconfig <install-dir>/output/kubeconfig --yes    # without a terminal
```

What it deletes and keeps depends on the provider; see the provider's Delete the global Cluster page. It does not support Bare Metal. On every provider:

- `destroy` refuses when the target is not a `global` cluster installed with `ac`, or when the platform still manages any other cluster, including imported and half-created ones. The error names the clusters. Neither check can be skipped.
- If the run breaks after the control plane is down, run the same command again on the same machine, as the same user, with the same kubeconfig: `destroy` continues from the plan it saved when you confirmed. The plan holds the infrastructure credentials.
- If the cluster answers but rejects the kubeconfig, with `401`, `403`, or an untrusted certificate, `destroy` stops without deleting anything: that address may now belong to another cluster.
- When something is left after the run, the error names the saved plan file. Delete the file after you clean up.
- A cluster that never answered cannot be destroyed with `ac`. Clean up such a failed installation on the infrastructure side.
- `destroy` leaves the bootstrap node as it is.
- `ac adm alpha cluster destroy --cluster global` is refused. That command is for workload clusters.
