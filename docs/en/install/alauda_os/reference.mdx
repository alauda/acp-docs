# Installation Reference

This page describes what every provider shares: the installation directory, the common `install-config.yaml` fields, the `create` and `destroy` commands, and what `ac` renders into every `global` cluster. Each provider's installation and parameter pages link here.

## Installation Directory \{#install-directory}

You write `install-config.yaml`; `ac` writes everything else in the directory. The directory holds no state file: every command reads the current state from the clusters.

```text
<install-dir>/
  install-config.yaml       written by you; ac never changes it
  manifests/                the rendered cluster objects (directory 0700, files 0600)
  output/kubeconfig         kubeconfig of the global cluster; it is not renewed automatically
  logs/ac.log               execution and wait log, appended on every run
  logs/cpaas-installer.log  copy of the platform installer log, written in stage 8
```

`install-config.yaml` holds plaintext credentials. Keep it at mode `0600`; `ac` warns when it is not. Keep the directory after installation: `output/kubeconfig` and `logs/` exist only there.

## Common `install-config.yaml` Fields \{#install-config}

The file has three parts: `global` (the registry and the platform identity), `cluster` (the network, keys, and encryption), and the node groups `controlPlane` and `computes`. Each provider adds its own `provider.<name>` section and node group fields; see the provider's parameter page. An unknown or misspelled field fails before `ac` touches the host, and the error names the field path.

| Field | Required | Default | Description |
|---|---|---|---|
| `global.registry.address` | Yes | — | The external registry, as `<host>[:port]`, without a scheme or path. |
| `global.registry.username`, `global.registry.password` | No | — | Registry credentials. Set both or neither. |
| `global.platform.address` | Yes | — | The platform access address: a domain name or an IP address, without a scheme or port. It is also written into the etcd server certificate. |
| `global.platform.username` | No | `admin@cpaas.io` | The platform administrator. It is lowercased. |
| `global.platform.password` | Yes | — | 8 to 32 characters with at least one letter, one digit, and one symbol from `!#$%&()*+=?@^_~-`. |
| `global.platform.extraAddresses` | No | `[]` | Other addresses the console answers on, without a port. To reach the console through the control plane VIP, list the VIP here. For [disaster recovery](./disaster_recovery.mdx), it is required on both sides and lists the side's own control plane VIP: it becomes the platform's `console.host`, and `ac` does not add the VIP for you. |
| `global.platform.cert` | No | Self-signed | A third-party console certificate: either `certificateFile` and `privateKeyFile` (PEM), or `pkcs12CertificateFile` and `pkcs12Password`. Paths are absolute. For [disaster recovery](./disaster_recovery.mdx#configure-install-config), it is required, with the same certificate on both sides; self-signed certificates are not supported. |
| `cluster.clusterName` | Must not be set | `global` | `ac` names the cluster. Setting the field, even to `global`, is an error. |
| `cluster.sshKeys` | Yes | — | SSH public keys for logging in to the nodes. |
| `cluster.ntpServers` | No | `[]` | NTP servers for the nodes. On Bare Metal they go into the Cluster API `ntp` configuration; on the other providers `ac` writes them as chronyd servers in `/etc/chrony.d/ntp-servers.conf`, preferred over the image's own servers. When empty, the nodes keep the image's time configuration. |
| `cluster.encryptionProviderConfig` | No | Generated | The aescbc key for encrypting Secrets at rest: the base64 of a 16, 24, or 32 byte key, not a whole configuration file. |
| `cluster.network.podCIDR` | No | `10.199.0.0/16` | Pod CIDR. |
| `cluster.network.serviceCIDR` | No | `10.96.0.0/12` | Service CIDR. |
| `cluster.network.kubeOVN.joinCIDR` | No | `100.64.0.0/16` | Kube-OVN join CIDR. The three ranges must not overlap. |
| `cluster.network.loadBalancer` | Provider-specific | — | The control plane endpoint: `type` (`internal` or `external`), `address` (the IPv4 VIP), `port` (`6443`), and for `internal` a `vrid` unique in the Layer 2 domain. The provider's parameter page lists the defaults and extra fields. |
| `controlPlane.replicas` | Yes | — | An odd number, `1` or `3` or more, on every provider. A single control plane node cannot be upgraded. |
| `controlPlane.deployMode`, `computes[].deployMode` | No | `normal` | `base` dedicates a node group to the platform. See [Platform Node Groups](#deploy-mode). |
| `computes` | No | — | Worker node groups. Each has a unique `name` and `replicas`. Without workers, the platform runs on the control plane nodes. |

### Platform Node Groups \{#deploy-mode}

`deployMode: base` labels and taints a node group so that only the platform runs on it. If any node group uses `base`, the whole platform is installed in `base` mode, and the `base` groups must hold at least one replica in total.

| | Applied to a `base` node group |
|---|---|
| Label | `node-role.kubernetes.io/cpaas-system: "true"` |
| Taint on a worker group | `node-role.kubernetes.io/cpaas-system:NoSchedule` |
| Taints on the control plane group | `node-role.kubernetes.io/control-plane:NoSchedule` and `node-role.kubernetes.io/cpaas-system:NoSchedule` |

## Rendered Manifests \{#render-manifests}

To render the cluster objects without applying anything, run:

```bash
<extract-dir>/res/<arch>/ac adm alpha global manifests \
  --dir <install-dir> --provider <baremetal|dcs|vsphere|hcs>
```

`manifests` validates `install-config.yaml`, opens the Core Package, runs the provider preflight checks, and writes the objects to `<install-dir>/manifests/`. `create` renders the same way, so this step is optional. The provider's parameter page lists its objects. On top of them, `ac` adds the following to every `global` cluster:

- The `cpaas.io/cluster-name: global` label on every object.
- The `is-global` label and the `cpaas.io/registry-address` annotation on `Cluster`.
- The etcd server certificate names in `KubeadmControlPlane`: the control plane VIP, the platform access address, and `etcd.kube-system`. kubeadm adds each node's own IP.
- The `dcs-import-extra-resources` ConfigMap, which lists the provider resources that `cpaas-installer` imports into the `global` cluster in stage 6. The name keeps its historical `dcs` prefix on every provider.
- The `global-etcd-sync-rules` ConfigMap, which keeps each side's infrastructure credentials out of [disaster recovery](./disaster_recovery.mdx) synchronization. It has no effect on a cluster that is not part of a DR pair.
- The label and taints of `base` node groups.

When `manifests/` already exists, `manifests` and `create` ask whether to reuse it. Press Enter to reuse it, or answer `n` to render again after you change `install-config.yaml`. When standard input is not a terminal, pass `--reuse-manifests=true` or `--reuse-manifests=false`.

- **Reusing** applies the files on disk as they are. A changed infrastructure credential, encryption key, or Bare Metal ServiceAccount signing key does not take effect.
- **Rendering again** deletes the whole `manifests/` directory, together with any hand edits in it.

## The `create` Command \{#create-command}

```bash
<extract-dir>/res/<arch>/ac adm alpha global create \
  --dir <install-dir> --provider <baremetal|dcs|vsphere|hcs>
```

| Flag | Description |
|---|---|
| `--dir` | The installation directory. Required. |
| `--provider` | `baremetal`, `dcs`, `vsphere`, or `hcs`. It must match the provider section in `install-config.yaml`. Required. |
| `--core-package` | The extracted Core Package. Needed only when `ac` runs from outside it. A relative path is resolved against the current directory. |
| `--reuse-manifests` | Reuse or render again an existing `manifests/` directory. See [Rendered Manifests](#render-manifests). |
| `--timeout` | The wait limit for each stage, timed separately. Default `2h`. |

`create` works only against the bootstrap cluster that `setup.sh` exports to `/var/cpaas/data/alauda.kubeconfig`, and rejects `--kubeconfig`. It triggers the platform installation itself in stage 6.

When `create` stops, because of an interruption, an error, or a stage that exceeds `--timeout`, run the same command again: completed work is skipped. Every error prints a command you can paste to resume, with an absolute `--dir`, `--reuse-manifests`, and your `--timeout` when it is not the default. It starts with `ac`, so if you ran `ac` by its path, run it the same way. When the registry check fails, the error also prints a variant with `--reuse-manifests=false`; run that one after you correct `global.registry`.

In stage 8, after the handover checks pass, `ac` installs both providers on the `global` cluster, writes and verifies `output/kubeconfig`, copies the installer log into `logs/`, and then deletes the `minialauda` KIND container and its `kind` container network. The bootstrap host itself is yours to reclaim.

<Directive type="warning" title="Do not delete the Cluster API objects to clean up">
  Do not run `kubectl delete cluster global`, and do not delete the `Cluster`, `KubeadmControlPlane`, or provider infrastructure objects on the `global` cluster. These objects own the live control plane machines, and deleting them destroys the cluster. To remove the cluster, use `destroy`.
</Directive>

## The `destroy` Command \{#destroy}

```bash
ac adm alpha global destroy          # lists what will be deleted, then asks you to type the cluster name
ac adm alpha global destroy --yes    # for automation
```

`destroy` reads the cluster itself, so it runs on any machine whose `--kubeconfig` or current context reaches the `global` cluster. What it deletes and keeps depends on the provider; see the provider's Delete the global Cluster page. It does not support Bare Metal. The following holds on every provider:

- **Two guards run before anything is deleted, and neither can be skipped.** The target must be a `global` cluster installed by this path, and the platform must not manage any other cluster. Imported and half-created clusters count, and so does a list that cannot be read; the refusal names the clusters.
- **The deletion plan is saved after you confirm**, to `~/.ac/global-destroy/`, readable only by you, with the infrastructure credentials.
  - If the run breaks after the control plane is down, run the same command with the same kubeconfig. `destroy` resumes from the plan only when the `global` cluster does not answer at all; it retries for up to one minute.
  - When the cluster answers but rejects the request, with a `401` or `403` or a certificate that the kubeconfig does not trust, `destroy` stops without deleting anything: that address may now belong to another cluster.
  - When everything is deleted, the plan file is removed. When something is left, the error names the file; delete it yourself after you clean up.
- **A cluster that never answered cannot be destroyed with `ac`.** Clean up such a failed installation on the infrastructure side.
- **The bootstrap node is left as it is.** If `minialauda` is still there, the next `create` reuses it and skips `setup.sh`.
- **`ac adm alpha cluster destroy --cluster global` is refused.** That command is for workload clusters.
