# Installation Reference

This page describes what every provider shares: the installation directory, the common `install-config.yaml` fields, and the `manifests`, `create`, and `destroy` commands. Each provider's installation and parameter pages link here.

## Installation Directory \{#install-directory}

You write `install-config.yaml`. `ac` writes everything else in the directory.

```text
<install-dir>/
  install-config.yaml       written by you; ac never changes it
  manifests/                the rendered cluster objects
  output/kubeconfig         kubeconfig of the global cluster; it is not renewed automatically
  logs/ac.log               log of every ac run in this directory
  logs/cpaas-installer.log  copy of the platform installer log
```

- Keep the file private (`chmod 600 <install-dir>/install-config.yaml`), because it contains passwords.
- Do not edit the files in `manifests/`.
- Keep the directory after the installation. `output/kubeconfig` and `logs/` exist only there.

## Common `install-config.yaml` Fields \{#install-config}

The file has four parts:

- `global`: the registry and the platform identity.
- `cluster`: the network, keys, and encryption.
- `provider.<name>`: the infrastructure of one provider.
- The node groups `controlPlane` and `computes`.

The following structure shows the fields that every provider uses. It is not a complete file. Copy the template of your provider instead. The template adds and describes the fields of that provider, such as the control plane endpoint, the node network, and the node disks. If a field is unknown or misspelled, `ac` fails before it changes anything, and the error names the field path.

```yaml title="install-config.yaml (common structure)"
global:
  registry:
    address: <host>:<port> # [!code callout]
    username: <user> # [!code callout]
    password: <password> # [!code callout]
  platform:
    address: <platform-domain-or-ip> # [!code callout]
    username: admin@cpaas.io # [!code callout]
    password: <password> # [!code callout]
    extraAddresses: [] # [!code callout]
    cert: # [!code callout]
      certificateFile: <console-cert-file>
      privateKeyFile: <console-key-file>
      # pkcs12CertificateFile: <console-pkcs12-file>
      # pkcs12Password: <password>

cluster:
  sshKeys: # [!code callout]
    - <ssh-public-key>
  encryptionProviderConfig: <encryption-key> # [!code callout]
  ntpServers: [] # [!code callout]
  network:
    podCIDR: 10.199.0.0/16 # [!code callout]
    serviceCIDR: 10.96.0.0/12 # [!code callout]
    kubeOVN:
      joinCIDR: 100.64.0.0/16 # [!code callout]

provider:
  <provider-name>: {} # [!code callout]

controlPlane:
  replicas: 3 # [!code callout]
  deployMode: normal # [!code callout]
  <provider-name>: {} # [!code callout]

computes:
  - name: worker # [!code callout]
    replicas: 3 # [!code callout]
    deployMode: normal
    <provider-name>: {}
```

`computes` is optional. Without it, the platform runs only on the control plane nodes.

### Platform Node Groups \{#deploy-mode}

`deployMode: base` labels and taints a node group so that only the platform runs on it. If any node group uses `base`, the whole platform is installed in `base` mode. The `base` groups must then have at least one replica in total.

| | Applied to a `base` node group |
|---|---|
| Label | `node-role.kubernetes.io/cpaas-system: "true"` |
| Taint on a worker group | `node-role.kubernetes.io/cpaas-system:NoSchedule` |
| Taints on the control plane group | `node-role.kubernetes.io/control-plane:NoSchedule` and `node-role.kubernetes.io/cpaas-system:NoSchedule` |

## Rendered Manifests \{#render-manifests}

To render the cluster objects without applying anything, run this command on the bootstrap node:

```bash
<extract-dir>/res/<arch>/ac adm alpha global manifests \
  --dir <install-dir> --provider <baremetal|dcs|vsphere|hcs>
```

This step is optional, because `create` renders the objects the same way. `manifests` runs the checks that do not need a bootstrap cluster and writes the objects to `<install-dir>/manifests/`. `create` runs the remaining checks.

When `manifests/` already exists, `manifests` and `create` ask whether to reuse it. Press Enter to reuse it. After you change `install-config.yaml`, answer `n` to render the manifests again. When standard input is not a terminal, pass `--reuse-manifests=true` or `--reuse-manifests=false`.

- **Reusing** applies the files on disk as they are, without checking them. A changed infrastructure credential, encryption key, or Bare Metal ServiceAccount signing key does not take effect.
- **Rendering again** replaces the whole `manifests/` directory. A Secret that is already applied does not change. A changed infrastructure credential or encryption key still does not take effect. A changed Bare Metal ServiceAccount signing key stops `create` with an error.

## The `create` Command \{#create-command}

Run `create` on the bootstrap node:

```bash
<extract-dir>/res/<arch>/ac adm alpha global create \
  --dir <install-dir> --provider <baremetal|dcs|vsphere|hcs>
```

| Flag | Description |
|---|---|
| `--dir` | The installation directory. Required. |
| `--provider` | `baremetal`, `dcs`, `vsphere`, or `hcs`. It must match the provider section in `install-config.yaml`. Required. |
| `--core-package` | The extracted Core Package. Needed only when `ac` runs from outside it. |
| `--reuse-manifests` | Whether to reuse an existing `manifests/` directory or render it again. See [Rendered Manifests](#render-manifests). |
| `--timeout` | The maximum wait for each stage. Each stage is timed separately. Default `2h`. |

`create` does not accept `--kubeconfig`.

If `create` stops because of an interruption, an error, or a stage that exceeds `--timeout`, run the same command again. Work that is already complete is skipped.

- Every error prints the command that resumes the installation. Replace the leading `ac` in it with `<extract-dir>/res/<arch>/ac`.
- When the registry check fails, the error also prints a variant with `--reuse-manifests=false`. Run that variant after you correct `global.registry`.
- Once the bootstrap cluster has started, do not change `global.registry`; see [Troubleshooting](./troubleshooting.mdx#common-failures).

When `create` returns without an error, the installation is complete and the bootstrap cluster is removed. For what to keep, see [Installation Directory](#install-directory). `create` only installs the cluster. To change the running cluster, see [Manage Nodes on Alauda OS Clusters](../../configure/nodes/alauda_os/index.mdx).

<Directive type="warning" title="Do not delete the Cluster API objects to clean up">
  On the `global` cluster, do not delete the Cluster API `Cluster` `global`, its `KubeadmControlPlane`, or the infrastructure objects of the provider. Deleting them destroys the machines of the cluster. To remove the cluster, use `destroy`.
</Directive>

## The `destroy` Command \{#destroy}

Run `destroy` on a machine that can reach the `global` cluster with a kubeconfig, for example `<install-dir>/output/kubeconfig`. On the bootstrap node, run `ac` as `<extract-dir>/res/<arch>/ac`.

```bash
ac adm alpha global destroy --kubeconfig <install-dir>/output/kubeconfig          # lists what will be deleted, then asks you to type the cluster name
ac adm alpha global destroy --kubeconfig <install-dir>/output/kubeconfig --yes    # without a terminal
```

What the command deletes and keeps depends on the provider; see the Delete the global Cluster page of your provider. The command does not support Bare Metal. The following applies on every provider:

- `destroy` refuses to run when the target is not a `global` cluster installed with `ac`. It also refuses when the platform still manages any other cluster, including imported clusters and clusters that were only partly created. The error names those clusters. You cannot skip either check.
- If the run fails or stops after the control plane is down, run the same command again on the same machine, as the same user, and with the same kubeconfig. `destroy` continues from the plan that it saved when you confirmed the deletion. The plan contains the infrastructure credentials.
- If the cluster responds but rejects the kubeconfig with `401`, `403`, or an untrusted certificate, `destroy` stops without deleting anything. The address may now belong to another cluster.
- If anything is left after the run, the error names the saved plan file. Delete the file after you clean up.
- If a cluster never responded, you cannot destroy it with `ac`. Clean up such a failed installation on the infrastructure side.
- `destroy` leaves the bootstrap node as it is.
- `ac adm alpha cluster destroy --cluster global` is refused. That command is for workload clusters.
