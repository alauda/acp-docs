# Install on Alauda OS

The `global` cluster is the control plane of the platform. It runs the platform services and manages every workload cluster. This section describes how to install the `global` cluster when its nodes run Alauda OS. To install it on a non-Alauda OS such as Ubuntu or RHEL, see [Install on Non-Alauda OS](../non_alauda_os/index.mdx).

## How the Installation Works

You describe the cluster in one `install-config.yaml` file and run `ac adm alpha global create` on a temporary bootstrap node. The installation then proceeds as follows:

1. `ac` checks `install-config.yaml`, the registry, and the infrastructure.
2. It starts a temporary bootstrap cluster on the bootstrap node and installs the Cluster Bootstrap Provider and the infrastructure provider into it. All images come from the external registry.
3. The providers create the machines of the `global` cluster, and the control plane is initialized.
4. The platform is installed on the `global` cluster.
5. Handover: the `global` cluster takes over its own machines and manages them from then on.
6. `ac` installs the two providers on the `global` cluster, writes the cluster's kubeconfig, and removes the bootstrap cluster.

After the installation, the `global` cluster runs the Cluster Bootstrap Provider and the infrastructure provider of its own platform. You no longer need the bootstrap node.

On Huawei DCS, VMware vSphere, and Huawei Cloud Stack, `ac` stores the infrastructure credential in the `global-credential` Secret on the `global` cluster. When you change the IaaS password, update that Secret.

Keep the installation directory, `<install-dir>`. It holds the only copy of `install-config.yaml`, the rendered manifests, `output/kubeconfig`, and the logs. Copy the directory to a safe place before you reclaim the bootstrap node. See [Installation Directory](./reference.mdx#install-directory).

## Disaster Recovery

A disaster recovery pair consists of two `global` installations, a primary and a standby. You install each one from its own bootstrap node with its own `install-config.yaml`. **<Term name="product" /> Global Cluster Disaster Recovery** runs on the standby and copies the data of the primary to it.

- The two sides share the platform domain, the user-provided certificate of the platform access address, the encryption key, and, on Bare Metal, the ServiceAccount signing key.
- Each side keeps its own control plane VIP, registry configuration, and infrastructure credentials.
- To fail over, you switch the platform domain manually; see [Fail Over to the Standby global Cluster](./disaster_recovery_failover.mdx).
- Metrics and logs are not replicated. Before you install either side, plan where workload clusters send them; see [Observability Placement](./global_dr.mdx#observability-placement).

See [Create a Global Cluster Disaster Recovery Pair](./global_dr.mdx).

## Deployment Path

1. **Prepare.** Meet the [common prerequisites](./prerequisites.mdx), then the prerequisites of your provider.
2. **Decide whether you need disaster recovery.** Read [Create a Global Cluster Disaster Recovery Pair](./global_dr.mdx) before you write the first `install-config.yaml`. You cannot add disaster recovery to an installed `global` cluster without technical support.
3. **Install the `global` cluster** on your provider. For a disaster recovery pair, install both sides as that page describes, then [start the synchronization](./global_dr.mdx#start-synchronization).
4. **Create workload clusters.** See [Create on Alauda OS](../../workload_clusters/alauda_os/index.mdx).
