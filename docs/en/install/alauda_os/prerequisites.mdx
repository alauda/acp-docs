# Prerequisites

Complete the following before you install a `global` cluster on any provider. Each provider adds its own prerequisites on its prerequisites page.

This installation path applies when the nodes of the `global` cluster run Alauda OS on Bare Metal, Huawei DCS, VMware vSphere, or Huawei Cloud Stack. For a non-Alauda OS such as Ubuntu or RHEL, use [Install on Non-Alauda OS](../non_alauda_os/index.mdx) instead.

## Common Prerequisites \{#common-prerequisites}

First prepare the resources that every installation needs, as listed in [Prepare Resources](../prepare/planning.mdx#prepare-resources): the installation packages, the external platform image registry with the payload uploaded, the platform domain name, and your own certificate if you use one. This installation path does not support the platform built-in Registry.

On Alauda OS, also prepare the following:

- **A bootstrap node** that meets the [Bootstrap Node](#bootstrap-host-requirements) requirements. A disaster recovery deployment needs one bootstrap node on each side.
- **The Alauda OS image published for this release.** Prepare it for the nodes as the prerequisites of your provider describe.
- **A stable control plane endpoint** on port `6443`. The endpoint is an external load balancer or a Self-built VIP; see [Plan the Control Plane Endpoint](#control-plane-endpoint). On Huawei Cloud Stack, the provider creates an ELB; see [its prerequisites](./huawei-cloud-stack/prerequisites.mdx).
- **On Huawei DCS, VMware vSphere, and Huawei Cloud Stack, a static IPv4 address and a hostname for each node.** The provider assigns them to the virtual machines that it creates. See the prerequisites of your provider.
- **For x86_64 nodes**, CPUs that support the `x86-64-v2` ISA baseline. See [OS Support Matrix](../../overview/alauda_os_support_matrix.mdx).

If you use your own certificate for the platform access address, put its files on the bootstrap node: a PEM certificate and private key, or a PKCS#12 bundle. `install-config.yaml` refers to them by absolute paths.

## Bootstrap Node \{#bootstrap-host-requirements}

The bootstrap node is a temporary machine. It runs `ac` and, during the installation, the bootstrap cluster. It never joins the `global` cluster. You can reclaim it after the installation; before you do, see [Installation Directory](./reference.mdx#install-directory) for what to keep.

### Hardware \{#bootstrap-host-hardware}

| Resource | Minimum (x86_64) |
|---|---|
| CPU | 4 cores |
| Memory | 8 GB |
| Disk | 300 GB or more, available to the directory where you extract the Core Package and to `/var/cpaas` |

On arm64, use at least 6 cores and 12 GB of memory. The recommended size is 8 cores and 16 GB.

### Operating System \{#bootstrap-host-os}

Use any 64-bit Linux distribution with Bash and `root` access.

### Network \{#bootstrap-host-network}

The bootstrap node needs a static IP address that does not change during the installation.

Allow the network flows that the Communication Matrix lists for the bootstrap node and the `global` nodes in these sections: [Installation](../prepare/communication_matrix.mdx#installation), [Infrastructure Providers](../prepare/communication_matrix.mdx#infrastructure_providers), and [Image Registry](../prepare/communication_matrix.mdx#image_registry).

## Prepare the Core Package and the Registry \{#prepare-core-package}

`ac` runs on the bootstrap node and reads the extracted Core Package there. Run these steps on the bootstrap node, or on the bootstrap node of each side for a disaster recovery pair:

1. Upload the Core Package to the bootstrap node and extract it. In this documentation, `<extract-dir>` is the extracted `installer/` directory.
2. Copy all packages of ACP Common Aligned Extensions into `<extract-dir>/plugins/`, as described in [Download](../prepare/download.mdx#copy-packages).
3. If you have not uploaded the payload to the external registry yet, upload it from `<extract-dir>` as described in [Prepare the Target-Version Payload](../prepare/external-platform-image-registry.mdx#prepare-the-target-version-payload). For a disaster recovery pair with one registry per side, upload it to both registries.

The Core Package contains `ac` at `<extract-dir>/res/<arch>/ac`, where `<arch>` is `amd64` or `arm64`. The installation pages run it from there. Keep it in place; you do not need to install it.

## Plan the Control Plane Endpoint \{#control-plane-endpoint}

Every cluster needs a stable endpoint for the Kubernetes API. Select the endpoint mode before you create the cluster.

:::warning
Do not change the control plane endpoint after the cluster is created. The endpoint is part of the API server certificates, the kubeconfigs, and the connection from the `global` cluster.
:::

### Endpoint Modes by Provider \{#endpoint-modes-by-provider}

| Provider | Endpoint modes | What you prepare |
|---|---|---|
| Huawei DCS | External load balancer (default), or a Self-built VIP. | External: the load balancer, before you create the cluster. Self-built VIP: an IPv4 VIP in the control plane Layer 2 network, and a VRID that is unique in that Layer 2 domain. |
| VMware vSphere | External load balancer (default), or a Self-built VIP. | External: the load balancer, before you create the cluster. Self-built VIP: an IPv4 VIP, a port (typically `6443`), and a VRID that is unique in the control plane Layer 2 domain. |
| Bare Metal | Self-built VIP (default), or an external load balancer. | Self-built VIP: a free VIP, a port (typically `6443`), and a VRID that is unique in the control plane Layer 2 domain. External: the load balancer, before you create the cluster. |
| Huawei Cloud Stack | An HCS ELB that the provider creates. | The ELB addresses: the VIP, two L4 addresses, and two L7 addresses. See [Control Plane ELB Addresses](../../workload_clusters/alauda_os/huawei-cloud-stack/prerequisites.mdx#control-plane-elb-addresses). |

If you do not choose a mode, the default applies. You set the mode and its values in `install-config.yaml`; see the template of your provider: [Bare Metal](./bare-metal/create_cluster.mdx#install-config), [Huawei DCS](./huawei-dcs/create_cluster.mdx#install-config), or [VMware vSphere](./vmware-vsphere/create_cluster.mdx#install-config).

On VMware vSphere, a cluster can use a Self-built VIP only if it was created with one. A cluster whose provider was upgraded from an earlier release keeps its external load balancer. See [Control Plane Endpoint Modes](../../workload_clusters/alauda_os/vmware-vsphere/prerequisites.mdx#control-plane-endpoint-modes).

### External Load Balancer \{#external-load-balancer}

Provision the load balancer before you create the cluster. It must meet the [External Load Balancer requirements](../prepare/communication_matrix.mdx#external_load_balancer).

#### Check the Listener Before Creation \{#check-the-listener}

Run this command on a node of the `global` cluster, or, for a `global` installation, on the bootstrap node:

```bash
nc -vz <control-plane-endpoint> 6443
```

| Result | Action |
|---|---|
| `succeeded` or `open` | Continue. |
| Connection refused or timed out | In the management interface of the load balancer, confirm that the TCP listener on `<control-plane-endpoint>:6443` exists, then continue. Some load balancers accept connections only after a backend is healthy. |

### Self-built VIP \{#self-built-vip}

- Reserve an unused IPv4 address in the same Layer 2 network as the control plane interface that will hold the VIP.
- Use a VRID from `1` to `255` that is unique in that Layer 2 domain.
- Allow VRRP traffic and gratuitous ARP updates between the control plane nodes and the surrounding network; see [Self-built VIP](../prepare/communication_matrix.mdx#self_built_vip).
- Use at least three control plane nodes for high availability.
- Use an IP address, not a domain name, for the Self-built VIP.
- Do not maintain a second backend list for the same VIP by hand. The provider updates the backend list when control plane nodes are replaced.
- If you name the VIP interface, use a Linux interface name of at most 15 characters, such as `eth0`. If you do not name one, the VIP is held on the interface that has the node address.

On Huawei DCS, the port group allows VIP ownership, gratuitous ARP, and VRRP traffic.

On VMware vSphere, the following additional rules apply:

- The VIP must be IPv4. IPv6 and dual-stack endpoints are not accepted.
- The VIP must not equal any node address, primary or additional. It must also be outside every external IPAM pool range, because the provider does not detect a conflict with an external IPAM pool.
- On nodes with more than one NIC, name the VIP interface explicitly. You cannot change it after the cluster is created.
- The dvPortGroup security policy and any NSX-T distributed firewall rule allow VRRP (IP protocol `112`, multicast `224.0.0.18`) and gratuitous ARP between the control plane nodes.
