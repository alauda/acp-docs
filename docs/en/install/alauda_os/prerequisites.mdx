# Prerequisites

Complete the following before you install a `global` cluster on any provider. Each provider adds its own prerequisites on its prerequisites page.

This path applies when the `global` cluster runs on Alauda OS, on Bare Metal, Huawei DCS, VMware vSphere, or Huawei Cloud Stack. For a non-Alauda OS such as Ubuntu or RHEL, use [Install on Non-Alauda OS](../non_alauda_os/index.mdx) instead.

## Common Prerequisites \{#common-prerequisites}

- **A bootstrap node** that meets the [Bootstrap Node](#bootstrap-host-requirements) requirements. A disaster recovery deployment needs one per side.
- **The Core Package** for the target <Term name="productShort" /> version and CPU architecture. It carries the `ac` binary, and `res/product.yaml` declares the provider chart versions. The provider packages are not in the Core Package.
- **The required Aligned Extension packages** for the same version and architecture. See [Required Aligned Extensions](../prepare/download.mdx#required-aligned-extensions).
- **Two provider packages** from **Common ACP Extensions**, at the versions that `res/product.yaml` declares: **Alauda Container Platform Cluster Bootstrap Provider** and the **Alauda Container Platform Infrastructure Provider** for your provider. See [Download](../prepare/download.mdx).
- **An external platform image registry that holds the complete target-version payload**, including both provider charts, reachable from the bootstrap node and every `global` node. `ac` never pushes to the registry, and this path does not support the platform built-in Registry. See [Prepare an External Platform Image Registry](../prepare/external-platform-image-registry.mdx).
- **Addresses for the `global` nodes and a stable control plane endpoint**, an external load balancer or a provider-managed internal VIP, on port `6443`. See [Plan the Control Plane Endpoint](../../workload_clusters/alauda_os/prepare/control-plane-endpoint.mdx).
- **A platform access address**: a domain name or an IP address. Disaster recovery requires a domain name and a third-party certificate that covers it, the same on both sides; self-signed certificates are not supported.
- **Pod, Service, and Kube-OVN join CIDR ranges** that overlap neither each other nor the node network.
- **For x86_64 nodes**, CPUs that support the `x86-64-v2` ISA baseline. See [OS Support Matrix](../../overview/alauda_os_support_matrix.mdx).

`ac` names the cluster `global` and every other object `global-<name>`. Disaster recovery identifies the `global` resources by this prefix, so do not rename the objects in the rendered manifests.

## Bootstrap Node \{#bootstrap-host-requirements}

The bootstrap node is a temporary machine that runs `ac`. During the installation it carries the KIND-based `minialauda` management cluster, the Cluster API providers, and `cpaas-installer`. It never joins the `global` cluster: `ac` deletes `minialauda` in the last stage, and you reclaim the host afterwards.

### Hardware \{#bootstrap-host-hardware}

| Resource | Minimum (x86_64) |
|---|---|
| CPU | 4 cores |
| Memory | 8 GB |
| Disk | 300 GB or more, available to the Core Package extraction directory and `/var/cpaas` |

On arm64, use at least 6 cores and 12 GB of memory; 8 cores and 16 GB are recommended. The extracted Core Package needs at least 100 GB. Images are pulled from the external registry, not served from this node.

### Operating System \{#bootstrap-host-os}

A 64-bit Linux distribution with Bash and `root` privilege; it does not run Alauda OS. [Node Preprocessing](../non_alauda_os/node_preprocessing.mdx) and the `x86-64-v2` baseline do not apply, because the node never joins a cluster, but a distribution from the validated list in that page is a safe default.

### Network \{#bootstrap-host-network}

The bootstrap node needs a static IP address that does not change during the installation.

| From | To | Port | Purpose |
|---|---|---|---|
| Bootstrap node | External registry | The registry port | `ac` checks the registry; `minialauda` and the providers pull their images from it. |
| Bootstrap node | `global` control plane endpoint | `TCP/6443` | Cluster API and `ac` reach the API server while the cluster is created and handed over. |
| Bootstrap node | Infrastructure API | Provider-specific | The providers create machines through it. See the provider's prerequisites. |
| `global` nodes | External registry | The registry port | Nodes pull platform images directly from the registry. |

## Versions \{#versions}

The Core Package fixes every component version in `res/product.yaml`: Kubernetes, etcd, Kube-OVN, both provider charts, and the product version. You do not set them in `install-config.yaml`. You choose only the Alauda OS image or VM template the nodes boot from, and it must carry the Kubernetes version that `product.yaml` declares; see [OS Support Matrix](../../overview/alauda_os_support_matrix.mdx).

An internal control plane VIP requires a Core Package whose product version is v4.4.0 or later. `ac` checks this before it changes anything on the host.

## Prepare the Core Package and the Registry \{#prepare-core-package}

1. Upload the Core Package to the bootstrap node and extract it.
2. Copy the required Aligned Extension packages and the two provider packages into its `plugins/` directory.
3. Upload the target-version payload into the external registry with `res/upload.sh`, in both modes, as described in [Prepare the Target-Version Payload](../prepare/external-platform-image-registry.mdx#prepare-the-target-version-payload).

Run `ac` from the extracted Core Package as `<extract-dir>/res/<arch>/ac`, where `<arch>` is `amd64` or `arm64`. `ac` locates the Core Package from its own path, also through a symbolic link; a copy outside the package needs `--core-package <extract-dir>`.

`res/upload.sh all` pushes every package in `plugins/`, so the provider charts reach the registry with the rest of the payload. You do not install the providers yourself: `ac` installs them from the registry, first into `minialauda` and at the end on the `global` cluster.
