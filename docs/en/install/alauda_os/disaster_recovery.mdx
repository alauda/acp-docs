# Global Cluster Disaster Recovery

A disaster recovery (DR) pair is a primary and a standby `global` cluster. Each side is an ordinary installation with ACP CLI (`ac`), run from its own bootstrap node with its own `install-config.yaml`. **<Term name="product" /> Global Cluster Disaster Recovery** (`etcd-sync`) on the standby then copies the primary's data to it. `ac` prepares every `global` cluster for DR, so a DR pair needs no manifest edits. Each side's infrastructure credentials are not synchronized, so the two sides can use different accounts.

This page applies to every provider. Configuration that differs by provider is shown in tabs; manual steps that only one provider needs are marked with the provider name.

## Prerequisites

- Each side has its own bootstrap node, infrastructure, external registry, and control plane VIP, and meets the [common prerequisites](./prerequisites.mdx) and the prerequisites of its provider.
- The platform access address is a DNS name that you can point at either VIP, with a third-party certificate whose SANs cover it. Self-signed certificates are not supported for DR.
- The network between the sites meets the [network requirements](#network-requirements).

## Network Requirements \{#network-requirements}

The platform access address must be a DNS name. During normal operation it resolves only to the primary VIP, and the standby uses it to reach platform services on the primary.

Before installing either cluster:

- Forward the ports below on each cluster's VIP to the control plane nodes behind it. Port `80` is needed only when users access the platform over HTTP.
  - External load balancer (`loadBalancer.type: external`): configure the listeners yourself, including `2379`.
  - Self-built VIP (`loadBalancer.type: internal`) on Bare Metal, Huawei DCS, or VMware vSphere: the provider already serves `80`, `443`, and `2379` on the VIP.
  - Huawei Cloud Stack: the provider opens `443` and `2379` on the control plane ELB; add `80` yourself when needed.
- Allow the ports in **both directions** between the primary and standby networks: firewalls, security groups, router ACLs, and any other inter-site controls. After failover the roles are reversed, so the former primary must reach the new primary on the same ports.

| TCP port | Service | Why it is required |
|----------|---------|--------------------|
| `443` | <Term name="productShort" /> platform HTTPS | The standby reaches the primary's platform through the platform access address. **<Term name="product" /> Global Cluster Disaster Recovery** uses it, and logging and monitoring send alert callbacks to it. |
| `80` | <Term name="productShort" /> platform HTTP | Only when users access the platform over HTTP. |
| `6443` | Kubernetes API server | During installation or reinstallation of **<Term name="product" /> Global Cluster Disaster Recovery**, the standby reads the etcd CA material from the primary's API server. |
| `2379` | etcd | **<Term name="product" /> Global Cluster Disaster Recovery** on the standby reads etcd data from the primary and writes it to the local etcd. |

Each side pulls its images from its own external registry, so no registry port crosses the sites.

## Procedure

Run the commands on a machine with `ac` that reaches both sides:

- **Primary**: log in once with `ac login https://<platform-domain>` as the platform administrator while the domain points at the primary. Commands for the primary start with `ac config use-cluster global`.
- **Standby**: use the standby's kubeconfig, `output/kubeconfig` in its installation directory, here `<standby-kubeconfig>`. Commands for the standby start with `export KUBECONFIG=<standby-kubeconfig>` and end with `unset KUBECONFIG`.

### 1. Write Both install-config.yaml Files \{#configure-install-config}

Write each side's `install-config.yaml` as for a single `global` cluster, following the installation page of its provider, with these values:

| Field | Primary | Standby |
|---|---|---|
| `global.platform.address` | The platform domain | The same domain |
| `global.platform.cert` | A third-party certificate and key whose SANs cover the domain | The same certificate and key files |
| `global.platform.extraAddresses` | `[<primary-vip>]` | `[<standby-vip>]` |
| `cluster.network.loadBalancer.address` (`provider.hcs.elb.vipAddress` on HCS) | The primary VIP | The standby VIP |
| `global.registry` | The primary's external registry | The standby's external registry |
| `cluster.encryptionProviderConfig` | A key, or empty to have one generated | The primary's key |
| `provider.baremetal.serviceAccountSigningKey` (Bare Metal) | A key, or empty to have one generated | The primary's key |

- **Certificate**: do not omit `global.platform.cert`. Without it, each side generates its own self-signed certificate, and after a failover clients reject the other side's certificate; on Bare Metal this includes the agents of the workload hosts.
- **`extraAddresses`**: each side's own VIP, which you use to reach that side while the domain points at the other one. `ac` does not add it.
- **Encryption key**: the standby cannot decrypt Secrets encrypted with another key. When the primary's is generated, read it on the primary before you install the standby:

  ```bash
  ac config use-cluster global
  ac -n cpaas-system get secret global-encryption-provider-config \
    -o jsonpath='{.data.encryption-provider\.conf}' | base64 -d | awk '$1=="secret:"{print $2}'
  ```

  VMware vSphere has no such Secret. Run this on a primary control plane node instead:

  ```bash
  awk '$1=="secret:"{print $2}' /etc/kubernetes/encryption-provider.conf
  ```

- **ServiceAccount signing key** (Bare Metal): when the primary's is generated, read it on the primary; the value is already in the form the field expects:

  ```bash
  ac config use-cluster global
  ac -n cpaas-system get secret global-sa -o jsonpath='{.data.tls\.key}'
  ```

  To set it in advance, generate a key with `openssl genrsa -out sa.key 2048` and set `base64 -w0 sa.key` on both sides. Keep the file private (`chmod 600 sa.key`); it holds the signing key. The key cannot be changed after installation: if the cluster already holds a different `global-sa`, `ac` stops rather than overwrite it.

- **VM folder** (VMware vSphere): when both sides share a vCenter, you can set a different `provider.vsphere.folder` on each side to keep their VMs apart. The same folder also works.

### 2. Install the Primary and the Standby \{#install-primary-and-standby-clusters}

The platform domain must point to the side being installed. While the domain points at one side, reach the other side through its VIP with the kubeconfig in its installation directory.

1. Point the platform domain at the primary VIP. On the primary bootstrap node, install the cluster as described on the Create the global Cluster page of its provider ([Bare Metal](./bare-metal/create_cluster.mdx), [Huawei DCS](./huawei-dcs/create_cluster.mdx), [VMware vSphere](./vmware-vsphere/create_cluster.mdx), or [Huawei Cloud Stack](./huawei-cloud-stack/create_cluster.mdx)), then return here.
2. When the primary is installed, point the platform domain at the standby VIP. On the standby bootstrap node, install the standby the same way.
3. **Bare Metal only:** on the standby, set the provider's `sharedAuthReadOnly` to `true`. Change no other `elemental` value:

   ```bash
   export KUBECONFIG=<standby-kubeconfig>
   ac get moduleinfo -l cpaas.io/cluster-name=global,cpaas.io/module-name=cluster-api-provider-baremetal
   ac patch moduleinfo <name> --type=json -p '[{"op":"replace","path":"/spec/valuesOverride/acp~1chart-cluster-api-provider-baremetal/elemental/systemAgent/sharedAuthReadOnly","value":true}]'
   ac -n cpaas-system get deploy elemental-operator -o yaml | grep -- --system-agent-shared-auth-read-only
   unset KUBECONFIG
   ```

   Continue when the last command prints `--system-agent-shared-auth-read-only`; otherwise, wait and run it again.

4. Point the platform domain back at the primary VIP.

Install the providers you use for workload clusters on **both** `global` clusters, so that the standby can reconcile the same workload clusters after a failover.

### 3. Bare Metal Only: Apply the Rule ConfigMap \{#apply-the-rule-configmap}

Apply the same `baremetal-dr-rules` ConfigMap to the primary and the standby, **before** you install `etcd-sync`. It lists every `global` plan Secret of both clusters; collect the names after both sides have completed `create`. On each side, list them with:

```bash
# Primary: ac config use-cluster global
# Standby: export KUBECONFIG=<standby-kubeconfig>, and unset KUBECONFIG afterwards
ac -n cpaas-system get machineinventories.elemental.cattle.io -o json | jq -r '.items[]
  | select(.metadata.annotations["baremetal.cluster.io/system-agent-auth-scope"]=="global")
  | .status.plan.secretRef.name // empty | "/registry/secrets/cpaas-system/" + .'
```

Update the ConfigMap on both sides whenever a `global` host is added or replaced.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: baremetal-dr-rules
  namespace: cpaas-system
  labels:
    etcd-sync.cpaas.io/enabled: "true"
  annotations:
    etcd-sync.cpaas.io/weight: "100"
data:
  ignore-equal.txt: |
    # One line for every global plan Secret on both sides, as printed above.
    /registry/secrets/cpaas-system/<primary-global-plan-secret>
    /registry/secrets/cpaas-system/<standby-global-plan-secret>
```

<Directive type="warning" title="Create the rule source before the mirror can start">
  Installing `etcd-sync` with the active cluster VIP and token already set starts synchronization immediately. Without the rule source, the first synchronization overwrites the standby's `global` plan Secrets with the primary's, and the standby `global` hosts receive plans that belong to the primary. If you must install the plugin first, leave the active cluster VIP unset until the rule source reports `accepted`.
</Directive>

### 4. Install etcd-sync \{#install-etcd-sync}

Install **<Term name="product" /> Global Cluster Disaster Recovery** (`etcd-sync`) on the standby `global` cluster only, after both sides have completed `create`. Never run it on both sides at once. Use the version released with <Term name="productShort" /> 4.5.

The platform domain must point at the primary when you install it. Reach the standby through its VIP.

1. Download the plugin package from the Customer Portal and upload it to the standby with `violet push`, setting the platform address to `https://<standby-vip>`; see [Upload Packages](../../extend/upload_package.mdx#violet_push_usage).
2. Create the token Secret on the standby. The value is the bearer token of the primary's `cpaas-system/k8sadmin` ServiceAccount:

   ```shell
   # On the primary:
   ac config use-cluster global
   ac -n cpaas-system get secret k8sadmin -o jsonpath='{.data.token}' | base64 -d

   # On the standby, with the value copied from above:
   export KUBECONFIG=<standby-kubeconfig>
   ACTIVE_CLUSTER_TOKEN='<paste-the-token-from-the-primary>'
   ac -n cpaas-system create secret generic etcd-sync-active-cluster-token \
     --from-literal=token="${ACTIVE_CLUSTER_TOKEN}" \
     --dry-run=client -o yaml | ac apply -f -
   unset KUBECONFIG
   ```

3. Open the standby Web Console at `https://<standby-vip>`, go to **Marketplace** → **Cluster Plugins**, select the `global` cluster, and install **<Term name="product" /> Global Cluster Disaster Recovery** with these parameters:

   | Parameter | Value |
   |-----------|-------|
   | Active Global Cluster VIP | Control plane VIP of the primary `global` cluster |
   | Active Global Cluster ETCD Endpoints | `https://<primary-control-plane-vip>:2379` |
   | Standby Cluster ETCD Endpoints | Default value |
   | Active Global Cluster Token Secret | `etcd-sync-active-cluster-token` |
   | Data Check Interval | Default value |
   | Print detail logs | Disabled unless troubleshooting |

4. **Bare Metal only:** immediately after the installation, check the rule source on the standby:

   ```shell
   export KUBECONFIG=<standby-kubeconfig>
   ac -n cpaas-system get configmap baremetal-dr-rules \
     -o jsonpath='{.metadata.annotations.etcd-sync\.cpaas\.io/status}{"\n"}'
   ac -n cpaas-system get configmap etcd-sync-rule-snapshot \
     -o jsonpath='{.data.snapshot\.json}'
   unset KUBECONFIG
   ```

   Continue when the first command prints `accepted` and the snapshot contains `baremetal-dr-rules`; otherwise, fix the ConfigMap as described in [Troubleshooting](#troubleshooting) before you continue.

### 5. Start and Verify Synchronization \{#start-and-verify-synchronization}

1. Wait for the `etcd-sync` `AppRelease` and both Deployments to become Ready.
2. Check the synchronization. Read the monitor's address on your machine:

   ```bash
   export KUBECONFIG=<standby-kubeconfig>
   ac -n cpaas-system get svc etcd-sync-monitor -o jsonpath='{.spec.clusterIP}{"\n"}'
   unset KUBECONFIG
   ```

   Then run the check on a standby control plane node; put an IPv6 address in brackets, for example `[fd00::10]`:

   ```bash
   curl -g "http://<monitor-cluster-ip>/check"
   ```

   | Result | Action |
   |---|---|
   | Zero missed and zero surplus keys | Continue. |
   | HTTP `425` | Wait, then run the check again. |
   | `LOCAL ETCD missed keys` | Restart the current leader Pod with the commands below, then run the check again. |
   | `LOCAL ETCD surplus keys` | Contact technical support. |

   ```bash
   export KUBECONFIG=<standby-kubeconfig>
   leader_pod=$(ac -n cpaas-system get lease etcd-sync-mirror -o jsonpath='{.spec.holderIdentity}')
   ac -n cpaas-system delete pod "$leader_pod"
   unset KUBECONFIG
   ```

3. **Bare Metal only:** check the shared workload agent identity on each side:

   ```bash
   # Primary: ac config use-cluster global
   # Standby: export KUBECONFIG=<standby-kubeconfig>, and unset KUBECONFIG afterwards
   ac -n cpaas-system get sa/baremetal-system-agent secret/baremetal-system-agent-token \
     role/baremetal-system-agent rolebinding/baremetal-system-agent
   ```

   Continue when all four objects exist on both sides, or none exists on either side; otherwise, contact technical support.

4. On each side, restart the Pods that must reload the DR and endpoint configuration, where installed:

   ```shell
   # Primary: ac config use-cluster global
   # Standby: export KUBECONFIG=<standby-kubeconfig>, and unset KUBECONFIG afterwards
   ac delete po -n cpaas-system -l 'service_name in (alertmanager,vmselect,vminsert)'
   ac delete po -n cpaas-system -l service_name=cpaas-elasticsearch
   ac delete po -n cpaas-system -l service_name=cluster-transformer
   ```

## Failover \{#failover-procedure}

Run the commands on the standby with `<standby-kubeconfig>`.

1. Fence the primary so it cannot write workload resources: stop its control plane, or block its VIP from the workload networks.
2. Run the [sync check](#start-and-verify-synchronization) and require no differences. If the primary is unreachable, the check cannot run: contact technical support before you uninstall the plugin. Then **uninstall** `etcd-sync` from the standby in **Marketplace** → **Cluster Plugins**; scaling the Deployments to zero is not enough, see the warning below. Check that the plugin's marker is gone:

   ```bash
   export KUBECONFIG=<standby-kubeconfig>
   ac -n kube-public get configmap etcd-sync
   unset KUBECONFIG
   ```

   Continue when the command reports `NotFound`; otherwise, wait and run it again. The providers do not reconcile workload clusters while the marker exists.

3. **Bare Metal only:** on the standby, which becomes the active cluster, set `sharedAuthReadOnly` back to `false`:

   ```bash
   export KUBECONFIG=<standby-kubeconfig>
   ac get moduleinfo -l cpaas.io/cluster-name=global,cpaas.io/module-name=cluster-api-provider-baremetal
   ac patch moduleinfo <name> --type=json -p '[{"op":"replace","path":"/spec/valuesOverride/acp~1chart-cluster-api-provider-baremetal/elemental/systemAgent/sharedAuthReadOnly","value":false}]'
   ac -n cpaas-system get deploy elemental-operator -o yaml | grep -- --system-agent-shared-auth-read-only
   unset KUBECONFIG
   ```

   Continue when the last command prints nothing; otherwise, wait and run it again. Until then, new worker nodes cannot obtain their plans.

4. Switch the platform domain to the standby VIP, and check that the platform resolves it there:

   ```bash
   export KUBECONFIG=<standby-kubeconfig>
   ac exec -n cpaas-system deployments/sentry -- nslookup <platform-domain>
   unset KUBECONFIG
   ```

   Continue when the answer is the standby VIP; otherwise, correct the DNS record and run it again.

5. Restart the Pods listed in [step 5](#start-and-verify-synchronization) on the new active cluster. If workload clusters send monitoring data to the `global` cluster, also restart `warlock` in each workload cluster. Log in again first: the platform domain now reaches the new active cluster.

   ```bash
   ac login https://<platform-domain>
   ac config use-cluster <cluster-name>
   ac delete po -n cpaas-system -l service_name=warlock
   ac config use-cluster global
   ```

6. To protect the new active cluster again, make the former primary the new standby once it is healthy: install `etcd-sync` on it with the reverse active and standby values, as in [step 4](#install-etcd-sync), with the former primary's kubeconfig in place of `<standby-kubeconfig>`. The active-cluster token now comes from the new active cluster. **Bare Metal only:** first set `sharedAuthReadOnly: true` on it as in [step 2](#install-primary-and-standby-clusters), and keep the same `baremetal-dr-rules` ConfigMap.

<Directive type="warning" title="Uninstall the mirror, do not just scale it down">
  On startup `etcd-sync` refuses to run when the cluster the platform domain points to has `etcd-sync` installed. If step 2 only scaled the Deployments to zero, the `ModuleInfo` still exists and the new standby refuses to start with:

  ~~~text
  check failed, error: moduleinfo <name> is found, it shouldn't happen,
    please remove it or check the DNS resolution of platformURL: <platform-domain>
  ~~~

  Delete the `etcd-sync` `ModuleInfo` on the new active cluster; the new standby then starts normally.
</Directive>

Switching back to the former primary is not this procedure run in reverse: plan it separately, deciding which side holds the authoritative data and how changes made on the standby since the failover are kept.

After the switch, verify on the new active cluster that every workload `Cluster` and `Machine` object is intact: on Alauda OS a lost `Machine` object becomes a deleted node. Also check:

<Tabs>
<Tab label="Bare Metal">

- Each `BaremetalMachine` still references the expected `MachineInventory`.
- A workload plan reaches `Applied` and its feedback is updated.
- A workload ISO whose URL uses the platform domain can register a new host.
- `global` hosts still use the local VIP, local token, and local plan Secrets.

</Tab>
<Tab label="Huawei DCS">

- The `DCSMachine` objects are intact, and no VM was deleted.
- The workload clusters' credential Secrets exist in `cpaas-system`.

</Tab>
<Tab label="VMware vSphere">

- The `VSphereMachine`, `VSphereVM`, and `VSphereMachineConfigPool` objects are intact, and no VM was deleted. The pools' slot and persistent disk status must have survived the synchronization.
- The workload clusters' vCenter credential Secrets exist in `cpaas-system`.

</Tab>
<Tab label="Huawei Cloud Stack">

- `HCSCluster global` reports its own side's VIP as the control plane endpoint, and the platform ELB listeners answer on it.
- The `HCSMachine` and `HCSMachineConfigPool` objects are intact, and no instance was deleted. The pools' persistent disk status must have survived the synchronization.
- The workload clusters' HCS credential Secrets exist in `cpaas-system`.

</Tab>
</Tabs>

## Operations \{#operational-scope}

After installation, operate DR as a separate lifecycle process with an approved runbook:

- Verify the health and replication lag of **<Term name="product" /> Global Cluster Disaster Recovery**, and that the standby can decrypt Secrets created on the primary.
- Before a planned failover, validate both control plane VIPs and the platform access path, and verify that the ports are allowed in both directions.
- On Bare Metal, update `baremetal-dr-rules` on both sides whenever a `global` host is added or replaced.

<Directive type="warning" title="Verify consistency before uninstalling Alauda Container Platform Global Cluster Disaster Recovery">
A failover and a DR-aware `global` cluster upgrade both uninstall **<Term name="product" /> Global Cluster Disaster Recovery**. Before that, confirm that the standby data is consistent with the primary. Workload nodes are backed by Cluster API `Machine` objects, so an inconsistent sync can delete those objects and destroy the backing machines. If the check reports missing or surplus keys, do not uninstall the plugin; resolve the inconsistency or contact technical support. For the upgrade, see [Upgrade in a DR Environment](../../upgrade/global/upgrade_global_dr.mdx).
</Directive>

### Observability Placement \{#observability-placement}

DR replicates only the `global` cluster's etcd data. Metrics and logs are stored outside etcd, so they are never copied to the standby. Plan observability before you install either cluster:

- Each `global` cluster collects, stores, and queries its own metrics and logs, so the standby can observe itself immediately after a failover.
- Do not write workload cluster monitoring and logging to either `global` cluster. Aggregate them in a dedicated workload cluster that runs the VictoriaMetrics Center and the log storage. A network zone that cannot reach it gets its own aggregation cluster.

For the synchronized and excluded scope, see [Global Cluster Disaster Recovery](../non_alauda_os/global_dr.mdx).

## Troubleshooting \{#troubleshooting}

| Symptom | First check |
| --- | --- |
| The new standby's `etcd-sync` refuses to start after a failover | The warning in [Failover](#failover-procedure). |
| The monitor reports differences | The active and standby direction, the rule snapshot, and the fencing state. |
| Workload machines are not reconciled after a failover | Whether `kube-public/etcd-sync` still exists on the new active cluster. |
| Bare Metal: the rule source is `rejected` | The rule data keys, the syntax, and the `message` annotation. |
| Bare Metal: a `global` plan is overwritten | Its exact Secret key is missing from `ignore-equal.txt`. Stop sync and update both rule ConfigMaps. |
| Bare Metal: a `global` inventory is deleted | The `etcd-sync` version; see [step 4](#install-etcd-sync). Stop sync before restoring the local object. |
| Bare Metal: a workload host gets `401` or `403` | `sharedAuthReadOnly` still `true` on the active cluster, the signing key, the shared token Secret, and the Role `resourceNames`. |

For how Bare Metal DR handles host endpoints, identities, and synchronization rules, see [Bare Metal DR Model](./bare-metal/reference/dr-model.mdx).
