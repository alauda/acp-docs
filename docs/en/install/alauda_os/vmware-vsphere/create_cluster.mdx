# Create the global Cluster on VMware vSphere

## Prerequisites \{#prerequisites}

- You completed the [common prerequisites](../prerequisites.mdx) and the [VMware vSphere prerequisites](./prerequisites.mdx).
- The Core Package is extracted on the bootstrap node and its payload is in the external registry; see [Prepare the Core Package and the Registry](../prerequisites.mdx#prepare-core-package).
- For a disaster recovery pair, write both files as described in [Create a Global Cluster Disaster Recovery Pair](../global_dr.mdx#configure-install-config), then run this procedure on each side.

## Procedure

### 1. Write `install-config.yaml` \{#install-config}

Create an installation directory on the bootstrap node and write `install-config.yaml` in it. Keep the file private (`chmod 600 install-config.yaml`); it holds the passwords.

Copy the following template and fill in the placeholders. The numbered lines are specific to VMware vSphere and are described below the template; for the other fields, see [Common `install-config.yaml` Fields](../reference.mdx#install-config). For the objects that `ac` renders from this file, see [Rendered Manifests](./reference/install-config-parameters.mdx).

Make sure that a datastore, folder, or port group given as an inventory path exists.

### 2. Create the Cluster \{#create}

On the bootstrap node:

```bash
<extract-dir>/res/<arch>/ac adm alpha global create --dir <install-dir> --provider vsphere
```

`ac` first checks the CPI image in the Core Package, the vCenter sign-in, and the vCenter objects named in `install-config.yaml`. If a check fails, nothing is changed and the error names the first missing item. Make sure that an `external` load balancer is ready before you run `create`.

`create` returns when the installation is complete. If `create` stops, run the same command again; completed work is skipped. See [The `create` Command](../reference.mdx#create-command).

### 3. Monitor the Installation \{#monitor}

From another terminal on the bootstrap node:

```bash
<extract-dir>/res/<arch>/ac adm alpha global status
```

For the stages and common failures, see [Troubleshooting](../troubleshooting.mdx); for VMware vSphere failures, see [Troubleshooting on VMware vSphere](./troubleshooting.mdx).

## Verification

When `create` returns, the installation is complete, but some platform components can take a few more minutes to become ready. Wait for them as described in [Additional Checks for Alauda OS](../../validation.mdx#alauda-os-checks) before you judge the result, then verify the platform as described in [Validation](../../validation.mdx), including its [checks for Alauda OS](../../validation.mdx#alauda-os-checks).

**Applies to**: a Self-built VIP (`cluster.network.loadBalancer.type: internal`). Skip it with an `external` load balancer.

Log in to a control plane node of the `global` cluster as the `boot` user, with the private key of an SSH public key in `cluster.sshKeys` (`ssh boot@<control-plane-node-ip>`). Only `root` can read the cluster CA file, so run `curl` with `sudo`:

```bash
sudo curl --cacert /etc/kubernetes/pki/ca.crt https://<control-plane-vip>:6443/healthz
```

Continue when it prints `ok`; otherwise see [Troubleshooting on VMware vSphere](./troubleshooting.mdx).
