# Create a Global Cluster Disaster Recovery Pair

This page creates a disaster recovery (DR) pair of `global` clusters, from planning to the first synchronization. Read it before you write the first `install-config.yaml` of either side.

| You are | Go to |
|---|---|
| Planning, or installing the two sides | The sections below, from the top |
| You already installed a single `global` cluster | [Decide Before You Install](#decide-before-you-install) |
| Both sides are installed | [Start Synchronization](#start-synchronization) |
| The primary has failed, or you switch over on purpose | [Fail Over to the Standby global Cluster](./disaster_recovery_failover.mdx) |

## What a DR Pair Is \{#what-a-dr-pair-is}

A DR pair is two `global` clusters: a primary and a standby. The primary is the `global` cluster that serves the platform access address, a domain name: in normal operation the domain points to it, except while you install the standby and during a failover. The other is the standby. After a failover, the former standby is the new primary.

Each side is an ordinary installation with ACP CLI (`ac`), run from its own bootstrap node with its own `install-config.yaml`. After both sides are installed, **<Term name="product" /> Global Cluster Disaster Recovery** (`etcd-sync`) on the standby copies the primary's etcd data to it. `ac` prepares every `global` cluster for DR, so a DR pair needs no manifest edits. Each side's infrastructure credentials are not synchronized, so the two sides can use different infrastructure accounts.

This page applies to every provider. Steps that only Bare Metal needs are marked **Bare Metal only**.

## Decide Before You Install \{#decide-before-you-install}

Decide before you write the first `install-config.yaml` of either side. The standby can decrypt the primary's Secrets only with the primary's encryption key, and an installed cluster keeps the key it was installed with. If a `global` cluster is already installed as a single cluster, contact technical support before you install a standby. Do not install a standby with a key of its own: it cannot decrypt the primary's Secrets.

## Prepare for DR \{#prepare-for-dr}

Each side has its own:

- Bootstrap node.
- Infrastructure.
- Control plane VIP.

Both sides must use the same `global.registry` address and account: either one external registry that both sides share, or one registry per side behind one domain name. Workload clusters that use the `global` registry keep this address and account after a failover, so with different values on each side they cannot use the registry of the new primary.

Each side meets the [common prerequisites](./prerequisites.mdx) and the prerequisites of its provider.

Also prepare:

- **The platform domain name.** It is the platform access address. During normal operation it resolves only to the primary VIP, and the standby reaches the primary's platform through it. You point it at a VIP three times during the installation, see [Install the Primary and the Standby](#install-primary-and-standby-clusters), and once more at a failover. Book those changes in advance.
- **A third-party certificate and its private key** for the domain, as the same files on both bootstrap nodes.
- **The registry domain name**, with one registry per side. It is `global.registry.address`. It resolves to the registry of the side that the platform domain points at, and you switch both domains together.
- **The shared keys**, generated once; see [Generate the Shared Keys](#generate-the-shared-keys).
- **A copy of each side's installation directory**, in particular `output/kubeconfig`, kept where you can reach it when a site is down.
- **Violet v4.2.13 or later** on a machine that reaches the standby VIP and the standby registry. The `etcd-sync` package is a component of **<Term name="product" /> Global Cluster Disaster Recovery** and is in **ACP Common Aligned Extensions**; see [Install etcd-sync](#install-etcd-sync).

### Generate the Shared Keys \{#generate-the-shared-keys}

Generate each key once and write the same value in both `install-config.yaml` files. A key file holds a secret: run `chmod 600` on it and keep it private.

Run the commands on a Linux machine with OpenSSL. Encryption key for Secrets at rest:

```bash
openssl rand -base64 32 > dr-encryption.key
chmod 600 dr-encryption.key
```

`ac` uses the value as it is and checks it before it changes anything: it must be the base64 of a 16, 24, or 32 byte key, as the command above produces.

**Bare Metal only:** the key that signs ServiceAccount tokens:

```bash
openssl genrsa -out sa.key 2048
base64 -w0 sa.key > sa.key.b64
chmod 600 sa.key sa.key.b64
```

The signing key cannot be changed after installation: if the cluster already holds a different `global-sa`, `ac` stops rather than overwrite it.

## Network \{#network-requirements}

Before you install either cluster, ask your network administrator for the flows that the communication matrix marks **Global DR**, allowed in both directions between the two sides' networks and, for a VIP on a load balancer, forwarded on both VIPs. See [Platform Access Address and `global` VIP](../prepare/communication_matrix.mdx#global_vip) and [Global Disaster Recovery](../prepare/communication_matrix.mdx#global_dr).

The nodes of each side pull their images from the registry in `global.registry`; the flows to it are in [Image Registry](../prepare/communication_matrix.mdx#image_registry).

## Observability Placement \{#observability-placement}

DR replicates only the `global` cluster's etcd data. Metrics and logs are stored outside etcd, so they are never copied to the standby. Plan observability before you install either cluster:

- Each `global` cluster collects, stores, and queries its own metrics and logs, so the standby can observe itself immediately after a failover.
- Do not write workload cluster monitoring and logging to either `global` cluster. Aggregate them in a dedicated workload cluster that runs the VictoriaMetrics Center and the log storage. A network zone that cannot reach it gets its own aggregation cluster.

For the synchronized and excluded scope, see [Global Cluster Disaster Recovery](../non_alauda_os/global_dr.mdx).

## Write the Two install-config.yaml Files \{#configure-install-config}

Write each side's `install-config.yaml` as for a single `global` cluster, following the Create the global Cluster page of your provider, with these values: [Bare Metal](./bare-metal/create_cluster.mdx), [Huawei DCS](./huawei-dcs/create_cluster.mdx), [VMware vSphere](./vmware-vsphere/create_cluster.mdx), or [Huawei Cloud Stack](./huawei-cloud-stack/create_cluster.mdx).

| Field | Primary | Standby |
|---|---|---|
| `global.platform.address` | The platform domain | The same domain |
| `global.platform.cert` | A third-party certificate and key whose SANs cover the domain | The same certificate and key files |
| `global.platform.username`, `global.platform.password` | The platform administrator account | The same values |
| `global.platform.extraAddresses` | `[<primary-vip>]` | `[<standby-vip>]` |
| `cluster.network.loadBalancer.address` (`provider.hcs.elb.vipAddress` on Huawei Cloud Stack) | The primary VIP | The standby VIP |
| `global.registry.address` | The shared registry address, or the registry domain | The same value |
| `global.registry.username`, `global.registry.password` | The registry account | The same values |
| `cluster.encryptionProviderConfig` | The encryption key from [Generate the Shared Keys](#generate-the-shared-keys) | The same value |
| `provider.baremetal.serviceAccountSigningKey` (Bare Metal only) | The content of `sa.key.b64` | The same value |

- **Platform address**: use a domain name, not an IP address. `ac` accepts an IP address here, but `etcd-sync` refuses to run when the platform address is not a domain name.
- **Certificate**: do not omit `global.platform.cert`. Self-signed certificates are not supported for DR: without the field, each side generates its own self-signed certificate, and after a failover clients reject the other side's certificate; on Bare Metal this includes the agents of the workload hosts. For the accepted formats, see [Common `install-config.yaml` Fields](./reference.mdx#install-config).
- **`extraAddresses`**: each side's own VIP, which you use to reach that side while the domain points at the other one. `ac` does not add it.
- **Keys**: write them before the first `manifests` or `create` run on each side. A key that you change afterward does not change what an installed cluster uses; see [Rendered Manifests](./reference.mdx#render-manifests).
- **VM folder** (VMware vSphere): when both sides share a vCenter, you can set a different `provider.vsphere.folder` on each side to keep their VMs apart. The same folder also works.

**Applies to**: every DR pair, before the first `manifests` or `create` run.

Run on each bootstrap node, in the installation directory:

```bash
v=$(awk '$1=="encryptionProviderConfig:"{gsub(/[\r"\047]/,"",$2);print $2}' install-config.yaml); [ -n "$v" ] && printf '%s' "$v" | sha256sum
```

Continue when the command prints a hash and both sides print the same hash; otherwise, set or correct the value in the file that prints nothing or a different hash.

**Bare Metal only.** Run this command as well on each bootstrap node, in the installation directory:

```bash
v=$(awk '$1=="serviceAccountSigningKey:"{gsub(/[\r"\047]/,"",$2);print $2}' install-config.yaml); [ -n "$v" ] && printf '%s' "$v" | sha256sum
```

Continue when the command prints a hash and both sides print the same hash; otherwise, set or correct the value in the file that prints nothing or a different hash.

## Install the Primary and the Standby \{#install-primary-and-standby-clusters}

The platform domain must point to the side being installed. While the domain points at one side, reach the other side through its VIP with the kubeconfig in its installation directory.

| Step | What you do |
|---|---|
| 1 | Point the domain at the primary VIP. On the primary bootstrap node, install the cluster as described on the Create the global Cluster page of your provider. |
| 2 | When the primary is installed, point the domain at the standby VIP. On the standby bootstrap node, install the standby the same way. |
| 3 | When the standby is installed, point the domain back at the primary VIP. |

With one registry per side, point the registry domain at the same side in each step.

When both sides are installed and the domain points at the primary, continue with [Start Synchronization](#start-synchronization).

## Start Synchronization \{#start-synchronization}

After both sides are installed, you install **<Term name="product" /> Global Cluster Disaster Recovery** (`etcd-sync`) on the standby, which then copies the primary's etcd data to it, and you verify the synchronization.

Before you start:

- The platform domain points at the primary VIP.
- Both sides were installed with the same `cluster.encryptionProviderConfig`; see [Generate the Shared Keys](#generate-the-shared-keys). If they were not, contact technical support before you continue.
- **Applies to** workload clusters on infrastructure other than the `global` cluster's own: install that provider on **both** `global` clusters, so that the standby can reconcile the same workload clusters after a failover. See [Prepare](../../workload_clusters/alauda_os/prepare/index.mdx). Upload to the standby with the standby's `--platform-address` and `--dest-repo`, as in [step 1](#install-etcd-sync). Skip it otherwise: `ac` has installed the provider of its own platform on each side.

### Conventions \{#conventions}

Run the commands on a machine with `ac` that reaches both sides:

- **Primary**: log in once with `ac login https://<platform-domain> --name <session-name>` as the platform administrator while the domain points at the primary. Commands for the primary start with `ac config use-cluster global`.
- **Standby**: use the standby's kubeconfig, `output/kubeconfig` in its installation directory, here `<standby-kubeconfig>`. Commands for the standby start with `export KUBECONFIG=<standby-kubeconfig>` and end with `unset KUBECONFIG`.
- To show which cluster a command talks to, run `ac whoami --show-server`.
- In the plugin's parameter names, **Active** means the primary.

The step marked **Bare Metal only** is not numbered.

### 1. Install etcd-sync \{#install-etcd-sync}

Install **<Term name="product" /> Global Cluster Disaster Recovery** (`etcd-sync`) on the standby `global` cluster only, after both sides have completed `create`. It must never be installed on both sides. Use the version released with <Term name="productShort" /> 4.5.

Reach the standby through its VIP.

1. Get the plugin package from **ACP Common Aligned Extensions** and upload it to the standby with **Violet v4.2.13 or later**. Create the token on the standby Web Console (`https://<standby-vip>`): **Profile** → **API Tokens**. Set both `--platform-address` and `--dest-repo` to the standby: otherwise the package goes to the primary. `--dest-repo` is `global.registry.address`, the same on both sides. With one registry per side, run the command on a machine where that address reaches the standby's registry. Use `--no-auth` instead of the registry credentials when the standby registry needs none. For the flags, see [Upload Packages](../../extend/upload_package.mdx#violet_push_usage).

   ```bash
   read -rsp "Standby platform token: " STANDBY_TOKEN; printf '\n'
   read -rsp "Standby registry password: " STANDBY_REGISTRY_PASSWORD; printf '\n'
   violet push <etcd-sync-package>.tgz \
     --platform-address "https://<standby-vip>" --platform-token "${STANDBY_TOKEN}" \
     --dest-repo "<registry-address>" --username "<registry-username>" --password "${STANDBY_REGISTRY_PASSWORD}"
   unset STANDBY_TOKEN STANDBY_REGISTRY_PASSWORD
   ```

2. Create the token Secret on the standby. The value is the bearer token of the primary's `cpaas-system/k8sadmin` ServiceAccount; the commands do not print it:

   ```bash
   ac config use-cluster global
   ac whoami --show-server   # the primary
   PRIMARY_TOKEN=$(ac -n cpaas-system get secret k8sadmin -o jsonpath='{.data.token}' | base64 -d)
   export KUBECONFIG=<standby-kubeconfig>
   ac whoami --show-server   # the standby VIP
   printf '%s' "${PRIMARY_TOKEN}" | ac -n cpaas-system create secret generic etcd-sync-active-cluster-token \
     --from-file=token=/dev/stdin --dry-run=client -o yaml | ac apply -f -
   unset PRIMARY_TOKEN
   unset KUBECONFIG
   ```

3. Open the standby Web Console at `https://<standby-vip>`, go to **Marketplace** → **Cluster Plugins**, select the `global` cluster, and install **<Term name="product" /> Global Cluster Disaster Recovery** with these parameters.

   | Parameter | Value |
   |-----------|-------|
   | Active Global Cluster VIP | Control plane VIP of the primary `global` cluster |
   | Active Global Cluster ETCD Endpoints | Optional. `https://<primary-control-plane-vip>:2379`; separate several addresses with commas |
   | Standby Cluster ETCD Endpoints | Default value |
   | Active Global Cluster Token Secret | `etcd-sync-active-cluster-token` |
   | Data Check Interval (unit: hour) | Default value |
   | Print detail logs | Disabled unless troubleshooting |

### 2. Start and Verify Synchronization \{#start-and-verify-synchronization}

First check that the plugin is running on the standby:

```bash
export KUBECONFIG=<standby-kubeconfig>
ac get moduleinfo -l cpaas.io/module-name=etcd-sync
ac -n cpaas-system get pod -l 'app in (etcd-sync,etcd-sync-monitor)'
unset KUBECONFIG
```

Continue when the `ModuleInfo` shows `STATUS` `Running` and every Pod is `Running`; otherwise, wait and run the commands again. If they do not change, run the steps in [Global Cluster Disaster Recovery Does Not Synchronize](../../upgrade/troubleshooting.mdx#dr-sync-diagnostics).

The mirror copies the primary's data after its start delay. Wait until the initial synchronization has finished:

```bash
export KUBECONFIG=<standby-kubeconfig>
leader_pod=$(ac -n cpaas-system get lease etcd-sync-mirror -o jsonpath='{.spec.holderIdentity}')
ac -n cpaas-system logs "$leader_pod" | grep "Start Sync update"
unset KUBECONFIG
```

Continue when the output contains `Start Sync update`; otherwise, wait and run it again.

Then check the synchronization. Read the monitor's address on your machine:

```bash
export KUBECONFIG=<standby-kubeconfig>
ac -n cpaas-system get svc etcd-sync-monitor -o jsonpath='{.spec.clusterIP}{"\n"}'
unset KUBECONFIG
```

Run the check on a standby control plane node; put an IPv6 address in brackets, for example `[fd00::10]`:

```bash
curl -g "http://<monitor-cluster-ip>/check"
```

| Result | Action |
|---|---|
| Zero missed and zero surplus keys (`localMissedKeys [0]` and `localSurplusKeys [0]`) | Continue. |
| HTTP `425` (`check too frequent`) | Wait, then run the check again. |
| Missed keys are listed (`localMissedKeys`) | Wait until the log of the current leader shows `Start Sync update`, then run the check again. If missed keys remain, restart the leader Pod with the commands below, wait for `Start Sync update` again, and run the check again. |
| Surplus keys are listed (`localSurplusKeys`) | Contact technical support. |
| `paused: true` | Synchronization is paused for an upgrade. Contact technical support. |
| The command fails or prints anything else | Run the steps in [Global Cluster Disaster Recovery Does Not Synchronize](../../upgrade/troubleshooting.mdx#dr-sync-diagnostics), then run the check again. |

```bash
export KUBECONFIG=<standby-kubeconfig>
leader_pod=$(ac -n cpaas-system get lease etcd-sync-mirror -o jsonpath='{.spec.holderIdentity}')
ac -n cpaas-system delete pod "$leader_pod"
unset KUBECONFIG
```

### Bare Metal Only: Check the Shared Agent Identity \{#check-the-shared-agent-identity}

Check the shared workload agent identity on each side:

```bash
# Primary: ac config use-cluster global
# Standby: export KUBECONFIG=<standby-kubeconfig>, and unset KUBECONFIG afterwards
ac -n cpaas-system get sa/baremetal-system-agent secret/baremetal-system-agent-token \
  role/baremetal-system-agent rolebinding/baremetal-system-agent
```

Continue when all four objects exist on both sides, or none exists on either side; otherwise, contact technical support.

### 3. Restart the Dependent Pods \{#restart-the-dependent-pods}

On each side, restart the Pods that must reload the DR and endpoint configuration, where installed:

```bash
# Primary: ac config use-cluster global
# Standby: export KUBECONFIG=<standby-kubeconfig>, and unset KUBECONFIG afterwards
ac delete po -n cpaas-system -l 'service_name in (alertmanager,vmselect,vminsert)'
ac delete po -n cpaas-system -l service_name=cpaas-elasticsearch
ac delete po -n cpaas-system -l service_name=cluster-transformer
```

## Keep It Healthy \{#keep-it-healthy}

- Run the check in [step 2](#start-and-verify-synchronization) regularly. The plugin also checks by itself, by default every hour, and reports the results as the metrics `local_missed_keys_count` and `local_surplus_keys_count`.
- After each change to your workload clusters, save the output of `ac get clusters.cluster.x-k8s.io -A` and `ac get machines.cluster.x-k8s.io -A` from the primary. After a failover you compare against it; see [Fail Over](./disaster_recovery_failover.mdx#check-the-new-primary).
- A DR-aware upgrade of the `global` clusters uninstalls the plugin and has its own consistency check; see [Upgrade `global` Clusters in a DR Environment](../../upgrade/global/upgrade_global_dr.mdx).

## Bare Metal: Agents and the Platform Address \{#bare-metal-dr}

**Bare Metal only.** The agent of a `global` host talks only to the API server of its own `global` cluster, through that cluster's VIP. The agent of a workload cluster host talks to the platform access address, not to the VIP of its cluster, so after a failover it reaches the new primary without any change.

A registration that you create later on a `global` cluster, for example to replace a `global` host, is named `global` or starts with `global-`; otherwise it is not ready and gives no registration URL. It needs these annotations so that its agent uses the local API server:

```yaml
metadata:
  annotations:
    baremetal.cluster.io/system-agent-auth-scope: global
    baremetal.cluster.io/system-agent-server-url: https://<local-control-plane-vip>:6443
    baremetal.cluster.io/system-agent-endpoint-mode: direct-apiserver
```

Otherwise write the registration and its `SeedImage` as in [Create the Registration and the ISO](../../workload_clusters/alauda_os/bare-metal/create_cluster.mdx#step-1-machineregistration-seedimage).

Do not reuse a bootstrap Global ISO after the handover; create a new Global registration and `SeedImage` on the `global` cluster that the host belongs to.
