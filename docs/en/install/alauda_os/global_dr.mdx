# Create a Global Cluster Disaster Recovery Pair

This page describes how to create a disaster recovery (DR) pair of `global` clusters, from planning to the first synchronization. Read it before you write the first `install-config.yaml` for either side.

| Situation | Go to |
|---|---|
| You are planning, or installing the two sides | The sections below, from the top |
| You already installed a single `global` cluster | [Decide Before You Install](#decide-before-you-install) |
| Both sides are installed | [Start Synchronization](#start-synchronization) |
| The primary `global` cluster has failed, or you switch over on purpose | [Fail Over to the Standby global Cluster](./disaster_recovery_failover.mdx) |

## What a DR Pair Is \{#what-a-dr-pair-is}

A DR pair consists of two `global` clusters: a primary `global` cluster and a standby `global` cluster. The primary `global` cluster serves the platform access address, which is a domain name. In normal operation, the domain points to the primary `global` cluster. The exceptions are while you install the standby `global` cluster and during a failover. The other cluster is the standby `global` cluster. After a failover, the former standby `global` cluster becomes the new primary `global` cluster.

You install each side as an ordinary installation with ACP CLI (`ac`), from its own bootstrap node and with its own `install-config.yaml`. After both sides are installed, **<Term name="product" /> Global Cluster Disaster Recovery** (`etcd-sync`) runs on the standby `global` cluster and copies the etcd data of the primary `global` cluster to it. `ac` prepares every `global` cluster for DR. You do not need to edit any manifests for a DR pair. The infrastructure credentials of each side are not synchronized. The two sides can therefore use different infrastructure accounts.

This page applies to every provider. Steps that only Bare Metal needs are marked **Bare Metal only**.

## Decide Before You Install \{#decide-before-you-install}

Decide on DR before you write the first `install-config.yaml` for either side. The standby `global` cluster can decrypt the Secrets of the primary `global` cluster only with the encryption key of the primary `global` cluster. An installed cluster keeps the key that it was installed with.

- If a `global` cluster is already installed as a single cluster, contact technical support before you install a standby `global` cluster.
- Do not install a standby `global` cluster with its own key. Such a standby `global` cluster cannot decrypt the Secrets of the primary `global` cluster.

## Prepare for DR \{#prepare-for-dr}

Each side has its own:

- Bootstrap node.
- Infrastructure.
- Control plane VIP.

Both sides must use the same `global.registry` address and account. Use one of these setups:

- One external registry that both sides share.
- One registry per side, behind one domain name.

Workload clusters that use the `global` registry keep this address and account after a failover. If the values differ between the two sides, those workload clusters cannot use the registry of the new primary `global` cluster.

Each `global` cluster keeps its own registry configuration, and synchronization does not copy it. When the registry password changes, update it on both `global` clusters.

Each side meets the [common prerequisites](./prerequisites.mdx) and the prerequisites of its provider.

Also prepare:

- **The platform domain name.** It is the platform access address. During normal operation, it resolves only to the primary VIP, and the standby `global` cluster reaches the platform of the primary `global` cluster through it. You point it at a VIP three times during the installation and once more at a failover; see [Install the Primary and the Standby](#install-primary-and-standby-clusters). Schedule these changes in advance.
- **A user-provided certificate and its private key** for the domain, with the same files on both bootstrap nodes.
- **The registry domain name**, if you use one registry per side. It is the value of `global.registry.address`. It resolves to the registry of the side that the platform domain points at. You switch both domains together.
- **The shared keys**, generated once; see [Generate the Shared Keys](#generate-the-shared-keys).
- **A copy of each side's installation directory**, in particular `output/kubeconfig`. Store it where you can reach it when a site is down.
- **Violet v4.2.13 or later**, on a machine that can reach the standby VIP and the standby registry. The `etcd-sync` package is a component of **<Term name="product" /> Global Cluster Disaster Recovery** and is shipped in **ACP Common Aligned Extensions**; see [Install etcd-sync](#install-etcd-sync).

### Generate the Shared Keys \{#generate-the-shared-keys}

Generate each key once and write the same value in both `install-config.yaml` files. A key file holds a secret. Run `chmod 600` on it and keep it private.

Run the commands on a Linux machine with OpenSSL. To generate the encryption key for Secrets at rest:

```bash
openssl rand -base64 32 > dr-encryption.key
chmod 600 dr-encryption.key
```

Add the key to both `install-config.yaml` files. Write the key itself on one line, not the file path. To print it, run `cat dr-encryption.key`.

```yaml title="install-config.yaml (both sides)"
cluster:
  encryptionProviderConfig: <dr-encryption-key>
```

`ac` uses the value as it is, and checks it before it changes anything. The value must be the base64 encoding of a 16, 24, or 32 byte key, which the command above produces.

**Bare Metal only:** to generate the key that signs ServiceAccount tokens:

```bash
openssl genrsa -out sa.key 2048
base64 -w0 sa.key > sa.key.b64
chmod 600 sa.key sa.key.b64
```

You cannot change the signing key after installation. If the cluster already holds a different `global-sa`, `ac` stops instead of overwriting it.

## Network \{#network-requirements}

Before you install either cluster, ask your network administrator to allow the flows in [Global Disaster Recovery](../prepare/communication_matrix.mdx#global_dr), in both directions between the networks of the two sides.

The nodes of each side pull their images from the registry in `global.registry`. For the flows to that registry, see [Image Registry](../prepare/communication_matrix.mdx#image_registry).

## Observability Placement \{#observability-placement}

DR replicates only the etcd data of the `global` cluster. Metrics and logs are stored outside etcd, so they are never copied to the standby `global` cluster. Plan observability before you install either cluster:

- Each `global` cluster collects, stores, and queries its own metrics and logs. The standby `global` cluster can therefore observe itself immediately after a failover.
- Do not send the monitoring data and logs of workload clusters to either `global` cluster. Aggregate them in a dedicated workload cluster that runs the VictoriaMetrics Center and the log storage. If a network zone cannot reach that cluster, give the zone its own aggregation cluster.

For what is synchronized and what is excluded, see [Global Cluster Disaster Recovery](../non_alauda_os/global_dr.mdx).

## Write the Two install-config.yaml Files \{#configure-install-config}

Write the `install-config.yaml` of each side as for a single `global` cluster. Follow the Create the global Cluster page of your provider: [Bare Metal](./bare-metal/create_cluster.mdx), [Huawei DCS](./huawei-dcs/create_cluster.mdx), [VMware vSphere](./vmware-vsphere/create_cluster.mdx), or [Huawei Cloud Stack](./huawei-cloud-stack/create_cluster.mdx). Set these values:

| Field | Primary | Standby |
|---|---|---|
| `global.platform.address` | The platform domain | The same domain |
| `global.platform.cert` | A user-provided certificate and key whose SANs cover the domain | The same certificate and key files |
| `global.platform.username`, `global.platform.password` | The platform administrator account | The same values |
| `global.platform.extraAddresses` | `[<primary-vip>]` | `[<standby-vip>]` |
| `cluster.network.loadBalancer.address` (`provider.hcs.elb.vipAddress` on Huawei Cloud Stack) | The primary VIP | The standby VIP |
| `global.registry.address` | The shared registry address, or the registry domain | The same value |
| `global.registry.username`, `global.registry.password` | The registry account | The same values |
| `cluster.encryptionProviderConfig` | The encryption key from [Generate the Shared Keys](#generate-the-shared-keys) | The same value |
| `provider.baremetal.serviceAccountSigningKey` (Bare Metal only) | The content of `sa.key.b64` | The same value |

- **Platform address**: use a domain name, not an IP address. `ac` accepts an IP address here, but `etcd-sync` refuses to run when the platform address is not a domain name.
- **Certificate**: do not omit `global.platform.cert`. DR does not support self-signed certificates. Without the field, each side generates its own self-signed certificate. After a failover, clients then reject the certificate of the other side. On Bare Metal, these clients include the agents of the workload hosts. For the accepted formats, see [Common `install-config.yaml` Fields](./reference.mdx#install-config).
- **`extraAddresses`**: each side lists its own VIP. You use that VIP to reach the side while the domain points at the other side. `ac` does not add the VIP.
- **Keys**: write them before the first `manifests` or `create` run on each side. If you change a key afterward, an installed cluster keeps the key that it was installed with; see [Rendered Manifests](./reference.mdx#render-manifests).
- **VM folder** (VMware vSphere): when both sides share a vCenter, you can set a different `provider.vsphere.folder` on each side to keep their VMs apart. The same folder also works.

**Applies to**: every DR pair, before the first `manifests` or `create` run.

Run this command on each bootstrap node, in the installation directory:

```bash
v=$(awk '$1=="encryptionProviderConfig:"{gsub(/[\r"\047]/,"",$2);print $2}' install-config.yaml); [ -n "$v" ] && printf '%s' "$v" | sha256sum
```

On the machine where you keep the shared keys, also run the following command. It drops the trailing newline of the file and prints the hash of the key. Compare the hashes of both sides with this one:

```bash
tr -d '\r\n' < dr-encryption.key | sha256sum
```

Continue when both sides print the same hash as the key file. On a side that prints nothing or another hash, set `cluster.encryptionProviderConfig` in its `install-config.yaml` to the content of `dr-encryption.key`.

**Bare Metal only.** Also run this command on each bootstrap node, in the installation directory:

```bash
v=$(awk '$1=="serviceAccountSigningKey:"{gsub(/[\r"\047]/,"",$2);print $2}' install-config.yaml); [ -n "$v" ] && printf '%s' "$v" | sha256sum
```

On the machine where you keep the shared keys, also run the following command:

```bash
tr -d '\r\n' < sa.key.b64 | sha256sum
```

Continue when both sides print the same hash as the key file. On a side that prints nothing or another hash, set `provider.baremetal.serviceAccountSigningKey` in its `install-config.yaml` to the content of `sa.key.b64`.

## Install the Primary and the Standby \{#install-primary-and-standby-clusters}

While you install a side, the platform domain must point to that side. To reach the other side meanwhile, use its VIP and the kubeconfig in its installation directory.

| Step | What you do |
|---|---|
| 1 | Point the domain at the primary VIP. On the primary bootstrap node, install the cluster as described on the Create the global Cluster page of your provider. |
| 2 | When the primary `global` cluster is installed, point the domain at the standby VIP. On the standby bootstrap node, install the standby `global` cluster the same way. |
| 3 | When the standby `global` cluster is installed, point the domain back at the primary VIP. |

If you use one registry per side, point the registry domain at the same side as the platform domain in each step.

When both sides are installed and the domain points at the primary `global` cluster, continue with [Start Synchronization](#start-synchronization).

## Start Synchronization \{#start-synchronization}

After both sides are installed, install **<Term name="product" /> Global Cluster Disaster Recovery** (`etcd-sync`) on the standby `global` cluster and verify the synchronization. The plugin copies the etcd data of the primary `global` cluster to the standby `global` cluster.

Before you start:

- The platform domain points at the primary VIP.
- Both sides were installed with the same `cluster.encryptionProviderConfig`; see [Generate the Shared Keys](#generate-the-shared-keys). If they were not, contact technical support before you continue.
- **Applies to** workload clusters on infrastructure other than that of the `global` cluster. Install the provider of that infrastructure on **both** `global` clusters, so that the standby `global` cluster can reconcile the same workload clusters after a failover. See [Prepare](../../workload_clusters/alauda_os/prepare/index.mdx). Upload the provider to the standby `global` cluster with `--platform-address` and `--dest-repo` set to the standby `global` cluster, as in [step 1](#install-etcd-sync). If no workload cluster runs on other infrastructure, skip this item. `ac` has already installed the provider of its own platform on each side.

### Conventions \{#conventions}

Run the commands on a machine that has `ac` and can reach both sides:

- **Primary**: while the domain points at the primary `global` cluster, log in once as the platform administrator with `ac login https://<platform-domain> --name acp` (see [Getting Started with ACP CLI](../../ui/cli_tools/ac/getting-started.md)). Commands for the primary `global` cluster start with `ac config use-cluster global`.
- **Standby**: use the kubeconfig of the standby `global` cluster, `output/kubeconfig` in its installation directory. This page calls it `<standby-kubeconfig>`. Commands for the standby `global` cluster start with `export KUBECONFIG=<standby-kubeconfig>` and end with `unset KUBECONFIG`.
- To show which cluster a command talks to, run `ac whoami --show-server`.
- In the parameter names of the plugin, **Active** means the primary `global` cluster.

The step marked **Bare Metal only** is not numbered.

### 1. Install etcd-sync \{#install-etcd-sync}

Install **<Term name="product" /> Global Cluster Disaster Recovery** (`etcd-sync`) only on the standby `global` cluster, after both sides have completed `create`. Never install it on both sides. Use the version released with <Term name="productShort" /> 4.5.

Reach the standby `global` cluster through its VIP.

1. Get the plugin package from **ACP Common Aligned Extensions** and upload it to the standby `global` cluster with **Violet v4.2.13 or later**.

   - Create the token in the Web Console of the standby `global` cluster (`https://<standby-vip>`): **Profile** → **API Tokens**.
   - Set both `--platform-address` and `--dest-repo` to the standby `global` cluster. Otherwise, the package goes to the primary `global` cluster.
   - `--dest-repo` is `global.registry.address`, which is the same on both sides. If you use one registry per side, run the command on a machine where that address reaches the registry of the standby `global` cluster.
   - If the standby registry needs no credentials, use `--no-auth` instead of the registry credentials.

   For the flags, see [Upload Packages](../../extend/upload_package.mdx#violet_push_usage).

   ```bash
   read -rsp "Standby platform token: " STANDBY_TOKEN; printf '\n'
   read -rsp "Standby registry password: " STANDBY_REGISTRY_PASSWORD; printf '\n'
   violet push <etcd-sync-package>.tgz \
     --platform-address "https://<standby-vip>" --platform-token "${STANDBY_TOKEN}" \
     --dest-repo "<registry-address>" --username "<registry-username>" --password "${STANDBY_REGISTRY_PASSWORD}"
   unset STANDBY_TOKEN STANDBY_REGISTRY_PASSWORD
   ```

2. Create the token Secret on the standby `global` cluster. Its value is the bearer token of the `cpaas-system/k8sadmin` ServiceAccount on the primary `global` cluster. The commands do not print the token:

   ```bash
   ac config use-cluster global
   ac whoami --show-server   # the primary
   PRIMARY_TOKEN=$(ac -n cpaas-system get secret k8sadmin -o jsonpath='{.data.token}' | base64 -d)
   export KUBECONFIG=<standby-kubeconfig>
   ac whoami --show-server   # the standby VIP
   printf '%s' "${PRIMARY_TOKEN}" | ac -n cpaas-system create secret generic etcd-sync-active-cluster-token \
     --from-file=token=/dev/stdin --dry-run=client -o yaml | ac apply -f -
   unset PRIMARY_TOKEN
   unset KUBECONFIG
   ```

3. Open the Web Console of the standby `global` cluster at `https://<standby-vip>`, go to **Marketplace** → **Cluster Plugins**, select the `global` cluster, and install **<Term name="product" /> Global Cluster Disaster Recovery** with these parameters.

   | Parameter | Value |
   |-----------|-------|
   | Active Global Cluster VIP | Control plane VIP of the primary `global` cluster. Required |
   | Active Global Cluster ETCD Endpoints | The etcd addresses of the control plane nodes of the primary `global` cluster, `https://<primary-control-plane-node-ip>:2379`; separate several addresses with commas. Required when the `global` clusters use the Self-built VIP. With a load balancer, you can leave it empty if the load balancers of both `global` clusters forward `2379`; see [Global Disaster Recovery](../prepare/communication_matrix.mdx#global_dr) |
   | Standby Cluster ETCD Endpoints | Default value |
   | Active Global Cluster Token Secret | `etcd-sync-active-cluster-token` |
   | Data Check Interval (unit: hour) | Default value |
   | Print detail logs | Disabled, unless you are troubleshooting |

### 2. Start and Verify Synchronization \{#start-and-verify-synchronization}

First check that the plugin is running on the standby `global` cluster:

```bash
export KUBECONFIG=<standby-kubeconfig>
ac get moduleinfo -l cpaas.io/module-name=etcd-sync
ac -n cpaas-system get pod -l 'app in (etcd-sync,etcd-sync-monitor)'
unset KUBECONFIG
```

Continue when the `ModuleInfo` shows `STATUS` `Running` and every Pod is `Running`. Otherwise, wait and run the commands again. If the results do not change, run the steps in [Global Cluster Disaster Recovery Does Not Synchronize](../../upgrade/troubleshooting.mdx#dr-sync-diagnostics).

The mirror copies the data of the primary `global` cluster after its start delay. Wait until the initial synchronization has finished:

```bash
export KUBECONFIG=<standby-kubeconfig>
leader_pod=$(ac -n cpaas-system get lease etcd-sync-mirror -o jsonpath='{.spec.holderIdentity}')
ac -n cpaas-system logs "$leader_pod" | grep "Start Sync update"
unset KUBECONFIG
```

Continue when the output contains `Start Sync update`. Otherwise, wait and run the commands again.

Then check the synchronization. On your machine, read the address of the monitor:

```bash
export KUBECONFIG=<standby-kubeconfig>
ac -n cpaas-system get svc etcd-sync-monitor -o jsonpath='{.spec.clusterIP}{"\n"}'
unset KUBECONFIG
```

Run the check on a control plane node of the standby `global` cluster. Put an IPv6 address in brackets, for example `[fd00::10]`:

```bash
curl -g "http://<monitor-cluster-ip>/check"
```

| Result | Action |
|---|---|
| Zero missed and zero surplus keys (`localMissedKeys [0]` and `localSurplusKeys [0]`) | Continue. |
| HTTP `425` (`check too frequent`) | Wait, then run the check again. |
| Missed keys are listed (`localMissedKeys`) | Wait until the log of the current leader shows `Start Sync update`, then run the check again. If missed keys remain, restart the leader Pod with the commands below, wait for `Start Sync update` again, and run the check again. |
| Surplus keys are listed (`localSurplusKeys`) | Contact technical support. |
| `paused: true` | Synchronization is paused for an upgrade. Contact technical support. |
| The command fails or prints anything else | Run the steps in [Global Cluster Disaster Recovery Does Not Synchronize](../../upgrade/troubleshooting.mdx#dr-sync-diagnostics), then run the check again. |

To restart the leader Pod, run the following commands. They read the name of the current leader Pod from the `etcd-sync-mirror` Lease on the standby `global` cluster and delete that Pod. Run them only when the table above tells you to:

```bash
export KUBECONFIG=<standby-kubeconfig>
leader_pod=$(ac -n cpaas-system get lease etcd-sync-mirror -o jsonpath='{.spec.holderIdentity}')
ac -n cpaas-system delete pod "$leader_pod"
unset KUBECONFIG
```

### Bare Metal Only: Check the Shared Agent Identity \{#check-the-shared-agent-identity}

Check the shared workload agent identity on each side:

```bash
# Primary: ac config use-cluster global
# Standby: export KUBECONFIG=<standby-kubeconfig>, and unset KUBECONFIG afterwards
ac -n cpaas-system get sa/baremetal-system-agent secret/baremetal-system-agent-token \
  role/baremetal-system-agent rolebinding/baremetal-system-agent
```

Continue when all four objects exist on both sides, or when none of them exists on either side. Otherwise, contact technical support.

### 3. Install the Cluster Plugins \{#restart-the-dependent-pods}

Installing a `global` cluster does not install every cluster plugin, for example <Term name="product" /> Advanced Monitoring. Install the cluster plugins that you need only now, on both `global` clusters, after both clusters are installed and synchronization runs.

## Keep It Healthy \{#keep-it-healthy}

- Run the check in [step 2](#start-and-verify-synchronization) regularly. The plugin also runs the check by itself, every hour by default, and reports the results as the metrics `local_missed_keys_count` and `local_surplus_keys_count`.
- After each change to your workload clusters, save the output of `ac get clusters.cluster.x-k8s.io -A` and `ac get machines.cluster.x-k8s.io -A` from the primary `global` cluster. After a failover, you compare the new primary `global` cluster against this output; see [Fail Over](./disaster_recovery_failover.mdx#check-the-new-primary).
- A DR-aware upgrade of the `global` clusters uninstalls the plugin and has its own consistency check; see [Upgrade `global` Clusters in a DR Environment](../../upgrade/global/upgrade_global_dr.mdx).

## Bare Metal: Agents and the Platform Address \{#bare-metal-dr}

**Bare Metal only.** The agent of a `global` host talks only to the API server of its own `global` cluster, through the VIP of that cluster. The agent of a workload cluster host talks to the platform access address, not to the VIP of its cluster. After a failover, it therefore reaches the new primary `global` cluster without any change.

To add or replace a `global` host after the installation, register it on the `global` cluster that it belongs to. Follow [Hosts for the global Cluster](../../workload_clusters/alauda_os/bare-metal/register_hosts.mdx#global-hosts), which describes the naming rule for the registration and the annotations that point the agent of the host at the local API server.
