# Managing Rollouts in the Web Console

## Overview

A `Rollout` replaces a Deployment when an application is delivered with canary or blue-green strategies. The web console lists Rollouts next to the other workloads, so application teams can see them, inspect their revisions, and perform day-to-day workload operations without the command line.

This page covers viewing and managing Rollout resources. For the deployment strategies themselves, see [Application Blue Green Deployment](./bluegreen_deployment.mdx) and [Application Canary Deployment](./canary_deployment.mdx).

:::note
The console covers the workload: its revisions, its Pods, and its lifecycle. It does not drive the release itself — see [What the console does not cover](#what-the-console-does-not-cover).
:::

## Prerequisites

- **Alauda Container Platform Progressive Delivery** is installed on the cluster. See [Installing Alauda Container Platform Progressive Delivery](./install_argo_rollouts.mdx).

    The **Rollouts** entry appears only on clusters where the plugin is installed. If you switch to a cluster without it, the entry disappears; after installing the plugin, refresh the page.

- You can view workloads in the namespace. Updating, deleting, starting, and stopping a Rollout require the same permission level as for a Deployment.

## Viewing the Rollouts list

1. Access the **Container Platform**.

2. In the left navigation bar, click **Workloads** > **Rollouts**.

The list shows:

| Column | Description |
| --- | --- |
| Name | Click to open the details page |
| Status | `<phase> (<available replicas>/<desired replicas>)`. The phase is one of `Healthy`, `Progressing`, `Paused`, `Degraded`, or `Stopped` |
| Strategy | `Canary` or `Blue-Green` |
| Application | The application the Rollout belongs to, or `-` |
| Created At | Creation time |

`Stopped` means the desired replica count is 0, that is, the Rollout has been stopped from the console.

Use the search box to filter by name and the refresh button to reload.

## Viewing Rollout details

Click a Rollout name to open its details page, which has five tabs:

| Tab | Content |
| --- | --- |
| **Details** | Basic information and containers, including the **Strategy** field and the Services used by that strategy |
| **YAML** | The full resource, read-only |
| **Revisions** | One row per revision, newest first. See below |
| **Pods** | The Pods currently running under this Rollout |
| **Real-time Events** | Events of the Rollout, used to find out why a release is not progressing |

### Revisions

The **Revisions** tab answers three questions: how many revisions are running and with how many replicas each, which revision is the canary and which is the stable one, and what image the previous revision used. The last one matters because a scaled-down revision has no Pods at all and therefore does not appear in the **Pods** tab.

Each row shows the revision number with its role badge (`Canary` / `Stable` for canary releases, `Active` / `Preview` for blue-green; historical revisions have no badge), the ReplicaSet name, the image, the ready and desired Pod counts, the status of that revision, and its creation time.

Click the arrow at the start of a row to expand it and list the Pods of that revision, with name, Pod IP, status, and creation time. For a revision scaled down to 0, the panel is empty — its history and image remain available in the row itself.

:::note
The status in **Revisions** describes a revision (a ReplicaSet) and uses a different set of values than the Rollout status in the list, which describes the Rollout as a whole.
:::

## Creating and updating a Rollout

Both go through the YAML editor:

- **Create**: in the Rollouts list, click **Create Rollout**. The editor opens with a complete example — API version, kind, metadata, replicas, selector, a canary strategy, and a container template — with the namespace already filled in. Edit it and submit.
- **Update**: on the Rollouts list, open the **⋮** menu on a row and click **Update**; or open the details page and click **Actions** > **Update**.

## Starting, stopping, and restarting

On the details page:

- **Stop** sets the desired replica count to 0 and remembers the previous count on the resource itself, so the value survives a page refresh and is the same for every user.
- **Start** restores the remembered replica count. If the Rollout has never been stopped, it starts with 1 replica.
- **Actions** > **Restart** recreates all Pods in place. It does **not** create a new revision and does **not** change the state of a release: a paused Rollout stays paused, and a progressing one keeps progressing.

When a Rollout runs several revisions, the controller distributes replicas across them; the console sets only the total.

## What the console does not cover \{#what-the-console-does-not-cover}

The following actions are not available in the console. Use the `kubectl argo rollouts` plugin or the Argo Rollouts dashboard:

- Release control: promote, full promote, abort, retry, rollback, and setting traffic weight.
- Release progress: the current step, the current traffic weight, the step sequence, and the remaining pause time.
- Analysis resources: `AnalysisTemplate`, `AnalysisRun`, and `Experiment` have no pages in the console.

Deployments that a Rollout has taken over are listed and displayed as usual on the **Deployments** page, without an extra indication.
