# Debugging a Pod by Creating a Copy

## Overview

When a container has already crashed, keeps restarting, or fails its health checks, you cannot open a terminal in it: there is no running process to attach to. **Debug (Copy Mode)** solves this by creating a *debug copy* of the Pod — same image, same volumes, same service account — but started with a shell instead of the original application process. You get a container that stays up, with the application files and configuration in place, so you can start the program by hand and watch it fail.

The copy is an ordinary Pod. It needs no privileged container and no extra capability, so it also works in namespaces that enforce the `restricted` Pod Security Standard.

:::note
The original Pod is never modified. Starting a debug copy does not restart, delete, or reschedule it.
:::

## Prerequisites

- You have permission to create Pods in the namespace.
- The Pod has at least one container that is not running and ready. Containers that are running normally do not appear in the menu — use **EXEC** or **Debug** for those.

## Creating a debug copy

1. Access the **Container Platform**.

2. Go to the Pod you want to debug, in either place:

    - In the left navigation bar, click **Workloads** > **Pods**, then open the **⋮** menu on the Pod's row.
    - Open the Pod's details page and click **Actions**.

3. Click **Debug (Copy Mode)**, then click the name of the container you want to debug under **Target Container**.

4. In the dialog, review the description and the volume warning, then set **Command**.

    The default is `/bin/sh`, which keeps the container running and lets you start the application yourself. The whole input is passed to `/bin/sh`, so arguments, quotes, pipes, `&&`, and environment variables all work — for example `export LOG_LEVEL=debug && /app/start.sh`.

    **Original Startup Commands** and **Original Arguments** above the input show what the container declares in the Pod, so you can copy them and run them by hand after the copy starts. They are read-only.

5. Click **Confirm**.

    A terminal window opens and the copy is created inside it. While the copy is starting, the window shows its current status and reason. When the target container is running, the terminal connects automatically.

:::note
If your browser blocks the terminal window, allow pop-ups for the platform address and click **Confirm** again.
:::

## Which containers can be debugged

The **Target Container** list only offers containers where a debug copy actually helps:

| Container state | Available in Debug (Copy Mode) |
| --- | --- |
| Running and ready | No — use **EXEC** or **Debug** instead |
| Running but not ready, for example failing a health check | Yes |
| Not running: crash looping, exited, or still starting | Yes |
| Waiting because the Pod is not scheduled yet | Yes |
| Waiting because the image cannot be pulled | No — the copy would fail to pull the same image |

**Debug (Copy Mode)** is hidden on a Pod that is itself a debug copy: you cannot make a copy of a copy.

## What the copy contains

| Item | In the copy |
| --- | --- |
| Image | Same as the original container |
| Node | Same node as the original Pod. If the original Pod is not scheduled yet, the cluster schedules the copy |
| Target container command | The command you entered, run by `/bin/sh` |
| Other containers, including sidecars | Started with `/bin/sh`, so they provide an environment but not their original function |
| Init containers | Kept and executed as configured |
| Volumes, service account, secrets, environment variables | Same as the original Pod |
| Security context, resource requests and limits | Inherited from the original Pod |
| Health checks and lifecycle hooks | Removed, so a process you start by hand is not killed |
| Restart policy | The copy does not restart after a process exits, which keeps the scene for inspection |
| Labels and owner references | Removed, so the copy receives no traffic and is not adopted by the original workload |
| Name | Original Pod name plus `-debug-` and a random suffix |

The copy counts against the project quota while it exists.

## Limitations

- **A `ReadWriteOncePod` volume prevents the copy from starting.** That access mode allows only one Pod to mount the volume, and the original Pod already holds it.
- **On shared storage such as NFS, the copy and the original Pod may write the same data at the same time.** Keep this in mind before you start the application inside the copy.
- The copy does not carry the additional network interfaces of the original Pod.

## Ending the debug session

Closing the terminal window, or closing the terminal tab, deletes the copy. Both do the same thing.

While it exists, the copy appears in the **Pods** list like any other Pod, so you can also delete it there with **Delete**.

If the browser crashes or the network drops before the copy is deleted, the platform reclaims it on the backend — a leftover copy does not need manual cleanup.
