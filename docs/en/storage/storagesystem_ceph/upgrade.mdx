# Upgrade

Use this procedure when you publish a new **Alauda Build of Rook-Ceph** Operator version into OperatorHub on an existing cluster.

To move an existing cluster from Ceph Squid (v19) to Ceph Tentacle (v20), see [Upgrade Ceph from Squid (v19) to Tentacle (v20)](#upgrade-squid-to-tentacle). That upgrade changes the Operator channel and is not triggered by publishing a package alone.

Approving that Operator package is the confirmation for both the Operator control plane and the Ceph image bound to the package. You do not patch `CephCluster.spec.cephVersion.image` from the console, and you do not wait on the details page for the data plane to finish.

The recommended path is the **Upgrade to** button on the Rook-Ceph cluster details page. That button only approves the pending `InstallPlan` for `rook-ceph/rook-operator`. Use `kubectl` when the button is unavailable.

:::warning
Confirm that the Rook Operator `Subscription` uses **Manual** approval before you upload the new package. If `installPlanApproval` is `Automatic`, OLM starts the Operator upgrade as soon as the new version appears in the catalog.
:::

## Before you start

- Identify the namespace of the Rook Operator. The default namespace created by the Distributed Storage wizard is `rook-ceph`.
- Download the new **Alauda Build of Rook-Ceph** Operator package that matches the cluster architecture.
- For **internal mode**, confirm `CephCluster` is `Ready` and `status.ceph.health` is `HEALTH_OK`. The details-page button stays disabled while local health is not `HEALTH_OK`.
- For **external mode** (`spec.external.enable: true`), the same button upgrades only the Operator. It does not write a local Ceph image.
- Do not edit generated CSV manifests as a persistent customization. Subsequent OLM reconciles can overwrite those edits. See [Architecture](./architecture.mdx).

## Procedure

### 1. Confirm Manual approval \{#confirm-manual-approval}

```bash
kubectl -n rook-ceph get subscription rook-operator \
  -o jsonpath='{.spec.installPlanApproval}{"\n"}'
```

The output must be `Manual`. If it is not, set it before you upload the package:

```bash
kubectl -n rook-ceph patch subscription rook-operator --type merge \
  -p '{"spec":{"installPlanApproval":"Manual"}}'
```

You can also set **Upgrade Strategy** to **Manual** in **Marketplace** > **OperatorHub** > **Alauda Build of Rook-Ceph**.

### 2. Upload the new Operator package

Upload the new **Alauda Build of Rook-Ceph** package with `violet`, then confirm the target version is visible in OperatorHub.

Follow [Upload Packages](../../extend/upload_package.mdx) and the OperatorHub steps in [Operator](../../extend/operator.mdx).

After the upload succeeds, OperatorHub shows the new version as available. Do not approve it until `installPlanApproval` is `Manual`.

### 3. Approve the Operator package \{#approve-operator-package}

OLM creates an `InstallPlan` for the new CSV. Approving that plan accepts the Operator version and the Ceph image bound to that package.

#### Recommended: Ceph details page

1. Log in and switch to the **Administrator** view.
2. Open the Rook-Ceph cluster details page.
3. When the button is enabled, it shows **Upgrade to** followed by the target CSV version. The version comes from the pending InstallPlan target CSV (`spec.version`, or the version segment of the CSV name such as `rook-ceph.v4.4.1` → `4.4.1`).
4. Click the button. The console sets that InstallPlan `spec.approved` to `true`. You can leave the page.

The button stays disabled when:

- The current user cannot update `InstallPlan` objects in `rook-ceph`.
- The cluster is internal mode and `status.ceph.health` is not `HEALTH_OK`.
- There is no pending unapproved InstallPlan referenced by `Subscription.status.installPlanRef`. A newer CSV in the catalog is not enough if OLM has not created that InstallPlan.

While an approved plan is installing, the button can show that an upgrade is in progress. After the pending plan disappears, it shows that no upgrade is available.

The button does not write `spec.cephVersion.image`, does not create a `StorageCluster`, and does not parse PackageManifest images.

#### Fallback: kubectl

```bash
kubectl -n rook-ceph get subscription rook-operator \
  -o jsonpath='{.status.state}{"\n"}{.status.installedCSV}{"\n"}{.status.currentCSV}{"\n"}{.status.installPlanRef.name}{"\n"}'
```

`UpgradePending` and `InstallPlanPending=True` mean the plan is waiting for approval. Approve only that referenced plan:

```bash
PLAN="$(kubectl -n rook-ceph get subscription rook-operator -o jsonpath='{.status.installPlanRef.name}')"
kubectl -n rook-ceph patch installplan "$PLAN" --type merge \
  -p '{"spec":{"approved":true}}'
```

### 4. Verify the Operator and data plane

Wait until the new CSV is `Succeeded` and the `Subscription` is `AtLatestKnown`:

```bash
kubectl -n rook-ceph get csv
kubectl -n rook-ceph get subscription rook-operator \
  -o jsonpath='{.status.state}{"\t"}{.status.installedCSV}{"\n"}'
```

For **internal mode**, after the installed CSV is `Succeeded`, the platform writes the unique CSV `relatedImages` entry whose `name` is `ceph` onto `CephCluster.spec.cephVersion.image`. If that image is already the running value, Ceph daemons do not roll. If the package has no unique `name=ceph` image, the platform does not guess another image.

Confirm:

```bash
kubectl -n rook-ceph get cephcluster <cephcluster-name> \
  -o jsonpath='phase={.status.phase} health={.status.ceph.health} image={.spec.cephVersion.image}{"\n"}'
```

- `phase=Ready` and `health=HEALTH_OK`.
- `spec.cephVersion.image` matches the unique CSV `relatedImages` entry named `ceph`.
- Existing PVCs remain `Bound`.

For **external mode**, skip the local image check. Existing consumer volumes should remain `Bound`.

## Upgrade Ceph from Squid (v19) to Tentacle (v20) \{#upgrade-squid-to-tentacle}

Each Ceph major version is delivered in its own Operator channel of the `rook-operator` package:

| Channel | Rook | Ceph |
|---|---|---|
| `alpha` | 1.19 | 19.2 Squid |
| `stable-1.20` | 1.20 | 20.2 Tentacle |

An existing cluster stays on its current channel. Publishing the Tentacle package to the catalog does not move it. You choose when to upgrade by switching the `Subscription` channel. If you do not switch the channel, the cluster keeps running Ceph Squid.

:::warning
The upgrade from Squid to Tentacle cannot be rolled back. After Ceph daemons run Tentacle, do not switch the `Subscription` back to `alpha`, and do not set `CephCluster.spec.cephVersion.image` to a Squid image.
:::

This procedure applies to Ceph clusters that you created from the console wizard or with Rook custom resources, where no `StorageCluster` object owns the `CephCluster`. Check it with:

```bash
kubectl get storagecluster -A
```

If the output lists a `StorageCluster` of type `Ceph`, do not use this procedure.

### Requirements

#### Platform

- The cluster runs <Term name="productShort" /> 4.5 or later. Rook 1.20 requires Kubernetes 1.31 or later, so upgrade the platform before you upgrade Rook-Ceph.
- The `rook-operator` package that contains the `stable-1.20` channel is uploaded to the catalog. See [Upload Packages](../../extend/upload_package.mdx).

#### Node kernel

All nodes that run Ceph daemons or mount Ceph volumes must meet these requirements:

| Requirement | Minimum | Applies to |
|---|---|---|
| Platform node requirement | Supported operating system with the vendor kernel, and Linux kernel 5.8 or later with cgroup v2. See [Supported OS and Kernel Versions](../../install/prepare/node_preprocessing.mdx#supported_os_and_kernels). | All nodes |
| RBD kernel client | Linux kernel 5.3 or later | Nodes that mount block (RBD) volumes |
| CephFS kernel client | Vendor-maintained kernel from a supported operating system. If the kernel is too old for the cluster features, use the FUSE client. | Nodes that mount file system (CephFS) volumes |
| In-transit encryption | Linux kernel 5.11 or later | Only when [in-transit encryption](./how_to/in-transit-encryption.mdx) is enabled |

Check the kernel version of every node:

```bash
kubectl get nodes -o custom-columns=NODE:.metadata.name,KERNEL:.status.nodeInfo.kernelVersion,OS:.status.nodeInfo.osImage
```

:::note
This upgrade was validated on Red Hat Enterprise Linux 9.6 with kernel `5.14.0-570.12.1.el9_6` for both RBD and CephFS kernel clients.
:::

#### Cluster state

- `CephCluster` is `Ready` and `status.ceph.health` is `HEALTH_OK`.
- All PVCs that use Ceph storage classes are `Bound`.
- The `rook-operator` `Subscription` uses **Manual** approval. See [Confirm Manual approval](#confirm-manual-approval).

### What to expect during the upgrade

- The Rook Operator is upgraded first. When the new Operator version reports `Succeeded`, the platform sets `CephCluster.spec.cephVersion.image` to the Tentacle image bound to the package. Rook then upgrades Ceph daemons in this order: monitors, managers, metadata servers (MDS), and OSDs.
- **CephFS is briefly unavailable.** To upgrade the MDS, Rook reduces the file system to one active MDS, stops the standby MDS, and restarts the active MDS on the new version. Until that MDS is running again, CephFS I/O pauses and resumes automatically. In validation the pause lasted about 10 seconds. Plan the upgrade during a maintenance window if workloads are sensitive to CephFS pauses. This also happens for later Ceph version updates.
- While monitors restart, `ceph status` can briefly report `MON_DOWN`. While the MDS restarts, it can briefly report `MDS_ALL_DOWN`. These checks clear when the daemons are running again.
- RBD volumes remain available during the upgrade. OSDs restart one at a time.

### Procedure

#### 1. Check the current state

```bash
kubectl -n rook-ceph get subscription rook-operator \
  -o jsonpath='channel={.spec.channel} approval={.spec.installPlanApproval} installed={.status.installedCSV}{"\n"}'
kubectl -n rook-ceph get cephcluster <cephcluster-name> \
  -o jsonpath='phase={.status.phase} health={.status.ceph.health} version={.status.version.version}{"\n"}'
```

Expected: `channel=alpha`, `approval=Manual`, `phase=Ready`, `health=HEALTH_OK`, and a `19.2.x` version.

Confirm that the catalog offers the `stable-1.20` channel:

```bash
kubectl -n cpaas-system get packagemanifest rook-operator \
  -o jsonpath='{range .status.channels[*]}{.name}={.currentCSV}{"\n"}{end}'
```

#### 2. Switch the Subscription channel

```bash
kubectl -n rook-ceph patch subscription rook-operator --type merge \
  -p '{"spec":{"channel":"stable-1.20"}}'
```

OLM creates an `InstallPlan` for the latest CSV in `stable-1.20`. Intermediate versions are skipped.

#### 3. Approve the InstallPlan

Approve the pending plan from the Ceph details page or with `kubectl`, as described in [Approve the Operator package](#approve-operator-package). Approving the plan starts the Ceph major version upgrade.

```bash
PLAN="$(kubectl -n rook-ceph get subscription rook-operator -o jsonpath='{.status.installPlanRef.name}')"
kubectl -n rook-ceph get installplan "$PLAN" \
  -o jsonpath='{.spec.clusterServiceVersionNames}{"\n"}'
kubectl -n rook-ceph patch installplan "$PLAN" --type merge \
  -p '{"spec":{"approved":true}}'
```

Confirm that the plan targets a `stable-1.20` CSV before you approve it.

#### 4. Wait for the upgrade to finish

Watch the daemon versions until every daemon reports `20.2.x`:

```bash
kubectl -n rook-ceph get deployments -l rook_cluster=rook-ceph \
  -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.metadata.labels.ceph-version}{"\n"}{end}'
```

In validation on a three-node cluster with six OSDs, the upgrade finished in about 7 minutes. The time grows with the number of OSDs.

#### 5. Verify

```bash
kubectl -n rook-ceph get csv
kubectl -n rook-ceph get cephcluster <cephcluster-name> \
  -o jsonpath='phase={.status.phase} health={.status.ceph.health} version={.status.version.version}{"\n"}'
kubectl get pvc -A | grep -v Bound
```

- The new CSV is `Succeeded`.
- `phase=Ready`, `health=HEALTH_OK`, and the version is `20.2.x`.
- No Ceph-backed PVC is in a state other than `Bound`.
- Existing workloads can read their data, and new PVCs can be created and mounted.

If the toolbox is available, confirm that all daemons run Tentacle:

```bash
kubectl -n rook-ceph exec deploy/rook-ceph-tools -- ceph versions
```

### If the upgrade does not progress

- **No InstallPlan after switching the channel**: confirm that the `stable-1.20` channel exists in the `PackageManifest` and that the `Subscription` has no `startingCSV` that pins an older version.
- **The Operator is upgraded but Ceph daemons do not roll**: confirm that the new CSV is `Succeeded` and that its `relatedImages` contains exactly one entry named `ceph`.
- **Health stays at `HEALTH_WARN` or `HEALTH_ERR` after all daemons restart**: run `ceph health detail` from the toolbox and resolve the reported checks before you continue.

Do not delete the `CephCluster`, Rook Operator, or PV objects to recover an upgrade.

## If the details-page button stays disabled

1. Confirm the user can update `installplans` in `rook-ceph`.
2. For internal mode, confirm `status.ceph.health` is `HEALTH_OK`.
3. Inspect the Subscription and the referenced InstallPlan:

   ```bash
   kubectl -n rook-ceph get subscription rook-operator
   kubectl -n rook-ceph get installplan
   ```

   If the catalog already has a newer CSV but there is no pending unapproved InstallPlan, check whether `startingCSV` is pinning the Subscription. Do not try to repair that pin from the details page.

4. If the InstallPlan is already approved but the Ceph image did not change, confirm the installed CSV is `Succeeded` and that `relatedImages` contains exactly one entry named `ceph`.

Do not delete the `CephCluster` or PV objects to cancel an upgrade.
