# Plan the Control Plane Endpoint

Every cluster needs a stable endpoint for the Kubernetes API. Select the endpoint mode before you create the cluster.

:::warning
Do not change the control plane endpoint after the cluster is created. The endpoint is part of the API server certificates, the kubeconfigs, and the connection from the `global` cluster.
:::

## Endpoint Modes by Provider \{#endpoint-modes-by-provider}

| Provider | Endpoint modes | What you prepare |
|---|---|---|
| Huawei DCS | External load balancer (default), or a Self-built VIP (`type: internal`). | External: the load balancer, before you create the cluster. Self-built VIP: an IPv4 VIP in the control plane Layer 2 network and a `vrid` unique in that Layer 2 domain. |
| VMware vSphere | External load balancer (default), or a Self-built VIP (`type: internal`). | External: the load balancer, before you create the cluster. Self-built VIP: an IPv4 VIP, a port (typically `6443`), and a `vrid` unique in the control plane Layer 2 domain. |
| Bare Metal | Self-built VIP (default, `type: internal`), or an external load balancer. | Self-built VIP: a free VIP, a port (typically `6443`), and a `vrid` unique in the control plane Layer 2 domain. External: the load balancer, before you create the cluster. |
| Huawei Cloud Stack | An HCS ELB that the provider creates. | The ELB inputs: VIP subnet, VIP address, bandwidth, and public IP preference. See [Create a Cluster on Huawei Cloud Stack](../huawei-cloud-stack/create_cluster.mdx). |

The default applies when `cluster.network.loadBalancer.type` is omitted from `install-config.yaml`.

On Huawei DCS, clusters that already use an external load balancer keep it unless you have a tested migration plan. On VMware vSphere, only a cluster created with `type: internal` can use the Self-built VIP; a cluster whose provider was upgraded from an earlier release keeps its external load balancer. See [Control Plane Endpoint Modes](../vmware-vsphere/prerequisites.mdx#control-plane-endpoint-modes).

## External LoadBalancer Contract \{#external-loadbalancer-contract}

Provision the load balancer before you create the cluster.

| Requirement | Contract |
|---|---|
| Listener | Layer 4 TCP forwarding with TLS passthrough. The Kubernetes API server terminates TLS. |
| Frontend | One stable VIP (an IP address) and TCP port `6443`. |
| Backends | Every control plane node IP on TCP port `6443`. Do not add worker nodes. |
| Health check | Prefer an HTTPS check to `https://<control-plane-node-ip>:6443/healthz` that requires HTTP `200`. Use a TCP check only when the device supports nothing else. |
| Backend ownership | The load balancer owner updates the backends when control plane nodes are added, replaced, or removed. The providers do not manage the backends of an external load balancer. |
| Reachability | All control plane nodes and the `global` cluster reach the frontend. During a `global` installation, the bootstrap node also reaches it. |
| Name and certificate | Use an IP address, not a DNS name (FQDN): cluster access by domain name is not supported. A customer-issued certificate cannot be served on the endpoint. |

For ACP port requirements, see the following pages:

- For a `global` cluster, see [LoadBalancer Forwarding Rules](../../../install/non_alauda_os/prerequisites.mdx#port-forward).
- For a workload cluster, see [Connecting global Cluster and Workload Cluster](../../create_on_non_alauda_os.mdx#connecting-global-cluster-and-workload-cluster).

### Check the Listener Before Creation

Run on a node of the `global` cluster, or on the bootstrap node for a `global` installation:

```bash
nc -vz <control-plane-endpoint> 6443
```

| Result | Action |
|---|---|
| `succeeded` or `open` | Continue. |
| Connection refused or timed out | Confirm in the management interface of the load balancer that the TCP listener on `<control-plane-endpoint>:6443` exists, then continue. Some load balancers accept connections only after a backend is healthy. |

### Check the Health Check After the First Control Plane Node Starts

Run on a host in the network from which the load balancer sends its health checks:

```bash
curl -kfsS https://<control-plane-node-ip>:6443/healthz
```

Continue when the output is `ok`; otherwise, correct the network path or firewall rules between that network and the control plane node.

## Self-built VIP Contract

For Bare Metal, follow the provider-specific guide.

- Reserve an unused IPv4 address in the same Layer 2 network as the control plane interface that will hold the VIP.
- Use a VRID that is unique in that Layer 2 domain.
- Allow VRRP traffic and gratuitous ARP updates between the control plane nodes and the surrounding network.
- Use at least three control plane nodes for high availability.
- Use an IP address, not a domain name, for the Self-built VIP.
- Do not maintain a second, manual backend list for the same VIP: the provider updates it when control plane nodes are replaced.

On VMware vSphere the following additional rules apply:

- The VIP must be IPv4. IPv6 and dual-stack endpoints are not accepted.
- `vrid` must be between `1` and `255`.
- The VIP must not equal any slot address (`network.primary.ip` or `network.additional[].ip`) in the machine config pools of the cluster, and must be outside every external IPAM pool range: the provider does not detect a conflict with an external IPAM pool.
- On nodes with more than one NIC, set `interface` explicitly: it cannot be changed after the cluster is created.

For Huawei DCS, set the endpoint in `cluster.network.loadBalancer`; see [Control Plane Endpoint and HA](../huawei-dcs/reference/install-config-parameters.mdx#configure-dcscluster). For Bare Metal, set the endpoint in `cluster.network.loadBalancer`; see [Write install-config.yaml](../bare-metal/create_cluster.mdx#write-install-config). For VMware vSphere, see [Control Plane Endpoint Modes](../vmware-vsphere/prerequisites.mdx#control-plane-endpoint-modes).
