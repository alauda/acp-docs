# Choose the Image Registry for a Workload Cluster

Alauda Container Platform installs and manages platform components on every workload cluster, such as Kube-OVN and the platform modules delivered after the cluster is up. By default, their images come from the registry that the `global` cluster uses. You can instead bind a workload cluster to a registry of its own, for example a registry close to a workload cluster in another region.

Decide before you create the cluster: an existing cluster cannot be moved to another registry.

## Options \{#options}

| Option | What you configure | When to use it |
| --- | --- | --- |
| Registry of the `global` cluster | Nothing in `install-config.yaml`. | The workload cluster reaches the registry of the `global` cluster with acceptable throughput and availability. |
| Dedicated registry | A RegistryCredential Secret in `cpaas-system` on the `global` cluster, named in `cluster.registrySecretRef` of `install-config.yaml`. | The workload cluster is in a different region or network segment and should pull from a registry close to it. |

A dedicated registry requires platform v4.4.0 or later, on every provider.

## What the Binding Covers \{#coverage}

The binding applies to the platform components that Alauda Container Platform installs and manages on the workload cluster, such as Kube-OVN and the platform modules delivered to it, and on Bare Metal to the OS image that hosts are reprovisioned with. It does **not** apply to the following:

| Not covered | Where it comes from instead |
| --- | --- |
| Images kubeadm manages: kube-apiserver, kube-controller-manager, kube-scheduler, etcd, CoreDNS, and kube-proxy | The Alauda OS image, which preloads them. `ac` sets the kubeadm image repository to `cpaas-registry.cpaas-system/acp/k8s` on every provider, whatever the binding. Use the Alauda OS image published for the platform release: an image from an earlier release cannot start the control plane, even with the same Kubernetes version. |
| The pause (sandbox) image | The container runtime configuration in the Alauda OS image. |
| The Bare Metal ISO image | `SeedImage.spec.baseImage`, which the `global` cluster pulls when it builds the ISO. |
| Application workload images | The image references and pull Secrets that each workload declares. |

## Inherit the Registry of the global Cluster \{#default}

This is the default. Leave `cluster.registrySecretRef` out of `install-config.yaml`. `ac` reads the registry address from the `registry` key of the `public-registry-credential` Secret in `cpaas-system` on the `global` cluster. The key must exist even when the registry needs no authentication.

Check the key before you create the cluster:

```bash
ac config use-cluster global
ac get secret public-registry-credential -n cpaas-system \
  -o jsonpath='{.data.registry}{"\n"}'
```

Continue when the command prints a value; otherwise, contact technical support.

If workload cluster nodes cannot reach the address of the `Platform Built-in` registry on the `global` cluster, see [Add External Address for Built-in Registry](../../how_to/add_external_addr_for_global_registry.mdx).

## Bind a Workload Cluster to Its Own Registry \{#dedicated}

### Before You Start \{#before-you-start}

- You can create Secrets in the `cpaas-system` namespace of the `global` cluster.
- The dedicated registry is reachable from every workload cluster node.
- The dedicated registry already holds Alauda Container Platform Core for the target version, plus the packages for every platform plugin you intend to install on this cluster. See [Prepare the Registry](#prepare-the-registry).

### Step 1 — Prepare the Registry \{#prepare-the-registry}

The platform never copies images into a dedicated registry. Populate it before you create the cluster:

- **Alauda Container Platform Core for the target version**, matching the version and CPU architecture of the cluster.
- **The packages of every platform plugin you intend to install on this cluster.** The platform does not fill gaps later.
- **On Bare Metal, the OS images of every Kubernetes version that the cluster uses.** Hosts pull them from this registry at every reprovision; see [Import the OS Images](../bare-metal/prerequisites.mdx#import-os-images).

Use the same Core Package upload procedure that prepares an external platform image registry, with the dedicated registry as the target address. See [Prepare the Target-Version Payload](../../../install/prepare/external-platform-image-registry.mdx#prepare-the-target-version-payload).

Then check that the registry answers. Run on a host in the network of the workload cluster nodes:

```bash
export DEDICATED_REGISTRY="<registry-host>:<port>"
curl -sk "https://${DEDICATED_REGISTRY}/v2/" -o /dev/null -w '%{http_code}\n'
```

Continue when the output is `200` or `401`; otherwise, correct the network path or the TLS setup of the registry.

:::warning
Confirm in the administration interface or API of the registry that the uploaded repositories and tags are complete before you create the cluster. A cluster bound to an incomplete registry still reaches `Ready`; the gap appears later as platform Pods stuck in `ImagePullBackOff`, and the binding cannot be changed.
:::

### Step 2 — Create the RegistryCredential Secret \{#create-the-secret}

Write the Secret manifest with an editor, not at a shell prompt: a shell keeps the password in its history. Quote values that contain YAML special characters. Use one of the two manifests below.

**Without a private CA**: the system trust store of the nodes verifies the registry certificate. For an anonymous registry, leave out `username` and `password`.

```yaml title="registry-credential.yaml"
apiVersion: v1
kind: Secret
metadata:
  name: <registry-credential-name>
  namespace: cpaas-system
  labels:
    capi.cpaas.io/provider: registry-credential
    cpaas.io/registry-credential-format: direct
type: CloudCredential
stringData:
  registry: <registry-host>:<port>
  username: <username>
  password: <password>
```

**With a private CA**: the registry certificate is self-signed or issued by a private CA. `registry`, `username`, and `password` are all required.

```yaml title="registry-credential.yaml"
apiVersion: v1
kind: Secret
metadata:
  name: <registry-credential-name>
  namespace: cpaas-system
  labels:
    capi.cpaas.io/provider: registry-credential
    cpaas.io/registry-credential-format: direct
type: CloudCredential
stringData:
  registry: <registry-host>:<port>
  username: <username>
  password: <password>
  config.json: |
    {
      "mode": "mirror",
      "endpoints": ["<registry-host>:<port>"],
      "ca": "<base64-encoded-ca>",
      "tlsPolicy": {
        "endpointInsecureSkipVerify": false
      }
    }
```

Keep the file private (`chmod 600 registry-credential.yaml`); it holds the password. Create the Secret on the `global` cluster, and then remove the file:

```bash
chmod 600 registry-credential.yaml
ac config use-cluster global
ac create -f registry-credential.yaml
rm -f registry-credential.yaml
```

:::warning
Do not create or update a credential Secret with `ac apply`: client-side apply stores every value of the manifest, including the password, in an annotation on the Secret. Base64 is an encoding, not protection.
:::

| Key | Required | Notes |
| --- | --- | --- |
| Namespace | Yes | Must be `cpaas-system`. |
| Name | Yes | At most 63 characters. |
| Type | Yes | `CloudCredential`. |
| `capi.cpaas.io/provider` label | Yes | Must be `registry-credential`. `ac` rejects a Secret without this label. |
| `cpaas.io/registry-credential-format` label | Yes | Must be `direct`. Without it, the platform expects the legacy encrypted format instead of the keys below. |
| `registry` | Yes | `<host>[:<port>]` only. No scheme, no path, no trailing `/`. |
| `username`, `password` | Together | Set both or neither. Omit both for an anonymous registry. Both are required with `config.json`. |
| `config.json` | Only for a private CA | See the fields below. |

The fields of `config.json`:

| Field | Value |
| --- | --- |
| `mode` | `mirror`. |
| `endpoints` | One entry, exactly the value of `registry`. |
| `ca` | The output of `base64 -w0 <ca-file>`, not the PEM text. Omit it when `endpointInsecureSkipVerify` is `true`. |
| `tlsPolicy.endpointInsecureSkipVerify` | `false` verifies the registry certificate against `ca`. `true` skips the verification. |

Keep the other fields as shown. Put the account in `username` and `password`, not in `config.json`. `ac` does not check `config.json`: a mistake in it surfaces only while the cluster is being created.

### Step 3 — Reference the Credential When You Create the Cluster \{#reference-the-credential}

Name the Secret in `cluster.registrySecretRef` of `install-config.yaml`, then create the cluster as described in your provider's cluster creation guide:

```yaml
cluster:
  registrySecretRef:
    name: <registry-credential-name>
    namespace: cpaas-system
```

`ac` checks the Secret before it applies anything. If a check fails, nothing is applied, and the error names the problem; see [Troubleshooting](#troubleshooting).

:::warning
The binding is read only when the cluster is created. Changing the `cpaas.io/registry-reference` label on an existing `Cluster` has no effect. To move an existing cluster to another registry, you must recreate the cluster.
:::

### Step 4 — Verify the Binding \{#verify}

#### Check the Registry Address on the global Cluster

```bash
ac config use-cluster global
ac get cluster.platform.tkestack.io <cluster-name> \
  -o jsonpath='{.metadata.labels.cpaas\.io/registry-reference}{" "}{.metadata.annotations.cpaas\.io/registry-address}{"\n"}'
```

Continue when the output is the Secret name followed by the registry address from the Secret; otherwise, see [Troubleshooting](#troubleshooting).

#### Check the Images on the Workload Cluster

```bash
ac config sync
ac config use-cluster <cluster-name>
ac get pods -A \
  -o jsonpath='{range .items[*]}{range .spec.containers[*]}{.image}{"\n"}{end}{end}' \
  | sort -u
ac config use-cluster global
```

Continue when the platform component images use the dedicated registry. Images kubeadm manages and the pause image come from elsewhere; see [What the Binding Covers](#coverage). If every platform component image still uses another registry, see [Troubleshooting](#troubleshooting).

#### Check the Registry Configuration of the Nodes

```bash
ac config use-cluster <cluster-name>
ac -n cpaas-system get registry cpaas-registry -o yaml
ac config use-cluster global
```

Continue when `spec.endpoints` lists the address in the Secret and, with a [private CA](#create-the-secret), `spec.tlsSecretRef.name` is `acp-registry-ca`.

## Operate an Existing Binding \{#operate}

| Task | Supported | How |
| --- | --- | --- |
| Rotate the registry password or switch to another account | Yes | Patch the Secret, as shown below. The platform propagates the change to every cluster that references it, without a cluster restart. |
| Correct the registry address in a credential | Yes | Patch the Secret. Every cluster that references it is repointed: make sure that all of them reach the new address and that it holds the payload for each of their versions. |
| Move an existing cluster to a different registry | No | Recreate the cluster with the intended reference. |
| Share one credential across clusters | Yes | Reference the same Secret from any number of clusters. |
| Delete a credential | Only when unreferenced | The platform rejects the deletion while a cluster still references the Secret, and the error names those clusters. |

Update a credential with `ac patch`, not `ac apply`. Quote values that contain YAML special characters: this file is YAML.

```yaml title="registry-credential-patch.yaml"
stringData:
  username: <new-username>
  password: <new-password>
```

Keep the file private (`chmod 600 registry-credential-patch.yaml`); it holds the password.

```bash
chmod 600 registry-credential-patch.yaml
ac config use-cluster global
ac patch secret <registry-credential-name> --namespace cpaas-system \
  --type=merge --patch-file=registry-credential-patch.yaml

rm -f registry-credential-patch.yaml
```

## Troubleshooting \{#troubleshooting}

| Result | Action |
| --- | --- |
| `ac` stops with `Secret cpaas-system/public-registry-credential …: the workload cluster registry cannot be derived` (no `registrySecretRef` set) | Contact technical support. |
| `ac` stops with `Secret cpaas-system/<registry-credential-name> does not exist …` | Create the Secret as in [Step 2](#create-the-secret), then run `create` again. |
| `ac` stops with `… must have label capi.cpaas.io/provider="registry-credential" …` | Apply both labels as in [Step 2](#create-the-secret), then run `create` again. |
| `ac` stops with `… has no "registry" key …`, `… has an invalid "registry" value …`, or `… keys "username" and "password" must either both be set or both be empty` | Correct the Secret as in [Step 2](#create-the-secret), then run `create` again. |
| `ac` stops with `cluster.registrySecretRef.namespace must be "cpaas-system" …` | Set `namespace: cpaas-system` in `install-config.yaml` and create the Secret there. |
| The Secret is rejected on create or update | Set `registry`, and set `username` and `password` together or leave both out. |
| The Secret is rejected with an unsupported-format message | Set `cpaas.io/registry-credential-format` to `direct`. |
| `cpaas.io/registry-address` on the platform cluster record is empty | Confirm the Secret name, the `cpaas-system` namespace, and both labels; otherwise, contact technical support. |
| The control plane is ready, but platform Pods stay in `ImagePullBackOff` | Repeat the check in [Step 1](#prepare-the-registry) from a workload cluster node, confirm the registry contents, and confirm the credential in the Secret. |
| Deleting a credential is rejected | Read the cluster names from the error. Delete those clusters, or recreate them against a different credential, before you delete this one. |
| A new label value on an existing `Cluster` changes nothing | Recreate the cluster with the intended reference. |
| Value changes to the Secret never reach the clusters, or the Secret can be deleted while clusters still use it | Apply the `capi.cpaas.io/provider: registry-credential` label. See [Step 2](#create-the-secret). |
