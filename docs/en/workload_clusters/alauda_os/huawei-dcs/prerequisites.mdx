# Prerequisites for Huawei DCS Workload Clusters

Meet the following before you [create the cluster](./create_cluster.mdx).

## Providers \{#providers}

Install these cluster plugins on the `global` cluster:

- **Alauda Container Platform Cluster Bootstrap Provider**
- **Alauda Container Platform Infrastructure Provider for Huawei DCS**

A `global` cluster installed on Huawei DCS with `ac` already runs both. Otherwise, download them from **ACP Common Aligned Extensions** (see [Download](../../../install/prepare/download.mdx)), upload them with `violet push` (see [Upload Packages](../../../extend/upload_package.mdx#violet_push_usage)), and install them as described in [Cluster Plugin](../../../extend/cluster_plugin.mdx). In a Global Cluster Disaster Recovery pair, install them on both `global` clusters.

## VM Template and Kubernetes Version \{#resolving-placeholders}

Create a VM template on DCS from the Alauda OS image that is published for the ACP release installed on the `global` cluster. Use the image without changes; see [Downloading Alauda OS](../../../overview/alauda_os_support_matrix.mdx#downloading-alauda-os). Note whether the template runs Alauda OS KO or Alauda OS KU, because the template OS is part of the cluster configuration.

### VM Template ConfigMap \{#vm-template-configmap}

Register each VM template with a ConfigMap on the `global` cluster when you create the template. Create one ConfigMap per VM template. It records:

- the VM template name
- the ACP version whose Alauda OS image the VM template was made from
- the Kubernetes version and the etcd tag of that ACP version

When you create a cluster, `ac` reads `kubernetesVersion` and `etcdTag` from the ConfigMap of the template. The platform upgrade uses these ConfigMaps to find the VM template of each Kubernetes version, and the ConfigMap of the template that a node group runs tells the upgrade the architecture of that group; see [Stage the Alauda OS Images](../../../upgrade/pre-upgrade.mdx#stage-alauda-os-images). The `cpaas.io/dcs-vm-template` label value must match the VM template name on DCS.

In the generator, select every architecture whose VM templates you register. Each generated ConfigMap records its architecture. Run `ac config use-cluster global` first, then the command that the generator prints.

<DcsVmTemplateConfigMap>
  Replace `<os>` with the OS of the VM template, such as `m55`, `ko`, or `ku`. Take `<acp-version>`, `<kubernetes-version>`, and `<etcd-tag>` from the matching row of [Version Mapping](../../../overview/alauda_os_support_matrix.mdx#version-mapping). Create one ConfigMap per architecture. Replace `<architecture>` with `x86_64` or `aarch64`, and write `x86_64` as `x86-64` in the ConfigMap name.
</DcsVmTemplateConfigMap>

For each Kubernetes version, register the VM templates of every architecture that your clusters use. In a cluster that mixes x86_64 and aarch64 node pools, every VM template ConfigMap must set `architecture`.

Check that the ConfigMap of your template exists. Run the following commands from a machine where `ac` is logged in to the platform:

```bash
ac config use-cluster global
ac -n cpaas-system get cm -l cpaas.io/dcs-vm-template -L cpaas.io/dcs-vm-template
```

If no ConfigMap lists your VM template name, create the ConfigMap of your template.

You do not set the Kubernetes or etcd version. If the ConfigMap of your template exists, `ac` installs the versions that it records. Without it, `ac` installs the default Kubernetes version of the platform, which is the version that a template made from the image of the current ACP release carries. A template ConfigMap without `kubernetesVersion` or `etcdTag` is rejected. When a template ConfigMap applies, `ac` prints a `Pinning Kubernetes <version>, etcd <tag>` line. Do not rely on that line. Read the version from `spec.version` of the `KubeadmControlPlane` in `manifests/` instead.

## Network Connectivity \{#network-connectivity}

Allow the flows from the `global` cluster nodes and from the machine that runs `ac` to DCS. The flows are listed in [Huawei DCS](../../../install/prepare/communication_matrix.mdx#provider-dcs). The `global` cluster nodes need these paths to create the cluster and to manage it later.

## Control Plane Endpoint and Image Registry \{#control-plane-endpoint}

The control plane endpoint is an IPv4 address. It is either:

- An external load balancer, which you provision as described in [Plan the Control Plane Endpoint](../../../install/alauda_os/prerequisites.mdx#control-plane-endpoint).
- A Self-built VIP, which the provider runs on the control plane nodes; see [Self-built VIP](../../../install/alauda_os/prerequisites.mdx#self-built-vip).

The cluster pulls its platform components from the registry of the `global` cluster, or from a dedicated registry. See [Choose the Image Registry for a Workload Cluster](../prepare/workload-cluster-image-registry.mdx).

## DCS Credential Secret \{#credential-secret}

A Secret in `cpaas-system` of the `global` cluster must hold the DCS sign-in. Note how the Secret is used:

- The cluster refers to the Secret by name. Unlike the `global` cluster, it does not hold an inline credential.
- `ac` never creates or deletes the Secret.
- One Secret can serve several clusters.

The account must have the `administrator` role and be one of the following user types:

| `userType` | DCS user | DCS-side requirement |
|---|---|---|
| `interconnect`, the default | Interface interconnection user | The policy **Whether to modify the password of an interface interconnection user upon password resetting and first login** (**System Management** → **Rights Management** → **Rights Management Policy**) must be **No**. Otherwise, the forced password change breaks sign-in. |
| `domain` | Domain user, backed by LDAP or AD | Your DCS administrator has configured domain authentication and created the directory user in the DCS portal. The directory service governs its password. |

Use a dedicated account rather than the portal `admin` account. DCS locks an account after repeated failed sign-ins, and locking the portal account would lock everyone else out too.

Write the values in a file with an editor, not on the command line, so the password stays out of shell history:

```text title="dcs-credential.env"
authUser=<auth-user>
authKey=<auth-key>
endpoint=https://<dcs-api-host>:7443
site=<dcs-site-id>
userType=interconnect
```

| Key | Value |
|---|---|
| `authUser` | The DCS API user name. |
| `authKey` | The password in plain text, not the SHA-256 digest that the DCS console shows. |
| `endpoint` | The API address, with `https://` and the port (typically `7443`), and without a trailing slash. |
| `site` | The bare site ID, not the `urn:sites:` form. |
| `userType` | Optional. `interconnect` or `domain`, case-insensitive. Other values are rejected. |

Write each line as `key=value` without quotes, because `ac` keeps quote characters as part of the value. Keep the file private (`chmod 600 dcs-credential.env`), because it holds the password. Create the Secret, then remove the file:

```bash
chmod 600 dcs-credential.env
ac config use-cluster global
ac create secret generic <credential-secret-name> -n cpaas-system --from-env-file=dcs-credential.env
rm -f dcs-credential.env
```

Do not create or update the Secret with `ac apply`, because it stores the password in the `kubectl.kubernetes.io/last-applied-configuration` annotation of the Secret. To change a value later, put the new value under `stringData` in a file, and run `ac patch secret <credential-secret-name> -n cpaas-system --type=merge --patch-file=<file>`.

## DCS Objects, Capacity, and Addresses \{#dcs-objects}

- The following exist on the site: the VM folder, the distributed virtual switches and port groups, the datastore or datastore cluster, and any compute cluster or host that `install-config.yaml` names. `ac` creates none of them. Make sure that they have room for the planned VMs.
- The datastores and hosts have room for the planned VMs. Each node needs its system disk plus every disk of its node group. If a datastore is nearly full, or the hosts are all heavily overcommitted, new VMs get stuck in `creating`.
- Control plane spread places the control plane VMs on different DCS hosts with a DRS rule. To use it, make sure that:
  - DRS is enabled on the compute cluster.
  - There are at least as many healthy hosts as control plane replicas.
  - A datastore is visible to all of those hosts.
  - Nothing blocks DRS migration, such as an attached CD-ROM.
  - The control plane is not pinned to one host.
- Every node has a static IPv4 address and a hostname, and neither is already in use or equal to the control plane endpoint. Neither `ac` nor the provider reserves addresses on DCS.


## Node Labels and Taints \{#node-labels}

To dedicate node pools to a purpose such as monitoring, logging, or ingress, plan their role labels and taints as described in [Infra Nodes](../../../configure/nodes/node_planning.mdx#create-infra-nodes-alauda-os). `install-config.yaml` does not set them.
