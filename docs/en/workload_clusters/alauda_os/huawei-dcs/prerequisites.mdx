# Prerequisites for Huawei DCS Workload Clusters

Meet the following before you [create the cluster](./create_cluster.mdx), with `ac` or in the [web UI](./create_cluster.mdx#create-in-web-ui).

## Providers \{#providers}

Install these cluster plugins on the `global` cluster:

- **Alauda Container Platform Cluster Bootstrap Provider**
- **Alauda Container Platform Infrastructure Provider for Huawei DCS**

A `global` cluster installed on Huawei DCS with `ac` already runs both. Otherwise, download them from **Common ACP Extensions** (see [Download](../../../install/prepare/download.mdx)), upload them with `violet push` (see [Upload Packages](../../../extend/upload_package.mdx#violet_push_usage)), and install them as described in [Cluster Plugin](../../../extend/cluster_plugin.mdx). In a Global Cluster Disaster Recovery pair, install them on both `global` clusters.

## VM Template and Kubernetes Version \{#resolving-placeholders}

A VM template is created on DCS from the Alauda OS image published for the ACP release on the `global` cluster, without changes; see [Downloading Alauda OS](../../../overview/alauda_os_support_matrix.mdx#downloading-alauda-os). For an Alauda OS K template, see [Alauda OS K Templates](./reference/install-config-parameters.mdx#alauda-os-k).

The Alauda OS release also ships a ConfigMap that records the versions its template carries. Apply it to `cpaas-system` of the `global` cluster, with its `cpaas.io/dcs-vm-template` label set to the VM template name on DCS. `ac` reads the `kubernetesVersion` and `etcdTag` keys from it, and the web UI lists only templates that have one. To list the ConfigMaps that are applied:

```bash
ac config use-cluster global
ac -n cpaas-system get cm -l cpaas.io/dcs-vm-template -L cpaas.io/dcs-vm-template
```

You do not set the Kubernetes or etcd version; the template decides them. Apply the ConfigMap of your template before you run `create`: without it, `ac` installs the platform's default Kubernetes version, which the template may not carry. A template ConfigMap without `kubernetesVersion` or `etcdTag` is rejected. Do not rely on the `Pinning Kubernetes <version>, etcd <tag>` line that `ac` prints when a template ConfigMap applies; read the version from `spec.version` of the `KubeadmControlPlane` in `manifests/`.

## Network Connectivity \{#network-connectivity}

The paths from the `global` cluster nodes are needed for creation and for later management.

| From | To | Port | Purpose |
|---|---|---|---|
| `global` cluster nodes | DCS VRM virtual IP | TCP/7443 | The DCS REST API. |
| `global` cluster nodes | The MGMT IP of every DCS physical host that may receive a clone | The port DCS returns, typically TCP/8443; confirm with the DCS administrator | The upload of each node's Ignition ISO. |
| The machine that runs `ac` | DCS VRM virtual IP | TCP/7443 | The preflight checks of `create`. |

If the `global` nodes have several NICs, for example one on the ACP network and one on the DCS management network, route both the VRM virtual IP and every host MGMT IP through the right NIC.

## Control Plane Endpoint and Image Registry \{#control-plane-endpoint}

The control plane endpoint is an IPv4 address: an external load balancer (`type: external`) that you provision as described in [Plan the Control Plane Endpoint](../prepare/control-plane-endpoint.mdx), or a Self-built VIP (`type: internal`) that the provider runs on the control plane nodes; see [Self-built VIP](./reference/install-config-parameters.mdx#self-built-vip). The web UI supports only an external load balancer.

The cluster pulls its platform components from the registry of the `global` cluster, or from a dedicated registry set with `cluster.registrySecretRef`, which the web UI does not support. See [Choose the Image Registry for a Workload Cluster](../prepare/workload-cluster-image-registry.mdx).

## DCS Credential Secret \{#credential-secret}

A Secret in `cpaas-system` of the `global` cluster holds the DCS sign-in. `ac` references it through `credentialRef` and never creates or deletes it, and one Secret can serve several clusters. The account has the `administrator` role and is one of the following user types:

| `userType` | DCS user | DCS-side requirement |
|---|---|---|
| `interconnect`, the default | Interface interconnection user | The policy **Whether to modify the password of an interface interconnection user upon password resetting and first login** (**System Management** → **Rights Management** → **Rights Management Policy**) is **No**; otherwise the forced password change breaks sign-in. |
| `domain` | Domain user, backed by LDAP or AD | Your DCS administrator has configured domain authentication and created the directory user in the DCS portal. The directory service governs its password. |

Use a dedicated account rather than the portal `admin` account: DCS locks an account after repeated failed sign-ins, which would lock everyone else out too.

Write the values in a file with an editor, not on the command line, so the password stays out of shell history:

```text title="dcs-credential.env"
authUser=<auth-user>
authKey=<auth-key>
endpoint=https://<dcs-api-host>:7443
site=<dcs-site-id>
userType=interconnect
```

| Key | Value |
|---|---|
| `authUser` | The DCS API user name. |
| `authKey` | The password in plain text, not the SHA-256 digest that the DCS console shows. |
| `endpoint` | The API address with `https://` and the port, typically `7443`, without a trailing slash. |
| `site` | The bare site ID, not the `urn:sites:` form. |
| `userType` | Optional. `interconnect` or `domain`, case-insensitive. Other values are rejected. |

Each line is `key=value`, unquoted: `ac` keeps quote characters as part of the value. Create the Secret, then remove the file:

```bash
chmod 600 dcs-credential.env
ac config use-cluster global
ac create secret generic <credential-secret-name> -n cpaas-system --from-env-file=dcs-credential.env
rm -f dcs-credential.env
```

Do not create or update the Secret with `ac apply`: it stores the password in the `kubectl.kubernetes.io/last-applied-configuration` annotation of the Secret. To change a value later, put it under `stringData` in a file and run `ac patch secret <credential-secret-name> -n cpaas-system --type=merge --patch-file=<file>`.

## DCS Objects, Capacity, and Addresses \{#dcs-objects}

- The VM folder, the distributed virtual switches and port groups, the datastore or datastore cluster, and any compute cluster or host that `install-config.yaml` names exist on the site. `ac` creates none of them, and preflight checks only their names, not their capacity.
- The datastores and hosts have room for the planned VMs: each node needs its system disk plus every disk of its node group. A datastore that is nearly full, or hosts that are all heavily overcommitted, leave new VMs stuck in `creating`.
- To spread the control plane across hosts with `controlPlaneHA: true`, DRS is enabled on the compute cluster, there are at least as many healthy hosts as control plane replicas, a datastore is visible to all of them, nothing blocks DRS migration, such as an attached CD-ROM, and the control plane is not pinned to one host through `resource`.
- Every node has a static IPv4 address and a hostname, not in use and not equal to the control plane endpoint. Neither `ac` nor the provider reserves addresses on DCS.


## Node Labels and Taints \{#node-labels}

Role labels and taints for dedicated node pools, for example for monitoring, logging, or ingress, are planned as described in [Infra Nodes](../../../configure/nodes/node_planning.mdx#create-infra-nodes-alauda-os). Neither `install-config.yaml` nor the web UI sets them.
