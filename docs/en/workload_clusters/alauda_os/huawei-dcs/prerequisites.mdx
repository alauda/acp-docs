# Prerequisites for Huawei DCS Workload Clusters

Meet the following before you [create the cluster](./create_cluster.mdx).

## Providers \{#providers}

Install these cluster plugins on the `global` cluster:

- **Alauda Container Platform Cluster Bootstrap Provider**
- **Alauda Container Platform Infrastructure Provider for Huawei DCS**

A `global` cluster installed on Huawei DCS with `ac` already runs both. Otherwise, download them from **ACP Common Aligned Extensions** (see [Download](../../../install/prepare/download.mdx)), upload them with `violet push` (see [Upload Packages](../../../extend/upload_package.mdx#violet_push_usage)), and install them as described in [Cluster Plugin](../../../extend/cluster_plugin.mdx). In a Global Cluster Disaster Recovery pair, install them on both `global` clusters.

## VM Template and Kubernetes Version \{#resolving-placeholders}

A VM template is created on DCS from the Alauda OS image published for the ACP release on the `global` cluster, without changes; see [Downloading Alauda OS](../../../overview/alauda_os_support_matrix.mdx#downloading-alauda-os). For an Alauda OS K template, see [Alauda OS K Templates](../../../install/alauda_os/huawei-dcs/reference/install-config-parameters.mdx#alauda-os-k).

### VM Template ConfigMap \{#vm-template-configmap}

Create one ConfigMap per VM template on the `global` cluster. It records the VM template name, the ACP version whose Alauda OS image the VM template was made from, and the Kubernetes version and etcd tag of that ACP version. `ac` reads `kubernetesVersion` and `etcdTag` from it, and the platform upgrade finds the VM template of each Kubernetes version through these ConfigMaps; see [Stage the Alauda OS Images](../../../upgrade/pre-upgrade.mdx#stage-alauda-os-images). The `cpaas.io/dcs-vm-template` label value must match the VM template name on DCS. Select every architecture whose VM templates you register; each generated ConfigMap records its architecture. Run `ac config use-cluster global` first, then the command that the generator prints.

<DcsVmTemplateConfigMap>
  Replace `<os>` with the OS of the VM template, such as `m55`, `ko`, or `ku`, and take `<acp-version>`, `<kubernetes-version>`, and `<etcd-tag>` from the matching row of [Version Mapping](../../../overview/alauda_os_support_matrix.mdx#version-mapping). Create one ConfigMap per architecture: replace `<architecture>` with `x86_64` or `aarch64`, and write `x86_64` as `x86-64` in the ConfigMap name.
</DcsVmTemplateConfigMap>

Check that the ConfigMap of your template exists. Run on a machine where `ac` is logged in to the platform:

```bash
ac config use-cluster global
ac -n cpaas-system get cm -l cpaas.io/dcs-vm-template -L cpaas.io/dcs-vm-template
```

Continue when a ConfigMap lists your VM template name; otherwise create the ConfigMap of your template.

You do not set the Kubernetes or etcd version; the template decides them. Create the ConfigMap of your template before you run `create`: without it, `ac` installs the platform's default Kubernetes version, which the template may not carry. A template ConfigMap without `kubernetesVersion` or `etcdTag` is rejected. Do not rely on the `Pinning Kubernetes <version>, etcd <tag>` line that `ac` prints when a template ConfigMap applies; read the version from `spec.version` of the `KubeadmControlPlane` in `manifests/`.

## Network Connectivity \{#network-connectivity}

The paths from the `global` cluster nodes are needed for creation and for later management. Allow the flows from the `global` cluster nodes and from the machine that runs `ac` to DCS that [Huawei DCS](../../../install/prepare/communication_matrix.mdx#provider-dcs) lists.

## Control Plane Endpoint and Image Registry \{#control-plane-endpoint}

The control plane endpoint is an IPv4 address: an external load balancer (`type: external`) that you provision as described in [Plan the Control Plane Endpoint](../../../install/alauda_os/prerequisites.mdx#control-plane-endpoint), or a Self-built VIP (`type: internal`) that the provider runs on the control plane nodes; see [Self-built VIP](./reference/install-config-parameters.mdx#self-built-vip).

The cluster pulls its platform components from the registry of the `global` cluster, or from a dedicated registry set with `cluster.registrySecretRef`. See [Choose the Image Registry for a Workload Cluster](../prepare/workload-cluster-image-registry.mdx).

## DCS Credential Secret \{#credential-secret}

A Secret in `cpaas-system` of the `global` cluster holds the DCS sign-in. `ac` references it through `credentialRef` and never creates or deletes it, and one Secret can serve several clusters. The account has the `administrator` role and is one of the following user types:

| `userType` | DCS user | DCS-side requirement |
|---|---|---|
| `interconnect`, the default | Interface interconnection user | The policy **Whether to modify the password of an interface interconnection user upon password resetting and first login** (**System Management** → **Rights Management** → **Rights Management Policy**) is **No**; otherwise the forced password change breaks sign-in. |
| `domain` | Domain user, backed by LDAP or AD | Your DCS administrator has configured domain authentication and created the directory user in the DCS portal. The directory service governs its password. |

Use a dedicated account rather than the portal `admin` account: DCS locks an account after repeated failed sign-ins, which would lock everyone else out too.

Write the values in a file with an editor, not on the command line, so the password stays out of shell history:

```text title="dcs-credential.env"
authUser=<auth-user>
authKey=<auth-key>
endpoint=https://<dcs-api-host>:7443
site=<dcs-site-id>
userType=interconnect
```

| Key | Value |
|---|---|
| `authUser` | The DCS API user name. |
| `authKey` | The password in plain text, not the SHA-256 digest that the DCS console shows. |
| `endpoint` | The API address with `https://` and the port, typically `7443`, without a trailing slash. |
| `site` | The bare site ID, not the `urn:sites:` form. |
| `userType` | Optional. `interconnect` or `domain`, case-insensitive. Other values are rejected. |

Each line is `key=value`, unquoted: `ac` keeps quote characters as part of the value. Keep the file private (`chmod 600 dcs-credential.env`); it holds the password. Create the Secret, then remove the file:

```bash
chmod 600 dcs-credential.env
ac config use-cluster global
ac create secret generic <credential-secret-name> -n cpaas-system --from-env-file=dcs-credential.env
rm -f dcs-credential.env
```

Do not create or update the Secret with `ac apply`: it stores the password in the `kubectl.kubernetes.io/last-applied-configuration` annotation of the Secret. To change a value later, put it under `stringData` in a file and run `ac patch secret <credential-secret-name> -n cpaas-system --type=merge --patch-file=<file>`.

## DCS Objects, Capacity, and Addresses \{#dcs-objects}

- The VM folder, the distributed virtual switches and port groups, the datastore or datastore cluster, and any compute cluster or host that `install-config.yaml` names exist on the site. `ac` creates none of them. Make sure that they have room for the planned VMs.
- The datastores and hosts have room for the planned VMs: each node needs its system disk plus every disk of its node group. A datastore that is nearly full, or hosts that are all heavily overcommitted, leave new VMs stuck in `creating`.
- To spread the control plane across hosts with `controlPlaneHA: true`, DRS is enabled on the compute cluster, there are at least as many healthy hosts as control plane replicas, a datastore is visible to all of them, nothing blocks DRS migration, such as an attached CD-ROM, and the control plane is not pinned to one host through `resource`.
- Every node has a static IPv4 address and a hostname, not in use and not equal to the control plane endpoint. Neither `ac` nor the provider reserves addresses on DCS.


## Node Labels and Taints \{#node-labels}

Role labels and taints for dedicated node pools, for example for monitoring, logging, or ingress, are planned as described in [Infra Nodes](../../../configure/nodes/node_planning.mdx#create-infra-nodes-alauda-os). `install-config.yaml` does not set them.
