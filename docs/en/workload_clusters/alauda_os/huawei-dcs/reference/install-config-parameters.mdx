# install-config.yaml Parameters for Huawei DCS

This page lists the fields of a Huawei DCS workload cluster's `install-config.yaml`, how they map to the rendered objects, and the optional topology. The `provider.dcs` and node group fields are the same as for the `global` cluster.

## Fields \{#fields}

| Field | Required | Default | Description |
|---|---|---|---|
| `cluster.clusterName` | Yes | — | The cluster name, a DNS-1123 subdomain of at most 63 characters. It must not be `global` or start with `global-`. `Cluster` and `DCSCluster` take this name, and every other object is prefixed with `<cluster-name>-`. |
| `cluster.sshKeys` | Yes | — | The SSH public keys installed on every node. |
| `cluster.registrySecretRef` | No | The registry of the `global` cluster | A Secret in `cpaas-system` labelled `capi.cpaas.io/provider=registry-credential`, with a required `registry` key and optional `username` and `password`, set together. See [Choose the Image Registry for a Workload Cluster](../../prepare/workload-cluster-image-registry.mdx). |
| `cluster.encryptionProviderConfig` | No | Generated | The key that encrypts Secrets in the workload API server: the base64 of a 16, 24, or 32 byte aescbc key. A generated key is kept only in `manifests/`; see [Run `create` Again](../create_cluster.mdx#rerun-create). |
| `cluster.network.podCIDR`, `serviceCIDR`, `kubeOVN.joinCIDR` | No | `10.199.0.0/16`, `10.96.0.0/12`, `100.64.0.0/16` | The Pod, Service, and Kube-OVN join networks. They must not overlap. |
| `cluster.network.loadBalancer` | Yes | — | The control plane endpoint: `type` (`external`, the default, or `internal`), `address`, `port` (`6443`), and for `internal` a `vrid` (1-255) and an optional `interface`. See [Control Plane Endpoint and HA](#configure-dcscluster). |
| `credentialRef` | Yes | — | The credential Secret, in `cpaas-system`. |
| `provider.dcs.vmTemplateName` | Yes | — | The VM template every node is cloned from. It decides the Kubernetes version; see [VM Template and Kubernetes Version](../prerequisites.mdx#resolving-placeholders). |
| `provider.dcs.controlPlaneHA` | Yes | — | `true` keeps the control plane VMs on different DCS hosts with a DRS rule. |
| `provider.dcs.machineFolder` | Yes | — | An existing VM folder. |
| `provider.dcs.cdRomDatastoreName` | No | Chosen by the provider | The datastore for the CD-ROM that carries each node's Ignition ISO. |
| `provider.dcs.rootDisk.sizeGiB` | No | The template's size | The system disk size. DCS rejects a size smaller than the template's. |
| `provider.dcs.resource` | No | Chosen by DCS | `type: cluster` places the VMs in a compute cluster, `type: host` on one physical host. See [Node Addresses and Placement](#node-addresses). |
| `provider.dcs.network` | Yes | — | `dvSwitchName` and `portGroupName` of the primary NIC of every node. |
| `provider.dcs.disks` | Yes | — | `datastore` (`type: Datastore` or `DatastoreCluster`, and `name`), `isThin` (default `false`), and `pciType` (`VIRTIO`, the default, `SCSI`, or `IDE`). See [Disks](#disks). |
| `controlPlane.replicas` | Yes | — | An odd number: `1`, or `3` or more. See [Control Plane Endpoint and HA](#configure-dcscluster). |
| `*.cpuCore`, `*.memoryGiB` | No | `8` and `16` | The VM size of a node group. |
| `*.dcs`, `*.disks.dcs`, `*.network.additions[].dcs` | No | The `provider.dcs` values | Overrides for one node group or one NIC. `*.dcs` takes `machineFolder`, `cdRomDatastoreName`, `rootDisk`, and `resource`; `*.disks.dcs` takes `datastore`, `isThin`, and `pciType`. Fields not set keep the cluster-level value. |
| `*.network` | Yes | — | The primary NIC network of a node group; see [Node Addresses and Placement](#node-addresses). |
| `*.disks` | Yes | — | The standard disk set and any raw disks; see [Disks](#disks). |
| `*.hosts` | Yes | — | One entry per node: `hostname`, `ip`, and `additionalIps`. |
| `computes[].name` | Yes | — | Unique per group. `control-plane` is reserved. |

### Alauda OS K Templates \{#alauda-os-k}

{/* eslint-disable-next-line mdx/remark -- the ac field name contains a legacy OS name */}
`provider.dcs.kubeOS` is optional and defaults to `false`. Set it to `true` when `vmTemplateName` is an Alauda OS K template: with `false`, Ignition fails on Alauda OS K and the VM has no network.

## Control Plane Endpoint and HA \{#configure-dcscluster}

- **`external`**: your load balancer forwards `TCP/6443` to the control plane nodes.
- **`internal`** (Self-built VIP): the provider runs the VIP on the control plane nodes; see [Self-built VIP](#self-built-vip).
- **`controlPlaneHA: true`**: the provider keeps a DRS mutual-exclusion rule for the control plane VMs, and the DCS scheduler keeps them on different hosts. It works with either endpoint mode. The provider does not run DRS itself. For the DCS-side requirements, see [DCS Objects, Capacity, and Addresses](../prerequisites.mdx#dcs-objects).

`controlPlane.replicas` is odd: `1`, or `3` or more. With fewer than three control plane nodes, contact technical support before you upgrade the cluster. A single node still needs one of the endpoint modes.

## Node Addresses and Placement \{#node-addresses}

Each node group lists its nodes in `hosts`, at least `replicas` entries; entries beyond `replicas` become spare slots in the group's `DCSIpHostnamePool`. Addresses are IPv4. Hostnames and addresses are unique across all node groups and differ from the control plane endpoint.

Every node of a group shares the group's `network`: `gateway` and `mask` are required, `mask` is a prefix length from 1 to 32, and DCS uses only the first `dns` entry. The primary NIC attaches to `provider.dcs.network`.

`machineFolder` groups the VMs on DCS and does not affect placement. By default the DCS scheduler picks each VM's host. `resource` fixes every VM of a node group to one compute cluster or one host; pinning the control plane to a single host defeats `controlPlaneHA`. If `resource.type: cluster` places the VMs in a compute cluster other than the one that holds the VM template, the template's datastore and the port groups must be visible to that compute cluster, or the clone fails on DCS. Set any of these per group under `<group>.dcs`.

## Disks \{#disks}

Every node group declares the whole standard disk set. `ac` rejects any other name, and rejects a group that leaves a standard disk out.

| Name | Kind | Mount path | Node groups |
|---|---|---|---|
| `var-lib-containerd` | `ephemeral` | `/var/lib/containerd` | All |
| `var-lib-kubelet` | `ephemeral` | `/var/lib/kubelet` | All |
| `var-lib-etcd` | `ephemeral` | `/var/lib/etcd` | Control plane only |
| `var-cpaas` | `persistent` | `/var/cpaas` | All |

- **Ephemeral disks** go to the `DCSMachineTemplate`, next to the system disk, and are recreated with the VM.
- **Persistent disks** and **raw disks** go to the address slot of each node in the `DCSIpHostnamePool`. When a VM is replaced, they are detached and reattached to the replacement, which mounts the existing filesystem instead of formatting it. See [Change Persistent Disks](#persistent-disks) and [Raw Disks for TopoLVM](#raw-disks).
- Every mounted disk is formatted `xfs`. The system disk keeps the template's size unless `rootDisk.sizeGiB` is set.
- `disks.datastore` applies to every disk of the node, the system disk included. `DatastoreCluster` lets DCS pick a member datastore with free space and is preferred when the platform has one.
- `isThin` and `pciType` reach the persistent and raw disks only.

Every node group, and a control plane of `3` or more replicas, is replaced one node at a time (`maxSurge: 0`).

### Change Persistent Disks \{#persistent-disks}

Persistent and raw disks are entries in `DCSIpHostnamePool.spec.pool[].persistentDisk`, as in [Worker Objects](#worker-objects). `slot` sets the attach order and the device name in the guest; each entry names exactly one of `datastoreName` and `datastoreClusterName`. When you change the entries of an existing pool:

- An appended entry is attached to the running VM on DCS, but it is formatted and mounted only when the VM is replaced.
- Removing an entry is rejected. `format`, `options`, and `pciType` cannot change.
- The size (`quantityGB`) and the datastore of an existing disk cannot change: the webhook rejects the change. `isThin` affects only volumes created later.
- `path` and `mountOptions` take effect on replacement VMs.

## Optional Topology \{#optional-topology}

Set these in `install-config.yaml` before the cluster is created.

### Self-built VIP \{#self-built-vip}

Set `cluster.network.loadBalancer.type: internal`, `address` to a reserved IPv4 VIP in the control plane Layer 2 network, and `vrid` to a virtual router ID from 1 to 255 that is unique in that Layer 2 domain. `interface` names the NIC that carries the VIP; empty uses the NIC that carries the node IP. `controlPlaneHA` is not required.

Constraints:

- The VIP is not a node address in `hosts[].ip` or `hosts[].additionalIps`.
- The DCS port group allows VIP ownership, gratuitous ARP, and VRRP traffic.
- `interface` is a Linux interface name of at most 15 characters, such as `eth0`.
- `type`, `address`, `port`, `vrid`, and `interface` cannot change after the control plane is initialized.

To check it, see [Verify the Self-built VIP](../create_cluster.mdx#verify-self-built-vip).

### Additional NICs \{#additional-nics}

A node group can attach NICs on secondary networks, such as storage, management, or isolation networks. Declare one entry per NIC in `<group>.network.additions`, and list each host's addresses in `hosts[].additionalIps` in the same order. A host may list fewer addresses than there are NICs; it gets only those.

```yaml
controlPlane:
  network:
    additions:
      - mask: <prefix-length>               # Optional: empty takes network.mask
        dcs:                                # Optional: empty takes provider.dcs.network
          dvSwitchName: <dv-switch-name>
          portGroupName: <port-group-name>
  hosts:
    - hostname: <cp-0-hostname>
      ip: <cp-0-ip>
      additionalIps: [<cp-0-nic2-ip>]
```

- Every additional NIC attaches to a switch and a port group. Without `dcs`, it takes those of `provider.dcs.network`, the same network as the primary NIC.
- An additional NIC gets no gateway and uses the node's first DNS server. Static routes and route metrics need MachineConfig or guest OS configuration.
- The primary `hosts[].ip` stays the Kubernetes Node IP.
- The NICs are added when the provider clones a VM. Changing them later does not hot-add NICs to running VMs.

### Raw Disks for TopoLVM \{#raw-disks}

`<group>.disks.rawDisks` attaches unformatted block devices for TopoLVM. Each entry has a `name` of your choice and a `sizeGiB`:

```yaml
disks:
  rawDisks:
    - name: data-001
      sizeGiB: 50
```

Raw disks are rendered as persistent disks without a mount path or filesystem, after the standard persistent disks in the slot order of the `DCSIpHostnamePool`, on the same datastore with the same `isThin` and `pciType`. Like `/var/cpaas`, they are kept when a VM is replaced and deleted with the cluster. Do not remove or reorder entries after the cluster is created: the slot of a disk follows its position, and removing a persistent disk is rejected.

## Rendered Manifests \{#render-manifests}

`ac` writes the objects it applies to `<install-dir>/manifests/`, one file per object, all in `cpaas-system`. For their API fields, see the [Huawei DCS API reference](../../../../apis/kubernetes_apis/infrastructure_providers/huawei-dcs/index.mdx).

| Object | Name | Notes |
|---|---|---|
| `Secret` | `<cluster-name>-encryption-provider-config` | The encryption configuration, referenced by `DCSCluster`. |
| `Cluster` | `<cluster-name>` | Labelled `cluster-type: DCS`. |
| `DCSCluster` | `<cluster-name>` | The site from the credential Secret, the control plane endpoint, `controlPlaneHA`, and the credential and encryption Secret references. |
| `KubeadmControlPlane`, `DCSMachineTemplate`, `DCSIpHostnamePool` | `<cluster-name>-control-plane` | |
| `MachineDeployment`, `DCSMachineTemplate`, `DCSIpHostnamePool` | `<cluster-name>-<group>` | |
| `KubeadmConfigTemplate` | `<cluster-name>-<group>-config` | |

The credential Secret is yours; `ac` does not render or delete it.

### Worker Objects \{#worker-objects}

`hosts`, `network`, and the persistent and raw disks go to the `DCSIpHostnamePool`; the VM size, the location, and the ephemeral disks go to the `DCSMachineTemplate`. For one worker host with the defaults:

```yaml
apiVersion: infrastructure.cluster.x-k8s.io/v1beta1
kind: DCSIpHostnamePool
metadata:
  name: <cluster-name>-worker
  namespace: cpaas-system
spec:
  pool:
  - hostname: <worker-0-hostname>
    ip: <worker-0-ip>
    mask: "24"
    gateway: <worker-gateway>
    dns: <dns-ip>
    persistentDisk:              # Kept when the VM is replaced
    - path: /var/cpaas
      quantityGB: 100
      slot: 0
      datastoreName: <datastore-name>
      format: xfs
      isThin: false
      pciType: VIRTIO
---
apiVersion: infrastructure.cluster.x-k8s.io/v1beta1
kind: DCSMachineTemplate
metadata:
  name: <cluster-name>-worker
  namespace: cpaas-system
spec:
  template:
    spec:
      vmTemplateName: <vm-template-name>
      ipHostPoolRef:
        name: <cluster-name>-worker
      location:
        type: folder
        name: <folder-name>
      vmConfig:
        dcsMachineCpuSpec:
          quantity: 8
        dcsMachineMemorySpec:
          quantity: 16384        # MiB
        dvSwitchName: <dv-switch-name>
        portGroupName: <port-group-name>
        dcsMachineDiskSpec:      # Recreated with the VM
        - systemVolume: true
          quantity: 0            # 0 keeps the template's system disk size
          datastoreName: <datastore-name>
        - path: /var/lib/containerd
          quantity: 100
          format: xfs
          datastoreName: <datastore-name>
        - path: /var/lib/kubelet
          quantity: 100
          format: xfs
          datastoreName: <datastore-name>
```

A `resource` setting renders as `spec.template.spec.resource`, and additional NICs as `additionNic` entries on each pool slot.
