# VMware vSphere Provider

<Overview />

The Infrastructure Provider for Virtualization Platform creates and manages Alauda OS clusters on the VMware vSphere platform. This provider is built on top of Cluster API Provider vSphere (CAPV) and integrates with vCenter to provision and manage virtual machines, networks, and storage for Kubernetes clusters.

## Overview

The vSphere Provider connects directly to vCenter to manage VM lifecycle, and extends CAPV with declarative node-slot allocation so that hostnames, static IP addresses, and persistent disks can be pre-defined before a cluster is provisioned.

:::info
**Endpoint modes and disk lifecycle**

The provider supports two control plane endpoint modes: an external LoadBalancer, which is the default, and a provider-managed Self-built VIP (`VSphereCluster.spec.controlPlaneLoadBalancer.type: internal`, Alive with keepalived and IPVS). The Self-built VIP requires ACP `v4.4` or later and is chosen when the cluster is created; see [Control Plane Endpoint](./prerequisites.mdx#control-plane-endpoint-modes). Machine-config-pool persistent disks follow the provider-managed `InUse → Released → reuse or reclaim` lifecycle; see [Persistent disk lifecycle](./reference/install-config-parameters.mdx#persistent-disk-lifecycle).
:::

## Key Features

- **vCenter Integration**: Direct vCenter connectivity to clone VM templates, manage VM lifecycle, and place workloads on target datacenters, compute clusters, and datastores
- **Two Control Plane Endpoint Modes**: an external LoadBalancer you own, or a provider-managed Self-built VIP on the control-plane nodes (`type: internal`, Alive with keepalived and IPVS, where the bootstrap VIP is handed over to Alive after `kubeadm init`), which requires ACP `v4.4` or later
- **Machine Configuration Pools**: `VSphereMachineConfigPool` defines per-node slots with fixed hostnames, static IPs, and per-slot data-disk layouts. Released slots can be reused by replacement Machines in the same existing pool, but slots and VMDKs are not shared across different pool objects
- **Static IP Allocation**: Static IP, gateway, and DNS configuration per node slot for enterprise network environments where DHCP is not available
- **Multi-NIC Support**: Primary and additional NICs per node, where the primary NIC drives the kubelet `node-ip` and additional NICs are attached in declared order for management, storage, or service networks
- **Flexible Data Disks**: Declarative per-slot persistent and ephemeral data disks with optional format/mount, `wipeFilesystem` control on persistent disks, raw-device mode exposed at `/dev/disk/by-capv/<name>`, and delayed release so replacement Machines can reuse the slot and VMDKs before provider-managed reclaim
- **Immutable-Template Rolling Updates**: Control plane and worker updates use new `VSphereMachineTemplate` and `KubeadmConfigTemplate` resources, enabling reproducible replacement and same-minor template recovery

## How It Works \{#how-it-works}

![VMware vSphere Cluster API resource dependencies](./assets/vsphere-resource-dependency.svg)

The top-level `Cluster` references `VSphereCluster` and the control plane or worker controllers. Those controllers reference `VSphereMachineTemplate` objects. Each template references one `VSphereMachineConfigPool`, whose slots provide hostnames, static network configuration, and persistent disks to the runtime `Machine`, `VSphereMachine`, and `VSphereVM` objects. One pool serves exactly one controller: when a machine allocates a slot, the provider records the owning `KubeadmControlPlane` or `MachineDeployment` in the pool's `status.consumerRef` and rejects a second controller, so every node group has its own pool.

The vSphere cloud provider (CPI) connects the workload nodes to vSphere, so that the cluster can report infrastructure identities and complete cloud-provider initialization. It reaches the workload cluster through a Cluster API `ClusterResourceSet` in the `global` cluster, which applies the referenced `ConfigMap` and `Secret` resources to the workload cluster once its API server is reachable. Until the CPI runs, the nodes stay tainted as uninitialized.

The provider connects directly to vCenter. It does not use vSphere Supervisor or `vm-operator`, and the documented workflows use `VSphereMachineConfigPool` for every node group. Kube-OVN is delivered by platform controllers that consume annotations on the `Cluster` resource, so these workflows depend on the platform and are not a generic standalone CAPV deployment guide.

## Supported Resources

The table below lists the primary user-facing resources used by the workflows in this documentation. Controller-reconciled resources (for example `VSphereVM`) and resources not exercised by the documented workflows (for example `VSphereClusterIdentity`, which is an alternative to the `Secret`-based `identityRef` used here) are covered in the [Provider APIs](../../../apis/kubernetes_apis/infrastructure_providers/vmware-vsphere/index.mdx) reference for completeness.

| Resource | Description |
|----------|-------------|
| `VSphereCluster` | Represents vSphere infrastructure including vCenter endpoint and control plane endpoint |
| `VSphereMachine` | Represents a virtual machine instance in vSphere |
| `VSphereMachineTemplate` | Template for creating vSphere machines with VM, CPU, memory, network, and disk specifications |
| `VSphereMachineConfigPool` | Pool of pre-defined node slots with hostnames, static IPs, and per-slot data-disk layouts |
