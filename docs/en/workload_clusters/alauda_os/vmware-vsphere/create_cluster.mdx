# Create a Cluster on VMware vSphere

ACP CLI (ac) renders the Cluster API, vSphere, and CPI objects from one `install-config.yaml`, applies them to the `global` cluster, and reports the creation stages. Every object lives in the `cpaas-system` namespace of the `global` cluster. There is no web UI for vSphere clusters. For how the provider objects fit together, see [How It Works](./overview.mdx#how-it-works).

## Prerequisites \{#prerequisites}

- You meet the [VMware vSphere prerequisites](./prerequisites.mdx).
- `ac` is logged in to the platform as a platform administrator (`ac login https://<platform-address>`).
- You work against the primary `global` cluster, not a disaster recovery standby; see [Standby Management Clusters](./reference/install_provider.mdx#standby-management-cluster).

## Procedure

### 1. Write `install-config.yaml` \{#write-install-config}

Create an installation directory for the cluster and write `install-config.yaml` in it. `ac` writes `manifests/` and `logs/ac.log` next to it. The template holds the required fields. The optional fields, such as the Self-built VIP, a second NIC, and data disks, are in [Parameters](./reference/install-config-parameters.mdx#optional-fields).

```yaml title="install-config.yaml"
cluster:
  clusterName: <cluster-name> # [!code callout]
  sshKeys: # [!code callout]
    - <ssh-public-key>
  network:
    loadBalancer:
      type: external # [!code callout]
      address: <control-plane-endpoint> # [!code callout]
      port: 6443

credentialRef: # [!code callout]
  name: <cluster-name>-credential
  namespace: cpaas-system

provider:
  vsphere:
    server: <vcenter-address> # [!code callout]
    datacenter: <datacenter> # [!code callout]
    template: <template-name-or-path> # [!code callout]
    datastore: <datastore> # [!code callout]
    computeResource: <cluster-or-host> # [!code callout]
    releaseDelayHours: 24 # [!code callout]
    network:
      name: <portgroup-name> # [!code callout]

controlPlane:
  replicas: 3 # [!code callout]
  network:
    gateway: <cp-gateway> # [!code callout]
    dns: [<dns-ip>] # [!code callout]
    mask: <prefix-length> # [!code callout]
  disks:
    ephemeral: # [!code callout]
      - name: var-lib-containerd
        sizeGiB: 100
      - name: var-lib-kubelet
        sizeGiB: 100
      - name: var-lib-etcd # [!code callout]
        sizeGiB: 20
    persistent: # [!code callout]
      - name: var-cpaas
        sizeGiB: 100
  hosts: # [!code callout]
    - hostname: <cp-0-hostname>
      ip: <cp-0-ip>
    - hostname: <cp-1-hostname>
      ip: <cp-1-ip>
    - hostname: <cp-2-hostname>
      ip: <cp-2-ip>

computes: # [!code callout]
  - name: worker
    replicas: 3
    network:
      gateway: <worker-gateway>
      dns: [<dns-ip>]
      mask: <prefix-length>
    disks:
      ephemeral: # [!code callout]
        - name: var-lib-containerd
          sizeGiB: 100
        - name: var-lib-kubelet
          sizeGiB: 100
      persistent:
        - name: var-cpaas
          sizeGiB: 100
    hosts:
      - hostname: <worker-0-hostname>
        ip: <worker-0-ip>
      - hostname: <worker-1-hostname>
        ip: <worker-1-ip>
      - hostname: <worker-2-hostname>
        ip: <worker-2-ip>
```


<Callouts>

1. `clusterName`: required. It must not be `global` or start with `global-`.
2. `sshKeys`: required. The SSH public keys installed on every node.
3. `type`: `external`, the default, or `internal`. It cannot be changed later. `internal` also needs `vrid`; see [Optional Fields](./reference/install-config-parameters.mdx#optional-fields).
4. `address`: required. The control plane endpoint, an IPv4 address.
5. `credentialRef`: required. The credential Secret.
6. `server`: required. The vCenter address.
7. `datacenter`: required. The datacenter name. Use an inventory path, such as `/folder/dc`, only when you do not set `computeResource`.
8. `template`: required. The VM template every node is cloned from.
9. `datastore`: required.
10. `computeResource`: the name of the DRS cluster or host, not a path. Set it when the datacenter has more than one.
11. `releaseDelayHours`: how long a released slot keeps its persistent disks before the provider deletes them.
12. `network.name`: required. The port group of the primary NIC.
13. `replicas`: an odd number, `1` or `3` or more. With fewer than three control plane nodes, contact technical support before you upgrade the cluster.
14. `gateway`: required.
15. `dns`: required.
16. `mask`: required. A prefix length from 1 to 32.
17. `ephemeral`: disks recreated with the VM.
18. `var-lib-etcd`: control plane only.
19. `persistent`: disks kept when the VM is replaced.
20. `hosts`: required. At least `replicas` entries.
21. `computes`: optional.
22. Workers have no `var-lib-etcd`.

</Callouts>

### 2. Create the Cluster \{#create-with-ac}

Run the following command from a machine where `ac` is logged in to the platform:

```bash
ac config use-cluster global
ac adm alpha cluster create --dir <install-dir> --provider vsphere
```

`ac` first checks the provider CRDs on the `global` cluster, the credential and the vCenter sign-in, the vCenter objects named in `install-config.yaml`, and the registry. If a check fails, nothing is changed and the error names the item.

`create` returns once the objects are applied, and the cluster keeps building. Add `--wait` to wait until all stages are ready; `--timeout` (default `2h`) limits only the wait. To render without applying, run `ac adm alpha cluster manifests` with the same flags.

### 3. Monitor the Creation \{#monitor-creation}

```bash
ac config use-cluster global
ac adm alpha cluster status --cluster <cluster-name>                      # prints the four stages once
ac adm alpha cluster wait-for install-complete --cluster <cluster-name>   # waits until all four are ready
```

| # | Stage | Done when |
|---:|---|---|
| 1 | `Cluster` | The object exists, is not being deleted, its `infrastructureRef` and `controlPlaneRef` resolve, it reports no failure, and `Available` is `True` when the `Cluster` reports it. |
| 2 | Control plane | `KubeadmControlPlane` `status.readyReplicas` reaches `spec.replicas`. |
| 3 | `MachineDeployment` | Every node group is ready. |
| 4 | `ClusterView` | The platform's view of the cluster reports `status.phase: Running`. `status` also shows the control plane endpoint and the ready node counts. |

Continue when all four stages are ready; otherwise see [Troubleshooting](./troubleshooting.mdx).

### 4. Verify the Cluster \{#verify-the-cluster}

Run the following commands from a machine where `ac` is logged in to the platform:

```bash
ac config use-cluster global
ac adm alpha cluster status --cluster <cluster-name>
ac config sync
ac config use-cluster <cluster-name>
ac get nodes
ac config use-cluster global
```

Continue when `status` reports all four stages ready and every node is `Ready`; otherwise see [Troubleshooting](./troubleshooting.mdx).

#### CPI and Pools \{#verify-cpi-and-pools}

```bash
ac config use-cluster global
ac -n cpaas-system get clusterresourceset,clusterresourcesetbinding
ac -n cpaas-system get vspheremachineconfigpool
ac config sync
ac config use-cluster <cluster-name>
ac -n kube-system get daemonset
ac config use-cluster global
```

Continue when a `ClusterResourceSetBinding` exists for the cluster, `vsphere-cloud-controller-manager` is listed in `kube-system`, and each pool reports `Ready=True` with `ALLOCATED` equal to the number of its machines; otherwise see [Troubleshooting](./troubleshooting.mdx#common-causes).

#### Persistent Disks \{#verify-persistent-disks}

Run it for each pool, `<cluster-name>-control-plane` and `<cluster-name>-<group>`:

```bash
ac config use-cluster global
ac -n cpaas-system get vspheremachineconfigpool <pool-name> \
  -o jsonpath='{range .status.persistentDiskStatuses[*]}{.hostname}{" "}{.name}{" "}{.phase}{"\n"}{end}'
```

Continue when every persistent disk of an allocated slot reports `Attached`; otherwise see [Troubleshooting](./troubleshooting.mdx#common-causes).

#### Optional Topology \{#verify-creation-time-variants}

**Applies to**: node groups with `network.additions` or `rawDisks`. Skip it when you use neither.

```bash
ac config use-cluster global
ac -n cpaas-system get vspheremachineconfigpool <pool-name> -o yaml
```

On a node of that group:

```bash
ls -l /dev/disk/by-capv/
```

Continue when each slot lists the declared additional NICs and disks, and every raw disk appears in `/dev/disk/by-capv/`; otherwise contact technical support.

#### Self-built VIP \{#verify-self-built-vip}

**Applies to**: `type: internal`. Skip it for an external load balancer.

```bash
ac config use-cluster global
ac -n cpaas-system get vspherecluster <cluster-name> \
  -o jsonpath='{.status.conditions[?(@.type=="SelfBuiltLoadBalancerReady")].status}{"\n"}'
ac config sync
ac config use-cluster <cluster-name>
ac -n kube-system get pods -l app=alive -o wide
ac config use-cluster global
```

Continue when the condition is `True` and one Alive Pod runs on each control plane node; otherwise see [Troubleshooting](./troubleshooting.mdx#self-built-vip).

## Run `create` Again \{#rerun-create}

If `create` stops, run the same command again; completed work is skipped. Running `create` again on the same directory puts back anything that has drifted, except the credential Secret, which `ac` does not render. When `manifests/` already exists, `create` asks whether to reuse it: press Enter to reuse it, or answer `n` to render again after you change `install-config.yaml`. When standard input is not a terminal, pass `--reuse-manifests=true` or `--reuse-manifests=false`.

Do not edit the files in `manifests/`.

:::warning
Keep `<install-dir>/manifests/`, or set `cluster.encryptionProviderConfig`: a generated encryption key is kept only in `manifests/`, and rendering again without either generates a new key and writes it into the `KubeadmControlPlane`, which the existing cluster cannot use.
:::

## Add or Change Node Groups \{#create-the-worker-objects}

To add a worker node group, add it to `computes` with its own `hosts`, then run `create --reuse-manifests=false` on the same directory. `ac` renders a new pool, template, bootstrap template, and `MachineDeployment` for it. To scale a group, change `replicas` and keep at least `replicas` entries in `hosts`. Slots that machines already hold are frozen; see [Allocated slot restrictions](./reference/install-config-parameters.mdx#create-the-machine-config-pools).

For worker scale-out and later template or runtime-topology changes, see [Manage Nodes on VMware vSphere](../../../configure/nodes/alauda_os/vmware-vsphere.mdx). Apply one change at a time and validate the result before you combine changes.
