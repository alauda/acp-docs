# Create a Cluster on VMware vSphere

ACP CLI (ac) renders the Cluster API, vSphere, and CPI objects from one `install-config.yaml`, applies them to the `global` cluster, and reports the creation stages. Every object lives in the `cpaas-system` namespace of the `global` cluster. For how the provider objects fit together, see [How It Works](./overview.mdx#how-it-works).

## Prerequisites \{#prerequisites}

- You meet the [VMware vSphere prerequisites](./prerequisites.mdx).
- `ac` is logged in to the platform as a platform administrator (`ac login https://<platform-address> --name <session-name>`).

## Procedure

### 1. Write `install-config.yaml` \{#write-install-config}

Create an installation directory for the cluster and write `install-config.yaml` in it. `ac` writes `manifests/` and `logs/ac.log` in the same directory.

Copy the following template and fill in the placeholders. The table below the template describes the numbered lines, which are specific to VMware vSphere. For the other fields, see [Common `install-config.yaml` Fields](../reference.mdx#install-config). For the objects that `ac` renders from this file, see [Parameters](./reference/install-config-parameters.mdx).

    # rootDisk:

    network: # [!code callout]

controlPlane:
  replicas: 3

  # [!code callout]
  # vsphere:
  #   datastore: <datastore>
  #   folder: <folder-path>
  #   computeResource: <cluster-or-host>
  #   rootDisk:
  #     sizeGiB: <root-disk-gib>
  network: # [!code callout]
    gateway: <cp-gateway>
    dns: [<dns-ip>]
    mask: <prefix-length>
    additions: []
    # additions:
    #   - mask: <prefix-length>
    # [!code callout]
    #     vsphere:
    #       name: <portgroup-name>
    #       deviceName: <nic-name>
  disks:
    ephemeral: # [!code callout]
      - name: var-lib-containerd
        sizeGiB: 100
      - name: var-lib-kubelet
        sizeGiB: 100

        sizeGiB: 20

      - name: var-cpaas
        sizeGiB: 100
    rawDisks: [] # [!code callout]
    # rawDisks:
    #   - name: data-001
    #     sizeGiB: 50
    # [!code callout]
    # vsphere:
    #   datastore: <datastore>
    #   storagePolicy: <storage-policy>
  hosts: # [!code callout]
    - hostname: <cp-0-hostname>

      additionalIps: []

      additionalIps: []

### 2. Create the Cluster \{#create-with-ac}

Run the following command from a machine where `ac` is logged in to the platform:

```bash
ac config use-cluster global
ac adm alpha cluster create --dir <install-dir> --provider vsphere
```

Before `ac` changes anything, it checks the following:

- The provider CRDs on the `global` cluster.
- The credential and the vCenter sign-in.
- The vCenter objects named in `install-config.yaml`.
- The registry.

If a check fails, nothing is changed, and the error names the failed item.

`create` returns as soon as the objects are applied. The cluster keeps building after that. To wait until all stages are ready, add `--wait`. `--timeout` (default `2h`) limits only the wait. To render the objects without applying them, run `ac adm alpha cluster manifests` with the same flags.

### 3. Monitor the Creation \{#monitor-creation}

```bash
ac config use-cluster global
ac adm alpha cluster status --cluster <cluster-name>                      # prints the four stages once
ac adm alpha cluster wait-for install-complete --cluster <cluster-name>   # waits until all four are ready
```

Continue when all four stages are ready; otherwise see [Troubleshooting](./troubleshooting.mdx).

### 4. Verify the Cluster \{#verify-the-cluster}

Run the following commands from a machine where `ac` is logged in to the platform:

```bash
ac config sync
ac config use-cluster <cluster-name>
ac get nodes
ac config use-cluster global
```

Continue when every node is `Ready`; otherwise see [Troubleshooting](./troubleshooting.mdx).

#### CPI and Pools \{#verify-cpi-and-pools}

```bash
ac config use-cluster global
ac -n cpaas-system get clusterresourceset,clusterresourcesetbinding
ac -n cpaas-system get vspheremachineconfigpool \
  -o custom-columns='NAME:.metadata.name,READY:.status.conditions[?(@.type=="Ready")].status,TOTAL:.status.total,ALLOCATED:.status.allocated'
ac config sync
ac config use-cluster <cluster-name>
ac -n kube-system get daemonset
ac config use-cluster global
```

Continue when a `ClusterResourceSetBinding` exists for the cluster, `vsphere-cloud-controller-manager` is listed in `kube-system`, and each pool of the cluster shows `READY` `True` with `ALLOCATED` equal to the number of its machines; otherwise see [Troubleshooting](./troubleshooting.mdx#common-causes).

#### Persistent Disks \{#verify-persistent-disks}

Run the following commands once for each pool, `<cluster-name>-control-plane` and `<cluster-name>-<group>`:

```bash
ac config use-cluster global
ac -n cpaas-system get vspheremachineconfigpool <pool-name> \
  -o jsonpath='{range .status.persistentDiskStatuses[*]}{.hostname}{" "}{.name}{" "}{.phase}{"\n"}{end}'
```

Continue when every persistent disk of an allocated slot reports `Attached`; otherwise see [Troubleshooting](./troubleshooting.mdx#common-causes).

#### Optional Topology \{#verify-creation-time-variants}

**Applies to**: node groups with `network.additions` or `rawDisks`. Skip it when you use neither.

```bash
ac config use-cluster global
ac -n cpaas-system get vspheremachineconfigpool <pool-name> -o yaml
```

On a node of that group:

```bash
ls -l /dev/disk/by-capv/
```

Continue when each slot lists the declared additional NICs and disks, and every raw disk appears in `/dev/disk/by-capv/`; otherwise contact technical support.

#### Self-built VIP \{#verify-self-built-vip}

**Applies to**: `type: internal`. Skip it for an external load balancer.

```bash
ac config use-cluster global
ac -n cpaas-system get vspherecluster <cluster-name> \
  -o jsonpath='{.status.conditions[?(@.type=="SelfBuiltLoadBalancerReady")].status}{"\n"}'
ac config sync
ac config use-cluster <cluster-name>
ac -n kube-system get pods -l app=alive -o wide
ac config use-cluster global
```

Continue when the condition is `True` and one Alive Pod runs on each control plane node; otherwise see [Troubleshooting](./troubleshooting.mdx#self-built-vip).

Log in to a control plane node of the cluster as the `boot` user (`ssh boot@<control-plane-node-ip>`). Use the private key that matches one of the SSH public keys in `cluster.sshKeys`. Run `curl` with `sudo`, because only `root` can read the cluster CA file:

```bash
sudo curl --cacert /etc/kubernetes/pki/ca.crt https://<vip>:6443/healthz
```

Continue when it prints `ok`; otherwise see [Troubleshooting](./troubleshooting.mdx#self-built-vip).

## Run `create` Again \{#rerun-create}

`create` only creates a cluster. Do not run it on a cluster that already exists. To change a running cluster, see [Manage Nodes](../../../configure/nodes/alauda_os/vmware-vsphere.mdx).

If `create` stops before the cluster is created, run the same command again. It skips the work that is already done.

When you run `create` again on the same directory:

- It recreates objects that were deleted, except the credential Secret, which `ac` does not render.
- It does not overwrite a field that was changed with another tool. When the rendered value differs, `create` stops and reports that another manager owns the fields. Do not delete the object that the error names.
- When `manifests/` already exists, `create` asks whether to reuse it. Press Enter to reuse it, or answer `n` to render again after you change `install-config.yaml`. When standard input is not a terminal, pass `--reuse-manifests=true` or `--reuse-manifests=false`.
- Reusing `manifests/` ignores `install-config.yaml` and skips every check.

Do not edit the files in `manifests/`.

:::warning
Keep `<install-dir>/manifests/`, or set `cluster.encryptionProviderConfig`. A generated encryption key is kept only in `manifests/`. If you render again without doing either, a new key is generated, and `manifests/` no longer records the key that the cluster uses.
:::
