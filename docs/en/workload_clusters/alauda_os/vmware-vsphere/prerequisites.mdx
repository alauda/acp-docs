# Prerequisites for VMware vSphere Workload Clusters

Meet the following before you [create the cluster](./create_cluster.mdx). `ac` creates none of the vCenter objects; it checks them before it applies anything.

## Providers \{#providers}

The Cluster Bootstrap Provider and the Infrastructure Provider for Virtualization Platform are installed on the `global` cluster. A `global` cluster installed on VMware vSphere with `ac` already runs both; otherwise see [Install the Provider](./reference/install_provider.mdx).

## vCenter Reachability \{#vcenter-reachability}

Allow the flows from the `global` cluster, the workload cluster nodes, and the machine that runs `ac` to vCenter that [VMware vSphere](../../../install/prepare/communication_matrix.mdx#provider-vsphere) lists.

## VM Template \{#vm-template-requirements}

The VM template, the datacenter, the port groups, the datastores, and the compute resource exist in vCenter. Create the VM template from the Alauda OS image published for the target platform release, without changes; it carries the Kubernetes version that `ac` installs, the latest Kubernetes version that the platform supports. See [OS Support Matrix](../../../overview/alauda_os_support_matrix.mdx).

### VM Template ConfigMap \{#vm-template-configmap}

ACP cannot discover the VM templates in your vCenter. Create one ConfigMap per VM template on the `global` cluster to register it. It records the VM template name, the ACP version whose Alauda OS image the VM template was made from, and the Kubernetes version and etcd tag of that ACP version. The `cpaas.io/vsphere-vm-template` label value must match the VM template name in vCenter. Run `ac config use-cluster global` first, then the command that the generator prints.

  Replace `<os>` with the OS of the VM template, such as `m55`, `ko`, or `ku`, and take `<acp-version>`, `<kubernetes-version>`, and `<etcd-tag>` from the matching row of [Version Mapping](../../../overview/alauda_os_support_matrix.mdx#version-mapping).

Check that the ConfigMap of your VM template exists. Run on a machine where `ac` is logged in to the platform:

```bash
ac config use-cluster global
ac -n cpaas-system get cm -l cpaas.io/vsphere-vm-template -L cpaas.io/vsphere-vm-template
```

Continue when a ConfigMap lists your VM template name; otherwise create the ConfigMap of your VM template.

## Control Plane Endpoint \{#control-plane-endpoint-modes}

Every cluster reaches its API server through a stable endpoint. Choose the mode before you write `install-config.yaml`: it cannot be changed after the cluster is created, and an existing cluster cannot switch to a Self-built VIP.

| `cluster.network.loadBalancer.type` | Who provides the endpoint |
|---|---|
| `external` (default) | You do. Provision an external Layer 4 TCP load balancer that satisfies [the External Load Balancer requirements](../../../install/prepare/communication_matrix.mdx#external_load_balancer). |
| `internal` | The provider runs a Self-built VIP on the control plane nodes. Meet the [Self-built VIP prerequisites](./reference/install-config-parameters.mdx#self-built-vip-prerequisites) first. |

## Static IP Addresses \{#static-ip-addresses}

Every node has a hostname and a static IPv4 address, plus one address for each additional NIC. All required addresses are allocated and not in use. Plan each host's addresses and disks before the cluster is created: once a machine takes a slot, they cannot be changed; see [Allocated slot restrictions](./reference/install-config-parameters.mdx#create-the-machine-config-pools).

## ClusterResourceSet \{#cluster-resource-set}

The vSphere cloud provider reaches the workload cluster through a Cluster API `ClusterResourceSet` on the `global` cluster. You do not prepare anything for it; if the nodes stay uninitialized after creation, see [Troubleshooting](./troubleshooting.mdx#common-causes).

## Image Registry \{#image-registry}

The cluster pulls its platform components from the registry of the `global` cluster, or from a dedicated registry set with `cluster.registrySecretRef`; see [Choose the Image Registry for a Workload Cluster](../prepare/workload-cluster-image-registry.mdx). The registry is reachable from workload nodes and contains the Kube-OVN chart and CoreDNS repositories and the vSphere CPI tag that the cluster needs.

## vCenter Credential Secret \{#before-you-start}

Create the vCenter credential Secret in `cpaas-system` of the `global` cluster; `ac` references it through `credentialRef` and never creates it. Write the account to `vsphere-credential.env` with an editor, one `key=value` per line, unquoted:

```text title="vsphere-credential.env"
username=<administrator@vsphere.local>
password=<password>
```

Keep the file private (`chmod 600 vsphere-credential.env`); it holds the password.

Run the following commands from a machine where `ac` is logged in to the platform, then remove the file:

```bash
ac config use-cluster global
ac -n cpaas-system create secret generic <cluster-name>-credential --from-env-file=vsphere-credential.env
rm -f vsphere-credential.env
```

Do not create the Secret with `ac apply`: it stores the password in an annotation of the Secret.

Use one Secret per cluster: the provider deletes it with the cluster, so create it again before you recreate a cluster. `ac` renders the CPI credential from the same account; you do not prepare a second one.

The account must be able to read the inventory, and to clone, power, reconfigure, and delete VMs and their disks. When custom attributes are in use, it also needs the privileges in [Install the Provider](./reference/install_provider.mdx#prerequisites).

## Node Labels and Taints \{#node-labels}

Role labels and taints for dedicated node groups, for example for monitoring, logging, or ingress, are planned before the cluster is created, as described in [Infra Nodes](../../../configure/nodes/node_planning.mdx#create-infra-nodes-alauda-os).
