# Prerequisites for Huawei Cloud Stack Workload Clusters

Meet the following before you [create the cluster](./create_cluster.mdx).

## Providers \{#providers}

Install these cluster plugins on the `global` cluster:

- **Alauda Container Platform Cluster Bootstrap Provider**
- **Alauda Container Platform Infrastructure Provider for Huawei Cloud Stack**

A `global` cluster installed on Huawei Cloud Stack with `ac` already runs both. Otherwise, download them from **ACP Common Aligned Extensions** (see [Download](../../../install/prepare/download.mdx)), upload them with `violet push` (see [Upload Packages](../../../extend/upload_package.mdx#violet_push_usage)), and install them as described in [Cluster Plugin](../../../extend/cluster_plugin.mdx). In a Global Cluster Disaster Recovery pair, install them on both `global` clusters.

## Compute Values \{#compute-values}

In `install-config.yaml`, name the image, the flavors, and the availability zones of the nodes by their HCS API values, not by the display names in the tenant UI. The image is described below. For the flavors and zones, see [HCS Objects, Quota, and Node Addresses](#hcs-inputs). For the disks of each node group, see [Disks](./reference/install-config-parameters.mdx#disks).

### Alauda OS Image \{#alauda-os-image}

Upload to HCS the Alauda OS image that is published for the ACP release installed on the `global` cluster; see [Downloading Alauda OS](../../../overview/alauda_os_support_matrix.mdx#downloading-alauda-os). Note the exact name you give the image when you upload it, because the cluster refers to the image by that name. The image architecture must match the architecture of the flavors. The image must carry the Kubernetes version that `ac` installs; see [Kubernetes Version](./reference/install-config-parameters.mdx#kubernetes-version).

### Image ConfigMap \{#image-configmap}

ACP cannot discover the images in your HCS project, so you register each image with a ConfigMap on the `global` cluster. Create one ConfigMap per image. It records:

- the image name
- the ACP version whose Alauda OS image the image was made from
- the Kubernetes version and the etcd tag of that ACP version

The platform upgrade uses these ConfigMaps to find the image of each Kubernetes version. Every HCS cluster therefore needs them, including a cluster created with YAML. Before an upgrade, register the image of every version on the upgrade path, as described in [Stage the Alauda OS Images](../../../upgrade/pre-upgrade.mdx#stage-alauda-os-images). In addition:

- Keep the ConfigMaps of earlier ACP versions.
- For each ACP version, register only one image per architecture.
- The `cpaas.io/hcs-vm-template` label value must match the image name in HCS.

In the generator, select every architecture whose images you register. Each generated ConfigMap records its architecture. Run `ac config use-cluster global` first, then the command that the generator prints.

For each Kubernetes version, register the images of every architecture that your clusters use. In a cluster that mixes x86_64 and aarch64 node pools, every image ConfigMap must set `architecture`.

Check that the ConfigMap of your image exists. Run the following commands from a machine where `ac` is logged in to the platform:

```bash
ac config use-cluster global
ac -n cpaas-system get cm -l cpaas.io/hcs-vm-template -L cpaas.io/hcs-vm-template
```

Continue when a ConfigMap lists your image name; otherwise create the ConfigMap of your image.

## Network Connectivity \{#network-connectivity}

Allow the flows from the `global` cluster nodes and from the machine that runs `ac` to the HCS service and IAM endpoints. The endpoints are listed in [Huawei Cloud Stack](../../../install/prepare/communication_matrix.mdx#provider-hcs). Also allow the `global` cluster nodes to reach the control plane VIP, as listed in [Workload Cluster VIP and Nodes](../../../install/prepare/communication_matrix.mdx#workload_cluster).

## Control Plane ELB Addresses \{#control-plane-elb-addresses}

In the ELB subnets, reserve one free IPv4 address for the VIP, and exactly two free IPv4 addresses for each of the L4 and L7 Hybrid Load Balancing groups. See [Control Plane Endpoint](./reference/install-config-parameters.mdx#configure-hcscluster).

## Image Registry \{#workload-cluster-image-registry}

The cluster pulls its platform components either from the registry of the `global` cluster or from a dedicated registry. Choose the registry before you create the cluster; see [Choose the Image Registry for a Workload Cluster](../prepare/workload-cluster-image-registry.mdx).

## HCS Credential Secret \{#credential-secret}

An HCS credential Secret must exist in `cpaas-system` of the `global` cluster. Note how the Secret is used:

- The cluster refers to the Secret by name. Unlike the `global` cluster, it does not hold an inline credential.
- `ac` never creates or deletes the Secret.
- One Secret can serve several clusters, and its name does not need to match the cluster name.
- Keep the Secret until every cluster that references it is deleted.

Write the credential file in an editor, not at a shell prompt, because the shell records the secret key in its history:

```text title="hcs-credential.env"
accessKey=<access-key>
secretKey=<secret-key>
projectID=<project-id>
region=<region>
externalGlobalDomain=<domain>
schema=https
```

| Key | Required | Description |
|---|---|---|
| `accessKey` | Yes | HCS access key ID from **My Settings** > **Access Keys**. |
| `secretKey` | Yes | HCS secret access key from **My Settings** > **Access Keys**. |
| `projectID` | Yes | Resource Space ID from **My Settings** > **Resource Spaces**, not the display name. |
| `region` | Yes | HCS region API value used by the provider. Tenant administrators cannot retrieve this value from the HCS UI; get it from the HCS administrator. |
| `externalGlobalDomain` | Yes | HCS platform access domain used by the provider. |
| `schema` | No | API scheme for the HCS IAM endpoint: `https` (default) or `http`. |

Write each line as `key=value` without quotes, because `ac` keeps quote characters as part of the value. A value may contain `=`. Only the first `=` on a line separates the key from the value. Create the Secret, then remove the file:

```bash
chmod 600 hcs-credential.env
ac config use-cluster global
ac create secret generic <credential-secret-name> -n cpaas-system --from-env-file=hcs-credential.env
rm -f hcs-credential.env
```

Do not create or update the Secret with `ac apply`, because it stores the secret key in the `kubectl.kubernetes.io/last-applied-configuration` annotation of the Secret. To change a value later, put the new value under `stringData` in a file, and run `ac patch secret <credential-secret-name> -n cpaas-system --type=merge --patch-file=<file>`.

## HCS Objects, Quota, and Node Addresses \{#hcs-inputs}

The following must exist in HCS. `install-config.yaml` names them by their HCS API values. `ac` creates none of them, and a wrong name stops the cluster creation; see [Troubleshooting](./troubleshooting.mdx).

- **The ECS flavors** for the control plane and each worker node group. Name each flavor by its API name, not by its display name in the tenant UI. The flavor fixes the CPU and memory.
- **The availability zones**, if you name them. Use the zone's API name, not a display name. See [Availability Zone Placement](./reference/install-config-parameters.mdx#availability-zone-placement).
- **A VPC, a security group, and every subnet** that `install-config.yaml` names. The subnets are the node subnet and any subnet for the ELB, an additional NIC, or a node group. They belong to that VPC and let cluster nodes reach each other. The security group allows the node-to-node ports in [Communication Matrix](../../../install/prepare/communication_matrix.mdx) and the traffic from the ELB to the control plane nodes that is listed in [Huawei Cloud Stack](../../../install/prepare/communication_matrix.mdx#provider-hcs).
- **An EVS disk type** named `SSD`, `SAS`, or `SATA` for the system and data disks. The type must be available in the target availability zone.
- **Quota** for the instances, the EVS disks, the ELB, and the server group. Confirm it before you create the cluster.

Every node needs a free static IPv4 address in its subnet, one more address for each additional NIC, and a hostname. HCS nodes use static addresses only. Get the exact flavor and zone values from the HCS administrator, because the HCS tenant console might not show them.

## Node Labels and Taints \{#node-labels}

To dedicate node pools to a purpose such as monitoring, logging, or ingress, plan their role labels and taints as described in [Infra Nodes](../../../configure/nodes/node_planning.mdx#create-infra-nodes-alauda-os). `install-config.yaml` does not set them.
