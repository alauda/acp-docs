# Prerequisites for Huawei Cloud Stack Workload Clusters

Meet the following before you [create the cluster](./create_cluster.mdx).

## Providers \{#providers}

Install these cluster plugins on the `global` cluster:

- **Alauda Container Platform Cluster Bootstrap Provider**
- **Alauda Container Platform Infrastructure Provider for Huawei Cloud Stack**

A `global` cluster installed on Huawei Cloud Stack with `ac` already runs both. Otherwise, download them from **ACP Common Aligned Extensions** (see [Download](../../../install/prepare/download.mdx)), upload them with `violet push` (see [Upload Packages](../../../extend/upload_package.mdx#violet_push_usage)), and install them as described in [Cluster Plugin](../../../extend/cluster_plugin.mdx). In a Global Cluster Disaster Recovery pair, install them on both `global` clusters.

## Compute Values \{#compute-values}

`install-config.yaml` names the image, the flavors, and the availability zones of the nodes by their HCS API values, not by tenant UI display names. The image is described below; for the flavors and zones, see [HCS Objects, Quota, and Node Addresses](#hcs-inputs); for the disks of each node group, see [Disks](./reference/install-config-parameters.mdx#disks).

### Alauda OS Image \{#alauda-os-image}

The Alauda OS image published for the ACP release installed on the `global` cluster is uploaded to HCS; see [Downloading Alauda OS](../../../overview/alauda_os_support_matrix.mdx#downloading-alauda-os). `provider.hcs.imageName` is the exact name it was uploaded under. The image architecture matches the architecture of the flavors. The image carries the Kubernetes version that `ac` installs; see [Kubernetes Version](./reference/install-config-parameters.mdx#kubernetes-version).

### Image ConfigMap \{#image-configmap}

ACP cannot discover the images in your HCS project. Create one ConfigMap per image on the `global` cluster to register it. It records the image name, the ACP version whose Alauda OS image the image was made from, and the Kubernetes version and etcd tag of that ACP version. The platform upgrade finds the image of each Kubernetes version through these ConfigMaps, so every HCS cluster needs them, including a cluster created with YAML: before an upgrade, register the image of every version on the upgrade path, as described in [Stage the Alauda OS Images](../../../upgrade/pre-upgrade.mdx#stage-alauda-os-images). Keep the ConfigMaps of earlier ACP versions, and for each ACP version, register only one image per architecture. The `cpaas.io/hcs-vm-template` label value must match the image name in HCS. Select every architecture whose images you register; each generated ConfigMap records its architecture. Run `ac config use-cluster global` first, then the command that the generator prints.

Check that the ConfigMap of your image exists. Run on a machine where `ac` is logged in to the platform:

```bash
ac config use-cluster global
ac -n cpaas-system get cm -l cpaas.io/hcs-vm-template -L cpaas.io/hcs-vm-template
```

Continue when a ConfigMap lists your image name; otherwise create the ConfigMap of your image.

## Network Connectivity \{#network-connectivity}

Allow the flows from the `global` cluster nodes and from the machine that runs `ac` to the HCS service and IAM endpoints that [Huawei Cloud Stack](../../../install/prepare/communication_matrix.mdx#provider-hcs) lists. The `global` cluster nodes also reach `<vipAddress>`, as listed in [Workload Cluster VIP and Nodes](../../../install/prepare/communication_matrix.mdx#workload_cluster).

## Control Plane ELB Addresses \{#control-plane-elb-addresses}

Reserve one free IPv4 address for the VIP and exactly two free IPv4 addresses each for the L4 and L7 Hybrid Load Balancing groups, in the subnets that `provider.hcs.elb` names. See [Control Plane Endpoint](./reference/install-config-parameters.mdx#configure-hcscluster).

## Image Registry \{#workload-cluster-image-registry}

The cluster pulls its platform components from the registry of the `global` cluster, or from a dedicated registry set with `cluster.registrySecretRef`. Choose the registry before you create the cluster; see [Choose the Image Registry for a Workload Cluster](../prepare/workload-cluster-image-registry.mdx).

## HCS Credential Secret \{#credential-secret}

An HCS credential Secret exists in `cpaas-system` of the `global` cluster. `ac` references it through `credentialRef` and never creates or deletes it, so one Secret can serve several clusters, and its name does not need to match the cluster name. Keep the Secret until every cluster that references it is deleted.

Write the credential file with an editor rather than at a shell prompt, which records the secret key in its history:

```text title="hcs-credential.env"
accessKey=<access-key>
secretKey=<secret-key>
projectID=<project-id>
region=<region>
externalGlobalDomain=<domain>
schema=https
```

| Key | Required | Description |
|---|---|---|
| `accessKey` | Yes | HCS access key ID from **My Settings** > **Access Keys**. |
| `secretKey` | Yes | HCS secret access key from **My Settings** > **Access Keys**. |
| `projectID` | Yes | Resource Space ID from **My Settings** > **Resource Spaces**, not the display name. |
| `region` | Yes | HCS region API value used by the provider. Tenant administrators cannot retrieve this value from the HCS UI; get it from the HCS administrator. |
| `externalGlobalDomain` | Yes | HCS platform access domain used by the provider. |
| `schema` | No | API scheme for the HCS IAM endpoint: `https` (default) or `http`. |

Each line is `key=value`, unquoted: `ac` keeps quote characters as part of the value. A value may contain `=`; only the first `=` on a line separates the key from the value. Create the Secret, then remove the file:

```bash
chmod 600 hcs-credential.env
ac config use-cluster global
ac create secret generic <credential-secret-name> -n cpaas-system --from-env-file=hcs-credential.env
rm -f hcs-credential.env
```

Do not create or update the Secret with `ac apply`: it stores the secret key in the `kubectl.kubernetes.io/last-applied-configuration` annotation of the Secret. To change a value later, put it under `stringData` in a file and run `ac patch secret <credential-secret-name> -n cpaas-system --type=merge --patch-file=<file>`.

## HCS Objects, Quota, and Node Addresses \{#hcs-inputs}

The following exist in HCS, and `install-config.yaml` names them by their HCS API values. `ac` creates none of them, and a wrong name stops the cluster creation; see [Troubleshooting](./troubleshooting.mdx).

- **The ECS flavors** for the control plane and each worker node group. Use the flavor's API name, not the tenant UI display name; the flavor fixes CPU and memory.
- **The availability zones**, if you name them: the zone's API name, not a display name. See [Availability Zone Placement](./reference/install-config-parameters.mdx#availability-zone-placement).
- **A VPC, a security group, and every subnet** that `install-config.yaml` names: the node subnet, and any subnet for the ELB, an additional NIC, or a node group. The subnets belong to that VPC and let cluster nodes reach each other. The security group allows the node-to-node ports in [Communication Matrix](../../../install/prepare/communication_matrix.mdx) and the traffic from the ELB to the control plane nodes listed in [Huawei Cloud Stack](../../../install/prepare/communication_matrix.mdx#provider-hcs).
- **An EVS disk type** named `SSD`, `SAS`, or `SATA` for the system and data disks, available in the target availability zone.
- **Quota** for the instances, the EVS disks, the ELB, and the server group. Confirm it before you create the cluster.

Every node has a free static IPv4 address in its subnet, one more per additional NIC, and a hostname; HCS nodes use static addresses only. Get the exact flavor and zone values from the HCS administrator: the HCS tenant console might not show them.

## Node Labels and Taints \{#node-labels}

Role labels and taints for dedicated node pools, for example for monitoring, logging, or ingress, are planned as described in [Infra Nodes](../../../configure/nodes/node_planning.mdx#create-infra-nodes-alauda-os). `install-config.yaml` does not set them.
