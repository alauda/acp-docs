# Prerequisites for Huawei Cloud Stack Workload Clusters

Meet the following before you [create the cluster](./create_cluster.mdx), with `ac` or in the [web UI](./create_cluster.mdx#create-in-web-ui).

## Providers \{#providers}

Install these cluster plugins on the `global` cluster:

- **Alauda Container Platform Cluster Bootstrap Provider**
- **Alauda Container Platform Infrastructure Provider for Huawei Cloud Stack**

A `global` cluster installed on Huawei Cloud Stack with `ac` already runs both. Otherwise, download them from **Common ACP Extensions** (see [Download](../../../install/prepare/download.mdx)), upload them with `violet push` (see [Upload Packages](../../../extend/upload_package.mdx#violet_push_usage)), and install them as described in [Cluster Plugin](../../../extend/cluster_plugin.mdx). In a Global Cluster Disaster Recovery pair, install them on both `global` clusters.

## Alauda OS Image \{#alauda-os-image}

The Alauda OS image published for the ACP release installed on the `global` cluster is uploaded to HCS; see [Downloading Alauda OS](../../../overview/alauda_os_support_matrix.mdx#downloading-alauda-os). `provider.hcs.imageName` is the exact name it was uploaded under. The image carries the Kubernetes version that `ac` installs; see [Kubernetes Version](./reference/install-config-parameters.mdx#kubernetes-version).

## Network Connectivity \{#network-connectivity}

The `global` cluster nodes reach the HCS API under `<externalGlobalDomain>`, on `TCP/443` for `schema: https` or `TCP/80` for `http`. The machine that runs `ac` reaches the IAM endpoint `iam-apigateway-proxy.<externalGlobalDomain>` on the same port.

## Control Plane ELB Addresses \{#control-plane-elb-addresses}

The provider creates the control plane Elastic Load Balance (ELB) itself; you do not prepare a load balancer. Reserve one free IPv4 address for the VIP and exactly two free IPv4 addresses each for the L4 and L7 Hybrid Load Balancing groups, in the subnets that `provider.hcs.elb` names. See [Control Plane Endpoint](./reference/install-config-parameters.mdx#configure-hcscluster).

## Image Registry \{#workload-cluster-image-registry}

Decide which registry the cluster pulls its platform components from: Kube-OVN and the platform modules.

| Option | What you configure | When to use it |
|---|---|---|
| Registry of the `global` cluster | Nothing. `ac` reads the address from the `registry` key of `cpaas-system/public-registry-credential`, and the web UI fills it in for you. | Workload nodes reach that registry with acceptable throughput. |
| Dedicated registry | A registry Secret in `cpaas-system`, referenced by `cluster.registrySecretRef`. `ac` only. | Workload nodes sit in another region or network segment. |

Either registry holds Alauda Container Platform Core for the target version and every plugin you intend to install, and every workload node reaches it. See [Choose the Image Registry for a Workload Cluster](../prepare/workload-cluster-image-registry.mdx).

Choose the registry before you create the cluster: changing or removing `cpaas.io/registry-reference` on an existing `Cluster` does not move it to another registry. The web UI always uses the registry of the `global` cluster.

## HCS Credential Secret \{#credential-secret}

An HCS credential Secret exists in `cpaas-system` of the `global` cluster. `ac` references it through `credentialRef` and never creates or deletes it, so one Secret can serve several clusters, and its name does not need to match the cluster name.

Write the credential file with an editor rather than at a shell prompt, which records the secret key in its history:

```text title="hcs-credential.env"
accessKey=<access-key>
secretKey=<secret-key>
projectID=<project-id>
region=<region>
externalGlobalDomain=<domain>
schema=https
```

Restrict the file, create the Secret from it, then remove it:

```bash
chmod 600 hcs-credential.env

HCS_SECRET_NAME="<credential-secret-name>"

ac config use-cluster global
ac create secret generic "${HCS_SECRET_NAME}" \
  --namespace cpaas-system \
  --from-env-file=hcs-credential.env

rm -f hcs-credential.env
```

Write the values in plain text, one `key=value` per line. Do not quote the values: `ac` takes quote characters literally. A value may contain `=`; only the first `=` on a line separates the key from the value.

Do not create or update the Secret with `ac apply`: it stores the secret key in the `kubectl.kubernetes.io/last-applied-configuration` annotation of the Secret.

| Key | Required | Description |
|---|---|---|
| `accessKey` | Yes | HCS access key ID from **My Settings** > **Access Keys**. |
| `secretKey` | Yes | HCS secret access key from **My Settings** > **Access Keys**. |
| `projectID` | Yes | Resource Space ID from **My Settings** > **Resource Spaces**, not the display name. |
| `region` | Yes | HCS region API value used by the provider. Tenant administrators cannot retrieve this value from the HCS UI; get it from the HCS administrator. |
| `externalGlobalDomain` | Yes | HCS platform access domain used by the provider. |
| `schema` | No | API scheme for the HCS IAM endpoint: `https` (default) or `http`. |

To also select the Secret as the Infrastructure Credential in the web UI, label it:

```bash
ac config use-cluster global
ac -n cpaas-system label secret "${HCS_SECRET_NAME}" capi.cpaas.io/provider=cluster-api-provider-hcs
```

## HCS Objects, Quota, and Node Addresses \{#hcs-inputs}

The following exist in HCS, and `install-config.yaml` names them by their HCS API values. `ac` creates none of them and does not look them up: a wrong name fails only when the provider creates the instances; see [Troubleshooting](./troubleshooting.mdx).

- **The ECS flavors** for the control plane and each worker node group. Use the flavor's API name, not the tenant UI display name; the flavor fixes CPU and memory.
- **The availability zones**, if you name them: the zone's API name, not a display name. See [Availability Zone Placement](./reference/install-config-parameters.mdx#availability-zone-placement).
- **A VPC, a security group, and every subnet** that `install-config.yaml` names: the node subnet, and any subnet for the ELB, an additional NIC, or a node group. The subnets belong to that VPC and let cluster nodes reach each other.
- **An EVS disk type** for the system and data disks that is available in the target availability zone.
- **Quota** for the instances, the EVS disks, the ELB, and the server group. `ac` does not check quota.

Every node has a free static IPv4 address in its subnet, one more per additional NIC, and a hostname; HCS nodes use static addresses only. Get the exact flavor and zone values from the HCS administrator: the HCS tenant console might not show them. The web UI loads them through the selected credential.

## Node Labels and Taints \{#node-labels}

Role labels and taints for dedicated node pools, for example for monitoring, logging, or ingress, are planned as described in [Infra Nodes](../../../configure/nodes/node_planning.mdx#create-infra-nodes-alauda-os). Neither `install-config.yaml` nor the web UI sets them.
