# Create a Cluster on Bare Metal
ACP CLI (ac) renders the cluster objects from one `install-config.yaml`, applies them to the `global` cluster, and the Bare Metal provider builds the cluster from the hosts in your pools. Before that, the hosts register with the `global` cluster as `MachineInventory` objects, and you collect them into one `MachineInventoryPool` per node group; `ac` neither registers hosts nor creates or deletes the pools and registration objects. Every object lives in the `cpaas-system` namespace of the `global` cluster. There is no web UI for Bare Metal clusters.

## Prerequisites

- You meet the [Bare Metal prerequisites](./prerequisites.mdx), including the network paths, the host clock, the TPM decision, and the disk preparation.
- You chose the cluster name. It **must not** be `global` or start with `global-`, which identifies the resources of the `global` disaster recovery pair. Use it as the prefix of the registration and the pools.
- `ac` is logged in to the `global` cluster with `ac login`, and the `global` cluster is the current context. For `type: external`, the machine that runs `ac` reaches the load balancer at `address:port`.

| Placeholder | Value |
|---|---|
| `<cluster-name>` | The workload cluster name, later `cluster.clusterName`. |
| `<registry-address>` | `kubectl get cluster global -n cpaas-system -o jsonpath='{.metadata.annotations.cpaas\.io/registry-address}'` |
| `<base-image-iso>` | `<registry-address>/tkestack/baremetal-base-image-iso:<os-image-tag>`, from [OS Images and Image Catalog](./prerequisites.mdx#os-images-and-image-catalog). |
| `<install-device>` | The whole-disk target for `elemental install`. On multi-disk hosts that reuse one ISO, `/dev/elemental-install-target`; see [Select a Fixed System Disk](./reference/configure-fixed-install-disk.mdx). |

## Procedure

### 1. Create the Registration and the ISO \{#step-1-machineregistration-seedimage}

Write a `MachineRegistration`, which describes the registration and the first-install configuration, and a `SeedImage`, which builds the ISO from `<base-image-iso>`. Take `<base-image-iso>` from the same OS archive as the `baremetal-base-image` in the image catalog.

```yaml title="01-machineregistration-seedimage.yaml"
apiVersion: elemental.cattle.io/v1beta1
kind: MachineRegistration
metadata:
  name: <cluster-name>-registration
  namespace: cpaas-system
  labels:
    app.kubernetes.io/part-of: cluster-api-provider-baremetal
spec:
  # ${...} placeholders are expanded by elemental-register from SMBIOS data.
  machineName: "<cluster-name>-${System Information/UUID}"
  machineInventoryLabels:
    app.kubernetes.io/part-of: cluster-api-provider-baremetal
    pool.baremetal.alauda.io/eligible: "true"
    elemental.cattle.io/serial-number: "${System Information/Serial Number}"
  machineInventoryAnnotations:
    elemental.cattle.io/machine-uuid: "${System Information/UUID}"
  config:
    elemental:
      install:
        device: <install-device>
        eject-cd: true
        reboot: true
        snapshotter:
          type: btrfs
          maxSnaps: 4
      registration:
        # false only when the host has a hardware TPM (/dev/tpm0); otherwise true,
        # with emulated-tpm-seed: -1.
        emulate-tpm: false
---
apiVersion: elemental.cattle.io/v1beta1
kind: SeedImage
metadata:
  name: <cluster-name>-registration-iso
  namespace: cpaas-system
  labels:
    app.kubernetes.io/part-of: cluster-api-provider-baremetal
spec:
  type: iso
  baseImage: <base-image-iso>
  registrationRef:
    apiVersion: elemental.cattle.io/v1beta1
    kind: MachineRegistration
    name: <cluster-name>-registration
    namespace: cpaas-system
  targetPlatform: linux/amd64
  size: 20Gi
  cleanupAfterMinutes: 120
  cloud-config:
    stages:
      boot:
        - name: "Size COS_STATE for reprovisioning"
          files:
            - path: /etc/elemental/config.d/partitions.yaml
              permissions: 0644
              content: |
                install:
                  partitions:
                    state:
                      size: 20480
```

- `install.device`, `eject-cd`, and `reboot` are required in practice. Without a device, `elemental install` can pick an unintended disk; with `eject-cd` or `reboot` false, a host can stay in the live environment and never become usable inventory.
- Do not annotate a workload `MachineRegistration` with `baremetal.cluster.io/system-agent-auth-scope: global`; that marks `global` hosts. Workload hosts register through the platform domain.
- Keep the ISO generic: do not add `/etc/resolv.conf` to `SeedImage.spec.cloud-config`. Put site-specific resolver configuration in `MachineRegistration.spec.config.cloud-config` only when first-boot registration needs it; node DNS is configured later by the kubeadm bootstrap data.

#### Size COS_STATE \{#size-cos-state}

The `state` partition holds the running system and every retained snapshot. An upgrade to a different image holds two systems of about 3.5 GiB at once, so the Elemental default of 8192 MiB fails part-way with `no space left on device`. Partition sizes are fixed at install time, so the failure surfaces only at a later cluster upgrade. The `SeedImage` above sizes it to 20480 MiB.

<Directive type="warning" title="Placement and stage both matter">
  The fragment must sit in `SeedImage.spec.cloud-config` under `stages.boot`. In `MachineRegistration.spec.config.cloud-config`, or under any other stage, the partition stays at 8 GiB and nothing reports an error.
</Directive>

Verify on the first installed host before you boot the rest:

```bash
lsblk -o NAME,SIZE,LABEL | grep COS_STATE    # expect about 20G, not 8G
df -h /
```

### 2. Build the ISO and Boot the Hosts \{#build-iso}

```bash
kubectl apply -f 01-machineregistration-seedimage.yaml
kubectl -n cpaas-system wait --for=condition=SeedImageReady=True \
  seedimage/<cluster-name>-registration-iso --timeout=30m
kubectl -n cpaas-system get seedimage <cluster-name>-registration-iso \
  -o jsonpath='{.status.conditions[?(@.type=="SeedImageReady")].reason}{"\n"}{.status.downloadURL}{"\n"}{.status.checksumURL}{"\n"}'
```

Continue only when the reason is `SeedImageBuildSuccess` and both URLs are non-empty. Do not use `status.state`, which the controller does not populate. After the download lifetime expires, `SeedImageReady` can stay `True` while the reason changes and the URLs are cleared.

Boot every host from the ISO. `elemental-register` creates the `MachineInventory` and uploads `observedNetwork`, then `elemental install` writes the OS to disk. If the live ISO has no DHCP address, configure the network from the host console as in [Network Connectivity](./prerequisites.mdx#network-connectivity).

### 3. Confirm the Registration \{#confirm-registration}

```bash
kubectl -n cpaas-system get machineinventories.elemental.cattle.io
```

Use an inventory only when it:

- Shows `Ready=True` and has a non-empty `status.plan.secretRef.name`.
- Has a `spec.observedNetwork` that matches the host's expected NIC, when the install-time IP must survive reprovisions.
- For managed data disks, runs an observer-capable OS image, reports a fresh `status.observedStorage`, and reaches `status.storage.phase=Prepared`.

Record the exact `MachineInventory` names for the pools.

### 4. Optional: Prepare Managed Data Disks \{#optional-prepare-managed-storage}

Managed storage belongs to the long-lived `MachineInventory`, so configure it while the inventory is unallocated, before you add it to a pool. Follow [Manage Data Disks on Bare-Metal Hosts](../../../configure/nodes/alauda_os/manage-bare-metal-storage.mdx) to verify `elemental-storage-observer.service`, select each device by a stable ID with `Adopt` or `InitializeIfBlank`, patch the declaration with `storagectl`, and wait for `StoragePrepared=True/AllRequiredVolumesPrepared` and `status.storage.phase=Prepared`.

Without managed disks, leave `spec.storage` absent or set `volumes: []`; the inventory converges to `Unmanaged` with `StoragePrepared=True/NoManagedVolumes`.

### 5. Create the Pools \{#step-2-pools}

Create one pool for the control plane and one for each worker node group; two node groups cannot share a pool, and a `MachineInventory` must not appear in two active pools.

```yaml title="02-machineinventorypool.yaml"
apiVersion: infrastructure.cluster.x-k8s.io/v1beta1
kind: MachineInventoryPool
metadata:
  name: <cluster-name>-control-plane-pool
  namespace: cpaas-system
spec:
  clusterName: <cluster-name> # [!code callout]
  machineInventories:
    - name: <control-plane-inventory-1> # [!code callout]
      hostname: <control-plane-host-1> # [!code callout]
    - name: <control-plane-inventory-2>
    - name: <control-plane-inventory-3>
---
apiVersion: infrastructure.cluster.x-k8s.io/v1beta1
kind: MachineInventoryPool
metadata:
  name: <cluster-name>-worker-pool
  namespace: cpaas-system
spec:
  clusterName: <cluster-name>
  machineInventories:
    - name: <worker-inventory-1>
    - name: <worker-inventory-2>
    - name: <worker-inventory-3>
```

<Callouts>

1. `clusterName`: the workload cluster this pool serves.
2. `name`: the exact `MachineInventory` name.
3. `hostname`: optional. Applied at reprovision; defaults to the inventory name.

</Callouts>

```bash
kubectl apply -f 02-machineinventorypool.yaml
kubectl -n cpaas-system get machineinventorypools.infrastructure.cluster.x-k8s.io
```

A healthy pool reports `Ready=True`, `total` equal to the number of listed inventories, and `available = total - allocated - preparing - reprovisioning - unavailable`. An inventory that is missing, has no plan Secret, is not Ready, or has unprepared storage counts as `unavailable` and appears in the `MembersValid` condition. The reconciler writes the `baremetal.alauda.io/pool=<pool-name>` annotation onto each member.

Size each pool to at least the `replicas` of its node group. Rolling upgrades delete a node and add its replacement from the same pool, so the pool must hold the entire replica count.

### 6. Write `install-config.yaml` \{#write-install-config}

Create an installation directory for the cluster and write `install-config.yaml` in it. The hosts supply the CPU, memory, network, and disks, so the node groups only name their pools. The fields are described in [Parameters](./reference/install-config-parameters.mdx).

```yaml title="install-config.yaml"
cluster:
  clusterName: <cluster-name> # [!code callout]
  sshKeys: # [!code callout]
    - <ssh-public-key>
  # registrySecretRef: # [!code callout]
  #   name: <registry-secret-name>
  #   namespace: cpaas-system
  network:
    loadBalancer:
      type: internal # [!code callout]
      address: <control-plane-vip> # [!code callout]
      port: 6443
      vrid: <vrid> # [!code callout]

controlPlane:
  replicas: 3 # [!code callout]
  baremetal:
    machineInventoryPool: <cluster-name>-control-plane-pool

computes: # [!code callout]
  - name: worker
    replicas: 3
    baremetal:
      machineInventoryPool: <cluster-name>-worker-pool
```

<Callouts>

1. `clusterName`: required. It must not be `global` or start with `global-`.
2. `sshKeys`: required. The SSH public keys for the nodes.
3. `registrySecretRef`: optional. A registry other than the platform's; requires platform v4.4.0 or later.
4. `type`: `internal`, the default, or `external`.
5. `address`: required. The control plane VIP, or the load balancer address for `external`.
6. `vrid`: required for `internal`, from 0 to 255. Omit it for `external`.
7. `replicas`: an odd number, `1` or `3` or more. A single control plane node cannot be upgraded.
8. `computes`: optional.

</Callouts>

You do not set the Kubernetes version: `ac` installs the latest version that the platform supports, which the image catalog must map; see [OS Images and Image Catalog](./prerequisites.mdx#os-images-and-image-catalog).

### 7. Create the Cluster \{#create-with-ac}

```bash
ac adm alpha cluster create --dir <install-dir> --provider baremetal
```

Before it applies anything, `ac` checks the following:

- The provider CRDs, including `MachineInventoryPool`, are served on the `global` cluster.
- Every pool exists. When the pool reports them, its `spec.clusterName` is the cluster name and its `status.total` covers the replicas of its node group. `ac` does not check `status.available`; see [Pool Capacity](#worker-pool-capacity).
- For an `internal` VIP, the platform version supports it. An `external` load balancer is not probed.
- The registry resolves: the Secret of `cluster.registrySecretRef`, or the `registry` key of `cpaas-system/public-registry-credential`.
- Every rendered object passes a server-side dry run on the `global` cluster. `ac` names any object it could not dry-run yet.

`create` returns once the objects are applied, and the cluster keeps building. Add `--wait` to wait until all stages are ready; `--timeout` limits the wait, defaults to `2h`, and ends only the wait, not the creation. To render without applying, run `ac adm alpha cluster manifests` with the same flags.

### 8. Monitor the Creation \{#monitor-creation}

```bash
ac adm alpha cluster status --cluster <cluster-name>                      # prints the four stages once
ac adm alpha cluster wait-for install-complete --cluster <cluster-name>   # waits until all four are ready
```

Both commands change nothing and need no installation directory. `--namespace` defaults to `cpaas-system`.

| # | Stage | Done when |
|---:|---|---|
| 1 | `Cluster` | The object exists, is not being deleted, its `infrastructureRef` and `controlPlaneRef` resolve, it reports no failure, and `Available` is `True` when the `Cluster` reports it. |
| 2 | Control plane | `KubeadmControlPlane` `status.readyReplicas` reaches `spec.replicas`. |
| 3 | `MachineDeployment` | Every node group is ready. |
| 4 | `ClusterView` | The platform's view of the cluster reports `status.phase: Running`. `status` also shows the control plane endpoint and the ready node counts. |

When a stage does not advance, see [Troubleshooting](./troubleshooting.mdx).

### 9. Verify the Cluster \{#verify-the-cluster}

```bash
kubectl -n cpaas-system get cluster <cluster-name>
kubectl -n cpaas-system get kubeadmcontrolplane <cluster-name>-control-plane
kubectl -n cpaas-system get machines.cluster.x-k8s.io,baremetalmachines.infrastructure.cluster.x-k8s.io
kubectl -n cpaas-system get machineinventorypools.infrastructure.cluster.x-k8s.io
kubectl -n cpaas-system get machineinventories.elemental.cattle.io \
  -o custom-columns='NAME:.metadata.name,PHASE:.status.storage.phase,PREPARED:.status.storage.conditions[?(@.type=="StoragePrepared")].status,ACTIVE:.status.storage.conditions[?(@.type=="StorageActive")].status'
kubectl --kubeconfig <workload-kubeconfig> get nodes -o wide
```

Expect:

- `Cluster` `Ready=True`, every `KubeadmControlPlane` replica Ready, and every Kubernetes node Ready.
- Every `BaremetalMachine` with `status.phase=Running` and `status.ready=true`.
- Every used `MachineInventory` with `status.plan.state=Applied`, and its plan Secret annotated `baremetal.alauda.io/plan.type=reprovision` (an annotation, not a label).
- Every used inventory with managed volumes in `status.storage.phase=Active` with `StoragePrepared=True` and `StorageActive=True`, and its `BaremetalMachine` with `StorageReady=True/AllVolumesReady`.
- Each pool with `available + allocated + preparing + reprovisioning + unavailable = total`.

Then check the control plane endpoint. The type prints as `Internal` or `External`:

```bash
kubectl -n cpaas-system get baremetalcluster <cluster-name> \
  -o jsonpath='{.spec.controlPlaneLoadBalancer.type}{" "}{.spec.controlPlaneEndpoint.host}{":"}{.spec.controlPlaneEndpoint.port}{"\n"}'
```

- For `Internal`, expect Ready Alive Pods and an API reachable through the VIP:

  ```bash
  kubectl --kubeconfig <workload-kubeconfig> -n kube-system get pods -l app=alive -o wide
  kubectl --kubeconfig <workload-kubeconfig> get --raw=/version
  ```

- For `External`, verify the frontend and every backend against [the External LoadBalancer contract](../prepare/control-plane-endpoint.mdx#external-loadbalancer-contract): every current control plane node is registered, and HTTPS `/healthz` returns HTTP `200` for each backend.

## Run `create` Again \{#rerun-create}

Running `create` again on the same directory puts back anything that has drifted, except Secrets, which `ac` creates once and then leaves as they are. When `manifests/` already exists, `create` asks whether to reuse it: press Enter to reuse it, or answer `n` to render again after you change `install-config.yaml`. When standard input is not a terminal, pass `--reuse-manifests=true` or `--reuse-manifests=false`.

- Reusing `manifests/` skips `install-config.yaml` and every check, and applies the files as they are.
- Rendering again discards hand edits in `manifests/`.
- A generated encryption key is kept only in `manifests/`. Keep that directory, or set `cluster.encryptionProviderConfig`: rendering again without either generates a new key. `create` keeps the existing encryption Secret, so the cluster keeps its key, but `manifests/` then records a different key that cannot restore it.

## Add or Change Node Groups \{#worker-node-deployment}

1. Register the new hosts and create a pool for the new group, as in [steps 1 to 5](#step-1-machineregistration-seedimage).
2. Add the group to `computes`, with `baremetal.machineInventoryPool` set to the new pool.
3. Run `create --reuse-manifests=false` on the same directory.

Changing `replicas` works the same way; the pool must hold at least the new replica count.

### Pool Capacity \{#worker-pool-capacity}

```bash
kubectl -n cpaas-system get machineinventorypools.infrastructure.cluster.x-k8s.io <cluster-name>-worker-pool
```

`status.available` must be at least the target replica count. For more capacity, register more hosts, prepare any managed storage while each inventory is unallocated, and add their names to `spec.machineInventories`. A new host goes through the same first boot as the original nodes, so confirm its [network paths](./prerequisites.mdx#network-connectivity) and [clock](./prerequisites.mdx#host-time-synchronization) as well.
