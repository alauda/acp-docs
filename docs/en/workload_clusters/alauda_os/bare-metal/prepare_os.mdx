# Prepare Alauda OS for Hosts

Before a host can register, three things must exist for its OS and architecture:

- The two OS images, in the registry.
- The key of the Kubernetes version, in the image catalog of the `global` cluster.
- A registration and its ISO, on the `global` cluster.

Prepare them once for each OS and architecture of your hosts, before you [register the hosts](./register_hosts.mdx). Prepare them again in these cases:

- After a platform upgrade, update the registrations; see [After a Platform Upgrade](#after-upgrade).
- When a cluster of an older version needs hosts of an architecture or OS that it has never used, push the images and add the catalog keys of the version of that cluster; see [After a Platform Upgrade](#after-upgrade).

If the `global` cluster was installed on Bare Metal with `ac`, the registry already has the images for the OS and architecture of its hosts, and the image catalog already has their key. For hosts of that OS and architecture, create only the registration and its ISO.

Meet the [Bare Metal prerequisites](./prerequisites.mdx) first. In particular, the Bare Metal provider must run on the `global` cluster. Run the `ac` commands on this page from a machine where `ac` is logged in to the platform.

## Choose the OS and Architecture \{#choose-os}

| OS | Host architectures | Registrations |
|---|---|---|
| Alauda OS M55 | `amd64` | `alaudaos-m55-amd64` |
| Alauda OS KU | `amd64`, `arm64` | `alaudaos-ku-amd64`, `alaudaos-ku-arm64` |

- Each architecture has its own OS archive, its own registration, and its own ISO. One registration serves the hosts of its OS and architecture for every workload cluster.
- All hosts of a cluster run the same OS. An Alauda OS M55 cluster uses `amd64` hosts. The hosts of an Alauda OS KU cluster can mix `amd64` and `arm64`, so prepare both architectures for it. See [Mixed Architecture within a Cluster](../../../overview/alauda_os_support_matrix.mdx#mixed-architecture).

Download the OS archive of each OS and architecture for the ACP version from the OS download page; see [Downloading Alauda OS](../../../overview/alauda_os_support_matrix.mdx#downloading-alauda-os). Each archive holds both OS images of one OS and one architecture; see [Image Format by Provider](../../../overview/alauda_os_support_matrix.mdx#image-format-by-provider).

## Generate the Commands \{#generate}

Fill in the generator below. It prints the following outputs, in this order:

- **Push the OS images**
- **Add the image catalog keys**
- For each architecture, a **Registration file** and the commands to **Create the registration and build the ISO**

The following sections tell you where to run each output.

The generator takes these values:

- **ACP version**: the ACP version of the `global` cluster. For an older cluster that needs hosts of a new architecture or OS, use the ACP version of that cluster. After `ac config use-cluster global`, `ac -n cpaas-system get cvsh` prints the ACP version of each cluster in the `CURRENT` column. When it is not available, see [Check Cluster Versions](../../../upgrade/pre-upgrade.mdx#check-compatibility).
- **OS** and **architectures**: as chosen in [Choose the OS and Architecture](#choose-os).
- **OS image tag**, one for each architecture: the archive file name without `.tar`, for example `alaudaos-45.ku.<timestamp>-0.x86_64`. When the images are already in the registry, for example because the `global` cluster was installed on Bare Metal, the tag is the value of `isoImageTag` in the `install-config.yaml` of that installation. Otherwise, list the tags as described in [Look Up the Image Tags](../../../install/alauda_os/bare-metal/prerequisites.mdx#os-image-tags), and use the tag of the archive for this ACP version.
- **Registry address**: the `registry` key of `cpaas-system/public-registry-credential` on the `global` cluster:

  ```bash
  ac config use-cluster global
  ac -n cpaas-system get secret public-registry-credential -o jsonpath='{.data.registry}' | base64 -d; echo
  ```

## Push the OS Images \{#import-os-images}

Skip this section when the registry already has both images with the OS image tag. This is the case, for example, for the OS and architecture of the hosts of a `global` cluster installed on Bare Metal with `ac`.

Run **Push the OS images** as root, one block for each architecture, on a Linux host that meets these conditions:

- It can reach the registry.
- It has the Core Package of the current platform version extracted. The `packtool` of this package also pushes the archives of earlier ACP versions.
- It has at least as much free space in `/var/tmp` as the archive size.

In the commands, `<extract-dir>` is the extracted `installer/` directory, and `<host-arch>` is the architecture of the host, `amd64` or `arm64`. Each block pushes the two images of one archive, and then lists the tags of both repositories in the registry.

- The `tkestack` project must exist in the registry.
- Use a registry account that can push to the `tkestack` project.
- Do not push with `docker push` or another tool that rewrites the image manifest, because the Alauda OS KU installer reads the manifest exactly as it is in the archive.
- Take both images from the same archive. Do not pair images from different archives, and do not point cluster resources at a build registry.
- For a workload cluster with a dedicated registry (`cluster.registrySecretRef`), push the images into that registry as well, with its address and account. Each time a host is reinstalled, it pulls the OS image that the image catalog names from the registry of the cluster; see [Image Registry](./prerequisites.mdx#image-registry).
- In a disaster recovery pair where the two `global` clusters use different registries, push the images into both registries.

Continue when each `tags/list` response includes the OS image tag. Otherwise, check the registry address, the credentials, the `tkestack` project, and the push output.

## Add the Image Catalog Keys \{#add-versions-to-image-catalog}

`elemental-image-catalog` needs a key for every `Machine.spec.version` that a cluster uses, for both the control plane and the worker nodes. The key is for the architecture and OS of the hosts, keeps the leading `v` of the version, and resolves to the pushed OS image. For the keys that you need, see [OS Image Keys per Architecture and OS](#catalog-key-format).

Skip this section when the catalog already has the keys. To see them, run `ac -n cpaas-system get configmap elemental-image-catalog -o yaml` on the `global` cluster. For example, a `global` cluster installed on Bare Metal with `ac` already has the key for the OS and architecture of its hosts, at the version of the `global` cluster.

Select the `global` cluster first. In a disaster recovery pair, also repeat the following for the standby `global` cluster. For the standby, use `export KUBECONFIG=<standby-kubeconfig>` instead of `ac config use-cluster global`, and run `unset KUBECONFIG` afterwards:

```bash
ac config use-cluster global
ac whoami --show-server
```

Then run **Add the image catalog keys**. The command adds to the ConfigMap the OS image keys of the selected architectures and the etcd key of the selected ACP version. It keeps the existing entries and shows the result. For a new cluster, the Kubernetes version must be the one that `ac` installs, which is the version of the `global` cluster. `ac adm alpha cluster manifests` prints this version as `Pinning Kubernetes <version>`.

Continue when the printed ConfigMap has the OS image keys and the `<kubernetes-version>_etcd` key that you added. Otherwise, run the command again with the correct values. Repeat the command for each OS that your clusters use.

Add the keys before you create the cluster. If its key is missing, a `BaremetalMachine` shows `ImageCatalogMiss`, and it continues by itself once you add the key.

### Image Catalog on the global Cluster \{#image-catalog-on-global}

The provider looks up the OS image of a host in the `elemental-image-catalog` ConfigMap in `cpaas-system` of the `global` cluster. The provider chart creates the catalog with no entries. No node can be provisioned until you add the version. Until the catalog has the key for the Kubernetes version, architecture, and OS of a host, the first `BaremetalMachine` of a workload cluster waits and does not touch the host. It reports:

```text
ImageResolved=False  ImageCatalogMiss:
  no OS image for Kubernetes version "<version>" on <arch> for <os-id> in ConfigMap cpaas-system/elemental-image-catalog (tried keys <keys>); add key "<key>", machines waiting for it continue without being deleted
```

When `ac` installs a `global` cluster, it adds to the catalog of that cluster the key of the Kubernetes version that it installs. That key serves hosts with the same OS and architecture as the hosts of the `global` cluster. For Alauda OS M55 on `amd64`, it also serves hosts registered without architecture and OS labels. Add keys in these cases:

- For hosts of another architecture or OS.
- For every other Kubernetes version that the `global` cluster manages.
- On a `global` cluster that was not installed on Bare Metal with `ac`.

In a disaster recovery pair, the catalog is not synchronized. Add the keys on both `global` clusters.

The image that a host is installed with comes from the catalog key for the Kubernetes version of the cluster that it joins. It does not come from the ISO that the host registered with. Therefore, a cluster of an older version can still get nodes, as long as the catalog has the key of that version for the architecture and OS of the hosts. Add the nodes as described in [Manage Nodes on Bare Metal](../../../configure/nodes/alauda_os/bare-metal.mdx).

### OS Image Keys per Architecture and OS \{#catalog-key-format}

The provider looks up the OS image of a host by the key `<kubernetes-version>_<arch>_<os-id>`, for example `v1.36.4-acp.3_amd64_alaudaos.k.25`. The last two parts come from labels on the `MachineInventory` of the host:

- `<arch>` is the value of `os.baremetal.alauda.io/arch`, or `amd64` when the label is absent.
- `<os-id>` is the value of `os.baremetal.alauda.io/id`, or `alaudaos.m.55` when the label is absent. Alauda OS M55 uses `alaudaos.m.55`, and Alauda OS KU uses `alaudaos.k.25`.

Only hosts with the OS identifier `alaudaos.m.55` fall back to `<kubernetes-version>_<arch>`. Of those, only `amd64` hosts fall back further to the bare `<kubernetes-version>` key. The generator writes the bare key for `amd64` hosts with Alauda OS M55, and the full key for every other combination.

A new host gets both labels from `MachineRegistration.spec.machineInventoryLabels` when it registers; see [Create the Registration and the ISO](#create-registration). A host registered without them is treated as `amd64` and `alaudaos.m.55`. For `amd64` hosts with Alauda OS M55, no action is needed. For other hosts that are already registered without the labels, contact technical support.

## Create the Registration and the ISO \{#create-registration}

For each architecture:

1. Save the **Registration file** under the `<name>.yaml` file name that the generator shows, for example `alaudaos-m55-amd64.yaml`. The file holds two objects: a `MachineRegistration`, which describes the registration and the first-install configuration, and a `SeedImage` named `<name>-iso`, which builds the ISO from the ISO image.
2. Run **Create the registration and build the ISO**. It applies the file on the `global` cluster, waits until the ISO is built, and prints the reason of `SeedImageReady`, the download URL, and the checksum URL of the ISO.

Continue only when the reason is `SeedImageBuildSuccess` and both URLs are non-empty. Each host that boots the ISO registers as a `MachineInventory` named `<name>-<system-uuid>`.

The generator writes the registration file for you. When you check or adapt it, keep the following:

- The name `<name>` appears in `metadata.name`, in `machineName`, and in the `SeedImage` name and its `registrationRef`. The default names are `alaudaos-m55-amd64`, `alaudaos-ku-amd64`, and `alaudaos-ku-arm64`. A workload registration must not be named `global` or start with `global-`. Those names are reserved for hosts of the `global` cluster; see [Hosts for the global Cluster](./register_hosts.mdx#global-hosts).
- Keep `device-selection: inventory`, `eject-cd: true`, and `reboot: true`. The first makes a host install only to the disk that you select in [Select the System Disk](./register_hosts.mdx#select-system-disk). Without the other two, the host can stay in the live environment.
- Keep the `os.baremetal.alauda.io/arch` and `os.baremetal.alauda.io/id` labels in `machineInventoryLabels`. The provider uses them to find the image catalog key of each host; see [OS Image Keys per Architecture and OS](#catalog-key-format).
- For Alauda OS KU, keep `install.system-uri`, the root filesystem image with the registry address. The Alauda OS KU installer installs from this image, and fails without it.
- Do not annotate a workload `MachineRegistration` with `baremetal.cluster.io/system-agent-auth-scope: global`. This annotation marks the hosts of the `global` cluster.
- Do not add `/etc/resolv.conf` to `SeedImage.spec.cloud-config`. Put site-specific resolver configuration in `MachineRegistration.spec.config.cloud-config` only when first-boot registration needs it.

### Size COS_STATE \{#size-cos-state}

**Applies to**: Alauda OS M55. The Alauda OS KU registration has no such fragment.

Keep the `state` partition size of 20480 MiB in the generated `SeedImage`. With the Elemental default of 8192 MiB, a later cluster upgrade fails with `no space left on device`. You cannot change the size after the host is installed.

<Directive type="warning" title="Placement and stage both matter">
  The fragment must be in `SeedImage.spec.cloud-config`, under `stages.boot`. If you put it in `MachineRegistration.spec.config.cloud-config` or under any other stage, the partition stays at 8 GiB, and no error is reported.
</Directive>

### Verify the ISO \{#verify-iso}

The checksum file holds the SHA-256 hash and the original file name of the ISO. The original name contains colons, which Windows does not allow in file names. The saved file therefore often has another name, and `sha256sum -c` cannot find it. Compare the hashes instead:

```bash
curl -sSk <checksum-url> | awk '{print $1}'    # expected hash
sha256sum <saved-iso-file> | awk '{print $1}'  # actual hash
```

Continue when the two hashes are the same. Otherwise, download the ISO again. On Windows, `certutil -hashfile <saved-iso-file> SHA256` prints the actual hash.

### Rebuild the ISO \{#rebuild-iso}

After `cleanupAfterMinutes`, the URLs are cleared, but `SeedImageReady` can stay `True`. Check the reason again before you download the ISO. To get a new URL, delete the `SeedImage` and apply the file again:

```bash
ac config use-cluster global
ac -n cpaas-system delete seedimage <name>-iso
ac apply -f <name>.yaml
```

Then repeat the `wait` and `get` commands of **Create the registration and build the ISO**. If you no longer have `<name>.yaml`, generate it again as described in [Generate the Commands](#generate), with the same ACP version and OS image tag.

Hosts that have already booted the old ISO continue to register. Boot the remaining hosts from the new ISO.

## After a Platform Upgrade \{#after-upgrade}

A registration uses the images of the platform version that it was generated for. After the `global` cluster is upgraded, update the registration of each OS and architecture that you still use:

1. Run the generator with the new ACP version and the OS image tag of its archive. Run **Push the OS images** and **Add the image catalog keys** only for an OS or architecture that was not staged. For the OS and architecture of the hosts in the pools, the images and the catalog keys of the new version were already staged before the upgrade, as described in [Stage the Alauda OS Images](../../../upgrade/pre-upgrade.mdx#stage-alauda-os-images).
2. Save the new **Registration file** under the same name, and rebuild the ISO from it as described in [Rebuild the ISO](#rebuild-iso).

Hosts that are already registered are not affected. To see which images a registration uses, list the `SeedImage` objects as described in [Boot the Hosts](./register_hosts.mdx#boot-hosts).

The catalog needs a key for every Kubernetes version in use, for each architecture and OS of the hosts. When a cluster of an older version needs hosts of an architecture or OS that it has never used, run the generator with the ACP version of that cluster. Run only **Push the OS images** and **Add the image catalog keys**, with the OS archive of that ACP version. Register the hosts with the registration of the current platform version, because a host is installed with the image of the cluster that it joins.
