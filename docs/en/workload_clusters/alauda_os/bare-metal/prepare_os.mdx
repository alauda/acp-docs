# Prepare Alauda OS for Hosts

A host joins the platform by booting from an ISO. On this page, you build that ISO: one registration and one ISO for each OS and architecture of your hosts. One registration serves the hosts of its OS and architecture for every workload cluster. Do this before you [register the hosts](./register_hosts.mdx).

Meet the [Bare Metal prerequisites](./prerequisites.mdx) first. Run the `ac` commands on this page from a machine where `ac` is logged in to the platform.

Find your case, and follow its sections:

| Your case | Sections to follow |
|---|---|
| The `global` cluster was installed on Bare Metal with `ac`. The hosts have the same OS and architecture as the hosts of the `global` cluster, and are for a new cluster that uses the registry of the `global` cluster. | [Generate the Commands](#generate), then [Create the Registration and the ISO](#create-registration). The installation of the `global` cluster already pushed the images and added the image catalog keys. |
| Any other new cluster: hosts of another OS or architecture, a cluster with a dedicated registry, or a `global` cluster that was not installed on Bare Metal with `ac`. | All sections, in order. |
| The platform was upgraded. | [After a Platform Upgrade](#after-upgrade). |
| An existing cluster of an older version needs hosts of an architecture that it has never used. | [Generate the Commands](#generate) with the ACP version of that cluster, then [Push the OS Images](#import-os-images) and [Add the Image Catalog Keys](#add-versions-to-image-catalog). Register the hosts with the registration of the current platform version. |

## Generate the Commands \{#generate}

Fill in the generator below, once for each OS:

| Field | Value |
|---|---|
| **ACP version** | The ACP version of the `global` cluster. A new cluster always has this version. |
| **OS** | Alauda OS M55 or Alauda OS KU. All hosts of a cluster run the same OS. |
| **Architectures** | The architectures of the hosts. Alauda OS M55 hosts are `amd64`. The hosts of an Alauda OS KU cluster can mix `amd64` and `arm64`. |
| **OS image tag** | One for each architecture: the file name of the OS archive without `.tar`. See [Look Up the Image Tags](../../../install/alauda_os/bare-metal/prerequisites.mdx#os-image-tags). |
| **Registry address** | The registry of the `global` cluster. The generator shows the command that prints it. |

The generator prints these outputs:

- **Push the OS images**: see [Push the OS Images](#import-os-images).
- **Add the image catalog keys**: see [Add the Image Catalog Keys](#add-versions-to-image-catalog).
- For each architecture, **Registration file** and **Create the registration and build the ISO**: see [Create the Registration and the ISO](#create-registration).

## Push the OS Images \{#import-os-images}

Download the OS archive of each architecture for the ACP version; see [Downloading Alauda OS](../../../overview/alauda_os_support_matrix.mdx#downloading-alauda-os).

Run **Push the OS images** as root, one block for each architecture, on a Linux host that meets these conditions:

- It can reach the registry.
- It has the Core Package of the current platform version extracted. The `packtool` of this package also pushes the archives of earlier ACP versions.
- It has at least as much free space in `/var/tmp` as the archive size.

In the commands, `<extract-dir>` is the extracted `installer/` directory, and `<host-arch>` is the architecture of the host, `amd64` or `arm64`. Each block pushes the two images of one archive, and then lists the tags of both repositories in the registry.

- The `tkestack` project must exist in the registry.
- Use a registry account that can push to the `tkestack` project.
- Do not push with `docker push` or another tool that rewrites the image manifest, because the Alauda OS KU installer reads the manifest exactly as it is in the archive.
- Take both images from the same archive. Do not pair images from different archives, and do not point cluster resources at a build registry.
- For a workload cluster with a dedicated registry (`cluster.registrySecretRef`), push the images into that registry as well, with its address and account. Each time a host is reinstalled, it pulls the OS image that the image catalog names from the registry of the cluster; see [Image Registry](./prerequisites.mdx#image-registry).
- In a disaster recovery pair where the two `global` clusters use different registries, push the images into both registries.

Continue when each `tags/list` response includes the OS image tag. Otherwise, check the registry address, the credentials, the `tkestack` project, and the push output.

## Add the Image Catalog Keys \{#add-versions-to-image-catalog}

The image catalog tells the provider which OS image to install on a host. Until the catalog has the key for the Kubernetes version, architecture, and OS of a host, the host waits and is not installed.

Select the `global` cluster, and run **Add the image catalog keys**:

```bash
ac config use-cluster global
ac whoami --show-server
```

The command adds the keys to the image catalog, keeps the existing keys, and prints the catalog. Continue when the printed catalog has the keys that you added. Otherwise, run the command again with the correct values.

In a disaster recovery pair, the image catalog is not synchronized. Run the command again for the standby `global` cluster: use `export KUBECONFIG=<standby-kubeconfig>` instead of `ac config use-cluster global`, and run `unset KUBECONFIG` afterwards.

## Create the Registration and the ISO \{#create-registration}

For each architecture:

1. Save the **Registration file** under the file name that the generator shows, for example `alaudaos-m55-amd64.yaml`. Use the file as generated.
2. Run **Create the registration and build the ISO**. It applies the file on the `global` cluster, waits until the ISO is built, and prints three lines: the result of the build, the download URL of the ISO, and the URL of its checksum.

Continue when the first line is `SeedImageBuildSuccess` and the two URLs are not empty. Then download the ISO, and verify it.

### Verify the ISO \{#verify-iso}

The checksum file holds the SHA-256 hash and the original file name of the ISO. The original name contains colons, which Windows does not allow in file names. The saved file therefore often has another name, and `sha256sum -c` cannot find it. Compare the hashes instead:

```bash
curl -sSk <checksum-url> | awk '{print $1}'    # expected hash
sha256sum <saved-iso-file> | awk '{print $1}'  # actual hash
```

Continue when the two hashes are the same. Otherwise, download the ISO again. On Windows, `certutil -hashfile <saved-iso-file> SHA256` prints the actual hash.

### Rebuild the ISO \{#rebuild-iso}

After `cleanupAfterMinutes`, the URLs are cleared, but `SeedImageReady` can stay `True`. Check the reason again before you download the ISO. To get a new URL, delete the `SeedImage` and apply the file again:

```bash
ac config use-cluster global
ac -n cpaas-system delete seedimage <name>-iso
ac apply -f <name>.yaml
```

Then repeat the `wait` and `get` commands of **Create the registration and build the ISO**. If you no longer have `<name>.yaml`, generate it again as described in [Generate the Commands](#generate), with the same ACP version and OS image tag.

Hosts that have already booted the old ISO continue to register. Boot the remaining hosts from the new ISO.

## After a Platform Upgrade \{#after-upgrade}

After the platform is upgraded, update the registration of each OS and architecture that you still use, so that new hosts register with the images of the new version. Hosts that are already registered are not affected.

1. Run the generator with the new ACP version and the OS image tag of its archive. You do not need **Push the OS images** or **Add the image catalog keys**: you pushed the images and added the keys of the new version before the upgrade, in [Stage the Alauda OS Images](../../../upgrade/pre-upgrade.mdx#stage-alauda-os-images).
2. Save the new **Registration file** under the same name, and rebuild the ISO as described in [Rebuild the ISO](#rebuild-iso).
