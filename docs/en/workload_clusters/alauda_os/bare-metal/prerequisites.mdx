# Prerequisites for Bare Metal Workload Clusters

Meet the following before you [register the hosts](./create_cluster.mdx#step-1-machineregistration-seedimage) and [create the cluster](./create_cluster.mdx). They also apply to every host that you add to a cluster later.

## Providers \{#providers}

Install these cluster plugins on the `global` cluster:

- **Alauda Container Platform Cluster Bootstrap Provider**
- **Alauda Container Platform Infrastructure Provider for Bare Metal**, which installs the bare-metal manager and `elemental-operator`

A `global` cluster installed on Bare Metal with `ac` already runs both. Otherwise, download them from **ACP Common Aligned Extensions** (see [Download](../../../install/prepare/download.mdx)), upload them with `violet push` (see [Upload Packages](../../../extend/upload_package.mdx#violet_push_usage)), and install them as described in [Cluster Plugin](../../../extend/cluster_plugin.mdx). In a disaster recovery pair, install them on both `global` clusters.

### Platform Certificate \{#platform-certificate}

**Applies to**: a platform that uses a third-party certificate. Skip it when the provider is already installed and `elemental-operator` runs.

Run the following commands from a machine where `ac` is logged in to the platform:

```bash
ac config use-cluster global
ac -n cpaas-system get secret dex.tls -o jsonpath='{.data}' | jq -r 'keys | join(",")'
```

Continue when the keys include `ca.crt`; otherwise, install the Infrastructure Provider for Bare Metal with YAML, as described in [Installing via YAML](../../../extend/cluster_plugin.mdx#installing-via-yaml), and set `elemental.tls.caCertSecretKey: tls.crt` in `spec.valuesOverride` of its `ModuleInfo`; the Web Console form has no field for it:

```yaml
spec:
  valuesOverride:
    acp/chart-cluster-api-provider-baremetal:
      elemental:
        tls:
          caCertSecretKey: tls.crt
```

## OS Images and Image Catalog \{#os-images-and-image-catalog}

Both Bare Metal OS images are in the platform registry, and `elemental-image-catalog` on the `global` cluster maps the Kubernetes version that `ac` installs to the root filesystem image, for the architecture and OS of your hosts. When the `global` cluster was installed on Bare Metal with `ac`, the images are already in the registry and the catalog already has the entry for `amd64` hosts with Alauda OS M55; skip [Import the OS Images](#import-os-images), and add keys only as described in [Image Catalog on the global Cluster](#image-catalog-on-global).

| Image | Used by | Purpose |
|---|---|---|
| `baremetal-base-image` | `elemental-image-catalog` | Reprovisions a registered host with the Kubernetes-specific root filesystem. |
| `baremetal-base-image-iso` | `SeedImage.spec.baseImage` | Builds the live ISO for initial installation and registration. |

The provider package contains no OS image, and the provider chart creates the catalog with no entries; adding a catalog entry or a `SeedImage` reference does not import the image.

### Import the OS Images \{#import-os-images}

The Bare Metal OS download is an archive of one OCI image layout that holds both images under the same tag; see [Image Format by Provider](../../../overview/alauda_os_support_matrix.mdx#image-format-by-provider). On a host with containerd that reaches the registry, such as a `global` control plane node, run as root, with free space in `/var/lib/containerd` of at least the archive size:

```bash
read -rsp 'Registry password: ' REGISTRY_PASSWORD; echo
ctr -n bare-metal-os images import --all-platforms --no-unpack <bare-metal-os-archive>
ctr -n bare-metal-os images ls -q     # baremetal-base-image:<os-image-tag> and baremetal-base-image-iso:<os-image-tag>

for repo in baremetal-base-image baremetal-base-image-iso; do
  ctr -n bare-metal-os images push --local --tlscacert <registry-ca-file> \
    -u "<registry-username>:${REGISTRY_PASSWORD}" \
    "<registry-address>/tkestack/${repo}:<os-image-tag>" "${repo}:<os-image-tag>"
  curl -sS --cacert <registry-ca-file> -u "<registry-username>:${REGISTRY_PASSWORD}" \
    "https://<registry-address>/v2/tkestack/${repo}/tags/list"
done

ctr -n bare-metal-os images rm \
  "baremetal-base-image:<os-image-tag>" "baremetal-base-image-iso:<os-image-tag>"
unset REGISTRY_PASSWORD
```

`--tlscacert` and `--skip-verify` require `--local`. Only for a self-signed registry that you trust and whose CA file you do not have, replace `--tlscacert <registry-ca-file>` with `--skip-verify` and `--cacert <registry-ca-file>` with `-k`. The `tkestack` project must exist in the registry. Continue when each `tags/list` response includes `<os-image-tag>`. For the registry of the `global` cluster, the user is `admin` and its password is in the `cpaas-system/registry-admin` Secret on the `global` cluster, and `<registry-address>` is the `registry` key of `cpaas-system/public-registry-credential` on the `global` cluster. In a disaster recovery pair, import into the registry of both `global` clusters. Take both images from the same archive; do not pair images from different archives or point cluster resources at a build registry.

### Image Catalog on the global Cluster \{#image-catalog-on-global}

The provider looks up the OS image of a host in the `elemental-image-catalog` ConfigMap in `cpaas-system` of the `global` cluster. Until the catalog has the key for the Kubernetes version, architecture, and OS of a host, the first `BaremetalMachine` of a workload cluster fails immediately:

```text
ImageResolved=False  ImageCatalogMiss:
  no OS image mapped for Kubernetes version "<version>" on <arch> for <os-id> (looked up key "<key>")
```

`ac` adds the key of the Kubernetes version that it installs to the catalog of the `global` cluster it installs. That key serves `amd64` hosts with Alauda OS M55, including hosts registered without architecture and OS labels. Add keys as described in [Add Kubernetes Versions to the Image Catalog](#add-versions-to-image-catalog) for hosts of another architecture or OS, for every other Kubernetes version that the `global` cluster manages, and on a `global` cluster that was not installed on Bare Metal with `ac`. In a disaster recovery pair, the catalog is not synchronized: add the keys on both `global` clusters.

### Add Kubernetes Versions to the Image Catalog \{#add-versions-to-image-catalog}

Every `Machine.spec.version` that a cluster uses, for the control plane and for the worker nodes alike, needs a key in `elemental-image-catalog` for the architecture and OS of the hosts, with the leading `v` preserved, that resolves to the imported OS image; see [OS Image Keys per Architecture and OS](#catalog-key-format). The provider chart creates the catalog with no entries, so no node can be provisioned until you add the version.

Run the following commands from a machine where `ac` is logged in to the platform. In a disaster recovery pair, repeat them for the standby `global` cluster, with `export KUBECONFIG=<standby-kubeconfig>` in place of `ac config use-cluster global`, and run `unset KUBECONFIG` afterwards:

```bash
ac config use-cluster global
ac whoami --show-server
```

Select the ACP version, the OS, and the architecture of the hosts, and enter the tag of the imported OS image below. All hosts of an Alauda OS M55 cluster use one architecture. The hosts of an Alauda OS KU cluster can mix x86_64 (`amd64`) and Arm (`arm64`): select every architecture that they use, and enter the tag of the image of each architecture. The command adds the OS image key of each selected architecture and the etcd key of that version. It patches the ConfigMap rather than replacing it, so that existing entries are kept, and then shows the result. For a new cluster, the Kubernetes version must be the one that `ac` installs; `ac adm alpha cluster manifests` prints it as `Pinning Kubernetes <version>`.

<BareMetalImageCatalog mode="single">
  The command creates a `ResourcePatch` that records the change. Do not delete it. Before the next platform upgrade, exempt it for the target version as described in [Handle Preflight Blocks](../../../upgrade/troubleshooting.mdx#handle-preflight-blocks-when-needed); otherwise the `ResourcePatchUpgradeable` preflight check blocks that upgrade.
</BareMetalImageCatalog>

Continue when the printed ConfigMap has the OS image keys and the `<kubernetes-version>_etcd` key that you added; otherwise, run the command again with the correct values. Run the generated command for each OS that your clusters use; for Alauda OS M55 clusters of different architectures, run it for each architecture.

Add the keys before you create the cluster. A `BaremetalMachine` that already hit `ImageCatalogMiss` stays `Failed` after you add them, and restarting the provider does not clear it: delete its `Machine` so that its owner, `KubeadmControlPlane` or the `MachineSet`, recreates it.

### OS Image Keys per Architecture and OS \{#catalog-key-format}

The provider looks up the OS image of a host by the key `<kubernetes-version>_<arch>_<os-id>`, for example `v1.36.4-acp.3_amd64_alaudaos.k.25`. Both parts come from labels on the host's `MachineInventory`:

- `<arch>` is the value of `os.baremetal.alauda.io/arch`, or `amd64` when the label is absent.
- `<os-id>` is the value of `os.baremetal.alauda.io/id`, or `alaudaos.m.55` when the label is absent. Alauda OS M55 uses `alaudaos.m.55`, and Alauda OS KU uses `alaudaos.k.25`.

Only hosts with the OS identifier `alaudaos.m.55` fall back to `<kubernetes-version>_<arch>`, and only `amd64` hosts with that identifier fall back further to the bare `<kubernetes-version>` key. The generator writes the bare key for `amd64` hosts with Alauda OS M55 and the full key for every other combination. An Alauda OS KU cluster whose hosts use both architectures needs the keys of both at every version.

A new host gets both labels when it registers, from `MachineRegistration.spec.machineInventoryLabels`; see [Create the Registration and the ISO](./create_cluster.mdx#step-1-machineregistration-seedimage). A host registered without them resolves to `amd64` and `alaudaos.m.55`. That needs no action for `amd64` hosts with Alauda OS M55. For other hosts that are already registered without the labels, contact technical support.

## Network Connectivity \{#network-connectivity}

Hosts are registered, installed, and joined over the network. Before the first host boots the ISO, open every flow in [Bare Metal](../../../install/prepare/communication_matrix.mdx#provider-baremetal), plus DNS and NTP from [Infrastructure Services](../../../install/prepare/communication_matrix.mdx#infrastructure_services) and the cluster-internal flows in [Within a Cluster](../../../install/prepare/communication_matrix.mdx#within_cluster). The host firewall on an Alauda OS node is maintained by the platform; see [Managing Firewall Ports](../../../configure/machine_config/firewall.mdx).

Do not boot a workload host from an ISO that was built while the `global` cluster was installed: it registers with the bootstrap node.

**Control plane endpoint.** For `type: internal`, the VIP is in the same Layer 2 domain as the control plane node IPs, the `vrid` is unique in it, and VRRP and gratuitous ARP are allowed. For `type: external`, provision the listener and backends before you run `create`; see [Plan the Control Plane Endpoint](../../../install/alauda_os/prerequisites.mdx#control-plane-endpoint).

**First-boot addressing.** If a host gets no DHCP address in the live ISO, configure it from the host console before you wait for registration:

```bash
nmcli connection show
nmcli connection modify "Wired connection 1" \
  ipv4.method manual \
  ipv4.addresses <host-ip>/<prefix-length> \
  ipv4.gateway <gateway-ip> \
  ipv4.dns <dns-ip> \
  ipv4.ignore-auto-dns yes
nmcli connection up "Wired connection 1"
```

## Host Time Synchronization \{#host-time-synchronization}

Every host carries the correct time when it boots the ISO: one time zone on every node and at most 10 seconds between nodes, as in [Node Checks](../../../install/non_alauda_os/node_preprocessing.mdx#node_checks). Nothing on this path verifies it for you, and a host with the wrong clock keeps the control plane from coming up.

- Make the site NTP servers reachable on UDP `123`. A production cluster should not depend on public NTP.
- Set the clock in the BIOS/UEFI setup or through the BMC; the install disk is wiped, so there is no OS to run a command in. Keep the hardware clock on UTC.
- Compare the hosts with each other: the spread across the hosts of one cluster stays within 10 seconds.
- After the nodes are `Ready`, confirm with `timedatectl` and `chronyc tracking` on each node.

A Day-2 chrony `MachineConfig`, as in [Configuring the Chrony Time Service](../../../configure/machine_config/managing.mdx#configuring-the-chrony-time-service), does not replace this: it configures running nodes only.

## TPM \{#tpm-decision}

Decide per host whether it exposes a working hardware TPM (`/dev/tpm0`), not whether it is physical or virtual. In the `MachineRegistration` of [Register the Hosts](./create_cluster.mdx#step-1-machineregistration-seedimage):

- `emulate-tpm: false`, or the field omitted, only for hosts with a hardware TPM.
- `emulate-tpm: true` with `emulated-tpm-seed: -1` for every other host, including physical servers without a TPM module. Otherwise `elemental-register` fails TPM attestation and never sends the registration request.

## Image Registry \{#image-registry}

By default the cluster uses the registry of the `global` cluster: `ac` reads its address from the `registry` key of `cpaas-system/public-registry-credential`, which must exist even when the registry needs no authentication. To pull platform component images from a dedicated registry instead, follow [Choose the Image Registry for a Workload Cluster](../prepare/workload-cluster-image-registry.mdx) and set `cluster.registrySecretRef`.

The hosts install and join with the platform registry address alone; a credential matters only when platform components are installed on the cluster. The choice of registry is fixed when the cluster is created, so decide before you run `create`. Neither choice affects the OS images, which hosts always pull from the platform registry.

## Host Disks and Boot Order \{#host-disk-and-boot-preparation}

Classify every disk and virtual disk on each host before it boots the ISO, and record the OS install target and the disks that must keep data:

- Wipe the OS install disk and any obsolete boot disk, so that the host boots the ISO and not an old OS. Set `install.device` in the `MachineRegistration` to the exact OS disk.
- Do **not** wipe a data disk that you will manage with the `Adopt` policy. Back it up and record its stable ID and filesystem UUID. A disk for `InitializeIfBlank` must be disposable and blank, and still needs a separate initialization approval after registration.
- Remove the Elemental labels `COS_STATE`, `COS_PERSISTENT`, `COS_OEM`, and `COS_RECOVERY` from **all** disks and every multipath path. Elemental resolves partitions by label, and a stale label on another disk makes the reprovision fail. Clean the disk rather than disabling multipath.
- On a host with several disks, do not leave `install.device` empty or use `/dev/sda`; follow [Select a Fixed System Disk on Multi-Disk Bare-Metal Hosts](./reference/configure-fixed-install-disk.mdx).
- Boot the virtual CD or ISO first.

Use only stable storage identities reported by the registered inventory. Runtime paths such as `/dev/sdX`, `/dev/vdX`, `/dev/nvmeXnY`, and `/dev/mapper/mpathX` must not be placed in `MachineInventory.spec.storage`.

## Node Labels and Taints \{#node-labels}

To reserve the nodes of a pool for monitoring, logging, or ingress, plan their role labels and taints before you create the pools, as described in [Infra Nodes](../../../configure/nodes/node_planning.mdx#create-infra-nodes-alauda-os).
