# Introduction 

Alauda Container Platform Virtualization with KubeVirt leverages Kubernetes extended API capabilities to abstract virtual machine images as a **Custom Resource Definition** (CRD). It provides a user interface (UI) for users to easily import virtual machine images stored in remote repositories into ACP for usage.

## Advantages 

- Support for Mainstream Operating Systems 

  Supports various commonly used Linux distributions and Windows operating systems.

- Multi-Architecture Support

  Compatible with both **X86_64** and **ARM64** architectures.

- Multi-Source Support

  Allows importing virtual machine images from:
  - Image registries
  - File servers (HTTP and HTTPS, including servers with a private CA)
  - S3-compatible object storage
  - Existing disks and volume snapshots of the cluster

- Multi-Format Support

  Supports virtual machine images in **QCOW2** and **RAW** formats.

## Image Sources and Image Instances

The console manages images at two levels:

| | Image source | Image instance |
| :-- | :-- | :-- |
| What it is | Where an image is stored (registry, HTTP or S3 address) and which projects may use it | The image imported into a cluster as a ready-to-boot volume |
| Kubernetes resource | `VirtualMachineImageTemplate`, a platform resource shared by all clusters | `DataSource` with a PersistentVolumeClaim filled by CDI, in one namespace of one cluster |
| Managed under | **Administrator** > **Virtualization** > **Images** > **Image Source** | **Administrator** > **Virtualization** > **Images** > **Image Instance** (shared, in `kube-public`), or **Container Platform** > **Virtualization** > **Images** > **Image Instance** (in a namespace) |
| A virtual machine created from it | Imports its system disk from the address | Clones its system disk from the volume — faster, and the image server is not contacted again |

Image instances in `kube-public` are shared by every namespace of the cluster; an image instance in a namespace is used only by that namespace. An image instance can also carry import settings an image source cannot, such as the CA certificate of an HTTPS server, and both can declare a default instance type and preference.

## Uploading Images from Outside the Cluster

To upload a **local** image file into the platform (rather than importing from a remote source), use `virtctl image-upload`, which streams the file to the CDI upload proxy. The `cdi-uploadproxy` Service (in the `kubevirt` namespace) must be reachable from where you run the command — expose it through the Gateway API, an Ingress, or a `NodePort`/`LoadBalancer` Service so administrators can upload images from outside the cluster. For the full procedure, including exposing the proxy and creating a virtual machine from the uploaded image, see [Uploading a Local Image and Creating a Virtual Machine](how_to/upload_local_image.mdx); for the `virtctl` reference, see [Using the virtctl Command-Line Tool](../virtual_machine/how_to/virtctl.mdx).
