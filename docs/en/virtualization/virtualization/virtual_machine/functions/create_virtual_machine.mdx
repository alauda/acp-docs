# Creating Virtual Machines

Create a virtual machine (a `VirtualMachine` resource) using an image, and schedule it to physical nodes with KubeVirt components installed and virtualization enabled. A `VirtualMachine` is the desired-state object (analogous to a Deployment); when it is started, KubeVirt produces a running `VirtualMachineInstance` (analogous to a Pod). For the terms used on this page, see [Concepts and Glossary](../../concepts.mdx).

You can create a virtual machine through [Create Virtual Machine](#virtual) using a form, and you may also switch to YAML format for the operation.

**Size new virtual machines with an instance type and a preference.** An instance type declares the CPU and memory once and is shared by every virtual machine that references it; a preference applies the device and firmware settings the guest operating system works best with. Setting CPU and memory directly in the virtual machine (a machine model) remains available as an alternative. See [Instance Types and Preferences](./instance_types_preferences.mdx).

## Prerequisites

- Before creating a virtual machine using an image, please confirm the following with the platform administrator:

  - The target cluster is a self-built cluster, and the Kubevirt components have been deployed.

  - The target node must be a physical node with virtualization enabled.

  - A virtual machine image has been added to the platform.

- If you need to use the physical GPU passthrough feature of the virtual machine, please contact the platform administrator for the following configuration:

  1. Obtain GPU passthrough environment preparation plan and prepare the necessary environment.

  2. Prepare the required physical GPU and enable the related features for physical GPU passthrough for the virtual machine.

## Notes

When using Windows virtual machines, only logins via the **username/password** set in the virtual machine image are supported. Please contact the platform administrator to obtain this information in advance.

## Create Virtual Machine\{#virtual}

### Procedure

**Note**: The following content presents an example of creating a virtual machine using a form, and you may also switch to YAML format for the operation.

1. Enter **Container Platform**.

2. In the left navigation bar, click **Virtualization** > **Virtual Machines**.

3. Click **Create Virtual Machine**.

4. In the **Basic Information** area, fill in the name and display name of the virtual machine and set tags or annotations.

   | Parameter | Description                                                                 |
   | :----------------- | :------------------------------------------------------------------ |
   | **Tags**            | Used to select objects and find collections of objects that meet certain criteria. Must be a key-value pair, for example: *app.kubernetes.io/name: hello-app*. |
   | **Annotations**     | Used to provide any information to development and operations teams. Must be a key-value pair, for example: *cpaas.io/maintainer: kim*.              |

5. In the **Image** area, choose the image the virtual machine boots from.

   | Parameter | Description |
   | :-- | :-- |
   | **CPU Architecture** | The architecture of the image; only images with the same architecture as the cluster can be selected. |
   | **Provision Method** | **Image Source**: a public image assigned to the project by the platform administrator. **Image Instance**: a [bootable volume](../bootable_volume.mdx) the virtual machine clones its system disk from. |
   | **Select Image** | The operating system and the image. An image instance can declare a default instance type and preference; they are then preselected in the **Model** area, and you can still change them. |

6. In the **Model** area, choose how the virtual machine is sized.

   | Parameter | Description |
   | :-- | :-- |
   | **Sizing** | **Instance Type** (default, recommended): the virtual machine references an instance type and carries no CPU or memory of its own. **Machine Model**: the CPU and memory are written into the virtual machine. The two cannot be combined. |
   | **Instance Type** | Shown for the instance type path. Lists the instance types of the current namespace (**This namespace**) and of the cluster (**Cluster**); each option shows its vCPU count, memory and — when it needs one — hugepage size, and common ones are marked **Provided by product**. An instance type with a hugepage size needs nodes that provide those hugepages. |
   | **Follow the image** | Offered when the selected image instance declares a default instance type (or preference). Instead of choosing an object, the virtual machine takes the one the image declares: it is read and written into the virtual machine when the virtual machine is created, and creation is refused if the image declares none. |
   | **Model** | Shown for the machine model path. Select a recommended usage scenario, or customize the CPU and memory; requests and limits are set to the same values. |
   | **Preference** | Optional on both paths, and recommended. Lists the preferences of the current namespace and of the cluster; the preference fills the device, firmware and clock settings the virtual machine leaves unset. |
   | **Physical GPU (Alpha)** | Select the model of the physical GPU; only one physical GPU can be allocated to each virtual machine. <br /><br />**Note**: Physical GPU passthrough for the virtual machine refers to the direct allocation of the actual Graphics Processing Unit (GPU) to the virtual machine in a virtualization environment, enabling it to directly access and utilize the physical GPU to achieve graphical performance equivalent to running directly on a physical machine, avoiding performance bottlenecks caused by virtual graphics adapters and enhancing overall performance. |

### Related Operations

You can click the ⋮ icon on the right side of the list page or the **Actions** in the upper right corner of the details page to update or delete the virtual machine as needed. For other related operations like resetting passwords or updating keys, please refer to [Manage Virtual Machines](./virtual_management.mdx).

**Note**:

- Updates can only be performed when the virtual machine is in **Abnormal**, **Unknown**, or **Stopped** status.

- Updates do not support displaying disks that were separately attached or created after the virtual machine was created.

- By default, **Start Immediately** is disabled during updates; you can enable it as needed.

## Using the API \{#using-the-api}

A virtual machine is a `VirtualMachine` (`kubevirt.io/v1`).

### Recommended: Reference an Instance Type and a Preference

The virtual machine below boots from a bootable volume (a `DataSource`), takes its size from the cluster instance type `u1.medium` and its device settings from the cluster preference `centos.stream9`, attaches a pod network, and injects an SSH key through cloud-init:

```yaml
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: web-01
  namespace: demo
spec:
  running: false           # set true to start on creation
  instancetype:            # the size: guest CPU and memory
    kind: VirtualMachineClusterInstancetype
    name: u1.medium
  preference:              # optional: preferred devices, firmware and clock
    kind: VirtualMachineClusterPreference
    name: centos.stream9
  dataVolumeTemplates:
    - metadata:
        name: web-01-rootfs
      spec:
        sourceRef:          # clone an existing bootable volume (DataSource)
          kind: DataSource
          name: centos-stream9
          namespace: kube-public
        storage:
          resources:
            requests:
              storage: 20Gi
          storageClassName: rbd-1
          volumeMode: Block
          accessModes:
            - ReadWriteMany
  template:
    metadata:
      labels:
        kubevirt.io/vm: web-01
    spec:
      domain:
        # No resources, cpu or memory.guest here: they come from the instance type.
        devices:
          disks:
            - name: rootfs
              disk: {}      # the preference chooses the disk bus
            - name: cloudinit
              disk: {}
          interfaces:
            - name: default
              masquerade: {}
      networks:
        - name: default
          pod: {}
      volumes:
        - name: rootfs
          dataVolume:
            name: web-01-rootfs
        - name: cloudinit
          cloudInitNoCloud:
            userData: |
              #cloud-config
              ssh_authorized_keys:
                - ssh-ed25519 AAAAC3...example user@host
```

```bash
kubectl apply -f vm.yaml
# Start it (ACP virtual machines use the spec.running field):
kubectl patch vm web-01 -n demo --type merge -p '{"spec":{"running":true}}'
```

- To reference a namespaced object, set `kind` to `VirtualMachineInstancetype` or `VirtualMachinePreference`; the object must be in the namespace of the virtual machine. A reference without `kind` means the cluster-scoped kind.
- A virtual machine that references an instance type must not set `spec.template.spec.domain.resources` CPU or memory, `domain.cpu.sockets` / `cores` / `threads`, `domain.memory.guest`, or any other setting the instance type sets; such a virtual machine is rejected.
- The preference only fills settings the virtual machine leaves unset: a disk with an explicit `bus`, for example, keeps its bus.

### Follow the Image

When the bootable volume declares a default instance type and preference (see [Bootable Volumes](../bootable_volume.mdx#default-instance-type-and-preference)), the virtual machine can take them from the volume instead of naming the objects. This is what **Follow the image** writes:

```yaml
spec:
  instancetype:
    inferFromVolume: rootfs            # the boot volume
    inferFromVolumeFailurePolicy: Reject
  preference:
    inferFromVolume: rootfs
    inferFromVolumeFailurePolicy: Reject
```

The platform reads the default from the volume once, when the virtual machine is created, and stores the object it names in the virtual machine — `spec.instancetype.name` and `spec.preference.name` replace the `inferFromVolume` fields. Changing the labels of the volume later does not change existing virtual machines. With the policy `Reject`, creation is refused if the volume declares no default; with `Ignore`, the virtual machine is created without that instance type or preference.

### Alternative: Set the Size in the Virtual Machine (Machine Model)

Without an instance type, the size is written into the template. ACP uses a resource-limit model, so `requests` and `limits` carry the same values. A preference can still be referenced:

```yaml
spec:
  preference:
    kind: VirtualMachineClusterPreference
    name: centos.stream9
  template:
    spec:
      domain:
        cpu:
          cores: 1
        resources:          # requests == limits
          requests:
            memory: 2Gi
          limits:
            memory: 2Gi
```

The boot disk is provisioned by the `dataVolumeTemplates` entry, which clones the referenced bootable volume. To change the size of a virtual machine later, or to move a virtual machine from a machine model to an instance type, see [Managing Virtual Machines](./virtual_management.mdx).
