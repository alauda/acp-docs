# KubeVirt Node Maintenance

Use this procedure for **planned maintenance of one worker node** (for
example, an OS update, kernel update, or hardware replacement). The goal is to
keep running VMs available by moving them with KubeVirt live migration before
the node is taken out of service.

Live migration keeps the guest running but can still cause a short pause and
uses guest memory and node-to-node network bandwidth. Schedule the change in a
low-traffic window and keep normal VM and application monitoring enabled.

This procedure is intentionally conservative. It migrates VMs one at a time,
checks the result, and only then drains the remaining Pods. It does not cover a
node that has already failed; see [Recover a VM after an abnormal node
failure](../trouble_shooting/vm_migration.mdx) for the fencing requirements.

:::warning
Do not start the node work until every VMI and `virt-launcher` Pod has left the
node. Do not use `--force`, `--disable-eviction`, `--grace-period=0`, or
`kubectl delete pod --force` as a planned-maintenance shortcut. Those options
can bypass the KubeVirt eviction path and interrupt the guest.
:::

## Before the maintenance window

### Confirm capacity and scheduling

Maintain at least two `Ready` and schedulable worker nodes, including a
possible destination for every VM on the node being serviced. Check CPU,
memory, device requests, taints, labels, affinity, and topology constraints on
the other workers. Do not maintain two workers at the same time unless the
cluster capacity plan explicitly allows it.

```bash
kubectl get nodes -o wide
kubectl describe node <destination-node>
```

Record the current placement before changing anything. The `NODE` column is
the node that must be emptied:

```bash
kubectl get vmi -A -o wide
kubectl get pod -A -l kubevirt.io=virt-launcher -o wide
```

### Check each VM that will be moved

For every VMI on the maintenance node, confirm all of the following:

- The VM is intended to stay running. For VMs that must be recreated after an
  interruption, use `spec.runStrategy: Always`. If an existing VM uses the
  deprecated `spec.running: true` field, do not add `spec.runStrategy` during
  this maintenance; the two fields are mutually exclusive.
- The **effective** eviction strategy is `LiveMigrate`: use the VM template's
  `spec.template.spec.evictionStrategy` when it is set, otherwise use the HCO
  cluster default. A VM-level value overrides the HCO default.
- The VMI is `Running`, has `Ready=True`, and has `LiveMigratable=True`.
- PVCs are bound and the VM's storage, network, CPU model, host devices, and
  placement constraints allow migration. Shared `ReadWriteMany` storage is a
  common requirement, but the `LiveMigratable` condition is the authoritative
  preflight check for the installed KubeVirt version.
- No migration is already in progress for the VM.

  ```bash
  kubectl get vm <vm-name> -n <vm-namespace> -o jsonpath='runStrategy={.spec.runStrategy}{"\n"}evictionStrategy={.spec.template.spec.evictionStrategy}{"\n"}'
  kubectl get vmi <vmi-name> -n <vm-namespace> -o jsonpath='{.metadata.uid}{"\n"}{.status.phase}{"\n"}{.status.nodeName}{"\n"}{.status.conditions}{"\n"}'
  kubectl get vmi <vmi-name> -n <vm-namespace> -o jsonpath='{range .status.conditions[?(@.type=="LiveMigratable")]}LiveMigratable={.status} reason={.reason} message={.message}{"\n"}{end}'
  kubectl get pvc -n <vm-namespace>
  kubectl get virtualmachineinstancemigration -n <vm-namespace>
  ```

If a VM is not live-migratable, stop the maintenance. Fix its storage or
device configuration, move it in an approved downtime window, or postpone the
node work. Do not change the VM to `LiveMigrateIfPossible` just to make a drain
finish: when migration is unavailable, that strategy falls back to ordinary
eviction and can stop or restart the VM.

### Check the cluster default without changing it

The ACP 4.4 HCO v1 field is
`spec.virtualization.evictionStrategy`. A VM-level strategy takes precedence.
On a multi-worker cluster the usual default is `LiveMigrate`, but verify the
installed resource before relying on a default. Do not patch the cluster-wide
HCO setting as part of an individual node-maintenance window; a change there
affects every VMI and triggers reconciliation.

```bash
kubectl get hyperconverged kubevirt-hyperconverged -n kubevirt \
  -o jsonpath='{.spec.virtualization.evictionStrategy}{"\n"}'
kubectl explain hyperconverged.spec.virtualization.evictionStrategy
```

The HCO strategies have different operational consequences:

| Strategy | Effect during eviction | Use for low-impact maintenance |
| --- | --- | --- |
| `LiveMigrate` | Migrates a live-migratable VMI; blocks eviction for a non-migratable VMI. | Preferred. Resolve every blocked VM before continuing. |
| `LiveMigrateIfPossible` | Migrates when possible; otherwise behaves like ordinary eviction. | Only with an explicitly approved outage. |
| `None` | Does not request live migration. | Not suitable for a no-interruption window. |
| `External` | Blocks eviction and signals an external controller. | Only when that controller is installed and owned by the operator. |

## Move the VMs off the node

1. **Cordon the node.** This prevents new Pods from landing on it while the
   existing VMs are moved. Cordon does not stop the VMs.

   ```bash
   kubectl cordon <maintenance-node>
   ```

2. **Trigger one Kubernetes eviction at a time.** Evict the
   `virt-launcher` Pod through the Kubernetes Eviction API. KubeVirt then
   applies the VM's effective `LiveMigrate` strategy; deleting the Pod would
   bypass that path. Create an eviction object with the launcher Pod's name:

   ```yaml
   apiVersion: policy/v1
   kind: Eviction
   metadata:
     name: <virt-launcher-pod>
     namespace: <vm-namespace>
   ```

   ```bash
   kubectl create -f eviction.yaml
   ```

   For a single VM, the platform's Live Migration action or `virtctl` is also
   acceptable instead of creating the Eviction object. Choose one method for
   each VM; do not submit an eviction and a manual migration simultaneously:

   ```bash
   virtctl migrate <vm-name> -n <vm-namespace>
   ```

   If the eviction path is unavailable in a controlled troubleshooting
   scenario, create a `VirtualMachineInstanceMigration` for the running VMI.
   Use a unique name for each request:

   ```yaml
   apiVersion: kubevirt.io/v1
   kind: VirtualMachineInstanceMigration
   metadata:
     name: <vmi-name>-maintenance
     namespace: <vm-namespace>
   spec:
     vmiName: <vmi-name>
   ```

   ```bash
   kubectl apply -f migration.yaml
   ```

3. **Watch the migration before starting another one.** During migration it
   is normal to see more than one launcher temporarily. The migration is
   complete only when the old launcher is gone.

   ```bash
   kubectl get virtualmachineinstancemigration -n <vm-namespace> -w
   kubectl get virtualmachineinstancemigration -n <vm-namespace> \
     -o custom-columns='NAME:.metadata.name,VMI:.spec.vmiName,PHASE:.status.phase'
   kubectl get vmi <vmi-name> -n <vm-namespace> -o wide -w
   kubectl get pod -n <vm-namespace> -l kubevirt.io=virt-launcher -o wide -w
   ```

   Accept the migration only when all of these checks pass:

   - The VMIM phase is `Succeeded`.
   - `status.migrationState.sourceNode` is the maintenance node and
     `status.migrationState.targetNode` is a different worker.
   - The VMI keeps the same UID, is `Running`, and remains `Ready`.
   - The VM remains `Running`/ready and exactly one active launcher remains.

   Capture the VMIM status as soon as it reaches `Succeeded`; completed VMIM
   objects can be garbage-collected by KubeVirt after the migration.

     ```bash
     kubectl get virtualmachineinstancemigration <migration-name> \
       -n <vm-namespace> -o jsonpath='phase={.status.phase}{"\n"}source={.status.migrationState.sourceNode}{"\n"}target={.status.migrationState.targetNode}{"\n"}'
     kubectl get vm <vm-name> -n <vm-namespace> \
       -o jsonpath='{.status.printableStatus}{" ready="}{.status.ready}{"\n"}'
     ```

4. Repeat the migration and verification for every VMI on the maintenance
   node. Keep the original VMI UID and source/target nodes in the change
   record. Respect the cluster's migration limits; a large batch increases
   memory and network pressure and makes a failure harder to isolate.

## Drain the remaining Pods

After all VMIs have moved, confirm that no launcher remains on the node:

```bash
kubectl get vmi -A -o wide
kubectl get pod -A -l kubevirt.io=virt-launcher \
  --field-selector spec.nodeName=<maintenance-node> -o wide
```

Now drain the node for ordinary workloads. The command uses the Kubernetes
Eviction API, so PodDisruptionBudgets and KubeVirt eviction handling remain in
effect:

```bash
kubectl drain <maintenance-node> \
  --ignore-daemonsets \
  --delete-emptydir-data \
  --timeout=30m
```

If you choose to let `drain` trigger KubeVirt migrations instead of moving the
VMs explicitly, run it only after cordoning and keep the same watches and
success criteria above. A drain that waits on a non-migratable VMI, a PDB, or
another eviction error is a stop condition. Do not add a force flag to make it
return success.

When the command reports that the node is drained, perform the OS or hardware
maintenance. If the drain cannot complete, leave the node cordoned and resolve
the reported workload; do not start the node work while Pods or VMIs remain.

## Finish and verify

After the node is healthy and `Ready`, make it schedulable again:

```bash
kubectl get node <maintenance-node>
kubectl uncordon <maintenance-node>
kubectl get node <maintenance-node>
```

Recheck every VM that was moved. Confirm that it is running, its VMI is ready,
there is one active launcher, and the VM is on the intended node or is
otherwise schedulable according to its affinity rules. Also check application
health and any alerts before closing the change.

## If a migration fails

Stop the maintenance and preserve the diagnostic objects before deleting or
retrying anything:

```bash
kubectl describe virtualmachineinstancemigration <migration-name> -n <vm-namespace>
kubectl describe vmi <vmi-name> -n <vm-namespace>
kubectl get events -n <vm-namespace> --sort-by=.lastTimestamp
kubectl get vmi <vmi-name> -n <vm-namespace> -o yaml
```

Check the `LiveMigratable` condition message, destination capacity and
constraints, PVC access modes, network annotations, and migration limits. An
in-progress migration can be cancelled by deleting its VMIM object, as
described in [Virtual Machine Live Migration](./vm_precopy.mdx); do this only
after confirming that cancellation is safe. Never force-delete the launcher
Pod while the source node may still be running the guest.

If the maintenance is being abandoned, uncordon the node only after its health
has been checked and the VM placement is stable.

## Unexpected node failure

The planned procedure must not be used for a powered-off or partitioned node.
KubeVirt cannot know whether the old guest is still running. First use the
approved out-of-band fencing or node-remediation procedure to isolate the
node. Only after fencing is confirmed should an administrator handle stale
VMI, launcher, or volume-attachment objects and verify that one replacement
VMI starts on a healthy node. The failure runbook must define the fencing and
volume-detach mechanism for the installed storage driver.

## Evidence checklist

Keep these values in the maintenance record:

- source node, destination node, VM/VMI name, and original VMI UID;
- VM `runStrategy` and effective `evictionStrategy`;
- `LiveMigratable=True` and `Ready=True` before and after migration;
- VMIM name, phase `Succeeded`, and migration source/target nodes;
- VM/guest health and exactly one active `virt-launcher` after migration;
- node drain and post-maintenance `Ready`/schedulable status.
