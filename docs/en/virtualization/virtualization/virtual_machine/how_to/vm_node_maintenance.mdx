# KubeVirt Node Maintenance

Use this runbook for **planned maintenance of one healthy worker node**. It
cordons the node, asks Kubernetes to drain it, and lets KubeVirt evacuate
live-migratable VMs before the node is taken out of service. The VM remains
running during a successful live migration, although a short guest pause and
additional CPU, memory, and network usage are possible.

This runbook is not a recovery procedure for a failed or partitioned node. In
that case, fence the node first and follow [VM Migration and Recovery from a
Node Failure](../trouble_shooting/vm_migration.mdx). Do not recreate a VM while
the old node might still be running it.

:::warning
Never use `--force`, `--disable-eviction`, `--grace-period=0`, or force-delete
a `virt-launcher` Pod to make a planned drain finish. These options can bypass
KubeVirt's evacuation path and interrupt the guest.
:::

## How KubeVirt handles a drain

`virt-launcher` is a Kubernetes Pod, but the guest is a KubeVirt VMI. When the
Kubernetes Eviction API receives an eviction request for a launcher, the
KubeVirt admission webhook marks a migratable VMI for evacuation. The first
request commonly returns HTTP 429 because migration has been started; the
launcher is protected by a PodDisruptionBudget while migration runs. A later
retry is allowed after the migration completes. `kubectl drain` performs these
retries automatically.

The effective eviction strategy is read from the VMI first and otherwise from
the KubeVirt cluster configuration:

| Strategy | Drain behavior | Use for low-impact maintenance |
| --- | --- | --- |
| `LiveMigrate` | Migrates a live-migratable VMI. A non-migratable VMI blocks the drain. | **Recommended**. Fix or separately handle every blocked VMI. |
| `LiveMigrateIfPossible` | Migrates when possible; otherwise evicts and follows the VM run strategy. | Use only when an outage is explicitly approved. |
| `None` | Does not request migration. | Not suitable for keeping the VM running. |
| `External` | Blocks eviction for an external controller. | Use only with that controller and its runbook. |

## Before the maintenance window

Do this validation before scheduling the change. A drain is not a test of VM
compatibility: if a VM cannot migrate, `LiveMigrate` deliberately leaves the
node undrained.

### 1. Confirm worker capacity

Keep at least two `Ready` and schedulable worker nodes, and confirm that a
destination can satisfy each VM's CPU, memory, device, affinity, taint,
toleration, topology, and network requirements.

```bash
kubectl get nodes -o wide
kubectl describe node <possible-destination>
kubectl get vmi -A -o wide
kubectl get pod -A -l kubevirt.io=virt-launcher -o wide
```

Do not start maintenance on two workers at once unless the capacity plan has
been approved.

### 2. Confirm the eviction strategy

For each VMI on the node, inspect the explicit VMI/VM value. If it is empty,
inspect the installed KubeVirt configuration; do not assume a value from the
ACP release number. In ACP 4.4's served `v1beta1` schema the HCO field is
`spec.evictionStrategy`; older or alternate served schemas can place it under
`spec.virtualization.evictionStrategy`. Use API discovery and `kubectl explain`
to confirm both the served version and the field path before reading or changing it.

```bash
kubectl get vmi <vmi-name> -n <vm-namespace> \
  -o jsonpath='evictionStrategy={.spec.evictionStrategy}{" node="}{.status.nodeName}{"\n"}'
kubectl get vm <vm-name> -n <vm-namespace> \
  -o jsonpath='runStrategy={.spec.runStrategy}{" templateEvictionStrategy="}{.spec.template.spec.evictionStrategy}{"\n"}'
kubectl get kubevirt -n kubevirt \
  -o jsonpath='{range .items[*]}{.metadata.name}{" evictionStrategy="}{.spec.configuration.evictionStrategy}{"\n"}{end}'
kubectl get crd hyperconvergeds.hco.kubevirt.io \
  -o jsonpath='{range .spec.versions[*]}{.name}{" served="}{.served}{" storage="}{.storage}{"\n"}{end}'
HCO_VERSION="$(
  kubectl get crd hyperconvergeds.hco.kubevirt.io \
    -o jsonpath='{range .spec.versions[?(@.served==true)]}{.name}{"\t"}{.storage}{"\n"}{end}' \
    | awk '$2 == "true" { print $1; exit }'
)"
test -n "$HCO_VERSION" || { echo "no served HCO CRD version found" >&2; exit 1; }
HCO_PATH=hyperconverged.spec.evictionStrategy
if ! kubectl explain "$HCO_PATH" --api-version="hco.kubevirt.io/${HCO_VERSION}" >/dev/null 2>&1; then
  HCO_PATH=hyperconverged.spec.virtualization.evictionStrategy
fi
kubectl explain "$HCO_PATH" \
  --api-version="hco.kubevirt.io/${HCO_VERSION}"
```

Do not hard-code `hco.kubevirt.io/v1` or a single field path in this command.
The ACP 4.4 CRD is served as `hco.kubevirt.io/v1beta1`; a later release can
serve another version or move the field. The command selects the served
storage version, probes the current root path, and falls back to the nested
path before calling `kubectl explain`.

For a VM that must stay running, set `LiveMigrate` in the VM template in its
source of truth (GitOps manifest, form, or API) before the window. Set
`runStrategy: Always` when the VM must be recreated and started after an
interruption. Do not add `runStrategy` to a VM that still has the deprecated
`spec.running` field; update the source manifest and use only one of them.

The relevant part of a VM manifest is:

```yaml
spec:
  runStrategy: Always
  template:
    spec:
      evictionStrategy: LiveMigrate
```

Keep the VM's existing domain, networks, volumes, and placement settings when
applying this change. A direct patch is acceptable only when the VM is not
managed by GitOps or another controller; otherwise update that source of truth.

Changing the VM template does not change an already-running VMI. Recreate or
restart it during an approved window if its effective VMI strategy is still
`None` or `LiveMigrateIfPossible`. Never patch a running VMI to force this
change.

### 3. Confirm every VMI is migratable

For every VMI currently on the maintenance node, require `Running`,
`Ready=True`, and `LiveMigratable=True`. Check that PVCs are bound and that
storage, networks, devices, CPU model, and placement rules allow a destination.
Shared storage such as RWX is common, but the `LiveMigratable` condition is the
authoritative check for the installed KubeVirt version.

```bash
kubectl get vmi <vmi-name> -n <vm-namespace> -o wide
kubectl get vmi <vmi-name> -n <vm-namespace> \
  -o jsonpath='{range .status.conditions[?(@.type=="LiveMigratable")]}LiveMigratable={.status}{" reason="}{.reason}{" message="}{.message}{"\n"}{end}'
kubectl get pvc -n <vm-namespace>
kubectl get vmim -n <vm-namespace>
```

If any VM is not migratable, stop. Fix it, move it in an approved downtime
window, or postpone the node work. Do not change it to
`LiveMigrateIfPossible` merely to bypass the drain.

## Drain the node

1. Record the node name, each VMI UID, and current VMI node before changing the
   node.

2. Cordon the healthy node. Cordon prevents new workloads from being placed on
   it; it does not stop existing VMs.

   ```bash
   kubectl cordon <maintenance-node>
   ```

3. Drain with the Kubernetes Eviction API and wait for KubeVirt to migrate the
   VMIs. Do not manually delete launcher Pods or create a one-off eviction and
   treat its first 429 response as failure.

   ```bash
   kubectl drain <maintenance-node> \
     --ignore-daemonsets \
     --delete-emptydir-data \
     --timeout=30m
   ```

4. In separate terminals, watch the migration and the drain:

   ```bash
   kubectl get vmim -A -w
   kubectl get vmi -A -o wide -w
   kubectl get pod -A -l kubevirt.io=virt-launcher -o wide -w
   kubectl get events -A --sort-by=.lastTimestamp
   ```

   For each VM, accept the move only when a matching VMIM is `Succeeded`, its
   `status.migrationState.sourceNode` is the maintenance node and
   `targetNode` is another worker, the VMI UID is unchanged, the VMI remains
   `Running` and `Ready`, and only one active launcher remains. A changed Pod
   name, a 429 response, or a descheduler/eviction log alone is not migration
   evidence.

5. Start OS or hardware work only after `kubectl drain` reports success and no
   VMI or launcher Pod is assigned to the node:

   ```bash
   kubectl get vmi -A -o wide
   kubectl get pod -A -l kubevirt.io=virt-launcher \
     --field-selector spec.nodeName=<maintenance-node> -o wide
   ```

If the drain times out or reports a blocked VMI, leave the node cordoned,
preserve the VMIM/VMI events and conditions, and resolve the stated capacity,
storage, placement, PDB, or migration-limit problem. Do not force the drain.

## Finish the maintenance

After the node is healthy and `Ready`, make it schedulable again:

```bash
kubectl get node <maintenance-node>
kubectl uncordon <maintenance-node>
kubectl get node <maintenance-node>
```

Recheck the moved VMs, their application health, and the absence of duplicate
active launchers before closing the change.

## Unexpected node failure

This planned procedure cannot safely recover a powered-off or partitioned
node. First use the approved out-of-band fencing or node-remediation workflow,
then handle stale VMI, launcher, and volume-attachment resources according to
that workflow. KubeVirt must never be allowed to run two copies of a guest.
