# Deploy with the Operator

This page describes the complete operator-based deployment path: install the
NetObserv Operator, prepare ClickHouse, create a `FlowCollector` (FLC), and
open the NetObserv console plugin.

## Prerequisites

Before you begin, make sure that you have:

- Administrator access to the target cluster.
- The NetObserv Operator package for the ACP release. Install it in the fixed
  `netobserv-operator` namespace through **Administrator** > **Marketplace** >
  **OperatorHub**.
- A ClickHouse server reachable from the cluster. You can use an existing
  server or deploy one with the ClickHouse Operator as described below.
- A ClickHouse database, username, and password that can be stored in a
  Kubernetes Secret.
- Linux nodes with kernel version 5.14 or later. The eBPF agent must be able to
  use `perf_event_open`; on Ubuntu, check `kernel.perf_event_paranoid` before
  deployment.

On Ubuntu, check the setting with:

```bash
sysctl kernel.perf_event_paranoid
```

If the value is greater than `3`, set it to `3` and persist the setting in
`/etc/sysctl.conf`:

```bash
sysctl -w kernel.perf_event_paranoid=3
echo 'kernel.perf_event_paranoid=3' >> /etc/sysctl.conf
```

The Operator is responsible for the long-running collection pipeline. For a
short, on-demand capture, use [Tasks for NetObserv](../how_to/tasks_for_netobserv.mdx)
instead.

To enable continuous network flow collection, you need:

1. A reachable ClickHouse server for storing flow logs
2. The NetObserv Operator
3. A FlowCollector instance

The ClickHouse backend can be prepared in either of these ways:

- Use an existing ClickHouse server and provide its connection information in the FlowCollector configuration
- Deploy a new ClickHouse instance in the cluster by using the ClickHouse Operator

## Choose a ClickHouse Deployment Option

Choose one of the following approaches before you create the FlowCollector instance:

- Existing ClickHouse server: Use this option if you already have a ClickHouse deployment that FlowCollector can access.
- New in-cluster ClickHouse instance: Use this option if you want to deploy ClickHouse in the cluster with the ClickHouse Operator.

If you use an existing ClickHouse server, prepare these values in advance:

- ClickHouse service address in `host:port` format
- Database name for flow logs
- Username and password for ClickHouse authentication
- The namespace that will be used in `.spec.namespace` of the FlowCollector

## Optional: Deploy ClickHouse with the ClickHouse Operator

If you already have a ClickHouse server for NetObserv, skip this section and go to [Install the NetObserv Operator](#install-the-netobserv-operator).

### Install the ClickHouse Operator

1. Navigate to __Administrator__ > __Marketplace__ > __OperatorHub__.

2. Search for "ClickHouse" and locate the ClickHouse Operator provided by <Term name="company"/>.

3. If the ClickHouse Operator status is _Absent_, upload the ClickHouse Operator package that you downloaded from the __<Term name="company"/> Customer Portal__.

4. Click on the ClickHouse Operator to open the details page.

5. On the operator details page, click __Install__.

6. Fill in the configuration parameters as needed.

7. Click __Install__ to start the installation.

8. Confirm the installation by clicking __Confirm__ in the pop-up dialog.

9. Wait for the installation to complete.

:::note
If the ClickHouse Operator provided by <Term name="company"/> is already installed, skip this section and go directly to creating a ClickHouse cluster for NetObserv.
:::

### Create a ClickHouseInstallation Instance

1. In the ClickHouse Operator details page, navigate to the __All Instances__ page and click __Create__.

2. In the pop-up dialog, click __Create__ in the __ClickHouseInstallation__ section.

3. In the __Create ClickHouseInstallation__ page, click __YAML__ on the top right corner to switch to YAML editing mode.

4. Edit the YAML file as needed and click __Create__ to create the ClickHouseInstallation instance.

Example ClickHouseInstallation YAML:

```yaml
apiVersion: clickhouse.altinity.com/v1
kind: ClickHouseInstallation
metadata:
  name: netobserv
  namespace: cpaas-system
spec:
  configuration:
    files:
      disable-trace-log: |
        <clickhouse>
          <trace_log remove="remove"/>
          <query_thread_log remove="remove"/>
          <query_log remove="remove"/>
          <text_log remove="remove"/>
          <metric_log remove="remove"/>
          <asynchronous_metric_log remove="remove"/>
          <part_log remove="remove"/>
        </clickhouse>
    clusters:
      - layout:
          replicasCount: 1
          shardsCount: 1
        name: replicated
    users:
      clickhouse_root/networks/ip:
        - 127.0.0.1
        - 0.0.0.0/0
        - ::/0
      clickhouse_root/password_sha256_hex: <SHA256_HEX_PASSWORD>
  defaults:
    templates:
      dataVolumeClaimTemplate: default
      logVolumeClaimTemplate: log-volume-template
      podTemplate: clickhouse:25.8
  templates:
    podTemplates:
      - name: clickhouse:25.8
        podDistribution:
          - type: ShardAntiAffinity
        spec:
          containers:
            - command:
                - clickhouse-server
                - --config-file=/etc/clickhouse-server/config.xml
              env:
                - name: CLICKHOUSE_DO_NOT_CHOWN
                  value: "1"
              image: <registry>/middleware/clickhouse-server:<version>
              name: clickhouse-pod
              resources:
                limits:
                  cpu: "2"
                  memory: 4Gi
                requests:
                  cpu: "1"
                  memory: 2Gi
              securityContext:
                readOnlyRootFilesystem: true
          securityContext:
            fsGroup: 101
            runAsGroup: 101
            runAsNonRoot: true
            runAsUser: 101
    volumeClaimTemplates:
      - name: default
        spec:
          storageClassName: <storage-class>
          accessModes:
            - ReadWriteOnce
          resources:
            requests:
              storage: 80Gi
      - name: log-volume-template
        spec:
          storageClassName: <storage-class>
          accessModes:
            - ReadWriteOnce
          resources:
            requests:
              storage: 15Gi
```

Replace the placeholders before applying the manifest: `<registry>` with the
registry that serves the ClickHouse server image in your environment, and
`<storage-class>` with a StorageClass that provides `ReadWriteOnce` volumes in
the target cluster.

After the ClickHouse instance is ready, get the service endpoint by inspecting field `.status.endpoint` of the ClickHouseInstallation instance.
You can also run the following command to get the endpoint:

```bash
kubectl -n cpaas-system get chi netobserv -o jsonpath="{.status.endpoint}"
```

`cpaas-system` and `netobserv` in the command must match the namespace and name of the ClickHouseInstallation instance respectively.
If you use a different namespace or name, replace `cpaas-system` and `netobserv` in the command accordingly.

Record the ClickHouse endpoint address and credentials for later use.
You will need this information when you create the FlowCollector instance.

## Create the ClickHouse Authentication Secret

Before you create the FlowCollector instance, create a Kubernetes secret for ClickHouse authentication.

This secret is referenced by `.spec.clickhouse.authSecret.name` in the FlowCollector configuration.

1. Create a local file named _ck-auth.env_ with the following content:

    ```ini
    username=<USERNAME>
    password=<PASSWORD>
    ```

2. Create the Kubernetes secret:

    ```bash
    # Create namespace if it does not exist
    test ! -n "$(kubectl get ns netobserv --ignore-not-found -o name)" && kubectl create ns netobserv
    # Create the secret from the environment file
    kubectl -n netobserv create secret generic ck-auth --from-env-file=./ck-auth.env
    ```

In this command, `netobserv` must match the value of `.spec.namespace` in the FlowCollector configuration.

If you use a different namespace in the FlowCollector configuration, replace `netobserv` in the command accordingly.

## Deploy a FlowCollector (FLC) instance

Before creating the FlowCollector instance, confirm that:

- The ClickHouse server is reachable from the cluster
- The `ck-auth` secret exists in the namespace specified by `.spec.namespace`
- The ClickHouse address, database, and credentials are correct

Then create the FlowCollector instance:

1. Navigate to the __All Instances__ page and click __Create__.

2. In the pop-up dialog, click __Create__ in the __FlowCollector__ section.

3. In the __Create FlowCollector__ page, click __YAML__ on the top right corner to switch to YAML editing mode.

4. Edit the YAML file as needed and click __Create__ to create the FlowCollector instance.

Example FlowCollector YAML:

```yaml
apiVersion: flows.netobserv.io/v1beta2
kind: FlowCollector
metadata:
  name: cluster
spec:
  agent:
    ebpf:
      features: # [!code callout]
        - DNSTracking
        - FlowRTT
        - PacketTranslation
        - TLSTracking
      metrics:
        enable: false
      sampling: 50 # [!code callout]
    type: eBPF
  clickhouse:
    addresses: # [!code callout]
      - clickhouse-netobserv.cpaas-system.svc.cluster.local:9000
    authSecret:
      name: ck-auth # [!code callout]
    database: netobserv # [!code callout]
    enable: true
    protocol: native
    readTimeout: 30s
    retention: 24h # [!code callout]
    writeBatchSize: 128
    writeBatchWait: 1s
    writeTimeout: 10s
  consolePlugin:
    enable: true
    replicas: 1
  deploymentModel: Service
  namespace: netobserv # [!code callout]
  processor:
    consumerReplicas: 1 # [!code callout]
    logTypes: Flows
    service:
      tlsType: Disabled
```

<Callouts>

1. Enabled features of the eBPF agent.
2. Sampling interval of the eBPF probe. A value of 100 means that 1 out of every 100 packets is sampled. A value of 0 or 1 means that all packets are sampled.
3. ClickHouse server addresses. Use the `host:port` format. These addresses can point to a ClickHouse instance created in the cluster or to an existing external ClickHouse server.
4. ClickHouse authentication secret. The secret __MUST__ contain two keys: `username` and `password`. The secret must be created in the same namespace specified by `.spec.namespace`.
5. Database name in ClickHouse for storing flow logs. If the database does not exist, it is created automatically.
6. Data retention period in ClickHouse. Use a number followed by a time unit, for example `24h`. The flow logs pipeline applies this value with `ALTER TABLE ... MODIFY TTL` every time it starts, so a change takes effect after the pipeline restarts and covers existing and new partitions.
7. Namespace where the eBPF agents and the flow logs pipeline are deployed.
8. Number of replicas for the flow logs pipeline.

</Callouts>

If you are using an existing ClickHouse server, make sure that the FlowCollector can reach the server address and that the referenced secret contains valid credentials.

After the FlowCollector instance is created, the eBPF agents and the flow logs pipeline are deployed to the namespace specified by `.spec.namespace`.

## Verify flow collection

A `Ready` FlowCollector only proves that the operator reconciled the resources.
It does not prove that flows reach ClickHouse. On a new cluster, check the data
path before you hand the environment over.

### Check the workloads and the table

```bash
NS=netobserv   # the value of .spec.namespace
kubectl -n $NS get pods
kubectl get flowcollector cluster \
  -o jsonpath='{range .status.conditions[*]}{.type}={.status} {.message}{"\n"}{end}'
kubectl -n kube-public get configmap global-info -o jsonpath='{.data.clusterName}{"\n"}'
```

The eBPF agent DaemonSet has one Ready Pod per node, and the flow logs pipeline
Pod is Ready. In the FlowCollector conditions, a `Waiting*` condition reports
`False` when the component is healthy; `True` or `Unknown` means the operator
is still waiting on, or deliberately skipped, that component.

Flows are written to `flow_logs_<clusterName>` in the ClickHouse database. The
table name is derived from `kube-public/global-info`, key `data.clusterName`,
after lowercasing it, replacing every character outside `[a-z0-9_]` with `_`,
collapsing repeated `_`, and trimming leading and trailing `_`. For example, a
cluster named `Biz-Cluster-1` writes to `flow_logs_biz_cluster_1`. Setting
`.spec.clickhouse.table` overrides the derived name; you can also read the name
the pipeline actually uses:

```bash
kubectl -n $NS get configmap flowlogs-pipeline-config \
  -o jsonpath='{.data.config\.json}' \
  | jq -r '.parameters[] | select(.name == "clickhouse") | .write.clickhouse.table'
```

Query the table to confirm rows are arriving and are recent:

```bash
CH_POD=$(kubectl -n cpaas-system get pod \
  -l clickhouse.altinity.com/chi=netobserv \
  -o jsonpath='{.items[0].metadata.name}')
kubectl -n cpaas-system exec "$CH_POD" -- clickhouse client \
  --user <user> --password <password> --database netobserv \
  --query 'SELECT count(), max(Timestamp) FROM flow_logs_<clusterName>'
```

Replace the label value, namespace, database, and table with the values of your
deployment when the ClickHouse instance is not the one from this page. If the
instance runs with a log sidecar container, add `-c <clickhouse-container>`.

### Install the monitoring dashboards

The package ships two dashboard manifests inside the controller-manager image,
under `/opt/netobserv/docs/ops/manifests/`. The operator does not create them, so
apply them once per cluster:

```bash
POD=$(kubectl -n netobserv-operator get pod -l app=netobserv-operator \
  -o jsonpath='{.items[0].metadata.name}')
for dashboard in netobserv-dashboard.yaml clickhouse-dashboard.yaml; do
  kubectl -n netobserv-operator cp "$POD:/opt/netobserv/docs/ops/manifests/$dashboard" "./$dashboard"
done
kubectl apply -f ./netobserv-dashboard.yaml -f ./clickhouse-dashboard.yaml
```

Both manifests are ACP `MonitorDashboard` resources created in `cpaas-system`
and tagged `netobserv`. They require the ACP monitoring components to be
installed, because the `MonitorDashboard` API comes from that package; applying
the manifests also needs permission to create resources in `cpaas-system` and
`pods/exec` in the operator namespace.

In the ACP console go to __Operations Center__ > __Monitoring__ > __Monitoring
Dashboards__ and filter by the `netobserv` tag. ACP 4.4 and later also provide
the Perses dashboard capability; the manifests above use the `MonitorDashboard`
(legacy) API, which stays available alongside Perses.

### Panels that need no extra configuration

`Agent Available`, `FLP Available`, and `Console Available` depend only on
kube-state-metrics. They are availability ratios rendered as percentages, so a
healthy deployment reads 100%, not the raw Pod count.

__NetObserv Agent and FLP__ proves that the pipeline ingests and writes:

| Panel | What to check |
| --- | --- |
| `FLP Ingest Rate` | Non-zero while there is traffic on the captured interfaces |
| `Flow Rate by FLP` | Non-zero, and its ClickHouse batch series follows the ingest rate |
| `FLP Queue Size` | Fluctuates but does not grow monotonically |
| `Container Restarts` | No repeated restarts of the pipeline container |

__ClickHouse Operations and Capacity__ proves that storage accepts the data:

| Panel | What to check |
| --- | --- |
| `ClickHouse Write Rate` | Non-zero and comparable with `FLP Ingest Rate` |
| `ClickHouse Write Errors` | Flat at 0 for all three series: retried, dropped, and uncertain |
| `ClickHouse Batch Send P95` | Stable; a growing trend points to ClickHouse pressure |
| `Selected Tables Rows` / `Selected Tables Size` | Growing, which confirms inserts land in the table |
| `ClickHouse Disk Used` | Within the capacity you provisioned for the retention period |

### Panels that need eBPF agent metrics

`End-to-End Flow Rate` plots the agent output, the pipeline ingest, and the
ClickHouse batch writes on one chart, so its agent series stays empty until agent
metrics are enabled.

The agent exposes its own Prometheus metrics only when
`spec.agent.ebpf.metrics.enable` is `true`. The FlowCollector example on this
page sets it to `false` to keep the footprint small, so these panels stay empty
until you enable it:

| Panel | What to check |
| --- | --- |
| `Agent Flow Rate` | Non-zero and in the same order of magnitude as `FLP Ingest Rate` |
| `Flow Rate by Agent` | Every node contributes; one silent node points to scheduling or eBPF problems |
| `Agent Dropped Flows` | Flat at 0. A rising curve means the pipeline cannot keep up |
| `Agent Sampling Interval` | Matches `spec.agent.ebpf.sampling` |

### ClickHouse dashboard prerequisites

The `chi_*` panels of __ClickHouse Operations and Capacity__ read the metrics
exported by the ClickHouse Operator, not by the ClickHouse server. They need a
ServiceMonitor that selects the operator's metrics port. Create it in the
namespace where the ClickHouse Operator runs, and set `namespaceSelector` to the
same namespace:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: netobserv-clickhouse
  namespace: <clickhouse-operator-namespace>
  labels:
    app.kubernetes.io/name: netobserv-clickhouse
    app.kubernetes.io/part-of: netobserv
spec:
  namespaceSelector:
    matchNames:
      - <clickhouse-operator-namespace>
  selector:
    matchLabels:
      app: clickhouse-operator
  endpoints:
    - port: clickhouse-operator-metrics
      honorLabels: true
      interval: 30s
      scrapeTimeout: 20s
```

This file is not part of the operator image; create it from the manifest above
when the monitoring stack does not already scrape the ClickHouse Operator.

The shipped dashboard panels select `namespace="cpaas-system"` and
`chi="netobserv"`. When ClickHouse runs elsewhere, or is an external server,
those panels stay empty; only the `netobserv_*` write panels remain meaningful.

### Cross-check in the console

Open **Observe** > **Network Traffic**, select a 5 to 15 minute range, and
confirm that bytes, packets, and flow counts are non-zero and comparable with
the dashboards above. The console shows traffic data from ClickHouse, not
component health, so use the two dashboards to diagnose a missing pipeline.

### When no data arrives

- `FLP Ingest Rate` is zero: the pipeline does not receive flows. Check whether
  the agent Pods are Ready, and whether `spec.agent.ebpf.sampling` is so coarse
  that little is captured.
- `FLP Ingest Rate` is non-zero but `ClickHouse Write Rate` stays zero: the
  pipeline cannot connect to ClickHouse. Check the `ck-auth` secret, the
  address in `spec.clickhouse.addresses`, and the pipeline logs.
- Rows exist but the console shows an empty page: check the time range first,
  then whether the console plugin reads the same database and table.
- A panel shows no series at all rather than a flat zero: the metrics are not
  scraped. Check that the monitoring stack scrapes the `netobserv` ServiceMonitors,
  and for the ClickHouse dashboard the ClickHouse Operator ServiceMonitor above.

## Use the NetObserv console

Set `spec.consolePlugin.enable` to `true` in the `FlowCollector` to deploy the
console plugin. The plugin reads flow records from ClickHouse through the
`netobserv-plugin` service. Wait until the following resources are ready before
opening the page:

```bash
kubectl get flowcollector cluster
kubectl -n netobserv get pods,svc
```

Replace `netobserv` with the value of `spec.namespace` when you use a different
namespace. In an ACP console session, select the target workload cluster and
open **Observe** > **Network Traffic**.

The console provides these views:

- **Overview**: aggregated bytes, packets, flow counts, and enabled feature
  metrics. Set a time range first, then use namespace, owner, node, or protocol
  filters to narrow the charts.
- **Flows**: raw flow records with source and destination IP, namespace,
  workload, node, port, protocol, bytes, packets, and other available fields.
  Open a row to inspect its details, add a field as a filter, configure visible
  columns, or export the filtered result as CSV.
- **Topology**: a graph of the selected traffic. Start with the **Namespace**
  scope to find the communicating namespaces, then switch to **Owner** or
  **Resource** to identify the workloads and services on the path.
Keep the same time range and filters when switching between views. A flow may
be absent when it falls outside the selected time range, was not sampled, or
the corresponding feature was not enabled in the `FlowCollector`. The UI shows
network metadata; it does not provide HTTP status codes or application error
stacks.

For a quick local check without an ACP console, forward the plugin service:

```bash
kubectl -n netobserv port-forward svc/netobserv-plugin 9001:9001
```

Then open [http://localhost:9001/](http://localhost:9001/). Stop the
port-forward with `Ctrl+C` when you finish.

## Pause flow collection without deleting the instance

Deleting the FlowCollector removes the agents and the pipeline and loses the
configuration. To stop collecting flows while keeping the configuration for
later, set the execution mode to `OnHold` instead:

```bash
kubectl patch flowcollector cluster --type=merge \
  -p '{"spec":{"execution":{"mode":"OnHold"}}}'
```

With `OnHold`, the operator deletes every workload and its supporting objects
that it owns:

- eBPF agent: the DaemonSet, its metrics Service, and its ServiceAccount
- flow logs pipeline: the Deployment, its ConfigMap, ServiceMonitor, and PrometheusRule
- console plugin: the Deployment, Service, HPA, metrics Service, ServiceAccount,
  ConfigMap, and ServiceMonitor

The FlowCollector itself, its namespace, the pipeline configuration, and all
flow records already written to ClickHouse are kept. The operator keeps
reconciling the instance but skips the deleted components.

Because the console plugin is removed while the instance is on hold,
**Observe** > **Network Traffic** cannot query the data during that period.
Records written before the pause stay in ClickHouse and become visible again as
soon as collection is resumed, until their retention period expires.

Confirm that the instance is on hold:

```bash
kubectl get flowcollector cluster \
  -o jsonpath='{range .status.conditions[*]}{.type}={.status} {.reason} {.message}{"\n"}{end}'
```

The paused components report `Unknown` with reason `ComponentUnused` and the
message `FlowCollector is on hold`. This applies to the `EBPFAgents`,
`WebConsole`, `FLPMonolith`, and `FLPTransformer` conditions. No agent, pipeline,
or plugin Pods remain.

Resume collection by setting the mode back to `Running`:

```bash
kubectl patch flowcollector cluster --type=merge \
  -p '{"spec":{"execution":{"mode":"Running"}}}'
```

The operator recreates the agents, the pipeline, and the console plugin with the
same configuration.
