# Upgrade Troubleshooting

Use this page when an upgrade check fails or an upgrade does not advance. An upgrade cannot be rolled back. Fix the reported cause and the upgrade continues; if it cannot be fixed, contact technical support.

## Inspect Upgrade State \{#inspect-upgrade-state}

Each command block on this page names the cluster it runs on. Run it from the execution host after `ac login`. Commands run on `global` unless the block switches to another cluster with `ac config use-cluster <cluster-name>`; such a block ends with `ac config use-cluster global`. `ac whoami --show-server` shows the cluster you are on: the platform address followed by `/kubernetes/<cluster-name>/`. For the standby `global` cluster in a DR environment, skip `ac config use-cluster` and add `--kubeconfig <standby-kubeconfig>` to each other `ac` command; `ac whoami --show-server` then prints the VIP of the standby.

For example, on the `global` cluster, read the state of the cluster being upgraded. Use `--cluster=global` for a `global` cluster itself:

```bash
ac config use-cluster global
ac whoami --show-server
ac adm upgrade status --cluster=<cluster-name> --verbose
```

`Upgrade` shows the state of the request:

- `Blocked`: a preflight check failed. Resolve the first `Failed` check under `Preflight`.
- `Retrying`: a preflight check reports `Retry`, and it runs again automatically.
- `InProgress`: the upgrade runs. A step that is being retried also shows `InProgress`.
- `Completed`: the cluster runs the target version.

`Conditions` (`Ready`, `Reconciling`, `Stalled`) and `Preflight` give the reason and message. `Failed (non-blocking)` does not stop the upgrade. `Upgrade stages` shows what is running. If `Upgrade` stays `InProgress` and `Ready` shows the reason `ClusterPluginAffinityMismatch`, see [Cluster Plugin Affinity Mismatch](#cluster-plugin-affinity-mismatch).

On Alauda OS, when `Upgrade` stays `InProgress` in the `Kubernetes` stage, a node replacement that does not advance shows only on the `InfraClusterVersion` of the cluster. On the `global` cluster that manages the cluster, read its `Stalled` condition:

```bash
ac -n cpaas-system get infraclusterversion <cluster-name> \
  -o jsonpath='{range .status.conditions[?(@.type=="Stalled")]}{.status}{"\t"}{.reason}{"\t"}{.message}{"\n"}{end}'
```

If it prints `True`, see [Stalled Reasons](#infra-stalled). For the full progress, see [Read the Progress](#infra-progress).

Before the request, `bash upgrade.sh --preflight` prints the same checks; for a workload cluster, add `--cluster=<cluster-name>`. After the request, the Cluster Version Operator (CVO) retries automatically. Submitting the request again does not clear a block.

## Handle Preflight Blocks \{#handle-preflight-blocks-when-needed}

A `ResourcePatch` records a customization of a platform resource. `ResourcePatchUpgradeable` fails with the reason `UnexemptResourcePatches` until each `ResourcePatch` is exempted for the target version. The message names up to five of them. Run the commands on the cluster being upgraded: for a `global` cluster, use `global` as `<cluster-name>`; in a DR environment, run them on the primary and again on the standby `global` cluster, with `--kubeconfig <standby-kubeconfig>` instead of `ac config use-cluster`. List the patches and their exemptions, review each patch, then exempt it:

```bash
ac config use-cluster <cluster-name>
ac get resourcepatches \
  -o custom-columns='NAME:.metadata.name,EXEMPT:.metadata.annotations.config\.cpaas\.io/exempt-for-ver'
ac get resourcepatches <rp-name> -o yaml
ac annotate resourcepatches <rp-name> config.cpaas.io/exempt-for-ver=<target-version> --overwrite
ac config use-cluster global
```

The value is the target version, for example `4.5.0`, and covers every patch version of that minor version. An exemption keeps the customization in place; it does not confirm that the customization still works on the target version. Confirm that with the technical support contact who supplied it.

### Resolve Other Preflight Blocks \{#resolve-other-preflight-blocks}

| `GlobalVersionReady` | **Verifies:** Workload clusters only: the `global` cluster has reached the target version.<br />**Fix:** Reason `GlobalVersionPending`: finish the `global` upgrade first; in a DR environment, on both `global` clusters, or on the primary while synchronization is paused. |
| `KubernetesVersionSupported` | **Verifies:** The target release supports the Kubernetes version of the cluster.<br />**Fix:** Contact technical support. |
| `ClusterRunning` | **Verifies:** The cluster status is `Running`.<br />**Fix:** Repair the cluster until its status is `Running`. The message shows the current status. |
| `DockerRuntimeUnsupported` | **Verifies:** No node uses the Docker runtime.<br />**Fix:** Migrate the affected nodes to `containerd`. |
| `ClusterModuleStable` | **Verifies:** ACP Core of the cluster is not being upgraded and has not failed to deploy.<br />**Fix:**<br />Status `Upgrading` or empty: run the check again later; if it does not change, contact technical support.<br />Status `DeployFailed` or `UpgradeFailed`: follow [Diagnose a Module That Does Not Advance](#module-not-advancing). |
| `ModuleInfoStable` | **Verifies:** ACP Core and the installed Extensions (Operators and Cluster Plugins) with the `Aligned` lifecycle are stable.<br />**Fix:** Follow the module rows of [Check the Registry, Modules, and etcd Backup](./pre-upgrade.mdx#global-common-checks); for a workload cluster, use its name instead of `global` in the `moduleinfo` command. |
| `InfraClusterVersionPreflight` and `InfraClusterVersionPreflight/<check>` | **Verifies:** Alauda OS: the Kubernetes upgrade can run. | `ResourcePatchConflict` | **Verifies:** No other `ResourcePatch` targets a resource that the upgrade patches itself. | `ClusterVersionUpgradeable` | **Verifies:** The request does not change the target to a patch version of the minor version that a running upgrade moves to.<br />**Fix:** Reason `MinorVersionClusterUpdateInProgress` or `MajorVersionClusterUpdateInProgress`: let the running upgrade to the version in the message complete, then request the patch version. If that upgrade cannot complete, contact technical support. |
| `ControlPlaneStaticPodsPresent` | **Verifies:** Every control plane node runs the static Pods `etcd-<node-name>`, `kube-apiserver-<node-name>`, `kube-controller-manager-<node-name>`, and `kube-scheduler-<node-name>` in `kube-system`.<br />**Fix:** Restore the static Pods that the message names: on the node, check the manifests in `/etc/kubernetes/manifests` and read `journalctl -u kubelet`. | `CustomEtcdBackupCronJobsAbsent` | **Verifies:** Non-Alauda OS clusters created by ACP: `cpaas-system` has no CronJob with the label `app=etcd-backup` other than `etcd-backup-default`.<br />**Fix:** Delete the CronJobs that the message names. `etcd-backup-default` keeps backing up etcd; see [Check the etcd Backup of a Cluster](./pre-upgrade.mdx#etcd-backup). |
| `CRIUpgradePodsAbsent` | **Verifies:** Non-Alauda OS clusters created by ACP: no Pod whose name starts with `cri-upgrade` remains in `kube-system`.<br />**Fix:** Delete the Pods that the message names. If one of them is still running, contact technical support. |
| `AdminAckRequired` | **Verifies:** `global` clusters only: every administrator gate is acknowledged.<br />**Fix:** See [Handle Administrator Acknowledgement Gates](#handle-administrator-acknowledgement-gates). |
| `DRSplitUpgradeWindow` | **Verifies:** Standby `global` cluster, identified by the DR marker `kube-public/etcd-sync`: synchronization is paused, the marker exists, no listed object is being deleted, and the token rotator is disabled and rolled out.<br />**Fix:** See [DR Standby Checks](#dr-split-upgrade-window). |
| Any other check | Contact technical support with the check name, reason, and message. |

Do not force an upgrade past a failed check. `spec.desiredUpdate.force` on the request turns every blocking failure of the whole preflight into a warning at once, not only the one you have reviewed; it releases nothing while any failure that cannot be bypassed remains. If a block cannot be resolved from this page, contact technical support.

### DR Standby Checks \{#dr-split-upgrade-window}

On a standby that has the DR marker, `DRSplitUpgradeWindow` passes only while synchronization is paused, the token rotator is disabled, and no object is being deleted, as in [Upgrade the Standby `global` Cluster After the Workload Clusters](./global/upgrade_global_dr_deferred_standby.mdx#upgrade-standby). Without the marker, for example after the plugin is uninstalled in [Upgrade `global` Clusters in a DR Environment](./global/upgrade_global_dr.mdx#before-you-begin), the check passes. In [Upgrade `global` Clusters in a DR Environment](./global/upgrade_global_dr.mdx#before-you-begin), a failure on the standby before the uninstall that names only `EtcdSyncNotPaused`, `TokenRotatorEnabled`, or both is expected: continue as described there, and do not pause synchronization or disable the token rotator. For `DeletingObjectsPresent`, let the deletion finish on the primary, wait until the standby is synchronized, and run the preflight again. The table applies only to [Upgrade the Standby `global` Cluster After the Workload Clusters](./global/upgrade_global_dr_deferred_standby.mdx). The message names the reason:

| Reason | Action |
| --- | --- |
| `EtcdSyncNotPaused` | Before the pause, in [Prepare Both `global` Clusters](./global/upgrade_global_dr_deferred_standby.mdx#prepare-both), this reason is expected; continue with the pause. After the pause: if the message says `etcd-sync is not paused yet`, wait until `status.phase` is `Paused` and run the preflight again; otherwise do not pause or resume synchronization yourself, and contact technical support. |
| `DRMarkerMissing` | The DR marker `kube-public/etcd-sync` was removed. Do not continue the standby upgrade, do not reinstall the plugin, and contact technical support. |
| `DeletingObjectsPresent` | The message lists objects that are being deleted on the standby. Before synchronization is paused, let the deletion finish on the primary, wait until the standby is synchronized, and run the preflight again. While synchronization is paused, changes on the primary do not reach the standby: contact technical support. |
| `TokenRotatorEnabled` | Before [Prepare Both `global` Clusters](./global/upgrade_global_dr_deferred_standby.mdx#prepare-both), this reason is expected; continue to that step. After it: disable the token rotator on the standby as described in [Prepare Both `global` Clusters](./global/upgrade_global_dr_deferred_standby.mdx#prepare-both), wait until its rollout finishes, and run the preflight again. |
| `DRSplitUpgradeWindowNotReady` | More than one item failed. The message lists each failed item with its reason. Handle each of them as described in this table. |
| `DependencyReadFailed` | The check could not read the standby. Confirm that its API server responds, for example with `ac get nodes`, and run the preflight again; a submitted upgrade request retries the check automatically. If it does not pass, contact technical support. |

## Handle Administrator Acknowledgement Gates \{#handle-administrator-acknowledgement-gates}

`AdminAckRequired` runs only for `global` clusters. In a DR environment, record the acknowledgement on the primary and again on the standby `global` cluster; it is not synchronized. On the `global` cluster, read the gates supplied by the target release:

```bash
ac config use-cluster global
ac -n cpaas-system get configmap admin-gates -o yaml
```

Complete the action that the gate describes. On a `global` cluster on ACP 4.4 or earlier, `AdminAckRequired` reports `Confirm Linux kernel 5.8+ and cgroup v2 readiness before upgrading to Kubernetes 1.35.` (gate key `ack-4.4-kubernetes-1.35-kernel-update`); complete [Check Node Readiness for Kubernetes 1.35 or Later](./pre-upgrade.mdx#kubernetes-135-node-readiness) for it. Then, on the same `global` cluster, record the acknowledgement with the key copied from `admin-gates`, and run the preflight again from the `installer/` directory of the extracted target Core Package. On the standby, run `export KUBECONFIG=<standby-kubeconfig>` instead of `ac config use-cluster global`, and `unset KUBECONFIG` afterwards. Continue when `Summary` shows `Passed` or `PassedWithWarnings`:

```bash
ac config use-cluster global
ac whoami --show-server
ACK_KEY='<key-from-admin-gates>'
ac -n cpaas-system patch configmap admin-acks --type merge \
  -p "{\"data\":{\"${ACK_KEY}\":\"true\"}}"
bash upgrade.sh --preflight
```

## Cluster Plugin Affinity Mismatch \{#cluster-plugin-affinity-mismatch}

When `Upgrade` stays `InProgress` and `Ready` shows the reason `ClusterPluginAffinityMismatch`, the labels of the cluster no longer match the cluster affinity of a Cluster Plugin installed on it, as defined in the target version. The message names the Cluster Plugins. No component of the cluster is upgraded until this is resolved; then the upgrade continues by itself. On the `global` cluster, read the labels of the cluster:

```bash
ac config use-cluster global
ac -n cpaas-system get clusters.cluster.x-k8s.io <cluster-name> --show-labels
```

If a label of the cluster was removed or changed, restore it. Otherwise, contact technical support with the message.

## Kubernetes Upgrade on Alauda OS \{#infra-kubernetes-upgrade}

On Alauda OS, the upgrade request also upgrades Kubernetes and Alauda OS. The platform tracks this in an `InfraClusterVersion` named after the cluster, on the `global` cluster that manages it; a `global` cluster has its own, named `global`.

### Kubernetes Upgrade Checks \{#infra-preflight-checks}

The platform checks the whole path to the target, including every intermediate Kubernetes version, and evaluates the checks again every 5 minutes. A fixed problem passes on the next evaluation. A message about one version on the path starts with `hop <version>: `, for example `hop v1.36.4-acp.3: DCS VM template <vm-template-name> not found`.

Each check in the tables below that fails or reports a warning has its own row in the upgrade preflight, named `InfraClusterVersionPreflight/<check>`, with the reason of the check; for example, `InfraClusterVersionPreflight/NoHostPathWorkloads`. When every check passes, the preflight shows only `InfraClusterVersionPreflight`.

- Before the `global` upgrade installs the new provider, `InfraClusterVersionPreflight` is a non-blocking warning with the reason `ProviderCapabilityNotDeclared`. This is expected: the checks run again in the `Kubernetes` stage, after ACP Core is upgraded.
- If a blocking check fails in the `Kubernetes` stage, the upgrade waits there and continues by itself once you fix the cause.

To read every check, run the commands below on the `global` cluster that manages the cluster. Replace `<preflight-name>` with the name at the start of the `InfraClusterVersionPreflight/<check>` message; in the list, it is the row whose `TARGET` is the target Kubernetes version:

```bash
ac -n cpaas-system get infraclusterversionpreflight -l upgrade.alauda.io/cluster=<cluster-name>
ac -n cpaas-system get infraclusterversionpreflight <preflight-name> \
  -o jsonpath='{range .status.checks[*]}{.name}{"\t"}{.severity}{"\t"}{.state}{"\t"}{.reason}{"\t"}{.message}{"\n"}{end}'
```

### Image Catalog Problems \{#image-catalog-problems}

On Huawei DCS and Huawei Cloud Stack, the platform picks the VM template or image of each Kubernetes version on the path from the ConfigMaps registered on `global`, separately for each architecture that the cluster uses. | Reason and message | Cause | What to do |
| --- | --- | --- |
| `ImageCatalogMiss`, naming a version, node pools, and an architecture | That Kubernetes version has no ConfigMap for an architecture that the cluster uses. | Register the VM template or image of that version for that architecture, as described in [Stage the Alauda OS Images](./pre-upgrade.mdx#stage-alauda-os-images). |

### Exempt a Confirmed Volume from NoHostPathWorkloads \{#exempt-hostpath-volume}

When you have confirmed that the data on a reported volume can be lost or survives node replacement, exempt that volume. On the `global` cluster, create the ConfigMap `icv-hostpath-exemptions` in `cpaas-system`, for example with `ac apply -f <file>`.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: icv-hostpath-exemptions
  namespace: cpaas-system
data:
  rules.yaml: |
    - clusters: [<cluster-name>]
      namespace: rook-ceph
      pod: rook-ceph-crashcollector-*
      hostPath: /var/lib/rook/rook-ceph/crash
      reason: Crash dumps can be lost; confirmed by <name> on <date>
```

| Field | Required | Meaning |
| --- | --- | --- |
| `clusters` | Yes | Cluster names, or `"*"` for all clusters. |
| `namespace` | Yes | The namespace of the Pod, or `"*"` for all namespaces. |
| `pod` | No | A glob for the Pod name. By default the rule covers every Pod in the namespace. |
| `hostPath` | One of three | An absolute path of a `hostPath` volume that the Pod defines itself; it also covers its subdirectories. `/` is not allowed. It does not match PersistentVolumes. |
| `persistentVolume` | One of three | A glob for the name of a node-local PersistentVolume that the Pod claims. |
| `csiDriver` | One of three | The exact CSI driver name of a PersistentVolume that the Pod claims, such as `topolvm.io`. It does not match local or `hostPath` PersistentVolumes. |
| `reason` | Yes | Why the exemption is safe. |

Set exactly one of `hostPath`, `persistentVolume`, and `csiDriver` in a rule.

Examples of rules in `rules.yaml`:

<Tabs>
  <Tab label="Rook logs">

Logs and crash dumps of one Ceph cluster, on one cluster:

```yaml
- clusters: [prod-a]
  namespace: rook-ceph
  hostPath: /var/lib/rook/rook-ceph/log
  reason: Ceph logs can be lost; confirmed by the storage owner
- clusters: [prod-a]
  namespace: rook-ceph
  hostPath: /var/lib/rook/rook-ceph/crash
  reason: Crash dumps can be lost; confirmed by the storage owner
```

  </Tab>
  <Tab label="Application cache">

A cache path of one application, on every cluster:

```yaml
- clusters: ["*"]
  namespace: media
  pod: thumbnailer-*
  hostPath: /data/thumbnail-cache
  reason: The cache rebuilds when the Pod starts
```

  </Tab>
  <Tab label="TopoLVM volumes">

TopoLVM volumes in one namespace, where the volume groups are on persistent disks:

```yaml
- clusters: [prod-a, prod-b]
  namespace: analytics
  csiDriver: topolvm.io
  reason: Volume groups are on persistent disks that survive node replacement
```

  </Tab>
  <Tab label="PersistentVolumes by name">

PersistentVolumes selected by name, in every namespace:

```yaml
- clusters: [prod-a]
  namespace: "*"
  persistentVolume: scratch-*
  reason: Each job recreates its scratch data
```

  </Tab>
</Tabs>

A rule exempts only the matching volume; other volumes on the same Pod are still reported. The check is evaluated again within 5 minutes, and when it passes, its message states how many volumes were exempted. Read the message with the command in [Kubernetes Upgrade Checks](#infra-preflight-checks).

If any rule is invalid, none of the rules apply, and the check fails with the reason `HostPathExemptionsInvalid`, naming the rule, even when no volume is reported. A ConfigMap without the `rules.yaml` key, or with an unknown field, is invalid too. Provider upgrades do not change this ConfigMap.

### Read the Progress \{#infra-progress}

On the `global` cluster that manages the cluster, read the summary, the conditions, the planned versions, the current step, and the events:

```bash
ac -n cpaas-system get infraclusterversion <cluster-name>
ac -n cpaas-system get infraclusterversion <cluster-name> \
  -o jsonpath='{range .status.conditions[*]}{.type}={.status} {.reason}: {.message}{"\n"}{end}'
ac -n cpaas-system get infraclusterversion <cluster-name> \
  -o jsonpath='{range .status.hops[*]}{.kubernetesVersion}{"\t"}{.phase}{"\n"}{end}{range .status.steps[*]}{.name}{"\t"}{.phase}{"\t"}{.message}{"\n"}{end}'
ac -n cpaas-system get events --field-selector involvedObject.kind=InfraClusterVersion,involvedObject.name=<cluster-name>
```

```text
NAME        PROVIDER     CURRENT         DESIRED         PHASE         HOLDER                     AGE
cluster-1   DCSCluster   v1.35.6-acp.9   v1.36.4-acp.3   Progressing   cluster-api-provider-dcs   128d
```

`CURRENT` advances after each intermediate Kubernetes version completes; `DESIRED` is the target. Until the provider takes a new target, `PHASE` is empty or `Pending`, or still shows `Succeeded` from an earlier upgrade. It then moves to `Preparing` (no node is replaced yet), `Progressing` (nodes are replaced one at a time; on Bare Metal, hosts are reinstalled), and `Succeeded`. There is no failed phase: a problem shows as `Stalled=True`, see [Stalled Reasons](#infra-stalled). On Bare Metal, a worker node pool that is not replaced at an intermediate version shows the step phase `Skipped`.

The Kubernetes upgrade is complete when `CURRENT` equals `DESIRED`, `PHASE` is `Succeeded`, and `Ready` is `True`. The `Ready` message `kube-proxy rollout pending` also means complete: kube-proxy is still rolling out; check the `kube-system/kube-proxy` DaemonSet on the cluster. While the upgrade runs, do not edit the `KubeadmControlPlane`, the `MachineDeployment` resources, their templates, the VM template ConfigMaps (Huawei DCS and VMware vSphere), the image ConfigMaps (Huawei Cloud Stack), or `elemental-image-catalog` (Bare Metal).

### Free Space on COS_STATE (Bare Metal) \{#check-cos-state-free-space}

Each Bare Metal host needs at least 4 GiB free on its `COS_STATE` partition to install the new OS image. A host that runs short fails with `no space left on device`, and each failed attempt leaves a partial snapshot that reduces the free space further. Check every host of the affected pools, because any `Available` host can receive the new image. On each host, read the free space and the snapshots. Use `btrfs`, not `df`, because `df` does not count snapshots. `Free (estimated)` must be at least 4 GiB:

```bash
btrfs filesystem usage -h /
snapper --no-dbus list
```

#### Remove Partial Snapshots \{#remove-partial-snapshots}

A snapshot left by a failed attempt shows `no` in the `default` and `active` columns and `update-in-progress=yes` in its userdata. On the host, list the snapshots, then delete only snapshots that match all three conditions:

:::warning
Never delete a snapshot whose `default` or `active` column is `yes`. The host boots the default snapshot and runs the active one; deleting either leaves the host unable to boot.
:::

```bash
snapper --no-dbus --csvout list --columns number,default,active,userdata
snapper --no-dbus delete --sync <number>
```

Run `btrfs filesystem usage -h /` again to confirm that the space was reclaimed. If the deletion fails, or the host still has less than 4 GiB free, the partition is too small. A host whose `COS_STATE` has the default 8 GiB size needs a reinstall from an ISO built as described in [Create the Registration and the ISO](../workload_clusters/alauda_os/bare-metal/prepare_os.mdx#create-registration), which has a larger partition. Reinstall such hosts before you upgrade the cluster; a reinstall replaces the node. If a host cannot be reinstalled, contact technical support.

### Hosts on a Different Image (Bare Metal) \{#correct-image-mismatch}

If `elemental-image-catalog` changed during the upgrade, some reinstalled hosts can run another image than the catalog now lists. The upgrade still completes and reports a Warning event `ImageMismatch` that names the `BaremetalMachine` objects and both images. After the cluster's `InfraClusterVersion` is `Succeeded`, confirm that the catalog holds the image you want. Then, on the `global` cluster, start a new rollout of the affected node group; its hosts are reinstalled according to the rollout settings, from the image now in the catalog:

```bash
ac -n cpaas-system patch machinedeployment <md-name> --type merge \
  -p "{\"spec\":{\"rolloutAfter\":\"$(date -u +%Y-%m-%dT%H:%M:%SZ)\"}}"
ac -n cpaas-system patch kubeadmcontrolplane <kcp-name> --type merge \
  -p "{\"spec\":{\"rolloutAfter\":\"$(date -u +%Y-%m-%dT%H:%M:%SZ)\"}}"
```

### Node Replacement Symptoms (Bare Metal) \{#bm-node-replacement}

| Symptom | What to check |
| --- | --- |
| The rollout stops at the first new node | The `ImageResolved` condition of the new `BaremetalMachine`: the key is in `elemental-image-catalog`, and the OS image can be pulled from the registry of the cluster; see [Provider Conditions](../workload_clusters/alauda_os/bare-metal/troubleshooting.mdx#provider-conditions). |
| A host reboots but never joins the cluster | `MachineInventory.status.plan.state` (`Failed` is final). Read the `elemental upgrade` errors on the host's serial console, and check that the registry of the cluster is reachable from the host. |
| A new control-plane node fails `kubeadm join` | The control-plane VIP is reachable. Check `ac -n kube-system get lease` on the cluster being upgraded, and, on its control-plane nodes, `ipvsadm -Ln` and the `keepalived` logs of the static Pod. |

### vSphere Rollout Holds That Are Not Failures \{#rollout-holds}

Some pauses during a vSphere rollout protect data. During such a hold, the `InfraClusterVersion` stays `Progressing`, its `Ready` message names the hold, and the upgrade continues by itself; no action is needed. Do not clear a hold by hand.

- **Attachment-safety hold.** While an old VM still has the slot's persistent disks attached, the provider keeps the deletion of the `VSphereVM` pending. A rollout that seems stuck at the deletion of the first old machine is often this hold. Do not remove the finalizer.
- **`Reclaimed` is a tombstone.** Do not delete a `phase: Reclaimed` entry to unstick a rollout.
- **`SlotAvailable=False` is expected.** With `maxSurge: 0` and a fully allocated pool, no slot is free until an old machine is deleted.
- **Power state.** A node that is powered off in vCenter stays off until you power it on there. A replacement VM is powered on, even if the node it replaces was off before the upgrade.

On the `global` cluster, read the disk handoff and the pending deletions. The normal handoff is `Attached`, then `Available` once the old VM is gone, then `Attached` again on the replacement:

```bash
ac -n <namespace> get vspheremachineconfigpool <pool-name> \
  -o jsonpath='{range .status.persistentDiskStatuses[*]}{.hostname}{" "}{.name}{" "}{.phase}{" owner="}{.ownerMachineName}{" err="}{.lastError}{"\n"}{end}'
ac -n <namespace> get vspherevm -o custom-columns='NAME:.metadata.name,DELETED:.metadata.deletionTimestamp,FINALIZERS:.metadata.finalizers'
```

## Kube-OVN and CoreDNS Takeover Is Blocked \{#core-addons-handoff-blocked}

On an Alauda OS cluster upgraded from a version earlier than v4.5, the platform takes over Kube-OVN and CoreDNS after the cluster and `global` both run v4.5. On the `global` cluster that manages the cluster, read the state from the cluster resource of its provider, `dcscluster`, `baremetalcluster`, `hcscluster`, or `vspherecluster`:

```bash
ac -n cpaas-system get <provider-cluster-resource> <cluster-name> \
  -o jsonpath='{range .status.conditions[?(@.type=="CoreAddonsHandedOff")]}{.status}{"\t"}{.reason}{"\t"}{.message}{"\n"}{end}'
```

- `True`: the platform manages Kube-OVN and CoreDNS.
- `False` with `CoreAddonsHandoffPending` or `CoreDNSSkipPhasePending`: the takeover is waiting, for example for a node rollout to finish. Check again later; if it does not change, contact technical support.
- `False` with `CoreAddonsHandoffNotApplicable`: the cluster is not on v4.5 yet; check again after its upgrade completes. If it still reports this reason then, contact technical support.
- `False` with `CoreAddonsHandoffBlocked`: the message names the setting. Contact technical support.
- No output: the cluster does not use Kube-OVN, and there is nothing to take over.

While the takeover is blocked, the cluster does not pass validation.

## Recover a Missing Aligned Extension Package \{#recover-missing-aligned-package}

Use this section when the target `ProductManifest` is not `Ready` after you deploy CVO, or when the upgrade status reports that an installed platform-aligned component `has no ready ModulePluginConfig`. A missing package does not change what is installed now. CVO can report it as `Ready=False` or `Reconciling=True` instead of `Stalled=True`.

On the `global` cluster, list the artifacts of the target release that are not `Ready`. Entries for optional components, for Extensions with the `Agnostic` lifecycle, or for components that are not installed can legitimately appear; compare the output with the installed Core and Aligned Extensions:

```bash
ac get productmanifest v<target-version> -o json | jq -r '
  .status.artifacts[] as $artifact
  | $artifact.channels[]
  | select(.artifactStatus != "Ready")
  | [$artifact.name, .channel, .tag, .artifactStatus]
  | @tsv'
```

### Aligned Cluster Plugins

`artifactStatus: Absent` means that the matching `ModulePluginConfig` is not fully `Ready`; it does not prove that the image is missing from the registry. On the `global` cluster, inspect the `ModulePluginConfig` named in the message, or identified by the component name and channel tag from the output above:

```bash
ac get modulepluginconfig <modulepluginconfig-name> \
  -o jsonpath='{.spec.image}{"\n"}{range .status.conditions[*]}{.type}{"\t"}{.status}{"\t"}{.reason}{"\t"}{.message}{"\n"}{end}'
```

| Evidence | Recovery |
| --- | --- |
| The named `ModulePluginConfig` does not exist | Inspect the conditions of the target `ProductManifest`. A missing object does not by itself prove that the package is absent. |
| `ResolveDigestFailed` reports `manifest unknown` or `not found`, or the registry confirms that `.spec.image` is absent | Publish the exact target package again, as described below. |
| An authentication (`unauthorized`, `denied`), certificate (`x509`), DNS, routing, timeout, or connection error | Correct the registry credentials, the certificate trust, or the network access from the component that resolves the image. |
| `LoadModulePluginFailed` | Inspect the package contents and `module-plugin.yaml`. Publish a corrected package only after you confirm that the package is invalid. |

- For a plugin of the `Upgrade from ACP 4.3 or earlier` scenario, copy its package into the `plugins/` directory of the target Core Package, then publish again as described in [Publish Core and the Staged Packages](./pre-upgrade.mdx#publish-core).
- For another Aligned Cluster Plugin, publish the target package with `violet push` to the `global` cluster whose upgrade reports it.

### Aligned Operators

Aligned Operators do not use `ModulePluginConfig`. On the affected cluster, inspect the `Subscription`, the target `InstallPlan`, and the catalog; on the `global` cluster, inspect the `ModuleInfo`:

```bash
ac config use-cluster <cluster-name>   # the affected cluster
ac get subscription -A
ac get installplan -A
ac config use-cluster global
ac get moduleinfo -l cpaas.io/cluster-name=<cluster-name>
```

If the target Operator package is missing, publish it to every cluster where the Operator is installed; for one workload cluster, use `violet push` with `--clusters "<cluster-name>"`. If the package exists, resolve the condition that CVO reports. Then watch the existing request with `ac adm upgrade status --cluster=<cluster-name>`; CVO retries automatically.

## Diagnose a Module That Does Not Advance \{#module-not-advancing}

On the `global` cluster, list the modules of the cluster, then read the conditions of the one that does not advance. Inspect the resource named in the condition and its Events; for an image pull failure, check registry access, CA trust, pull credentials, and the referenced manifest from the affected node:

```bash
ac get moduleinfo -l cpaas.io/cluster-name=<cluster-name> \
  -o custom-columns='MODULE:.metadata.labels.cpaas\.io/module-name,CURRENT:.status.version,TARGET:.spec.version,AVAILABLE:.status.availableVersions[*].version,PHASE:.status.phase'
ac get moduleinfo <moduleinfo-name> \
  -o jsonpath='{range .status.conditions[*]}{.type}{"\t"}{.status}{"\t"}{.reason}{"\t"}{.message}{"\n"}{end}'
```

## machine-config-daemon Does Not Start \{#mcd-readonly-usr-local-bin}

Use this section when an upgrade stays in the component stage and Kubernetes node replacement has not started. `machine-config` is not ready. `machine-config-daemon` is `CrashLoopBackOff`. The Pod log contains:

```text
failed to re-exec: writing /rootfs/usr/local/bin/machine-config-daemon: open /rootfs/usr/local/bin/.machine-config-daemon: read-only file system
```

Handle one node at a time. Do not restart the node, delete a snapshot, or submit the upgrade request again. The overlay is stored on `/run` and disappears after any node restart. If the node restarts unexpectedly and `/usr/local/bin` is still read-only, mount the overlay again, then delete that node's `machine-config-daemon` Pod so it is recreated.

On the affected node, as root, mount a writable overlay on `/usr/local/bin`:

```bash
mkdir -p -m 0755 /run/usr-local-bin/upper /run/usr-local-bin/work
if command -v getenforce >/dev/null 2>&1 && [ "$(getenforce)" != "Disabled" ]; then
  chcon -t bin_t /run/usr-local-bin/upper
fi
if ! findmnt -M /usr/local/bin -no FSTYPE,OPTIONS | grep -Eq '^overlay rw(,|$)'; then
  mount -t overlay overlay \
    -o lowerdir=/usr/local/bin,upperdir=/run/usr-local-bin/upper,workdir=/run/usr-local-bin/work \
    /usr/local/bin
fi
```

On the cluster being upgraded, delete only that node's daemon Pod. Wait until the new Pod is `Running` and the node stays `Ready`:

```bash
ac config use-cluster <cluster-name>
ac -n cpaas-system delete pod -l app=machine-config-daemon --field-selector spec.nodeName=<node-name>
ac -n cpaas-system get pod -l app=machine-config-daemon -o wide
ac get node <node-name>
ac config use-cluster global
```

Repeat for every node whose log matches. While any `machine-config-daemon` Pod is `CrashLoopBackOff`, continue to watch the existing request:

```bash
ac config use-cluster global
ac adm upgrade status --cluster=<cluster-name> --verbose
```

## Global Cluster Disaster Recovery Does Not Synchronize \{#dr-sync-diagnostics}

Use this section when the Pods of the Alauda Container Platform Global Cluster Disaster Recovery plugin are not `Running`, or the `/check` command does not report `localMissedKeys [0]` and `localSurplusKeys [0]`. Run every command on the standby `global` cluster: export its kubeconfig, and confirm that `ac whoami --show-server` prints the VIP of the standby. The `etcd-sync-bootstrap` Job runs before the synchronization starts: check the Job and the credentials it creates (if the Job failed, its log names the failing step), then the synchronization Pods and the current leader:

```bash
export KUBECONFIG=<standby-kubeconfig>
ac whoami --show-server
ac get job -n cpaas-system etcd-sync-bootstrap
ac logs -n cpaas-system job/etcd-sync-bootstrap
ac get secret -n cpaas-system remote-etcd-ca remote-etcd-client
ac get issuer -n cpaas-system remote-etcd-issuer
ac get certificate -n cpaas-system remote-etcd-client
ac get po -n cpaas-system -l app=etcd-sync
ac get lease -n cpaas-system etcd-sync-mirror
leader_pod=$(ac get lease -n cpaas-system etcd-sync-mirror -o jsonpath='{.spec.holderIdentity}')
ac logs -n cpaas-system "$leader_pod" | grep -E "Acquired leader lease|Start Sync update"
unset KUBECONFIG
```

In the `/check` output, the keys under `localSurplusKeys` (lines starting with `+`) exist on the standby but not on the primary; review them with your operations team before you delete them. The keys under `localMissedKeys` (lines starting with `-`) exist on the primary but not on the standby; this often resolves after you recreate the current leader Pod. Recreate it also when resources with `ownerReference` dependencies must be synchronized again. Wait until `Start Sync update` appears in its log, then run on the standby:

```bash
export KUBECONFIG=<standby-kubeconfig>
leader_pod=$(ac get lease -n cpaas-system etcd-sync-mirror -o jsonpath='{.spec.holderIdentity}')
ac delete po -n cpaas-system "$leader_pod"
unset KUBECONFIG
```

Run the `/check` command again. If it still does not report `localMissedKeys [0]` and `localSurplusKeys [0]`, or a Pod is not `Running`, contact technical support.

## Collect Evidence Before Escalation \{#collect-evidence}

Record the source and target ACP versions and the affected `ModuleInfo` or `ModulePluginConfig`. Do not include tokens, registry passwords, kubeconfig files, or Secret contents. On the `global` cluster that manages the cluster, also save the upgrade state and, on Alauda OS, the Kubernetes upgrade state:

```bash
ac config use-cluster global
ac adm upgrade status --cluster=<cluster-name> --verbose > upgrade-status.txt
ac -n cpaas-system get infraclusterversion <cluster-name> -o yaml > infraclusterversion.yaml
ac -n cpaas-system get infraclusterversionpreflight -l upgrade.alauda.io/cluster=<cluster-name> -o yaml > infraclusterversionpreflight.yaml
ac -n cpaas-system get events --sort-by=.lastTimestamp > events.txt
```
