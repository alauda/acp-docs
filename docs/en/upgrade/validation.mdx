# Upgrade Validation

Validate each upgraded cluster before you close its maintenance window. In a DR environment, validate the standby and the primary `global` cluster separately, before you upgrade any workload cluster. If a check fails, keep the window open and see [Upgrade Troubleshooting](./troubleshooting.mdx).

## Check the ACP Version \{#check-distribution-version}

Select the `global` cluster and read the upgrade status and history of the cluster. Replace `<cluster-name>` with `global` or the workload cluster name. In a DR environment, select the primary for a workload cluster, and the side you validate for a `global` cluster:

```bash
export KUBECONFIG=<global-kubeconfig>
kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}{"\n"}'
ac adm upgrade status --cluster=<cluster-name>
kubectl -n cpaas-system get cvsh <cluster-name> \
  -o jsonpath='{range .status.history[*]}{.version}{"\t"}{.state}{"\t"}{.startedTime}{"\t"}{.completionTime}{"\n"}{end}'
```

The ACP version (Distribution Version) is correct when `Upgrade` is `Completed`, `Current` shows `4.5.0`, the `Ready` condition is `True`, and `Stalled` is not `True`. The first history entry shows `4.5.0` with the state `Completed`.

## Check Kubernetes, Nodes, and Extensions \{#check-kubernetes-nodes-plugins}

On the `global` cluster, check the Core and the installed Extensions of the cluster. Every module is `Running` with `CURRENT` equal to `TARGET`, and `deployStatus` is not `Upgrading`, `DeployFailed`, or `UpgradeFailed`:

```bash
kubectl get moduleinfo -l cpaas.io/cluster-name=<cluster-name> \
  -o custom-columns='MODULE:.metadata.labels.cpaas\.io/module-name,CURRENT:.status.version,TARGET:.spec.version,PHASE:.status.phase'
kubectl get clustermodule <cluster-name> -o jsonpath='{.status.base.deployStatus}{"\n"}'
```

Then, with a kubeconfig for the upgraded cluster, check Kubernetes, the nodes, and the Pods:

```bash
kubectl version
kubectl get nodes
kubectl get pods --all-namespaces \
  | awk '{if ($4 != "Running" && $4 != "Completed")print}' \
  | awk -F'[/ ]+' '{if ($3 != $4)print}'
```

The server version is the Kubernetes version of the target ACP release, and every node is `Ready` with that version. Critical Pods are `Running` or `Completed`, and no Pod reports `ImagePullBackOff` or `ErrImagePull`.

## Additional Checks for Alauda OS Clusters \{#alauda-os-checks}

Run these checks on the `global` cluster that you selected above. Check that the platform has taken over Kube-OVN and CoreDNS; use the kind that matches the provider of the cluster, `dcscluster`, `baremetalcluster`, `hcscluster`, or `vspherecluster`:

```bash
kubectl -n cpaas-system get <provider-cluster-kind> <cluster-name> \
  -o jsonpath='{range .status.conditions[?(@.type=="CoreAddonsHandedOff")]}{.status}{"\t"}{.reason}{"\t"}{.message}{"\n"}{end}'
```

The status is `True`. A cluster that does not use Kube-OVN has no such condition. With the reason `CoreAddonsHandoffPending`, the takeover is still in progress; read the condition again later. With the reason `CoreAddonsHandoffBlocked`, the message names the setting that blocks the takeover: move a customized CoreDNS Corefile to the configuration of the `coredns` `ModuleInfo`; for any other setting, contact technical support. Then run the checks for the provider of the cluster:

<Tabs>
  <Tab label="Huawei DCS">

```bash
kubectl -n cpaas-system get infraclusterversion <cluster-name>
kubectl -n cpaas-system get infraclusterversion <cluster-name> \
  -o jsonpath='{range .status.conditions[?(@.type=="Ready")]}{.status}{"\t"}{.message}{"\n"}{end}'
```

`PHASE` is `Succeeded` and `Ready` is `True`. If the message starts with `kube-proxy rollout pending`, wait until the `kube-proxy` DaemonSet in `kube-system` of the cluster has rolled out.

  </Tab>
  <Tab label="Bare Metal">

```bash
kubectl -n cpaas-system get infraclusterversion <cluster-name>
kubectl -n cpaas-system get baremetalmachines.infrastructure.cluster.x-k8s.io -l cluster.x-k8s.io/cluster-name=<cluster-name> \
  -o custom-columns='NAME:.metadata.name,PHASE:.status.phase,INVENTORY:.status.machineInventoryRef.name,PLAN_SECRET:.status.planSecretRef.name'
kubectl -n cpaas-system get machineinventories.elemental.cattle.io <inventory-name> \
  -o jsonpath='{.status.plan.state}{" storage="}{.status.storage.phase}{"\n"}'
kubectl -n cpaas-system get secret <plan-secret-name> \
  -o jsonpath='{.metadata.annotations.baremetal\.alauda\.io/plan\.type}{"\n"}'
```

`PHASE` of the `InfraClusterVersion` is `Succeeded`, and every `BaremetalMachine` is `Running`. For each listed `INVENTORY` and `PLAN_SECRET`, the inventory reports `Applied` and the plan Secret reports `reprovision`. An inventory with managed volumes also reports `storage=Active`. Compare the `INVENTORY` column with the inventories you recorded during preparation: a node that now runs on a different inventory does not have the data of the data volumes declared on its previous host.

  </Tab>
  <Tab label="Huawei Cloud Stack">

```bash
kubectl -n cpaas-system get kubeadmcontrolplane,machinedeployment -l cluster.x-k8s.io/cluster-name=<cluster-name>
```

On every row, `VERSION` is the target Kubernetes version, and `READY` and `UPDATED` equal `REPLICAS`.

  </Tab>
  <Tab label="VMware vSphere">

```bash
kubectl -n cpaas-system get kubeadmcontrolplane,machinedeployment -l cluster.x-k8s.io/cluster-name=<cluster-name>
kubectl -n cpaas-system get vspheremachineconfigpool
kubectl -n cpaas-system get vspheremachineconfigpool <pool-name> \

```

On every `KubeadmControlPlane` and `MachineDeployment` row, `VERSION` is the target Kubernetes version, and `READY` and `UPDATED` equal `REPLICAS`. Each pool of the cluster reports `Ready=True` and `PersistentDisksReady=True`, its `ALLOCATED` count equals the number of running machines drawn from it, and its `TOTAL` count is unchanged. Every persistent disk on an allocated slot is `Attached`.

## Check the Web UI \{#check-web-ui}

Open the platform Web UI and confirm that login, cluster pages, and Marketplace pages load. For each Extension with the `Agnostic` lifecycle that you upgraded, confirm that its pages open and its main function works.

## Next Step

After you validate the `global` clusters, continue with [Upgrade Workload Clusters](./workload/upgrade_workload_cluster.mdx). After you validate a workload cluster, continue with the next cluster; after the last one, continue with [After All Clusters Are Upgraded](#after-all-clusters).

## After All Clusters Are Upgraded \{#after-all-clusters}

When `global` and every workload cluster run the target ACP version:

- If the source ACP version was earlier than 4.3 and the PKCE hardening is not done yet, follow [Disabling the PKCE Plain Method](../security/platform_security_configurations/disable_pkce_plain_method.mdx).
- On Bare Metal, rebuild the `SeedImage` with the target `base-image-iso` before you add new hosts. Take it from the same archive as the `base-image` in the image catalog. See [Build the SeedImage and Register Hosts](../workload_clusters/alauda_os/bare-metal/create_cluster.mdx#step-1-machineregistration-seedimage).
- Delete a VM template, cloud image, or Bare Metal OS image of an earlier version only after the last cluster that uses it is upgraded.
