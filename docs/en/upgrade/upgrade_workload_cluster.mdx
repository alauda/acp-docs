# Upgrade Workload Clusters

<Directive type="info" title="Upgrade Path">
This page covers the **traditional operating system** path for workload clusters. For workload clusters that use Alauda OS, the Kubernetes step lives in the Immutable Infrastructure documentation — see <ExternalSiteLink name="immutable-infra" href="/upgrade-cluster/index.html" children="Upgrading Clusters on Immutable Infrastructure" />. The Core, Aligned, and Agnostic steps described on this page still apply to immutable-OS clusters; only the way Kubernetes is rolled out differs.
</Directive>

:::warning MySQL-PXC Removed in Alauda Data Services Relational Database E1 v4.3.0
**MySQL-PXC is removed** starting from Alauda Data Services Relational Database E1 v4.3.0. Existing PXC instances will no longer be managed by the MySQL operator after upgrading to ACP v4.3.0 or later. See <ExternalSiteLink name="mysql-mgr" href="/upgrade" children="MySQL Operator Upgrade Guide" /> for migration instructions before upgrading.
:::

Workload clusters can be upgraded after the global tier has already reached the target ACP Distribution Version. The global tier does not need to be upgraded again if it is already at that Distribution Version.

Workload cluster upgrades use the same CVO-based workflow as the `global` cluster: confirm prerequisites, run preflight checks, request the upgrade, and observe execution. This workflow has two additional rules:

- If the platform uses **global DR**, both the standby and primary `global` clusters must reach the target Distribution Version before any workload cluster is upgraded to that Distribution Version.
- The target version normally becomes available for a workload cluster only after the global tier has already reached that same Distribution Version.

A workload cluster upgrade is staged like the `global` cluster upgrade, but shorter. A workload cluster does not have its own cluster version operator — the CVO runs on the `global` cluster and drives workload upgrades centrally — so a workload cluster has no artifact-synchronization or CVO-deployment step of its own:

| Phase | When | What happens |
| --- | --- | --- |
| 1. Preflight | 1–2 weeks before the window | Confirm prerequisites and run `upgrade.sh --cluster=<cluster> --preflight`; resolve every blocking item before the window opens. |
| 2. Upgrade | During the maintenance window | Request the upgrade and observe execution until the cluster reaches the target version. |

## Workflow

<Steps>

### Confirm workload-cluster prerequisites

Before requesting the upgrade, verify that:

* The workload cluster version is lower than the current `global` cluster version.
* The global tier has already reached the target ACP Distribution Version.
* In global DR environments, both the standby and primary `global` clusters have already reached that target Distribution Version.

### Ensure Aligned operator packages are available \{#operator-push-fallback}

The recommended pattern in [Upgrade the `global` cluster](./upgrade_global_cluster.mdx) pushes operator packages to every <Term name="productShort" /> cluster during the global upgrade window. If the recommendation was followed, the workload cluster already has every operator package it needs and you can skip this section.

Cluster plugins do not need a per-workload-cluster publication. A cluster plugin made available to the global tier through `upgrade.sh` or `violet` is installable and upgradable on every cluster in the platform.

If the global window did not push operator packages to this workload cluster — for example, the cluster was offline during the global window or was added later — push the target-version package for each Aligned operator installed on this workload cluster before the upgrade request:

```bash
violet push <path/to/operator-package> \
  --platform-address "https://<your-platform-domain>" \
  --platform-token "<platform_token>" \
  --clusters "<workload-cluster-name>"
```

You only need to push packages for Aligned operators actually installed on the workload cluster. Aligned cluster plugin packages made available to the global tier are available to all workload clusters and do not need per-cluster publication.

If an installed Aligned operator's target package is unavailable, CVO can wait for a matching target `InstallPlan` and then report an error while retrying the existing request. Inspect the operator's catalog, `Subscription`, `InstallPlan`, and `ModuleInfo`; publish a missing package with the command above, or correct the reported catalog or registry problem. Continue observing the existing request; you do not need to submit it again. Packages for Aligned operators that are not installed on this workload cluster do not block its upgrade.

### Run preflight checks

**When:** 1–2 weeks before the maintenance window, so there is time to resolve any blocking items before the window opens.

Run `upgrade.sh` in preflight mode for the target cluster:

```bash
bash upgrade.sh --cluster=<cluster> --preflight
```

Preflight is read-only — it validates upgrade readiness and does not change cluster state.

Preflight returns two parts:

| Output | Purpose |
| --- | --- |
| `Summary` | Shows the overall result, current version, desired version, and desired image. |
| `Checks` | Shows the result of each individual validation item. |

If preflight does not pass, do not submit the upgrade request until all blocking items are resolved.

For preflight block handling patterns, see [Upgrade Troubleshooting](./troubleshooting.mdx#handle-preflight-blocks-when-needed).

### Request the upgrade

**When:** during the maintenance window, after preflight passes.

Request the upgrade through one of the following entry points. The entry points are equivalent; pick the one that fits your operating model.

The platform offers two cluster management interfaces in the Web Console. **Web Console** is the built-in interface that ships with the platform and is the default path. **Web Console (Fleet Essentials)** is the newer cluster management interface, delivered as a separate cluster plugin that must be installed before it can be used.

<Tabs>
  <Tab label="Web Console">

  This is the built-in cluster management interface. The workload-cluster upgrade uses the same pages as the global-cluster upgrade, opened on the workload cluster instead of `global`.

  Requesting the upgrade requires update permission on the target cluster's `ClusterVersionShadow` and `ResourcePatch` resources.

  1. In the left navigation bar, click **Clusters** > **Clusters**, then click the workload cluster.

  2. Open the **Functional Components** tab, and click **Upgrade**.

     The button is disabled when there is no upgradable version (**No upgradable version**), when an upgrade is already running (**Upgrading**), or when the cluster is not healthy (**Cluster Abnormality**). A workload cluster has no upgradable version until the global tier has reached the target Distribution Version.

  3. On the **Personalized Configuration Confirmation** step, review the listed configurations, then click **Acknowledge**.

     This step appears **only when the cluster carries personalized configuration** — a customized `ModuleInfo`, a customized `ClusterModule`, or a `ResourcePatch`. When the cluster carries none, the step does not appear and the page opens directly on the confirmation form.

  4. On the **Confirm Component Upgrade** step, review **Current Version** and **Target Version**.

     For a workload cluster the target version is the Distribution Version the global tier has already reached; it cannot be selected manually in this interface.

  5. Click **Upgrade**, then confirm in the **Are you sure you want to upgrade the cluster version?** dialog.

  :::warning Maintenance mode is switched on by default, and applies to the whole platform
  The confirmation dialog is shared with the global-cluster upgrade and opens with **Maintenance mode** already enabled. The switch writes the **platform-wide** maintenance mode setting, not a workload-cluster setting: while it is on, users who are not platform administrators are restricted from accessing platform features across the platform, and the text in **Platform maintenance announcements** is shown to them. Turn the switch off before submitting unless you intend to restrict the whole platform for the duration of this workload-cluster upgrade.
  :::

  After the request is submitted, the page returns to the **Functional Components** tab and shows *The upgrade has been initiated. It may take 5~10 minute for the status to update.*

  </Tab>

  <Tab label="Web Console (Fleet Essentials)">

  This entry point belongs to the new cluster management interface, delivered as the **Alauda Container Platform Fleet Essentials** cluster plugin. It is **not installed by default**.

  **Prerequisite**: install **Alauda Container Platform Fleet Essentials** **v1.0.4 or later** from **Marketplace** > **Cluster Plugins**. The plugin adds a **Clusters (New)** entry to the left navigation bar. When that entry is absent, the plugin is not installed on this platform — use the **Web Console** tab instead.

  1. In the left navigation bar, click **Clusters (New)**, then click the workload cluster.

  2. Stay on the **Overview** tab and find the **Version & Update** card.

     The banner reads **Target not ready** while the global tier has not yet reached the target Distribution Version. In a global DR environment, both the primary and the standby `global` cluster must reach the target version first.

  3. Click **Upgrade** to open the **Update Cluster** dialog.

  4. On the **Custom Configuration** step, review the pending `ResourcePatch` entries that will be exempted to the target version, then click **Next**.

  5. On the **Confirm & Upgrade** step, review **Current Version** and **Target Version**.

     For a workload cluster the target equals the current `global` cluster version and is read-only — the drop-down list offered on the `global` cluster does not apply here.

  6. Click **Confirm & Start**.

     This interface has no second confirmation dialog and no maintenance mode switch. The card refreshes into the **Upgrading** state, and the **Preflight Checks**, **Upgrade Progress**, and **Update History** sections of the card track the run.

  </Tab>

  <Tab label="ACP CLI">

  Use ACP CLI when your current ACP session can access the target workload cluster. To avoid ambiguity, specify the target cluster explicitly with `--cluster`. ACP CLI is not used to upgrade the `global` cluster.

  ```bash
  # Request upgrade to the highest version currently published in availableUpdates
  ac adm upgrade --cluster=<cluster> --to-latest

  # Request upgrade to a specific target version
  ac adm upgrade --cluster=<cluster> --to=<target-version>
  ```

  ACP CLI submits the requested target for the specified workload cluster. Whether the upgrade can proceed is still determined by the cluster's available upgrade targets and the upgrade controller's preflight checks.

  If you are new to ACP CLI, see [Getting Started with ACP CLI](/ui/cli_tools/ac/getting-started.md). For session and cluster selection, see [Managing CLI Profiles](/ui/cli_tools/ac/managing-cli-profiles.md). For the complete AC CLI upgrade workflow (metadata preparation, available updates, request modes, and status interpretation), see [Upgrading Clusters](/ui/cli_tools/ac/upgrading-clusters.md). For full command and flag syntax, see [AC CLI Administrator Command Reference](/ui/cli_tools/ac/administrator-command-reference.md).

  </Tab>
</Tabs>

### Observe progress

After the upgrade request is submitted, use `cvsh.status` to track current version, desired version, preflight results, stages, and history:

```bash
kubectl get cvsh <cluster> -n cpaas-system
kubectl get cvsh <cluster> -n cpaas-system -o yaml
```

If your current ACP context points to the target workload cluster, you can also check the CLI-reported status:

```bash
# Show summary, preflight, and stage progress for the target cluster upgrade
ac adm upgrade status
```

For detailed semantics of `ac adm upgrade status` output (preflight and stage interpretation), see [Upgrading Clusters](/ui/cli_tools/ac/upgrading-clusters.md).

If the upgrade reports `Stalled=True`, use [Upgrade Troubleshooting](./troubleshooting.mdx). Missing Aligned operator and cluster-plugin packages have different recovery paths.

The commands above track the cluster-level (Core and Aligned) upgrade. To observe an individual plugin or operator module — for example while upgrading an Agnostic Extension — read its `ModuleInfo`:

```bash
kubectl get moduleinfo -l cpaas.io/cluster-name=<cluster> \
  -o custom-columns='MODULE:.metadata.labels.cpaas\.io/module-name,CURRENT:.status.version,TARGET:.spec.version,NEW:.status.availableVersions[0].version,PHASE:.status.phase'
```

A module has reached its target when `status.phase` is `Running` and `status.version` equals the target version.

### Recover NodeGroup Isolation Bindings \{#restore-nodegroup-isolation-bindings}

After node replacement finishes, wait until the new nodes are stable before reviewing any binding. Confirm that the backup identifier, business-cluster identifier and target ACP version match this upgrade. Compare the scoped backup with the current Node names and NodeGroup and with existing business records before deciding what to restore. A Node with the same name does not automatically recover a binding that the controller removed from `NodeGroup.spec.nodes`.

Record the evidence and decision for every backed-up NodeItem:

| NodeItem decision | Required evidence and action |
| --- | --- |
| Same-name Node is still required | Confirm the same name in the current cluster and in existing business records. A reviewer may retain the backed-up NodeItem. |
| Different-name Node replaces the backed-up Node | Restore only when existing business records confirm the replacement. Record the evidence and manually update the NodeItem; no provider mapping is required. |
| Different-name or otherwise uncertain Node | Do not restore the NodeItem. Do not use name similarity, provider guesses or automatic inference. Stop the affected recovery if the resulting binding cannot be confirmed. |
| Binding is no longer needed | Do not restore it. Record the decision and its basis. |

Build a target NodeGroup `spec` only from confirmed NodeItems, retaining the manually confirmed `spec.shareMode` and `spec.projects`. Do not apply the complete backed-up object or copy `metadata.resourceVersion`, `uid`, `generation`, `status`, `finalizers` or other runtime fields. Keep the original backup, reviewed spec, confirmation evidence and operation record in the controlled location.

Before running these commands, confirm that the account can manage `nodegroups.security.alauda.io`. The permissions documentation identifies the function as `acp-nodegroups`; verify that permission for the target release and environment instead of assuming a more specific RBAC name. Build `<reviewed-spec-patch>` from the controlled recovery record. It is a Kubernetes JSON merge patch in the form `{"spec":{"shareMode":...,"nodes":[...],"projects":[...]}}`; include only human-confirmed `spec` fields and no runtime fields.

Use the output and update forms verified for this target release:

```bash
ac config use-cluster <business-cluster>
ac get nodes \
  --selector='acp.cpaas.io/node-group-name=<nodegroup-name>' \
  -L acp.cpaas.io/node-group-name,acp.cpaas.io/node-group-share-mode
ac get nodegroups.security.alauda.io <nodegroup-name> \
  -o 'custom-columns=NAME:.metadata.name,MODE:.spec.shareMode,PROJECTS:.spec.projects[*].name,NODES:.spec.nodes[*].name,PHASE:.status.phase'
ac get nodegroups.security.alauda.io <nodegroup-name> \
  -o jsonpath='{.status.phase}{"\n"}'
ac describe node <node-name>
ac patch nodegroups.security.alauda.io <nodegroup-name> \
  --type=merge \
  -p '<reviewed-spec-patch>'
```

The `<reviewed-spec-patch>` must update only the reviewed NodeGroup `spec` and include the complete final `nodes` and `projects` arrays. Do not apply the complete object or copy runtime fields. Do not use this procedure to edit a Node label or taint. The existing NodeGroup controller must reconcile `acp.cpaas.io/node-group-name`, the applicable share-mode label and the Exclusive-mode taint from the reviewed `spec`. After it converges, complete the [NodeGroup isolation validation gate](./validation.mdx#validate-nodegroup-isolation) before continuing this upgrade.

If the backup is missing or incomplete, a mapping is uncertain, the update fails or conflicts, the update is only partially applied, the controller does not converge, or validation fails, stop further changes to that NodeGroup. Preserve the original backup, reviewed spec, confirmation evidence, object state, logs and error or Pod event records, then contact the release owner or technical support. Retry only a confirmed target after reviewing the current `spec`; do not delete the NodeGroup, widen the backup, or bypass the controller with direct label or taint changes. If the result is uncertain, keep the cluster blocked and record an incident decision.

If the upgrade is interrupted during node replacement, first use the applicable ACP release troubleshooting procedure to return the cluster to an operable and stable state, then repeat the node and backup review. A version rollback does not automatically restore NodeGroup members removed from `spec.nodes`; after rollback, repeat the same manual review, controller convergence and validation gate. Do not continue until the gate passes or a release owner records an incident decision with impact, risk acceptance or compensating measures, owner and follow-up actions.

### Upgrade Agnostic Extensions from Marketplace \{#upgrade-agnostic-from-marketplace}

CVO drives Core and Aligned Extensions. **Agnostic Extensions are outside CVO's scope** and must be upgraded individually after this workload cluster has reached the target Distribution Version.

For each in-use Agnostic Extension on this workload cluster:

1. In the Web Console, switch to **Administrator** view.
2. Navigate to **Marketplace > Cluster Plugins** for Agnostic cluster plugins, or to the operator workflow for Agnostic operators.
3. Select the target plugin or operator and trigger the upgrade.

Whether each Agnostic Extension needs to be upgraded in this window depends on its own Kubernetes compatibility — see the Extension's release notes for compatibility with the new Kubernetes version that the workload cluster has reached.

If the Marketplace does not offer the target version of an operator on this workload cluster, follow [Ensure Aligned operator packages are available](#operator-push-fallback) for that operator first and then retry the Marketplace upgrade.

</Steps>
