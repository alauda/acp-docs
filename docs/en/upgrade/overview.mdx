# Upgrade Overview

An upgrade moves each cluster to a new ACP version (Distribution Version), with one upgrade request per cluster: the `global` cluster first, then the workload clusters. You submit each request with ACP CLI (`ac adm upgrade`), and the Cluster Version Operator (CVO) on the `global` cluster carries it out. For the terms used in the upgrade pages, see [Glossary](../overview/glossary.mdx#upgrade-terms).

## Upgrade at a Glance \{#upgrade-at-a-glance}

1. Complete [Prepare for the Upgrade](./pre-upgrade.mdx) before you upgrade the first cluster. [Checks at a Glance](./pre-upgrade.mdx#lead-time) lists the checks that apply to each cluster.
2. Only for Huawei DCS and Huawei Cloud Stack clusters that keep platform data on machine template disks: [Migrate to Pool-Managed Persistent Disks](./persistent_disk_migration.mdx) before the upgrade.
3. Upgrade `global`: [Upgrade the `global` Cluster](./global/upgrade_global_cluster.mdx), or in a DR environment, [Upgrade `global` Clusters in a DR Environment](./global/upgrade_global_dr.mdx).
4. Upgrade the workload clusters, one or more at a time: [Upgrade Workload Clusters](./workload/upgrade_workload_cluster.mdx).
5. Validate each cluster after its upgrade: [Upgrade Validation](./validation.mdx).
6. After the last cluster is upgraded, finish with [After All Clusters Are Upgraded](./validation.mdx#after-all-clusters).

## What an Upgrade Changes \{#what-an-upgrade-changes}

Extensions (Operators and Cluster Plugins) with the `Aligned` lifecycle, Aligned Extensions for short, follow the ACP release. Extensions with the `Agnostic` lifecycle, Agnostic Extensions, are released independently. See [Lifecycle Types](../overview/core-and-extensions.mdx#lifecycle-types).

| Part | Upgraded by |
| --- | --- |
| ACP Core | The CVO, through the upgrade request of the cluster. |
| Aligned Extensions | The CVO, in the same request, for each Aligned Extension installed on the cluster. |
| Kubernetes, and Alauda OS on Alauda OS nodes | Depends on the node operating system and the provider; see [Who Upgrades Kubernetes](#upgrade-steps-by-node-os). |
| Agnostic Extensions | You, separately for each Extension, after the cluster reaches the target ACP version, by following the documentation of the Extension. |

The request stops if the package of an installed Aligned Extension is missing; preparation publishes these packages.

The infrastructure providers for Huawei DCS, Bare Metal, Huawei Cloud Stack, and VMware vSphere are Aligned Extensions installed on the `global` cluster, so they are upgraded with `global`. Their checks for a workload cluster are meaningful only after `global` is upgraded.

On an Alauda OS cluster upgraded from a version earlier than v4.5, the platform takes over Kube-OVN and CoreDNS once the cluster and `global` both run v4.5, and Kube-OVN is rolled out once at that point. A blocked takeover fails validation and, on Huawei Cloud Stack and VMware vSphere, keeps the Kubernetes upgrade from starting. If the takeover is blocked, contact technical support.

## Who Upgrades Kubernetes \{#upgrade-steps-by-node-os}

| Cluster | Who upgrades Kubernetes | How |
| --- | --- | --- |
| Alauda OS on Huawei DCS or Bare Metal | The platform, in the same upgrade request | Nodes are replaced one at a time, as described in [What Happens on Alauda OS Nodes](#alauda-os-nodes). Control-plane and worker nodes pass through each intermediate Kubernetes version; on Bare Metal, workers are reinstalled only at the target version. The request completes when every node runs the target version. |
| Alauda OS on Huawei Cloud Stack or VMware vSphere | You, right after the request completes | You replace the control-plane and worker nodes for each Kubernetes version on the path by following [Upgrade Kubernetes on Huawei Cloud Stack and VMware vSphere](./upgrade_kubernetes_hcs_vsphere.mdx). |
| Non-Alauda OS | The platform, in the same upgrade request | In place on the existing nodes; nodes are not replaced. Every node must already run Linux kernel 5.8 or later with cgroup v2. Complete a node OS update before the upgrade; it restarts the nodes. |

One deployment can mix providers, for example `global` on Huawei DCS and workload clusters on Huawei DCS and VMware vSphere. Each cluster follows the row of its own provider.

### ACP Version and Kubernetes Version \{#distribution-version-vs-kubernetes-version}

ACP Core goes straight from the current to the target ACP version. Kubernetes moves one minor version at a time. Each ACP minor version from 4.1 on currently upgrades clusters to one Kubernetes minor: 1.34 on ACP 4.3, 1.35 on ACP 4.4, and 1.36 on ACP 4.5. On Alauda OS, an upgrade from ACP 4.3 to 4.5 therefore passes through the intermediate Kubernetes version 1.35, and each intermediate Kubernetes version needs its own Alauda OS image, prepared before the upgrade. Preparation also publishes the images of the ACP release of each intermediate Kubernetes version, such as v4.4.1 for 1.35; you never request an upgrade to that release.

On Huawei Cloud Stack and VMware vSphere, upgrade Kubernetes right after the upgrade request of the cluster completes; do not leave the cluster on the new ACP version with the previous Kubernetes version.

Patch upgrades follow the same rules:

- On Huawei DCS and Bare Metal, a patch upgrade also replaces every node, one at a time, when the target release changes the Kubernetes build or the Alauda OS image. When neither changes, no node is replaced, but the platform still runs its checks, so the preparation applies to every upgrade.
- On Huawei Cloud Stack and VMware vSphere, every upgrade must bring Kubernetes to the target version of the ACP release, including a patch upgrade that changes only the Kubernetes build.

## What Happens on Alauda OS Nodes \{#alauda-os-nodes}

Alauda OS nodes are not upgraded in place. On Huawei DCS, Huawei Cloud Stack, and VMware vSphere, each node is replaced with a new virtual machine, one at a time. Bare Metal needs no additional machines: the existing hosts are reinstalled one at a time. The nodes of an Alauda OS `global` cluster are replaced the same way, so the upgrade is run from a host outside every cluster.

While a node is replaced, the cluster has one node fewer. Pods are evicted from a node before it is replaced and start again on other nodes; a workload with a single replica is unavailable until its Pod runs again. A worker node pool with a single node has no node for its Pods while that node is replaced.

| Data | During node replacement |
| --- | --- |
| Data on the node's own disks, such as `hostPath` volumes and local PersistentVolumes, unless they are on pool-managed persistent disks (Bare Metal: declared data volumes) | Not kept. Move it to CSI storage before the upgrade. |
| Data on pool-managed persistent disks (Huawei DCS, Huawei Cloud Stack, VMware vSphere) and on declared data volumes (Bare Metal), such as the platform data in `/var/cpaas` | Kept when the replacement node takes over the pool entry or host of the node it replaces. On Huawei DCS, Huawei Cloud Stack, and Bare Metal, this is guaranteed only when the pool has no free entry or host, in control-plane and worker pools alike: for example, three entries for a three-node control plane. Remove the free entries from the pool before the upgrade, as described in [Check the `global` Cluster](./pre-upgrade.mdx#check-global-cluster) and, for workload clusters, [Before You Upgrade the Clusters](./workload/upgrade_workload_cluster.mdx#before-the-window). VMware vSphere reuses the released entry. |
| External storage, such as volumes provided through CSI | Not affected. |

Huawei DCS and Huawei Cloud Stack clusters that still keep platform data on machine template disks must first migrate to pool-managed persistent disks. Complete the migration before the upgrade; it replaces every node.

The time a cluster needs grows with its number of nodes multiplied by the number of Kubernetes versions on its path; on Bare Metal, workers are reinstalled once. On Huawei Cloud Stack and VMware vSphere, add the time for your own steps.

## Upgrade Order and Compatibility \{#upgrade-order}

Upgrade the `global` cluster first, then the workload clusters. A workload cluster can be upgraded only to the ACP version that `global` currently runs. You can request the upgrade of several workload clusters at once; the platform upgrades a limited number of them at the same time, and the others wait. A cluster that is not upgraded yet must still be within the direct upgrade window and, if ACP created it, the Compatible Versions of the next `global` upgrade; otherwise upgrade it before that `global` upgrade.

**Direct upgrade window.** A cluster can be upgraded directly to ACP 4.5 from ACP 4.2, 4.3, or 4.4; preparation confirms that the platform offers the target for your exact patch version. On Alauda OS, the documented path starts at v4.3.2: for an Alauda OS cluster on an earlier version, contact technical support; see [Check Cluster Versions](./pre-upgrade.mdx#check-compatibility). Clusters on ACP 4.1 or earlier must first be upgraded into the direct upgrade window. The window applies to every cluster registered on `global`: the ACP components on imported and registered third-party clusters must also be within it, otherwise the `global` upgrade is blocked, so upgrade those clusters first.

**Compatible Versions.** Before you upgrade `global`, every workload cluster created by ACP must run a Kubernetes version within the Compatible Versions of the target release, listed in the [Kubernetes Support Matrix](../overview/kubernetes-support-matrix.mdx#version-support-matrix). Preflight does not check this rule; check it yourself as described in [Check Cluster Versions](./pre-upgrade.mdx#check-compatibility). Upgrade a cluster outside this range first, to the ACP version that `global` runs now. The Kubernetes version of imported and registered third-party clusters is not covered by Compatible Versions and does not block the upgrade.

**Global Cluster Disaster Recovery.** With the Alauda Container Platform Global Cluster Disaster Recovery plugin, upgrade both `global` clusters before any workload cluster. Upgrade the standby, then the primary, and reinstall the plugin without delay; do not change clusters on either `global` cluster until the plugin is reinstalled. Prepare both `global` clusters; the plugin does not synchronize the preparation.

**Upgrading `global` again.** You can upgrade `global` again, for example to a later patch, before every workload cluster is upgraded:

- Do not start it while a workload cluster upgrade is running. The platform does not prevent it.
- Workload clusters that lag behind then upgrade directly to the ACP version that `global` runs; preparation confirms that this version accepts their current version. For them, prepare the Alauda OS images of that version and of each intermediate Kubernetes version on their path. Images of the skipped ACP patch versions are not needed.
- Each new `global` upgrade starts again with the preparation and uses the same `global` upgrade page.

## Risks and Recovery \{#risks-and-recovery}

Every upgrade request runs preflight checks before it applies the target version. If `global` has never been upgraded with the CVO, its first preflight runs during its upgrade, after you deploy the CVO. On Huawei DCS and Bare Metal, the platform also checks the cluster before it replaces nodes; for the `global` cluster, these node checks can run only after its ACP Core is upgraded, so preparation includes checking those items yourself. On Huawei Cloud Stack and VMware vSphere, the platform does not check the Kubernetes part; preparation covers it.

An upgrade cannot be rolled back, on any provider or node operating system, and you cannot request a lower ACP version. Restoring an etcd backup does not return a cluster to an earlier ACP version. Fix the reported cause and the upgrade continues; if it cannot be fixed, contact technical support. For the reported causes, see [Upgrade Troubleshooting](./troubleshooting.mdx).

With Global Cluster Disaster Recovery, uninstall the plugin only when the standby is fully synchronized with the primary: uninstalling it while the standby misses data can delete workload cluster machines and, on Alauda OS, the nodes behind them. The DR page checks this first. From the moment you uninstall the plugin until you reinstall it, there is no DR protection, and the two `global` upgrades, including their Kubernetes upgrade on Huawei Cloud Stack or VMware vSphere, are the only cluster changes allowed on either `global` cluster.
