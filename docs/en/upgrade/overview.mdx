# Upgrade Overview

An upgrade moves each cluster to a new ACP version (Distribution Version), with one upgrade request per cluster: the `global` cluster first, then the workload clusters. You submit each request with ACP CLI (`ac adm upgrade`), and the Cluster Version Operator (CVO) on the `global` cluster carries it out. For the terms used in the upgrade pages, see [Glossary](../overview/glossary.mdx#upgrade-terms).

## What an Upgrade Changes \{#what-an-upgrade-changes}

Extensions (Operators and Cluster Plugins) with the `Aligned` lifecycle, Aligned Extensions for short, follow the ACP release. Extensions with the `Agnostic` lifecycle, Agnostic Extensions, are released independently. See [Lifecycle Types](../overview/core-and-extensions.mdx#lifecycle-types).

| Part | Upgraded by | When |
| --- | --- | --- |
| ACP Core | CVO, through the upgrade request | In the maintenance window of the cluster |
| Aligned Extensions | CVO, in the same request, for each Aligned Extension installed on the cluster | Same window |
| Kubernetes, and Alauda OS on Alauda OS nodes | Depends on the node operating system and the provider; see [Who Upgrades Kubernetes](#upgrade-steps-by-node-os) | Same window |
| Agnostic Extensions | You, separately for each Extension, by following its own documentation | After the cluster reaches the target ACP version |

The request stops if the package of an installed Aligned Extension is missing, so preparation publishes all of them. A published package does not install the Extension on clusters that do not use it.

If the source ACP version is earlier than 4.3, plan to upgrade these Agnostic Extensions in the same window, or their pages can fail to open: Alauda DevOps v3, Alauda AI Essentials, Alauda Hyperflux, and Alauda Container Platform Data Services Essentials.

The infrastructure providers for Huawei DCS, Bare Metal, Huawei Cloud Stack, and VMware vSphere are Aligned Extensions installed on the `global` cluster, so they are upgraded with `global`. Their checks for a workload cluster are meaningful only after `global` is upgraded.

On an Alauda OS cluster upgraded from a version earlier than v4.5, the platform takes over Kube-OVN and CoreDNS once the cluster and `global` both run v4.5, and Kube-OVN is rolled out once at that point. A Kube-OVN or CoreDNS setup that differs from what the platform installs, such as a customized Corefile, blocks the takeover; preparation checks for it.

If the takeover is blocked, the cluster does not pass validation, and on Huawei Cloud Stack and VMware vSphere the manual Kubernetes upgrade cannot start, so the window cannot be closed. Resolve it with technical support before you schedule the cluster. For a customized Corefile, the takeover continues only after the `kube-system/coredns` Corefile is back to the default.

## Who Upgrades Kubernetes \{#upgrade-steps-by-node-os}

| Cluster | Who upgrades Kubernetes | How |
| --- | --- | --- |
| Alauda OS on Huawei DCS or Bare Metal | The platform, in the same upgrade request | Nodes are replaced one at a time, as described in [What Happens on Alauda OS Nodes](#alauda-os-nodes). Control-plane and worker nodes pass through each intermediate Kubernetes version; on Bare Metal, workers are reinstalled only at the target version. The request completes when every node runs the target version. |
| Alauda OS on Huawei Cloud Stack or VMware vSphere | You, after the request completes, in the same window | You replace the control-plane and worker nodes for each Kubernetes version on the path by following [Upgrade Kubernetes on Huawei Cloud Stack and VMware vSphere](./upgrade_kubernetes_hcs_vsphere.mdx). |
| Non-Alauda OS | The platform, in the same upgrade request | In place on the existing nodes; nodes are not replaced. Every node must already run Linux kernel 5.8 or later with cgroup v2: update the node OS in its own change window before the upgrade window. |

One deployment can mix providers, for example `global` on Huawei DCS and workload clusters on Huawei DCS and VMware vSphere. Each cluster follows the row of its own provider.

### ACP Version and Kubernetes Version \{#distribution-version-vs-kubernetes-version}

ACP Core goes straight from the current to the target ACP version. Kubernetes moves one minor version at a time. Each ACP minor version from 4.1 on currently upgrades clusters to one Kubernetes minor: 1.34 on ACP 4.3, 1.35 on ACP 4.4, and 1.36 on ACP 4.5. On Alauda OS, an upgrade from ACP 4.3 to 4.5 therefore passes through the intermediate Kubernetes version 1.35, and each intermediate Kubernetes version needs its own Alauda OS image, prepared in advance. Preparation also publishes the images of the ACP release of each intermediate Kubernetes version, such as v4.4.1 for 1.35; you never request an upgrade to that release.

Kubernetes is finished in the same window as ACP Core and the Aligned Extensions. A cluster on the new ACP version with the old Kubernetes version is only a transition state; do not close the window in that state.

Patch upgrades follow the same rules:

- On Huawei DCS and Bare Metal, a patch upgrade also replaces every node, one at a time, when the target release changes the Kubernetes build or the Alauda OS image. When neither changes, no node is replaced, but the platform still runs its checks, so the preparation applies to every upgrade.
- On Huawei Cloud Stack and VMware vSphere, every upgrade must bring Kubernetes to the target version of the ACP release, including a patch upgrade that changes only the Kubernetes build.

## What Happens on Alauda OS Nodes \{#alauda-os-nodes}

Alauda OS nodes are not upgraded in place. On Huawei DCS, Huawei Cloud Stack, and VMware vSphere, each node is replaced with a new virtual machine, one at a time. Bare Metal needs no additional machines: the existing hosts are reinstalled one at a time. The nodes of an Alauda OS `global` cluster are replaced the same way, so the upgrade is run from a host outside every cluster.

While a node is replaced, the cluster has one node fewer. Applications with a single replica, and worker node pools with a single node, are interrupted while that node is replaced.

| Data | During node replacement |
| --- | --- |
| Application data stored on the node itself, such as `hostPath` volumes and local PersistentVolumes | Not kept. Move it to CSI storage before the upgrade. |
| Data on pool-managed persistent disks (Huawei DCS, Huawei Cloud Stack, VMware vSphere) and on declared data volumes (Bare Metal), such as the platform data in `/var/cpaas` | Kept when the replacement node takes over the pool entry or host of the node it replaces. On Huawei DCS, Huawei Cloud Stack, and Bare Metal, this is guaranteed only when the pool has no free entry or host, for control-plane and worker pools alike: for example, three entries for a three-node control plane. VMware vSphere reuses the released entry. Preparation checks this. |
| External storage, such as volumes provided through CSI | Not affected. |

Huawei DCS and Huawei Cloud Stack clusters that still keep platform data on machine template disks must first migrate to pool-managed persistent disks. The migration replaces every node and needs its own change window before the first upgrade window.

The time a cluster needs grows with its number of nodes multiplied by the number of Kubernetes versions on its path; on Bare Metal, workers are reinstalled once. On Huawei Cloud Stack and VMware vSphere, add the time for your own steps.

## Upgrade Order and Compatibility \{#upgrade-order}

Upgrade the `global` cluster first, then the workload clusters. A workload cluster can be upgraded only to the ACP version that `global` currently runs. In one window you can request several workload clusters; the platform upgrades a limited number of them at the same time, and the others wait. You can spread the workload clusters over several later windows. A cluster that is not upgraded yet must still be within the direct upgrade window and, if ACP created it, the Compatible Versions of the next `global` upgrade; otherwise upgrade it before that `global` upgrade.

**Direct upgrade window.** A cluster can be upgraded directly to ACP 4.5 from ACP 4.2, 4.3, or 4.4; preparation confirms that the platform offers the target for your exact patch version. On Alauda OS, the documented path starts at v4.3.2: for an Alauda OS cluster on an earlier version, contact technical support, as listed in [Items That Need Lead Time](./pre-upgrade.mdx#lead-time). Clusters on ACP 4.1 or earlier must first be upgraded into the direct upgrade window. The window applies to every cluster registered on `global`: the ACP components on imported and registered third-party clusters must also be within it, otherwise the `global` upgrade is blocked, so upgrade those clusters first.

**Compatible Versions.** Before you upgrade `global`, every workload cluster created by ACP must run a Kubernetes version within the Compatible Versions of the target release, listed in the [Kubernetes Support Matrix](../overview/kubernetes-support-matrix.mdx#version-support-matrix). Preflight does not check this rule; check it yourself as described in [Check Workload Cluster Compatibility](./pre-upgrade.mdx#check-compatibility). Upgrade a cluster outside this range first, to the ACP version that `global` runs now. The Kubernetes version of imported and registered third-party clusters is not covered by Compatible Versions and does not block the upgrade.

**Global Cluster Disaster Recovery.** With the Alauda Container Platform Global Cluster Disaster Recovery plugin, upgrade the standby `global` cluster and then the primary in the same window, before you upgrade any workload cluster. Prepare both `global` clusters; the plugin does not synchronize the preparation.

**Upgrading `global` again.** You can upgrade `global` again, for example to a later patch, before every workload cluster is upgraded:

- Do not start it while a workload cluster upgrade is running. The platform does not prevent it.
- Workload clusters that lag behind then upgrade directly to the ACP version that `global` runs; preparation confirms that this version accepts their current version. For them, prepare the Alauda OS images of that version and of each intermediate Kubernetes version on their path. Images of the skipped ACP patch versions are not needed.
- Each new `global` upgrade starts again with the preparation and uses the same `global` upgrade page as the first window.

## Risks and Recovery \{#risks-and-recovery}

Every upgrade request runs preflight checks before it applies the target version. If `global` has never been upgraded with the CVO, its first preflight runs inside the first window; plan time for it. On Huawei DCS and Bare Metal, the platform also checks the cluster before it replaces nodes; for the `global` cluster, these node checks can run only after its ACP Core is upgraded, so preparation includes checking those items yourself. On Huawei Cloud Stack and VMware vSphere, the platform does not check the Kubernetes part; preparation covers it.

An upgrade cannot be rolled back, on any provider or node operating system, and you cannot request a lower ACP version. Restoring an etcd backup does not return a cluster to an earlier ACP version. Fix the reported cause and the upgrade continues; if it cannot be fixed, contact technical support. For the reported causes, see [Upgrade Troubleshooting](./troubleshooting.mdx).

With Global Cluster Disaster Recovery, uninstall the plugin only when the standby is fully synchronized with the primary: uninstalling it while the standby misses data can delete workload cluster machines and, on Alauda OS, the nodes behind them. The DR page checks this first. From the moment you uninstall the plugin until you reinstall it, there is no DR protection, and you must not change clusters on either `global` cluster other than the two `global` upgrades, including their Kubernetes upgrade on Huawei Cloud Stack or VMware vSphere.
