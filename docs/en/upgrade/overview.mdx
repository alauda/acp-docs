# Upgrade Overview

An upgrade moves each cluster to a new ACP version (Distribution Version), one cluster at a time: the `global` cluster first, then the workload clusters. For each cluster, you submit one upgrade request with ACP CLI (`ac adm upgrade`), and the Cluster Version Operator (CVO) on the `global` cluster carries it out. For the terms used in the upgrade pages, see [Glossary](../overview/glossary.mdx#upgrade-terms).

## What an Upgrade Changes \{#what-an-upgrade-changes}

Extensions (Operators and Cluster Plugins) with the `Aligned` lifecycle, Aligned Extensions for short, follow the ACP release. Extensions with the `Agnostic` lifecycle, Agnostic Extensions, are released independently. See [Lifecycle Types](../overview/core-and-extensions.mdx#lifecycle-types).

| Part | Upgraded by | When |
| --- | --- | --- |
| ACP Core | CVO, through the upgrade request | In the maintenance window of the cluster |
| Aligned Extensions | CVO, in the same request, for each Aligned Extension installed on the cluster | Same window |
| Kubernetes, and Alauda OS on Alauda OS nodes | Depends on the node operating system and the provider; see [Who Upgrades Kubernetes](#upgrade-steps-by-node-os) | Same window |
| Agnostic Extensions | You, separately for each Extension, by following its own documentation | After the cluster reaches the target ACP version |

The request stops if the package of an installed Aligned Extension is missing, so preparation publishes all of them. A published package does not install the Extension on clusters that do not use it.

The infrastructure providers for Huawei DCS, Bare Metal, Huawei Cloud Stack, and VMware vSphere are Aligned Extensions installed on the `global` cluster, so they are upgraded with `global`. Their checks for a workload cluster are meaningful only after `global` is upgraded.

On an Alauda OS cluster upgraded from a version earlier than v4.5, the platform takes over Kube-OVN and CoreDNS once the cluster and `global` both run v4.5, and Kube-OVN is rolled out once at that point. A Kube-OVN or CoreDNS setup that differs from what the platform installs, such as a customized Corefile, blocks the takeover; preparation checks for it.

## Who Upgrades Kubernetes \{#upgrade-steps-by-node-os}

| Cluster | Who upgrades Kubernetes | How |
| --- | --- | --- |
| Alauda OS on Huawei DCS or Bare Metal | The platform, in the same upgrade request | Nodes are replaced one at a time, as described in [What Happens on Alauda OS Nodes](#alauda-os-nodes). Control-plane and worker nodes pass through each intermediate Kubernetes version; on Bare Metal, workers are reinstalled only at the target version. The request completes when every node runs the target version. |
| Alauda OS on Huawei Cloud Stack or VMware vSphere | You, after the request completes, in the same window | You replace the control-plane and worker nodes for each Kubernetes version on the path by following [Upgrade Kubernetes on Huawei Cloud Stack and VMware vSphere](./upgrade_kubernetes_hcs_vsphere.mdx). |
| Non-Alauda OS | The platform, in the same upgrade request | In place on the existing nodes. Nodes are not replaced. |

One deployment can mix providers, for example `global` on Huawei DCS and workload clusters on Huawei DCS and VMware vSphere. Each cluster follows the row of its own provider.

### ACP Version and Kubernetes Version \{#distribution-version-vs-kubernetes-version}

ACP Core goes straight from the current to the target ACP version. Kubernetes moves one minor version at a time, and each ACP minor version runs one Kubernetes minor: 1.34 on ACP 4.3, 1.35 on ACP 4.4, and 1.36 on ACP 4.5. On Alauda OS, an upgrade from ACP 4.3 to 4.5 therefore passes through Kubernetes 1.35, and each intermediate Kubernetes version needs its own Alauda OS image, prepared in advance.

Kubernetes is finished in the same window as ACP Core and the Aligned Extensions. A cluster on the new ACP version with the old Kubernetes version is only a transition state; do not close the window in that state.

Patch upgrades follow the same rules:

- On Huawei DCS and Bare Metal, a patch upgrade also replaces every node, one at a time, when the target release changes the Kubernetes build or the Alauda OS image. When neither changes, no node is replaced, but the platform still runs its checks, so the preparation applies to every upgrade.
- On Huawei Cloud Stack and VMware vSphere, every upgrade must bring Kubernetes to the target version of the ACP release, including a patch upgrade that changes only the Kubernetes build.

## What Happens on Alauda OS Nodes \{#alauda-os-nodes}

Alauda OS nodes are not upgraded in place. On Huawei DCS, Huawei Cloud Stack, and VMware vSphere, each node is replaced with a new virtual machine, one at a time. Bare Metal needs no additional machines: the existing hosts are reinstalled one at a time. The nodes of an Alauda OS `global` cluster are replaced the same way, so the upgrade is run from a host outside every cluster.

While a node is replaced, the cluster has one node fewer. Applications with a single replica, and worker node pools with a single node, are interrupted while that node is replaced.

| Data | During node replacement |
| --- | --- |
| Application data stored on the node itself, such as `hostPath` volumes and local PersistentVolumes | Not kept. Move it to CSI storage before the upgrade. On Bare Metal, data on declared data volumes stays on its host, but a node is not guaranteed to come back on the same host when the pool has spare hosts, so do not rely on it either. |
| Platform data on the pool-managed persistent disk | Kept. |
| External storage, such as volumes provided through CSI | Not affected. |

Huawei DCS and Huawei Cloud Stack clusters that still keep platform data on machine template disks must first migrate to pool-managed persistent disks. The migration replaces every node and needs its own change window before the first upgrade window.

The time a cluster needs grows with its number of nodes multiplied by the number of Kubernetes versions on its path; on Bare Metal, workers are reinstalled once. On Huawei Cloud Stack and VMware vSphere, add the time for your own steps.

## Upgrade Order and Compatibility \{#upgrade-order}

Upgrade the `global` cluster first, then the workload clusters. A workload cluster can be upgraded only to the ACP version that `global` currently runs. You can spread the workload clusters over several later windows: until they are upgraded, `global` keeps managing them as long as their Kubernetes version is within the Compatible Versions.

**Direct upgrade window.** A cluster can be upgraded directly to ACP 4.5 from ACP 4.2, 4.3, or 4.4; preparation confirms that the platform offers the target for your exact patch version. The direct upgrade window applies to every cluster registered on `global`: the ACP components on imported and registered third-party clusters must also be within it, otherwise the `global` upgrade is blocked, so upgrade those clusters first. Clusters on earlier versions need intermediate upgrades first, and some Alauda OS clusters need technical support; the Plan stage in [Upgrade at a Glance](#upgrade-at-a-glance) links to the list.

**Compatible Versions.** Before you upgrade `global`, every workload cluster created by ACP must run a Kubernetes version within the Compatible Versions of the target release, listed in the [Kubernetes Support Matrix](../overview/kubernetes-support-matrix.mdx#version-support-matrix). Upgrade a cluster outside this range first, to the ACP version that `global` runs now. The Kubernetes version of imported and registered third-party clusters is not covered by Compatible Versions and does not block the upgrade.

**Global Cluster Disaster Recovery.** With the Alauda Container Platform Global Cluster Disaster Recovery plugin, upgrade the standby `global` cluster and then the primary in the same window, before you upgrade any workload cluster. Prepare both `global` clusters; the plugin does not synchronize the preparation.

**Upgrading `global` again.** You can upgrade `global` again, for example to a later patch, before every workload cluster is upgraded:

- Do not start it while a workload cluster upgrade is running. The platform does not prevent it.
- Workload clusters that lag behind then upgrade directly to the ACP version that `global` runs. For them, prepare the Alauda OS images of that version and of each intermediate Kubernetes version on their path. Images of the skipped ACP patch versions are not needed.
- Each new `global` upgrade starts again with the preparation.

## Risks and Recovery \{#risks-and-recovery}

Every upgrade request runs preflight checks before it applies the target version. On Huawei DCS and Bare Metal, the platform also checks the cluster before it replaces nodes; for the `global` cluster, these node checks can run only after its ACP Core is upgraded, so preparation includes checking those items yourself. On Huawei Cloud Stack and VMware vSphere, the platform does not check the Kubernetes part; preparation covers it.

An upgrade cannot be rolled back, on any provider or node operating system, and you cannot request a lower ACP version. Fix the reported cause and the upgrade continues; if it cannot be fixed, contact technical support. For the reported causes, see [Upgrade Troubleshooting](./troubleshooting.mdx).

With Global Cluster Disaster Recovery, there is no DR protection from the moment you uninstall the plugin on the standby until you reinstall it, and you must not change clusters on either `global` cluster during that time.
