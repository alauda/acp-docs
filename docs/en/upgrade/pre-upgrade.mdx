# Prepare for the Upgrade

Complete these steps before you upgrade. Prepare again for every upgrade, including a patch upgrade of the ACP version (Distribution Version) and an upgrade of `global` before every workload cluster has caught up.

In a DR environment with Alauda Container Platform Global Cluster Disaster Recovery, do every step that names `global` on both `global` clusters. If your clusters run on more than one provider, complete the steps for each of them, including the provider of the `global` cluster.

## Prepare the Execution Host \{#execution-host}

Run every upgrade command from one execution host. The few steps that run on a node say so; return to the execution host after each of them.

- A Linux host (x86_64 or aarch64) outside every cluster that reaches the platform address, and the VIP and registry of each `global` cluster.
- `kubectl`, ACP CLI (`ac`), and Violet v4.2.13 or later (`violet version`).
- A platform account with the platform administrator role.
- In DR, a kubeconfig of the standby `global` cluster that points to its VIP, `<standby-kubeconfig>`. For example, copy `/etc/kubernetes/admin.conf`, with any certificate files it references, from a control-plane node of the standby, and set its `server` to the VIP if it points elsewhere.
- The extracted target Core Package, kept on this host until every cluster is upgraded.

Log in once with the platform administrator account, with `KUBECONFIG` unset:

```bash
ac login https://<platform-address> --name <session>
ac config use-cluster <cluster-name>
ac whoami --show-server
ac config use-cluster global
```

- The session is saved in `~/.kube/config`, and `ac` commands run on `global`, the primary in DR. For a workload cluster, run `ac config use-cluster <cluster-name>` first and `ac config use-cluster global` afterwards; `ac whoami --show-server` then ends with `/kubernetes/<cluster-name>/`.
- `upgrade.sh` uses `kubectl` with this session. Run `ac config use-cluster global` right before the script.
- For the standby, run `export KUBECONFIG=<standby-kubeconfig>` first, confirm that `ac whoami --show-server` prints the standby VIP, and run `unset KUBECONFIG` afterwards.

## Check Cluster Versions \{#check-compatibility}

**Applies to**: every cluster registered on `global`, `global` included, imported clusters included. In DR, run it on each `global` cluster; on the standby, read only its own version.

On `global`, list the ACP version (the `CURRENT` column of the first list), the Kubernetes version, and the infrastructure provider of every cluster. In the last list, `DCSCluster`, `BaremetalCluster`, `HCSCluster`, and `VSphereCluster` mark an Alauda OS cluster, `UserProvisionedCluster` a cluster that does not run Alauda OS, and `<none>` an imported cluster:

```bash
ac config use-cluster global
ac whoami --show-server
ac -n cpaas-system get cvsh
ac -n cpaas-system get clusters.clusterregistry.k8s.io -o custom-columns='NAME:.metadata.name,KUBERNETES:.status.version'
ac -n cpaas-system get clusters.cluster.x-k8s.io -o custom-columns='NAME:.metadata.name,INFRASTRUCTURE:.spec.infrastructureRef.kind'
```

If `cvsh` reports `the server doesn't have a resource type`, or does not list a cluster, take the ACP version of that cluster from `VERSION`:

```bash
ac get clustermodule -o custom-columns='NAME:.metadata.name,VERSION:.spec.version'
```

In DR, read the version of the standby, from `CURRENT`, or from `VERSION` when `cvsh` is not available:

```bash
ac --kubeconfig <standby-kubeconfig> -n cpaas-system get cvsh global
ac --kubeconfig <standby-kubeconfig> get clustermodule global -o custom-columns='NAME:.metadata.name,VERSION:.spec.version'
```

### Upgrade Path and Compatibility \{#check-upgrade-path}

Compare each cluster with the table. Continue when every cluster matches a row whose action is Continue; otherwise, take the action of each row that matches.

| Result for a cluster | Action |
| --- | --- |
| ACP 4.2, 4.3, or 4.4, on Alauda OS v4.3.2 or later; and, for a cluster created by ACP, a Kubernetes version within the Compatible Versions of the target in the [Kubernetes Support Matrix](../overview/kubernetes-support-matrix.mdx) | Continue. The preflight check `VersionUpgradePath` confirms the exact patch version. |
| Already the target minor version: a patch upgrade, or `global` upgraded again | Continue. |
| ACP 4.1 or earlier | Contact technical support. |
| On Alauda OS, an ACP version earlier than v4.3.2 | Contact technical support. |
| Created by ACP, with a Kubernetes version outside the Compatible Versions of the target | Upgrade the cluster on the current `global` first, as described in the documentation of its current ACP version. |
| No version is shown for the cluster | Contact technical support. |

## Download the Packages \{#download-packages}

<Steps>

### Download the Core Package and the Alauda OS Images \{#download-core-package}

From the <Term name="company" /> Customer Portal, download the Core Package of the target ACP version for your architecture, and extract it on the execution host. On Alauda OS, also download:

- The Core Package of the ACP release of each intermediate Kubernetes version. You use it only to publish its images.
- From the OS download page, the image of the target version and of each intermediate Kubernetes version, for the architecture and OS variant of your nodes: `qcow2` for Huawei DCS and Huawei Cloud Stack, `ova` for VMware vSphere, and the archive of an OCI image layout for Bare Metal.

### Download the Other Extension Packages \{#download-other-extensions}

Export the Extensions installed on `global` to `apps.yaml`. Then let the Customer Portal check the file and download the target-version packages of the installed Extensions, including the infrastructure providers and the Cluster Bootstrap Provider. Set `<arch>` to `amd64`, `arm64`, or `hybrid` to match the Core Package, and `<target-version>` to the target ACP version, such as `4.5.0`.

```bash
read -rsp "Customer Portal token: " AC_TOKEN; printf '\n'
violet ac login --access-token="${AC_TOKEN}" --ac-url=<customer-portal-url>
read -rsp "Platform token: " PLATFORM_TOKEN; printf '\n'
violet list --platform-address "https://<platform-address>" --platform-token "${PLATFORM_TOKEN}" --output-file "./apps.yaml"
violet ac import-yaml --arch=<arch> --platformVersion=v<target-version> --path=./apps.yaml --download=true
```

In a DR environment, do the same for the standby, into its own file. The two `global` clusters can run different Extensions; for example, Global Cluster Disaster Recovery runs only on the standby:

```bash
read -rsp "Standby platform token: " STANDBY_TOKEN; printf '\n'
violet list --platform-address "https://<standby-vip>" --platform-token "${STANDBY_TOKEN}" --output-file "./standby-apps.yaml"
violet ac import-yaml --arch=<arch> --platformVersion=v<target-version> --path=./standby-apps.yaml --download=true
```

### Download the Upgrade Scenario for ACP 4.3 or Earlier \{#download-upgrade-scenario}

Only when the source ACP version is 4.3 or earlier. With the Customer Portal login of the previous step, download the `Upgrade from ACP 4.3 or earlier` scenario:

```bash
violet ac scenarios --arch=<arch> --platformVersion=v<target-version>
violet ac download-app --arch=<arch> --platformVersion=v<target-version> --scenario="Upgrade from ACP 4.3 or earlier"
```

</Steps>

## Check the Registry Storage \{#registry-storage}

**Applies to**: non-Alauda OS `global` clusters that use the platform built-in Registry. In DR, run it on each `global` cluster. Skip it for Alauda OS `global` clusters and for an external registry.

On `global`, read the registry type: `false` is the platform built-in Registry, `true` an external registry. On the standby, run `unset KUBECONFIG` afterwards:

```bash
ac config use-cluster global        # on the standby, instead: export KUBECONFIG=<standby-kubeconfig>
ac whoami --show-server
ac get productbase base -o jsonpath='{.spec.registry.external}{"\n"}'
```

With the built-in Registry, on each control-plane node of `global`:

```bash
df -h /cpaas/minio
```

Continue when at least 120 GB is available; otherwise, expand that disk, and if you cannot, contact technical support.

## Publish the Packages \{#sync-upgrade-artifacts}

Run the steps from the `installer/` directory of the extracted target Core Package, against `global`, and complete them before you upgrade `global`.

<Steps>

### Stage the Upgrade Scenario Packages \{#stage-plugins}

Only when the source ACP version is 4.3 or earlier. Copy every package of [the upgrade scenario](#download-upgrade-scenario) into `plugins/`, then list the directory and compare it with the downloaded packages.

```bash
cp <path-to-scenario-package> ./plugins/
ls -1 ./plugins/
```

### Publish Core and the Staged Packages \{#publish-core}

Read the registry type of `global`: the second value is `false` for the platform built-in Registry and `true` for an external registry. Every Aligned Extension installed on a cluster needs its target-version package before that cluster's upgrade; otherwise the upgrade stops until you publish it.

```bash
ac config use-cluster global
ac whoami --show-server
ac get productbase base -o jsonpath='{.spec.registry.address}{"\t"}{.spec.registry.external}{"\n"}'
```

<Tabs>
  <Tab label="Platform built-in Registry">

```bash
ac config use-cluster global
ac whoami --show-server
bash upgrade.sh --only-sync-image
```

  </Tab>
  <Tab label="External registry">

`upgrade.sh` does not upload to an external registry. Run both upload modes; both must succeed. Do not export the registry username or password: `bash upgrade.sh --preflight` stops while either is set in the environment.

```bash
REGISTRY_ADDRESS="<registry-address>"
REGISTRY_USERNAME="<registry-username>"
read -rsp "Registry password: " REGISTRY_PASSWORD; printf '\n'
bash res/upload.sh all "$REGISTRY_ADDRESS" "$REGISTRY_USERNAME" "$REGISTRY_PASSWORD"
bash res/upload.sh necessary "$REGISTRY_ADDRESS" "$REGISTRY_USERNAME" "$REGISTRY_PASSWORD"
unset REGISTRY_USERNAME REGISTRY_PASSWORD
```

  </Tab>
</Tabs>

### Publish the Other Extensions \{#publish-other-extensions}

Publish the packages downloaded for `apps.yaml` in [Download the Other Extension Packages](#download-other-extensions) with `violet push`. The packages for the standby follow in the next step.

| Packages | Publish to | When |
| --- | --- | --- |
| Cluster plugins, including the providers | `global` | Before the `global` upgrade |
| Operators | `global` and each workload cluster that runs the operator | Before the upgrade of each such cluster |

```bash
# A cluster plugin: the platform distributes it
violet push <cluster-plugin-package>.tgz --platform-address "https://<platform-address>" --platform-token "${PLATFORM_TOKEN}"
# An operator: global and every workload cluster that runs it
violet push <operator-package>.tgz --platform-address "https://<platform-address>" --platform-token "${PLATFORM_TOKEN}" \
  --clusters "global,<cluster-name-1>,<cluster-name-2>"
```

### Publish to the Standby global Cluster \{#publish-standby}

In a DR environment only. Select the standby for the rest of this step, and read its registry type, as on the primary:

```bash
export KUBECONFIG=<standby-kubeconfig>
ac whoami --show-server
ac get productbase base -o jsonpath='{.spec.registry.address}{"\t"}{.spec.registry.external}{"\n"}'
```

<Tabs>
  <Tab label="Platform built-in Registry">

Publish the images to the registry of the standby: run the command from the `installer/` directory of the target Core Package, and again from that of each intermediate Core Package. The script uses the registry of the cluster in `KUBECONFIG`.

```bash
bash upgrade.sh --only-sync-image
```

Then push the packages downloaded for `standby-apps.yaml` in [Download the Other Extension Packages](#download-other-extensions). Set `<registry-port>` to the port of the registry address printed above. Always set `--platform-address` and `--dest-repo`; without them, the packages go to the primary.

```bash
STANDBY_REGISTRY_USER=$(ac -n cpaas-system get secret registry-admin -o jsonpath='{.data.username}' | base64 -d)
STANDBY_REGISTRY_PASSWORD=$(ac -n cpaas-system get secret registry-admin -o jsonpath='{.data.password}' | base64 -d)
read -rsp "Standby platform token: " STANDBY_TOKEN; printf '\n'
violet push <package>.tgz --platform-address "https://<standby-vip>" --platform-token "${STANDBY_TOKEN}" \
  --dest-repo "<standby-vip>:<registry-port>" --username "${STANDBY_REGISTRY_USER}" --password "${STANDBY_REGISTRY_PASSWORD}"
# Repeat violet push for each package, then:
unset STANDBY_REGISTRY_USER STANDBY_REGISTRY_PASSWORD STANDBY_TOKEN
```

  </Tab>
  <Tab label="External registry">

`upgrade.sh` does not upload to an external registry. When the standby uses the same registry endpoint as the primary, the images are already there. When it uses its own endpoint, run the external registry commands of [Publish Core and the Staged Packages](#publish-core) and [Publish the Intermediate Core Images](#sync-intermediate-images) again, with the address and credentials of that endpoint.

Then push the packages downloaded for `standby-apps.yaml` with `violet push --platform-address "https://<standby-vip>"`. Confirm its registry options for an external registry with technical support before you upgrade the standby.

  </Tab>
</Tabs>

On the standby, list the versions of each Cluster Plugin you pushed, for example Global Cluster Disaster Recovery, then return to the login session:

```bash
export KUBECONFIG=<standby-kubeconfig>
ac whoami --show-server
ac get moduleconfigs -l cpaas.io/module-name=etcd-sync
unset KUBECONFIG
```

Continue when each Cluster Plugin you pushed lists its target version; otherwise, run `violet push` for it again as above.

</Steps>

## Stage the Alauda OS Images \{#stage-alauda-os-images}

On non-Alauda OS clusters, skip this section.

Stage the image of the target version and of every intermediate Kubernetes version for each provider in use. The commands that the Huawei DCS and Bare Metal tabs generate run on `global`; in DR, run them on both `global` clusters, on the standby after `export KUBECONFIG=<standby-kubeconfig>`, and run `unset KUBECONFIG` afterwards:

```bash
ac config use-cluster global
ac whoami --show-server
```

<Tabs>
  <Tab label="Huawei DCS">

Upload the `qcow2` image of each version to every DCS site that your clusters use, and register it as a VM template with the same name on every site. Then generate the VM template ConfigMaps and apply them on `global`:

<DcsVmTemplateConfigMap mode="path">
  Replace `<os>` with the OS of the VM templates, such as `m55`, `ko`, or `ku`, and take the ACP version, Kubernetes version, and etcd tag of each ConfigMap from [Version Mapping](../overview/alauda_os_support_matrix.mdx#version-mapping). Repeat the intermediate ConfigMap for each intermediate Kubernetes version, and omit it when there is none.
</DcsVmTemplateConfigMap>

  </Tab>
  <Tab label="Bare Metal">

On a host that has containerd and reaches the registry of `global`, such as a `global` control-plane node, import the archive of each version and push the images it holds; this push is the only step of this tab on a node, so return to the execution host afterwards. For Alauda OS M55, push both `baremetal-base-image` and `baremetal-base-image-iso`. For Alauda OS KU, push the OS image that the list command prints to the repository used in the command below, which the catalog command also uses. The `admin` password is in the `cpaas-system/registry-admin` Secret of `global`. In DR, push to the registry of both `global` clusters.

{/* lint ignore no-legacy-os-names */}

```bash
ctr -n bare-metal-os images import --all-platforms --no-unpack <bare-metal-os-archive>
ctr -n bare-metal-os images ls -q
read -rsp "Registry password: " REGISTRY_PASSWORD; printf '\n'
# Alauda OS M55
for repo in baremetal-base-image baremetal-base-image-iso; do
  ctr -n bare-metal-os images push --local --skip-verify -u "<registry-username>:${REGISTRY_PASSWORD}" \
    "<registry-address>/tkestack/${repo}:<os-image-tag>" "${repo}:<os-image-tag>"
done
# Alauda OS KU
ctr -n bare-metal-os images push --local --skip-verify -u "<registry-username>:${REGISTRY_PASSWORD}" \
  "<registry-address>/tkestack/kubeos-rootfs:<os-image-tag>" "<listed-os-image>"
unset REGISTRY_PASSWORD
```

Add the keys of every version to the image catalog on `global` before you request the upgrade: a host replaced while its key is missing fails and does not recover when you add the key later. Run the command once for each combination of architecture and OS in the pools:

<BareMetalImageCatalog mode="path">

## Check the Clusters \{#prepare-alauda-os-clusters}

Unless a check says otherwise, run its commands on `global`, with `<cluster-name>` set to the cluster that you check, `global` included. In DR, check workload clusters on the primary, and each `global` cluster on its own side: on the standby, run `export KUBECONFIG=<standby-kubeconfig>` instead of `ac config use-cluster global`, set `<cluster-name>` to `global`, and run `unset KUBECONFIG` afterwards.

:::warning
On Alauda OS, data on a node's own disks, such as `hostPath` volumes and local PersistentVolumes, is not kept when the node is replaced, unless it is on a pool-managed persistent disk (Bare Metal: a declared data volume). Move it to CSI storage, or onto a pool-managed persistent disk, before the upgrade.
:::

### Check That No Machine Template Declares `/var/cpaas` \{#var-cpaas-disk}

**Applies to**: Huawei DCS and Huawei Cloud Stack clusters. In DR, run it on each `global` cluster. Skip it for other clusters; on VMware vSphere, do not restructure the disk lists of the machine config pools as part of an upgrade.

On `global`, list the machine templates that the cluster uses: the control-plane template, and the `TEMPLATE` of each MachineDeployment. On the standby, run `unset KUBECONFIG` at the end of this check:

```bash
ac config use-cluster global        # on the standby, instead: export KUBECONFIG=<standby-kubeconfig>
ac whoami --show-server
KCP=$(ac -n cpaas-system get clusters.cluster.x-k8s.io <cluster-name> -o jsonpath='{.spec.controlPlaneRef.name}')
ac -n cpaas-system get kubeadmcontrolplane "${KCP}" -o jsonpath='{.spec.machineTemplate.infrastructureRef.name}{"\n"}'
ac -n cpaas-system get machinedeployment -l cluster.x-k8s.io/cluster-name=<cluster-name> \
  -o custom-columns='NAME:.metadata.name,TEMPLATE:.spec.template.spec.infrastructureRef.name'
```

Then read each of these templates, `<template-name>`:

<Tabs>
  <Tab label="Huawei DCS">

```bash
ac -n cpaas-system get dcsmachinetemplate <template-name> -o custom-columns='NAME:.metadata.name,TEMPLATE_DISKS:.spec.template.spec.vmConfig.dcsMachineDiskSpec[*].path'
```

Continue when no template lists `/var/cpaas`; otherwise, [migrate to pool-managed persistent disks](./persistent_disk_migration.mdx) before the upgrade. The migration replaces nodes.

  </Tab>
  <Tab label="Huawei Cloud Stack">

```bash
ac -n cpaas-system get hcsmachinetemplate <template-name> \
  -o custom-columns='NAME:.metadata.name,DATA_VOLUMES:.spec.template.spec.dataVolumes[*].mountPath,POOL:.spec.template.spec.configPoolRef.name'
```

Continue when no template lists `/var/cpaas` in `DATA_VOLUMES`; otherwise, [migrate to pool-managed persistent disks](./persistent_disk_migration.mdx) before the upgrade. The migration replaces nodes. [Check the Free Pool Entries](#persistent-disk-layout) uses the `POOL` names.

  </Tab>
</Tabs>

### Check the Free Pool Entries \{#persistent-disk-layout}

**Applies to**: control-plane and worker pools of Huawei DCS, Huawei Cloud Stack, and Bare Metal clusters whose nodes keep data on persistent disks or data volumes. In DR, run it on each `global` cluster. Skip it for VMware vSphere and non-Alauda OS clusters.

On `global`; on the standby, run `unset KUBECONFIG` at the end of this check:

```bash
ac config use-cluster global        # on the standby, instead: export KUBECONFIG=<standby-kubeconfig>
ac whoami --show-server
```

<Tabs>
  <Tab label="Huawei DCS">

The last command prints the type and the address of the control-plane load balancer of the cluster:

```bash
ac -n cpaas-system get dcsiphostnamepool \
  -o custom-columns='NAME:.metadata.name,IPS:.spec.pool[*].ip,DISKS:.spec.pool[*].persistentDisk[*].path,KEPT_DISKS:.status.persistentDiskStatus[*].ip'
ac -n cpaas-system get dcsmachine -l cluster.x-k8s.io/cluster-name=<cluster-name> -o custom-columns='NAME:.metadata.name,POOL:.spec.ipHostPoolRef.name,IP:.status.networkConfig.ip'
ac -n cpaas-system get dcscluster <cluster-name> -o jsonpath='{.spec.controlPlaneLoadBalancer.type}{" "}{.spec.controlPlaneLoadBalancer.host}{"\n"}'
```

Check each pool in the `POOL` column that lists disks. A free entry is an IP address of the pool that no machine of the cluster uses and that is not the load balancer address when the type is `internal`.

| Result | Action |
| --- | --- |
| The pools have no free entry | Continue. |
| A free entry is not in `KEPT_DISKS` | Remove it from `spec.pool` with `ac -n cpaas-system edit dcsiphostnamepool <pool-name>`. Keep the entry of the internal load balancer address. |
| A free entry is in `KEPT_DISKS` | Contact technical support. Do not remove the entry. |

  </Tab>
  <Tab label="Bare Metal">

```bash
ac -n cpaas-system get baremetalmachines.infrastructure.cluster.x-k8s.io -l cluster.x-k8s.io/cluster-name=<cluster-name> \
  -o custom-columns='NAME:.metadata.name,INVENTORY:.status.machineInventoryRef.name'
ac -n cpaas-system get machineinventorypools.infrastructure.cluster.x-k8s.io \
  -o custom-columns='NAME:.metadata.name,CLUSTER:.spec.clusterName,TOTAL:.status.total,ALLOCATED:.status.allocated,HOSTS:.spec.machineInventories[*].name'
```

Continue when `TOTAL` equals `ALLOCATED` for each pool whose hosts declare data volumes; otherwise, remove the free hosts, the ones in `HOSTS` that no machine uses as its `INVENTORY`, from `spec.machineInventories` with `ac -n cpaas-system edit machineinventorypools.infrastructure.cluster.x-k8s.io <pool-name>`. Removing a free host from the pool does not change the host.

  </Tab>
  <Tab label="Huawei Cloud Stack">

### Check the Rollout Settings \{#rollout-settings}

**Applies to**: Alauda OS clusters. In DR, run it on each `global` cluster. Skip it for non-Alauda OS clusters.

On `global`; on the standby, run `unset KUBECONFIG` at the end of this check:

```bash
ac config use-cluster global        # on the standby, instead: export KUBECONFIG=<standby-kubeconfig>
ac whoami --show-server
KCP=$(ac -n cpaas-system get clusters.cluster.x-k8s.io <cluster-name> -o jsonpath='{.spec.controlPlaneRef.name}')
ac -n cpaas-system get kubeadmcontrolplane "${KCP}" -o jsonpath='replicas={.spec.replicas} maxSurge={.spec.rolloutStrategy.rollingUpdate.maxSurge}{"\n"}'
ac -n cpaas-system get machinedeployment -l cluster.x-k8s.io/cluster-name=<cluster-name> \
  -o custom-columns='NAME:.metadata.name,SURGE:.spec.strategy.rollingUpdate.maxSurge,UNAVAILABLE:.spec.strategy.rollingUpdate.maxUnavailable,BOOTSTRAP:.spec.template.spec.bootstrap.configRef.name'
```

On VMware vSphere, also read the machine config pools:

```bash
ac -n cpaas-system get vspheremachineconfigpool -o custom-columns='NAME:.metadata.name,READY:.status.conditions[?(@.type=="Ready")].status'
```

| Result | Action |
| --- | --- |
| `replicas` is 3 or more and `maxSurge` is `0`, and every MachineDeployment shows `SURGE` `0` and `UNAVAILABLE` `1`; every vSphere pool is `True` | Continue. |
| `replicas` is less than 3 | Contact technical support. |
| `replicas` is 3 or more and `maxSurge` is empty or not `0` | Run the `kubeadmcontrolplane` command below. |
| A MachineDeployment shows `SURGE` empty or not `0`, or `UNAVAILABLE` empty or not `1` | Run the `machinedeployment` command below for it. |
| A vSphere pool is not `True` | Contact technical support. |

```bash
ac -n cpaas-system patch kubeadmcontrolplane "${KCP}" --type merge \
  -p '{"spec":{"rolloutStrategy":{"type":"RollingUpdate","rollingUpdate":{"maxSurge":0}}}}'
ac -n cpaas-system patch machinedeployment <md-name> --type merge \
  -p '{"spec":{"strategy":{"type":"RollingUpdate","rollingUpdate":{"maxSurge":0,"maxUnavailable":1}}}}'
```

:::warning
On Bare Metal, a node pool with a single host has no worker while that host is reinstalled. Make sure its workloads can run on other nodes, or accept the interruption.
:::

## Run Preflight Checks \{#run-preflight}

**Applies to**: every `global` cluster. In DR, run it on each `global` cluster. Skip it for workload clusters.

From the `installer/` directory of the target Core Package, on each `global` cluster; on the standby, run `unset KUBECONFIG` afterwards:

```bash
ac config use-cluster global        # on the standby, instead: export KUBECONFIG=<standby-kubeconfig>
ac whoami --show-server
unset REGISTRY_USERNAME REGISTRY_PASSWORD
ac get productmanifests
bash upgrade.sh --preflight
```

| Result | Action |
| --- | --- |
| `Summary` shows `Passed` or `PassedWithWarnings` | Continue. |
| `ac get productmanifests` reports `the server doesn't have a resource type` | Continue without `bash upgrade.sh --preflight`. You run it in [Run the Final Preflight Check](./global/upgrade_global_cluster.mdx#final-preflight), after you deploy the Cluster Version Operator (CVO). |
| On the standby, `DRSplitUpgradeWindow` fails | Continue. |
| On a `global` cluster on Huawei DCS or Bare Metal, `InfraClusterVersionPreflight` reports `ProviderCapabilityNotDeclared` | Continue after [Check the Providers and Images of `global`](#check-global-cluster). |
| `ResourcePatchUpgradeable` fails | Run the exemption commands in [Resolve Preflight Blocks](#resolve-preflight-blocks). |
| `AdminAckRequired` fails | Run the acknowledgement commands in [Resolve Preflight Blocks](#resolve-preflight-blocks). |
| `VersionUpgradePath` fails | Follow [Resolve Other Preflight Blocks](./troubleshooting.mdx#resolve-other-preflight-blocks). Do not bypass the check with an explicit upgrade request. |
| Any other check fails | Follow [Resolve Other Preflight Blocks](./troubleshooting.mdx#resolve-other-preflight-blocks). If the check is not listed there, contact technical support. |

### Resolve Preflight Blocks \{#resolve-preflight-blocks}

For `ResourcePatchUpgradeable`, review each listed patch with technical support, then exempt it on the `global` cluster, with the target version as the value; do not use `*`. In DR, do it on each side; on the standby, run `unset KUBECONFIG` afterwards:

```bash
ac config use-cluster global        # on the standby, instead: export KUBECONFIG=<standby-kubeconfig>
ac whoami --show-server
ac get resourcepatches \
  -o custom-columns='NAME:.metadata.name,EXEMPT:.metadata.annotations.config\.cpaas\.io/exempt-for-ver'
ac get resourcepatches <rp-name> -o yaml
ac annotate resourcepatches <rp-name> config.cpaas.io/exempt-for-ver=<target-version> --overwrite
```

For `AdminAckRequired`, complete [Check Kubernetes 1.35 or Later Node Readiness](#kubernetes-135-node-readiness) on non-Alauda OS clusters. Then copy the key from `admin-gates`, record the acknowledgement, and run preflight again. In DR, do it on each side; on the standby, run `unset KUBECONFIG` afterwards:

```bash
ac config use-cluster global        # on the standby, instead: export KUBECONFIG=<standby-kubeconfig>
ac whoami --show-server
ac -n cpaas-system get configmap admin-gates -o yaml
ACK_KEY='<key-from-admin-gates>'
ac -n cpaas-system patch configmap admin-acks --type merge -p "{\"data\":{\"${ACK_KEY}\":\"true\"}}"
bash upgrade.sh --preflight
```
