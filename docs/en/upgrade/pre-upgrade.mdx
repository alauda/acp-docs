# Prepare for the Upgrade

Complete these steps before you upgrade. Most of them do not change running clusters; the exceptions are marked in [Items to Resolve Before the Upgrade](#lead-time). Prepare again for every upgrade, including a patch upgrade of the ACP version (Distribution Version) and an upgrade of `global` before every workload cluster has caught up.

In a DR environment, do every step that names `global` on both `global` clusters: the Alauda Container Platform Global Cluster Disaster Recovery plugin does not synchronize packages, images, or the objects these steps create. If your clusters run on more than one provider, complete the steps for each of them, including the provider of the `global` cluster.

## Items to Resolve Before the Upgrade \{#lead-time}

:::warning
Some items change running clusters, `global` included: migrating to pool-managed persistent disks and reinstalling a host replace nodes, and updating the node OS restarts nodes. Complete them before you upgrade the cluster.
:::

| Item | Applies to | Where to check | What to do |
| --- | --- | --- | --- |
| ACP version earlier than v4.3.2 | Alauda OS clusters | [Check Workload Cluster Compatibility](#check-compatibility) | Contact technical support. |
| Fewer than three control-plane nodes | Alauda OS clusters | [Check the Rollout Settings](#rollout-settings) | Contact technical support. |
| Worker node pools created from a machine template that references another VM template than the control plane | Huawei DCS | [Check the Disks and Hosts](#persistent-disk-layout) | Contact technical support. |
| `/var/cpaas` not on a pool-managed persistent disk | Huawei DCS, Huawei Cloud Stack | [Check the Disks and Hosts](#persistent-disk-layout) | [Migrate to Pool-Managed Persistent Disks](./persistent_disk_migration.mdx). The migration replaces nodes. |
| A free entry in an IP pool, machine config pool, or host pool whose nodes keep data on persistent disks or data volumes, for control-plane and worker nodes alike | Huawei DCS, Huawei Cloud Stack, Bare Metal | [Check the Disks and Hosts](#persistent-disk-layout) | Remove the free entries from the pool, as described there. A replaced node may take a free entry and come up without the data of the node it replaces. |
| `maxSurge` not `0`, or a vSphere pool not `Ready` | Alauda OS clusters | [Check the Rollout Settings](#rollout-settings) | Correct it as described there. |
| System state partition (`COS_STATE`) of 8 GiB, the default size when the host installation does not set it | Bare Metal hosts with Alauda OS M55 | [Check the Disks and Hosts](#persistent-disk-layout) | Reinstall the host with a larger partition. The reinstall replaces the node. |
| A recent successful etcd backup | Every cluster | [etcd Backup and Restore](../configure/backup/etcd.mdx) | Install Alauda Container Platform Cluster Enhancement on every cluster so that each cluster has a recent successful etcd backup before its upgrade. |
| Linux kernel 5.8 or later and cgroup v2 | Every node of non-Alauda OS clusters, workload clusters included | [Check Kubernetes 1.35 or Later Node Readiness](#kubernetes-135-node-readiness) | Update the node OS. The update restarts the node. |

## Prepare the Execution Host \{#execution-host}

Run every upgrade command from one execution host. The few steps that run on a node say so; return to the execution host after each of them.

- A Linux host (x86_64 or aarch64) outside every cluster that reaches the platform address, and the VIP and registry of each `global` cluster.
- `kubectl`, ACP CLI (`ac`), and Violet v4.2.13 or later (`violet version`).
- A platform account with the platform administrator role.
- For `upgrade.sh` and for the standby, a kubeconfig of each `global` cluster that points to its VIP: `<global-kubeconfig>`, and in DR `<primary-kubeconfig>` and `<standby-kubeconfig>`. On this page, `<global-kubeconfig>` means the primary in DR. For example, copy `/etc/kubernetes/admin.conf`, with any certificate files it references, from a control-plane node of the cluster, and set its `server` to the VIP if it points elsewhere.
- The extracted target Core Package, kept on this host until every cluster is upgraded.

:::info
On Alauda OS, do not use a node of any cluster as the execution host. The upgrade replaces the nodes, and files and sessions on a replaced node are lost.
:::

Log in to the platform with `ac` once, with `KUBECONFIG` unset, so that the session is saved in the default kubeconfig, `~/.kube/config`. After the login, `ac` commands run on `global`, the primary in DR. Before commands for a workload cluster, switch to it, and switch back afterwards. `ac whoami --show-server` prints the platform address followed by `/kubernetes/<cluster-name>/`:

```bash
ac login https://<platform-address> --name <session>
ac config use-cluster <cluster-name>
ac whoami --show-server
ac config use-cluster global
```

`upgrade.sh` uses `kubectl` with the kubeconfig in `KUBECONFIG`, and the standby is reached only with its own kubeconfig. For these blocks, run `export KUBECONFIG=<global-kubeconfig>` or `export KUBECONFIG=<standby-kubeconfig>` first, confirm that `ac whoami --show-server` prints the VIP of the intended cluster, and run `unset KUBECONFIG` at the end to return to the login session. For a single command on the standby, `ac --kubeconfig <standby-kubeconfig> …` does the same.

## Check the Upgrade Path \{#check-upgrade-path}

ACP 4.2, 4.3, and 4.4 are within the direct upgrade window of ACP 4.5. Not every source patch can reach every target patch: upgrade only to a target that the platform offers for the current version. Preflight checks this as `VersionUpgradePath` in [Run Preflight Checks](#run-preflight); do not bypass it with an explicit upgrade request. Request the version exactly as `ac adm upgrade` lists it, for example `4.5.0`. ACP 4.1 and earlier are outside the direct upgrade window: follow the intermediate upgrade chain that the platform offers, and check `VersionUpgradePath` at every step.

## Check Workload Cluster Compatibility \{#check-compatibility}

Before you upgrade `global`, every cluster registered on it must meet these rules. Upgrade a cluster that breaks one on the current `global` first.

- Its ACP version is within the direct upgrade window of the target. This includes the ACP components on imported and registered clusters.
- A cluster created by ACP runs a Kubernetes version within the target's Compatible Versions in the [Kubernetes Support Matrix](../overview/kubernetes-support-matrix.mdx). The Kubernetes version of an imported or registered third-party cluster is not covered by Compatible Versions and does not block the upgrade.

On `global`, list the ACP version, the Kubernetes version, and the infrastructure provider of every cluster. `DCSCluster`, `BaremetalCluster`, `HCSCluster`, and `VSphereCluster` mark the provider of an Alauda OS cluster. `UserProvisionedCluster` marks a cluster that does not run Alauda OS, and an imported cluster shows `<none>`:

```bash
ac config use-cluster global
ac whoami --show-server
ac -n cpaas-system get cvsh
ac -n cpaas-system get clusters.clusterregistry.k8s.io -o custom-columns='NAME:.metadata.name,KUBERNETES:.status.version'
ac -n cpaas-system get clusters.cluster.x-k8s.io -o custom-columns='NAME:.metadata.name,INFRASTRUCTURE:.spec.infrastructureRef.kind'
```

## Determine the Versions to Prepare \{#alauda-os-versions}

On non-Alauda OS clusters, Kubernetes is upgraded in place to the target version: skip to [Download the Packages](#download-packages).

On Alauda OS, ACP Core goes straight to the target, while Kubernetes moves one minor version at a time: a cluster passes through an intermediate Kubernetes version for each ACP minor version in between, taken from the latest patch release of that minor. Select the current version of each cluster, and prepare the versions of all paths together:

<AlaudaOsUpgradePath>
  The Kubernetes version and the etcd tag of every ACP version are listed in [Version Mapping](../overview/alauda_os_support_matrix.mdx#version-mapping).
</AlaudaOsUpgradePath>

For example, from v4.3.2 to v4.5.0 a cluster passes through the intermediate Kubernetes version v1.35.6-acp.9, taken from ACP v4.4.1, to Kubernetes v1.36.4-acp.3. From any v4.4.x to a v4.5.x version, there is no intermediate Kubernetes version. You use the ACP release of an intermediate Kubernetes version, such as v4.4.1, only to publish its images; you never request an upgrade to it.

:::info
Prepare every image in the Alauda OS variant that the cluster runs today. Bare Metal supports Alauda OS M55 and Alauda OS KU.
:::

## Download the Packages \{#download-packages}

<Steps>

### Download the Core Package and the Alauda OS Images \{#download-core-package}

From the <Term name="company" /> Customer Portal, download the Core Package of the target ACP version for your architecture, and extract it on the execution host. On Alauda OS, also download:

- The Core Package of the ACP release of each intermediate Kubernetes version. You use it only to publish its images.
- From the OS download page, the image of the target version and of each intermediate Kubernetes version, for the architecture and OS variant of your nodes: `qcow2` for Huawei DCS and Huawei Cloud Stack, `ova` for VMware vSphere, and the archive of an OCI image layout for Bare Metal.

### Download the Other Extension Packages \{#download-other-extensions}

Export the Extensions installed on `global` to `apps.yaml`. Then let the Customer Portal check the file and download the target-version packages of the installed Extensions, including the infrastructure providers and the Cluster Bootstrap Provider. Set `<arch>` to `amd64`, `arm64`, or `hybrid` to match the Core Package, and `<target-version>` to the target ACP version, such as `4.5.0`. Violet versions earlier than v4.2.13 fail here with `failed to get user info from platform server`.

```bash
read -rsp "Customer Portal token: " AC_TOKEN; printf '\n'
violet ac login --access-token="${AC_TOKEN}" --ac-url=<customer-portal-url>
read -rsp "Platform token: " PLATFORM_TOKEN; printf '\n'
violet list --platform-address "https://<platform-address>" --platform-token "${PLATFORM_TOKEN}" --output-file "./apps.yaml"
violet ac import-yaml --arch=<arch> --platformVersion=v<target-version> --path=./apps.yaml --download=true
```

In a DR environment, do the same for the standby, into its own file. The two `global` clusters can run different Extensions; for example, Global Cluster Disaster Recovery runs only on the standby:

```bash
read -rsp "Standby platform token: " STANDBY_TOKEN; printf '\n'
violet list --platform-address "https://<standby-vip>" --platform-token "${STANDBY_TOKEN}" --output-file "./standby-apps.yaml"
violet ac import-yaml --arch=<arch> --platformVersion=v<target-version> --path=./standby-apps.yaml --download=true
```

### Download the Upgrade Scenario for ACP 4.3 or Earlier \{#download-upgrade-scenario}

Only when the source ACP version is 4.3 or earlier. With the Customer Portal login of the previous step, download the `Upgrade from ACP 4.3 or earlier` scenario:

```bash
violet ac scenarios --arch=<arch> --platformVersion=v<target-version>
violet ac download-app --arch=<arch> --platformVersion=v<target-version> --scenario="Upgrade from ACP 4.3 or earlier"
```

</Steps>

## Publish the Packages \{#sync-upgrade-artifacts}

Publishing uploads images and packages; it does not change running applications. Run the steps from the `installer/` directory of the extracted target Core Package, against `global`, and complete them before you upgrade `global`.

<Steps>

### Stage the Upgrade Scenario Packages \{#stage-plugins}

Only when the source ACP version is 4.3 or earlier. Copy every package of [the upgrade scenario](#download-upgrade-scenario) into `plugins/`, then list the directory and compare it with the downloaded packages. Publishing checks the version of each package in `plugins/`, but not whether every package of the scenario is there.

```bash
cp <path-to-scenario-package> ./plugins/
ls -1 ./plugins/
```

### Publish Core and the Staged Packages \{#publish-core}

Read the registry type of `global`: the second value is `false` for the platform built-in Registry and `true` for an external registry. Every Aligned Extension installed on a cluster needs its target-version package before that cluster's upgrade; otherwise the upgrade stops until you publish it.

```bash
ac config use-cluster global
ac whoami --show-server
ac get productbase base -o jsonpath='{.spec.registry.address}{"\t"}{.spec.registry.external}{"\n"}'
```

<Tabs>
  <Tab label="Platform built-in Registry">

```bash
export KUBECONFIG=<global-kubeconfig>
ac whoami --show-server
bash upgrade.sh --only-sync-image
unset KUBECONFIG
```

  </Tab>
  <Tab label="External registry">

`upgrade.sh` does not upload to an external registry. Run both upload modes; both must succeed. Do not export the registry username or password: `bash upgrade.sh --preflight` stops while either is set in the environment.

```bash
REGISTRY_ADDRESS="<registry-address>"
REGISTRY_USERNAME="<registry-username>"
read -rsp "Registry password: " REGISTRY_PASSWORD; printf '\n'
bash res/upload.sh all "$REGISTRY_ADDRESS" "$REGISTRY_USERNAME" "$REGISTRY_PASSWORD"
bash res/upload.sh necessary "$REGISTRY_ADDRESS" "$REGISTRY_USERNAME" "$REGISTRY_PASSWORD"
unset REGISTRY_USERNAME REGISTRY_PASSWORD
```

  </Tab>
</Tabs>

### Publish the Other Extensions \{#publish-other-extensions}

Publish the packages downloaded for `apps.yaml` in [Download the Other Extension Packages](#download-other-extensions) with `violet push`. The packages for the standby follow in the next step.

| Packages | Publish to | When |
| --- | --- | --- |
| Cluster plugins, including the providers | `global` | Before the `global` upgrade |
| Operators | `global` and each workload cluster that runs the operator | Before the upgrade of each such cluster |

```bash
# A cluster plugin: the platform distributes it
violet push <cluster-plugin-package>.tgz --platform-address "https://<platform-address>" --platform-token "${PLATFORM_TOKEN}"
# An operator: global and every workload cluster that runs it
violet push <operator-package>.tgz --platform-address "https://<platform-address>" --platform-token "${PLATFORM_TOKEN}" \
  --clusters "global,<cluster-name-1>,<cluster-name-2>"
```

### Publish to the Standby global Cluster \{#publish-standby}

In a DR environment only. Select the standby for the rest of this step, and read its registry type, as on the primary:

```bash
export KUBECONFIG=<standby-kubeconfig>
ac whoami --show-server
ac get productbase base -o jsonpath='{.spec.registry.address}{"\t"}{.spec.registry.external}{"\n"}'
```

<Tabs>
  <Tab label="Platform built-in Registry">

Publish the images to the registry of the standby: run the command from the `installer/` directory of the target Core Package, and again from that of each intermediate Core Package. The script uses the registry of the cluster in `KUBECONFIG`.

```bash
bash upgrade.sh --only-sync-image
```

Then push the packages downloaded for `standby-apps.yaml` in [Download the Other Extension Packages](#download-other-extensions). Set `<registry-port>` to the port of the registry address printed above. Without `--platform-address` and `--dest-repo`, the packages go to the primary.

```bash
STANDBY_REGISTRY_USER=$(ac -n cpaas-system get secret registry-admin -o jsonpath='{.data.username}' | base64 -d)
STANDBY_REGISTRY_PASSWORD=$(ac -n cpaas-system get secret registry-admin -o jsonpath='{.data.password}' | base64 -d)
read -rsp "Standby platform token: " STANDBY_TOKEN; printf '\n'
violet push <package>.tgz --platform-address "https://<standby-vip>" --platform-token "${STANDBY_TOKEN}" \
  --dest-repo "<standby-vip>:<registry-port>" --username "${STANDBY_REGISTRY_USER}" --password "${STANDBY_REGISTRY_PASSWORD}"
# Repeat violet push for each package, then:
unset STANDBY_REGISTRY_USER STANDBY_REGISTRY_PASSWORD STANDBY_TOKEN
```

  </Tab>
  <Tab label="External registry">

`upgrade.sh` does not upload to an external registry. When the standby uses the same registry endpoint as the primary, the images are already there. When it uses its own endpoint, run the external registry commands of [Publish Core and the Staged Packages](#publish-core) and [Publish the Intermediate Core Images](#sync-intermediate-images) again, with the address and credentials of that endpoint.

Then push the packages downloaded for `standby-apps.yaml` with `violet push --platform-address "https://<standby-vip>"`. Confirm its registry options for an external registry with technical support before you upgrade the standby.

  </Tab>
</Tabs>

On the standby, confirm that each Cluster Plugin you pushed lists its target version, for example Global Cluster Disaster Recovery, then return to the login session:

```bash
ac get moduleconfigs -l cpaas.io/module-name=etcd-sync
unset KUBECONFIG
```

</Steps>

## Stage the Alauda OS Images \{#stage-alauda-os-images}

On non-Alauda OS clusters, skip this section.

Stage the image of the target version and of every intermediate Kubernetes version for each provider in use. The commands that the Huawei DCS and Bare Metal tabs generate run on `global`; in DR, run them on both `global` clusters, on the standby after `export KUBECONFIG=<standby-kubeconfig>`, and run `unset KUBECONFIG` afterwards:

```bash
ac config use-cluster global
ac whoami --show-server
```

<Tabs>
  <Tab label="Huawei DCS">

Upload the `qcow2` image of each version to every DCS site that your clusters use, and register it as a VM template with the same name on every site. Then generate the VM template ConfigMaps and apply them on `global`:

<DcsVmTemplateConfigMap mode="path">
  Replace `<os>` with the OS of the VM templates, such as `m55`, `ko`, or `ku`, and take the ACP version, Kubernetes version, and etcd tag of each ConfigMap from [Version Mapping](../overview/alauda_os_support_matrix.mdx#version-mapping). Repeat the intermediate ConfigMap for each intermediate Kubernetes version, and omit it when there is none.
</DcsVmTemplateConfigMap>

  </Tab>
  <Tab label="Bare Metal">

On a host that has containerd and reaches the registry of `global`, such as a `global` control-plane node, import the archive of each version and push the images it holds; this push is the only step of this tab on a node, so return to the execution host afterwards. For Alauda OS M55, push both `baremetal-base-image` and `baremetal-base-image-iso`. For Alauda OS KU, push the OS image that the list command prints to the repository used in the command below, which the catalog command also uses. The `admin` password is in the `cpaas-system/registry-admin` Secret of `global`. In DR, push to the registry of both `global` clusters.

{/* lint ignore no-legacy-os-names */}

```bash
ctr -n bare-metal-os images import --all-platforms --no-unpack <bare-metal-os-archive>
ctr -n bare-metal-os images ls -q
read -rsp "Registry password: " REGISTRY_PASSWORD; printf '\n'
# Alauda OS M55
for repo in baremetal-base-image baremetal-base-image-iso; do
  ctr -n bare-metal-os images push --local --skip-verify -u "<registry-username>:${REGISTRY_PASSWORD}" \
    "<registry-address>/tkestack/${repo}:<os-image-tag>" "${repo}:<os-image-tag>"
done
# Alauda OS KU
ctr -n bare-metal-os images push --local --skip-verify -u "<registry-username>:${REGISTRY_PASSWORD}" \
  "<registry-address>/tkestack/kubeos-rootfs:<os-image-tag>" "<listed-os-image>"
```

## Prepare the Clusters \{#prepare-alauda-os-clusters}

On non-Alauda OS clusters, only the last step applies: go to [Check Kubernetes 1.35 or Later Node Readiness](#kubernetes-135-node-readiness).

Run the other steps for each Alauda OS cluster, `global` included. Unless a step says otherwise, run the commands on `global` with `<cluster-name>` set to the cluster: the Cluster API objects of every cluster are in `cpaas-system` there. In DR, check workload clusters on the primary, and each `global` cluster on its own side. The checks only read; make the fixes they lead to before you upgrade the cluster, as listed in [Items to Resolve Before the Upgrade](#lead-time).

```bash
ac config use-cluster global
ac whoami --show-server
```

<Steps>

### Check the Disks and Hosts \{#persistent-disk-layout}

:::warning
Data on a node's own disks, such as `hostPath` volumes and local PersistentVolumes, is not kept when the node is replaced, unless it is on a pool-managed persistent disk (Bare Metal: a declared data volume). Move it to CSI storage, or onto a pool-managed persistent disk, before the upgrade. On Huawei Cloud Stack and VMware vSphere, the platform does not check for it.
:::

<Tabs>
  <Tab label="Huawei DCS">

`/var/cpaas` must be a `persistentDisk` of the IP pool, and every machine must use the same VM template. Continue when the first command lists no `/var/cpaas` and the second shows one VM template. Otherwise, migrate the disks first, as listed in [Items to Resolve Before the Upgrade](#lead-time); for different VM templates, contact technical support.

```bash
ac -n cpaas-system get dcsmachinetemplate -o custom-columns='NAME:.metadata.name,TEMPLATE_DISKS:.spec.template.spec.vmConfig.dcsMachineDiskSpec[*].path'
ac -n cpaas-system get dcsmachine -l cluster.x-k8s.io/cluster-name=<cluster-name> -o custom-columns='NAME:.metadata.name,VM_TEMPLATE:.spec.vmTemplateName'
```

A replaced node gets the IP address, hostname, and persistent disks of the node it replaces only when its IP pool has no free entry, for control-plane and worker pools alike. List the pools with their disks, and the IP addresses that the machines of the cluster use:

```bash
ac -n cpaas-system get dcsiphostnamepool \
  -o custom-columns='NAME:.metadata.name,IPS:.spec.pool[*].ip,DISKS:.spec.pool[*].persistentDisk[*].path,KEPT_DISKS:.status.persistentDiskStatus[*].ip'
ac -n cpaas-system get dcsmachine -l cluster.x-k8s.io/cluster-name=<cluster-name> -o custom-columns='NAME:.metadata.name,POOL:.spec.ipHostPoolRef.name,IP:.status.networkConfig.ip'
```

Continue when every IP address of each pool that lists disks is used by a machine of the cluster, or is the address of its internal control-plane load balancer. Otherwise, remove the free entries from `spec.pool` before the upgrade, with `ac -n cpaas-system edit dcsiphostnamepool <pool-name>`. Keep the entry of the internal control-plane load balancer VIP. An address in `KEPT_DISKS` that no machine uses belonged to a node before: removing its entry also deletes the disks kept for it.

  </Tab>
  <Tab label="Bare Metal">

Every inventory with a storage declaration must show `STORAGE` `Prepared`, or `Active` once it is allocated. Do not add a storage declaration to a host installed before managed storage was available. Record which inventory backs each machine and the filesystem UUIDs:

```bash
ac -n cpaas-system get baremetalmachines.infrastructure.cluster.x-k8s.io -l cluster.x-k8s.io/cluster-name=<cluster-name> \
  -o custom-columns='NAME:.metadata.name,INVENTORY:.status.machineInventoryRef.name'
ac -n cpaas-system get machineinventories.elemental.cattle.io \
  -o custom-columns='NAME:.metadata.name,STORAGE:.status.storage.phase,UUIDS:.status.storage.appliedVolumes[*].filesystemUUID'
```

A replaced node comes back on the host of the node it replaces, with that host's data volumes, only when its host pool has no free host, for control-plane and worker pools alike. For each pool whose hosts declare data volumes, continue when `TOTAL` equals `ALLOCATED`:

```bash
ac -n cpaas-system get machineinventorypools.infrastructure.cluster.x-k8s.io \
  -o custom-columns='NAME:.metadata.name,CLUSTER:.spec.clusterName,TOTAL:.status.total,ALLOCATED:.status.allocated,HOSTS:.spec.machineInventories[*].name'
```

Otherwise, remove the free hosts, the ones in `HOSTS` that no machine uses as its `INVENTORY`, from `spec.machineInventories` before the upgrade, with `ac -n cpaas-system edit machineinventorypools.infrastructure.cluster.x-k8s.io <pool-name>`. Removing a free host from the pool does not change the host.

On every Alauda OS M55 host in the pools of the cluster, spare hosts included, `COS_STATE` needs at least 4 GiB `Free (estimated)` and no snapshot left from a failed upgrade; if not, see [Free Space on COS_STATE](./troubleshooting.mdx#check-cos-state-free-space). If `COS_STATE` is 8 GiB, reinstall the host with a larger partition before the upgrade. On Alauda OS KU hosts, the upgrade uses `/persist` instead; ask technical support how much free space it needs. Every host must also reach the platform registry. The platform does not check these items. On each M55 host:

```bash
lsblk -o NAME,SIZE,LABEL | grep COS_STATE
btrfs filesystem usage -h /
snapper --no-dbus list
```

  </Tab>
  <Tab label="Huawei Cloud Stack">

`/var/cpaas` must be in `persistentDisks` of the `HCSMachineConfigPool`. Continue when no machine template lists it in `dataVolumes`; otherwise, migrate first, as listed in [Items to Resolve Before the Upgrade](#lead-time):

```bash
ac -n cpaas-system get hcsmachinetemplate -o custom-columns='NAME:.metadata.name,DATA_VOLUMES:.spec.template.spec.dataVolumes[*].mountPath'
```

A replaced node gets the hostname, IP address, and persistent disks of the node it replaces only when its `HCSMachineConfigPool` has no free configuration, for control-plane and worker pools alike. For each pool that lists disks, continue when `AVAILABLE` is empty or `0`:

```bash
ac -n cpaas-system get hcsmachineconfigpool \
  -o custom-columns='NAME:.metadata.name,TOTAL:.status.totalCount,AVAILABLE:.status.availableCount,DISKS:.spec.configs[*].persistentDisks[*].mountPath,HOSTNAMES:.spec.configs[*].hostname,USED:.status.usedConfigs[*].hostname'
```

Otherwise, remove the free configurations, the ones in `HOSTNAMES` that are not in `USED`, from `spec.configs` before the upgrade, with `ac -n cpaas-system edit hcsmachineconfigpool <pool-name>`. A configuration that was used before cannot be removed; contact technical support for it.

  </Tab>
  <Tab label="VMware vSphere">

No action is needed on this provider: a replaced node takes over the released slot of its machine config pool. Do not restructure the disk lists of the machine config pools as part of an upgrade.

  </Tab>
</Tabs>

### Check the Rollout Settings \{#rollout-settings}

Nodes are replaced one at a time, which needs `maxSurge: 0` on the `KubeadmControlPlane` and on every `MachineDeployment`. Read the current values; an empty value is unset, which counts as `1`:

```bash
KCP=$(ac -n cpaas-system get clusters.cluster.x-k8s.io <cluster-name> -o jsonpath='{.spec.controlPlaneRef.name}')
ac -n cpaas-system get kubeadmcontrolplane "${KCP}" -o jsonpath='replicas={.spec.replicas} maxSurge={.spec.rolloutStrategy.rollingUpdate.maxSurge}{"\n"}'
ac -n cpaas-system get machinedeployment -l cluster.x-k8s.io/cluster-name=<cluster-name> \
  -o custom-columns='NAME:.metadata.name,SURGE:.spec.strategy.rollingUpdate.maxSurge,UNAVAILABLE:.spec.strategy.rollingUpdate.maxUnavailable,BOOTSTRAP:.spec.template.spec.bootstrap.configRef.name'
```

Continue when `replicas` is 3 or more and every `maxSurge` is `0`. With fewer than three control-plane nodes, contact technical support. Correct `maxSurge` before the upgrade:

```bash
ac -n cpaas-system patch kubeadmcontrolplane "${KCP}" --type merge \
  -p '{"spec":{"rolloutStrategy":{"type":"RollingUpdate","rollingUpdate":{"maxSurge":0}}}}'
ac -n cpaas-system patch machinedeployment <md-name> --type merge \
  -p '{"spec":{"strategy":{"type":"RollingUpdate","rollingUpdate":{"maxSurge":0,"maxUnavailable":1}}}}'
```

On Bare Metal, a node pool with a single host has no worker while that host is reinstalled; make sure its workloads can run on other nodes, or accept the interruption. On Huawei Cloud Stack, the platform does not check these values; set them anyway, because with a larger `maxSurge` every additional machine needs a free hostname and IP address in the `HCSMachineConfigPool`.

On VMware vSphere, the platform does not check the cluster before the upgrade, and the admission webhook rejects the version change of a control plane whose `maxSurge` is not `0`. Also check that every machine config pool is ready. If a pool is not `True`, read its `MembersValid`, `MembersUnique`, and `PersistentDisksReady` conditions and correct the pool:

```bash
ac -n cpaas-system get vspheremachineconfigpool -o custom-columns='NAME:.metadata.name,READY:.status.conditions[?(@.type=="Ready")].status'
```

### Check the Kubelet Patch File \{#kubernetes-1-35-kubelet-patch}

From Kubernetes 1.35, the bootstrap configuration of every new node needs the kubelet patch file `/etc/kubernetes/patches/kubeletconfiguration0+strategic.json`. With `KCP` from the previous step, print it from the control plane and from each `BOOTSTRAP` template listed there:

```bash
ac -n cpaas-system get kubeadmcontrolplane "${KCP}" -o jsonpath='{range .spec.kubeadmConfigSpec.files[?(@.path=="/etc/kubernetes/patches/kubeletconfiguration0+strategic.json")]}{.content}{.contentFrom.secret.name}{"\n"}{end}'
ac -n cpaas-system get kubeadmconfigtemplate <bootstrap-template> -o jsonpath='{range .spec.template.spec.files[?(@.path=="/etc/kubernetes/patches/kubeletconfiguration0+strategic.json")]}{.content}{.contentFrom.secret.name}{"\n"}{end}'
```

Continue when each command prints the file content, or the name of a Secret in `cpaas-system` that holds it. If a file is missing, contact technical support. On Kubernetes 1.35 or later, the file must contain `"imagePullCredentialsVerificationPolicy": "NeverVerify"`; do not add it for Kubernetes 1.34 or earlier. On Huawei DCS and Bare Metal, the platform adds the setting when the upgrade reaches 1.35. On Huawei Cloud Stack and VMware vSphere, add it in the same edit that moves the cluster to 1.35; on a cluster that already runs 1.35 or later, confirm that it is there.

### Check Kubernetes 1.35 or Later Node Readiness \{#kubernetes-135-node-readiness}

On non-Alauda OS clusters only; Alauda OS nodes are replaced with the target image during the upgrade. Kubernetes 1.35 and later need Linux kernel 5.8 or later and cgroup v2, and the preflight of a `global` cluster on ACP 4.4 or earlier asks you to confirm it. uname -r

## Check Module Stability \{#module-stability-self-check}

Preflight blocks the upgrade while a Core or Aligned module of the cluster is installing, upgrading, or failed, for example during a separate plugin upgrade. On `global`, for each cluster, confirm that every module is `Running` and that `deployStatus` is not `Upgrading`, `DeployFailed`, or `UpgradeFailed`; in DR, also check `global` on the standby, with `--kubeconfig <standby-kubeconfig>` after `ac`. Wait for a module that is still upgrading; resolve a module that is `Failed` or `Blocked` before you upgrade the cluster.

```bash
ac config use-cluster global
ac whoami --show-server
ac get moduleinfo -l cpaas.io/cluster-name=<cluster-name> \
  -o custom-columns='MODULE:.metadata.labels.cpaas\.io/module-name,CURRENT:.status.version,TARGET:.spec.version,PHASE:.status.phase'
ac get clustermodule <cluster-name> -o jsonpath='{.status.base.deployStatus}{"\n"}'
```

On a non-Alauda OS `global` cluster that uses the platform built-in Registry, also confirm on each control-plane node that `/cpaas/minio` has at least 120 GB free, with `df -h /cpaas/minio`.

## Check DR Synchronization \{#check-dr-sync}

In a DR environment only. Log in to a control-plane node of the standby `global` cluster, where the Service address is reachable, run the check there, and then return to the execution host:

```bash
export KUBECONFIG=/etc/kubernetes/admin.conf
mirror_svc=$(kubectl get svc -n cpaas-system etcd-sync-monitor -o jsonpath='{.spec.clusterIP}')
if [[ $mirror_svc =~ ^[0-9a-fA-F:]+$ ]]; then mirror_host="[$mirror_svc]"; else mirror_host="$mirror_svc"; fi
curl -g "http://${mirror_host}/check"
```

Continue when the output shows `localMissedKeys [0]` and `localSurplusKeys [0]`. If it reports `check too frequent`, wait one minute and run it again. Otherwise, restore synchronization before you upgrade; see [Global Cluster Disaster Recovery Does Not Synchronize](./troubleshooting.mdx#dr-sync-diagnostics).

## Run Preflight Checks \{#run-preflight}

Run preflight on `global` from the `installer/` directory of the target Core Package; in DR, repeat the block on the standby with `<standby-kubeconfig>`. If `ac get productmanifests` reports `the server doesn't have a resource type`, the cluster has never been upgraded with the Cluster Version Operator (CVO): preflight runs during the upgrade of `global`, after you deploy CVO.

```bash
export KUBECONFIG=<global-kubeconfig>
ac whoami --show-server
unset REGISTRY_USERNAME REGISTRY_PASSWORD        # preflight stops while either is set
ac get productmanifests
bash upgrade.sh --preflight
unset KUBECONFIG
```

Continue when the summary is `Passed` or `PassedWithWarnings`. Workload clusters are checked later, after `global` runs the target version; in DR, after both `global` clusters do.

### Resolve Preflight Blocks \{#resolve-preflight-blocks}

For blocks not described here, see [Handle Preflight Blocks](./troubleshooting.mdx#handle-preflight-blocks-when-needed). `ResourcePatchUpgradeable` lists customizations that need an exemption. Review each patch with technical support, then exempt it on the cluster that is upgraded, with the target version as the value; do not use `*`. The value compares the major and minor version only, so the exemption covers every patch of the target minor version. In DR, do it on each side; on the standby, add `--kubeconfig <standby-kubeconfig>` after `ac`. Requests made with `ac adm upgrade` do not add the exemption:

```bash
ac get resourcepatches \
  -o custom-columns='NAME:.metadata.name,EXEMPT:.metadata.annotations.config\.cpaas\.io/exempt-for-ver'
ac get resourcepatches <rp-name> -o yaml
ac annotate resourcepatches <rp-name> config.cpaas.io/exempt-for-ver=<target-version> --overwrite
```

`AdminAckRequired` asks for an administrator acknowledgement on every `global` cluster upgraded from v4.4 or earlier, on each side in DR. Complete [Check Kubernetes 1.35 or Later Node Readiness](#kubernetes-135-node-readiness), which has nothing to check on Alauda OS, then copy the key from `admin-gates`, record it, and run preflight again. On the standby, use `<standby-kubeconfig>`:

```bash
export KUBECONFIG=<global-kubeconfig>
ac whoami --show-server
ac -n cpaas-system get configmap admin-gates -o yaml
ACK_KEY='<key-from-admin-gates>'
ac -n cpaas-system patch configmap admin-acks --type merge -p "{\"data\":{\"${ACK_KEY}\":\"true\"}}"
bash upgrade.sh --preflight
unset KUBECONFIG
```
