# Prepare for the Upgrade

Start at least two weeks before the first maintenance window: uploads are slow, and problems found now can be fixed before the window. Most steps do not change running clusters; the exceptions are marked in [Items That Need Lead Time](#lead-time). Prepare again for every upgrade, including a patch upgrade of the ACP version (Distribution Version) and an upgrade of `global` before every workload cluster has caught up.

In a DR environment, do every step that names `global` on both `global` clusters: the Alauda Container Platform Global Cluster Disaster Recovery plugin does not synchronize packages, images, or the objects these steps create. If your clusters use more than one infrastructure provider, complete the tab of every provider in use, including the one that `global` runs on.

The commands on this page use `4.5.0` as the target ACP version. For another target, such as a later patch, use that version in every command, including `--platformVersion=v<version>`.

## Items That Need Lead Time \{#lead-time}

:::warning
Items marked **Change window** change running clusters, `global` included: the persistent disk migration and a host reinstall replace nodes, and a node OS update restarts nodes. Schedule each in its own change window before the upgrade window of the cluster; for `global`, before the first window.
:::

| Item | Applies to | Where to check | What to do |
| --- | --- | --- | --- |
| ACP version earlier than v4.3.2 | Alauda OS clusters | [Check Workload Cluster Compatibility](#check-compatibility) | Contact technical support. |
| Fewer than three control-plane nodes | Alauda OS clusters | [Check the Rollout Settings](#rollout-settings) | Contact technical support. |
| Control plane and node pools on different VM templates | Huawei DCS | [Check the Disks and Hosts](#persistent-disk-layout) | Contact technical support. |
| Kube-OVN not in `geneve` overlay mode with IPv4 | Huawei DCS, Huawei Cloud Stack, and VMware vSphere clusters upgraded from before v4.5 | [Check Kube-OVN and CoreDNS Takeover](#network-addon-takeover) | Contact technical support. |
| Customized CoreDNS Corefile | Alauda OS clusters upgraded from before v4.5 | [Check Kube-OVN and CoreDNS Takeover](#network-addon-takeover) | **Change window**: resolve it with technical support. The takeover continues only after the `kube-system/coredns` Corefile is back to the default. |
| `/var/cpaas` not on a pool-managed persistent disk | Huawei DCS, Huawei Cloud Stack | [Check the Disks and Hosts](#persistent-disk-layout) | **Change window**: [Migrate to Pool-Managed Persistent Disks](./persistent_disk_migration.mdx). |
| `maxSurge` not `0`, or a vSphere pool not `Ready` | Alauda OS clusters | [Check the Rollout Settings](#rollout-settings) | **Change window**: correct it as described there. |
| System state partition (`COS_STATE`) of 8 GiB | Bare Metal hosts with Alauda OS M55 | [Check the Disks and Hosts](#persistent-disk-layout) | **Change window**: reinstall the host. |
| Infrastructure provider of the IaaS that `global` runs on, or the Cluster Bootstrap Provider, not installed on `global` | Alauda OS `global` clusters, both clusters in DR | [Check the global Cluster Yourself](#check-global-cluster) | **Change window**: install them on `global`, as described in [Install the Infrastructure Provider](../workload_clusters/alauda_os/prepare/index.mdx#install-the-provider). |
| x86_64 CPUs without the `x86-64-v2` baseline | Alauda OS x86_64 nodes | Each host or hypervisor | The target Alauda OS images require this baseline. If a CPU lacks it, contact technical support. |
| A recent successful etcd backup | Every cluster | [etcd Backup and Restore](../configure/backup/etcd.mdx) | Install Alauda Container Platform Cluster Enhancement on every cluster so that each cluster has a recent successful etcd backup before its upgrade. |
| Linux kernel 5.8 or later and cgroup v2 | Every node of non-Alauda OS clusters, workload clusters included | [Check Kubernetes 1.35 or Later Node Readiness](#kubernetes-135-node-readiness) | **Change window**: update the node OS. It must be in place before the window of the cluster; for `global`, before the first window. |
| Source ACP version earlier than 4.3, with Alauda DevOps v3, Alauda AI Essentials, Alauda Hyperflux, or Alauda Container Platform Data Services Essentials | Clusters that run them | [Check Agnostic Extension Compatibility](#check-agnostic-compatibility) | Plan to upgrade these Extensions in the same window as the cluster; otherwise their pages can fail to open. |

## Prepare the Execution Host \{#execution-host}

Run every upgrade command from one execution host. The few steps that run on a node say so; return to the execution host after each of them.

- A Linux host (x86_64 or aarch64) outside every cluster that reaches the VIP, the registry, and the platform address of each `global` cluster.
- `kubectl`, ACP CLI (`ac`), and Violet v4.2.13 or later (`violet version`).
- One kubeconfig per `global` cluster, pointing to the VIP of that cluster: `<global-kubeconfig>`, and in DR `<primary-kubeconfig>` and `<standby-kubeconfig>`. For example, copy `/etc/kubernetes/admin.conf`, with any certificate files it references, from a control-plane node of the cluster, and set its `server` to the VIP if it points elsewhere. On this page, `<global-kubeconfig>` means the primary in DR. `ac`, `kubectl`, and `upgrade.sh` use the exported `KUBECONFIG`.
- The extracted target Core Package, kept on this host until the last window ends.

:::info
On Alauda OS, do not use a node of any cluster as the execution host. The upgrade replaces the nodes, and files and sessions on a replaced node are lost.
:::

Before each command block that targets a `global` cluster, select it and confirm that the printed address is its VIP. `KUBECONFIG` stays on `global`; commands for a workload cluster pass its kubeconfig with `kubectl --kubeconfig=<cluster-name>.kubeconfig`. Save the kubeconfig of an Alauda OS workload cluster from `global`; for a non-Alauda OS workload cluster, see [Access a Cluster with KubeConfig](../workload_clusters/how_to/access-cluster-with-kubeconfig.mdx).

```bash
export KUBECONFIG=<global-kubeconfig>
kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}{"\n"}'
kubectl -n cpaas-system get secret <cluster-name>-kubeconfig -o jsonpath='{.data.value}' | base64 -d > <cluster-name>.kubeconfig
```

## Check the Upgrade Path \{#check-upgrade-path}

ACP 4.2, 4.3, and 4.4 are within the direct upgrade window of ACP 4.5. Not every source patch can reach every target patch: upgrade only to a target that the platform offers for the current version. Preflight checks this as `VersionUpgradePath` in [Run Preflight Checks](#run-preflight); do not bypass it with an explicit upgrade request. In the window, request the version exactly as `ac adm upgrade` lists it, for example `4.5.0`. ACP 4.1 and earlier are outside the direct upgrade window: follow the intermediate upgrade chain that the platform offers, and check `VersionUpgradePath` at every step.

## Check Workload Cluster Compatibility \{#check-compatibility}

Before you upgrade `global`, every cluster registered on it must meet these rules. Upgrade a cluster that breaks one on the current `global` first.

- Its ACP version is within the direct upgrade window of the target. This includes the ACP components on imported and registered clusters.
- A cluster created by ACP runs a Kubernetes version within the target's Compatible Versions in the [Kubernetes Support Matrix](../overview/kubernetes-support-matrix.mdx). The Kubernetes version of an imported or registered third-party cluster is not covered by Compatible Versions and does not block the upgrade.

On `global`, list the ACP version, the Kubernetes version, and the infrastructure provider of every cluster. `DCSCluster`, `BaremetalCluster`, `HCSCluster`, and `VSphereCluster` mark the provider of an Alauda OS cluster:

```bash
export KUBECONFIG=<global-kubeconfig>
kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}{"\n"}'
kubectl -n cpaas-system get cvsh
kubectl -n cpaas-system get clusters.clusterregistry.k8s.io -o custom-columns='NAME:.metadata.name,KUBERNETES:.status.version'
kubectl -n cpaas-system get clusters.cluster.x-k8s.io -o custom-columns='NAME:.metadata.name,INFRASTRUCTURE:.spec.infrastructureRef.kind'
```

## Determine the Versions to Prepare \{#alauda-os-versions}

On non-Alauda OS clusters, Kubernetes is upgraded in place to the target version: skip to [Download the Packages](#download-packages).

On Alauda OS, ACP Core goes straight to the target, while Kubernetes moves one minor version at a time: a cluster passes through an intermediate Kubernetes version for each ACP minor version in between, taken from the latest patch release of that minor. Select the current version of each cluster, and prepare the versions of all paths together:

<AlaudaOsUpgradePath>
  The Kubernetes version and the etcd tag of every ACP version are listed in [Version Mapping](../overview/alauda_os_support_matrix.mdx#version-mapping).
</AlaudaOsUpgradePath>

For example, from v4.3.2 to v4.5.0 a cluster passes through the intermediate Kubernetes version v1.35.6-acp.9, taken from ACP v4.4.1, to Kubernetes v1.36.4-acp.3. From any v4.4.x to a v4.5.x version, there is no intermediate Kubernetes version. You use the ACP release of an intermediate Kubernetes version, such as v4.4.1, only to publish its images; you never request an upgrade to it.

:::info
Prepare every image in the Alauda OS variant that the cluster runs today. Bare Metal supports Alauda OS M55 and Alauda OS KU.
:::

## Download the Packages \{#download-packages}

<Steps>

### Download the Core Package and the Alauda OS Images \{#download-core-package}

From the <Term name="company" /> Customer Portal, download the ACP 4.5 Core Package for your architecture, and extract it on the execution host. On Alauda OS, also download:

- The Core Package of the ACP release of each intermediate Kubernetes version. You use it only to publish its images.
- From the OS download page, the image of the target version and of each intermediate Kubernetes version, for the architecture and OS variant of your nodes: `qcow2` for Huawei DCS and Huawei Cloud Stack, `ova` for VMware vSphere, and the archive of an OCI image layout for Bare Metal.

### Download ACP Upgrade to v4.5 \{#download-acp-upgrade-to-v45}

**ACP Upgrade to v4.5** holds the target packages of eleven Extensions (Operators and Cluster Plugins) with the `Aligned` lifecycle. Log in to the Customer Portal with Violet and download it, with `<arch>` set to `amd64`, `arm64`, or `hybrid` to match the Core Package. As an alternative, select the same scenario in **Marketplace > Batch Download** of the Customer Portal.

```bash
read -rsp "Customer Portal token: " AC_TOKEN; printf '\n'
violet ac login --access-token="${AC_TOKEN}" --ac-url=<customer-portal-url>
violet ac scenarios --arch=<arch> --platformVersion=v4.5.0
violet ac download-app --arch=<arch> --platformVersion=v4.5.0 --scenario="ACP Upgrade to v4.5"
```

Files are named `<package-name>.<arch>.<version>.tgz`. Confirm that you have all eleven:

| Application | Package | Application | Package |
| --- | --- | --- | --- |
| Alauda Container Platform Web Console | `console` | Alauda Container Platform Essentials | `container-platform` |
| Alauda Container Platform Web Console Central | `console-central` | Alauda Container Platform Cluster Essentials | `acp-business` |
| Alauda Container Platform Marketplace Web Console | `console-marketplace` | Alauda Container Platform GatewayAPI Plugin | `gatewayapi-plugin` |
| Alauda Container Platform Application Catalog | `application-catalog` | Alauda Container Platform Basic Monitoring | `prometheus` |
| Alauda Container Platform Observability Essentials | `aiops-base` | Alauda Language Pack for Chinese | `i18n-zh` |
| Alauda Container Platform Networking E1 | `calico` | | |

### Download the Other Extension Packages \{#download-other-extensions}

Export the installed Extensions to `apps.yaml`. Then, with the Customer Portal login of the previous step, let the Customer Portal check the file and download the target-version packages of the other installed Aligned Extensions, including the infrastructure providers and the Cluster Bootstrap Provider. You already have the eleven applications above. Violet versions earlier than v4.2.13 fail here with `failed to get user info from platform server`.

```bash
read -rsp "Platform token: " PLATFORM_TOKEN; printf '\n'
violet list --platform-address "https://<platform-address>" --platform-token "${PLATFORM_TOKEN}" --output-file "./apps.yaml"
violet ac import-yaml --arch=<arch> --platformVersion=v4.5.0 --path=./apps.yaml --download=true
```

### Check Agnostic Extension Compatibility \{#check-agnostic-compatibility}

For each Extension (Operator or Cluster Plugin) with the `Agnostic` lifecycle in use, confirm in the Customer Portal that a version compatible with the target ACP version exists, and download it; in a DR environment, include the ones installed on the standby. Agnostic Extensions are upgraded separately, following each Extension's own documentation. If the source ACP version is earlier than 4.3, plan to upgrade Alauda DevOps v3, Alauda AI Essentials, Alauda Hyperflux, and Alauda Container Platform Data Services Essentials in the same window as the cluster that runs them.

### Download the Global Cluster Disaster Recovery Package \{#download-dr-package}

In a DR environment only: download the target-version package of Alauda Container Platform Global Cluster Disaster Recovery (`etcd-sync`) separately. It is not part of **ACP Upgrade to v4.5**, and it is installed only on the standby, so `apps.yaml` does not list it.

</Steps>

## Publish the Packages \{#sync-upgrade-artifacts}

Publishing uploads images and packages; it does not change running applications. Run the steps from the `installer/` directory of the extracted target Core Package, against `global`, and do not open the maintenance window until publishing is complete.

<Steps>

### Stage the ACP Upgrade to v4.5 Packages \{#stage-plugins}

Copy each of the eleven packages into `plugins/`, then list the directory:

```bash
cp <path-to-upgrade-package> ./plugins/
ls -1 ./plugins/
```

:::info
Publishing checks the version of each package in `plugins/`, but not whether all eleven are there. Compare the list with [Download ACP Upgrade to v4.5](#download-acp-upgrade-to-v45).
:::

### Publish Core and the Staged Packages \{#publish-core}

Select `global` and read the registry type: the second value is `false` for the platform built-in Registry and `true` for an external registry. Every Aligned Extension installed on a cluster needs its target-version package before that cluster's upgrade; otherwise the upgrade stops until you publish it.

```bash
export KUBECONFIG=<global-kubeconfig>
kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}{"\n"}'
kubectl get productbase base -o jsonpath='{.spec.registry.address}{"\t"}{.spec.registry.external}{"\n"}'
```

<Tabs>
  <Tab label="Platform built-in Registry">

```bash
bash upgrade.sh --only-sync-image
```

  </Tab>
  <Tab label="External registry">

`upgrade.sh` does not upload to an external registry. Run both upload modes; both must succeed. Do not export the registry username or password: `bash upgrade.sh --preflight` stops while either is set in the environment.

```bash
REGISTRY_ADDRESS="<registry-address>"
REGISTRY_USERNAME="<registry-username>"
read -rsp "Registry password: " REGISTRY_PASSWORD; printf '\n'
bash res/upload.sh all "$REGISTRY_ADDRESS" "$REGISTRY_USERNAME" "$REGISTRY_PASSWORD"
bash res/upload.sh necessary "$REGISTRY_ADDRESS" "$REGISTRY_USERNAME" "$REGISTRY_PASSWORD"
unset REGISTRY_USERNAME REGISTRY_PASSWORD
```

  </Tab>
</Tabs>

### Publish the Other Extensions \{#publish-other-extensions}

Publish the packages from [Download the Other Extension Packages](#download-other-extensions) and [Check Agnostic Extension Compatibility](#check-agnostic-compatibility) with `violet push`:

| Packages | Publish to | When |
| --- | --- | --- |
| Other Aligned cluster plugins, including the providers | `global` | Before the `global` upgrade |
| Other Aligned operators | `global` and each workload cluster that runs the operator | Before the upgrade of each such cluster |
| Agnostic Extensions | The clusters where you upgrade them; in DR, the standby too, as described in the next step | Before their own upgrade |

```bash
# A cluster plugin: the platform distributes it
violet push <cluster-plugin-package>.tgz --platform-address "https://<platform-address>" --platform-token "${PLATFORM_TOKEN}"
# An operator: global and every workload cluster that runs it
violet push <operator-package>.tgz --platform-address "https://<platform-address>" --platform-token "${PLATFORM_TOKEN}" \
  --clusters "global,<cluster-name-1>,<cluster-name-2>"
```

### Publish to the Standby global Cluster \{#publish-standby}

In a DR environment only. Select the standby and read its registry type, as on the primary:

```bash
export KUBECONFIG=<standby-kubeconfig>
kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}{"\n"}'
kubectl get productbase base -o jsonpath='{.spec.registry.address}{"\t"}{.spec.registry.external}{"\n"}'
```

<Tabs>
  <Tab label="Platform built-in Registry">

Publish the images to the registry of the standby: run the command from the `installer/` directory of the target Core Package, and again from that of each intermediate Core Package. The script uses the registry of the selected cluster.

```bash
bash upgrade.sh --only-sync-image
```

Then push the other Aligned packages, the Global Cluster Disaster Recovery package, and the target packages of the Agnostic Extensions installed on the standby. Set `<registry-port>` to the port of the registry address printed above. Without `--platform-address` and `--dest-repo`, the packages go to the primary.

```bash
STANDBY_REGISTRY_USER=$(kubectl -n cpaas-system get secret registry-admin -o jsonpath='{.data.username}' | base64 -d)
STANDBY_REGISTRY_PASSWORD=$(kubectl -n cpaas-system get secret registry-admin -o jsonpath='{.data.password}' | base64 -d)
read -rsp "Standby platform token: " STANDBY_TOKEN; printf '\n'
violet push <package>.tgz --platform-address "https://<standby-vip>" --platform-token "${STANDBY_TOKEN}" \
  --dest-repo "<standby-vip>:<registry-port>" --username "${STANDBY_REGISTRY_USER}" --password "${STANDBY_REGISTRY_PASSWORD}"
# Repeat violet push for each package, then:
unset STANDBY_REGISTRY_USER STANDBY_REGISTRY_PASSWORD STANDBY_TOKEN
```

  </Tab>
  <Tab label="External registry">

`upgrade.sh` does not upload to an external registry. When the standby uses the same registry endpoint as the primary, the images are already there. When it uses its own endpoint, run the external registry commands of [Publish Core and the Staged Packages](#publish-core) and [Publish the Intermediate Core Images](#sync-intermediate-images) again, with the address and credentials of that endpoint.

Then push the other Aligned packages, the Global Cluster Disaster Recovery package, and the target packages of the Agnostic Extensions installed on the standby with `violet push --platform-address "https://<standby-vip>"`. Confirm its registry options for an external registry with technical support before the window.

  </Tab>
</Tabs>

On the standby, confirm that each Cluster Plugin you pushed lists its target version, for example the Global Cluster Disaster Recovery package:

```bash
kubectl get moduleconfigs -l cpaas.io/module-name=etcd-sync
```

</Steps>

## Stage the Alauda OS Images \{#stage-alauda-os-images}

On non-Alauda OS clusters, skip this section.

Stage the image of the target version and of every intermediate Kubernetes version for each provider in use. The commands that the Huawei DCS and Bare Metal tabs generate run on the selected `global` cluster; in DR, run them on each side:

```bash
export KUBECONFIG=<global-kubeconfig>        # then <standby-kubeconfig> in DR
kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}{"\n"}'
```

<Tabs>
  <Tab label="Huawei DCS">

Upload the `qcow2` image of each version to every DCS site that your clusters use, and register it as a VM template with the same name on every site. Then generate the VM template ConfigMaps and apply them on `global`:

<DcsVmTemplateConfigMap mode="path">
  Replace `<os>` with the OS of the VM templates, such as `m55`, `ko`, or `ku`, and take the ACP version, Kubernetes version, and etcd tag of each ConfigMap from [Version Mapping](../overview/alauda_os_support_matrix.mdx#version-mapping). Repeat the intermediate ConfigMap for each intermediate Kubernetes version, and omit it when there is none.
</DcsVmTemplateConfigMap>

  </Tab>
  <Tab label="Bare Metal">

On a host that has containerd and reaches the registry of `global`, such as a `global` control-plane node, import the archive of each version and push the images it holds; this push is the only step of this tab on a node, so return to the execution host afterwards. For Alauda OS M55, push both `baremetal-base-image` and `baremetal-base-image-iso`. For Alauda OS KU, push the OS image that the list command prints to the repository used in the command below, which the catalog command also uses. The `admin` password is in the `cpaas-system/registry-admin` Secret of `global`. In DR, push to the registry of both `global` clusters.

{/* lint ignore no-legacy-os-names */}

```bash
ctr -n bare-metal-os images import --all-platforms --no-unpack <bare-metal-os-archive>
ctr -n bare-metal-os images ls -q
read -rsp "Registry password: " REGISTRY_PASSWORD; printf '\n'
# Alauda OS M55
for repo in baremetal-base-image baremetal-base-image-iso; do
  ctr -n bare-metal-os images push --local --skip-verify -u "<registry-username>:${REGISTRY_PASSWORD}" \
    "<registry-address>/tkestack/${repo}:<os-image-tag>" "${repo}:<os-image-tag>"
done
# Alauda OS KU
ctr -n bare-metal-os images push --local --skip-verify -u "<registry-username>:${REGISTRY_PASSWORD}" \
  "<registry-address>/tkestack/kubeos-rootfs:<os-image-tag>" "<listed-os-image>"
unset REGISTRY_PASSWORD
```

Add the keys of every version to the image catalog on `global` before you request the upgrade: a host replaced while its key is missing fails and does not recover when you add the key later. Run the command once for each combination of architecture and OS in the pools:

<BareMetalImageCatalog mode="path">

List the labels with `kubectl -n cpaas-system get machineinventories.elemental.cattle.io -L os.baremetal.alauda.io/arch,os.baremetal.alauda.io/id`.

  </Tab>

Upload the `qcow2` image of each version as an ECS image, and record its name for the Kubernetes upgrade.

  </Tab>

## Prepare the Clusters \{#prepare-alauda-os-clusters}

On non-Alauda OS clusters, only the last step applies: go to [Check Kubernetes 1.35 or Later Node Readiness](#kubernetes-135-node-readiness).

Run the other steps for each Alauda OS cluster, `global` included. Unless a step says otherwise, run the commands on `global` with `<cluster-name>` set to the cluster: the Cluster API objects of every cluster are in `cpaas-system` there. In DR, check workload clusters on the primary, and each `global` cluster on its own side. The checks only read; make the fixes they lead to in a change window, as listed in [Items That Need Lead Time](#lead-time).

```bash
export KUBECONFIG=<global-kubeconfig>
kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}{"\n"}'
```

<Steps>

### Check the Disks and Hosts \{#persistent-disk-layout}

:::warning
Application data stored on a node itself, in `hostPath` volumes or local PersistentVolumes, is lost when the node is replaced. Move it to CSI storage before the window. On Huawei Cloud Stack and VMware vSphere, the platform does not check for it.
:::

<Tabs>
  <Tab label="Huawei DCS">

`/var/cpaas` must be a `persistentDisk` of the IP pool, and every machine must use the same VM template. Continue when the first command lists no `/var/cpaas` and the second shows one VM template. Otherwise, migrate the disks first, as listed in [Items That Need Lead Time](#lead-time); for different VM templates, contact technical support.

```bash
kubectl -n cpaas-system get dcsmachinetemplate -o custom-columns='NAME:.metadata.name,TEMPLATE_DISKS:.spec.template.spec.vmConfig.dcsMachineDiskSpec[*].path'
kubectl -n cpaas-system get dcsmachine -l cluster.x-k8s.io/cluster-name=<cluster-name> -o custom-columns='NAME:.metadata.name,VM_TEMPLATE:.spec.vmTemplateName'
```

  </Tab>
  <Tab label="Bare Metal">

Every inventory with a storage declaration must show `STORAGE` `Prepared`, or `Active` once it is allocated. Do not add a storage declaration to a host installed before managed storage was available. A replaced node is not guaranteed to come back on the same host, so record which inventory backs each machine and the filesystem UUIDs:

```bash
kubectl -n cpaas-system get baremetalmachines.infrastructure.cluster.x-k8s.io -l cluster.x-k8s.io/cluster-name=<cluster-name> \
  -o custom-columns='NAME:.metadata.name,INVENTORY:.status.machineInventoryRef.name'
kubectl -n cpaas-system get machineinventories.elemental.cattle.io \
  -o custom-columns='NAME:.metadata.name,STORAGE:.status.storage.phase,UUIDS:.status.storage.appliedVolumes[*].filesystemUUID'
```

On every Alauda OS M55 host in the pools of the cluster, spare hosts included, `COS_STATE` needs at least 4 GiB `Free (estimated)` and no snapshot left from a failed upgrade; if not, see [Free Space on COS_STATE](./troubleshooting.mdx#check-cos-state-free-space). On Alauda OS KU hosts, the upgrade uses `/persist` instead; ask technical support how much free space it needs. Every host must also reach the platform registry. The platform does not check these items. On each M55 host:

```bash
btrfs filesystem usage -h /
snapper --no-dbus list
```

  </Tab>
  <Tab label="Huawei Cloud Stack">

kubectl -n cpaas-system get hcsmachinetemplate -o custom-columns='NAME:.metadata.name,DATA_VOLUMES:.spec.template.spec.dataVolumes[*].mountPath'

### Check the Rollout Settings \{#rollout-settings}

Nodes are replaced one at a time, which needs `maxSurge: 0` on the `KubeadmControlPlane` and on every `MachineDeployment`. Read the current values; an empty value is unset, which counts as `1`:

```bash
KCP=$(kubectl -n cpaas-system get clusters.cluster.x-k8s.io <cluster-name> -o jsonpath='{.spec.controlPlaneRef.name}')
kubectl -n cpaas-system get kubeadmcontrolplane "${KCP}" -o jsonpath='replicas={.spec.replicas} maxSurge={.spec.rolloutStrategy.rollingUpdate.maxSurge}{"\n"}'
kubectl -n cpaas-system get machinedeployment -l cluster.x-k8s.io/cluster-name=<cluster-name> \
  -o custom-columns='NAME:.metadata.name,SURGE:.spec.strategy.rollingUpdate.maxSurge,UNAVAILABLE:.spec.strategy.rollingUpdate.maxUnavailable,BOOTSTRAP:.spec.template.spec.bootstrap.configRef.name'
```

Continue when `replicas` is 3 or more and every `maxSurge` is `0`. With fewer than three control-plane nodes, contact technical support. Correct `maxSurge` in its own change, before the window:

```bash
kubectl -n cpaas-system patch kubeadmcontrolplane "${KCP}" --type merge \
  -p '{"spec":{"rolloutStrategy":{"type":"RollingUpdate","rollingUpdate":{"maxSurge":0}}}}'
kubectl -n cpaas-system patch machinedeployment <md-name> --type merge \
  -p '{"spec":{"strategy":{"type":"RollingUpdate","rollingUpdate":{"maxSurge":0,"maxUnavailable":1}}}}'
```

On Bare Metal, a node pool with a single host has no worker while that host is reinstalled; make sure its workloads can run on other nodes, or accept the interruption. On Huawei Cloud Stack, the platform does not check these values; set them anyway, because with a larger `maxSurge` every additional machine needs a free hostname and IP address in the `HCSMachineConfigPool`.

On VMware vSphere, the platform does not check the cluster before the upgrade, and the admission webhook rejects the version change of a control plane whose `maxSurge` is not `0`. Also check that every machine config pool is ready. If a pool is not `True`, read its `MembersValid`, `MembersUnique`, and `PersistentDisksReady` conditions and correct the pool:

```bash
kubectl -n cpaas-system get vspheremachineconfigpool -o custom-columns='NAME:.metadata.name,READY:.status.conditions[?(@.type=="Ready")].status'
```

### Check the Kubelet Patch File \{#kubernetes-1-35-kubelet-patch}

From Kubernetes 1.35, the bootstrap configuration of every new node needs the kubelet patch file `/etc/kubernetes/patches/kubeletconfiguration0+strategic.json`. With `KCP` from the previous step, print it from the control plane and from each `BOOTSTRAP` template listed there:

```bash
kubectl -n cpaas-system get kubeadmcontrolplane "${KCP}" -o jsonpath='{range .spec.kubeadmConfigSpec.files[?(@.path=="/etc/kubernetes/patches/kubeletconfiguration0+strategic.json")]}{.content}{.contentFrom.secret.name}{"\n"}{end}'
kubectl -n cpaas-system get kubeadmconfigtemplate <bootstrap-template> -o jsonpath='{range .spec.template.spec.files[?(@.path=="/etc/kubernetes/patches/kubeletconfiguration0+strategic.json")]}{.content}{.contentFrom.secret.name}{"\n"}{end}'
```

Continue when each command prints the file content, or the name of a Secret in `cpaas-system` that holds it. If a file is missing, contact technical support. On Kubernetes 1.35 or later, the file must contain `"imagePullCredentialsVerificationPolicy": "NeverVerify"`; do not add it for Kubernetes 1.34 or earlier. On Huawei DCS and Bare Metal, the platform adds the setting when the upgrade reaches 1.35. On Huawei Cloud Stack and VMware vSphere, add it in the same edit that moves the cluster to 1.35; on a cluster that already runs 1.35 or later, confirm that it is there.

### Check Kube-OVN and CoreDNS Takeover \{#network-addon-takeover}

For an Alauda OS cluster that uses Kube-OVN and is upgraded from a version earlier than v4.5, the platform takes over Kube-OVN and CoreDNS once the cluster and `global` both run v4.5, but only when the current setup matches what the platform renders from the cluster definition. Read the definition on `global`, then the current setup in the cluster itself; for `global`, use its own `kubeconfig` in place of `<cluster-name>.kubeconfig`:

```bash
kubectl -n cpaas-system get clusters.cluster.x-k8s.io <cluster-name> -o jsonpath='{.spec.clusterNetwork.pods.cidrBlocks[0]} {.spec.clusterNetwork.services.cidrBlocks[0]} {.metadata.annotations.cpaas\.io/kube-ovn-join-cidr} {.metadata.annotations.kube-ovn\.cpaas\.io/network-device}{"\n"}'
kubectl --kubeconfig=<cluster-name>.kubeconfig -n cpaas-system get apprelease cni-kube-ovn -o jsonpath='{.spec.source.charts[0].name}{"\n"}{.spec.values.networking}{"\n"}{.spec.values.ipv4}{"\n"}'
kubectl --kubeconfig=<cluster-name>.kubeconfig -n kube-system get configmap coredns -o jsonpath='{.data.Corefile}'
kubectl --kubeconfig=<cluster-name>.kubeconfig -n kube-system get service kube-dns -o jsonpath='{.spec.clusterIP}{"\n"}'
```

Continue when all of the following hold:

1. Kube-OVN: the chart is `acp/chart-kube-ovn` or `acp/chart-cpaas-kube-ovn`. On Huawei DCS, Huawei Cloud Stack, and VMware vSphere, `networking.NETWORK_TYPE` is `geneve`, `networking.NET_STACK` is `ipv4`, and `ipv4.POD_CIDR`, `ipv4.SVC_CIDR`, and `ipv4.JOIN_CIDR` equal the first three values of the definition. On Huawei Cloud Stack and VMware vSphere, `networking.IFACE` and `networking.vlan.VLAN_INTERFACE_NAME` also equal the fourth value, or `eth0` when it is empty. On Bare Metal, the values must match the network settings that the cluster was created with, underlay and IPv6 included; if you changed them by hand, contact technical support.
2. CoreDNS: the Corefile has one server block, `.:53`, and uses only the plugins `errors`, `health`, `ready`, `kubernetes`, `prometheus`, `forward`, `cache`, `loop`, `reload`, and `loadbalance`.
3. The `kube-dns` ClusterIP is the 10th address of the Service CIDR, for example `10.96.0.10` for `10.96.0.0/12`.
4. For `global` only: every node is `Ready`, and the `ovn-central` Deployment in `kube-system` has all replicas ready. Keep it so through the first window.

If the takeover is blocked, the cluster does not pass validation, and on Huawei Cloud Stack and VMware vSphere the manual Kubernetes upgrade cannot start, so the window cannot be closed. Resolve it with technical support before you schedule the cluster. For a customized Corefile, the takeover continues only after the `kube-system/coredns` Corefile is back to the default.

## Check Module Stability \{#module-stability-self-check}

Preflight blocks the upgrade while a Core or Aligned module of the cluster is installing, upgrading, or failed, for example during a separate plugin upgrade. On `global`, for each cluster, confirm that every module is `Running` and that `deployStatus` is not `Upgrading`, `DeployFailed`, or `UpgradeFailed`; in DR, also check `global` on the standby, with `<standby-kubeconfig>`. Wait for a module that is still upgrading; resolve a module that is `Failed` or `Blocked` before the window.

```bash
export KUBECONFIG=<global-kubeconfig>
kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}{"\n"}'
kubectl get moduleinfo -l cpaas.io/cluster-name=<cluster-name> \
  -o custom-columns='MODULE:.metadata.labels.cpaas\.io/module-name,CURRENT:.status.version,TARGET:.spec.version,PHASE:.status.phase'
kubectl get clustermodule <cluster-name> -o jsonpath='{.status.base.deployStatus}{"\n"}'
```

On a non-Alauda OS `global` cluster that uses the platform built-in Registry, also confirm on each control-plane node that `/cpaas/minio` has at least 120 GB free, with `df -h /cpaas/minio`.

## Check DR Synchronization \{#check-dr-sync}

In a DR environment only. Check synchronization now, so that a problem can be fixed before the first window. Log in to a control-plane node of the standby `global` cluster, where the Service address is reachable, run the check there, and then return to the execution host:

```bash
export KUBECONFIG=/etc/kubernetes/admin.conf
mirror_svc=$(kubectl get svc -n cpaas-system etcd-sync-monitor -o jsonpath='{.spec.clusterIP}')
if [[ $mirror_svc =~ ^[0-9a-fA-F:]+$ ]]; then mirror_host="[$mirror_svc]"; else mirror_host="$mirror_svc"; fi
curl -g "http://${mirror_host}/check"
```

Continue when the output shows `localMissedKeys [0]` and `localSurplusKeys [0]`. If it reports `check too frequent`, wait one minute and run it again. Otherwise, restore synchronization before the window; see [Global Cluster Disaster Recovery Does Not Synchronize](./troubleshooting.mdx#dr-sync-diagnostics).

## Run Preflight Checks \{#run-preflight}

Run preflight on `global` from the `installer/` directory of the target Core Package; in DR, repeat it with `<standby-kubeconfig>`. If `kubectl get productmanifests` reports `the server doesn't have a resource type`, the cluster has never been upgraded with the Cluster Version Operator (CVO): run preflight in the window, after you deploy CVO.

```bash
export KUBECONFIG=<global-kubeconfig>
kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}{"\n"}'
unset REGISTRY_USERNAME REGISTRY_PASSWORD        # preflight stops while either is set
kubectl get productmanifests
bash upgrade.sh --preflight
```

Continue when the summary is `Passed` or `PassedWithWarnings`. Workload clusters are checked later, after `global` runs the target version; in DR, after both `global` clusters do.

### Resolve Preflight Blocks \{#resolve-preflight-blocks}

For blocks not described here, see [Handle Preflight Blocks](./troubleshooting.mdx#handle-preflight-blocks-when-needed). `ResourcePatchUpgradeable` lists customizations that need an exemption. Review each patch with technical support, then exempt it on the cluster that is upgraded, with the target version as the value; do not use `*`. The value compares the major and minor version only, so an exemption for 4.5 covers every 4.5 patch. In DR, do it on each side. Requests made with `ac` do not add the exemption:

```bash
kubectl get resourcepatches \
  -o custom-columns='NAME:.metadata.name,EXEMPT:.metadata.annotations.config\.cpaas\.io/exempt-for-ver'
kubectl get resourcepatches <rp-name> -o yaml
kubectl annotate resourcepatches <rp-name> config.cpaas.io/exempt-for-ver=4.5.0 --overwrite
```

`AdminAckRequired` asks for an administrator acknowledgement on every `global` cluster upgraded from v4.4 or earlier, on each side in DR. Complete [Check Kubernetes 1.35 or Later Node Readiness](#kubernetes-135-node-readiness), which has nothing to check on Alauda OS, then copy the key from `admin-gates`, record it, and run preflight again:

```bash
kubectl -n cpaas-system get configmap admin-gates -o yaml
ACK_KEY='<key-from-admin-gates>'
kubectl -n cpaas-system patch configmap admin-acks --type merge -p "{\"data\":{\"${ACK_KEY}\":\"true\"}}"
bash upgrade.sh --preflight
```
