# Upgrade Kubernetes on Alauda OS for the `global` Cluster

This document describes how to upgrade Kubernetes on a `global` cluster that runs Alauda OS. Upgrades replace nodes with new Alauda OS images managed by the Cluster API provider; in-place node upgrades are not used.

For a Huawei DCS `global` cluster, select the Alauda OS image published for the target ACP release. If the cluster's VM templates were made from an Alauda OS image published for a release earlier than ACP `v4.3.2`, they do not match DCS Provider `v1.0.21` or later. Upgrade the provider together with the Distribution Version of the `global` cluster, because the platform upgrades the installed Aligned plugins during that upgrade; see [Pre-Upgrade Preparation](../pre-upgrade.mdx). Then create the VM template from the Alauda OS image published for the target ACP release and replace the nodes by following this document. See [Upgrade Kubernetes on Huawei DCS](../workload/alauda_os/huawei-dcs.mdx).

## When to Use This Path

Choose this upgrade path when:

- The `global` cluster was installed on Alauda OS. See [Installing the global Cluster](../../install/alauda_os/installing.mdx).
- Your infrastructure is one of the documented providers: Huawei DCS, VMware vSphere, Huawei Cloud Stack, or Bare Metal.

For a non-Alauda OS `global` cluster, Kubernetes is upgraded in place as part of [Upgrade the Distribution Version](./upgrade_global_cluster.mdx); this page does not apply.

In a DR pair, upgrade Kubernetes on both `global` clusters. On Huawei DCS and Bare Metal, each `global` cluster upgrades Kubernetes as part of its own platform upgrade; prepare both clusters as described in [Huawei DCS and Bare Metal: Automatic Upgrade](#automatic-upgrade). With the manual procedure, run it on each `global` cluster with its own `global` kubeconfig. For the Distribution Version upgrade of the pair, see [Upgrade in a DR Environment](./upgrade_global_dr.mdx).

## Two-Phase Upgrade Overview

Like workload clusters, an Alauda OS `global` cluster follows a two-phase upgrade.

1. **Phase 1 — ACP Core and Distribution Version**: prepare artifacts and plugin packages, then use CVO to move the global tier to the target Distribution Version. See [Pre-Upgrade Preparation](../pre-upgrade.mdx) and [Upgrade the Distribution Version](./upgrade_global_cluster.mdx).
2. **Phase 2 — Kubernetes and OS Image**: nodes are replaced with new Alauda OS images that contain the target Kubernetes version. This document focuses on Phase 2 for the `global` cluster.

On Huawei DCS and Bare Metal, Phase 2 of the `global` cluster runs automatically as part of the platform upgrade; see [Huawei DCS and Bare Metal: Automatic Upgrade](#automatic-upgrade). On VMware vSphere and Huawei Cloud Stack, and for a Huawei DCS or Bare Metal `global` cluster in manual mode, follow the [Manual Procedure](#procedure) after Phase 1.

<Directive type="info" title="Phase 1 Compatibility">
  Before you upgrade the `global` cluster, verify that every workload cluster falls within the Compatible Versions matrix of the target Distribution Version. Workload clusters that are out of range must be upgraded first.
</Directive>

## Common Prerequisites

- For the manual procedure, the `global` cluster has completed Phase 1 (Distribution Version upgrade). The automatic upgrade on Huawei DCS and Bare Metal performs both phases in one platform upgrade.
- The infrastructure provider for the IaaS that the `global` cluster runs on and the Cluster Bootstrap Provider are uploaded and installed on the `global` cluster. If they are not, install them first by following the provider installation page for [Bare Metal](../../workload_clusters/alauda_os/bare-metal/install_provider.mdx), [Huawei DCS](../../workload_clusters/alauda_os/huawei-dcs/install_provider.mdx), [Huawei Cloud Stack](../../workload_clusters/alauda_os/huawei-cloud-stack/install_provider.mdx), or [VMware vSphere](../../workload_clusters/alauda_os/vmware-vsphere/install_provider.mdx). In a DR pair, install them on both `global` clusters.
- The infrastructure provider version, the Alauda OS image version, and the ACP version match. Phase 1 upgrades the provider together with the Distribution Version of the `global` cluster.
- An etcd backup of the `global` cluster has been taken and verified.
- The target row in [OS Support Matrix](../../overview/alauda_os_support_matrix.mdx) is available, and its Kubernetes version and etcd tag are staged, together with the Alauda OS image published for that release. Kube-OVN and CoreDNS are upgraded automatically and are not changed by hand; see [Kube-OVN and CoreDNS](../workload/alauda_os/index.mdx#kube-ovn-coredns).
- The previous machine templates and bootstrap templates are retained until Phase 2 is verified.
- A maintenance window plan that accounts for rolling control plane replacement.
- For cross-version upgrades that span more than one Kubernetes minor, the intermediate-version Core images and OS images are pre-staged. See [Cross-Version Upgrade Preparation](../workload/alauda_os/index.mdx#cross-version-preparation).

## Huawei DCS and Bare Metal: Automatic Upgrade \{#automatic-upgrade}

The `global` cluster is upgraded the same way as a workload cluster on the same provider. The platform tracks its Kubernetes and OS upgrade in the `InfraClusterVersion` resource named `global`, checks it before changing anything, and upgrades Kubernetes and the OS image through every intermediate version after ACP Core. The platform upgrade of the `global` cluster is reported complete only after its nodes run the target version, so workload clusters start their upgrade only after that.

1. Prepare the `global` cluster as described for its provider. Apply the preparation to the `global` cluster itself, using the `global` kubeconfig:
   - Huawei DCS: [Prepare the Cluster](../workload/alauda_os/huawei-dcs.mdx#automatic-prepare). In a DR pair, create the VM template ConfigMaps on both `global` clusters.
   - Bare Metal: [Prepare the Cluster](../workload/alauda_os/bare-metal.mdx#automatic-prepare). In a DR pair, update the image catalog on both `global` clusters.
2. Request the platform upgrade by following [Upgrade the Distribution Version](./upgrade_global_cluster.mdx), or [Upgrade in a DR Environment](./upgrade_global_dr.mdx) for a DR pair. Resolve any failed [preflight check](../workload/alauda_os/huawei-dcs.mdx#preflight-checks) for the `global` cluster; the Bare Metal checks are listed in [Preflight Checks](../workload/alauda_os/bare-metal.mdx#preflight-checks).
3. Watch the upgrade:

   ```shell
   kubectl --kubeconfig <global-kubeconfig> -n cpaas-system get infraclusterversion global
   ```

   The upgrade is complete when `PHASE` is `Succeeded` and the `Ready` condition is `True`. While the control plane of the `global` cluster is replaced, the upgrade controller can move to another node; the upgrade continues on its own. For monitoring and troubleshooting details, see [Huawei DCS](../workload/alauda_os/huawei-dcs.mdx#automatic-monitor) or [Bare Metal](../workload/alauda_os/bare-metal.mdx#automatic-monitor).

A Huawei DCS `global` cluster whose control plane has fewer than 3 replicas cannot be upgraded automatically. Before the platform upgrade, put it in manual mode with `kubectl --kubeconfig <global-kubeconfig> -n cpaas-system label cluster.cluster.x-k8s.io global upgrade.alauda.io/mode=manual`, then follow the [Manual Procedure](#procedure) once the platform upgrade reports `ManualUpgradeRequired`.

The automatic upgrade only moves forward. It cannot be paused, cancelled, or rolled back. If the `global` cluster cannot be repaired forward, recover it from the verified pre-upgrade etcd backup or the Global DR procedure.

## Manual Procedure \{#procedure}

Use this procedure for VMware vSphere and Huawei Cloud Stack, and for a Huawei DCS or Bare Metal `global` cluster in manual mode. The Cluster API controllers that manage the `global` cluster run on the `global` cluster itself. Use the `global` kubeconfig for the `kubectl` commands in this procedure.

<Directive type="warning" title="Required when the target is Kubernetes 1.35">
  In Kubernetes 1.35, kubelet credential verification can apply to images that are already present on a node. On the hop to Kubernetes 1.35 or later, add `imagePullCredentialsVerificationPolicy: NeverVerify` to the kubelet patch used by every replacement node. Update the control-plane file in the same `KubeadmControlPlane` edit as `spec.version`. For workers, create a new `KubeadmConfigTemplate` with the updated patch and switch `MachineDeployment.spec.template.spec.bootstrap.configRef.name` in the same edit as the version. Do not add this parameter for Kubernetes 1.34 or earlier. See [Required kubelet patch for Kubernetes 1.35](../workload/alauda_os/index.mdx#kubernetes-1-35-kubelet-patch).
</Directive>

### Step 1 — Update the Control Plane Resources

Update the control plane resources of the `global` cluster to reference the new Alauda OS image and Kubernetes version. The fields to update are provider-specific. Update the worker node resources in Step 3.

<Tabs>
  <Tab label="Huawei DCS">

Use this tab only for a `global` cluster in manual mode. Before you start, see [Prerequisites](../workload/alauda_os/huawei-dcs.mdx#manual-prerequisites).

For DCS, create new infrastructure templates instead of editing templates that are already referenced by running machines.

Update the control plane resources:

- Create a new `DCSMachineTemplate` for the target image and set `spec.template.spec.vmTemplateName` to the Alauda OS template that matches the target Kubernetes version.
- Keep preserved node-local data, including `/var/cpaas`, in `DCSIpHostnamePool.spec.pool[].persistentDisk`. Do not move preserved disks back into `DCSMachineTemplate`.
- Set `KubeadmControlPlane.spec.version` to the target Kubernetes version.
- Set the etcd image tag in `KubeadmControlPlane.spec.kubeadmConfigSpec.clusterConfiguration` from the same OS Support Matrix row. Leave `clusterConfiguration.dns` unchanged.
- When the target is Kubernetes 1.35 or later, update the control-plane kubelet patch in `KubeadmControlPlane.spec.kubeadmConfigSpec.files` in the same manifest edit.
- Point `KubeadmControlPlane.spec.machineTemplate.infrastructureRef.name` to the new `DCSMachineTemplate`.
- After the `KubeadmControlPlane` edit, set the `capi.cpaas.io/kubernetes` annotation on the `global` `Cluster` to the new `KubeadmControlPlane.spec.version`: `kubectl annotate cluster global -n cpaas-system capi.cpaas.io/kubernetes=<target-kubernetes-version> --overwrite`.
- Keep `KubeadmControlPlane.spec.rolloutStrategy.rollingUpdate.maxSurge: 0` when the cluster uses pool-managed persistent disks.

Pool-managed persistent disks are declared on the IP pool, not on the machine template:

```yaml
apiVersion: infrastructure.cluster.x-k8s.io/v1beta1
kind: DCSIpHostnamePool
metadata:
  name: <global-pool-name>
  namespace: cpaas-system
spec:
  pool:
    - ip: <node-ip>
      hostname: <node-hostname>
      persistentDisk:
        - slot: 0
          quantityGB: 40
          datastoreName: <datastore-name>
          path: /var/cpaas
          format: xfs
          mountOptions:
            - defaults
```

Use `isThin` only when the DCS environment requires an explicit thin-provisioning value. If omitted, the provider does not send `isThin` and DCS uses the platform default. New persistent volumes are created as independent persistent normal volumes.

Use the IP pool status to confirm that preserved disks are detached from old VMs and attached to replacement VMs during the rolling replacement.

  </Tab>
  <Tab label="VMware vSphere">

Before you start, see [Check the manifests against the admission rules](../workload/alauda_os/vmware-vsphere.mdx#preflight-admission-rules).

For vSphere, create new infrastructure templates instead of editing templates that are already referenced by running machines.

Update the control plane resources:

- Export the current `VSphereMachineTemplate`, give the copy a new name, remove server-generated metadata and `status`, and set `spec.template.spec.template` to the VM template created in vSphere from the Alauda OS image published for the target ACP release.
- Preserve the existing vCenter, folder, datastore, network, clone-mode, CPU, memory, and disk configuration unless the release procedure explicitly changes it. Leave `spec.template.spec.providerID` unset.
- Keep preserved node-local data, including `/var/cpaas`, in `VSphereMachineConfigPool.spec.configs[].persistentDisks[]`; do not move it into the machine template.
- Set `KubeadmControlPlane.spec.version` and the etcd tag from the same OS Support Matrix row. Leave `clusterConfiguration.dns` unchanged.
- When the target is Kubernetes 1.35 or later, update the control-plane kubelet patch in `KubeadmControlPlane.spec.kubeadmConfigSpec.files` in the same manifest edit.
- Point `KubeadmControlPlane.spec.machineTemplate.infrastructureRef.name` to the new `VSphereMachineTemplate`.
- Keep `KubeadmControlPlane.spec.rolloutStrategy.rollingUpdate.maxSurge: 0` when the control plane pool uses fixed slots or pool-managed persistent disks.

</Tab>
  <Tab label="Huawei Cloud Stack">

Before you start, see [Prerequisites](../workload/alauda_os/huawei-cloud-stack.mdx#prerequisites).

For HCS, create new infrastructure templates instead of editing templates that are already referenced by running machines.

Update the control plane resources:

- Create a new `HCSMachineTemplate` for the target image and set `spec.template.spec.imageName` to the Alauda OS image that matches the target Kubernetes version.
- Keep preserved node-local data, including `/var/cpaas`, in `HCSMachineConfigPool.spec.configs[].persistentDisks[]`. Do not move preserved disks back into `HCSMachineTemplate.spec.template.spec.dataVolumes[]`.
- Leave runtime identity fields unset in the new template, including `spec.template.spec.providerID` and `spec.template.spec.serverId`.
- Set `KubeadmControlPlane.spec.version` to the target Kubernetes version.
- Set the etcd image tag in `KubeadmControlPlane.spec.kubeadmConfigSpec.clusterConfiguration` from the same OS Support Matrix row. Leave `clusterConfiguration.dns` unchanged.
- When the target is Kubernetes 1.35 or later, update the control-plane kubelet patch in `KubeadmControlPlane.spec.kubeadmConfigSpec.files` in the same manifest edit.
- Point `KubeadmControlPlane.spec.machineTemplate.infrastructureRef.name` to the new `HCSMachineTemplate`.
- Keep `KubeadmControlPlane.spec.rolloutStrategy.rollingUpdate.maxSurge: 0` when the control plane pool uses pool-managed persistent disks.

Pool-managed persistent disks are declared on the machine configuration pool, not on the machine template:

```yaml
apiVersion: infrastructure.cluster.x-k8s.io/v1beta1
kind: HCSMachineConfigPool
metadata:
  name: <global-pool-name>
  namespace: cpaas-system
  labels:
    cluster.x-k8s.io/cluster-name: global
spec:
  configs:
    - hostname: <node-hostname>
      networks:
        - subnetName: <subnet-name>
          ipAddress: <node-ip>
      persistentDisks:
        - slot: 0
          size: 100
          type: SSD
          mountPath: /var/cpaas
          format: xfs
          mountOptions:
            - defaults
            - noatime
```

Do not treat HCS `dataVolumes[]` as preserved state during node replacement. This rolling upgrade workflow supports highly available control planes that can replace `HCSMachineTemplate` and `KubeadmControlPlane` references while `HCSMachineConfigPool` retains enough fixed identities and persistent disk slots for the rollout. Single-control-plane HCS clusters, including a `global` cluster with one control plane node, are not supported by this rolling upgrade workflow. Use an alternative documented procedure, recreate the control plane with immutable templates, or consult the out-of-band migration guide or support before proceeding.

  </Tab>
  <Tab label="Bare Metal">

Before you start, see [Check COS_STATE Free Space](../workload/alauda_os/bare-metal.mdx#check-cos-state-free-space) and [Update the Image Catalog](../workload/alauda_os/bare-metal.mdx#update-the-image-catalog).

Use this tab only for a `global` cluster in manual mode, and only after the Bare Metal provider is installed on the `global` cluster and the target OS Support Matrix row is available in the installed release. Before editing Cluster API resources, confirm that the provider `AppRelease` requested and installed revisions match and its chart phase is `Success`.

Import the target release's Bare Metal OS images into the `global` cluster's registry and add the target Kubernetes version to its `elemental-image-catalog`, as described in [OS Images Imported and Image Catalog Populated](../../workload_clusters/alauda_os/bare-metal/create_cluster.mdx#os-images-and-image-catalog). Neither the provider plugin nor the Distribution Version upgrade adds the version for you. In a DR pair, do this on both `global` clusters. Then verify the catalog:

```shell
kubectl --kubeconfig <global-kubeconfig> -n cpaas-system \
  get configmap elemental-image-catalog -o yaml
```

The target version must appear as a key with a reachable base-image reference. A replacement `Machine` created while the key is missing leaves its `BaremetalMachine` in `Failed` with `Reason=ImageCatalogMiss`, and adding the key afterwards does not recover it. The Bare Metal provider resolves the replacement image from `Machine.spec.version`; a Kubernetes-only upgrade does not require a new `BaremetalMachineTemplate` unless the control plane or workers must move to a different `MachineInventoryPool`.

Update the existing `KubeadmControlPlane` manifest with values from the same OS Support Matrix row. Preserve all fields not shown here:

```yaml
spec:
  version: <target-kubernetes-version>
  rolloutStrategy:
    rollingUpdate:
      maxSurge: 0
  kubeadmConfigSpec:
    clusterConfiguration:
      etcd:
        local:
          imageTag: <target-etcd-tag>
```

Retain the existing `spec.kubeadmConfigSpec.files` entries. For Kubernetes 1.35 or later, update the existing `kubeletconfiguration0+strategic.json` entry in that list as documented above; do not replace the list with an empty value.

Apply the complete retained control plane manifests in Step 2. The provider deletes each old machine, cleans its inventory, allocates an available inventory from the same pool, and writes a `reprovision` plan for the target image.

  </Tab>
</Tabs>

### Step 2 — Apply the Control Plane Changes and Wait

Apply the updated control plane manifests against the `global` cluster.

```shell
kubectl --kubeconfig <global-kubeconfig> apply -f <updated-control-plane-manifest>
```

The Cluster API provider begins replacing control plane nodes by using the new image. When `maxSurge: 0` is set, each old node is drained and deleted before its replacement can reuse the same fixed identity, IP address, or preserved disk.

Wait until all control plane nodes have been replaced.

```shell
kubectl --kubeconfig <global-kubeconfig> get machines -A -o wide
kubectl --kubeconfig <global-kubeconfig> get kubeadmcontrolplane -A
```

The control plane replacement is complete when every control plane `Machine` reports the new Kubernetes version and `Phase: Running`, and the `KubeadmControlPlane` reports `Ready: True` against the new version.

### Step 3 — Update the Worker Resources

Update the worker node resources of the `global` cluster to reference the new Alauda OS image and Kubernetes version. The fields to update are provider-specific.

<Tabs>
  <Tab label="Huawei DCS">

Update worker node resources:

- Create a new worker `DCSMachineTemplate` with the target `vmTemplateName`.
- Set each `MachineDeployment.spec.template.spec.version` to the target Kubernetes version.
- When the target is Kubernetes 1.35 or later, create a new worker `KubeadmConfigTemplate` with the required kubelet patch and point `MachineDeployment.spec.template.spec.bootstrap.configRef.name` to it.
- Point each `MachineDeployment.spec.template.spec.infrastructureRef.name` to the new worker `DCSMachineTemplate`.
- Keep each `MachineDeployment.spec.strategy.rollingUpdate.maxSurge: 0` when the worker pool uses pool-managed persistent disks.

</Tab>
  <Tab label="VMware vSphere">

Update worker node resources:

- Create a new worker `VSphereMachineTemplate` with the target VM template and the retained provider configuration.
- Set each `MachineDeployment.spec.template.spec.version` to the target Kubernetes version.
- When the target is Kubernetes 1.35 or later, create a new worker `KubeadmConfigTemplate` with the required kubelet patch and point `MachineDeployment.spec.template.spec.bootstrap.configRef.name` to it.
- Point each `MachineDeployment.spec.template.spec.infrastructureRef.name` to the new worker `VSphereMachineTemplate`.
- Keep each `MachineDeployment.spec.strategy.rollingUpdate.maxSurge: 0` when the worker pool uses fixed slots or pool-managed persistent disks.

Do not edit a template that running machines reference. Keep the previous control-plane and worker templates until the new rollout is verified.

  </Tab>
  <Tab label="Huawei Cloud Stack">

Update worker node resources:

- Create a new worker `HCSMachineTemplate` with the target `imageName`.
- Set each `MachineDeployment.spec.template.spec.version` to the target Kubernetes version.
- When the target is Kubernetes 1.35 or later, create a new worker `KubeadmConfigTemplate` with the required kubelet patch and point `MachineDeployment.spec.template.spec.bootstrap.configRef.name` to it.
- Point each `MachineDeployment.spec.template.spec.infrastructureRef.name` to the new worker `HCSMachineTemplate`.
- Keep each `MachineDeployment.spec.strategy.rollingUpdate.maxSurge: 0` when the worker pool uses pool-managed persistent disks.

</Tab>
  <Tab label="Bare Metal">

For each worker `MachineDeployment`, set the target Kubernetes version and keep `maxSurge: 0`. When the target is Kubernetes 1.35 or later, first create a new `KubeadmConfigTemplate` containing the required kubelet patch, then reference it in the same manifest change:

```yaml
spec:
  strategy:
    rollingUpdate:
      maxSurge: 0
  template:
    spec:
      version: <target-kubernetes-version>
      bootstrap:
        configRef:
          name: <target-kubeadm-config-template>
```

Omit the `bootstrap.configRef` change for an earlier target when no bootstrap setting changes. Apply the complete retained worker manifests in Step 4.

  </Tab>
</Tabs>

### Step 4 — Apply the Worker Changes

Apply the updated worker manifests against the `global` cluster.

```shell
kubectl --kubeconfig <global-kubeconfig> apply -f <updated-worker-manifest>
```

The Cluster API provider begins replacing worker nodes by using the new image. When `maxSurge: 0` is set, each old node is drained and deleted before its replacement can reuse the same fixed identity, IP address, or preserved disk.

### Step 5 — Monitor the Rolling Replacement

Watch the rolling replacement until all worker nodes have been replaced.

```shell
kubectl --kubeconfig <global-kubeconfig> get machines -A -o wide
kubectl --kubeconfig <global-kubeconfig> get kubeadmcontrolplane -A
```

The upgrade is complete when every `Machine` reports the new Kubernetes version and `Phase: Running`, and the `KubeadmControlPlane` reports `Ready: True` against the new version.

### Step 6 — Confirm Completion in Manual Mode

For a Huawei DCS or Bare Metal `global` cluster in manual mode, confirm the upgrade once after every node runs the final target version:

```shell
kubectl --kubeconfig <global-kubeconfig> -n cpaas-system exec deploy/cluster-version-operator -- \
  cluster-version-operator infra-version complete --cluster global
```

Exit code `0` confirms the upgrade. For the other exit codes, see [Confirm Completion](../workload/alauda_os/huawei-dcs.mdx#manual-confirm). VMware vSphere and Huawei Cloud Stack `global` clusters skip this step.

## Verification

After the rolling replacement finishes, verify that the upgraded `global` cluster is healthy.

```shell
kubectl --kubeconfig <global-kubeconfig> get nodes -o wide
kubectl --kubeconfig <global-kubeconfig> get clusterversionshadow -o yaml
kubectl --kubeconfig <global-kubeconfig> get pods -n cpaas-system
```

All nodes must report the new Kubernetes version, the `ClusterVersionShadow` must reflect the target Distribution Version, and core platform pods must be `Running`.

On a Huawei DCS or Bare Metal `global` cluster upgraded from a release earlier than v4.5, also check that the provider has handed Kube-OVN and CoreDNS over to the platform. Read the `CoreAddonsHandedOff` condition of the `DCSCluster` or `BaremetalCluster` named `global`, and the `cni-type` label of the CAPI `Cluster`:

```shell
# Huawei DCS; on Bare Metal use baremetalclusters.infrastructure.cluster.x-k8s.io
kubectl --kubeconfig <global-kubeconfig> -n cpaas-system get dcsclusters.infrastructure.cluster.x-k8s.io global \
  -o jsonpath='{.status.conditions[?(@.type=="CoreAddonsHandedOff")]}'
kubectl --kubeconfig <global-kubeconfig> -n cpaas-system get cluster.cluster.x-k8s.io global --show-labels
```

The handoff is complete when the condition is `True` and the `Cluster` carries the label `cni-type=kube-ovn`. It can finish up to about an hour and a half after the platform upgrade is reported complete; until then, the previous Kube-OVN version keeps running. If the condition reports `CoreAddonsHandoffBlocked`, its message names the cause. See [Kube-OVN and CoreDNS](../workload/alauda_os/index.mdx#kube-ovn-coredns).

## Recovery Considerations

These stage rules apply to the manual procedure. An automatic upgrade on Huawei DCS or Bare Metal only moves forward; see [Huawei DCS and Bare Metal: Automatic Upgrade](#automatic-upgrade).

Do not treat a Kubernetes minor downgrade as an ordinary rollback. Choose the recovery path from the rollout stage:

1. **No target-version control-plane `Machine` has been created**: restore the previous manifest values. This cancels the target rollout before a new control-plane data format is introduced.
2. **Only the machine template or OS image changed, and the Kubernetes minor did not change**: point the controlling resource back to the previous template and let Cluster API perform another replacement rollout. Keep the Kubernetes minor unchanged.
3. **A control-plane `Machine` on the target Kubernetes minor has joined the cluster**: do not patch Kubernetes or etcd back to the previous minor. Stop further rollout and repair forward on the target minor, or recover the `global` cluster from the verified pre-upgrade etcd backup or Global DR procedure.

If a target-minor control-plane `Machine` was created but never joined, restore healthy etcd quorum and determine whether the failed replacement can be removed safely before changing manifests.

<Tabs>
  <Tab label="Huawei DCS">

For DCS clusters that use pool-managed persistent disks, confirm disk state before rollback:

First, check `DCSIpHostnamePool.status.persistentDiskStatus` before deleting or recreating machines. Do not delete retained DCS volumes that are listed in `DCSIpHostnamePool.spec.pool[].persistentDisk`.

Keep `maxSurge: 0` while returning to previous machine templates in a same-minor replacement recovery. If a target-minor control-plane machine has joined, retain the target baseline and use forward recovery or backup restore.

  </Tab>
  <Tab label="VMware vSphere">

For a same-minor template recovery, keep `maxSurge: 0`, point the control plane and worker resources to the retained previous `VSphereMachineTemplate` resources, and verify that each fixed slot reattaches its pool-managed persistent disks. If a target-minor control-plane machine has joined, retain the target Kubernetes and etcd baseline and use forward recovery or backup restore.

  </Tab>
  <Tab label="Huawei Cloud Stack">

Node-local data on HCS `dataVolumes[]` is not a recovery source because node replacement may delete the old VM and attached volumes. Data declared in `HCSMachineConfigPool.spec.configs[].persistentDisks[]` is reattached during replacement. For a same-minor template recovery, keep `maxSurge: 0` and point the controlling resources to the retained previous `HCSMachineTemplate` resources. If a target-minor control-plane machine has joined, retain the target baseline and use forward recovery or backup restore.

  </Tab>
  <Tab label="Bare Metal">

Restore the previous manifests only if no target-minor control-plane `Machine` has been created.

Every host that completes a `reprovision` plan has already replaced its OS image and cleared Kubernetes-managed state. If a target-minor control-plane machine has joined, do not patch Kubernetes or etcd back to the previous minor. Repair forward, or recover the `global` cluster through the verified etcd backup or Global DR procedure.

  </Tab>
</Tabs>
