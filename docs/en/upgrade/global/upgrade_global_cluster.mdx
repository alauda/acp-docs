# Upgrade the `global` Cluster

Use this page in the first maintenance window to upgrade a `global` cluster that has no disaster recovery standby. If the platform has a primary and a standby `global` cluster, use [Upgrade `global` Clusters in a DR Environment](./upgrade_global_dr.mdx) instead.

One upgrade request moves the `global` cluster to the target ACP version (Distribution Version): ACP Core and the installed Extensions (Operators and Cluster Plugins) with the `Aligned` lifecycle. On Huawei DCS and Bare Metal, the same request also upgrades Kubernetes, one node at a time. On Huawei Cloud Stack and VMware vSphere, you upgrade Kubernetes yourself in the same window. On non-Alauda OS clusters, the request upgrades Kubernetes in place.

## Before You Begin \{#before-you-begin}

- [Prepare for the Upgrade](../pre-upgrade.mdx) is complete for the `global` cluster, including the `global` cluster checks on Huawei DCS and Bare Metal.
- The preflight check has passed, including any administrator acknowledgement that it reported. On a cluster that has never run the Cluster Version Operator (CVO), the final preflight check on this page is the first one.
- The `global` cluster has a recent successful etcd backup. See [etcd Backup and Restore](../../configure/backup/etcd.mdx).
- You are on the execution host, in the directory of the extracted target Core Package.

Select the `global` cluster and confirm that the printed API address is its VIP. `ac`, `kubectl`, and `upgrade.sh` use this kubeconfig for every command on this page.

```bash
export KUBECONFIG=<global-kubeconfig>
kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}{"\n"}'
```

:::info
On Alauda OS, run the upgrade commands from the execution host, not from a node of the `global` cluster. The upgrade replaces the nodes, and files and sessions on a replaced node are lost.
:::

## Upgrade the `global` Cluster \{#upgrade-the-global-cluster}

<Steps>

### Deploy the Cluster Version Operator \{#deploy-the-cluster-version-operator}

Deploy CVO and the target release information. The artifacts were published during preparation, so skip the image sync:

```bash
bash upgrade.sh --skip-sync-image
kubectl get productmanifest v4.5.0
```

Continue when the script completes without an error and `READY` is `True`. Otherwise, see [Recover a Missing Aligned Package](../troubleshooting.mdx#recover-missing-aligned-package).

### Run the Final Preflight Check \{#final-preflight}

```bash
bash upgrade.sh --preflight
```

Continue when `Summary` shows `Passed` or `PassedWithWarnings`. Otherwise, resolve the reported checks as described in [Handle Preflight Blocks](../troubleshooting.mdx#handle-preflight-blocks-when-needed), then run the check again. `AdminAckRequired` can appear for the first time here, after the target CVO is deployed; handle it as described in [Handle Administrator Acknowledgement Gates](../troubleshooting.mdx#handle-administrator-acknowledgement-gates).

### Request the Upgrade \{#request-the-upgrade}

:::warning
An upgrade cannot be rolled back. On Huawei DCS, this request also replaces every node with a new VM; on Bare Metal, it reinstalls every host. Both happen one node at a time.
:::

List the available updates, then request the target version exactly as it is listed:

```bash
ac adm upgrade
ac adm upgrade --cluster=global --to=4.5.0
```

### Monitor the Upgrade \{#monitor-the-upgrade}

```bash
ac adm upgrade status --cluster=global
```

Run the command again until `Current` shows `4.5.0` and the `Ready` condition is `True`. Add `--verbose` to see every check and stage.

On Huawei DCS and Bare Metal, also follow the Kubernetes upgrade:

```bash
kubectl -n cpaas-system get infraclusterversion global
```

`CURRENT` advances through each intermediate Kubernetes version. Continue when `PHASE` is `Succeeded`. While the control plane nodes are replaced, a command can fail to connect; run it again. The upgrade continues on its own.

If `Stalled` is `True`, fix the reported cause by following [Inspect Upgrade State](../troubleshooting.mdx#inspect-upgrade-state); the upgrade then continues. If the cause cannot be fixed, contact technical support.

### Upgrade Kubernetes on Huawei Cloud Stack or VMware vSphere \{#upgrade-kubernetes-hcs-vsphere}

:::warning
On Huawei Cloud Stack and VMware vSphere, finish this step in the same maintenance window for every upgrade, including a patch upgrade whose Kubernetes build changes. Do not leave the cluster on the new ACP version with the old Kubernetes version.
:::

Follow [Upgrade Kubernetes on Huawei Cloud Stack and VMware vSphere](../upgrade_kubernetes_hcs_vsphere.mdx) with `<global-kubeconfig>`, then return to this page.

On Huawei DCS, Bare Metal, and non-Alauda OS clusters, skip this step.

### Upgrade the Agnostic Extensions \{#upgrade-agnostic-extensions}

The upgrade request does not upgrade Extensions (Operators and Cluster Plugins) with the `Agnostic` lifecycle. Upgrade each Agnostic Extension separately by following its own documentation, for example:

- <ExternalSiteLink name="ai" href="/upgrade/upgrade-from-aml-1.2.html" children="Upgrade Alauda AI" />
- <ExternalSiteLink name="devops" href="/upgrade/index.html" children="Upgrade Alauda DevOps" />

If the source ACP version is earlier than 4.3, also upgrade these Agnostic Extensions to versions compatible with the target, or their pages can fail to open: Alauda DevOps v3, Alauda AI Essentials, Alauda Hyperflux, and Alauda Container Platform Data Services Essentials.

### Validate the Upgrade \{#validate}

Complete [Upgrade Validation](../validation.mdx) for the `global` cluster before you close the maintenance window.

</Steps>
