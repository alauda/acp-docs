# Upgrade the `global` Cluster

Use this page to upgrade a `global` cluster that has no disaster recovery standby, for every upgrade, patch upgrades included. If the platform has a primary and a standby `global` cluster, use [Upgrade `global` Clusters in a DR Environment](./upgrade_global_dr.mdx) instead.

One upgrade request moves the `global` cluster to the target ACP version (Distribution Version): ACP Core and the installed Extensions (Operators and Cluster Plugins) with the `Aligned` lifecycle. On Huawei DCS and Bare Metal, the same request also upgrades Kubernetes, one node at a time. On Huawei Cloud Stack and VMware vSphere, you upgrade Kubernetes yourself right after the request completes. On non-Alauda OS clusters, the request upgrades Kubernetes in place.

## Before You Begin \{#before-you-begin}

- [Prepare for the Upgrade](../pre-upgrade.mdx) is complete for the `global` cluster, including the `global` cluster checks on Huawei DCS and Bare Metal.
- The preflight check has passed, including any administrator acknowledgement that it reported. On a cluster that has never run the Cluster Version Operator (CVO), the final preflight check on this page is the first one.
- The `global` cluster has a recent successful etcd backup. See [etcd Backup and Restore](../../configure/backup/etcd.mdx).
- You are on the execution host, logged in with `ac login`, in the `installer/` directory of the extracted target Core Package, with the kubeconfig of the `global` cluster, `<global-kubeconfig>`, for `upgrade.sh`.

Select the `global` cluster, then confirm that no workload cluster upgrade is running; the platform does not block a `global` upgrade while one runs:

```bash
ac config use-cluster global
ac whoami --show-server
ac -n cpaas-system get cvsh \
  -o custom-columns='CLUSTER:.metadata.name,REQUESTED:.spec.desiredUpdate.version,CURRENT:.status.current.version'
```

Continue when the address ends with `/kubernetes/global/` and, on every row, `REQUESTED` is empty or equal to `CURRENT`; otherwise, wait until that upgrade completes. If the last command reports `the server doesn't have a resource type`, the cluster has never been upgraded with CVO; continue.

:::info
On Alauda OS, run the upgrade commands from the execution host, not from a node of the `global` cluster. The upgrade replaces the nodes, and files and sessions on a replaced node are lost.
:::

## Upgrade the `global` Cluster \{#upgrade-the-global-cluster}

<Steps>

### Deploy the Cluster Version Operator \{#deploy-the-cluster-version-operator}

Deploy CVO and the target release information. The artifacts were published during preparation, so skip the image sync. `<target-version>` is the target ACP version, for example `4.5.0`:

```bash
export KUBECONFIG=<global-kubeconfig>   # upgrade.sh uses kubectl with the kubeconfig in KUBECONFIG
ac whoami --show-server                 # the VIP of the global cluster
bash upgrade.sh --skip-sync-image
unset KUBECONFIG
ac get productmanifest v<target-version>
```

Continue when the script completes without an error and `READY` is `True`. Otherwise, see [Recover a Missing Aligned Extension Package](../troubleshooting.mdx#recover-missing-aligned-package).

### Run the Final Preflight Check \{#final-preflight}

```bash
export KUBECONFIG=<global-kubeconfig>   # upgrade.sh uses kubectl with the kubeconfig in KUBECONFIG
bash upgrade.sh --preflight
unset KUBECONFIG
```

Continue when `Summary` shows `Passed` or `PassedWithWarnings`. Otherwise, resolve the reported checks as described in [Handle Preflight Blocks](../troubleshooting.mdx#handle-preflight-blocks-when-needed), then run the check again. `AdminAckRequired` can appear for the first time here, after the target CVO is deployed; handle it as described in [Handle Administrator Acknowledgement Gates](../troubleshooting.mdx#handle-administrator-acknowledgement-gates).

### Request the Upgrade \{#request-the-upgrade}

:::warning
An upgrade cannot be rolled back. On Huawei DCS, the request also replaces every node with a new VM, one at a time; on Bare Metal, it reinstalls every host, one at a time. This happens on every minor upgrade, and on a patch upgrade when the target changes the Kubernetes build or the Alauda OS image.
:::

List the available updates, then request the target version exactly as it is listed:

```bash
ac adm upgrade
ac adm upgrade --cluster=global --to=<target-version>
```

### Monitor the Upgrade \{#monitor-the-upgrade}

```bash
ac adm upgrade status --cluster=global
```

Run the command again until `Current` shows the target version and the `Ready` condition is `True`. Add `--verbose` to see every check and stage.

On Huawei DCS and Bare Metal, also follow the Kubernetes upgrade:

```bash
ac -n cpaas-system get infraclusterversion global
```

`CURRENT` advances through each intermediate Kubernetes version. Continue when `PHASE` is `Succeeded`. While the control plane nodes are replaced, a command can fail to connect; run it again. The upgrade continues on its own.

If `Upgrade` shows `Blocked` or `Retrying`, see [Inspect Upgrade State](../troubleshooting.mdx#inspect-upgrade-state). On Huawei DCS and Bare Metal, if the upgrade stays `InProgress` in the `Kubernetes` stage, read the `Stalled` condition of the `InfraClusterVersion` as described there. Fix the reported cause and the upgrade continues; if it cannot be fixed, contact technical support.

### Upgrade Kubernetes on Huawei Cloud Stack or VMware vSphere \{#upgrade-kubernetes-hcs-vsphere}

:::warning
On Huawei Cloud Stack and VMware vSphere, upgrade Kubernetes right after the upgrade request of the cluster completes, for every upgrade, including a patch upgrade whose Kubernetes build changes. Do not leave the cluster on the new ACP version with the previous Kubernetes version.
:::

Follow [Upgrade Kubernetes on Huawei Cloud Stack and VMware vSphere](../upgrade_kubernetes_hcs_vsphere.mdx) for the `global` cluster, then return to this page.

On Huawei DCS, Bare Metal, and non-Alauda OS clusters, skip this step.

### Upgrade the Agnostic Extensions \{#upgrade-agnostic-extensions}

The upgrade request does not upgrade Extensions (Operators and Cluster Plugins) with the `Agnostic` lifecycle. Upgrade each Agnostic Extension separately by following its own documentation, for example:

- <ExternalSiteLink name="ai" href="/upgrade/upgrade-from-aml-1.2.html" children="Upgrade Alauda AI" />
- <ExternalSiteLink name="devops" href="/upgrade/index.html" children="Upgrade Alauda DevOps" />

If the source ACP version is earlier than 4.3, also upgrade these Agnostic Extensions to versions compatible with the target, or their pages can fail to open: Alauda DevOps v3, Alauda AI Essentials, Alauda Hyperflux, and Alauda Container Platform Data Services Essentials.

### Validate the Upgrade \{#validate}

Complete [Upgrade Validation](../validation.mdx) for the `global` cluster to finish its upgrade.

</Steps>
