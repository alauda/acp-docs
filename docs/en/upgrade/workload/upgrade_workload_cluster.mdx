# Upgrade Workload Clusters

Use this page after the `global` cluster is upgraded; in a DR environment, after both `global` clusters are upgraded. Each workload cluster moves to the ACP version (Distribution Version) that `global` runs now. Unless a step says otherwise, run the commands from the execution host, logged in with `ac login`, on the `global` cluster, which is the primary `global` cluster in a DR environment. Commands for a workload cluster itself run after `ac config use-cluster <cluster-name>`; switch back with `ac config use-cluster global`.

:::warning
Do not start another `global` upgrade while a workload cluster upgrade is running; the platform does not block it. The `global` upgrade pages check this before the upgrade. See [Upgrade Order and Compatibility](../overview.mdx#upgrade-order).
:::

## Before You Upgrade the Clusters \{#before-the-window}

Complete these steps for every cluster that you plan to upgrade, and confirm that each of these clusters has a recent successful etcd backup. See [etcd Backup and Restore](../../configure/backup/etcd.mdx).

<Steps>

### Confirm the `global` Clusters Are Upgraded \{#confirm-global}

Check the ACP version of the `global` cluster, and continue when the address ends with `/kubernetes/global/`, `Current` shows the target ACP version, and the `Ready` condition is `True`:

```bash
ac config use-cluster global
ac whoami --show-server
ac adm upgrade status --cluster=global
```

In a DR environment, also check the standby; the first command prints the standby VIP, and the second must pass in the same way:

```bash
ac --kubeconfig <standby-kubeconfig> whoami --show-server
ac --kubeconfig <standby-kubeconfig> adm upgrade status --cluster=global
```

### Make Operator Packages Available \{#operator-push-fallback}

Extensions (Operators and Cluster Plugins) with the `Aligned` lifecycle upgrade with the cluster. An Aligned Operator needs its target package on every cluster where it is installed; Cluster Plugins published to `global` are available to every cluster. If a cluster did not receive its Operator packages during preparation, for example because it was added later, push the target package of each Aligned Operator installed on it. Packages of Operators that are not installed on the cluster do not block its upgrade. From the execution host:

```bash
read -rsp "Platform token: " PLATFORM_TOKEN; printf '\n'
violet push <operator-package>.tgz --platform-address "https://<platform-address>" \
  --platform-token "${PLATFORM_TOKEN}" --clusters "<cluster-name>"
```

### Run Preflight Checks for the Cluster \{#run-preflight}

Run this check only after the `global` clusters are upgraded; before that, it reports `Retry` with the reason `GlobalVersionPending`. In the `installer/` directory of the extracted target Core Package, run the script with the `kubeconfig` of the `global` cluster, `<primary-kubeconfig>` in a DR environment. Continue when the second command prints its VIP:

```bash
export KUBECONFIG=<global-kubeconfig>   # upgrade.sh uses kubectl with the kubeconfig in KUBECONFIG
ac whoami --show-server
bash upgrade.sh --preflight --cluster=<cluster-name>
unset KUBECONFIG
```

Continue when `Summary` shows `Passed` or `PassedWithWarnings`. Otherwise, fix each blocking check before you upgrade the cluster, as described in [Handle Preflight Blocks](../troubleshooting.mdx#handle-preflight-blocks-when-needed), and run the check again. The `ResourcePatch` objects that `ResourcePatchUpgradeable` names are on the workload cluster, so run the exemption commands on it after `ac config use-cluster <cluster-name>`, then switch back with `ac config use-cluster global`.

On Huawei DCS and Bare Metal, if `InfraClusterVersionPreflight` reports `PreflightPending`, the checks are not evaluated yet; run the preflight again after 5 minutes. If it reports `PreflightUnconsumed`, contact technical support. To read its individual checks, run the following on the `global` cluster; for the meaning of each check and what to do, see [Kubernetes Upgrade Checks](../troubleshooting.mdx#infra-preflight-checks).

```bash
ac config use-cluster global
ac -n cpaas-system get infraclusterversionpreflight -l upgrade.alauda.io/cluster=<cluster-name>
ac -n cpaas-system get infraclusterversionpreflight <preflight-name> \
  -o jsonpath='{range .status.checks[*]}{.name}{"\t"}{.severity}{"\t"}{.state}{"\t"}{.reason}{"\t"}{.message}{"\n"}{end}'
```

### Check Huawei Cloud Stack and VMware vSphere Clusters \{#check-vsphere}

Only for clusters created with these providers. The platform does not check their Kubernetes upgrade in advance, so check the rollout settings, the pools, and the provider version before you upgrade them. For each such cluster, read its rollout settings on the `global` cluster:

```bash
ac config use-cluster global
KCP=$(ac -n cpaas-system get clusters.cluster.x-k8s.io <cluster-name> -o jsonpath='{.spec.controlPlaneRef.name}')
ac -n cpaas-system get kubeadmcontrolplane "${KCP}" -o jsonpath='replicas={.spec.replicas} maxSurge={.spec.rolloutStrategy.rollingUpdate.maxSurge}{"\n"}'
ac -n cpaas-system get machinedeployment -l cluster.x-k8s.io/cluster-name=<cluster-name> \
  -o custom-columns='NAME:.metadata.name,TYPE:.spec.strategy.type,SURGE:.spec.strategy.rollingUpdate.maxSurge'
```

Then read the pools and the provider:

<Tabs>
  <Tab label="Huawei Cloud Stack">

```bash
ac -n cpaas-system get hcsmachineconfigpool \
  -o custom-columns='NAME:.metadata.name,TOTAL:.status.totalCount,AVAILABLE:.status.availableCount,DISKS:.spec.configs[*].persistentDisks[*].mountPath'
ac -n cpaas-system get apprelease \
  -o custom-columns='NAME:.metadata.name,CHART:.spec.source.charts[*].name,REQUESTED:.spec.source.charts[*].targetRevision,INSTALLED:.status.charts.*.installedRevision,SYNC:.status.conditions[?(@.type=="Sync")].status,HEALTH:.status.conditions[?(@.type=="Health")].status' \
  | grep -E '^NAME|chart-cluster-api-provider-hcs'
```

Every pool of the cluster that lists `DISKS` shows `AVAILABLE` empty or `0`, and the provider shows `REQUESTED` equal to `INSTALLED` with `SYNC` and `HEALTH` `True`.

  </Tab>
  <Tab label="VMware vSphere">

```bash
ac -n cpaas-system get vspheremachineconfigpool -o custom-columns='NAME:.metadata.name,READY:.status.conditions[?(@.type=="Ready")].status'
ac -n cpaas-system get apprelease \
  -o custom-columns='NAME:.metadata.name,CHART:.spec.source.charts[*].name,REQUESTED:.spec.source.charts[*].targetRevision,INSTALLED:.status.charts.*.installedRevision,SYNC:.status.conditions[?(@.type=="Sync")].status,HEALTH:.status.conditions[?(@.type=="Health")].status' \
  | grep -E '^NAME|chart-cluster-api-provider-vsphere'
```

Every pool of the cluster reports `True`, and the provider shows `REQUESTED` equal to `INSTALLED` with `SYNC` and `HEALTH` `True`.

  </Tab>
</Tabs>

Continue when `replicas` is 3 or more, `maxSurge` and every `SURGE` are `0` (an empty value counts as `1`; a MachineDeployment of `TYPE` `OnDelete` needs none), and the pools and the provider pass the check of their tab. With fewer than three control-plane nodes, contact technical support. If the provider does not match, also contact technical support. If `maxSurge` or a pool differs, correct it before you upgrade the cluster, as described in [Prepare the Clusters](../pre-upgrade.mdx#prepare-alauda-os-clusters).

### Check DR Synchronization \{#check-dr-sync}

In a DR environment, check synchronization on a control plane node of the standby `global` cluster; the check address is reachable only from inside the cluster. This check is the only command on this page that runs on a node; then return to the execution host. Continue when the output lists no missed keys and no surplus keys; otherwise, restore synchronization before you upgrade the cluster. See [Global Cluster Disaster Recovery Does Not Synchronize](../troubleshooting.mdx#dr-sync-diagnostics).

```bash
export KUBECONFIG=/etc/kubernetes/admin.conf
mirror_svc=$(kubectl get svc -n cpaas-system etcd-sync-monitor -o jsonpath='{.spec.clusterIP}')
if [[ $mirror_svc =~ ^[0-9a-fA-F:]+$ ]]; then mirror_host="[$mirror_svc]"; else mirror_host="$mirror_svc"; fi
curl -g "http://${mirror_host}/check"
```

</Steps>

## Upgrade a Workload Cluster \{#upgrade-a-workload-cluster}

<Steps>

### Request the Upgrade \{#request-the-upgrade}

:::warning
An upgrade cannot be rolled back. On Huawei DCS, the request also replaces every node with a new VM, one at a time; on Bare Metal, it reinstalls every host, one at a time. This happens on every minor upgrade, and on a patch upgrade when the target changes the Kubernetes build or the Alauda OS image.
:::

Select the `global` cluster, list the available updates of the workload cluster, then request the version it lists as `<target-version>`, for example `4.5.0`. Each cluster has its own request; repeat it for each cluster that you upgrade. The platform upgrades a limited number of clusters at the same time, and the rest wait.

```bash
ac config use-cluster global
ac whoami --show-server
ac adm upgrade --cluster=<cluster-name>
ac adm upgrade --cluster=<cluster-name> --to=<target-version>
```

### Monitor the Upgrade \{#monitor-the-upgrade}

```bash
ac adm upgrade status --cluster=<cluster-name>
ac -n cpaas-system get infraclusterversion <cluster-name>   # Huawei DCS and Bare Metal
```

Run the commands again until `Current` shows the target version and the `Ready` condition is `True`; add `--verbose` to see every check and stage. If `Upgrade` shows `Blocked` or `Retrying`, see [Inspect Upgrade State](../troubleshooting.mdx#inspect-upgrade-state). On Huawei DCS and Bare Metal, if the upgrade stays `InProgress` in the `Kubernetes` stage, read the `Stalled` condition of the `InfraClusterVersion` as described there. Fix the reported cause and the upgrade continues; if it cannot be fixed, contact technical support.

On Huawei DCS and Bare Metal, `CURRENT` of the `InfraClusterVersion` advances through each intermediate Kubernetes version; also wait until `PHASE` is `Succeeded`. Until then, do not edit the cluster's `KubeadmControlPlane`, `MachineDeployment` resources, or their templates.

### Upgrade Kubernetes on Huawei Cloud Stack or VMware vSphere \{#upgrade-kubernetes-hcs-vsphere}

:::warning
On Huawei Cloud Stack and VMware vSphere, upgrade Kubernetes right after the upgrade request of the cluster completes, for every upgrade, including a patch upgrade whose Kubernetes build changes. Do not leave the cluster on the new ACP version with the previous Kubernetes version.
:::

Follow [Upgrade Kubernetes on Huawei Cloud Stack and VMware vSphere](../upgrade_kubernetes_hcs_vsphere.mdx) for the workload cluster on the `global` cluster (the primary in a DR environment), then return to this page. On Huawei DCS, Bare Metal, and non-Alauda OS clusters, skip this step.

### Upgrade the Agnostic Extensions \{#upgrade-agnostic-extensions}

The upgrade request does not upgrade Extensions (Operators and Cluster Plugins) with the `Agnostic` lifecycle. Upgrade each Agnostic Extension separately by following its own documentation, for example:

- <ExternalSiteLink name="ai" href="/upgrade/upgrade-from-aml-1.2.html" children="Upgrade Alauda AI" />
- <ExternalSiteLink name="devops" href="/upgrade/index.html" children="Upgrade Alauda DevOps" />

If the source ACP version is earlier than 4.3, also upgrade these Agnostic Extensions to versions compatible with the target, or their pages can fail to open: Alauda DevOps v3, Alauda AI Essentials, Alauda Hyperflux, and Alauda Container Platform Data Services Essentials.

### Validate the Cluster \{#validate}

Complete [Upgrade Validation](../validation.mdx) for each workload cluster that you upgraded to finish its upgrade.

</Steps>
