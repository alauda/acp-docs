# Upgrade Kubernetes on Alauda OS for Workload Clusters

This section provides instructions for upgrading Kubernetes on Alauda OS workload clusters managed by Cluster API.

## Upgrade Overview

Cluster upgrades on Alauda OS follow a two-phase approach:

1. **Phase 1**: Upgrade ACP Core and the cluster Distribution Version through CVO. See [Upgrade the Distribution Version](../upgrade_workload_cluster.mdx).
2. **Phase 2**: Upgrade Kubernetes and replace nodes with the matching Alauda OS image. This section describes Phase 2.

How Phase 2 runs depends on the infrastructure provider:

| Provider | Phase 2 |
|---|---|
| Huawei DCS | Automatic. The same platform upgrade request upgrades Kubernetes and Alauda OS through every intermediate version. See [Upgrade Kubernetes on Huawei DCS](./huawei-dcs.mdx). |
| Bare Metal | Automatic. The same platform upgrade request upgrades Kubernetes and the OS image through every intermediate version. See [Upgrade Kubernetes on Bare Metal](./bare-metal.mdx). |
| Huawei Cloud Stack | Manual. After Phase 1, follow [Upgrade Kubernetes on Huawei Cloud Stack](./huawei-cloud-stack.mdx). |
| VMware vSphere | Manual. After Phase 1, follow [Upgrade Kubernetes on VMware vSphere](./vmware-vsphere.mdx). |

:::info
For Huawei DCS and Bare Metal clusters, the platform upgrade is reported complete only after Kubernetes and the OS image reach the target version. For Huawei Cloud Stack and VMware vSphere clusters, it is reported complete after Phase 1, and Kubernetes and the OS image stay at the previous version until you complete Phase 2.

Phase 1 prerequisites, supported ACP upgrade paths, artifact preparation, and CVO procedures are described in the pages listed under Phase 1 below. This section describes the Alauda OS Kubernetes and OS replacement in Phase 2.
:::

For how the Distribution Version relates to the Kubernetes and OS baseline, see [Distribution Version vs Kubernetes Version](../../overview.mdx#distribution-version-vs-kubernetes-version). Use [OS Support Matrix](../../../overview/alauda_os_support_matrix.mdx) for the exact patch-specific Kubernetes and component values offered for Phase 2.

### Prerequisites

- Complete [Pre-Upgrade Preparation](../../pre-upgrade.mdx), including validation that the source ACP release can upgrade to the target Distribution Version.
- On Huawei Cloud Stack and VMware vSphere, complete the ACP Core and Distribution Version upgrade before starting Phase 2. On Huawei DCS and Bare Metal, complete the provider-specific preparation before you request the platform upgrade.
- Verify that the control plane is reachable and healthy.
- Verify that all nodes are in the `Ready` state.
- Take and verify the backups required by the provider-specific procedure.
- Confirm sufficient IP or machine-slot capacity for rolling replacement.

## Phase 1: Upgrade ACP Core and Distribution Version

Use the following pages as the single procedure owner for this phase:

- [Upgrade Overview](../../overview.mdx)
- [Pre-Upgrade Preparation](../../pre-upgrade.mdx)
- [Upgrade the Distribution Version of the `global` Cluster](../../global/upgrade_global_cluster.mdx)
- [Upgrade the Distribution Version of Workload Clusters](../upgrade_workload_cluster.mdx)

Follow that sequence to prepare artifacts and plugin packages, upgrade the `global` tier, and then move each workload cluster to the target Distribution Version through CVO. Do not use intermediate Kubernetes hops in Phase 2 to bypass an unsupported ACP Core upgrade path.

:::info
Fleet Essentials 1.0.4 and later can use the ACP 4.3-and-later CVO workflow to request a Distribution Version upgrade. For Huawei DCS and Bare Metal clusters, that request also performs Phase 2. For Huawei Cloud Stack and VMware vSphere clusters, it covers Phase 1 only; use the provider-specific YAML procedure in this section for Phase 2.
:::

### Post-Upgrade Verification

After the Distribution Version upgrade completes:

- Verify that the cluster reports the target Distribution Version and CVO is no longer progressing or blocked.
- Confirm that the target row and all required intermediate rows exist in the OS Support Matrix.
- On Huawei Cloud Stack and VMware vSphere, proceed to Phase 2 only after the management-side Cluster API providers are healthy. See [Identify the Installed Provider Version](#identify-the-installed-provider-version).

### Identify the Installed Provider Version \{#identify-the-installed-provider-version}

Do not infer the provider version from the ACP Distribution Version. Inspect the provider `AppRelease` on the management cluster. The resource name can vary, so the following command finds the provider by chart name and prints the requested and installed revisions:

```bash
kubectl -n cpaas-system get apprelease \
  -o custom-columns='APPRELEASE:.metadata.name,CHART:.spec.source.charts[*].name,REQUESTED:.spec.source.charts[*].targetRevision,INSTALLED:.status.charts[*].installedRevision,PHASE:.status.charts[*].phase'
```

Find the row whose chart name ends with `chart-cluster-api-provider-dcs`, `chart-cluster-api-provider-hcs`, `chart-cluster-api-provider-vsphere`, or `chart-cluster-api-provider-baremetal`, as appropriate. If the requested and installed revisions differ, or the provider chart is not in `Success`, finish or repair the provider upgrade before starting the cluster upgrade.

## Phase 2: Upgrading Kubernetes Version

On Huawei DCS and Bare Metal, Phase 2 runs automatically as part of the platform upgrade. The provider pages describe the preparation, the preflight checks, and monitoring.

On Huawei Cloud Stack and VMware vSphere, upgrade Kubernetes and the Alauda OS image through the provider-specific Cluster API procedure after Phase 1.

Kube-OVN and CoreDNS are upgraded automatically, so the provider-specific procedures do not set the Kube-OVN chart version or the CoreDNS image tag. See [Kube-OVN and CoreDNS](#kube-ovn-coredns).

### Required kubelet patch for Kubernetes 1.35 \{#kubernetes-1-35-kubelet-patch}

On Huawei DCS and Bare Metal, the platform applies this setting itself. The rest of this section applies to Huawei Cloud Stack and VMware vSphere.

When an upgrade hop targets Kubernetes 1.35 or later, the kubelet patch file at `/etc/kubernetes/patches/kubeletconfiguration0+strategic.json` must include the following setting:

```json
{
  "imagePullCredentialsVerificationPolicy": "NeverVerify"
}
```

In Kubernetes 1.35, kubelet credential verification can apply even when an image is already present on the node. `NeverVerify` tells the kubelet not to verify pull credentials for these pre-pulled images. Add this field only to kubelet configurations that will run on Kubernetes 1.35 or later; do not add it for Kubernetes 1.34 or earlier.

Apply this change only on the hop to Kubernetes 1.35 or later:

- For control-plane nodes, update the matching file in `KubeadmControlPlane.spec.kubeadmConfigSpec.files` in the **same edit** that changes `spec.version` to 1.35. Do not roll out the policy separately while the target version is still 1.34.
- For worker nodes, create a new `KubeadmConfigTemplate` containing the updated file, then update `MachineDeployment.spec.template.spec.bootstrap.configRef.name` in the same edit as the target version and infrastructure template.
- If the file uses `contentFrom.secret`, verify that the referenced Secret key contains this parameter. An older version-specific Secret is not automatically suitable for the 1.35 hop.

For Kubernetes 1.34 or earlier, omit `imagePullCredentialsVerificationPolicy`. Add it only on the upgrade hop whose target is Kubernetes 1.35 or later.

See platform-specific guides:
- [Huawei DCS](./huawei-dcs.mdx)
- [Huawei Cloud Stack](./huawei-cloud-stack.mdx)
- [VMware vSphere](./vmware-vsphere.mdx)
- [Bare Metal](./bare-metal.mdx)

## Kube-OVN and CoreDNS \{#kube-ovn-coredns}

On Alauda OS clusters, Kube-OVN and CoreDNS are never upgraded by hand. This applies to every provider: Huawei DCS, Bare Metal, Huawei Cloud Stack, and VMware vSphere. Which component upgrades them depends on the release the cluster is upgraded from:

- **Upgrades from a release earlier than ACP v4.5**: before v4.5, the infrastructure provider manages Kube-OVN and CoreDNS on its clusters. The provider is upgraded together with the platform. Once a cluster reaches v4.5, the provider hands Kube-OVN and CoreDNS over to the platform, and the platform then upgrades both components automatically. The handoff takes place after the Kubernetes upgrade and can finish after the platform reports the upgrade complete; on a `global` cluster, this can take up to about an hour and a half. Until then, the previous Kube-OVN version keeps running. This is expected.
- **Upgrades from ACP v4.5 or later**: after the handoff, the platform upgrades Kube-OVN and CoreDNS automatically as part of every platform upgrade.

## Preparing for Cross-Version Upgrades  \{#cross-version-preparation}

When the target ACP Distribution Version is more than one Kubernetes minor above the cluster's current version, additional preparation is required. On Huawei DCS and Bare Metal, complete it before you request the platform upgrade; on Huawei Cloud Stack and VMware vSphere, complete it before starting Phase 2. Single-minor upgrades skip this section.

Each ACP minor version runs one Kubernetes minor version:

| ACP | Kubernetes |
|---|---|
| 4.0 | 1.31 |
| 4.1 | 1.32 |
| 4.2 | 1.33 |
| 4.3 | 1.34 |
| 4.4 | 1.35 |
| 4.5 | 1.36 |

Kubernetes moves one minor version at a time, so every ACP minor version between the current and the target version needs its Alauda OS image.

### Choosing Intermediate Versions \{#cross-version-intermediate}

For each intermediate ACP minor version, use its latest patch release: the row with the highest Kubernetes version in that minor in [Version Mapping](../../../overview/alauda_os_support_matrix.mdx#version-mapping). On Huawei DCS and Bare Metal, the platform upgrades through the highest staged version of each intermediate minor.

Select the current and target ACP versions to list the versions on the path:

<AlaudaOsUpgradePath>
  Whether an intermediate ACP version also needs an ACP Core upgrade is described in [Pre-Upgrade Preparation](../../pre-upgrade.mdx). The Kubernetes and etcd versions of each ACP version are listed in [Version Mapping](../../../overview/alauda_os_support_matrix.mdx#version-mapping).
</AlaudaOsUpgradePath>

### Choosing the OS \{#cross-version-os}

Every intermediate and target image uses the Alauda OS variant that the cluster runs today: Alauda OS M55, Alauda OS KO, or Alauda OS KU. Do not prepare images of different variants for one ACP version. On Huawei DCS and Bare Metal, the platform selects the image of each version by its Kubernetes version only, so an image of another variant can move the cluster to that variant.

### Example \{#cross-version-example}

A Huawei DCS cluster on ACP v4.3.2 with Alauda OS M55, upgraded to ACP v4.5:

| Step | ACP version | Kubernetes | Prepare |
|---|---|---|---|
| Current | v4.3.2 | v1.34.5-3 | VM template ConfigMap, if the cluster has none |
| Intermediate | v4.4.1 | v1.35.6-acp.9 | Alauda OS M55 image, VM template, ConfigMap; `upgrade.sh --only-sync-image` |
| Target | v4.5 | 1.36 | Alauda OS M55 image, VM template, ConfigMap |

On Bare Metal, the same rows apply: import the images and add their keys to the image catalog instead of creating VM templates and ConfigMaps. See [Update the Image Catalog](./bare-metal.mdx#update-the-image-catalog).

### Step 1 — Confirm Core hops and pre-sync intermediate images

The Distribution Version follows every source-to-target hop offered by CVO, while Kubernetes and the OS image can need more intermediate versions than the ACP Core path. Keep the two apart.

If CVO offers an intermediate Distribution Version as part of the supported Core path, perform the full ACP artifact preparation and Core/CVO upgrade for that hop during Phase 1. This is required for paths such as ACP 4.0.x to 4.4, and `--only-sync-image` does not replace it. Verify `availableUpdates` and `VersionUpgradePath` at every Core hop. For such a hop, prepare and upgrade Aligned plugins as directed by the Phase 1 procedure.

For each intermediate version that is needed only for the Kubernetes and OS rollout, download the corresponding Core package and synchronize only its images into the registry. Do not request an additional Core upgrade for it, and do not run an extra `violet push` for Aligned plugins.

```bash
bash upgrade.sh --only-sync-image
```

See [Sync upgrade artifacts](../../global/upgrade_global_cluster.mdx#sync-upgrade-artifacts) for command options.

The rollout pulls the Kubernetes component images of each intermediate version, such as etcd and kube-proxy, from the registry. In an air-gapped environment, missing intermediate images prevent the new control plane components from starting.

### Step 2 — Stage intermediate OS images for the provisioning mechanism

For each intermediate version, make the Alauda OS image published for that ACP release available to the node provisioning mechanism:

- **Huawei DCS**: upload the OS image, register it as a VM template, and create its VM template ConfigMap. See [Prepare the Cluster](./huawei-dcs.mdx#automatic-prepare).
- **VMware vSphere and Huawei Cloud Stack**: upload the OS image and register it as a VM template or VM image. Record the name it is registered under — the machine templates reference that name.
- **Bare metal**: import the OS images and add the version and its etcd image to `elemental-image-catalog`. See [Update the Image Catalog](./bare-metal.mdx#update-the-image-catalog).

### Step 3 — Upgrade through each intermediate version

On Huawei DCS and Bare Metal, there is nothing more to do: the platform plans the path from the staged versions and upgrades through it.

On Huawei Cloud Stack and VMware vSphere, repeat the platform-specific Phase 2 procedure for each intermediate version in turn, using its row in [OS Support Matrix](../../../overview/alauda_os_support_matrix.mdx) for `KubeadmControlPlane` and `MachineDeployment` values. For each hop, upgrade the control plane, followed by workers. On the hop to Kubernetes 1.35, also apply the [required kubelet patch](#kubernetes-1-35-kubelet-patch) to the control-plane and worker bootstrap configurations. Complete the whole hop before starting the next one. After all intermediate hops succeed, apply the same procedure once more for the target version.
