# Upgrade Kubernetes on Bare Metal

On bare metal, the platform upgrades Kubernetes and the host OS automatically. A single platform upgrade request moves the cluster through ACP Core, Kubernetes, and the OS image, and the upgrade is reported complete only after every node runs the target version. Your part is to import the OS images, add them to the image catalog, check the hosts, and watch the progress.

:::info
**Where this page fits in the full ACP upgrade flow**

The full ACP upgrade flow — including upgrade artifact synchronization, the platform upgrade request, Aligned plugin upgrades, and Agnostic plugin upgrades from Marketplace — is documented in the following pages. This page covers what is specific to bare-metal clusters:

- [Upgrade Overview (scope and sequencing)](../../overview.mdx)
- [Pre-Upgrade Preparation](../../pre-upgrade.mdx)
- [Upgrade the Distribution Version of the `global` cluster (Core, Aligned, Agnostic)](../../global/upgrade_global_cluster.mdx)
- [Upgrade the Distribution Version of workload clusters (Core, Aligned, Agnostic)](../upgrade_workload_cluster.mdx)

The Kubernetes step on bare metal replaces every node from a new `elemental upgrade` image rather than upgrading binaries in place.
:::

## Key Considerations

Bare-metal upgrades replace every node — they do not run `kubeadm upgrade` on the existing OS. The mechanism is:

1. CAPI deletes one `Machine` according to the rollout strategy.
2. The provider writes a `clean` plan to the inventory's plan secret.
3. The host stops kubelet, deactivates any managed data mounts, clears CRI workload, stops containerd, then returns to `Available` in the same pool.
4. CAPI creates a replacement `Machine`.
5. The provider picks an `Available` inventory from the same pool, resolves the new Kubernetes version against `elemental-image-catalog`, and writes a `reprovision` plan.
6. The host stages managed-volume activation, runs `cloud-init clean` → `elemental upgrade --system <new-image>` → reboot. `initramfs` clears Kubernetes persistent state; managed mount units start before kubelet, and cloud-init re-executes and runs `kubeadm init` / `kubeadm join` against the new control plane.

Two structural consequences operators must internalize before starting:

- **Kubernetes-managed system state is not preserved.** `/var/lib/kubelet`, `/var/lib/containerd`, `/var/lib/etcd`, and `/etc/kubernetes` are cleared by the initramfs cleanup step of every reprovision. Storage v2 does not permit these protected paths as managed data mounts.
- **Declared data volumes can remain on an inventory.** The clean plan deactivates them without wiping their filesystems, and reprovision activates the selected inventory's prepared volumes before kubelet. This is host-local retention, not a backup or data-migration mechanism.
- **The same `MachineInventory` may not be re-picked.** The provider does not guarantee that the inventory released by a `clean` plan is the same one re-allocated to the replacement `Machine`; data does not follow the replacement automatically. Replacements are performed as delete-then-add when `maxSurge=0` (no overlap between old and new node), so pool capacity sizing need only accommodate the desired replica count — old and new nodes do not coexist during the rollout.

## Storage Compatibility Across Provider Upgrades

An existing cluster created before managed storage was introduced remains compatible when `MachineInventory.spec.storage` stays absent or has `volumes: []`. In this unmanaged mode, the storage controller performs no disk operation and does not rewrite the running Machine's plan merely because the management-side provider was upgraded.

This compatibility does **not** mean that managed storage can be enabled in place on every old host:

- Upgrading only the provider and `elemental-operator` on the `global` cluster does not install `elemental-storage-observer.service` or early-boot storage integration into an older host OS.
- Keep `spec.storage` empty on such hosts. To enable managed storage later, reinstall, reset, or replace the host with an approved observer-capable image, then verify the observer service and a fresh `status.observedStorage` report while the inventory is unallocated.
- Configure and Prepare managed volumes only after those host-image prerequisites are satisfied. Do not add a non-empty storage declaration to a running or allocated inventory.

For the preparation and validation procedure, see [Manage Data Disks on Bare-Metal Hosts](../../../configure/nodes/alauda_os/manage-bare-metal-storage.mdx).

## Check COS_STATE Free Space \{#check-cos-state-free-space}

Every reprovision creates a new snapshot on `COS_STATE` and writes the complete target system into it. Because the upgrade targets a *different* image, the partition has to hold two unrelated systems of roughly 3.5 GiB at the same time. A host that is short on space fails part-way through with `no space left on device`, and the failed attempt leaves its partial snapshot behind — so each automatic retry starts with *less* free space than the one before it. Three retries on an 8 GiB partition is enough to fill it completely.

Check this before starting the rollout. Check every host in the affected pools, not only the ones you expect to be replaced: the inventory released by a `clean` plan is not guaranteed to be re-picked, so any `Available` inventory can receive the new image.

On each host:

```bash
# Free space on COS_STATE. Use btrfs, not df — df does not account for snapshot extents.
btrfs filesystem usage -h /

# Retained snapshots
snapper --no-dbus list
```

`Free (estimated)` must be at least **4 GiB** — the target system is roughly 3.5 GiB, plus headroom for btrfs metadata written during the copy. If it is lower, free space before starting the rollout.

### Remove partial snapshots left by a failed upgrade \{#remove-partial-snapshots}

Elemental marks a snapshot `update-in-progress=yes` while it writes into it, and clears the flag only when the upgrade completes. A snapshot that still carries the flag, and is neither the default nor the running one, is the residue of a failed attempt and is safe to delete.

List the snapshots with the three columns that decide this:

```bash
snapper --no-dbus --csvout list --columns number,default,active,userdata
```

Delete a snapshot only when all three conditions hold — `default` is `no`, `active` is `no`, and the userdata column contains `update-in-progress=yes`:

```bash
snapper --no-dbus delete --sync <number>
```

:::warning
Never delete a snapshot whose `default` or `active` column is `yes`. Those are the snapshot the host will boot next and the one it is running now; deleting either leaves the host unable to boot.
:::

Re-run `btrfs filesystem usage -h /` afterwards to confirm the space was actually reclaimed. On a partition that is already 100% full, `snapper delete` can itself fail for lack of metadata space — this is the same condition that let the partial snapshots accumulate in the first place. If deletion fails, treat the host as needing a reinstall rather than retrying the rollout against it.

If the host still has less than 4 GiB free after every partial snapshot is gone, the partition itself is too small. Hosts installed before [COS_STATE sizing](../../../workload_clusters/alauda_os/bare-metal/create_cluster.mdx#size-cos-state) was applied carry an 8 GiB `COS_STATE`, and partition sizes are fixed at install time — growing it requires a reinstall. Plan that separately; do not start the rollout against such a host and expect it to succeed.

## Update the Image Catalog \{#update-the-image-catalog}

`elemental-image-catalog` is the resource that introduces a Kubernetes version to the bare-metal provider. Add the target version and every intermediate version before the upgrade starts.

:::info
The bare-metal provider plugin does not carry any Kubernetes version or OS image. Its chart creates `elemental-image-catalog` with no entries, and upgrading the plugin or the Distribution Version does not add one. Every new Kubernetes version must be added explicitly, after its OS images are in the platform registry.
:::

First import the OS images of the target version and of every intermediate version into the platform registry, as described in [OS Images Imported and Image Catalog Populated](../../../workload_clusters/alauda_os/bare-metal/create_cluster.mdx#os-images-and-image-catalog). See [Preparing for Cross-Version Upgrades](./index.mdx#cross-version-preparation) for the intermediate versions.

Then select the current and target ACP versions, the OS and the architecture of the hosts, and enter the tag of each imported OS image below. One command adds the OS image key and the etcd key of every intermediate version and of the target version.

<BareMetalImageCatalog mode="path">
  The command creates a `ResourcePatch` that records the change. Do not delete it. Before the next platform upgrade, exempt it for the target version as described in [Handle Preflight Blocks](../../troubleshooting.mdx#handle-preflight-blocks-when-needed); otherwise the `ResourcePatchUpgradeable` preflight check blocks that upgrade.
</BareMetalImageCatalog>

If the pools contain hosts of more than one architecture or OS, run the generated command for each combination.

If a key is missing when CAPI creates the replacement `Machine`, the resulting `BaremetalMachine` enters `Failed` with `ImageResolved=False / Reason=ImageCatalogMiss` and no `reprovision` plan is written. Adding the key later does **not** restart it: the `BaremetalMachine` stays `Failed` until you delete that `Machine` and its owner creates a new one. With `maxSurge: 0` the node being replaced is already gone at that point, so add the keys before you change any version.

**Alternative: chart override.** If the bare-metal provider plugin is installed with a chart override for the image catalog, add the keys under `provider.imageCatalog.images` instead, and reapply the plugin. The values use `global.registry.address` as the registry:

```yaml
provider:
  imageCatalog:
    images:
      <kubernetes-version>:
        repository: tkestack/baremetal-base-image
        tag: <os-image-tag>
      <kubernetes-version>_etcd:
        repository: acp/k8s/etcd
        tag: <etcd-tag>
```

Write each Kubernetes version with its leading `v`, such as `v1.36.4-acp.3`, and use the key format in [OS Image Keys per Architecture and OS](#catalog-key-format) for hosts of another architecture or OS. The chart renders `elemental-image-catalog` from these values, so the values must keep every existing key.

### Add the etcd Image for Each Version \{#catalog-etcd-key}

For each Kubernetes version, the catalog also holds a `<kubernetes-version>_etcd` key whose value is the etcd image of the same release, with the tag from the **etcd** column of [Version Mapping](../../../overview/alauda_os_support_matrix.mdx#version-mapping). The upgrade reads the tag from this key when it upgrades the control plane to that version. The provider uses only the tag of this value.

### OS Image Keys per Architecture and OS \{#catalog-key-format}

The provider looks up the OS image of a host by the key `<kubernetes-version>_<arch>_<os-id>`, for example `v1.35.6-acp.9_arm64_alaudaos.k.25`. Both parts come from labels on the host's `MachineInventory`:

- `<arch>` is the value of `os.baremetal.alauda.io/arch`, or `amd64` when the label is absent.
- `<os-id>` is the value of `os.baremetal.alauda.io/id`, or `alaudaos.m.55` when the label is absent. Alauda OS M55 uses `alaudaos.m.55`; Alauda OS KO and Alauda OS KU both use `alaudaos.k.25`.

Only hosts with the default OS identifier `alaudaos.m.55` fall back to `<kubernetes-version>_<arch>`, and only `amd64` hosts with that identifier fall back further to the bare `<kubernetes-version>` key. The generator writes the bare key for `amd64` hosts with Alauda OS M55 and the full key for every other combination. Hosts registered on ACP v4.4 or earlier carry neither label, so they resolve to `amd64` and `alaudaos.m.55`: for `amd64` hosts of that kind, the bare `<kubernetes-version>` key is enough.

If a pool contains hosts of another architecture or OS, add a key for every combination at every version. The `UpgradePathResolvable` [preflight check](#preflight-checks) names any missing key.

### Refresh the Installation ISO \{#refresh-installation-iso}

The bare-metal provider uses `base-image` for reprovisioning and does not rebuild SeedImages automatically. Before future host onboarding, refresh `MachineRegistration` / `SeedImage` with the `base-image-iso` imported from the same archive. Do not pair images from different archives or substitute an independently built image.

## Automatic Upgrade \{#automatic-upgrade}

### What the Platform Does \{#automatic-what-the-platform-does}

After you request the platform upgrade, the platform:

1. Checks the cluster before changing anything and blocks the upgrade if a [preflight check](#preflight-checks) fails.
2. Upgrades ACP Core and the Distribution Version.
3. Upgrades Kubernetes one minor version at a time through every intermediate version to the target. The control plane is replaced at every version.
   Worker node pools are replaced at the target version. At an intermediate version, a worker node pool is replaced only when skipping it would leave it more than three minor versions behind the next control plane version. The platform also sets the etcd image tag, adds the Kubernetes 1.35 kubelet setting when the version reaches 1.35, and updates the `capi.cpaas.io/kubernetes` annotation on the `Cluster`.

The platform creates new `BaremetalMachineTemplate` resources for the replaced node groups and keeps the previous ones. It does not change the rollout strategy of the `KubeadmControlPlane` or the `MachineDeployment` resources.

### Prepare the Cluster \{#automatic-prepare}

If the cluster runs an ACP version earlier than v4.3.2, contact technical support before you upgrade it.

Complete these steps before you request the platform upgrade:

1. **Import the OS images and update the catalog.** For the target version and every intermediate Kubernetes version, import the OS images and add the OS image key and the `<kubernetes-version>_etcd` key to `elemental-image-catalog`, as described in [Update the Image Catalog](#update-the-image-catalog). See [Preparing for Cross-Version Upgrades](./index.mdx#cross-version-preparation) for the intermediate rows. In a DR pair, update the catalog on both `global` clusters. Do not change the catalog again until the upgrade completes.
2. **Check COS_STATE on every host.** Every host in the affected pools needs at least 4 GiB free on `COS_STATE` and no partial snapshot from an earlier failed upgrade. The platform cannot check this for you. See [Check COS_STATE Free Space](#check-cos-state-free-space).
3. **Check registry access.** The platform registry is reachable from every host in the cluster.
4. **Check managed storage.** Every inventory with a non-empty storage declaration reports `StoragePrepared=True`, and every currently allocated inventory reports `StorageActive=True`. Record each `BaremetalMachine.status.machineInventoryRef` and the managed filesystem UUIDs before the rollout so that you can detect selection of a different inventory instead of assuming data moved with the Machine.
5. **Check the rollout settings.** The `KubeadmControlPlane` and every `MachineDeployment` use `maxSurge: 0`. With `maxSurge: 0`, a node is removed before its replacement joins. A worker node pool with a single host therefore has no worker while that host is replaced. Make sure its workloads can be scheduled on other nodes, or accept the interruption.
6. **Restore the default Kube-OVN and CoreDNS settings when upgrading from a release earlier than v4.5.** If you changed the CoreDNS Corefile or Kube-OVN parameters by hand, restore the defaults before the upgrade. Otherwise the platform cannot take over Kube-OVN and CoreDNS, and they stay at their previous versions. The same applies when the ClusterIP of the `kube-dns` Service in `kube-system` is not the 10th address of the service CIDR, for example `10.96.0.10` for `10.96.0.0/12`.
7. **Back up etcd.** Use [ACP Cluster Enhancement](../../../configure/backup/etcd.mdx) to create a current on-demand etcd backup. Verify that the newest `status.records` entry reports `result: Success`, record its `backupTimestamp` and `fileName`, and confirm that the corresponding backup archive exists and will remain retrievable if any control-plane node is reprovisioned or becomes unavailable. The platform does not check for a backup.

:::info
The default local archive under `/var/cpaas/backup` can be used for recovery; S3-compatible storage is not required. However, bare-metal replacement can make the original node-local copy unavailable, and the replacement `Machine` is not guaranteed to use the same `MachineInventory`. If your recovery design cannot guarantee access to the local archive after node replacement or failure, keep an off-node copy in S3-compatible storage or another secure location outside the node before starting the upgrade.
:::

### Preflight Checks \{#preflight-checks}

The platform evaluates these checks for the whole upgrade path, including every intermediate version, and repeats the evaluation every 5 minutes. The result appears in the platform upgrade preflight as `InfraClusterVersionPreflight`. When a problem concerns one version on the path, its message starts with `hop <version>: `, for example `hop v1.35.6-acp.9: missing v1.35.6-acp.9_etcd`. After you fix a problem, the check passes on the next evaluation.

To read the checks of a cluster on the `global` cluster:

```bash
kubectl -n cpaas-system get infraclusterversionpreflight -l upgrade.alauda.io/cluster=<cluster-name>
kubectl -n cpaas-system get infraclusterversionpreflight <preflight-name> \
  -o jsonpath='{range .status.checks[*]}{.name}{"\t"}{.severity}{"\t"}{.state}{"\t"}{.reason}{"\t"}{.message}{"\n"}{end}'
```

Until the platform upgrade installs the new Bare Metal provider, the platform upgrade preflight reports `InfraClusterVersionPreflight` as a non-blocking warning with the reason `ProviderCapabilityNotDeclared`. This is expected, and you can start the upgrade. The checks below start as soon as the new provider is installed, not only when the upgrade reaches the Kubernetes step. If a blocking check fails, the upgrade stops at the Kubernetes step with the earlier stages already done, and it resumes by itself once you fix the cause.

| Check | Effect when it fails | What it verifies | What to do |
|---|---|---|---|
| `UpgradePathResolvable` | Blocks | The catalog has an OS image key for every host type in the pools at every version, and a `<kubernetes-version>_etcd` key for every version at which the control plane is upgraded. The OS identity of every host can be read. The message lists the planned path or the missing keys. | Add the missing keys. See [Update the Image Catalog](#update-the-image-catalog). |
| `TargetImagePresent` | Blocks | Every OS image that a replacement host will pull exists in the platform registry. | Import the missing image. Check that the `Cluster` carries `cpaas.io/registry-address` and that the registry is reachable. |
| `RolloutMaxSurgeZero` | Blocks | `maxSurge` is `0` on the `KubeadmControlPlane` and on every `MachineDeployment`. An unset value counts as `1`. | Correct the rollout strategy. |
| `NoFailedMachines` | Blocks | No `BaremetalMachine` of the cluster is `Failed`, and no machine has exceeded the node-join timeout (20 minutes) or the rollout-stall timeout (90 minutes). Machines that are still being replaced within those limits are listed in the message but do not fail the check. | Repair or replace the machines that fail the check. |
| `KubeletPatchReady` | Blocks | When the control plane or a worker node pool reaches Kubernetes 1.35, its bootstrap configuration contains a readable `/etc/kubernetes/patches/kubeletconfiguration0+strategic.json`. On every path, including one that stays below 1.35, every Secret and key referenced by `contentFrom.secret` in any file of the `KubeadmControlPlane` or a worker `KubeadmConfigTemplate` exists. | Add the file, or restore the referenced Secret or key. |
| `ControlPlaneTopology` | Blocks | The cluster uses a `KubeadmControlPlane` and bare-metal machine templates, and no worker node pool runs a newer Kubernetes version than the control plane. | Correct the topology before the upgrade. |
| `NoHostPathWorkloads` | Blocks; can be bypassed with `spec.desiredUpdate.force` on the cluster's `ClusterVersionShadow` | No Pod outside the system namespaces uses a `hostPath` volume, or a `PersistentVolumeClaim` bound to a local or `hostPath` `PersistentVolume`. Their data is lost when the node is replaced. Pods owned by a DaemonSet and static (mirror) Pods are exempt. | Move the data, or set `spec.desiredUpdate.force: true` to accept the loss. |
| `AllNodesReady` | Warning | Every node of the cluster is `Ready`. | Repair the nodes, or confirm that the upgrade can proceed. |
| `PoolHealthy` | Warning | No pool used by the cluster has `Unavailable` members. | Repair or remove the unavailable hosts. |

Only `NoHostPathWorkloads` can be bypassed. `spec.desiredUpdate.force` does not bypass any other blocking check.

### Monitor the Upgrade \{#automatic-monitor}

The platform tracks the Kubernetes and OS upgrade of each cluster in an `InfraClusterVersion` resource on the `global` cluster, named after the cluster:

```bash
kubectl -n cpaas-system get infraclusterversion <cluster-name>
```

```text
NAME   PROVIDER           CURRENT         DESIRED         PHASE         HOLDER                           AGE
c2     BaremetalCluster   v1.34.5-acp.5   v1.35.6-acp.9   Progressing   cluster-api-provider-baremetal   96d
```

`CURRENT` advances after each intermediate version completes. `DESIRED` is the target Kubernetes version. `PHASE` moves from `Pending` to `Preparing` (planning, no change to the cluster yet), `Progressing` (replacing nodes), and `Succeeded`.

Read the conditions, the planned versions, and the current step. A worker node pool that is not replaced at an intermediate version shows the step phase `Skipped`:

```bash
kubectl -n cpaas-system get infraclusterversion <cluster-name> \
  -o jsonpath='{range .status.conditions[*]}{.type}={.status} {.reason}: {.message}{"\n"}{end}'
kubectl -n cpaas-system get infraclusterversion <cluster-name> \
  -o jsonpath='{range .status.hops[*]}{.kubernetesVersion}{"\t"}{.phase}{"\n"}{end}{range .status.steps[*]}{.name}{"\t"}{.phase}{"\t"}{.message}{"\n"}{end}'
kubectl -n cpaas-system get events --field-selector involvedObject.kind=InfraClusterVersion,involvedObject.name=<cluster-name>
```

The upgrade is complete when `PHASE` is `Succeeded` and the `Ready` condition is `True`. If the `Ready` message reports `kube-proxy rollout pending`, the upgrade has completed and kube-proxy on the workload cluster is still rolling out. Check the `kube-system/kube-proxy` DaemonSet. Then run the checks in [Verify the Node Replacement](#verification).

While the upgrade runs, do not edit the `KubeadmControlPlane`, the `MachineDeployment` resources, their templates, or the image catalog.

### Troubleshooting \{#automatic-troubleshooting}

A problem appears as the condition `Stalled=True` with a reason. In `Preparing`, the cluster has not been changed yet: fix the cause, and the platform retries automatically within 15 minutes. In `Progressing`, the platform keeps the upgrade where it is and continues as soon as the cause is cleared.

Before you change any Cluster API resource of the cluster by hand during an upgrade, including deleting a `Machine`, stop the upgrade controller, and start it again when you are done. Otherwise it continues the upgrade while you work:

```bash
kubectl -n cpaas-system scale deployment cluster-api-provider-baremetal-icv-controller --replicas=0
# ... manual changes ...
kubectl -n cpaas-system scale deployment cluster-api-provider-baremetal-icv-controller --replicas=1
```

| Reason | Meaning | What to do |
|---|---|---|
| A preflight check reason, such as `ImageCatalogMiss`, `ImageNotFound`, `NoSpareInventory`, or `FailedMachinesPresent` | The planning step found the same problem as the preflight check. | Fix it as described in [Preflight Checks](#preflight-checks). |
| `RolloutFailed` | A `BaremetalMachine` is `Failed`, or a new machine did not become `Running` within 90 minutes. The message names the machines. | Fix the cause reported by the `BaremetalMachine`, such as `COS_STATE` space, a missing catalog key, or an unreadable OS identity. Remove a faulty host from the pool's `spec.machineInventories`, because the pool may select it again. Then delete the `Machine`; its owner creates a new one and the upgrade continues. A `Failed` machine does not recover on its own, even after you add a missing catalog key. |
| `NodeJoinFailed` | A host was reprovisioned but did not join the cluster within 20 minutes. The message names the `Machine`. | Read the cloud-init and kubelet logs on the host. Confirm that the machine is not an etcd member, then delete the `Machine`. |
| `PoolExhausted` | A new machine has waited more than 15 minutes for an `Available` host. Shorter waits are normal while a replaced host is being cleaned. | Add a host to the pool, or repair the `Unavailable` hosts. |

For node-level symptoms, see [Troubleshooting Node Replacement](#troubleshooting).

If the phase stays `Pending` and the cluster's platform upgrade reports `InfraClusterVersionUnconsumed`, check that the `cluster-api-provider-baremetal-icv-controller` Deployment in `cpaas-system` is running.

#### Correct Hosts on a Different Image \{#correct-image-mismatch}

If the catalog changed during the upgrade, some replaced hosts can run a different image than the catalog now lists. The upgrade still completes and reports a Warning event `ImageMismatch` that names the `BaremetalMachine` objects and both images. After the upgrade is `Succeeded`, confirm that the catalog holds the image you want, then replace the hosts of the affected group:

```bash
# MachineDeployment
kubectl -n cpaas-system patch machinedeployment <md-name> --type merge \
  -p "{\"spec\":{\"rolloutAfter\":\"$(date -u +%Y-%m-%dT%H:%M:%SZ)\"}}"
# KubeadmControlPlane
kubectl -n cpaas-system patch kubeadmcontrolplane <kcp-name> --type merge \
  -p "{\"spec\":{\"rolloutAfter\":\"$(date -u +%Y-%m-%dT%H:%M:%SZ)\"}}"
```

Cluster API then replaces every machine of that group according to its rollout strategy, and each host installs the image currently in the catalog. If an upgrade is in progress, stop the upgrade controller first.

### No Rollback \{#automatic-no-rollback}

An automatic upgrade only moves forward. It cannot be paused, cancelled, or rolled back, and changing the requested platform version does not stop it: the current upgrade finishes first. Every reprovisioned host has already replaced its OS image and cleared its Kubernetes state. If the cluster cannot be repaired forward, restore it from the verified pre-upgrade backup by following the [ACP etcd restore procedure](../../../configure/backup/etcd.mdx#etcd-restore).

## Verify the Node Replacement \{#verification}

After the upgrade completes:

```bash
kubectl -n cpaas-system get baremetalmachines.infrastructure.cluster.x-k8s.io \
  -l cluster.x-k8s.io/cluster-name=<cluster-name> \
  -o custom-columns='NAME:.metadata.name,PHASE:.status.phase,INVENTORY:.status.machineInventoryRef.name,PLAN_SECRET:.status.planSecretRef.name'
kubectl -n cpaas-system get machines.cluster.x-k8s.io \
  -l cluster.x-k8s.io/cluster-name=<cluster-name>
kubectl get nodes -o wide
```

For the target cluster, every current `BaremetalMachine` should be `Running`, every CAPI `Machine` should report the new `spec.version`, and every workload `Node` should be `Ready` with the new `kubelet` version.

For each current `BaremetalMachine`, use the `INVENTORY` and `PLAN_SECRET` columns to verify the inventory and plan that back the running node:

```bash
kubectl -n cpaas-system get machineinventories.elemental.cattle.io <inventory-name> \
  -o jsonpath='{.status.plan.state}{" storage="}{.status.storage.phase}{"\n"}'
kubectl -n cpaas-system get secret <plan-secret-name> \
  -o jsonpath='{.metadata.annotations.baremetal\.alauda\.io/plan\.type}{"\n"}'
```

Each referenced `MachineInventory` should report `Applied`, and each referenced plan Secret should report `reprovision`. Apply this check only to inventories referenced by the current `BaremetalMachine` objects. A spare inventory that did not participate in the rollout may have no `reprovision` plan. An inventory that completed a `clean` plan but was not selected for a replacement Machine may still report `clean`; neither case means that the rollout is incomplete.

For an inventory with managed volumes, also verify `status.storage.phase=Active`, `StoragePrepared=True`, `StorageActive=True`, and `BaremetalMachine.status.conditions[StorageReady]=True/AllVolumesReady`. Compare its current filesystem UUIDs with the pre-upgrade record. A different UUID usually means a different inventory was selected; it must not be interpreted as the original data having migrated.

`MachineInventoryPool.status` should satisfy `available + allocated + preparing + reprovisioning + unavailable = total` with `preparing = reprovisioning = 0`. `available` may remain greater than zero when the pool contains spare inventories; those inventories are outside the plan verification above.

## Troubleshooting Node Replacement \{#troubleshooting}

| Issue | What to check |
|---|---|
| Rollout stuck on the first new node | `BaremetalMachine.status.conditions[ImageResolved]` — confirm the new key is in `elemental-image-catalog` and that the `Cluster` carries `cpaas.io/registry-address`. |
| Inventory does not become allocatable after clean | Check `MachineInventory.status.storage` and `status.observedStorage`. Managed volumes must be confirmed inactive and Prepared from a fresh host observation before the inventory can return to the allocation set. |
| Replacement Machine waits on `StorageReady` | Verify that the selected inventory is the intended one, required device IDs and filesystem UUIDs still match, required mount units are active, and the host produced a fresh post-reboot observation. |
| Host reboots into a state that never joins the cluster | `MachineInventory.status.plan.state` (`Failed` is terminal); inspect the host's serial console for `elemental upgrade` errors. Verify the platform registry is reachable from the host. |
| `elemental upgrade` fails with `no space left on device` | The `state` partition is too small — an 8 GiB `COS_STATE` cannot hold the running system and an upgrade to a different image at the same time. Each failed attempt also leaves a partial snapshot behind, so free space keeps shrinking. Recover by removing them as described in [Remove partial snapshots left by a failed upgrade](#remove-partial-snapshots), then let the plan retry. Hosts installed before [COS_STATE sizing](../../../workload_clusters/alauda_os/bare-metal/create_cluster.mdx#size-cos-state) was applied need a reinstall to grow the partition. |
| New control-plane node fails `kubeadm join` | Confirm the VIP is still reachable; `alive` may have lost the lock. Check `kubectl -n kube-system get lease`, `ipvsadm -Ln`, `keepalived` logs from the static pod. |
| Worker rollout stalls with `MachineDeployment.spec.strategy.rollingUpdate.maxSurge > 0` set | Bare-metal pools cannot honour over-provisioning. Set `maxSurge=0` and bump `maxUnavailable` to budget more parallel replacements within the pool. During an upgrade, stop the upgrade controller before you edit the `MachineDeployment`; see [Troubleshooting](#automatic-troubleshooting). |
| Pool capacity exhausted mid-rollout | `MachineInventoryPool.status.available=0` and `allocated` still includes the not-yet-replaced nodes. Add another `MachineInventory` to the pool to free the queue, or wait for in-flight `Preparing` nodes to drain. |

For the full operator-side state machine reference (every condition reason and recovery action), see [Provider Overview](../../../workload_clusters/alauda_os/bare-metal/overview.mdx#clean-reprovision).
