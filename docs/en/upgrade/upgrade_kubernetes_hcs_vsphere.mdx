# Upgrade Kubernetes on Huawei Cloud Stack and VMware vSphere

On Huawei Cloud Stack and VMware vSphere, the upgrade request moves ACP Core and the installed Extensions (Operators and Cluster Plugins) with the `Aligned` lifecycle to the target ACP version (Distribution Version), but the nodes keep the previous Kubernetes version and Alauda OS image. Use this page to replace the nodes. Go through the procedure once for each Kubernetes version on the upgrade path: every intermediate Kubernetes version, then the target.

:::warning
Every upgrade must bring Kubernetes to the version of the target ACP release, including a patch upgrade whose Kubernetes build changes. Upgrade Kubernetes right after the upgrade request of the cluster completes; do not leave the cluster on the new ACP version with the previous Kubernetes version.
:::

Run every command from the execution host, after `ac login`, on the `global` cluster that manages the cluster you upgrade. All objects are in the `cpaas-system` namespace.

- For a `global` cluster, use `global` as `<cluster-name>`. For the standby `global` cluster in a DR environment, use its kubeconfig instead of `ac login`.
- For a workload cluster, use the primary `global` cluster. The standby does not act on workload clusters.

## Before You Begin \{#before-you-begin}

Select the `global` cluster that runs the commands, and confirm that the printed address ends with `/kubernetes/global/`:

```bash
ac config use-cluster global
ac whoami --show-server
```

For the standby `global` cluster in a DR environment, replace the first command with `export KUBECONFIG=<standby-kubeconfig>`; the second command then prints the VIP of the standby, and every later `ac` command on this page uses this kubeconfig.

Also confirm that:

- The Alauda OS image of every version on the path is staged, and you recorded its name: the image in each Huawei Cloud Stack region and project that the cluster uses, or the VM template in each vCenter datacenter that the cluster uses. Otherwise, complete [Stage the Alauda OS Images](./pre-upgrade.mdx#stage-alauda-os-images) first.
- The cluster has a recent successful etcd backup, as described in [Check the etcd Backup](./pre-upgrade.mdx#etcd-backup).

Then run the following checks on the same cluster.

### Check the Upgrade Request \{#check-upgrade-request}

```bash
ac adm upgrade status --cluster=<cluster-name>
```

Continue when `Current` shows the target version and `Ready` is `True`; otherwise, finish the upgrade request on the page you came from first.

### Check the Provider Version \{#identify-the-installed-provider-version}

```bash
ac -n cpaas-system get apprelease \
  -o custom-columns='APPRELEASE:.metadata.name,CHART:.spec.source.charts[*].name,REQUESTED:.spec.source.charts[*].targetRevision,INSTALLED:.status.charts.*.installedRevision,SYNC:.status.conditions[?(@.type=="Sync")].status,HEALTH:.status.conditions[?(@.type=="Health")].status'
```

Continue when, in the row whose chart name ends with `chart-cluster-api-provider-hcs` or `chart-cluster-api-provider-vsphere`, `REQUESTED` equals `INSTALLED` and `SYNC` and `HEALTH` are `True`; otherwise, contact technical support.

### Check the Kube-OVN and CoreDNS Takeover \{#check-core-addons}

Replace `<hcscluster-or-vspherecluster>` with `hcscluster` on Huawei Cloud Stack or `vspherecluster` on VMware vSphere:

```bash
ac -n cpaas-system get <hcscluster-or-vspherecluster> <cluster-name> \
  -o jsonpath='{range .status.conditions[?(@.type=="CoreAddonsHandedOff")]}{.status}{"\t"}{.reason}{"\t"}{.message}{"\n"}{end}'
```

| Result | Action |
|---|---|
| `True`, or no output on a cluster that does not use Kube-OVN | Continue. |
| `False` with `CoreAddonsHandoffPending`, `CoreDNSSkipPhasePending`, or `CoreAddonsHandoffNotApplicable` | Run the command again later; if it does not change, contact technical support. |
| `False` with `CoreAddonsHandoffBlocked` | Contact technical support with the message, which names the setting. |

### Check the Rollout Settings \{#check-rollout-settings}

```bash
ac -n cpaas-system get clusters.cluster.x-k8s.io <cluster-name> \
  -o jsonpath='{.spec.controlPlaneRef.name}{"\n"}'
ac -n cpaas-system get kubeadmcontrolplane <kcp-name> \
  -o jsonpath='replicas={.spec.replicas} maxSurge={.spec.rolloutStrategy.rollingUpdate.maxSurge}{"\n"}'
ac -n cpaas-system get kubeadmcontrolplane <kcp-name> \
  -o custom-columns='NAME:.metadata.name,VERSION:.spec.version,TEMPLATE:.spec.machineTemplate.infrastructureRef.name'
ac -n cpaas-system get machinedeployment -l cluster.x-k8s.io/cluster-name=<cluster-name> \
  -o custom-columns='NAME:.metadata.name,SURGE:.spec.strategy.rollingUpdate.maxSurge,UNAVAILABLE:.spec.strategy.rollingUpdate.maxUnavailable,VERSION:.spec.template.spec.version,TEMPLATE:.spec.template.spec.infrastructureRef.name,BOOTSTRAP:.spec.template.spec.bootstrap.configRef.name'
```

The first command prints the KubeadmControlPlane name, `<kcp-name>`. Keep the output of the last two commands: the procedure uses the template names in the `TEMPLATE` and `BOOTSTRAP` columns.

| Result | Action |
|---|---|
| `replicas` is 3 or more and `maxSurge` is `0`, and every MachineDeployment shows `SURGE` `0` and `UNAVAILABLE` `1` | Continue. |
| `replicas` is less than 3 | Contact technical support. |
| `replicas` is 3 or more and `maxSurge` is empty or not `0` | Run the `kubeadmcontrolplane` command below. |
| A MachineDeployment shows `SURGE` empty or not `0`, or `UNAVAILABLE` empty or not `1` | Run the `machinedeployment` command below for it. |

```bash
ac -n cpaas-system patch kubeadmcontrolplane <kcp-name> --type=merge \
  -p '{"spec":{"rolloutStrategy":{"type":"RollingUpdate","rollingUpdate":{"maxSurge":0}}}}'
ac -n cpaas-system patch machinedeployment <machinedeployment-name> --type=merge \
  -p '{"spec":{"strategy":{"type":"RollingUpdate","rollingUpdate":{"maxSurge":0,"maxUnavailable":1}}}}'
```

## Values for Each Version \{#required-values}

Select the ACP version that the cluster ran before this upgrade and the target ACP version. Each Intermediate row, and then the Target row, is one pass through the procedure; "the row" below means the row of the current pass.

<AlaudaOsUpgradePath>
  The Kubernetes version and etcd tag of every ACP version are also listed in [Version Mapping](../overview/alauda_os_support_matrix.mdx#version-mapping).
</AlaudaOsUpgradePath>

| Value | Field |
|---|---|
| Kubernetes version of the row, for example `v1.36.4-acp.3` | KubeadmControlPlane `spec.version`, MachineDeployment `spec.template.spec.version` |
| etcd tag of the row, for example `v3.6.13-acp.5` | KubeadmControlPlane `spec.kubeadmConfigSpec.clusterConfiguration.etcd.local.imageTag` |
| Image name you recorded for the ACP version of the row | Huawei Cloud Stack: `HCSMachineTemplate` `spec.template.spec.imageName`; VMware vSphere: `VSphereMachineTemplate` `spec.template.spec.template` |

Leave `clusterConfiguration.dns` unchanged; the platform manages CoreDNS.

## Upgrade Procedure \{#upgrade-procedure}

Run the steps on the `global` cluster you selected in [Before You Begin](#before-you-begin).

<Steps>

### Create the Control Plane Machine Template \{#create-cp-template}

Export the template that the control plane uses now, from the `TEMPLATE` column of the KubeadmControlPlane, and set the image of the row in the copy:

<Tabs>
  <Tab label="Huawei Cloud Stack">

```bash
ac -n cpaas-system get hcsmachinetemplate <current-cp-template-name> -o yaml > new-cp-template.yaml
```

In `new-cp-template.yaml`, set `spec.template.spec.imageName` to the image name of the row. Leave `spec.template.spec.providerID` and `spec.template.spec.serverId` unset.

  </Tab>
  <Tab label="VMware vSphere">

```bash
ac -n cpaas-system get vspheremachinetemplate <current-cp-template-name> -o yaml > new-cp-template.yaml
```

In `new-cp-template.yaml`, set `spec.template.spec.template` to the VM template name of the row. Leave `spec.template.spec.providerID` unset.

  </Tab>
</Tabs>

In the same file:

- Set `metadata.name` to a name that is not used yet.
- Delete `metadata.resourceVersion`, `metadata.uid`, `metadata.generation`, `metadata.creationTimestamp`, `metadata.managedFields`, the `kubectl.kubernetes.io/last-applied-configuration` annotation, and `status`.
- Keep every other field as it is.

Create the template:

```bash
ac apply -f new-cp-template.yaml
```

### Update the KubeadmControlPlane \{#update-kcp}

When the row is Kubernetes 1.35 or later, first print the kubelet patch file of the control plane. The first command prints `encoding=[]`, then the file content or the name and key of the Secret that holds it; for a Secret, run the second command, with each `.` in `<secret-key>` escaped as `\.`:

```bash
ac -n cpaas-system get kubeadmcontrolplane <kcp-name> \
  -o jsonpath='{range .spec.kubeadmConfigSpec.files[?(@.path=="/etc/kubernetes/patches/kubeletconfiguration0+strategic.json")]}{"encoding=["}{.encoding}{"] "}{.content}{.contentFrom.secret.name}{" "}{.contentFrom.secret.key}{"\n"}{end}'
ac -n cpaas-system get secret <secret-name> -o jsonpath='{.data.<secret-key>}' | base64 -d
```

If the first command prints nothing, or a value inside `encoding=[]`, such as `encoding=[base64]`, or the Secret or its key does not exist, contact technical support. Otherwise, open the KubeadmControlPlane:

```bash
ac -n cpaas-system edit kubeadmcontrolplane <kcp-name>
```

:::info
Change all of the following in this one edit; changing only `spec.version` leaves etcd on the previous version. Edit the live object: keep the annotations that the provider added, and do not apply a saved copy of the manifest instead.
:::

- `spec.version`: the Kubernetes version of the row.
- `spec.kubeadmConfigSpec.clusterConfiguration.etcd.local.imageTag`: the etcd tag of the row.
- `spec.machineTemplate.infrastructureRef.name`: the template you created in the previous step.
- When the row is Kubernetes 1.35 or later and the printed content lacks `"imagePullCredentialsVerificationPolicy": "NeverVerify"`: add it to the content of `/etc/kubernetes/patches/kubeletconfiguration0+strategic.json` in `spec.kubeadmConfigSpec.files`. If that file uses `contentFrom`, replace `contentFrom` with `content` set to the printed content plus this setting. Do not add it for a row on Kubernetes 1.34 or earlier.

Save and close the editor. The control plane nodes are now replaced with new VMs, one at a time.

### Wait for the Control Plane Rollout \{#wait-cp}

```bash
ac -n cpaas-system get kubeadmcontrolplane <kcp-name>
ac -n cpaas-system get machines.cluster.x-k8s.io -l cluster.x-k8s.io/cluster-name=<cluster-name>,cluster.x-k8s.io/control-plane
```

Run the commands again until every control plane Machine is `Running` with the new `VERSION`, and the KubeadmControlPlane shows `REPLICAS` equal to `DESIRED`, `READY` and `UPDATED` equal to `REPLICAS`, and `UNAVAILABLE` at `0`. For the `global` cluster, a command can fail to connect while its control plane nodes are replaced; run it again.

### Create the Worker Templates \{#create-worker-templates}

For each template in the `TEMPLATE` column of the MachineDeployment list, export it:

<Tabs>
  <Tab label="Huawei Cloud Stack">

```bash
ac -n cpaas-system get hcsmachinetemplate <current-worker-template-name> -o yaml > <new-worker-template-name>.yaml
```

In the file, set `spec.template.spec.imageName` to the image name of the row.

  </Tab>
  <Tab label="VMware vSphere">

```bash
ac -n cpaas-system get vspheremachinetemplate <current-worker-template-name> -o yaml > <new-worker-template-name>.yaml
```

In the file, set `spec.template.spec.template` to the VM template name of the row.

  </Tab>
</Tabs>

Edit the rest of the file as for the control plane template: a new `metadata.name`, and the same server-generated fields deleted. Then create it with `ac apply -f <new-worker-template-name>.yaml`.

When the row is Kubernetes 1.35 or later, print the kubelet patch file of each template in the `BOOTSTRAP` column, and, for a Secret, its content, as for the control plane:

```bash
ac -n cpaas-system get kubeadmconfigtemplate <current-bootstrap-template-name> \
  -o jsonpath='{range .spec.template.spec.files[?(@.path=="/etc/kubernetes/patches/kubeletconfiguration0+strategic.json")]}{"encoding=["}{.encoding}{"] "}{.content}{.contentFrom.secret.name}{" "}{.contentFrom.secret.key}{"\n"}{end}'
ac -n cpaas-system get secret <secret-name> -o jsonpath='{.data.<secret-key>}' | base64 -d
```

If the first command prints nothing, or a value inside `encoding=[]`, such as `encoding=[base64]`, or the Secret or its key does not exist, contact technical support. For each template whose content lacks `"imagePullCredentialsVerificationPolicy": "NeverVerify"`, create a new bootstrap template:

```bash
ac -n cpaas-system get kubeadmconfigtemplate <current-bootstrap-template-name> -o yaml > <new-bootstrap-template-name>.yaml
```

In the file, set a new `metadata.name`, add `"imagePullCredentialsVerificationPolicy": "NeverVerify"` to the content of `/etc/kubernetes/patches/kubeletconfiguration0+strategic.json` in `spec.template.spec.files`, and delete the same server-generated fields. If that file uses `contentFrom`, replace `contentFrom` with `content` set to the printed content plus this setting. Then create it with `ac apply -f <new-bootstrap-template-name>.yaml`.

### Update Each MachineDeployment \{#worker-node-upgrades}

Patch every MachineDeployment in the list. Use the Kubernetes version of the row and the new template that replaces the one the MachineDeployment uses now:

```bash
ac -n cpaas-system patch machinedeployment <machinedeployment-name> --type=merge \
  -p '{"spec":{"template":{"spec":{"version":"<kubernetes-version>","infrastructureRef":{"name":"<new-worker-template-name>"}}}}}'
```

If you created a new bootstrap template, change it in the same patch:

```bash
ac -n cpaas-system patch machinedeployment <machinedeployment-name> --type=merge \
  -p '{"spec":{"template":{"spec":{"version":"<kubernetes-version>","infrastructureRef":{"name":"<new-worker-template-name>"},"bootstrap":{"configRef":{"name":"<new-bootstrap-template-name>"}}}}}}'
```

Each MachineDeployment now replaces its worker nodes with new VMs.

### Wait for the Worker Rollout \{#wait-workers}

```bash
ac -n cpaas-system get machinedeployment -l cluster.x-k8s.io/cluster-name=<cluster-name>
ac -n cpaas-system get machines.cluster.x-k8s.io -l cluster.x-k8s.io/cluster-name=<cluster-name>
```

Run the commands again until every MachineDeployment shows `READY` and `UPDATED` equal to `REPLICAS` and `UNAVAILABLE` at `0`, and every Machine is `Running` with the new `VERSION`.

Then check the nodes. For a `global` cluster, run `ac get nodes`. For a workload cluster, switch to it, and back to `global` afterwards:

```bash
ac config use-cluster <cluster-name>
ac get nodes
ac config use-cluster global
```

Continue when every node is `Ready` and its `VERSION` is the Kubernetes version of the row.

### Repeat for the Next Version \{#repeat-next-version}

If the path has another row, start again at [Create the Control Plane Machine Template](#create-cp-template) with the values of that row. Finish each row, control plane and workers, before you start the next one.

After the Target row, the Kubernetes upgrade of this cluster is complete.

</Steps>

## If a Step Fails \{#if-a-step-fails}

An upgrade cannot be rolled back: do not set the versions or the templates back to their previous values. Fix the reported cause and the rollout continues; if the cause cannot be fixed, contact technical support. For checks by symptom, see [Upgrade Troubleshooting](./troubleshooting.mdx#manual-kubernetes-upgrade).
