# Managing Access and Cleanup

Use this page for Alauda Container Platform Registry administrator and namespace administrator tasks,
including namespace image access, usage reporting, image pruning, registry garbage collection, and
recorded image signature identity checks.

## Task Index

| Task | Use when |
| --- | --- |
| [Grant namespace permissions](#grant-namespace-permissions) | A user or service account needs pull, push, delete, or image catalog access in an image namespace. |
| [View usage](#view-usage) | An administrator needs image or ImageStream usage information. |
| [Check recorded signature identity](#verify-image-signatures) | An administrator needs to compare recorded identity claims or record an independently verified trust decision. |
| [Prune images](#prune-images) | An administrator needs to remove unused image metadata after reviewing a dry run. |
| [Run registry garbage collection](#run-registry-garbage-collection) | An administrator needs to unlink pruned manifests and reclaim unreferenced blobs, or collect blobs already unlinked from storage manifests. |

## Prerequisites

- <Term name="productShort" /> Registry is installed and available.
- You have `kubectl` and `ac` access to the target cluster.
- You have permission to create RoleBindings in the image namespace.
- You can create cluster-scoped `subjectaccessreviews.authorization.k8s.io` to check another principal's permissions.
- You have administrator permissions for usage reporting and cleanup. Garbage collection requires Registry Pod execution access and permission to update `Config/cluster` and `ImagePruner/cluster`.
- For signature identity checks, you can `get` cluster-scoped `imagedigests.image.alauda.io`. Saving conditions or removing embedded signatures also requires `update` on that resource.

Select the ACP 4.4 Registry backend before using the `ac` administrative commands:

```bash
ac config set-registry-mode modern
```

Expected result:

- Subsequent `ac` Image API, pruning, garbage-collection, and signature commands use the ACP 4.4
  Registry.

## Grant Namespace Permissions \{#grant-namespace-permissions}

Grant pull permission to a user:

```bash
kubectl create rolebinding image-puller-user \
  --clusterrole=system:image-puller \
  --user=<username> \
  -n <image-namespace>
```

Grant push permission to a user:

```bash
kubectl create rolebinding image-pusher-user \
  --clusterrole=system:image-pusher \
  --user=<username> \
  -n <image-namespace>
```

Grant pull permission to a service account in another namespace:

```bash
kubectl create rolebinding image-puller-sa \
  --clusterrole=system:image-puller \
  --serviceaccount=<workload-namespace>:<serviceaccount-name> \
  -n <image-namespace>
```

| Placeholder | Description |
| --- | --- |
| `<username>` | <Term name="productShort" /> or Kubernetes username to check. For a ServiceAccount, use `system:serviceaccount:<workload-namespace>:<serviceaccount-name>`. |
| `<image-namespace>` | Namespace that owns the image repository, for example `team-a`. |
| `<repository>` | ImageStream name in the image namespace, for example `demo`. |
| `<workload-namespace>` | Namespace where the workload service account runs. |
| `<serviceaccount-name>` | ServiceAccount name used by the workload that pulls the image. |

Verify that the RoleBinding exists:

```bash
kubectl -n <image-namespace> get rolebinding
```

The Registry uses the following permissions in the `image.alauda.io` API group:

| Operation | Typical role | Scope | Permission |
| --- | --- | --- | --- |
| Pull | `system:image-puller` | Image namespace | `imagestreams/layers` `get` |
| Push | `system:image-pusher` | Image namespace | `imagestreams/layers` `update` |
| Delete image references | `system:image-deleter` | Image namespace | `imagestreamtags` `delete` |
| Delete an OCI manifest by digest | `system:image-deleter` | Image namespace and repository | `imagestreamtags` `delete`, checked against the repository name |
| Upload signatures through the Registry | `system:image-signature-writer` | Image namespace and repository | `imagesignatures` `create` |
| Manage ImageSignature API records | `system:image-signature-writer` | Cluster | `imagesignatures` `create`, `delete` |
| Read the image catalog | `system:image-registry-catalog-reader` | Bound namespace, or cluster with a ClusterRoleBinding | `imagestreams` `list` |
| Read Registry metrics | `system:image-registry-metrics-reader` | Cluster | `registry/metrics` `get` |

Use a RoleBinding for namespace access. Direct ImageSignature API operations and metrics require
cluster-scoped authorization; a ClusterRoleBinding grants that role across the cluster. The
administrative signature command uses ImageDigest `get` and `update` permissions instead.

Catalog visibility also honors pull permission. A user with `get` on `imagestreams/layers` can see
the permitted repositories without a separate catalog-reader grant. A namespace-wide grant covers
that namespace; a grant restricted to named repositories covers only those repositories. Catalog
visibility does not grant image push or delete permission.

Deleting a manifest by digest through the OCI Registry API can remove every current tag in that
repository that points to the digest. Its authorization check uses the repository name, whereas
an ImageStreamTag API deletion targets a single `<repository>:<tag>` resource name. These namespace
grants do not authorize deletion of cluster-scoped ImageDigest objects. To remove only one tag,
use [Delete image references](../../developer/registry/managing_images_with_ac.mdx#delete-image-references).

The `system:image-pruner` ClusterRole is reserved for the Operator-managed `pruner` ServiceAccount.
It is not a namespace access role. Manual pruning and garbage collection require the corresponding
administrator permissions.

Check effective pull access with a `SubjectAccessReview` matching the Registry authorization check.
Run the standard resource command in the target cluster's kubeconfig context so any API proxy path
is preserved. `--validate=false` bypasses the client schema check when OpenAPI validation blocks
the request; authentication and RBAC still apply:

```bash
kubectl create --validate=false -f - -o jsonpath='{.status.allowed}{"\n"}' <<'EOF'
{
  "apiVersion": "authorization.k8s.io/v1",
  "kind": "SubjectAccessReview",
  "spec": {
    "user": "<username>",
    "groups": ["system:authenticated"],
    "resourceAttributes": {
      "namespace": "<image-namespace>",
      "verb": "get",
      "group": "image.alauda.io",
      "resource": "imagestreams/layers",
      "name": "<repository>"
    }
  }
}
EOF
```

Supply the principal's actual groups when testing group-based grants. For a ServiceAccount,
include `system:serviceaccounts`, `system:serviceaccounts:<workload-namespace>`, and
`system:authenticated`. For push access, repeat the request with `verb` set to `update`.

The command prints `status.allowed`: `true` means the supplied identity and resource attributes
are authorized. A `false` result does not establish whether the account exists. For details,
repeat with `-o json` and inspect `status.reason` and `status.evaluationError`.

For Registry signature uploads, reuse the request above with these `resourceAttributes`:

```json
{
  "namespace": "<image-namespace>",
  "verb": "create",
  "group": "image.alauda.io",
  "resource": "imagesignatures",
  "name": "<repository>"
}
```

For direct cluster-scoped ImageSignature API creation, omit the namespace and repository name:

```json
{
  "verb": "create",
  "group": "image.alauda.io",
  "resource": "imagesignatures"
}
```

Repeat that review with `verb` set to `delete` to check direct signature deletion. To check the
administrative signature command, use `resource: imagedigests`, `name: sha256:<digest>`, and
`verb: get` or `verb: update`, still without a namespace.

`registry/metrics` is an RBAC-only subresource absent from Image API discovery. Check its
cluster-scoped permission directly:

```bash
kubectl create --validate=false -f - -o jsonpath='{.status.allowed}{"\n"}' <<'EOF'
{
  "apiVersion": "authorization.k8s.io/v1",
  "kind": "SubjectAccessReview",
  "spec": {
    "user": "<username>",
    "groups": ["system:authenticated"],
    "resourceAttributes": {
      "verb": "get",
      "group": "image.alauda.io",
      "resource": "registry",
      "subresource": "metrics"
    }
  }
}
EOF
```

Use the principal's actual groups as above. The command prints `true` when the supplied identity
has the metrics reader permission in the target cluster.

## View Usage \{#view-usage}

Show metadata-derived storage totals and Pod usage for ImageDigest objects:

```bash
ac adm top images
```

Show metadata-derived totals for ImageStreams:

```bash
ac adm top imagestreams
```

Expected result:

- The command prints usage rows for ImageDigest or ImageStream resources visible to the current administrator.

Interpret the columns as follows:

- Image `STORAGE` sums recorded layer sizes and child-manifest sizes. ImageStream `STORAGE` sums
  those values once per distinct referenced image digest, including tag history.
- Shared layers are counted again across different images. These totals do not measure physical
  backend usage or predict reclaimable bytes.
- Image `USAGE` counts Pods with matching digest references in the queried Pod scope. It does not
  include every workload or external consumer. `METADATA` counts recorded layer and child-manifest
  entries; ImageStream `LAYERS` sums those counts per referenced image.
- Image `IMAGESTREAMTAG` lists the `namespace/stream:tag` references that contribute the row,
  comma-separated when several match. ImageStream `IMAGES` counts the distinct image digests the
  stream references.

## Check Recorded Signature Identity \{#verify-image-signatures}

This command compares identity claims already recorded on an ImageDigest object. It does not verify
signature cryptography, signer trust, or image integrity. Independently verify the signature under
your signing policy before recording a trust decision.

Check the recorded identity without modifying the object:

```bash
ac adm verify-image-signature 'sha256:<digest>' \
  --expected-identity=registry.example.com/team-a/demo:latest
```

| Placeholder | Description |
| --- | --- |
| `sha256:<digest>` | Digest of the ImageDigest object to verify. Use `ac get imagedigests.image.alauda.io` or `ac get imagestreamtags <name>:<tag> -n <namespace> -o wide` to find the digest. |
| `registry.example.com/team-a/demo:latest` | Expected signed image identity. Use the image reference required by your signing policy. |

Expected result: the command reports a matching recorded identity and leaves the ImageDigest unchanged.

Before changing signatures, back up the ImageDigest metadata to a protected local file:

```bash
umask 077
ac get imagedigests.image.alauda.io 'sha256:<digest>' -o yaml > image-signatures-backup.yaml
```

> **Warning:** `--save` replaces the matching signatures' conditions with `Trusted=True` and
> `ForImage=True`. An identity match alone does not justify trust. Use this option only after
> independent verification, with cluster-scoped ImageDigest `update` permission and a metadata backup.

Record the independently verified trust decision:

```bash
ac adm verify-image-signature 'sha256:<digest>' \
  --expected-identity=registry.example.com/team-a/demo:latest \
  --save
```

Verify the saved condition:

```bash
ac get imagedigests.image.alauda.io 'sha256:<digest>' -o yaml
```

Expected result:

- Matching signature records contain `Trusted=True` and `ForImage=True` conditions.

To roll back `--save`, restore the affected signatures' previous conditions from the metadata backup.

> **Warning:** `--remove-all` immediately clears all embedded signature data from the ImageDigest
> object without a confirmation prompt. The Registry cannot undo this operation. Keep a metadata
> backup and confirm the records are no longer required before running it.

Remove the embedded records and verify that `signatures` is empty:

```bash
ac adm verify-image-signature 'sha256:<digest>' --remove-all
ac get imagedigests.image.alauda.io 'sha256:<digest>' -o yaml
```

## Prune Images \{#prune-images}

> **Warning:** Confirmed pruning permanently removes selected image metadata. Keep metadata and
> storage backups, use a maintenance window, and review a dry run with the same retention and
> exclusion flags before adding `--confirm`.

Pruning is a platform-level operation. The account must be allowed to `get`
`configs.imageregistry.operator.alauda.io/cluster`; otherwise the command exits before scanning.
Namespace image roles such as `system:image-deleter` are not sufficient.

The pruner scans Pod specifications in this cluster's Pods, Deployments, StatefulSets, DaemonSets,
ReplicaSets, ReplicationControllers, Jobs, and CronJobs. Tagged images and tag history can be prune
candidates. Consumers in other clusters or outside the platform are not scanned; exclude their
repositories with `--whitelist` or retain the required images before proceeding.

Manual retention defaults to zero revisions and zero age, independently of `ImagePruner/cluster`.
The examples explicitly retain five revisions per tag and images younger than 72 hours. Adjust
these values to your policy in every preview and confirmation command.

This metadata-only procedure updates ImageStream references and removes eligible ImageDigest
objects. Storage manifest links remain. If storage reclamation is intended, start with the
[combined cleanup procedure](#prune-and-reclaim-storage) while the metadata graph is still intact.

Preview image pruning:

```bash
ac adm prune images \
  --keep-tag-revisions=5 \
  --keep-younger-than=72h
```

Expected result:

- The dry run lists prune candidates and does not delete image metadata.

Run pruning after reviewing the dry-run output:

```bash
ac adm prune images \
  --keep-tag-revisions=5 \
  --keep-younger-than=72h \
  --confirm
```

Verify pruning:

```bash
ac adm prune images \
  --keep-tag-revisions=5 \
  --keep-younger-than=72h
```

Expected result:

- A follow-up dry run no longer lists the metadata that was pruned by the confirmed command.

Keep repositories out of pruning with `--whitelist`. The flag takes regular expressions and can be
repeated:

```bash
ac adm prune images \
  --keep-tag-revisions=5 \
  --keep-younger-than=72h \
  --whitelist='^cpaas-system/.*'
```

After reviewing the preview, confirm the same policy:

```bash
ac adm prune images \
  --keep-tag-revisions=5 \
  --keep-younger-than=72h \
  --whitelist='^cpaas-system/.*' \
  --confirm
```

For scheduled pruning, see [Setting up and configuring the registry](./setting_up_and_configuring_the_registry.mdx#configure-scheduled-image-pruning).

Confirmed pruning is not automatically reversible. Restore pruned metadata from backup, recreate
metadata from a trusted image source, or re-import the image when recovery is required.

## Run Registry Garbage Collection \{#run-registry-garbage-collection}

Storage reclamation has three stages: prune Image API metadata, unlink eligible storage manifests,
then collect blobs no longer referenced by storage manifests. Metadata-only pruning followed by
standalone GC can leave blobs retained by their storage manifest links.

> **Warning:** Confirmed blob reclamation is irreversible through the Registry. Neither standalone
> GC nor combined pruning automatically stops writers. Prevent concurrent pushes, imports, and other
> Registry or Image API writes, and let in-flight writes finish before cleanup. Keep writers paused
> until verification completes. Restore missing data from a storage backup or a trusted image source.

### Prepare the Maintenance Window

Both `ac adm registry gc` and `ac adm prune images --prune-registry` resolve the Registry operand
namespace from the installation binding. This also applies when Registry mode is selected
explicitly. The CLI refuses cleanup when it cannot verify the binding or find a ready Registry Pod.

Run the procedure from an administrator environment with `kubectl`, `ac`, `curl`, pull access to
the critical images, and enough disk space to extract them. Select and verify the access path
before changing Registry settings:

- For an external endpoint, use the verified HTTPS hostname from
  [Exposing the Registry](./exposing_the_registry.mdx).
- For an internal-only Registry, run from a maintenance environment with cluster network and DNS
  access. Use `image-registry.cpaas-system.svc:5000` and the Registry service CA. You do not need to
  expose an external Ingress for cleanup.

An administrator can obtain the internal service CA from the operand namespace:

```bash
REGISTRY_NAMESPACE="$(kubectl get configs.imageregistry.operator.alauda.io cluster \
  -o jsonpath='{.metadata.annotations.imageregistry\.operator\.alauda\.io/operand-namespace}')" || exit 1
test -n "$REGISTRY_NAMESPACE" || {
  echo "The Registry operand namespace binding is missing." >&2
  exit 1
}
kubectl -n "$REGISTRY_NAMESPACE" get configmap serviceca \
  -o jsonpath='{.data.service-ca\.crt}' > registry-service-ca.crt
```

Set the endpoint and CA bundle for the selected path. The CA bundle must validate the endpoint's
certificate chain and hostname. The examples pass it explicitly to `curl` and pruning. On Linux,
`SSL_CERT_FILE` provides it to each direct `ac` client invocation. On macOS or Windows, add the CA
to the client's system trust store before login and extraction; the environment variable does not
replace that step. See [Configure client trust](./exposing_the_registry.mdx#configure-client-trust).

```bash
REGISTRY_HOST='<registry-host>'
REGISTRY_URL="https://$REGISTRY_HOST"
REGISTRY_CA='/absolute/path/to/registry-ca.crt'

HTTP_STATUS="$(curl --silent --show-error --cacert "$REGISTRY_CA" \
  --output /dev/null --write-out '%{http_code}' "${REGISTRY_URL%/}/v2/")" || exit 1
case "$HTTP_STATUS" in
  200|401) ;;
  *) echo "Registry endpoint check failed: HTTP $HTTP_STATUS" >&2; exit 1 ;;
esac

REGISTRY_AUTH_DIR="$(mktemp -d "${TMPDIR:-/tmp}/registry-auth.XXXXXX")" || exit 1
REGISTRY_AUTH_FILE="$REGISTRY_AUTH_DIR/config.json"
SSL_CERT_FILE="$REGISTRY_CA" ac registry login \
  --registry "$REGISTRY_HOST" --to "$REGISTRY_AUTH_FILE" || exit 1
VERIFY_IMAGE="$REGISTRY_HOST/team-a/demo@sha256:<digest>"
VERIFY_PLATFORM=linux/amd64
```

| Value | Description |
| --- | --- |
| `<registry-host>` | Verified external Registry host, or `image-registry.cpaas-system.svc:5000` from a maintenance environment that can reach it. Do not include a scheme or path. |
| `REGISTRY_CA` | Absolute path to a PEM CA bundle that validates the selected endpoint. For the internal service, use the `registry-service-ca.crt` file obtained above. For a public certificate, you can use the workstation's system CA bundle. |
| `VERIFY_IMAGE` | Immutable reference to an image that must survive cleanup. Replace `team-a/demo` and the hexadecimal `<digest>` with a critical repository and digest. |
| `VERIFY_PLATFORM` | Platform required by consumers, in `os/arch` form. |

A `401` response is the expected unauthenticated challenge; it proves reachability, not permission.
Use the following extraction as the baseline verification before entering maintenance:

```bash
VERIFY_DIR="$(mktemp -d "${TMPDIR:-/tmp}/registry-verify.XXXXXX")" || exit 1
SSL_CERT_FILE="$REGISTRY_CA" ac image extract "$VERIFY_IMAGE" \
  --filter-by-os="$VERIFY_PLATFORM" \
  --path "/:$VERIFY_DIR" \
  --registry-config="$REGISTRY_AUTH_FILE" || exit 1
```

Expected result: the image filesystem is extracted successfully. Repeat with every critical image
and required platform, each time using a fresh directory. Resolve any failure before cleanup.
Keep these endpoint, authentication, and verification variables in the same shell throughout the
maintenance procedure.

Record the current settings and suspend scheduled pruning to prevent overlapping cleanup:

```bash
REGISTRY_READ_ONLY="$(kubectl get configs.imageregistry.operator.alauda.io cluster \
  -o jsonpath='{.spec.readOnly}')" || exit 1
REGISTRY_READ_ONLY="${REGISTRY_READ_ONLY:-false}"
kubectl patch imagepruners.imageregistry.operator.alauda.io cluster \
  --type=merge -p '{"spec":{"suspend":true}}' || exit 1
kubectl -n "$REGISTRY_NAMESPACE" wait cronjob/image-pruner \
  --for=jsonpath='{.spec.suspend}'=true --timeout=300s || exit 1
kubectl -n "$REGISTRY_NAMESPACE" get jobs -l created-by=image-pruner \
  -o custom-columns='NAME:.metadata.name,CONDITION:.status.conditions[*].type'
```

Wait until every existing pruner Job has a terminal `Complete` or `Failed` condition. Suspending the
schedule does not stop an existing Job. Pause image-changing workflows and prevent other clients
from writing throughout the selected cleanup procedure.

### Prune Metadata and Reclaim Storage \{#prune-and-reclaim-storage}

Use this path before metadata-only pruning when you need to remove eligible manifest links and
reclaim blobs. The recorded `REGISTRY_READ_ONLY` value must be `false`; if it is `true`, resolve the
existing maintenance restriction before proceeding. Keep `spec.readOnly` false during this path
because pruning must update and delete Image API resources. Enforce writer exclusion through your
maintenance controls instead.

Use the endpoint and CA verified during preparation, with the administrator account authenticated
to this cluster. Preview the metadata candidates with explicit retention and repository exclusions:

```bash
ac adm prune images \
  --registry-url="$REGISTRY_URL" \
  --certificate-authority="$REGISTRY_CA" \
  --keep-tag-revisions=5 \
  --keep-younger-than=72h \
  --whitelist='^cpaas-system/.*' \
  --prune-registry
```

This dry run lists metadata candidates and skips GC. The confirmed run also unlinks eligible
storage manifests and collects all then-unreferenced blobs, including previously unlinked content.
After reviewing the candidates and backups, run:

```bash
ac adm prune images \
  --registry-url="$REGISTRY_URL" \
  --certificate-authority="$REGISTRY_CA" \
  --keep-tag-revisions=5 \
  --keep-younger-than=72h \
  --whitelist='^cpaas-system/.*' \
  --prune-registry \
  --confirm
```

Remaining ImageStream references can retain a shared digest or manifest. Verify metadata cleanup
with the same dry run, then continue to [verify blob availability](#verify-blob-availability).
The CLI saves pending manifest targets in `image-pruner-state` in the operand namespace before
deleting metadata. A manifest deletion failure returns a nonzero exit status and prevents GC.
Resolve the reported error, review another dry run, and repeat the command with the same endpoint,
retention policy, and exclusion options. The dry run includes pending targets from the earlier
attempt; confirmation rechecks live references and workload usage. Changed pruning options are
rejected while targets remain pending. Do not delete the state ConfigMap to bypass that check.

### Collect Already Unlinked Blobs

Use standalone GC when storage manifest links have already been removed. It does not unlink
manifests based on Image API retention. After stopping writers, complete the enabling steps in
[Enable read-only mode](./setting_up_and_configuring_the_registry.mdx#enable-read-only-mode).
Wait for the requested Config generation to reconcile and the Registry rollout to complete; keep
read-only mode enabled until blob verification finishes. Do not run metadata pruning in this mode;
Image API writes and deletes are blocked.

Preview storage garbage collection:

```bash
ac adm registry gc
```

Expected result:

- The command previews eligible unreferenced blobs and does not delete them.

Run registry garbage collection only after reviewing the preview:

```bash
ac adm registry gc --confirm
```

Expected result:

- The command removes eligible unreferenced blobs from Registry storage.

Continue to verify blob availability before restoring the previous settings.

### Verify Blob Availability \{#verify-blob-availability}

Repeat the baseline verification from preparation, using the same immutable image reference and
platform. Extract into a fresh directory to read the image layers without a local runtime cache:

```bash
VERIFY_DIR="$(mktemp -d "${TMPDIR:-/tmp}/registry-verify.XXXXXX")" || exit 1
SSL_CERT_FILE="$REGISTRY_CA" ac image extract "$VERIFY_IMAGE" \
  --filter-by-os="$VERIFY_PLATFORM" \
  --path "/:$VERIFY_DIR" \
  --registry-config="$REGISTRY_AUTH_FILE" || exit 1
```

Expected result: extraction completes and writes the image filesystem to `$VERIFY_DIR`. Repeat for
every critical image and required platform checked before cleanup. An `ac image info` inspection
alone does not verify layer availability. Remove temporary authentication and image directories
after verification and any investigation are complete.

### Restore the Previous Settings

After successful verification, restore the recorded read-only setting. Keep scheduled pruning suspended:

```bash
REGISTRY_CONFIG_GENERATION="$(kubectl patch configs.imageregistry.operator.alauda.io cluster \
  --type=merge -p "{\"spec\":{\"readOnly\":$REGISTRY_READ_ONLY}}" \
  -o jsonpath='{.metadata.generation}')" || exit 1
kubectl wait configs.imageregistry.operator.alauda.io/cluster \
  --for=jsonpath='{.status.observedGeneration}'="$REGISTRY_CONFIG_GENERATION" --timeout=300s || exit 1
kubectl wait configs.imageregistry.operator.alauda.io/cluster \
  --for=condition=Degraded=false --timeout=300s || exit 1
kubectl wait configs.imageregistry.operator.alauda.io/cluster \
  --for=condition=Progressing=false --timeout=300s || exit 1
EXPECTED_REGISTRY_READ_ONLY=''
if [ "$REGISTRY_READ_ONLY" = true ]; then
  EXPECTED_REGISTRY_READ_ONLY='{enabled: true}'
fi
REGISTRY_TEMPLATE_READ_ONLY="$(kubectl -n "$REGISTRY_NAMESPACE" get deployment image-registry \
  -o jsonpath='{.spec.template.spec.containers[?(@.name=="registry")].env[?(@.name=="REGISTRY_STORAGE_MAINTENANCE_READONLY")].value}')" || exit 1
test "$REGISTRY_TEMPLATE_READ_ONLY" = "$EXPECTED_REGISTRY_READ_ONLY" || {
  echo "The Registry Pod template does not match the recorded read-only setting." >&2
  exit 1
}
kubectl -n "$REGISTRY_NAMESPACE" rollout status deployment/image-registry --timeout=300s || exit 1

kubectl -n "$REGISTRY_NAMESPACE" get pods -l app.kubernetes.io/name=image-registry \
  -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.metadata.deletionTimestamp}{"\t"}{.spec.containers[?(@.name=="registry")].env[?(@.name=="REGISTRY_STORAGE_MAINTENANCE_READONLY")].value}{"\n"}{end}'
```

Continue only when Pods are present, no row has a deletion timestamp, and every read-only value
matches `EXPECTED_REGISTRY_READ_ONLY` (empty when the recorded setting was `false`). Repeat the
Pod check until all old Pods have terminated. Verify that scheduled pruning remains suspended:

```bash
kubectl patch imagepruners.imageregistry.operator.alauda.io cluster \
  --type=merge -p '{"spec":{"suspend":true}}' || exit 1
kubectl -n "$REGISTRY_NAMESPACE" wait cronjob/image-pruner \
  --for=jsonpath='{.spec.suspend}'=true --timeout=300s || exit 1
```

Verify that the rollout completes, read-only mode matches its recorded value, and pruning remains suspended. Resume writers
when the Registry is intended to be writable. If verification fails, keep the maintenance controls
in place while investigating.
