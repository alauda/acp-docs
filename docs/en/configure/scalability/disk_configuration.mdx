## Storage Capacity \{#storage_capacity}

The disks of a node depend on the environment and on the role of the node. The sections below give the disk layout of each environment, the size of each path, the raw disk for TopoLVM, and a summary by node role.

### Disk Layout by Environment \{#disk_layout}

| Environment | Disks of each node |
|---|---|
| Alauda OS on Huawei DCS, Huawei Cloud Stack, or VMware vSphere | A system disk, plus a separate disk for each of `/var/lib/etcd` (control plane nodes only), `/var/lib/containerd`, `/var/lib/kubelet`, and `/var/cpaas`. Declare only `/var/cpaas` as a persistent disk, so that it is kept when the provider replaces the node. Declare the other three as standard disks. |
| Alauda OS on Bare Metal | One system disk. The provider does not wipe the host disk when it upgrades or updates the host, so all paths can share the system disk. Size it for the sum of the paths; see [System Disk on Bare Metal](#bare_metal_system_disk). |
| Bare Metal on a non-Alauda OS | The same as Alauda OS on Bare Metal, with `/cpaas` in place of `/var/cpaas`. Create the paths as LVM logical volumes so that they can be expanded later. |

A node that runs TopoLVM also needs a raw disk in every environment; see [Raw Disk for TopoLVM](#topolvm_raw_disk).

On Alauda OS, the disks are declared in the machine configuration of the provider rather than partitioned manually. For the procedure of each provider, see [Create Workload Clusters on Alauda OS](../../workload_clusters/alauda_os/index.mdx).

### Path Sizes \{#path_sizes}

| Path | Used for | Size and notes |
|---|---|---|
| `/` | Operating system | At least 50 GB; 100 GB recommended. Keep utilization below 80%; above this threshold, Pods on the node may be evicted. |
| `/var/lib/etcd` | etcd data, on control plane nodes only | At least 10 GB; 20 GB recommended. Use a dedicated high-IO disk; see [Recommended ETCD Practices](#recommended_etcd_practices). |
| `/var/lib/containerd` | Container images and container writable layers | At least 100 GB; 150 GB recommended. |
| `/var/lib/kubelet` | Pod ephemeral data, such as `emptyDir` volumes | At least 100 GB. 200 GB recommended on nodes of the `global` cluster, including a Single Cluster; 100 GB recommended on nodes of workload clusters. |
| `/var/cpaas` on Alauda OS<br></br>`/cpaas` on a non-Alauda OS | Platform data: etcd local backups, the log collection buffer, and audit data | At least 100 GB on control plane nodes, which keep etcd local backups in `/var/cpaas/backup` (see [etcd Backup and Restore](../backup/etcd.mdx)), and at least 50 GB on other nodes. 200 GB recommended on log storage nodes, which run ClickHouse and Kafka; otherwise the minimum is also the recommended size. |
| Any location on the machine that runs the installer, for downloading and extracting the installation packages | The Core Package and the Extension packages placed next to it | At least 120 GB; 250 GB recommended. The actual size depends on the Extensions that you install, so plan more space if you expect to add components later. |

### Raw Disk for TopoLVM \{#topolvm_raw_disk}

A node that runs TopoLVM needs an additional raw disk, on Alauda OS providers and on Bare Metal alike. TopoLVM manages this disk, so do not format or mount it. Size it by what the node runs:

| Workloads on the node | Raw disk size |
|---|---|
| Logging, with or without monitoring | 1 TB |
| Monitoring only | 512 GB |

The logging size covers about 5,000 log entries per second with 7 days of retention. For more logs, add capacity to the TopoLVM volume group. On Bare Metal, raw disks usually come in sizes such as 512 GB and 1 TB; select the smallest size that covers the need.

Harbor and the DevOps tools need no TopoLVM disk. Harbor, GitLab, SonarQube, Nexus, and their PostgreSQL and Redis instances keep their data in Ceph (RBD and RGW). For the OSD disks of the storage nodes, see <ExternalSiteLink name="devops" href="/install/planning-devops-cluster.html#harbor-on-global" children="Harbor on the global Cluster" /> and <ExternalSiteLink name="devops" href="/install/planning-devops-cluster.html#devops-cluster" children="Dedicated DevOps Cluster" />. The infra nodes of a DevOps cluster run monitoring and logging, like the infra nodes of a workload cluster, and use a 1 TB TopoLVM disk.

### System Disk on Bare Metal \{#bare_metal_system_disk}

| Node | Minimum size | Recommended size |
|---|---|---|
| Control plane node of the `global` cluster or a Single Cluster; infra node of the `global` cluster, a Single Cluster, or a workload cluster; log node of a workload cluster | 512 GB | 1 TB |
| Control plane node of a workload cluster; monitor and gateway nodes; storage nodes; application worker nodes | 512 GB | 512 GB |

Each size covers the sum of the recommended sizes of the paths on that node.

## Recommended ETCD Practices \{#recommended_etcd_practices}

Fast storage is essential for etcd to perform reliably. etcd depends on durable, low-latency disk operations to persist proposals to its write-ahead log (WAL).  
If disk writes take too long, fsync delays can cause the member to miss heartbeats, fail to commit proposals promptly, and experience request timeouts or temporary leader changes. These issues can also slow the Kubernetes API and degrade overall cluster responsiveness.  
In conclusion, HDDs are a poor choice and are not recommended. If you must use HDDs for etcd, choose the fastest available (for example, 15,000 RPM).  

:::info
The following hard drive practices provide optimal etcd performance:

- Prefer SSDs or NVMe as etcd drives. When write endurance and stability are priorities, consider server-grade single-level cell (SLC) SSDs. Avoid NAS, SAN, and HDDs.
  - Prefer drives with high write throughput to accelerate compaction and defragmentation.
  - Prefer drives with strong read bandwidth to reduce recovery time after failures.
  - Prefer drives with consistently low latency to ensure fast read and write operations.
- Avoid distributed block storage systems such as Ceph RADOS Block Device (RBD), Network File System (NFS), and other network-attached backends, because they introduce unpredictable latency.

- Keep etcd data on a dedicated drive or a dedicated logical volume.
  - Do not place I/O-sensitive (such as logging) or other intensive filesystem activity on control-plane hosts, or at least do not let them share the same underlying storage with etcd.

- Continuously benchmark with tools like `fio` and use the results to track performance as the cluster grows. For more information, see the [disk benchmarking guide](#benchmark_with_fio).
:::

### Validating the hardware for etcd

| Specification | Minimum Requirement | Recommended | Notes |
|----------------|---------------------|--------------|--------|
| Sequential write IOPS | 50 | 500 (higher is better) | Most cloud providers publish *concurrent* IOPS rather than *sequential* IOPS. The concurrent IOPS values are typically about 10× higher than sequential ones. |
| Disk bandwidth | 10 MB/s | 100 MB/s (higher is better) | Higher disk bandwidth allows faster data recovery when a failed member needs to catch up with the cluster. |
| Throughput (sequential 8 kB write with `fdatasync`) | 50 writes per 10 ms | 500 writes per 2 ms | Reflects sustained write throughput when data is flushed to disk after each write operation. |

#### Benchmarking with fio \{#benchmark_with_fio}

To measure actual sequential IOPS and throughput, use the disk benchmarking tool `fio`:

:::warning
Do not run these tests against any nodes of the <Term name="productShort" /> clusters.  
Instead, run the tests against a dedicated VM that has the same set up as the control plane nodes.  
:::

```bash
set -e
mkdir -p /var/lib/etcd/

echo "INFO: Running fio"
fio --rw=write --ioengine=sync --fdatasync=1 --directory=/var/lib/etcd --size=100m --bs=8000 --name=etcd_perf --output-format=json --runtime=60 --time_based=1 | tee /tmp/fio.out

# Scrape the fio output for p99 of fsync in ns
fsync=$(cat /tmp/fio.out | jq '.jobs[0].sync.lat_ns.percentile["99.000000"]')
iops=$(cat /tmp/fio.out | jq '.jobs[0].write.iops')
echo "INFO: 99th percentile of fsync is $fsync ns"

# Compare against the recommended value
if [[ $fsync -ge 10000000 ]]; then
    echo "WARN: IOPS is $iops, 99th percentile of the fsync is greater than the recommended value which is ${fsync} ns > 10 ms, faster disks are recommended to host etcd for better performance"
else
    echo "INFO: IOPS is $iops, 99th percentile of the fsync is within the recommended threshold: - 10 ms, the disk can be used to host etcd"
fi
```
