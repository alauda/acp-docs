# Configure Node Resource Reservation

Node resource reservation keeps CPU, memory, and ephemeral storage available for the operating system and Kubernetes components. On clusters that run Alauda OS, Machine Configuration can apply this reservation after a node starts.

The reservation uses a `KubeletConfig` object. Machine Configuration converts that object into a `MachineConfig`, and the machine configuration daemon applies it to the selected nodes.

## Supported Fields

The `KubeletConfig` API supports only these kubelet fields:

| Field | Purpose |
| --- | --- |
| `systemReserved` | Resources reserved for operating system daemons |
| `kubeReserved` | Resources reserved for Kubernetes components |
| `evictionHard` | Hard eviction thresholds |

Other kubelet settings remain with the node provider configuration. Do not use this API as a general kubelet configuration override.

## Choose a Reservation Mode

Set `spec.autoSizingReserved` to choose the mode:

- `true`: Machine Configuration calculates `systemReserved` on each node. Do not set `systemReserved` in the same object. You can still set `kubeReserved` and `evictionHard`.
- `false`: Machine Configuration uses only the values that you set. It does not calculate missing values.

A node pool can match only one `KubeletConfig`. If more than one object selects the same pool, Machine Configuration reports a conflict and does not merge the objects.

## Use the Default Automatic Reservation

Machine Configuration creates a default object named `acp-default-node-reservation` on supported clusters. The default object uses automatic mode:

```yaml
apiVersion: machineconfiguration.alauda.io/v1alpha1
kind: KubeletConfig
metadata:
  name: acp-default-node-reservation
spec:
  autoSizingReserved: true
  machineConfigPoolSelector:
    matchLabels:
      machineconfiguration.alauda.io/node-reservation: "true"
```

The default control plane and worker pools receive the `machineconfiguration.alauda.io/node-reservation=true` label. The default object applies to both pools.

To confirm the default object:

```bash
kubectl get kubeletconfig acp-default-node-reservation
kubectl get machineconfigpool -L machineconfiguration.alauda.io/node-reservation
```

## Set Static Reservation Values

Use static mode when the reserved values must be the same on every selected node.

1. Create the target worker pool before you apply the reservation. Follow [Managing Node Configuration](./managing.mdx) to create the pool and assign nodes to it. This example uses a custom pool named `worker-static`.

2. Add a label that the reservation object can select:

   ```bash
   kubectl label machineconfigpool worker-static reservation=static
   ```

3. Create a `KubeletConfig` that selects that label:

   ```yaml
   apiVersion: machineconfiguration.alauda.io/v1alpha1
   kind: KubeletConfig
   metadata:
     name: worker-static-reservation
   spec:
     autoSizingReserved: false
     machineConfigPoolSelector:
       matchLabels:
         reservation: static
     kubeletConfig:
       systemReserved:
         cpu: 500m
         memory: 1Gi
         ephemeral-storage: 1Gi
       kubeReserved:
         cpu: 200m
         memory: 1Gi
       evictionHard:
         memory.available: 100Mi
         nodefs.available: 10%
   ```

4. Apply the object:

   ```bash
   kubectl apply -f worker-static-reservation.yaml
   ```

Static mode does not create the node sizing service. It writes only the values in `spec.kubeletConfig`.

## Verify the Reservation

1. Confirm that the object was accepted:

   ```bash
   kubectl get kubeletconfig worker-static-reservation -o yaml
   ```

   The object should not report a conflict or validation failure.

2. Confirm that the selected pool is updating or has finished updating:

   ```bash
   kubectl get machineconfigpool worker-static
   ```

3. Confirm that each target node has finished applying the configuration:

   ```bash
   kubectl get node -o custom-columns=NODE:.metadata.name,CURRENT:.metadata.annotations."machineconfiguration\.alauda\.io/currentConfig",DESIRED:.metadata.annotations."machineconfiguration\.alauda\.io/desiredConfig",STATE:.metadata.annotations."machineconfiguration\.alauda\.io/state"
   ```

   `STATE` should be `Done`, and `CURRENT` should match `DESIRED`.

4. On a target node, confirm that kubelet is using the reserved values:

   ```bash
   ps -ef | grep kubelet | grep system-reserved
   ```

   For automatic mode, also confirm that the node sizing result contains `ACP_KUBELET_RESERVATION_ARGS`:

   ```bash
   grep ACP_KUBELET_RESERVATION_ARGS /etc/systemd/node-sizing.env
   ```

   The command should print a `--system-reserved` value. If the file contains only `ACP_KUBELET_STATIC_ARGS`, the reservation has not finished calculating.

## Update Behavior

A successful reservation update reloads systemd and restarts kubelet. It does not plan a node reboot.

Machine Configuration applies the reservation after the node has already started. The first control plane node can start with the provider configuration and then receive the reservation during Machine Configuration convergence.

Do not place the same reservation in provider bootstrap files when you want Machine Configuration to own it. Bootstrap file changes can replace control plane machines. The reservation objects in this procedure do not change those bootstrap files.

## Limitations

- The feature applies to clusters that run Alauda OS and Machine Configuration.
- It does not apply to OpenShift, imported clusters, registered clusters, or managed cloud clusters that Machine Configuration does not manage.
- Automatic mode calculates `systemReserved` only. It does not calculate `kubeReserved` or `evictionHard`.
- A pool cannot use two reservation objects at the same time.
