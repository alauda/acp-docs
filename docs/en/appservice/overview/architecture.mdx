# Architecture

![](./assets/appservice_architecture_en.png)

The Alauda Application Services platform is a robust, open-source service management solution built on Kubernetes (K8S), tailored for seamless Alauda Application Services operations. It serves as a centralized hub, efficiently orchestrating a diverse range of popular service components, including MySQL, Redis, Kafka, and RabbitMQ. Here's how it works:

- Service Components: The platform supports key services like MySQL, Redis, Kafka, and RabbitMQ, ensuring stable, reliable operation across all components.

- Common Services: It provides parameter templates, inspection, alert management, backup services etc, offering users a one-stop service management solution.

- Operator Controller: The Operator Controller is an extension of Kubernetes, designed to simplify the deployment and management of applications. It extends the Kubernetes API through Custom Resource Definitions (CRD) to manage the lifecycle of applications.

- Container Infrastructure: The Alauda Application Services platform is built on Kubernetes and leverages the underlying infrastructure it provides to offer foundational capabilities such as data persistence and external access.

## Rich Services Support \{#compatible_sc}

The Alauda Application Services platform supports various types of services, including databases, caches, message queues, etc. The following are the compatible storage classes and default scheduling rules of the main alauda application services. Each service is released independently of the platform, so its supported versions are listed in its own documentation: <ExternalSiteLink name="mysql-pxc" children="MySQL-PXC" />, <ExternalSiteLink name="mysql-mgr" children="MySQL-MGR" />, <ExternalSiteLink name="redis" children="Redis" />, <ExternalSiteLink name="valkey" children="Valkey" />, <ExternalSiteLink name="kafka" children="Kafka" />, <ExternalSiteLink name="rabbitmq" children="RabbitMQ" />, and <ExternalSiteLink name="postgresql" children="PostgreSQL" />.

  | Alauda Application Services | Data Persistence Compatible Storage Class | Backup Compatible Storage Class        | Default Scheduling Rule (Single Instance)                                |
  | --------------------------- | ----------------------------------------- | -------------------------------------- | ------------------------------------------------------------------------ |
  | MySQL-PXC                   | TopoLVM (recommended)                     | S3 (recommended), TopoLVM              | At most (required) only one MySQL node can be scheduled on each node.    |
  | MySQL-MGR                   | TopoLVM (recommended)                     | S3 (recommended)                       | At most (required) only one MySQL node can be scheduled on each node.    |
  | Redis                       | TopoLVM (recommended)                     | S3 (recommended), TopoLVM, CephFS, NFS | Cluster mode: At most (required) only one Redis node can be scheduled on each node. Sentinel mode: At most (required) only one Redis data node and only one Redis Sentinel node can be scheduled on each node, so a data node and a Sentinel node can share a node. |
  | Valkey                      | TopoLVM                                   | -                                      | Cluster mode: At most (required) only one Valkey node of the same shard can be scheduled on each node; nodes of different shards can share a node. Failover mode: At most (required) only one Valkey data node and only one Sentinel node can be scheduled on each node, so a data node and a Sentinel node can share a node. Replica mode: At most (required) only one Valkey data node can be scheduled on each node. |
  | Kafka                       | TopoLVM (recommended)                     | -                                      | At most (required) only one Broker node can be scheduled on each node.   |
  | RabbitMQ                    | TopoLVM (recommended)                     | -                                      | At most (required) only one RabbitMQ node can be scheduled on each node. |
  | PostgreSQL                  | TopoLVM (recommended)                     | S3 (recommended)                       | Strive to schedule one PostgreSQL node on each node.                     |
