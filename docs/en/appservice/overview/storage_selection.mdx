# Storage Selection

Choose the storage before you create an instance. The storage class of a persistent volume claim cannot be changed later, so moving to other storage means creating a new instance and moving the data. This page covers high availability and backup in a single <Term name="product" /> (<Term name="productShort" />) cluster in one data center.

## Selection Procedure

1. List the storage on site. Count enterprise storage only if it exists or is within the budget.
2. Find the rows of each instance and its backup in the tables below.
3. If the storage is not TopoLVM, [make it selectable in the console](#console).
4. Run the [pre-production checks](#verify).

Each cell gives a recommendation: **Recommended**, **Secondary** (when the recommended storage is not available or does not fit), **Last resort** (test it first, see [Storage Limits](#limits)), or **Avoid**. **Testing only** means only where data loss is acceptable. Two **Recommended** cells in a row are equal choices. A dash means not applicable or not evaluated.

Back up to a different device from the primary data. Where the product supports it, register the backup target in [Backup Management](/appservice/unified-om/backup-mgt/index.mdx), also called **Backup Center**. If the primary data is in Ceph, back up outside that Ceph cluster.

### Storage Limits \{#limits}

- **TopoLVM**: a volume stays on its node and cannot span nodes. A node failure makes it unavailable, and a disk failure can lose its data. After a permanent loss, the replica restarts empty on another node once its persistent volume claim is deleted. In production, use device classes whose **Provision Type** is **Thick**, because a **Thin** device class over-provisions and a volume can run out of space early.
- **Enterprise SAN**: all replicas on one array share it as a failure domain. Two arrays still leave a majority of 3 members on one array, so use three arrays to survive the loss of one. After an unexpected node shutdown, a volume might not detach. See [Detach CSI Volumes After Non-Graceful Node Shutdown](/configure/storage/trouble_shooting/detach_csi_volumes_non_graceful_shutdown.mdx). No product documents a validated SAN.
- **Ceph RBD**: all replicas share one Ceph failure domain, and the default three-replica pool turns 3 copies into 9.

## Storage Classes in the Console \{#console}

The instance forms of MySQL-MGR, PostgreSQL, Redis, Kafka, and RabbitMQ offer only TopoLVM by default. To offer another storage class, an administrator adds its provisioner to the `middleware-sc-cm` ConfigMap in the `cpaas-system` namespace of the `global` cluster, under the component key `MGR`, `PostgreSQL`, `Redis`, `Kafka`, or `RabbitMQ`. Do not edit `middleware-sc-cm-base`.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: middleware-sc-cm
  namespace: cpaas-system
data:
  middleware_sc_map.yaml: |
    Redis:
      instance:
        - rook-ceph.rbd.csi.ceph.com
```

The `Redis.backup` key controls Redis PVC backups, and from Data Services Essentials v4.4.1 it allows NFS, CephFS, and TopoLVM by default. Valkey, CloudNativePG, ClickHouse, OpenSearch, and Milvus are not in the list.

- Prefer the SAN over TopoLVM only when a full rebuild of the largest replica takes too long, the SAN passes your commit latency test, and you accept the array as a shared failure domain.
- For RPO = 0, use synchronous replication: MySQL-MGR with 3 or 5 members, PostgreSQL with `spec.patroni.synchronous_mode` and `synchronous_mode_strict` set to `true`, and CloudNativePG with `spec.postgresql.synchronous` and `dataDurability` not set to `preferred`. Run at least 3 instances, so that losing one replica does not stop writes. PostgreSQL and CloudNativePG pause writes when too few synchronous standbys remain.

## Pre-Production Checks \{#verify}

The product documentation gives no thresholds, so test against your own requirements:

- Commit latency for databases, ClickHouse Keeper, and Milvus etcd, especially on an enterprise SAN or Ceph RBD.
- Throughput on Ceph RBD, and the rebuild time of the largest replica on TopoLVM.
- Recovery after you shut down a node, as described in [Node and Disk Loss](#node-loss).
- A restore into a new instance, repeated regularly.

## Node and Disk Loss \{#node-loss}

On TopoLVM and Local Storage, check what the product documents before you delete the persistent volume claim of a lost node:

| Product | Product documentation |
| --- | --- |
| MySQL-MGR | Recovery needs manual reprovisioning and data resync. See <ExternalSiteLink name="mysql-mgr" href="/how_to/40-deploy-without-topolvm.html" children="Deploy MySQL-MGR Without TopoLVM" />. |
| CloudNativePG | PVC replacement was tested with RPO = 0. Node shutdown was not tested for v1.30.1-acp.1. See <ExternalSiteLink name="cnpg" href="/release_notes.html" children="Release Notes" />. |
| Valkey | Do not delete the claim until the recovery procedure is known. See <ExternalSiteLink name="valkey" href="/trouble_shooting/10-instance-not-ready.html" children="Diagnose an instance that is not Ready" />. |
| ClickHouse Keeper | Losing two of 3 members, or the Keeper volumes, makes replicated tables read-only. See <ExternalSiteLink name="clickhouse" href="/how_to/deploy_keeper_quorum.html" children="Deploy a Keeper quorum" />. |
| OpenSearch | Keep `number_of_replicas` at 1 or more so that no data is lost. See <ExternalSiteLink name="opensearch" href="/functions/storage.html" children="Storage" />. |
| Others | Not documented. Test the recovery first. RabbitMQ quorum queue membership may need manual repair. |
