# Storage Selection

Choose the storage for an Alauda Application Services instance before you create it. The storage class of a persistent volume claim cannot be changed after the claim is created, so moving an instance to other storage means creating a new instance and moving the data. For example, the OpenSearch operator rejects a storage class change on an existing node pool, and the Valkey operator provides no volume migration.

This page covers high availability and backup inside a single Kubernetes cluster in a single data center. Cross-data-center disaster recovery is out of scope.

## How to Choose

1. List the storage available on site. See [Storage Types](#storage-types).
2. For each instance, find its product and topology in the tables of [Relational Databases](#relational), [Middleware That Replicates Data Itself](#replicated), or [Milvus](#milvus), and read the recommended storage.
3. If the storage is not TopoLVM, [make it selectable in the console](#console).
4. Before going live, run the checks in [Verify Before Going Live](#verify).
5. Plan backup to a different device. See [Backup](#backup).

The tables on this page give recommendations, not support statements:

- **Recommended**: the default choice.
- **Secondary**: the choice when the recommended storage is not available or does not fit your environment.
- **Last resort**: works, with the drawback given in the table; test it before going live.
- **Not recommended**: avoid in production for this scenario.
- **Do not use**: unsuitable for this scenario.
- **Not needed**: the scenario does not call for this storage.

Whether a product is validated on a storage type is stated in the **What the product documentation states** columns and in the notes.

## Storage Types \{#storage-types}

| Storage | Provisioner | When the node of a Pod is lost | Expansion | Snapshot |
| --- | --- | --- | --- | --- |

For the storage systems that the platform provides and their typical uses, see [Overview](/storage/overview.mdx). For the access modes and the expansion and snapshot support of each storage class, see [Access Modes and Volume Modes](/configure/storage/concepts/selection.mdx). To make the platform recognize the capabilities of a third-party storage class, see [Third-Party Storage Capability Annotation Guide](/configure/storage/how_to/third_mask.mdx).

This page uses the following terms:

- **The volume follows the Pod**: when a Pod is rescheduled to another node, its volume is attached to that node. TopoLVM and Local Storage volumes are bound to the disks of one node and do not follow the Pod.
- **Copies**: the total number of copies of the data, including the primary. Products count differently. For example, OpenSearch `number_of_replicas: 1` and a Redis instance with one replica each mean **2 copies**.

## Make the Storage Selectable in the Console \{#console}

The instance forms of MySQL-MGR, PostgreSQL, Redis, Kafka, and RabbitMQ list only the storage classes whose provisioner is allowed for that component. By default, only TopoLVM (`topolvm.cybozu.com`) is allowed for instances. To select another storage class recommended on this page, such as an enterprise SAN or Ceph RBD, an administrator adds its provisioner to the `middleware-sc-cm` ConfigMap in the `cpaas-system` namespace of the `global` cluster. The entries are added to the default list; they do not replace it. For example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: middleware-sc-cm
  namespace: cpaas-system
data:
  middleware_sc_map.yaml: |
    Redis:
      instance:
        - rook-ceph.rbd.csi.ceph.com
```

Use the component keys `MGR`, `PostgreSQL`, `Redis`, `Kafka`, and `RabbitMQ`, and the `provisioner` value of the storage class. Do not edit the `middleware-sc-cm-base` ConfigMap, which is the shipped default.

- The same list controls the storage classes offered for Redis PVC backups, under `Redis.backup`. From Alauda Container Platform Data Services Essentials v4.4.1, the default list for backups contains NFS, CephFS, and TopoLVM.
- The list has no entries for Valkey, CloudNativePG, ClickHouse, OpenSearch, or Milvus. Valkey has no Web Console; set `spec.storage.storageClassName` in the custom resource.

## Relational Databases \{#relational}

This section covers **MySQL-MGR, PostgreSQL, and CloudNativePG**.

### Recommended Storage

| Scenario | TopoLVM | Enterprise SAN | Ceph RBD | NFS or CephFS | Why |
| --- | --- | --- | --- | --- | --- |
| **Multi-replica production database** | Secondary | Recommended | Last resort | Do not use | Rebuilding a database replica copies the whole database. A SAN replica survives the loss of its node and follows the Pod, so it only catches up on missing changes instead of being rebuilt. The array handles disk failures.<br />TopoLVM gives each replica its own failure domain and the lowest latency, but a replica on it is fully rebuilt after its node or disk is lost permanently.<br />On Ceph RBD, all replicas share one Ceph failure domain, and every write is replicated again inside Ceph.<br />NFS and CephFS are shared file storage. CloudNativePG asks for a block-mode storage class, and none of the three products recommends file storage. |
| **Single-instance database** | Not recommended | Recommended | Secondary | Do not use | No replica can copy the data back, so the volume must follow the Pod to a replacement node. |
| **Development and testing** | Recommended | Not needed | Not needed | Not needed | Data loss is acceptable. The default storage class also works. |

RPO = 0 comes from synchronous replication, not from storage. See [Settings for RPO = 0](#rpo-zero).

| --- | --- | --- | --- |
| **MySQL-MGR**, 3 or more members. The console offers Single Master (the default) and Multi-Master, and recommends at least 3 members; the maximum is 9. | One copy per member. A transaction commits after a majority of members agree. | Multi-replica production database | TopoLVM is recommended, and the console asks for a TopoLVM storage class. v4.4.1 fixed instances that failed to start on Ceph RBD and NFS. | **PostgreSQL**, Primary-Replica Replication with 3 or more instances | One copy per instance. Replication is asynchronous unless `synchronous_mode` is enabled; its default is `false`. | Multi-replica production database | A storage class with dynamic provisioning, SSD storage with high IOPS, and at least 50 GB. No storage type is named. See <ExternalSiteLink name="postgresql" href="/how_to/configure_ha_cluster.html" children="Configuring a High Availability PostgreSQL Cluster" />. |
| **CloudNativePG**, 3 or more instances | One copy per instance, replicated by streaming WAL with no shared storage. Synchronous when `spec.postgresql.synchronous` is set. | Multi-replica production database | A block-mode storage class; the sample uses a TopoLVM class for production. ### Notes

- MySQL-MGR on storage other than TopoLVM, including an enterprise SAN, Ceph RBD, and NFS, requires MySQL-MGR v4.4.1 or later. Earlier versions cannot initialize the data directory on such volumes.
- MySQL-MGR is validated on TopoLVM, Ceph RBD, and local persistent volumes. Validate it on your SAN before going live.
- Prefer TopoLVM over the SAN if only one array is available and you cannot accept it as a common failure domain, if the SAN cannot meet your commit latency requirement in tests, or if the array lacks capacity. All replicas on one array share it as a failure domain.
- With two arrays, place the replicas of each database on different arrays by using CSI topology and Pod anti-affinity. One array still holds a majority of a 3-member MySQL-MGR cluster, so losing that array stops writes. To survive the loss of any one array, use three arrays.
- On TopoLVM, one instance must fit on one node.
- MySQL-MGR places at most one member on each node by default, so an N-member cluster needs at least N schedulable nodes. If the cluster has no more nodes than replicas, add nodes. With required anti-affinity, no storage lets a Pod move to a node that already runs another replica.

### Settings for RPO = 0 \{#rpo-zero}

Configure synchronous replication and run at least 3 instances, so that losing one replica does not stop writes.

- MySQL-MGR: 3 or 5 members. A transaction commits only after a majority of members agree on it, and writes stop when a majority is lost.
- PostgreSQL: set `spec.patroni.synchronous_mode` and `spec.patroni.synchronous_mode_strict` to `true`. With `synchronous_mode` alone, Patroni falls back to asynchronous replication when no synchronous standby is left.
- CloudNativePG: configure `spec.postgresql.synchronous` (`method` and `number`), and leave `dataDurability` unset or set to `required`. Do not set it to `preferred`.

With these settings, PostgreSQL and CloudNativePG pause writes when not enough synchronous standbys are available.

## Middleware That Replicates Data Itself \{#replicated}

This section covers **Redis, Valkey, Kafka, RabbitMQ, ClickHouse, and OpenSearch**. These components rebuild a lost replica from the other copies.

### Recommended Storage

| Scenario | TopoLVM | Enterprise SAN | Ceph RBD | Why |
| --- | --- | --- | --- | --- |
| **Multiple copies** | Recommended | Secondary | Last resort | Rebuilding a replica from the other copies is routine. TopoLVM gives the lowest latency and one failure domain per replica, without paying for redundancy twice.<br />With 2 copies, only one copy remains while a replica is rebuilt. A SAN shortens that window, because a replica on it survives the loss of its node.<br />On Ceph RBD with the default three-replica pool, 3 copies become 9 copies on the network. |
| **One copy only** | Not recommended | Recommended | Secondary | No replica can copy the data back, so the volume must follow the Pod. |
| **No persistence** | No persistent volume | No persistent volume | No persistent volume | The data can be regenerated. |

This page does not evaluate NFS or CephFS for the data volumes of these components.

### Notes

- With asynchronous replication, an acknowledged write may exist on only one copy and is lost on a failover, whatever the storage. Use synchronous or majority writes where the product supports them, or accept the risk.
- For components with only one copy, prefer adding copies, for example a higher Kafka replication factor or RabbitMQ quorum queues, so that TopoLVM becomes an option.
- Message queues that must not lose messages:
  - Kafka: replication factor 3, `min.insync.replicas=2`, and producer `acks=all`.
  - RabbitMQ: 3 or 5 nodes, quorum queues or streams, publisher confirms, and manual consumer acknowledgements.
- `insert_quorum` is a ClickHouse user setting, set in a profile or on each insert. The operator does not set it. With 2 replicas per shard and `insert_quorum` 2, inserts stop while one replica is down.
- Put ClickHouse Keeper or ZooKeeper on SSDs or NVMe. They commit through `fsync`, and slow disks show up as replication and insert latency.
- Size ClickHouse volumes with free space for merges, on any storage. On TopoLVM, also keep free space in each node's volume group, so that the volumes can be expanded later.
- RabbitMQ instances created in the console place at most one node on each host. If the cluster has no more nodes than replicas, add nodes.

## Verify Before Going Live \{#verify}

Test the storage with the instance's own workload before going live. The product documentation states no latency or throughput thresholds; compare the results with your requirements.

- **Commit latency** of the storage class for databases, ClickHouse Keeper or ZooKeeper, and Milvus etcd, especially on storage marked Secondary or Last resort above. The product documentation points to fast storage: MySQL-MGR selects its parameter template by storage medium, PostgreSQL recommends SSD storage with high IOPS, and Redis AOF persistence needs high-performance storage.
- **Throughput** on Ceph RBD for components with multiple copies.
- **Full rebuild time** of a replica of the largest instance on TopoLVM, measured against how long you can run with one copy fewer.
- **S3 conditional writes** on the object storage for Milvus with Woodpecker.
- **Node loss**: shut down a node that runs a member, and confirm that the instance recovers as described in [When a Node or Disk Is Lost](#node-loss).
- **Restore**: restore a backup into a new instance. A successful backup job does not prove that the data can be restored. Repeat this regularly.

## When a Node or Disk Is Lost \{#node-loss}

| Storage | What happens |
| --- | --- |
| TopoLVM, Local Storage | The volume stays on the lost node, so the Pod cannot start on another node until its volume is removed. A Pod started without the volume starts empty, and whether the replica is rebuilt automatically depends on the component. |
| Ceph RBD, CephFS, NFS, enterprise SAN | The volume is attached to the node that the Pod moves to. After an unexpected node shutdown, the volume might not detach automatically. See [Detach CSI Volumes After Non-Graceful Node Shutdown](/configure/storage/trouble_shooting/detach_csi_volumes_non_graceful_shutdown.mdx). |

Before you remove a volume on TopoLVM or Local Storage, read what the product documents about recovery:

| Product | What the product documentation states |
| --- | --- |
| MySQL-MGR | Persistent volumes bound to a lost node cannot be migrated. Recovery requires manual reprovisioning and data resync. See <ExternalSiteLink name="mysql-mgr" href="/how_to/40-deploy-without-topolvm.html" children="Deploy MySQL-MGR Without TopoLVM" />. |
| CloudNativePG | When the node of the primary fails, the operator promotes the most advanced standby automatically. See <ExternalSiteLink name="cnpg" href="/how_to/ops-runbook.html" children="Operations Runbook" />. |
| Valkey | Do not delete a persistent volume claim until its data-retention requirement and recovery procedure are known. See <ExternalSiteLink name="valkey" href="/trouble_shooting/10-instance-not-ready.html" children="Diagnose an instance that is not Ready" />. |
| ClickHouse | Losing one of 3 Keeper members is tolerated. Losing two makes replicated tables read-only until a second member is back. Deleting the Keeper volumes makes them read-only until their replicas are registered again. See <ExternalSiteLink name="clickhouse" href="/how_to/deploy_keeper_quorum.html" children="Deploy a Keeper quorum" />. |
| OpenSearch | The Pod cannot start elsewhere until the volume is removed. Keep `number_of_replicas` at 1 or more so that the cluster keeps all data. See <ExternalSiteLink name="opensearch" href="/functions/storage.html" children="Storage" />. |
| PostgreSQL, Redis, Kafka, RabbitMQ, Milvus | Not documented. For example, RabbitMQ quorum queue membership may need to be repaired by hand. Test the recovery before you rely on TopoLVM. |

## Backup \{#backup}

Back up every production component that supports backup to storage on a different device from the primary data, preferably object storage registered in [Backup Management](/appservice/unified-om/backup-mgt/index.mdx). Replicas do not replace backup, because accidental deletion is replicated to every copy. Snapshots that stay on the same array or node are not backups.

For the backup target, use enterprise object storage, or Ceph Object Storage as the secondary choice. If the primary data is in Ceph, back up outside that Ceph cluster; when Ceph is the only storage on site, Ceph Object Storage does not meet this rule.

| Product | Backup | Documentation |
| --- | --- | --- |

| PostgreSQL | Scheduled and manual backups to S3-compatible object storage, with PITR. A restore creates a new instance. | <ExternalSiteLink name="postgresql" href="/functions/15_back_restore.html" children="Backup and Restore" /> |

Volume snapshot backups also exist; they count as backups only when the snapshots are stored off the primary device, and they were not tested in v1.30.1. | <ExternalSiteLink name="cnpg" href="/how_to/ops-runbook.html" children="Operations Runbook" /> |
| Redis | S3 backup, or PVC backup to NFS, CephFS, or TopoLVM. A PVC backup counts as a backup only on NFS or CephFS separate from the primary data. ## Why These Recommendations

- **Match the storage to the redundancy of the middleware.** In production, use TopoLVM only when the middleware keeps at least 2 copies of the data at the application layer. Otherwise, use storage whose volume follows the Pod, such as an enterprise SAN or Ceph RBD.
- **Storage does not replace replication.** Redis and Valkey replicate asynchronously. On a failover, writes that did not reach the promoted replica are lost, whatever storage the old primary uses. No storage gives them a recovery point objective (RPO) of zero.
- **Storage-layer redundancy under replicated middleware multiplies capacity and traffic.** That is why Ceph RBD is the last resort for components with multiple copies.
- **Rebuild cost differs.** Rebuilding a database replica copies the whole database, which is why a SAN, on which a replica only catches up, is preferred for databases. Components that replicate data themselves rebuild replicas as a routine operation, which is why TopoLVM is preferred for them.
- **Consider enterprise storage only when it is available**, that is, it already exists on site or is within the budget.
