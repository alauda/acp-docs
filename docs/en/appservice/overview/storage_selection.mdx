# Storage Selection

This guide helps you choose storage for Alauda Application Services. It first describes the storage selection principles for each type of middleware, then gives storage recommendations for the main scenarios of each type.

The guide covers high availability and backup inside a single Kubernetes cluster in a single data center. Cross-data-center disaster recovery is out of scope. For the storage types that the platform provides and their typical uses, see [Overview](/storage/overview.mdx). For the access modes and features of each storage class, see [Access Modes and Volume Modes](/configure/storage/concepts/selection.mdx).

This guide uses the following terms:

- **Enterprise storage**: external storage products from third-party vendors, such as an enterprise storage area network (SAN) array or enterprise object storage, connected to the cluster through the vendor's CSI driver. To make the platform recognize the capabilities of a third-party storage class, see [Third-Party Storage Capability Annotation Guide](/configure/storage/how_to/third_mask.mdx).
- **TopoLVM**: the TopoLVM-based dynamic provisioner of [LVM Storage](/storage/storagesystem_topolvm/index.mdx). A TopoLVM volume is bound to the disks of one node.
- **Ceph RBD** and **Ceph Object Storage**: the block storage and object storage of [Ceph Distributed Storage](/storage/storagesystem_ceph/index.mdx). See [Creating CephRBD Block Storage Class](/configure/storage/functions/cephrbd_storageclass.mdx).
- **The volume follows the Pod**: when a Pod is rescheduled to another node, its volume is attached to that node. This applies to network storage such as an enterprise SAN or Ceph RBD, but not to TopoLVM.
- **Copies**: this guide counts the total number of copies of the data, including the primary. Products count differently. For example, OpenSearch `number_of_replicas: 1` and a Redis instance with one replica each mean **2 copies**.

## Make the Storage Selectable in the Console

The instance forms of MySQL-MGR, PostgreSQL, Redis, Kafka, and RabbitMQ list only the storage classes whose provisioner is allowed for that component. By default, only TopoLVM (`topolvm.cybozu.com`) is allowed for instances. To select another storage class recommended in this guide, such as an enterprise SAN or Ceph RBD, an administrator adds its provisioner to the `middleware-sc-cm` ConfigMap in the `cpaas-system` namespace of the `global` cluster. The entries are added to the default list; they do not replace it. For example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: middleware-sc-cm
  namespace: cpaas-system
data:
  middleware_sc_map.yaml: |
    Redis:
      instance:
        - rook-ceph.rbd.csi.ceph.com
```

Use the component keys `MGR`, `PostgreSQL`, `Redis`, `Kafka`, and `RabbitMQ`, and the `provisioner` value of the storage class. Do not edit the `middleware-sc-cm-base` ConfigMap, which is the shipped default.

## Selection Principles

### General Principles

- **Match the storage to the redundancy of the middleware.** In production, use TopoLVM only when the middleware keeps at least 2 copies of the data at the application layer. Otherwise, use storage whose volume follows the Pod, such as an enterprise SAN or Ceph RBD.
- **Storage does not replace replication.** For example, Redis and Valkey replicate asynchronously. On a failover, writes that did not reach the promoted replica are lost, whatever storage the old primary uses. No storage gives them a recovery point objective (RPO) of zero.
- **Back up every production component that supports backup** to storage on a different device from the primary data, preferably object storage registered in [Backup Management](/appservice/unified-om/backup-mgt/index.mdx). Snapshots that stay on the same array or node are not backups. If the primary data is in Ceph, back up outside that Ceph cluster. When Ceph is the only storage on site, the Ceph Object Storage options in the backup rows below do not meet this principle.
- **Consider enterprise storage only when it is available**, that is, it already exists on site or is within the budget.

### Relational Databases

- **Prefer an enterprise SAN.** Rebuilding a database replica copies the whole database. A SAN volume survives a node failure and follows the Pod, so the replica only catches up on missing changes instead of being rebuilt.
- **Use TopoLVM when independent failure domains matter more.** All replicas on one array share the array as a failure domain. TopoLVM gives each replica its own failure domain, but a replica must be fully rebuilt when its node or disk is lost permanently.
- **For multi-replica databases, use Ceph RBD only as a last resort.** All replicas share one Ceph failure domain, and every write is replicated over the network inside Ceph. Do not use NFS or CephFS for databases.
- **Backup is mandatory**, and so is point-in-time recovery (PITR) where the database supports it.

### Middleware That Replicates Data Itself

- **Prefer TopoLVM.** These components rebuild replicas from the other copies. TopoLVM gives the lowest latency and a separate failure domain for each replica. Storage-layer redundancy only multiplies capacity and traffic: 3 copies on Ceph RBD with the default three-replica pool become 9 copies.
- **Put ClickHouse Keeper or ZooKeeper on SSDs or NVMe.** They commit through `fsync`, and slow disks show up as replication and insert latency.
- **Two copies and asynchronous replication carry different risks.**
  - With 2 copies, only one copy remains while a replica is rebuilt. Storage whose volume follows the Pod, such as an enterprise SAN, shortens that window because a replica on it survives the loss of its node.
  - With asynchronous replication, an acknowledged write may exist on only one copy and is lost on a failover. Storage cannot fix this. Use synchronous or majority writes where the product supports them, or accept the risk.
- **Without application-layer redundancy, use storage whose volume follows the Pod**, or better, change the component to keep multiple copies.
- **Replicas do not replace backup.** Accidental deletion is replicated to every copy.

### Vector Databases

- **Use external object storage with its own redundancy in production.** Milvus keeps vector data in object storage. The built-in Silo object storage is documented as a single instance, so use it for development and testing only. Its Kubernetes resources are named `<instance>-minio`.
- **Confirm that the object storage supports S3 conditional writes** when Woodpecker is the write-ahead log (WAL) of Milvus, which requires `spec.dependencies.msgStreamType: woodpecker` in cluster mode. With the default setting, Milvus does not start if the object storage lacks conditional writes.
- **Plan storage for etcd.** Milvus keeps its metadata in etcd, not in object storage.
- **Plan backup separately.** The Milvus operator does not provide a general-purpose backup.

## Recommendations by Middleware

In the tables below, **Recommended** is the default choice and **Secondary** is the choice when the recommended storage is not available or does not fit your environment. Notes under each table list the last-resort option and conditions that change the order.

### Relational Databases \{#rec-relational}

This category covers **MySQL-MGR, PostgreSQL, and CloudNativePG**.

| Scenario | Recommended | Secondary | Rationale |
| --- | --- | --- | --- |
| **Multi-replica production databases** | Enterprise SAN | TopoLVM | SAN: after a node failure, a replica only catches up on missing changes. The array handles disk failures.<br />TopoLVM: independent failure domains and the lowest latency, but a full rebuild after losing a node or disk.<br />RPO = 0 comes from synchronous replication, not from storage. See the notes. |
| **Single-instance databases** | Enterprise SAN | Ceph RBD | No replica can copy the data back.<br />A SAN or Ceph RBD volume survives a lost node and can be attached to a replacement node. |
| **Backup** | Enterprise object storage | Ceph Object Storage | MySQL-MGR and PostgreSQL back up only to S3.<br />CloudNativePG backs up to object storage through the Barman Cloud plugin. It also supports volume snapshot backups, which count as backups only when the snapshots are stored off the primary device.<br />Replicas and same-device snapshots do not protect against deletion or device failure. |
| **PITR**: PostgreSQL and CloudNativePG only | Enterprise object storage | Ceph Object Storage | PostgreSQL (WAL-G) and CloudNativePG (Barman Cloud plugin) archive WAL to object storage for point-in-time recovery.<br />MySQL-MGR does not provide PITR. |
| **Development and testing** | TopoLVM | Default storage class | Data loss is acceptable. |

Notes:

- MySQL-MGR on storage other than TopoLVM, including an enterprise SAN, Ceph RBD, and NFS, requires MySQL-MGR v4.4.1 or later. Earlier versions cannot initialize the data directory on such volumes.
- MySQL-MGR is validated on TopoLVM, Ceph RBD, and local persistent volumes. Validate it on your SAN before going live.
- Prefer TopoLVM over the SAN if only one array is available and you cannot accept it as a common failure domain, if the SAN cannot meet your commit latency requirement in tests, or if the array lacks capacity.
- With two arrays, place the replicas of each database on different arrays by using CSI topology and Pod anti-affinity. One array still holds a majority of a 3-member MySQL-MGR cluster, so losing that array stops writes. To survive the loss of any one array, use three arrays.
- On TopoLVM, one instance must fit on one node. Measure the full rebuild time before going live.
- Ceph RBD is the last resort for multi-replica databases. Measure the commit latency first.
- MySQL-MGR places at most one member on each node by default, so an N-member cluster needs at least N schedulable nodes. If the cluster has no more nodes than replicas, add nodes. With required anti-affinity, no storage lets a Pod move to a node that already runs another replica.
- After an unexpected node shutdown, a SAN or Ceph RBD volume might not detach automatically. See [Detach CSI Volumes After Non-Graceful Node Shutdown](/configure/storage/trouble_shooting/detach_csi_volumes_non_graceful_shutdown.mdx).
- For RPO = 0, configure synchronous replication and run at least 3 instances, so that losing one replica does not stop writes.
  - MySQL-MGR: 3 or 5 members. A transaction commits only after a majority of members agree on it, and writes stop when a majority is lost.
  - PostgreSQL: set `spec.patroni.synchronous_mode` and `spec.patroni.synchronous_mode_strict` to `true`. With `synchronous_mode` alone, Patroni falls back to asynchronous replication when no synchronous standby is left.
  - CloudNativePG: configure `spec.postgresql.synchronous` (`method` and `number`), and leave `dataDurability` unset or set to `required`. Do not set it to `preferred`.
  - With these settings, PostgreSQL and CloudNativePG pause writes when not enough synchronous standbys are available.
- Run restore drills regularly. A successful backup job does not prove that the data can be restored.

### Middleware That Replicates Data Itself \{#rec-replicated}

This category covers **Redis, Valkey, Kafka, RabbitMQ, ClickHouse and ClickHouse Keeper, and OpenSearch**.

| Scenario | Recommended | Secondary | Rationale |
| --- | --- | --- | --- |
| **At least 3 copies with majority or synchronous writes**: Kafka (replication factor 3, `min.insync.replicas=2`), RabbitMQ quorum queues and streams, ClickHouse with at least 3 replicas per shard and `insert_quorum` set, 3-member ClickHouse Keeper, OpenSearch indices with `number_of_replicas` of 2 or more | TopoLVM | Enterprise SAN | Rebuilding a replica is routine and safe with one replica down.<br />TopoLVM: the lowest latency and one failure domain per replica.<br />No need to pay for three copies on an array. |
| **2 copies**: Redis or Valkey with persistence and one replica, ClickHouse with 2 replicas per shard, OpenSearch with `number_of_replicas: 1` on at least 2 data nodes | TopoLVM | Enterprise SAN | Only one copy remains while a replica is rebuilt.<br />If you cannot accept this window, use the SAN, so that a replica survives the loss of its node. |
| **Asynchronous replication**: Redis or Valkey, ClickHouse without `insert_quorum` | TopoLVM | Enterprise SAN | An acknowledged write may exist on only one copy and is lost on a failover, whatever the storage.<br />Choose the storage by the number of copies. |
| **One copy only**: Kafka (replication factor 1), RabbitMQ classic queues (non-mirrored, and all classic queues on RabbitMQ 4.x), ClickHouse with 1 replica per shard or non-replicated tables, OpenSearch with `number_of_replicas: 0` or a single data node, Redis or Valkey without replicas, single-member ClickHouse Keeper, Milvus Silo | Enterprise SAN | Ceph RBD | No replica can copy the data back, so the volume must follow the Pod. |
| **Pure cache**: Redis or Valkey without persistence | No persistent volume | Not applicable | The data can be regenerated. |
| **Backup**: Redis, ClickHouse, OpenSearch | Enterprise object storage | Ceph Object Storage | Replicas also replicate accidental deletions.<br />Redis: backs up to S3. Redis also supports PVC backup, which counts as a backup only on NFS or CephFS separate from the primary data. A PVC backup on TopoLVM stays on one node's disks; use it only for development and testing.<br />OpenSearch: snapshots to an S3 repository. The `repository-s3` plugin is not included in the image. Install it through `spec.general.pluginsList`; in an air-gapped environment, use a reachable URL of the plugin zip that matches the OpenSearch version, otherwise the nodes do not start. Provide the S3 credentials through `spec.general.keystore`.<br />ClickHouse: the operator does not provide backup. Use the ClickHouse `BACKUP` and `RESTORE` statements with S3, or an external tool. |

Notes:

- Valkey, Kafka, and RabbitMQ have no backup of message or cache data. For Kafka, export the topic configurations; for RabbitMQ, export the definitions. Neither recovers the data itself.
- Ceph RBD is the last resort for components with multiple copies. With the default three-replica pool, every write to a 3-copy component becomes 9 copies on the network. Test the throughput first.
- For components with only one copy, prefer adding copies, for example a higher Kafka replication factor or RabbitMQ quorum queues, so that TopoLVM becomes an option.
- Message queues that must not lose messages:
  - Kafka: replication factor 3, `min.insync.replicas=2`, and producer `acks=all`.
  - RabbitMQ: 3 or 5 nodes, quorum queues or streams, publisher confirms, and manual consumer acknowledgements.
- `insert_quorum` is a ClickHouse user setting, set in a profile or on each insert. The operator does not set it. Without it, ClickHouse replication is asynchronous. With 2 replicas per shard and `insert_quorum` 2, inserts stop while one replica is down.
- Size ClickHouse volumes with free space for merges, on any storage. On TopoLVM, also keep free space in each node's volume group, so that the volumes can be expanded later.
- Keep ClickHouse Keeper or ZooKeeper data safe. If it is lost, replicated tables become read-only until they are restored with `SYSTEM RESTORE REPLICA`.
- RabbitMQ instances created in the console place at most one node on each host. If the cluster has no more nodes than replicas, add nodes.
- On TopoLVM, after a node or disk is lost permanently, the Pod cannot move to another node until its PVC is deleted, and it then starts with an empty volume. Whether the replica is rebuilt automatically depends on the component; see its documentation before you rely on TopoLVM. For example, RabbitMQ quorum queue membership may need to be repaired by hand.

### Vector Databases \{#rec-vector}

This category covers **Milvus**.

| Scenario | Recommended | Secondary | Rationale |
| --- | --- | --- | --- |
| **Vector data and the WAL** | Enterprise object storage | Ceph Object Storage | Replaces the single-instance Silo with redundant object storage.<br />Woodpecker needs S3 conditional writes for a WAL in object storage. Test them first. |
| **etcd metadata** | TopoLVM with 3 etcd members | Enterprise SAN | 3 members replicate the metadata, as in [Middleware That Replicates Data Itself](#rec-replicated).<br />A single etcd member is one copy only; use storage whose volume follows the Pod. |
| **Backup**: vector data and metadata | Enterprise object storage | Ceph Object Storage | The Milvus operator does not provide a general-purpose backup.<br />Copy the object storage data and etcd together to another device with an external tool, so that they stay consistent. |

Notes:

- If the object storage does not support conditional writes, either set `woodpecker.logstore.fencePolicy.conditionWrite: disable` in the Milvus configuration, which uses etcd-based fencing, or use an external Kafka or Pulsar as the message stream. Test whichever you choose.
- If you must use Silo outside development and testing, choose its volume by the "One copy only" row in [Middleware That Replicates Data Itself](#rec-replicated).
