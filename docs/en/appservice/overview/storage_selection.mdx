# Storage Selection

Choose the storage for an Alauda Application Services instance before you create it. The storage class of a persistent volume claim cannot be changed after the claim is created, so moving an instance to other storage means creating a new instance and moving the data. For example, the OpenSearch operator rejects a storage class change on an existing node pool, and the Valkey operator provides no volume migration.

This page covers high availability and backup inside a single <Term name="product" /> (<Term name="productShort" />) cluster in a single data center. Cross-data-center disaster recovery is out of scope.

## Selection Procedure

1. List the storage available on site. See [Storage Types](#storage-types). Count enterprise storage only if it already exists on site or is within the budget.
2. Look up the product of each instance in [Relational Databases](#relational), [Middleware That Replicates Data Itself](#replicated), or [Milvus](#milvus). The topology of the instance gives its scenario, and the scenario gives the storage for its data and its backup.
3. If the storage is not TopoLVM, [make it selectable in the console](#console).
4. Before going live, run the [pre-production checks](#verify).

The tables give recommendations. **Secondary** is the choice when the recommended storage is not available or does not fit, and **Last resort** works with the drawback given in the table, so test it first. Whether a product is validated on a storage type is stated in the **Product documentation** columns and in the notes.

## Storage Types \{#storage-types}

| Storage | Provisioner | When the node of a Pod is lost | Expansion | Snapshot |
| --- | --- | --- | --- | --- |
| **TopoLVM** ([LVM Storage](/storage/storagesystem_topolvm/index.mdx)) | `topolvm.cybozu.com` | The volume stays on that node. | Supported | Depends on the LVM Storage configuration |
| **Local Storage** ([Local Storage](/storage/local_storage/index.mdx)) | Static volumes from Alauda Container Platform Local Disk Provisioner | The volume stays on that node. | Not stated | Not stated |
| **Ceph RBD** ([Ceph Distributed Storage](/storage/storagesystem_ceph/index.mdx)) | `rook-ceph.rbd.csi.ceph.com` | The volume follows the Pod. | Supported | Supported |
| **CephFS** ([Ceph Distributed Storage](/storage/storagesystem_ceph/index.mdx)) | `rook-ceph.cephfs.csi.ceph.com` | The volume follows the Pod. | Supported | Supported |
| **NFS** ([Creating an NFS Shared Storage Class](/configure/storage/functions/nfs_storageclass.mdx)) | `nfs.csi.k8s.io` | The volume follows the Pod. | Not supported | Not supported |
| **Enterprise SAN**: a storage area network array from a third-party vendor | The vendor's CSI driver | The volume follows the Pod. | Depends on the driver | Depends on the driver |
| **Object storage**: Ceph Object Storage, or enterprise object storage from a third-party vendor | Not a storage class | Not applicable | Not applicable | Not applicable |

In production, use TopoLVM device classes whose **Provision Type** is **Thick** (`type: thick` in the lvmd configuration). On this page, TopoLVM means a Thick device class. A **Thin** device class allows over-provisioning: its volumes share the physical space of a thin pool, so a volume can run out of space before it reaches its requested size.

For the storage systems that the platform provides, see [Overview](/storage/overview.mdx). For access modes, expansion, and snapshots per storage class, see [Access Modes and Volume Modes](/configure/storage/concepts/selection.mdx). To make the platform recognize the capabilities of a third-party storage class, see [Third-Party Storage Capability Annotation Guide](/configure/storage/how_to/third_mask.mdx).

This page uses two terms:

- **The volume follows the Pod**: when a Pod is rescheduled to another node, its volume is attached to that node. TopoLVM and Local Storage volumes are bound to the disks of one node and do not follow the Pod.
- **Copies**: the total number of copies of the data, including the primary. For example, OpenSearch `number_of_replicas: 1` and a Redis instance with one replica each mean **2 copies**.

## Storage Classes in the Console \{#console}

The instance forms of MySQL-MGR, PostgreSQL, Redis, Kafka, and RabbitMQ list only the storage classes whose provisioner is allowed for that component, and by default only TopoLVM (`topolvm.cybozu.com`) is allowed. To offer another storage class, such as an enterprise SAN or Ceph RBD, an administrator adds its provisioner to the `middleware-sc-cm` ConfigMap in the `cpaas-system` namespace of the `global` cluster. The entries are added to the default list. For example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: middleware-sc-cm
  namespace: cpaas-system
data:
  middleware_sc_map.yaml: |
    Redis:
      instance:
        - rook-ceph.rbd.csi.ceph.com
```

Use the component keys `MGR`, `PostgreSQL`, `Redis`, `Kafka`, and `RabbitMQ`, and the `provisioner` value of the storage class. Do not edit the `middleware-sc-cm-base` ConfigMap, which is the shipped default.

- The `Redis.backup` key controls the storage classes offered for Redis PVC backups. From Alauda Container Platform Data Services Essentials v4.4.1, its default list contains NFS, CephFS, and TopoLVM.
- The list has no entries for Valkey, CloudNativePG, ClickHouse, OpenSearch, or Milvus. Valkey has no Web Console. Set `spec.storage.storageClassName` in its custom resource.

## Relational Databases \{#relational}

This section covers **MySQL-MGR, PostgreSQL, and CloudNativePG**.

### Recommendations by Scenario

| Scenario | Recommended | Secondary | Last resort | Avoid | Why |
| --- | --- | --- | --- | --- | --- |
| **Multi-replica production database** | TopoLVM | Enterprise SAN | Ceph RBD | NFS, CephFS | TopoLVM gives each replica its own failure domain and the lowest latency, but a replica is rebuilt in full after its node or disk is lost permanently. The MySQL-MGR documentation recommends it, and a CloudNativePG configuration sample uses it for production.<br />A replica on a SAN survives the loss of its node and only catches up, but all replicas on one array share it as a failure domain. See the notes for when to prefer it.<br />On Ceph RBD, all replicas share one Ceph failure domain, and Ceph replicates every write again.<br />NFS and CephFS are file storage. CloudNativePG asks for a block-mode storage class, and none of the three products recommends file storage. |
| **Single-instance database** | Enterprise SAN | Ceph RBD | — | TopoLVM, NFS, CephFS | With one copy, the data survives a node loss only if the volume follows the Pod. |
| **Development and testing** | TopoLVM, or the default storage class | — | — | — | Data loss is acceptable. |
| **Backup** | Enterprise object storage | Ceph Object Storage | — | Any storage on the same device as the primary data | Where the product supports it, register the target in [Backup Management](/appservice/unified-om/backup-mgt/index.mdx), also called **Backup Center**. Replicas copy an accidental deletion, and a snapshot on the same array or node is lost with that array or node. If the primary data is in Ceph, back up outside that Ceph cluster, which a site with only Ceph cannot do. |

### Notes

- MySQL-MGR on storage other than TopoLVM, including an enterprise SAN, Ceph RBD, and NFS, requires MySQL-MGR v4.4.1 or later, because earlier versions cannot initialize the data directory on such volumes. MySQL-MGR is validated on TopoLVM, Ceph RBD, and local persistent volumes, so validate it on your SAN before going live.
- Prefer the SAN over TopoLVM only when a full rebuild of a replica of the largest database takes longer than you can run with one replica fewer, the SAN meets your commit latency requirement in tests, and you accept the array as a failure domain shared by all replicas.
- To spread replicas over arrays, use CSI topology and Pod anti-affinity. With two arrays, one array still holds a majority of a 3-member MySQL-MGR cluster, so losing it stops writes. To survive the loss of any one array, use three arrays.
- A TopoLVM volume cannot span nodes, so the data of each replica must fit in the volume group of one node.
- MySQL-MGR places at most one member on each node by default, so an N-member cluster needs at least N schedulable nodes, and one more for a Pod to move to after a node loss.

### Settings for RPO = 0 \{#rpo-zero}

For RPO = 0, configure synchronous replication. Run at least 3 instances, so that losing one replica does not stop writes.

- MySQL-MGR: 3 or 5 members. A transaction commits only after a majority of members agree on it, and writes stop when a majority is lost.
- PostgreSQL: set `spec.patroni.synchronous_mode` and `spec.patroni.synchronous_mode_strict` to `true`. With `synchronous_mode` alone, Patroni falls back to asynchronous replication when no synchronous standby is left.
- CloudNativePG: configure `spec.postgresql.synchronous` (`method` and `number`), and leave `dataDurability` unset or set to `required`. Do not set it to `preferred`.

With these settings, PostgreSQL and CloudNativePG pause writes when not enough synchronous standbys are available.

### Recommendations by Scenario

| Scenario | Recommended | Secondary | Last resort | Avoid | Why |
| --- | --- | --- | --- | --- | --- |

### Notes

- With asynchronous replication, an acknowledged write may exist on only one copy and is lost on a failover, whatever the storage.
- For a component with one copy, consider adding copies, for example a higher Kafka replication factor or RabbitMQ quorum queues, so that TopoLVM becomes an option.
- For RabbitMQ without message loss, also use publisher confirms and manual consumer acknowledgements.
- `insert_quorum` is a ClickHouse user setting, set in a profile or on each insert, and the operator does not set it. With 2 replicas per shard and `insert_quorum` 2, inserts stop while one replica is down.
- Put ClickHouse Keeper or ZooKeeper on SSDs or NVMe. They commit through `fsync`, and slow disks show up as replication and insert latency.
- Size ClickHouse volumes with free space for merges. On TopoLVM, also keep free space in the volume group of each node for later expansion.
- RabbitMQ instances created in the console place at most one node on each host. If the cluster has no more nodes than replicas, add nodes.

## Pre-Production Checks \{#verify}

Test the storage with the workload of the instance. The product documentation gives no latency or throughput thresholds, so compare the results with your own requirements.

- **Commit latency** for databases, ClickHouse Keeper or ZooKeeper, and Milvus etcd, especially on Secondary or Last resort storage. MySQL-MGR selects its parameter template by storage medium, and PostgreSQL recommends SSD storage with high IOPS.
- **Throughput** on Ceph RBD for components with multiple copies.
- **Rebuild time** of a replica of the largest instance on TopoLVM, compared with how long you can run with one copy fewer.
- **Node loss**: shut down a node that runs a member, and check that the instance recovers as described in [Node and Disk Loss](#node-loss).
- **Restore**: restore a backup into a new instance, and repeat this regularly.

## Node and Disk Loss \{#node-loss}

| Storage | What happens |
| --- | --- |
| TopoLVM, Local Storage | The volume stays on the lost node. The Pod can start on another node only after its persistent volume claim is deleted, and it then gets a new, empty volume. Whether the replica is rebuilt automatically depends on the component. |
| Ceph RBD, CephFS, NFS, enterprise SAN | The volume is attached to the node that the Pod moves to. After an unexpected node shutdown, the volume might not detach automatically. See [Detach CSI Volumes After Non-Graceful Node Shutdown](/configure/storage/trouble_shooting/detach_csi_volumes_non_graceful_shutdown.mdx). |

Before you delete a persistent volume claim on TopoLVM or Local Storage, check what the product documents about recovery:

| Product | Product documentation |
| --- | --- |
| MySQL-MGR | Persistent volumes bound to a lost node cannot be migrated. Recovery requires manual reprovisioning and data resync. See <ExternalSiteLink name="mysql-mgr" href="/how_to/40-deploy-without-topolvm.html" children="Deploy MySQL-MGR Without TopoLVM" />. |
| CloudNativePG | Replacing a persistent volume claim was tested and completed with RPO = 0. Node shutdown and reboot were not tested for v1.30.1-acp.1. See <ExternalSiteLink name="cnpg" href="/release_notes.html" children="Release Notes" />. |
| Valkey | Do not delete a persistent volume claim until its data-retention requirement and recovery procedure are known. See <ExternalSiteLink name="valkey" href="/trouble_shooting/10-instance-not-ready.html" children="Diagnose an instance that is not Ready" />. |
| ClickHouse Keeper | Losing one of 3 members is tolerated. Losing two makes replicated tables read-only until a second member is back. Deleting the Keeper volumes makes the tables read-only until their replicas are registered again. See <ExternalSiteLink name="clickhouse" href="/how_to/deploy_keeper_quorum.html" children="Deploy a Keeper quorum" />. |
| OpenSearch | The Pod cannot start elsewhere until the volume is removed. Keep `number_of_replicas` at 1 or more so that the cluster keeps all data. See <ExternalSiteLink name="opensearch" href="/functions/storage.html" children="Storage" />. |
| PostgreSQL, Redis, Kafka, RabbitMQ, ClickHouse data replicas, Milvus | Not documented. Test the recovery before you rely on TopoLVM. For RabbitMQ, include quorum queue membership, which may need to be repaired by hand. |
