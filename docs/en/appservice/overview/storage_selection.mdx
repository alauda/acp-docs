# Storage Selection

Choose the storage for an Alauda Application Services instance before you create it. The storage class of a persistent volume claim cannot be changed after the claim is created, so moving an instance to other storage means creating a new instance and moving the data. For example, the OpenSearch operator rejects a storage class change on an existing node pool, and the Valkey operator provides no volume migration.

This page covers high availability and backup inside a single <Term name="product" /> (<Term name="productShort" />) cluster in a single data center. Cross-data-center disaster recovery is out of scope.

## Selection Procedure

1. List the storage available on site. See [Storage Types](#storage-types). Count enterprise storage only if it already exists on site or is within the budget.
2. Find the row of each instance in [Relational Databases](#relational), [Middleware That Replicates Data Itself](#replicated), or [Milvus](#milvus). The row gives the storage for its data and its backup.
3. If the storage is not TopoLVM, [make it selectable in the console](#console).
4. Before going live, run the [pre-production checks](#verify).

In the **Data storage** columns, "or" joins choices that are equally recommended, and "then" gives the order of preference. A **last resort** works with the limits described in [Storage Limits](#limits), so test it first. Whether a product is validated on a storage type is stated in the **Notes** columns.

This page uses two terms:

- **The volume follows the Pod**: when a Pod is rescheduled to another node, its volume is attached to that node. TopoLVM and Local Storage volumes are bound to the disks of one node and do not follow the Pod.
- **Copies**: the total number of copies of the data, including the primary. For example, OpenSearch `number_of_replicas: 1` and a Redis instance with one replica each mean **2 copies**.

### Storage Limits \{#limits}

**TopoLVM**

- A volume stays on its node. A node failure makes the volume unavailable, and a disk failure can cause data loss. After a node or disk is lost permanently, the Pod starts on another node only after its persistent volume claim is deleted, and the replica must then be rebuilt from the other copies.
- A volume cannot span nodes, so the data of each replica must fit in the volume group of one node. Keep free space in each volume group for later expansion.
- In production, use device classes whose **Provision Type** is **Thick** (`type: thick` in the lvmd configuration). A **Thin** device class allows over-provisioning: its volumes share the physical space of a thin pool, so a volume can run out of space before it reaches its requested size. On this page, TopoLVM means a Thick device class.

**Enterprise SAN**

- All replicas on one array share it as a failure domain. To spread replicas over arrays, use CSI topology and Pod anti-affinity. With two arrays, one array still holds a majority of a 3-member cluster, so use three arrays to survive the loss of any one array.
- After an unexpected node shutdown, a volume might not detach automatically. See [Detach CSI Volumes After Non-Graceful Node Shutdown](/configure/storage/trouble_shooting/detach_csi_volumes_non_graceful_shutdown.mdx).
- The product documentation names no validated SAN, and MySQL-MGR is not validated on one. Test the array with the product before going live.

**Ceph RBD**

- All replicas share one Ceph failure domain, and Ceph replicates every write again. With the default three-replica pool, 3 copies of a component become 9 copies on disk.

## Storage Classes in the Console \{#console}

The instance forms of MySQL-MGR, PostgreSQL, Redis, Kafka, and RabbitMQ list only the storage classes whose provisioner is allowed for that component, and by default only TopoLVM (`topolvm.cybozu.com`) is allowed. To offer another storage class, such as an enterprise SAN or Ceph RBD, an administrator adds its provisioner to the `middleware-sc-cm` ConfigMap in the `cpaas-system` namespace of the `global` cluster. The entries are added to the default list. For example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: middleware-sc-cm
  namespace: cpaas-system
data:
  middleware_sc_map.yaml: |
    Redis:
      instance:
        - rook-ceph.rbd.csi.ceph.com
```

Use the component keys `MGR`, `PostgreSQL`, `Redis`, `Kafka`, and `RabbitMQ`, and the `provisioner` value of the storage class. Do not edit the `middleware-sc-cm-base` ConfigMap, which is the shipped default.

- The `Redis.backup` key controls the storage classes offered for Redis PVC backups. From Alauda Container Platform Data Services Essentials v4.4.1, its default list contains NFS, CephFS, and TopoLVM.
- The list has no entries for Valkey, CloudNativePG, ClickHouse, OpenSearch, or Milvus. Valkey has no Web Console. Set `spec.storage.storageClassName` in its custom resource.

## Relational Databases \{#relational}

This section covers **MySQL-MGR, PostgreSQL, and CloudNativePG**.

- **Multiple replicas**: TopoLVM is the default, and the MySQL-MGR documentation recommends it. Prefer an enterprise SAN only when a full rebuild of a replica of the largest database takes longer than you can run with one replica fewer, the SAN meets your commit latency requirement in tests, and you accept the array as a shared failure domain. On a SAN, a replica survives the loss of its node and only catches up instead of being rebuilt.
- **A single member or instance**: for testing, TopoLVM or the default storage class. In production, the volume must follow the Pod to a replacement node.
- **NFS and CephFS**: do not use them for databases. They are file storage, CloudNativePG asks for a block-mode storage class, and none of the three products recommends file storage.
- **RPO = 0**: configure synchronous replication as given in the Notes column, and run at least 3 instances, so that losing one replica does not stop writes.
- **Backup**: back up to enterprise object storage, or to Ceph Object Storage as the secondary choice, on a different device from the primary data. Where the product supports it, register the target in [Backup Management](/appservice/unified-om/backup-mgt/index.mdx), also called **Backup Center**. Replicas copy an accidental deletion, and a snapshot on the same array or node is lost with that array or node. If the primary data is in Ceph, back up outside that Ceph cluster, which a site with only Ceph cannot do.

## Middleware That Replicates Data Itself \{#replicated}

This section covers **Redis, Valkey, Kafka, RabbitMQ, ClickHouse, and OpenSearch**.

- **Multiple copies**: TopoLVM and an enterprise SAN are both recommended. The component rebuilds a lost replica from the other copies, so choose by what is on site and by the [limits](#limits) of each. With 2 copies, a SAN shortens the time during which a single copy carries the data while a replica is rebuilt.
- **One copy only**: the volume must follow the Pod, so use an enterprise SAN, then Ceph RBD. Consider adding copies instead, for example a higher Kafka replication factor or RabbitMQ quorum queues, so that TopoLVM becomes an option.
- **Asynchronous replication**: an acknowledged write may exist on only one copy and is lost on a failover, whatever the storage.
- **NFS and CephFS**: this page does not evaluate them for the data volumes of these components.
- **Backup**: as for [relational databases](#relational), where the product provides backup.

The product documentation names no storage type for these components unless a row says otherwise.

## Pre-Production Checks \{#verify}

Test the storage with the workload of the instance. The product documentation gives no latency or throughput thresholds, so compare the results with your own requirements.

- **Commit latency** for databases, ClickHouse Keeper or ZooKeeper, and Milvus etcd, especially on an enterprise SAN or Ceph RBD. MySQL-MGR selects its parameter template by storage medium, and PostgreSQL recommends SSD storage with high IOPS.
- **Throughput** on Ceph RBD for components with multiple copies.
- **Rebuild time** of a replica of the largest instance on TopoLVM, compared with how long you can run with one copy fewer.
- **Node loss**: shut down a node that runs a member, and check that the instance recovers as described in [Node and Disk Loss](#node-loss).
- **Restore**: restore a backup into a new instance, and repeat this regularly.

## Node and Disk Loss \{#node-loss}

On TopoLVM and Local Storage, the Pod of a lost node starts elsewhere only after its persistent volume claim is deleted. Before you delete it, check what the product documents about recovery:

| Product | Product documentation |
| --- | --- |
| MySQL-MGR | Persistent volumes bound to a lost node cannot be migrated. Recovery requires manual reprovisioning and data resync. See <ExternalSiteLink name="mysql-mgr" href="/how_to/40-deploy-without-topolvm.html" children="Deploy MySQL-MGR Without TopoLVM" />. |
| CloudNativePG | Replacing a persistent volume claim was tested and completed with RPO = 0. Node shutdown and reboot were not tested for v1.30.1-acp.1. See <ExternalSiteLink name="cnpg" href="/release_notes.html" children="Release Notes" />. |
| Valkey | Do not delete a persistent volume claim until its data-retention requirement and recovery procedure are known. See <ExternalSiteLink name="valkey" href="/trouble_shooting/10-instance-not-ready.html" children="Diagnose an instance that is not Ready" />. |
| ClickHouse Keeper | Losing one of 3 members is tolerated. Losing two makes replicated tables read-only until a second member is back. Deleting the Keeper volumes makes the tables read-only until their replicas are registered again. See <ExternalSiteLink name="clickhouse" href="/how_to/deploy_keeper_quorum.html" children="Deploy a Keeper quorum" />. |
| OpenSearch | The Pod cannot start elsewhere until the volume is removed. Keep `number_of_replicas` at 1 or more so that the cluster keeps all data. See <ExternalSiteLink name="opensearch" href="/functions/storage.html" children="Storage" />. |
| PostgreSQL, Redis, Kafka, RabbitMQ, ClickHouse data replicas, Milvus | Not documented. Test the recovery before you rely on TopoLVM. For RabbitMQ, include quorum queue membership, which may need to be repaired by hand. |
