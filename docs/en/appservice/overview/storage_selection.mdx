# Storage Selection

Choose the storage for an Alauda Application Services instance before you create it. The storage class of a persistent volume claim cannot be changed after the claim is created, so moving an instance to other storage means creating a new instance and moving the data. For example, the OpenSearch operator rejects a storage class change on an existing node pool, and the Valkey operator provides no volume migration.

This page covers high availability and backup inside a single <Term name="product" /> (<Term name="productShort" />) cluster in a single data center. Cross-data-center disaster recovery is out of scope.

## Selection Procedure

1. List the storage available on site. See [Storage Types](#storage-types).
2. Look up the product of each instance in [Relational Databases](#relational), [Middleware That Replicates Data Itself](#replicated), or [Milvus](#milvus). The topology of the instance gives its scenario, and the scenario gives the recommended storage.
3. If the storage is not TopoLVM, [make it selectable in the console](#console).
4. Before going live, run the [pre-production checks](#verify).
5. Plan backup to a different device. See [Backup](#backup).

The tables use the following status words. They express recommendations. Whether a product is validated on a storage type is stated in the **What the product documentation states** columns and in the notes.

- **Recommended**: the default choice.
- **Secondary**: the choice when the recommended storage is not available or does not fit your environment.
- **Last resort**: works, with the drawback given in the table. Test it before going live.
- **Not recommended**: avoid in production for this scenario.
- **Do not use**: unsuitable for this scenario.
- **Not needed**: the scenario does not call for this storage.

## Storage Types \{#storage-types}

| Storage | Provisioner | When the node of a Pod is lost | Expansion | Snapshot |
| --- | --- | --- | --- | --- |
| **TopoLVM** ([LVM Storage](/storage/storagesystem_topolvm/index.mdx)) | `topolvm.cybozu.com` | The volume stays on that node. | Supported | Depends on the LVM Storage configuration |
| **Local Storage** ([Local Storage](/storage/local_storage/index.mdx)) | The StorageClass that the operator creates | The volume stays on that node. | Not stated | Not stated |
| **Ceph RBD** ([Ceph Distributed Storage](/storage/storagesystem_ceph/index.mdx)) | `rook-ceph.rbd.csi.ceph.com` | The volume follows the Pod. | Supported | Supported |
| **CephFS** ([Ceph Distributed Storage](/storage/storagesystem_ceph/index.mdx)) | `rook-ceph.cephfs.csi.ceph.com` | The volume follows the Pod. | Supported | Supported |
| **NFS** ([Creating an NFS Shared Storage Class](/configure/storage/functions/nfs_storageclass.mdx)) | `nfs.csi.k8s.io` | The volume follows the Pod. | Not supported | Not supported |
| **Enterprise SAN**: a storage area network array from a third-party vendor | The vendor's CSI driver | The volume follows the Pod. | Depends on the driver | Depends on the driver |
| **Object storage**: Ceph Object Storage, or enterprise object storage from a third-party vendor | Not a storage class | Not applicable | Not applicable | Not applicable |

In production, use TopoLVM device classes whose **Provision Type** is **Thick** (`type: thick` in the lvmd configuration). On this page, TopoLVM means a Thick device class. A **Thin** device class allows over-provisioning: its volumes share the physical space of a thin pool, so a volume can run out of space before it reaches its requested size.

For the storage systems that the platform provides and their typical uses, see [Overview](/storage/overview.mdx). For the access modes and the expansion and snapshot support of each storage class, see [Access Modes and Volume Modes](/configure/storage/concepts/selection.mdx). To make the platform recognize the capabilities of a third-party storage class, see [Third-Party Storage Capability Annotation Guide](/configure/storage/how_to/third_mask.mdx).

This page uses the following terms:

- **The volume follows the Pod**: when a Pod is rescheduled to another node, its volume is attached to that node. TopoLVM and Local Storage volumes are bound to the disks of one node and do not follow the Pod.
- **Copies**: the total number of copies of the data, including the primary. Products count differently. For example, OpenSearch `number_of_replicas: 1` and a Redis instance with one replica each mean **2 copies**.

## Storage Classes in the Console \{#console}

The instance forms of MySQL-MGR, PostgreSQL, Redis, Kafka, and RabbitMQ list only the storage classes whose provisioner is allowed for that component. By default, only TopoLVM (`topolvm.cybozu.com`) is allowed for instances. To select another storage class recommended on this page, such as an enterprise SAN or Ceph RBD, an administrator adds its provisioner to the `middleware-sc-cm` ConfigMap in the `cpaas-system` namespace of the `global` cluster. The entries are added to the default list and do not replace it. For example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: middleware-sc-cm
  namespace: cpaas-system
data:
  middleware_sc_map.yaml: |
    Redis:
      instance:
        - rook-ceph.rbd.csi.ceph.com
```

Use the component keys `MGR`, `PostgreSQL`, `Redis`, `Kafka`, and `RabbitMQ`, and the `provisioner` value of the storage class. Do not edit the `middleware-sc-cm-base` ConfigMap, which is the shipped default.

- The same list controls the storage classes offered for Redis PVC backups, under `Redis.backup`. From Alauda Container Platform Data Services Essentials v4.4.1, the default list for backups contains NFS, CephFS, and TopoLVM.
- The list has no entries for Valkey, CloudNativePG, ClickHouse, OpenSearch, or Milvus. Valkey has no Web Console. Set `spec.storage.storageClassName` in its custom resource.

## Relational Databases \{#relational}

This section covers **MySQL-MGR, PostgreSQL, and CloudNativePG**.

### Recommendations by Scenario

| Scenario | TopoLVM | Enterprise SAN | Ceph RBD | NFS or CephFS | Why |
| --- | --- | --- | --- | --- | --- |
| **Multi-replica production database** | Recommended | Secondary | Last resort | Do not use | TopoLVM gives each replica its own failure domain and the lowest latency, and the MySQL-MGR and CloudNativePG documentation recommends it. After its node or disk is lost permanently, a replica on TopoLVM is rebuilt in full.<br />A replica on a SAN survives the loss of its node and only catches up on missing changes. All replicas on one array share it as a failure domain. The notes say when to prefer the SAN.<br />On Ceph RBD, all replicas share one Ceph failure domain, and Ceph replicates every write again.<br />NFS and CephFS are shared file storage. CloudNativePG asks for a block-mode storage class, and none of the three products recommends file storage. |
| **Single-instance database** | Not recommended | Recommended | Secondary | Do not use | With one copy, the data survives a node loss only if the volume follows the Pod to a replacement node. |
| **Development and testing** | Recommended | Not needed | Not needed | Not needed | Data loss is acceptable. The default storage class also works. |

For RPO = 0, configure synchronous replication. See [Settings for RPO = 0](#rpo-zero).

### Topologies by Product

| Product | Multi-replica production database | One member or instance | What the product documentation states |
| --- | --- | --- | --- |
| **MySQL-MGR** | 3 or more members, up to 9. A transaction commits after a majority of members agree. The console offers Single Master, the default, and Multi-Master. | 1 member, for testing | TopoLVM is recommended, and the console asks for a TopoLVM storage class. v4.4.1 fixed instances that failed to start on Ceph RBD and NFS. A procedure for local persistent volumes is documented. See <ExternalSiteLink name="mysql-mgr" href="/functions/01-create.html" children="Create Instance" /> and <ExternalSiteLink name="mysql-mgr" href="/how_to/40-deploy-without-topolvm.html" children="Deploy MySQL-MGR Without TopoLVM" />. |
| **PostgreSQL** | Primary-Replica Replication with 3 or more instances. Replication is asynchronous unless `synchronous_mode` is enabled, and it is disabled by default. | Single Node, for development and testing | A storage class with dynamic provisioning, SSD storage with high IOPS, and at least 50 GB. No storage type is named. See <ExternalSiteLink name="postgresql" href="/how_to/configure_ha_cluster.html" children="Configuring a High Availability PostgreSQL Cluster" />. |
| **CloudNativePG** | 3 or more instances, replicated by streaming WAL with no shared storage. ### Notes

- MySQL-MGR on storage other than TopoLVM, including an enterprise SAN, Ceph RBD, and NFS, requires MySQL-MGR v4.4.1 or later. Earlier versions cannot initialize the data directory on such volumes.
- MySQL-MGR is validated on TopoLVM, Ceph RBD, and local persistent volumes. Validate it on your SAN before going live.
- Prefer the SAN over TopoLVM only when all of these hold:
  - A full rebuild of a replica of the largest database takes longer than you can run with one replica fewer.
  - The SAN meets your commit latency requirement in tests, and the array has the capacity.
  - You accept the array as a failure domain shared by all replicas, or you spread the replicas over arrays as described in the next note.
- With two arrays, place the replicas of each database on different arrays by using CSI topology and Pod anti-affinity. One array still holds a majority of a 3-member MySQL-MGR cluster, so losing that array stops writes. To survive the loss of any one array, use three arrays.
- A TopoLVM volume cannot span nodes, so the data of each replica must fit in the volume group of one node.
- MySQL-MGR places at most one member on each node by default, so an N-member cluster needs at least N schedulable nodes. With required anti-affinity, a Pod cannot move to a node that already runs another replica, on any storage. If the cluster has no more nodes than replicas, add nodes.

### Settings for RPO = 0 \{#rpo-zero}

Configure synchronous replication and run at least 3 instances, so that losing one replica does not stop writes.

- MySQL-MGR: 3 or 5 members. A transaction commits only after a majority of members agree on it, and writes stop when a majority is lost.
- PostgreSQL: set `spec.patroni.synchronous_mode` and `spec.patroni.synchronous_mode_strict` to `true`. With `synchronous_mode` alone, Patroni falls back to asynchronous replication when no synchronous standby is left.
- CloudNativePG: configure `spec.postgresql.synchronous` (`method` and `number`), and leave `dataDurability` unset or set to `required`. Do not set it to `preferred`.

With these settings, PostgreSQL and CloudNativePG pause writes when not enough synchronous standbys are available.

## Middleware That Replicates Data Itself \{#replicated}

This section covers **Redis, Valkey, Kafka, RabbitMQ, ClickHouse, and OpenSearch**.

### Recommendations by Scenario

| Scenario | TopoLVM | Enterprise SAN | Ceph RBD | Why |
| --- | --- | --- | --- | --- |
| **Multiple copies** | Recommended | Secondary | Last resort | A lost replica is rebuilt from the other copies. TopoLVM gives the lowest latency and one failure domain per replica, and adds no second layer of redundancy.<br />With 2 copies, a single copy carries the data while a replica is rebuilt. A replica on a SAN survives the loss of its node, which shortens that window.<br />Ceph RBD replicates every write again inside Ceph. |
| **One copy only** | Not recommended | Recommended | Secondary | As for a single-instance database, the volume must follow the Pod to a replacement node. |
| **No persistence** | No persistent volume | No persistent volume | No persistent volume | The data can be regenerated. |

This page does not evaluate NFS or CephFS for the data volumes of these components.

### Notes

- With asynchronous replication, an acknowledged write may exist on only one copy and is lost on a failover, whatever the storage. Use synchronous or majority writes where the product supports them, or accept the risk.
- For a component with one copy, consider adding copies, for example a higher Kafka replication factor or RabbitMQ quorum queues, so that TopoLVM becomes an option.
- Message queues that must not lose messages:
  - Kafka: replication factor 3, `min.insync.replicas=2`, and producer `acks=all`.
  - RabbitMQ: 3 or 5 nodes, quorum queues or streams, publisher confirms, and manual consumer acknowledgements.
- `insert_quorum` is a ClickHouse user setting, set in a profile or on each insert. The operator does not set it. With 2 replicas per shard and `insert_quorum` 2, inserts stop while one replica is down.
- Put ClickHouse Keeper or ZooKeeper on SSDs or NVMe. They commit through `fsync`, and slow disks show up as replication and insert latency.
- Size ClickHouse volumes with free space for merges, on any storage. On TopoLVM, also keep free space in the volume group of each node, so that the volumes can be expanded later.
- RabbitMQ instances created in the console place at most one node on each host. If the cluster has no more nodes than replicas, add nodes.

## Pre-Production Checks \{#verify}

Test the storage with the workload of the instance. The product documentation gives no latency or throughput thresholds, so compare the results with your own requirements.

- **Commit latency** for databases, ClickHouse Keeper or ZooKeeper, and Milvus etcd, especially on storage marked Secondary or Last resort. The product documentation asks for fast storage: MySQL-MGR selects its parameter template by storage medium, PostgreSQL recommends SSD storage with high IOPS, and Redis AOF persistence needs high-performance storage.
- **Throughput** on Ceph RBD for components with multiple copies.
- **Rebuild time** of a replica of the largest instance on TopoLVM, compared with how long you can run with one copy fewer.
- **S3 conditional writes** on the object storage of Milvus with Woodpecker.
- **Node loss**: shut down a node that runs a member, and check that the instance recovers as described in [Node and Disk Loss](#node-loss).
- **Restore**: restore a backup into a new instance, and repeat this regularly.

## Node and Disk Loss \{#node-loss}

| Storage | What happens |
| --- | --- |
| TopoLVM, Local Storage | The volume stays on the lost node. The Pod can start on another node only after its persistent volume claim is deleted, and it then gets a new, empty volume. Whether the replica is then rebuilt automatically depends on the component. |
| Ceph RBD, CephFS, NFS, enterprise SAN | The volume is attached to the node that the Pod moves to. After an unexpected node shutdown, the volume might not detach automatically. See [Detach CSI Volumes After Non-Graceful Node Shutdown](/configure/storage/trouble_shooting/detach_csi_volumes_non_graceful_shutdown.mdx). |

| Product | What the product documentation states |

| CloudNativePG | Replacing a persistent volume claim was tested and completed with RPO = 0. Node shutdown and reboot scenarios were not tested for v1.30.1-acp.1. See <ExternalSiteLink name="cnpg" href="/release_notes.html" children="Release Notes" />. |

## Backup \{#backup}

Back up every production component that supports backup to a different device from the primary data, preferably to object storage registered in [Backup Management](/appservice/unified-om/backup-mgt/index.mdx), also called **Backup Center**. Replication copies an accidental deletion to every copy, and a snapshot on the same array or node is lost together with that array or node, so neither counts as a backup.

Use enterprise object storage as the backup target, or Ceph Object Storage as the secondary choice. If the primary data is in Ceph, back up outside that Ceph cluster. A site whose only storage is Ceph cannot meet this.

| Product | Backup | Documentation |
| --- | --- | --- |

| PostgreSQL | Scheduled and manual backups to S3-compatible object storage, with PITR. A restore creates a new instance. | <ExternalSiteLink name="postgresql" href="/functions/15_back_restore.html" children="Backup and Restore" /> |
| CloudNativePG | Backups and PITR through the Barman Cloud plugin, to S3-compatible object storage. Volume snapshot backups also exist. They need a storage class with snapshot support and count as backups only when the snapshots are stored off the primary device. They were not tested in v1.30.1-acp.1. | <ExternalSiteLink name="cnpg" href="/how_to/ops-runbook.html" children="Operations Runbook" /> |

## Rationale

- TopoLVM volumes stay on one node. In production, use them only for components that keep at least 2 copies of the data themselves, so that a lost node does not take the only copy with it. Components with one copy need storage whose volume follows the Pod, such as an enterprise SAN or Ceph RBD.
- Replication at the storage layer under a component that already keeps copies multiplies capacity and network traffic. On Ceph RBD with the default three-replica pool, a component with 3 copies stores 9. This is why Ceph RBD is the last resort for components with multiple copies.
- A replica on a SAN survives the loss of its node and only catches up instead of being rebuilt. This helps a large database, whose rebuild copies the whole database, and a component with 2 copies, which runs on one copy during a rebuild. All replicas on one array share it as a failure domain, so the SAN is the secondary choice.
- Consider enterprise storage only when it already exists on site or is within the budget.
