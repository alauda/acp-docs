# Release Notes

Review release notes with the [Kubernetes Support Matrix](./kubernetes-support-matrix.mdx), [Version and Lifecycle](./version-and-lifecycle.mdx), and feature-specific documentation to understand release changes and exact support boundaries.

## 4.5.0

Issued: 2026-11-17

### Features and Enhancements

#### Kubernetes 1.36

<Term name="productShort" /> 4.5 creates new platform-managed clusters on **Kubernetes 1.36**. Before you upgrade the `global` cluster to 4.5, workload clusters created by <Term name="productShort" /> must run Kubernetes 1.36, 1.35, 1.34, or 1.33. The Kubernetes version of imported and registered third-party clusters does not block the `global` cluster upgrade, but the <Term name="productShort" /> components on those clusters must be within the direct upgrade window.

For the version relationships and the Kubernetes, containerd, and etcd versions in each Alauda OS image, see [Kubernetes Support Matrix](./kubernetes-support-matrix.mdx) and [Alauda OS Support Matrix](./alauda_os_support_matrix.mdx#version-mapping).

#### Alauda OS Cluster Upgrades in One Request

On Huawei DCS, Huawei Cloud Stack, VMware vSphere, and Bare Metal clusters that run Alauda OS, one upgrade request now upgrades <Term name="productShort" /> Core, the installed Aligned Extensions, Kubernetes, and Alauda OS. You no longer upgrade Kubernetes on these clusters in a separate manual procedure.

- **Node replacement through every intermediate version** — The platform replaces nodes one at a time and moves the control plane and workers through each intermediate Kubernetes minor version. On Bare Metal, workers are reinstalled only at the target version. Progress is reported in an `InfraClusterVersion` resource, and provider-specific preflight checks run before any node is replaced.
- **Infrastructure providers upgraded with `global`** — The infrastructure providers for Huawei DCS, Huawei Cloud Stack, VMware vSphere, and Bare Metal are Aligned Extensions on the `global` cluster and are upgraded together with it.
- **Kube-OVN and CoreDNS managed by the platform** — The platform installs and upgrades Kube-OVN and CoreDNS on Alauda OS clusters; do not upgrade them by hand. On a cluster upgraded from a version earlier than 4.5, the platform takes them over once the cluster and `global` both run 4.5. The takeover can finish after the upgrade request completes.

Upgrade boundaries for Alauda OS clusters:

- The documented upgrade path starts at <Term name="productShort" /> v4.3.2. For an Alauda OS cluster on an earlier version, contact technical support.
- A cluster with a single control plane node is for testing and cannot be upgraded.

For details, see [Upgrade Overview](../upgrade/overview.mdx#upgrade-steps-by-node-os).

#### Alauda OS Cluster Installation with ACP CLI (Technology Preview)

You describe an Alauda OS `global` cluster or workload cluster in one `install-config.yaml` file and create it with the <Term name="productShort" /> CLI: `ac adm alpha global create` for the `global` cluster, and `ac adm alpha cluster create` for a workload cluster on Huawei DCS, Huawei Cloud Stack, VMware vSphere, or Bare Metal. The CLI validates the configuration, the registry, and the infrastructure before it creates the cluster, replacing the previous step-by-step manifest procedure. The `ac adm alpha` commands are a Technology Preview.

For details, see [Install on Alauda OS](../install/alauda_os/index.mdx) and [Create a Cluster on Alauda OS](../workload_clusters/alauda_os/index.mdx).

#### Alauda OS Node Configuration

- **Machine Configuration included** — Machine Configuration is delivered with every Alauda OS cluster and no longer needs a separate installation. For details, see [Machine Configuration Overview](../configure/machine_config/overview.mdx).
- **Automatic node resource reservation** — The new `KubeletConfig` API reserves CPU, memory, and ephemeral storage for the operating system and Kubernetes components on Alauda OS nodes. On supported clusters, the platform creates the `acp-default-node-reservation` object, which calculates the reservation for each node. You can also set static values for a node pool. For details, see [Configure Node Resource Reservation](../configure/machine_config/node_resource_reservation.mdx).
- **Bare Metal system disk selection** — A Bare Metal host now reports its disks when it registers and waits until you select its system disk. This replaces the fixed installation disk setting. For details, see [Select the System Disk](../workload_clusters/alauda_os/bare-metal/register_hosts.mdx#select-system-disk).

#### Platform Image Registry \{#platform-image-registry}

A new <Term name="productShort" /> 4.5 installation requires an external platform image registry, on Alauda OS and on other operating systems. The platform built-in Registry is no longer deployed on new installations. A `global` cluster upgraded from an earlier version can continue to use it.

- **mirror-registry** — For environments without an image registry, <Term name="productShort" /> provides mirror-registry, a single-instance registry available on the Core Package download page. It is not highly available and is not recommended for production environments. For details, see [Create an Image Registry with mirror-registry](../install/prepare/mirror-registry.mdx).
- **Publishing Extensions** — When you publish Extensions with `violet push`, set `--dest-repo` to the registry that the target cluster uses. For details, see [violet CLI](../ui/cli_tools/violet.mdx#addresses-and-credentials).

For registry requirements, see [Prepare an External Platform Image Registry](../install/prepare/external-platform-image-registry.mdx).

#### Upgrade Preparation

- **Package download based on installed Extensions** — Before an upgrade, you export the Extensions installed on the `global` cluster. The Customer Portal checks the list and downloads the matching target-version packages, including the infrastructure providers.
- **Aligned and Agnostic download scenarios** — For a new installation, the Customer Portal provides the **ACP Common Aligned Extensions** and **ACP Common Agnostic Extensions** scenarios. The **Upgrade from ACP 4.3 or earlier** scenario is needed only when the source version is 4.3 or earlier. For details, see [Download Packages](../extend/download_package.mdx).
- **Direct upgrade window** — A cluster can be upgraded directly to 4.5 from 4.2, 4.3, or 4.4. The window applies to every cluster registered on the `global` cluster, including the <Term name="productShort" /> components on imported and registered third-party clusters.

For the preparation steps, see [Prepare for the Upgrade](../upgrade/pre-upgrade.mdx).

#### Global Cluster Disaster Recovery Upgrades

For a patch upgrade within the same minor version, starting from 4.5.0, you can upgrade the primary `global` cluster and selected workload clusters first, and the standby `global` cluster afterwards. The Global Cluster Disaster Recovery plugin stays installed; synchronization is paused during the upgrades and resumed after the standby is upgraded. There is no disaster recovery protection while synchronization is paused.

For details, see [Upgrade the Standby `global` Cluster After the Workload Clusters](../upgrade/global/upgrade_global_dr_deferred_standby.mdx).

#### Alauda OS Documentation

The Immutable Infrastructure documentation is now part of the <Term name="productShort" /> documentation. Alauda OS installation, workload cluster creation, node management, Machine Configuration, upgrades, the Cluster API and infrastructure provider API references, and the new [Alauda OS Support Matrix](./alauda_os_support_matrix.mdx) are published here. Starting with 4.5, infrastructure provider changes are published in these release notes.

For an overview of the node operating system options, see [Cluster Management Models](./cluster-management-models.mdx#node-operating-system).

#### Networking

- **EnvoyProxy resource quotas** — The `EnvoyProxyResourceQuota` resource limits the total CPU and memory requests that `EnvoyProxy` resources in a namespace can declare. Requests that exceed the quota are rejected. For details, see [Configure EnvoyProxy Resource Quotas](../networking/functions/configure_envoyproxy_resource_quota.mdx).
- **HSTS and custom error pages on Envoy Gateway** — Set the `Strict-Transport-Security` header for a whole Gateway, and return custom error pages by status code. For details, see [Configure HSTS](../networking/how_to/tasks_for_envoy_gateway.mdx#configure_hsts) and [Configure Custom Error Pages](../networking/how_to/tasks_for_envoy_gateway.mdx#configure_custom_error_pages).

#### Storage

- **Ceph OSDs on Local Storage volumes** — In Internal Mode, Ceph can use block persistent volumes provisioned by Local Storage as OSDs instead of host devices. Local Storage can provision these volumes with `LocalVolume` or the new `LocalVolumeSet`. A Ceph cluster cannot mix host devices and Local Storage volumes. For details, see [Deploying in Internal Mode with Local Storage](../storage/storagesystem_ceph/installation/create_service_stand_local_storage.mdx) and [Provision with LocalVolumeSet](../storage/local_storage/functions/local_volume_set.mdx).
- **Ceph Tentacle upgrade** — Alauda Storage provides Ceph 20.2 Tentacle in a separate Operator channel. Existing Ceph clusters are not upgraded automatically; you choose when to upgrade from Ceph 19.2 Squid. The upgrade requires <Term name="productShort" /> 4.5 or later and Linux kernel 5.11 or later on every node that runs Ceph daemons or mounts Ceph volumes, and it cannot be rolled back. For details, see [Upgrade Ceph from Squid (v19) to Tentacle (v20)](../storage/storagesystem_ceph/upgrade/upgrade_squid_to_tentacle.mdx).

#### Virtualization

- **Live migration during node drain** — A new virtualization installation sets the cluster eviction strategy to `LiveMigrateIfPossible`. When a node is drained, for example during maintenance or a cluster upgrade, virtual machines that can be live migrated move to another node, and the others are restarted on another node. An existing installation keeps its current setting; to change it, follow [KubeVirt Node Maintenance](../virtualization/virtualization/virtual_machine/how_to/vm_node_maintenance.mdx).

### Deprecations and Removals

- **Alauda Build of Prometheus Operator removed** — The Alauda Build of Prometheus Operator is no longer shipped in OperatorHub starting in 4.5. On a cluster upgraded from 4.4, an existing installation keeps running but receives no further upgrades. Use Alauda Container Platform Advanced Monitoring or Alauda Container Platform Basic Monitoring instead. Unless you have a specific technology stack requirement, use Alauda Container Platform Advanced Monitoring. For details, see [Monitoring Installation](../observability/monitor/install_monitor.mdx).
- **Platform built-in Registry not deployed on new installations** — A new installation of <Term name="productShort" /> 4.5 requires an external platform image registry. A `global` cluster upgraded from an earlier version can continue to use the platform built-in Registry. For details, see [Platform Image Registry](#platform-image-registry).
- **Cluster upgrade from the Web Console removed** — Upgrading clusters from the Web Console is removed. Use `ac adm upgrade` instead. For details, see [Upgrade Overview](../upgrade/overview.mdx).
- **Huawei DCS and Huawei Cloud Stack cluster creation from the Web Console removed** — Creating Huawei DCS and Huawei Cloud Stack clusters from the Web Console is removed. Use `ac adm alpha cluster create` instead. For details, see [Create a Cluster on Alauda OS](../workload_clusters/alauda_os/index.mdx).
- **Legacy monitoring and alerting APIs remain deprecated** — The `/v2/metrics`, `/v2/alerts`, and `/v1/alerthistories` endpoints, deprecated in 4.4, remain available in 4.5 and are planned for removal in a future release. Migrate to the corresponding `/platform` endpoints. For details, see [Monitoring APIs](../apis/advanced_apis/monitor/index.mdx) and [Alert APIs](../apis/advanced_apis/alert/index.mdx).

### Product and Component Name Changes \{#plugin-name-changes}

Effective with this release, Alauda has renamed a number of products and components. For example, **Alauda Build of Jaeger v2** is now **Alauda Container Platform Distributed Tracing**. The change applies to display names only; package names are not changed.

For the scope of the change and the complete list of previous and new names, see [Product and Component Name Changes](../extend/name-changes.mdx).
